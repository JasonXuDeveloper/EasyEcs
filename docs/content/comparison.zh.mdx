## 变更怎么生效 [#how-changes-are-made]

最大的区别不在速度，而在系统怎么改动 World。Friflo、Arch 和 DefaultEcs 在查询迭代时禁止（或不保护）结构变更，所以系统要
把变更记进命令缓冲，之后再回放：在那之前实体还是旧的组件，效果的先后取决于缓冲何时刷新。EasyEcs 的每个变更都当场生效，
遍历同一张表的途中也一样，并且每个实体仍然最多访问一次：

```csharp title="DeathSystem.cs"
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Die(Entity unit, in Health hp)
    {
        if (hp.Value <= 0) unit.Set(new Dead());   // 当场生效：后面的系统已经能看到尸体
    }
}
```

移植代码都按各库的模型来写（Friflo 和 Arch 在每个记录变更的系统之后回放命令缓冲），所以被测的 World 行为相同。EasyEcs
怎样让即时变更变得便宜，见 [EasyEcs 为什么快](/zh/docs/why-fast#structural-changes)。

## 单项操作 [#operations]

`OperationBenchmark` 把那个 World（100,000 个实体）里的单项操作拆出来，EasyEcs 对 tick 上最接近的 Friflo。每个操作结束
时都把 World 还原。

<BenchChart bench="OperationBenchmark" title="单项操作，100,000 个实体：EasyEcs 与 Friflo.Engine.ECS" />

- **Toggle**（眩晕 5% 的战斗单位，再恢复）是存在位见效的地方：EasyEcs 翻一个位，实体留在原行；Friflo 要通过命令缓冲把
  它搬到另一个原型再搬回来。
- **Instantiate** 生成 5,000 个六组件的 NPC：EasyEcs 一次把 `Prefab` 的行复制到连续的行里，Friflo 逐个克隆 store 里的
  实体（`CloneEntity`）。
- **Entity**：逐实体 job 拿到的句柄由行里 8 字节的 `EntityId` 构造；Friflo 的 `ForEachEntity` 每个实体调一次委托。
- **打平**：两组件、三组件遍历（`Iterate2`、`Iterate3`）和批量实体访问（`EntityBatch`）不分上下。两个库在这里都是走
  紧凑数组，循环受内存带宽限制，与库无关。

## 变更追踪 [#change-tracking]

`ChangeTrackingComparison`：100,000 个实体，每个 tick 有 10 个（安静的 tick）或 1,000 个拿到新的血量，一个系统把变了的
血量复制到副本。有内置功能的库用内置功能（EasyEcs 的 `[Changed<T>]`，DefaultEcs 由 `NotifyChanged<T>()` 喂数据的
`WhenChanged<T>()`），没有的就用比较值的扫描，或写入时加、复制后删的脏标签。

两种写入量下 `[Changed<T>]` 都领先，而且写入处不需要任何代码：通过 `ref` 写就是变更。变化的实体少时脏标签很便宜，但每个

要求每次写入旁边都调 `NotifyChanged<T>()`。跳过是怎么做到的：[变更 tick 摘要](/zh/docs/why-fast#change-ticks)。

## 移除检测 [#removal-detection]

## 并行工作 [#parallel]

`ParallelQueryComparison`：100,000 个代理在所有核心上转向 16 个路点中最近的一个。EasyEcs 用
`[ForEach(Parallel = true)]`，Friflo 用配 `ParallelJobRunner` 的 `QueryJob`，Arch 用 job 调度器上的 `InlineParallelQuery`，
DefaultEcs 用配 `DefaultParallelRunner` 的 `AEntitySetSystem`。

<BenchChart bench="ParallelQueryComparison" title="用所有核心驱动 100,000 个代理" />

**这一项 EasyEcs 没赢**：Friflo（<BenchValue k="parallelQuery.friflo" />）和 Arch 都领先 EasyEcs
（<BenchValue k="parallelQuery.easyecs" />）。它们的调度器有自己的工作线程；EasyEcs 在调用线程加线程池帮手上运行，帮手只在
划算时唤醒。像 BenchmarkDotNet 这样连续测量时，专用工作线程占优；而在服务器 tick 里，两遍之间隔着几毫秒，一组专用的
自旋线程测出来尾延迟更差、每 tick 的 CPU 更多（[D22](/zh/docs/decisions)），所以 EasyEcs 保留线程池。

`ParallelSystemsComparison`：四个互不相关的系统跑 100,000 个实体，串行与并行。同类里只有 DefaultEcs 能把整个系统并行调度
（`ParallelSystem<T>`）；EasyEcs 依据系统生成的访问集组成阶段，所以不会误把两个冲突的系统放进同一个阶段。

## EasyEcs 没赢的地方 [#where-easyecs-does-not-win]

| 对比 | 结果 | 原因 |
| --- | --- | --- |
| [并行查询](#parallel) | Friflo 和 Arch 领先 | 连续运行时，专用工作线程胜过被唤醒的线程池线程；EasyEcs 为服务器 tick 选了线程池 |
| [关系](#indexes-and-relations) | Friflo 略快，在误差之内 | 两个库设计相同 |
| [10 次移除](#removal-detection) | Friflo 的事件领先 | 回调在移除发生时就收集 id；EasyEcs 从摘要里读 |
| [两组件、三组件遍历，批量实体](#operations) | 和 Friflo 打平 | 两边都是紧凑数组；循环受内存带宽限制 |
| [100,000 个里禁用 100 个](#disabling) | 和 Friflo 打平 | 大头是求和，不是切换 |
| Unity 和老运行时 | 不支持 | EasyEcs 只面向 net10.0 |

## 它们的功能在 EasyEcs 里怎么做 [#their-features-in-easyecs]

其他库提供的功能，以及 EasyEcs 怎么完成同样的事。有些以别的名字内置；有些用数据而不是机制来做（EasyEcs 刻意没有事件和
命令缓冲）；少数不提供。[战斗服务器示例](/zh/docs/example) 用到了其中大部分。

| 它们的功能 | 出自 | EasyEcs |
| --- | --- | --- |
| 查询期间变更用的命令缓冲 | Friflo、Arch、DefaultEcs | 不需要：变更当场生效，遍历途中也一样 |
| 线程安全的命令缓冲 | Friflo | 自己持有的队列，由 World 线程上的系统消费（[线程](/zh/docs/guide/threading)） |
| 组件添加 / 移除 / 设置事件 | Friflo、Arch、DefaultEcs | 状态变化就是数据：下一个系统去查询的组件 |
| `WhenChanged` 集合和 `NotifyChanged` | DefaultEcs | `[Changed<T>]`、`QueryFilter.Changed<T>(since)`：`ref` 写入就是变更 |
| `WhenRemoved` 集合、移除事件 | DefaultEcs、Friflo、Arch | `[Removed<T>]`、`QueryFilter.Removed<T>(since)` |
| 预制体实体、克隆 | Friflo、DefaultEcs | `Prefab` 和 `world.Instantiate`；活着的实体用 `entity.Clone()` |
| 标签 | Friflo | 空组件；移除时只翻一个位 |
| 唯一实体、World 组件 | Friflo、DefaultEcs | 单例，作为 `[ForEach]` 参数或 `SingletonRef<T>` |
| 启用 / 禁用实体 | Friflo、DefaultEcs | 一个标签（`[Without<Asleep>]`），或对单个组件用 `Disable<T>()` |
| 系统、分组、顺序 | Friflo、DefaultEcs、Arch.Extended | `EcsSystem`、`[UpdateBefore<T>]` / `[UpdateAfter<T>]`、`ISystemGroup`、`UpdateInterval` |
| struct 查询 job、chunk 遍历 | Arch、Friflo | `IForEach`、`IForEachEntity`、`IForEachBatch`；批量 `[ForEach]` 方法 |
| 并行查询 | Friflo、Arch、DefaultEcs | `[ForEach(Parallel = true)]`、`ForEachParallel`、`ForEachEntityParallel` |
| 并行系统 | DefaultEcs | `WorldOptions.ParallelSystems` |
| 批量变更 | Friflo、Arch | `SetAll`、`RemoveAll`、`DisableAll`、`EnableAll`、`CreateEntities`、`DestroyEntities` |
| 索引组件 | Friflo、DefaultEcs | `IIndexed<TKey>`：`Find`、`TryFind`、`Count`、有序 `Range` |
| 链接和关系 | Friflo | 索引的 `EntityId`，多目标用 `IRelation` |
| 父子层级 | Friflo | `ChildOf`、`world.Children`、级联销毁；不做 transform 传递 |
| 序列化 | Friflo（JSON）、DefaultEcs（文本、二进制） | 二进制 `Save` / `Load`，外加内存里的 `Capture` / `Restore` |
| 系统性能监控 | Friflo | `WorldOptions.MeasureSystems`、`system.Stats` |
| 共享组件（`SetSameAs`） | DefaultEcs | 没有内置：共享数据放进单例，组件里存一个 id |
| Unity、老运行时 | 三者都有 | 不支持：只面向 net10.0 |

## 该选哪个库 [#which-one-to-pick]

| 选 | 什么时候 |
| --- | --- |
| **EasyEcs** | .NET 10 服务器或模拟，状态频繁翻转，想让变更在决定的地方就生效，系统由生成器生成并在编译期检查，内置变更与移除追踪、预制体、索引、关系、存档和快照，每个 tick 零分配。 |
| **Friflo.Engine.ECS** | 需要 Unity 或老运行时、事件或 JSON 序列化，能接受遍历期间用命令缓冲改结构，想要一个快速的通用 ECS。 |
| **Arch** | 需要 Unity 或老运行时，想要基于 chunk 存储的小核心，系统和生成器从 Arch.Extended 里加。 |
| **DefaultEcs** | 需要低至 netstandard1.1，想要响应式集合和内置序列化器，而且 World 小到每 tick 的分配无所谓。 |
