public struct DynamicBuffer<T> : IComponent, ITracked

A list of `T` per entity, held as a component: an inventory, a path, the hits of this tick. Writes go through a `ref` to the component (`ref` parameters of `[ForEach]` methods and jobs, [`Entity.Get`](/en/docs/reference/entity#get)), so they are tracked like any write of an [`ITracked`](/en/docs/reference/itracked) component and `[Changed<DynamicBuffer<T>>]` selects the entities whose list changed. Through `in` or [`Entity.Read`](/en/docs/reference/entity#read) the list is read-only: the mutating methods ([`DynamicBufferExtensions`](/en/docs/reference/dynamicbufferextensions)) take `ref this`, so a write through a read-only reference does not compile. Snapshots copy the elements ([`World.Capture`](/en/docs/reference/world#capture)); a moved row keeps its list. Adding within the capacity allocates nothing.

#### Remarks

A `new DynamicBuffer<T>()` holds no list: each entity's list is made by its first write (reserve room with [`DynamicBufferExtensions.EnsureCapacity`](/en/docs/reference/dynamicbufferextensions#ensurecapacity)), so one value can create many entities; an instance of a prefab whose buffer is empty holds none either, so its first write takes a list from the pool. The list lives in an object the component refers to, and a copy of the component would refer to the same list: the analyzer rejects copies (EECS012), reach the list through the entity.

### `MaxPooledLength` [#maxpooledlength]

```csharp
public static int MaxPooledLength { get; set; }
```

The longest list, in elements, that a destroyed or removed buffer of `T` gives back to the pool, for the next buffer's first write to reuse instead of allocating one, on any thread: the lists the owner thread takes back serve the first writes of a parallel `[ForEach]` too (default: 4,096 bytes of elements, 4,096 for a `byte` or a byte-sized enum). A longer list is left to the GC. Raise it for buffers of one size that come and go in numbers, such as the blocks of chunks loaded and unloaded around players; 0 pools none. The pool holds at most as many lists as died while none were taken, so what it keeps is that peak times this capacity. Process-wide, for every world and thread: set it at startup, before a world uses the type.

**Exceptions**

- `ArgumentOutOfRangeException`: The value is negative.

### `FillPool` [#fillpool]

```csharp
public static void FillPool(int lists);
```

Fill the pool with lists until it holds `lists`, each of [`DynamicBuffer.MaxPooledLength`](/en/docs/reference/dynamicbuffer#maxpooledlength) elements, so the first writes of that many buffers take a list instead of allocating one: a server that knows how many buffers of `T` it keeps at its peak (the chunks around its players) pays for them at startup, and its ticks allocate nothing even while the world grows to that peak. Process-wide, like the pool; lists already in the pool count. O(`lists`) allocations once; nothing when the pool holds enough.

**Exceptions**

- `ArgumentOutOfRangeException`: `lists` is negative.
