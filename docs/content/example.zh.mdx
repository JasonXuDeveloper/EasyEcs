这是一个用上 EasyEcs 全部功能的战斗服，写法就是推荐的写法：组件只放数据，每个系统只做一件事，系统之间互不知道对方，
宿主负责驱动 tick，并在两次 tick 之间回答各种查询。本页逐段讲解这份代码。页面上的每段代码都直接引用自
[`BattleServer.cs`](https://github.com/JasonXuDeveloper/EasyEcs/blob/master/benchmarks/EasyEcs.Benchmark/BattleServer.cs)，
`BattleServerBenchmark` 测的是它，
[`BattleServerTests`](https://github.com/JasonXuDeveloper/EasyEcs/blob/master/tests/EasyEcs.UnitTest/BattleServerTests.cs)
逐个功能验证的也是它。你在这里读到的，就是真正在跑的代码。

## 这个 World 模拟了什么 [#what-it-simulates]

一场有 `units` 个实体的战斗，三分之一是玩家，其余是 NPC，地图 4,096 × 4,096，分成四个区域：

- NPC 先规划要去哪个路点，再朝它移动；所有单位都会移动、按冷却攻击，还可能着火或被冻住。
- 血量归零即死亡。玩家在活着的好友身边复活；NPC 把掉落交给同区域的一名玩家，之后由一个新 NPC 顶替。
- 玩家消耗法力发射投射物，投射物飞行二十个 tick，归属于发射它的玩家。
- 开局时的玩家都是机器人；客户端用账号登录，拿到一个属于自己的英雄。
- 每三个 tick 同步一次变化：血量、刚着火或刚熄灭的状态、NPC 的目标、背包。断开一阵后回来的客户端，从它最后确认的
  tick 开始补发。
- 两次 tick 之间，宿主回答查询：人口统计、最近的玩家、击杀榜、存档、回滚。

每次 `Tick()` 按下面的顺序跑默认分组的系统，每三个 tick 再跑一次 `Replication` 分组：

```mermaid
flowchart LR
    M["规划、转向、<br/>移动、法力、区域"] --> F["战斗、状态、<br/>异常统计、死亡"]
    F --> R["复活、移除、<br/>重生"]
    R --> P["投射物、<br/>回血"]
    P --> C[时钟]
    C -->|每三个 tick| Rep["Replication 分组"]
```

打开 `ParallelSystems` 后，彼此没有顺序约束、访问也不冲突的系统会进同一个阶段同时运行（`ManaSystem` 碰的数据
`PlanningSystem` 一样都不碰，两者就并排跑），结果和逐个运行完全一样。`Schedule()` 能打印出各个阶段，以及每个系统为什么要等。

## 数据 [#data]

### 组件 [#components]

所有组件都是普通的 `record struct`。有四种声明会改变组件的存储方式：`ITracked` 会给组件加一列隐藏的变更 tick
（`Health`、`Burning` 和 `Goal` 需要同步）；`[Group]` 按一个字段的值拆分表（每个 `Zone` 一组表）；`[IndexKey]` 为它维护一个值索引
（击杀榜 `Kills`）；`[UniqueKey]` 让一个键只对应一个实体（`Account`：一个账号只有一个英雄）。这些 `partial` 结构体的
`IGroup` / `IIndexed<TKey>` / `IUniqueIndexed<TKey>` 部分由生成器写出。另有两个声明把 World 的设置写在类型上，每个 World 都照此运行：
`[GroupBy]` 按 `Zone` 分组建表，`[WhenTargetDestroyed]` 在玩家被销毁时把它从指向它的 `Friend` 链接里删掉。`Spawn` 是清理组件，`Loot` 和 `Friend` 是动态缓冲的元素，空结构体就是标签。

### 单例与系统分组 [#singletons]

整场战斗只有一份的状态做成单例：`Battle` 记录各种计数，`Rules` 把战斗规则写成数据，`Waypoints` 是规划和转向都要读的定长数组。
`Replication` 是一个空结构体，作为系统分组的名字，由单独的调用来更新。

## 系统 [#systems]

每个系统只做一件事，和其他系统之间只共享组件和单例。`[ForEach]` 方法的参数说明它做什么：`in` 读，`ref` 写它经过的每一行，`Mut<T>` 只写它改了的行，`Span<T>` 一次拿一段行；生成器据此生成循环和访问集。

### 移动 [#moving]

`PlanningSystem` 给每个 NPC 选要去的路点：离它最近、而且还没到过的那个。它规划时用的 `Waypoints` 单例在 `[OnCreate]`
里创建，在 `[OnDestroy]` 里移除。规划不必每个 tick 都是最新的，所以 `[ForEach(Slices = 4)]` 把它摊到四次运行上：每次只规划
四分之一的 NPC，每个 NPC 每四个 tick 规划一次，哪个 tick 都不会出现尖峰。大多数时候规划出来的还是原来的目标，而 `Goal`
要同步，所以方法收的是 `Mut<Goal>` 而不是 `ref Goal`：被追踪组件的 `ref` 参数会把方法经过的每一行都算作写入，
`SetIfChanged` 却只给真正变了的目标打 tick，同步也就只发这些。`SteeringSystem` 每个实体的计算量大，所以跑在所有核心上
（`Parallel = true`），朝着目标转向。`MovementSystem` 接收 span，把整段连续行当作 `Vector<float>` 相加。`ManaSystem` 每十次更新跑一次，
比 `RegenerationSystem` 晚五次，两者的开销落在不同的 tick 上。`ZoneSystem` 只在单位真的换了区域时才写 `Zone`，
这一写会把它的行搬到新区域的表里。

### 战斗 [#fighting]

战斗拆成两部分：`CombatSystem` 只管伤害，`StatusSystem` 只管状态。冻住一个单位就是禁用它的 `Attack` 和 `Velocity`：
值还留着，但在 `Thaw` 重新启用之前没有查询能看到它们。于是被冻住的单位不攻击、不移动、不射击，却没有任何系统需要检查
`Frozen`。`AfflictionSystem` 统计着火或冻住的单位时不写循环：`Count` 直接读存在位，一次 64 行。`DeathSystem`
给死者打上标签，其他系统按这个标签过滤。`CombatSystem` 以 `Mut<Health>` 接收 `Health`：大多数单位处在两次攻击之间，只有出手的
单位的 `Health` 会被打 tick，而且每行不用再按实体查找一次；调度器看到的是系统读写了哪些组件，而不是一个经由 `Entity`
访问组件的系统。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#combat</include>

### 死亡与复活 [#respawn]

`RespawnSystem` 响应 `Dead` 标签，`DeathSystem` 根本不知道它存在。玩家复活时召回自己的投射物（子实体）、清空背包、
顺着 `Friend` 关系找到一个活着的好友并出现在他身边，再用一次 `Remove<Dead, Burning, Frozen>()` 去掉所有状态。
NPC 死亡时，把下一个 NPC 的出生点写进 `Spawn` 清理组件，把掉落交给同区域的一名玩家（只需看一个分组的表）；`[Consume]` 在方法之后销毁它，也就是让它退休：
`Spawn` 带着 `Retired` 标签留下来，等 `Revive` 生成下一个 NPC 并移除它，旧实体才真正释放。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#respawn</include>

### 投射物、回血和时钟 [#projectiles]

投射物是一个带 `ChildOf` 的实体，指向发射它的玩家，玩家被销毁时投射物随之销毁。
`Instantiate(Shot, p, velocity, new ChildOf(player))` 复制 `Shot` 预制体，同时写入这三个值：投射物一次行拷贝就落进最终的表，
生成时就已经挂在玩家下面。`RegenerationSystem` 用一个方法处理两种情况：
`Maybe<Burning>` 告诉它这个实体有没有着火，着火的玩家回血更少；`Mut<Health>` 只给真正回了血的玩家打 tick，满血的不打。`ClockSystem` 最先注册，却因为
`[UpdateAfter<RegenerationSystem>]` 排到了最后。

## 靠变更追踪做同步 [#replication]

`ReplicationSystem` 属于 `Replication` 分组，宿主每三个 tick 更新一次。每个方法只访问系统上次运行以来变了的东西：
被写过的血量（`[Changed<Health>]`）、刚着火的单位（`[Changed<Burning>]`）、火已熄灭的单位（`[Removed<Burning>]`，
即失去了这个组件且现在仍没有它的实体）、变了的目标（`[Changed<Goal>]`：只有 `Plan` 真正写过的那几个，而不是它经过的每个
NPC），以及通过 `ref` 写过的背包（`[Changed<DynamicBuffer<Loot>>]`）。没有任何地方手动标脏：写入本身就是标记，不管是通过 `ref` 还是 `Mut<T>`。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#replication</include>

### 客户端补发 [#catch-up]

`ReplicationSystem` 面向每次同步都收到了的客户端。断开一阵再回来的客户端（重连、丢包）确认过的是更早的 tick，而且每个客户端
各不相同。`CatchUp` 只凭这个 tick 就能回答，服务端不用给每个客户端存状态：`ChangedAny<Health, Burning, Goal>`
只存一个过滤条件，选出三者任一变过的单位，`Since(acked)` 换上这个客户端的 tick 来跑；`Removed<Burning>` 再补上熄灭的火。
客户端还得知道哪些单位没了，而被销毁的实体已经没有行可找，所以 World 开了销毁日志（`WorldOptions.DestroyLogCapacity`，一个环形缓冲，
记着最近销毁的 id）：`DestroyedSince` 列出这个 tick 以来销毁的 id。客户端落后得比环形缓冲还远时，它返回 false，
客户端就重新拿一遍整场战斗。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#catch-up</include>

为什么划算、哪些操作算写入，见[变更追踪](/zh/docs/guide/change-tracking)和[移除检测](/zh/docs/guide/change-tracking#removal-detection)。

## tick 之外的遍历 [#reports]

普通静态类里的静态 `[ForEach]` 方法就是一个 runner：生成器会写一个入口，参数是 World 加上方法的其余参数
（`Reports.SumMana(world, ref total)`）。宿主在两次 tick 之间调用它们。`SumHealth` 把整段行当作 `Vector<int>` 读；
`HealFully` 和 `Scatter` 分块并行。`Dice` 只取决于 tick 和实体，所以在哪个线程上掷出的结果都一样。

## 宿主 [#host]

`BattleServer` 在一个线程上独占一个 World，负责 tick，并在两次 tick 之间回答查询。

### 过滤条件与预制体 [#prefabs]

过滤条件只建一次，放在 `static readonly` 字段里；`WrittenPlayers`、`ClientChanges` 和 `FiresOut` 每次调用时用 `Since`
换上新的 tick。预制体是不属于任何 World 的配方，查询看不到它们：`Hero` 既可以一次设置多个组件，也可以用生成的方法逐个设置；
`Brute` 是变体，复制自 `Grunt` 并改了三个值；`Shot` 只放每颗投射物都一样的部分，其余的在发射时给出。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#prefabs</include>

### 搭建 World [#setup]

构造函数配置 World（并行系统、计时、出错的系统直接关掉而不是抛异常、每个单位一条的销毁日志；分组和目标策略都声明在类型上），
按 tick 顺序注册系统，再批量生成单位：每一波只扩容一次表。`Reserve` 为 NPC 的重生波次预留空间，
tick 中表不会再扩容。`SpawnNpc` 实例化重生的 NPC 时直接给出位置。

### tick [#the-tick]

`Tick()` 就是两次调用。`Battle` 通过只解析一次的 `SingletonRef` 读计数。`Failure` 找出抛过异常的系统：在
`SystemErrorPolicy.Disable` 下，异常作为数据留在 `system.Error` 里，战斗照常进行。`Ceasefire` 是一条规则，修改它就是写一个单例，
而不是调用某个系统。

### 用账号加入 [#accounts]

客户端用账号登录。`Account` 带 `[UniqueKey]`（因此实现了 `IUniqueIndexed<int>`）：一个键只对应一个实体，所以 `TryGet` 一次哈希查找就能找到账号的英雄；
要是某次写入会让第二个英雄拿到已被占用的账号，它会在改动任何东西之前抛异常。`Join` 用
`Instantiate(Hero, at, new Account(account))` 给新账号生成英雄，位置和账号跟预制体的组件在同一次行拷贝里写入；
已经有英雄的账号拿回原来那个（重连）。`Kick` 也这样找英雄。`Get` 也是查找，只是没有实体持有这个键时会抛异常。

### tick 之间的查询 [#queries]

`PlayersIn` 只数一个分组的表。`Any` 找到第一个就停。`ShotsLeft` 和 `Hit` 从客户端发来的句柄或 id 出发：失效的直接返回 false。
`Hit` 是作用在单个单位上的请求，所以调用 `[ForEntity]` 方法的入口 `Requests.TakeHit`：方法要的组件只查一次表，`[Without<Dead>]` 把死掉的单位挡在外面。
方法以 `ref` 接收 `Health`，所以这次命中会打上变更 tick，随下一次同步发出去。

### 背包、克隆、击杀榜和好友 [#buffers-and-indexes]

`Mirror` 原样克隆一个活着的单位，索引、分组和下一次同步都会知道这个副本。英雄的副本会和它共用账号，唯一键不允许这样
（`Clone` 会抛异常），所以只克隆机器人和 NPC。`LootValue` 读背包，不算写入；`Give` 先用读操作校验，
再同时写两个背包。`TopKillers` 从顶部遍历有序的 `Kills` 索引，`FriendsOf` 向关系索引查询有谁把这个玩家加为好友。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#buffers-and-indexes</include>

### 离开与换场 [#leave-and-transfer]

玩家离开就是被销毁：投射物（子实体）随之销毁，目标策略把它从所有好友列表里移除。`Transfer` 用 `Descendants(player).AddTo`
把玩家的整棵子树收进一个复用的列表，再用 `MoveEntities` 搬到同一线程上的另一场战斗：它们在那边是新实体，投射物仍是它的子实体。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#leave-and-transfer</include>

### 人口统计 [#census]

一个临时 `Query` 找出最近的活着的玩家；统计把几个 runner 和计数的结果汇总起来。

### 新一轮 [#new-round]

批量调用逐表处理所有匹配：一次遍历销毁全部投射物，移除状态，启用被禁用的组件，再用两个并行 runner 回满血、打散 NPC。

<include lang="csharp" meta='title="BattleServer.cs"'>../../benchmarks/EasyEcs.Benchmark/BattleServer.cs#new-round</include>

### 快照与存档 [#snapshots-and-saves]

检查点就是一份内存快照，再加上拍快照时的变更 tick，宿主据此统计之后被写过的玩家数。`Save` 和 `Load` 把整场战斗写成字节、
再读回来；实体保留原来的 id，组件里存的 `EntityId` 仍然指向正确的实体。

### 诊断 [#diagnostics]

`DescribeTables` 列出每张表的列、行数和字节数，可以直接放进监控面板。`Schedule` 描述系统怎么跑：每个分组的阶段、每个系统读写什么、
为什么要等前一个阶段；服务器启动时打一次日志。打开 `MeasureSystems` 后，每个系统的运行时间都记在 `system.Stats` 里，
还有它分配的字节数和访问过的实体数。

## 跑起来 [#running-it]

```csharp title="Program.cs" doccheck=skip
using System.Buffers;
using EasyEcs.Benchmark.Showcase;

using var server = new BattleServer(100_000);
Console.WriteLine(server.Schedule());                     // 启动时打一次：阶段、访问、等待
server.Checkpoint();                                      // 比如执行一条有风险的管理命令之前
var hero = server.Join(1001, new Position(2048, 2048));   // 客户端用账号登录

while (running)
{
    server.Tick();                                        // 表达到峰值规模后不再分配
    if (server.WrittenSinceCheckpoint > 1_000) server.Checkpoint();
}

var gone = new EntityId[100_000];                         // WorldOptions.DestroyLogCapacity 个 id：一定装得下
if (!server.CatchUp(acked, gone, out int updates, out int destroyed))   // acked：客户端确认过的 tick
    SendWholeBattle();                                    // 客户端落后得比日志还远

var census = server.Census();                             // tick 之间：runner、Count、分组
Console.WriteLine($"{census.Alive}/{census.Players} alive, {server.PlayersIn(0)} in zone 0, slowest {server.Slowest()}");
server.Ceasefire = true;                                  // 规则即数据：玩家停火，飞行中的投射物照常到期
server.NewRound();
server.Rewind();                                          // 在内存里回滚战斗

var save = new ArrayBufferWriter<byte>();
server.Save(save);                                        // 写盘或发给另一个进程：Load(save.WrittenSpan)

using var other = new BattleServer(10_000);
server.Transfer(server.NearestPlayer(default), other);    // 玩家带着投射物换到另一场战斗

// 每个线程一个 World 就能用满多核：World 之间不共享任何东西。
var threads = new Thread[4];
for (int i = 0; i < threads.Length; i++)
    (threads[i] = new Thread(() => { using var battle = new BattleServer(25_000); while (running) battle.Tick(); })).Start();
```

每个系统都可以单独删掉、调整顺序或单独测试：它们之间只共享组件和单例。
