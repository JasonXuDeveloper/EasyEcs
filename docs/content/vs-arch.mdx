[Arch](https://github.com/genaray/Arch) and EasyEcs are both archetype ECS libraries for C#: entities with the same
components share a table, and queries walk its columns. They differ in what the core does for you. Arch is a small,
fast core: queries, struct jobs, chunks and a command buffer, with systems and source generators in the separate
Arch.Extended packages. EasyEcs puts systems, generated jobs, change tracking, indexes, relations, saves and
snapshots in one package for .NET 10 servers and games, and applies structural changes immediately instead of through a
command buffer.

In the <FeatureCount library="Arch" k="total" /> head-to-head benchmarks both libraries take part in, EasyEcs is faster in
<FeatureCount library="Arch" k="ahead" />, within the measurement error in <FeatureCount library="Arch" k="even" /> and slower in <FeatureCount library="Arch" k="slower" />.
On the same server tick of 100,000 entities, Arch takes <BenchValue k="peers.arch.ratio" /> the time of EasyEcs and
allocates <BenchValue k="peers.arch.alloc" /> per tick, where EasyEcs allocates <BenchValue k="peers.easyecs.alloc" />.
Arch runs on more runtimes (netstandard2.1, net6.0, net8.0 and Unity); EasyEcs needs .NET 10.

## At a glance [#at-a-glance]

| | EasyEcs | Arch |
| --- | --- | --- |
| Storage | archetype tables, presence bits per column | archetypes in chunks |
| Changes during a query | applied at once | recorded in a `CommandBuffer`, played back later |
| Removing a component | flips a bit, the entity keeps its row | moves the entity to another archetype |
| Systems | built in, generated from `[ForEach]` methods | Arch.Extended |
| Change and removal tracking | `[Changed<T>]`, `[Removed<T>]` | events (`SubscribeComponentSet`, `SubscribeComponentRemoved`) |
| Indexes, relations, hierarchy | built in | relations in a separate package |
| Allocation per server tick | none | the command buffer allocates |
| Runtimes | net10.0 | netstandard2.1, net6.0, net8.0; Unity |

## Concepts side by side [#concepts]

| Concept | Arch | EasyEcs |
| --- | --- | --- |
| World | `World.Create()`, `World.Destroy(world)` | `new World()`, `world.Dispose()` |
| Component | any struct | a struct implementing `IComponent` |
| Tag | an empty struct | an empty struct implementing `IComponent` |
| Singleton | none (a component on one entity) | `ISingletonComponent`, `world.AddSingleton<T>()` |
| Query | `new QueryDescription().WithAll<A, B>().WithNone<C>()` | `[ForEach, Without<C>]` on a method; `QueryFilter.Create().Without<C>()` for ad-hoc calls |
| Struct job | `IForEach<A, B>` with `Update(ref A, ref B)`, run by `world.InlineQuery<Job, A, B>(in query, ref job)` | `IForEach<A, B>` with `Execute(ref A, ref B)`, run by `world.ForEach<A, B, Job>(ref job, in filter)` |
| Job with the entity | `IForEachWithEntity<A>`, `InlineEntityQuery` | `IForEachEntity<A>`, `ForEachEntity`, or an `Entity` parameter of a `[ForEach]` method |
| Chunks | `world.Query(in query).GetChunkIterator()`, then `chunk.GetSpan<T>()` | batch `[ForEach]` methods taking `Span<T>`, or `ForEachBatch` |
| System | Arch.Extended `BaseSystem` | `EcsSystem` with `[ForEach]` methods |
| Command buffer | `CommandBuffer`, `Playback(world)` | none: `entity.SetFire(10)`, `RemoveFire()`, `Destroy()` apply at once |
| Bulk change | `world.Add(in query, value)`, `world.Remove<T>(in query)` | `world.SetAll(value, filter)`, `world.RemoveAll<T>(filter)` |
| Reserve before creating | `world.EnsureCapacity(in signature, n)` | `world.Reserve<A, B>(n)`, or `world.CreateEntities(span, a, b)` at once |
| Parallel query | `World.SharedJobScheduler`, `InlineParallelQuery` | `[ForEach(Parallel = true)]` |
| Events | `SubscribeComponentAdded` / `Removed` / `Set` | none: `[Changed<T>]`, `[Removed<T>]`, tags queried by later systems |

## The same task in both [#same-task]

The combat system of the headline tick: fighters attack on a cooldown and some hits set the target on fire. Arch
cannot add `Burning` while its query iterates, so the port records the change and plays it back after the system
(`ArchSimulation.cs`). EasyEcs adds it on the spot (`WorldSimulation.cs`).

<Tabs items={['EasyEcs', 'Arch']}>
<Tab value="EasyEcs">

```csharp title="CombatSystem.cs"
public struct Attack : IComponent { public int Damage, Cooldown, Interval; }
public struct Hp : IComponent { public int Value, Max; }
public struct Fire : IComponent { public int Ticks; }

public class CombatSystem : EcsSystem
{
    [ForEach, Without<Dead>, Without<Stunned>]
    static void Fight(Entity entity, ref Attack attack, ref Hp hp)
    {
        if (--attack.Cooldown > 0) return;
        attack.Cooldown = attack.Interval;
        hp.Value -= attack.Damage;
        if (entity.Id.Index % 20 == 0 && !entity.HasFire)
            entity.SetFire(10);   // applied now, also mid-pass
    }
}
```

```csharp
world.AddSystem<CombatSystem>();
world.Update();
```

</Tab>
<Tab value="Arch">

```csharp title="ArchCombat.cs" doccheck=skip
private static readonly QueryDescription Fighters =
    new QueryDescription().WithAll<Attack, Hp>().WithNone<Dead, Stunned>();

private struct Fight : IForEachWithEntity<Attack, Hp>
{
    public World W;
    public CommandBuffer B;

    public void Update(Entity e, ref Attack attack, ref Hp hp)
    {
        if (--attack.Cooldown > 0) return;
        attack.Cooldown = attack.Interval;
        hp.Value -= attack.Damage;
        if (e.Id % 20 == 0 && !W.Has<Fire>(e))
            B.Add(e, new Fire { Ticks = 10 });   // recorded
    }
}

var fight = new Fight { W = world, B = buffer };
world.InlineEntityQuery<Fight, Attack, Hp>(in Fighters, ref fight);
buffer.Playback(world);                          // applied here
```

</Tab>
</Tabs>

In EasyEcs the filter, the job struct and the call are generated from the method; the system's access (writes
`Attack` and `Hp`) is generated too, and the analyzer rejects a method that would break it.

## What Arch does better [#what-arch-does-better]

- **The parallel query.** `InlineParallelQuery` on Arch's job scheduler is ahead of EasyEcs' parallel `[ForEach]`
  in this run: the scheduler keeps worker threads of its own, which wins when passes run back to back. EasyEcs
  chose thread-pool helpers woken only while they pay ([D22](/en/docs/decisions)); the parallel numbers of this run
  carry a large error.
- **Filling a fresh world without a reservation.** Created one by one in a new world, Arch's entities take
  <BenchValue k="cold.perEntity.arch" /> against EasyEcs' <BenchValue k="cold.perEntity" />: EasyEcs' doubling arrays
  reach the large object heap and start a full collection, Arch's 16 KB chunks never do. Reserve the table first
  (`Reserve<T1, …, Tn>(n)`) or create in one call, and EasyEcs is ahead
  ([creating entities in a fresh world](/en/docs/performance#cold-create)).
- **Reach.** Arch runs on netstandard2.1, net6.0 and net8.0, and in Unity. EasyEcs needs .NET 10.
- **A small core.** If you want queries and storage and nothing else, Arch's core is smaller; systems, relations and
  persistence are packages you add when you need them.
- **Events.** Arch raises component and entity events; EasyEcs has none by design ([D1](/en/docs/decisions)).

## When to choose Arch [#when-to-choose-arch]

Choose Arch when you need Unity or a runtime older than .NET 10, want a minimal core and are happy to assemble
systems and tooling from Arch.Extended. Choose EasyEcs for a .NET 10 server or Godot game whose state changes every tick: changes
applied where they are decided, generated and analyzer-checked systems, change and removal tracking, and no
allocation per tick. Porting an Arch codebase: [Migrate from Arch](/en/docs/migrate-from-arch).
