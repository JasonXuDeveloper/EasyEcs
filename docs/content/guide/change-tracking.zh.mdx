很多系统只关心“变了什么”：把状态同步给客户端、把脏实体存盘、给移动过的单位重建空间索引。给组件加上
`ITracked`，再给方法加上 `[Changed<T>]`，这个方法就只会访问自系统上次运行以来 `T` 被写过的实体。
`[Removed<T>]` 则反过来，专门找出这段时间里失去了 `T` 的实体；被销毁的实体由[销毁日志](#destroy-log)报告。

## 什么时候用 [#when-to-use-it]

<Callout type="idea" title="适合">
  只需要追踪少数变化的实体：同步给客户端、脏数据存盘、移动后重建索引，以及通知某样东西没了（状态结束、护盾破了）。
</Callout>

<Callout type="warn" title="不适合">
  每个 tick 每一行的值都真的会变的组件，比如一直在飞的子弹的 `Position`：没有可跳过的行，每次写入还要多记一个 tick。
  代码每个 tick 都重写、但值大多不变的组件，反而值得追踪：[值变了才写](#set-if-changed)。只追踪有人消费的组件，
  不要什么都追踪。
</Callout>

## 怎么用 [#how-to-use-it]

<Steps>
<Step>

### 标记组件 [#mark-the-component]

`ITracked` 会给组件加一列隐藏的 tick，每次写入都会记下发生的时间。

```csharp
public record struct Health(int Value) : IComponent, ITracked;
public record struct Replica(int Health) : IComponent;
```

</Step>
<Step>

### 给方法加过滤 [#filter-the-method]

`[Changed<Health>]` 只选出系统上次运行之后被写过的行。被追踪的组件用 `in` 读取。

```csharp title="Replicate.cs"
public class Replicate : EcsSystem
{
    // 只处理自本系统上次运行以来 Health 被写过的实体
    // （第一次运行时是全部实体）
    [ForEach, Changed<Health>] // [!code highlight]
    static void Copy(in Health health, ref Replica replica) => replica.Health = health.Value;
}
```

</Step>
<Step>

### 照常写入 [#write-as-usual]

任何系统或外部代码只要通过 `ref` 写了 `Health`，这一行就会被打上 tick，别的什么都不用改。

```csharp
world.AddSystem<Replicate>();
unit.SetHealth(40);   // 这是一次写入：Replicate 下次运行时会看到这个单位
world.Update();
```

</Step>
</Steps>

### 哪些算写入 [#what-counts-as-a-write]

被追踪组件的每一行都记着最后一次写入时 World 的变更 tick。只要拿到了 `ref`，就算写入，不管代码有没有真的赋值：

| 算写入 | 不算写入 |
| --- | --- |
| `[ForEach]` 方法和结构体 job（`WriteMask`）的 `ref T` 参数（批处理方法是 `Span<T>`） | `in T` 参数、`ReadOnlySpan<T>` |
| [`Mut<T>`](#set-if-changed) 参数：`Write()`，以及值不同时的 `SetIfChanged(value)`（只算这一行） | `Mut<T>.Value`，以及值相等时的 `SetIfChanged(value)` |
| `Query` 的元素（枚举器会给访问到的每一行打上 tick） | [`world.Read<T1..Tn>`](/zh/docs/guide/queries#read) 的元素、`TryGet<T>(out T)`（拿到的是副本）、`entity.Read<T>()`（只读） |
| `entity.Get<T>()`、找到时的 `TryGetRef<T>(out found)`、`GetOrAdd<T>()`、`Set(...)`，值不同时的 `SetIfChanged(value)` 和 `SetXIfChanged(…)` | `Has<T>()`，值相等时的 `SetIfChanged(value)` 和 `SetXIfChanged(…)` |
| 带着该组件的 `CreateEntity(...)`、`CreateEntities(...)`、`Instantiate(...)`、`Clone()` | 移除组件（属于[移除](#removal-detection)） |
| `entity.Enable<T>()`、`world.EnableAll<T>()`（保留的值回来了） | `entity.Disable<T>()`（算作移除） |
| `world.Restore(snapshot)`、`world.Load(bytes)`、`LoadEntities(...)`、`LoadEntitiesInto(...)`（恢复或加载的每一行） | `LoadEntitiesInto(..., markWritten: false)`：记录里的每个组件 tick 都为 0，不管是覆盖的还是新加的。用于恢复持久化的记录，又不想把它再存一遍或再发一遍（[恢复记录](/zh/docs/guide/migration-and-unload#records)）。`world.Load(bytes, markWritten: false)`：加载的每一行 tick 都为 0，也没有哪一行算作移除，用于重启后接着跑存下的 World（[重启](/zh/docs/guide/saves#restart)） |
| `entity.Run<…>(ref job)`（[单个实体](/zh/docs/guide/queries#run-on-one-entity)）：结构体 job 的 `WriteMask` 里的组件（job 没有重写 `WriteMask` 时是全部组件；只读的 job 声明 `WriteMask => 0`），只在 `Run` 返回 true 时打 tick | 返回 false 的 `entity.Run`：job 没有运行 |

[`DynamicBuffer<T>`](/zh/docs/guide/dynamic-buffers) 只能通过 `ref` 修改，所以它的写入总会被追踪到。

### Tick [#ticks]

`world.ChangeTick` 每过一个系统阶段加一（阶段是指彼此没有顺序约束、也没有冲突、可以同时跑的一组系统，或者单个系统），
每次更新结束后再加一，所以两次更新之间的写入一定比所有系统的上次运行更新。`system.LastRunTick` 是系统上次运行时的
tick。`[Changed<T>]` 方法选的是在它之后写入的行，因此系统这一轮自己写的东西，不会在下一轮被当成变化。新系统从 0 开始：
第一次运行会访问 World 创建以来写过的每一行（tick 为 0、从未写过的行除外）。`world.AddSystem<T>(changesFromNow: true)`
改为从当前 tick 开始，第一次运行只访问它加进来之后写入的行：适合加到已经有状态的 World 上的系统。写 `T` 的系统
不会和读 `T` 变化的 `[Changed<T>]`、`[Removed<T>]` 方法排进同一个并行阶段，因为这类方法声明了对 `T` 的读取。

在系统之外，用之前记下的 tick 来过滤：

```csharp
ulong mark = world.ChangeTick;
unit.SetHealth(40);                                                 // 记下 tick 之后的一次写入
var changed = QueryFilter.Create().Changed<Health>(mark);           // mark 及之后写入的行
int count = world.Count<Health>(changed);
foreach (var item in world.Read<Health>(changed))                   // Read 不打 tick：这些行保持原样
    Console.WriteLine($"{item.Entity}: {item.Health.Value} hp");
```

tick 之所以是调用参数，是因为“变化”总是相对于某个人上次看的时间点：`[Changed<T>]` 方法用的是自己系统的上次运行，
临时查询用的是调用方记下的 tick。tick 为 0 时会选中所有拥有 `T` 的行。

## 值变了才写 [#set-if-changed]

很多系统每个 tick 都重新算一个很少变化的值：已经站在目的地的 NPC 再走一步，AI 选出的还是原来那个目标，没人换过的装备
再汇总一遍属性。用 `ref` 参数的话，方法访问到的每一行都算作写入，下游每个 `[Changed<T>]` 读取方都得把所有行过一遍。
换成 `Mut<T>` 参数，只有方法真正写过的行才会打上 tick：

| `Mut<T>` 的成员 | 作用 |
| --- | --- |
| `Value` | 以 `ref readonly` 拿到组件：只是读取，不打 tick |
| `Write()` | 以 `ref` 拿到组件，并给这一行打上 tick：方法确定要写时调用 |
| `SetIfChanged(in value)` | 只有 `value` 和当前值不同时才存入并打 tick；返回是否写了 |

```csharp title="Patrol.cs"
public record struct Position(float X, float Y) : IComponent, ITracked;
public record struct Destination(float X, float Y) : IComponent;
public record struct PositionReplica(float X, float Y) : IComponent;

public class StepSystem : EcsSystem
{
    // 每个 tick 处理每个 NPC：其中大多数已经站在目的地上。
    [ForEach]
    static void Step(Mut<Position> position, in Destination destination)
    {
        ref readonly var p = ref position.Value;                    // 只读：不打 tick
        float x = p.X + Math.Clamp(destination.X - p.X, -1f, 1f);
        float y = p.Y + Math.Clamp(destination.Y - p.Y, -1f, 1f);
        position.SetIfChanged(new Position(x, y));                  // NPC 真的动了才打 tick // [!code highlight]
    }
}

[UpdateAfter<StepSystem>]
public class ReplicatePositionSystem : EcsSystem
{
    // 只访问位置变了的 NPC，而不是 StepSystem 访问过的每一个。
    [ForEach, Changed<Position>]
    static void Send(in Position position, ref PositionReplica replica) =>
        replica = new PositionReplica(position.X, position.Y);
}
```

```csharp
world.AddSystem<StepSystem>();
world.AddSystem<ReplicatePositionSystem>();
var npcs = new Entity[1000];
world.CreateEntities(npcs, new Position(0, 0), new Destination(0, 0), new PositionReplica(0, 0));
world.Update();                     // 同步系统第一次运行发送全部 1,000 个：对它来说都是新的
npcs[7].SetDestination(5, 0);       // 一个 NPC 开始走动
world.Update();                     // StepSystem 访问 1,000 个 NPC；同步只发 1 个
```

被追踪组件的 `ref` 参数，某条路径没写它（提前 `return`、写在 `if` 里），这正是 `Mut<T>` 要解决的情况，分析器会指出来
（[EECS053](/zh/docs/guide/analyzer#eecs053)）：代码修复把组件改成 `Mut<T>`，读走 `Value`，要写的路径上走 `Write()`。

```csharp tab="报告" doccheck=system,expect-EECS053
[ForEach]
static void Settle(ref Position position, in Destination destination)
{
    if (position.X == destination.X) return;   // 没动过的行照样打 tick
    position.X = destination.X;
}
```

```csharp tab="修正" doccheck=system
[ForEach]
static void Settle(Mut<Position> position, in Destination destination)
{
    if (position.Value.X == destination.X) return;
    position.Write().X = destination.X;         // 只有这条路径给行打 tick
}
```

系统外的代码也有同样的选择：`entity.SetIfChanged(value)` 和 `Set` 一样设置组件（没有就添加），但实体已经是这个值时
什么都不做，返回 false：不写入、不打 tick、不动索引。被追踪、[建了索引](/zh/docs/guide/indexes-and-relations)或
[分组](/zh/docs/guide/groups)的有字段组件，生成器还会给它生成 `SetXIfChanged(…)`，参数和 `SetX` 一样是构造函数的参数：

```csharp
bool moved = npcs[7].SetPositionIfChanged(1, 0);   // false：走了一步，已经在那儿了
```

在 `Set` 前手写比较（`if (e.Position.X != x) e.SetPosition(x, y);`）就是 `SetXIfChanged` 做的事，
[EECS033](/zh/docs/guide/analyzer#eecs033) 会建议改用它，有代码修复。

- **怎么判断相等：** 组件实现了 `IEquatable<T>`（record struct 都实现了）就用它，不装箱；否则非托管组件逐字节比较；
  再否则 `SetIfChanged` 抛 `NotSupportedException`，也不会生成 `SetXIfChanged`。带托管字段的组件请实现
  `IEquatable<T>`，或者改成 record struct。
- **字节不等于值：** 字节相同就是值相同，但值相同的字节未必相同。字段之间的填充字节、`-0.0` 与 `0.0`、负载不同的两个
  NaN 都会被当成变化：值没变也会写入并给这一行打 tick（最多多打一次，绝不会漏掉变化）。带 `float` 或 `double`
  字段的组件请改成 record struct，让它按数值比较。
- **`Mut<T>` 能用在哪：** 逐实体的方法，包括并行方法和会做结构变更的方法（实体挪了行之后再写，打的是新行）。批处理方法
  拿的是 span，不能用（[EECS009](/zh/docs/guide/analyzer#eecs009)）。建了索引或分组的组件从不通过 ref 写入
  （[EECS015](/zh/docs/guide/analyzer#eecs015)），请用 `entity.SetXIfChanged(…)`。没有 `ITracked` 的组件，
  `Mut<T>` 就是普通的 `ref`。
- **对调度器来说**，`Mut<T>` 参数就是对 `T` 的写入：这个系统不会和读 `T` 的系统排进同一个并行阶段。
- **开销：** `Value` 零开销。每次 `Write()`，以及每次真正改了值的 `SetIfChanged`，都要找到实体所在的行（查一次实体记录）
  再打 tick：每写一行比 `ref` 略贵，没写的行不花钱。每次 `SetIfChanged` 都要比较两个值，O(`T` 的大小)。

## 移除检测 [#removal-detection]

同步不仅要告诉客户端什么变了，还要告诉它什么没了：火灭了、护盾破了、buff 到期了。`[Removed<T>]` 会访问自系统上次运行
以来失去被追踪组件 `T` 的实体：

```csharp title="ReplicateFire.cs"
public record struct Burning(int Ticks) : IComponent, ITracked;           // 被追踪：移除也会被记录
public record struct FireReplica(bool Burning) : IComponent;              // 客户端知道的着火状态

public class ReplicateFire : EcsSystem
{
    [ForEach, Changed<Burning>]                     // 上次运行后被点燃（或火势被改写）
    static void Lit(ref FireReplica replica) => replica.Burning = true;

    [ForEach, Removed<Burning>]                     // 上次运行后火灭了 // [!code highlight]
    static void Out(ref FireReplica replica) => replica.Burning = false;
}
```

之所以能做到，是因为移除组件不会挪走实体所在的行：这一行只是清掉了存在位，而被追踪组件的移除会给这一行打上变更
tick。被移除的行和普通行没有区别，方法照样能读写实体的其他组件，批处理方法也会成段地拿到这些行。

<Accordions>
  <Accordion title="每次移除只报告一次">
    失去 `T` 且一直没有补回的实体，只会被移除之后系统的第一次运行访问一次。之后再次被移除，会再次被访问。
  </Accordion>
  <Accordion title="移除后又加回">
    在系统运行之前移除又加回，不算移除（实体身上有 `T`）。这种情况由 `[Changed<T>]` 看到，因为添加组件本身就是一次写入。
  </Accordion>
  <Accordion title="被销毁的实体">
    被销毁的实体已经没有行了，所以 `[Removed<T>]` 不会访问它。它们由[销毁日志](#destroy-log)报告：
    `world.DestroyedSince(tick, …)` 列出某个 tick 以来被销毁的实体，读取方有多少个都行。因持有
    [清理组件](/zh/docs/guide/cleanup-and-disable#cleanup-components)而被 `Destroy` 变成退休的实体会保留它的行直到这些组件被移除，
    但它失去其他组件同样不算移除：在它被释放、由销毁日志报告之前，什么都不会报告它。
  </Accordion>
  <Accordion title="没有不等于失去">
    创建时就没有 `T`、从[预制体](/zh/docs/guide/prefabs)实例化或克隆出来时就没有 `T` 的实体，从来没有失去过它，所以不会被报告。
  </Accordion>
  <Accordion title="恢复快照之后">
    `world.Restore` 之后，恢复出来且没有 `T` 的每一行都算作被移除，正如有 `T` 的每一行都算作被写入：恢复一次就是全量重发。
  </Accordion>
</Accordions>

在系统之外，`QueryFilter.Removed<T>(since)` 用调用方记下的 tick 做同样的事，并且和过滤条件里的 `Changed` 共用同一个
tick（`Since(tick)` 会同时移动它们）：

```csharp
// 类里的一个字段：tick 每次调用时再设置
private static readonly QueryFilter FireOut = QueryFilter.Create().Removed<Burning>(0);

ulong mark = world.ChangeTick;
world.Update();
int extinguished = world.Count<FireReplica>(FireOut.Since(mark));
foreach (var item in world.Query<FireReplica>(FireOut.Since(mark))) item.FireReplica.Burning = false;
```

## 几个组件任意一个：`ChangedAny` 和 `RemovedAny` [#changed-any]

客户端看到的一个单位由好几个组件组成（血量、护甲、位置），其中任何一个变了，都要把这个单位发出去。写几个
`[Changed<T>]` 要求的是它们全都变了；`[ChangedAny<T1, …, Tn>]` 只要求至少一个变了。`[RemovedAny<T1, …, Tn>]` 是
对应的移除版本：失去了其中至少一个、而且还没补回来的行。

```csharp
public record struct Armor(int Value) : IComponent, ITracked;
public record struct Poisoned(int Ticks) : IComponent, ITracked;
public record struct UnitReplica(int Health, int Armor, float X, float Y) : IComponent;
public record struct StatusReplica(bool Burning, bool Poisoned) : IComponent;

public class ReplicateUnitSystem : EcsSystem
{
    // 上次运行后血量、护甲或位置被写过：不管变了几个，每个单位只访问一次。
    [ForEach, ChangedAny<Health, Armor, Position>] // [!code highlight]
    static void Send(in Health health, in Armor armor, in Position position, ref UnitReplica replica) =>
        replica = new UnitReplica(health.Value, armor.Value, position.X, position.Y);

    // 某个状态结束了：上次运行后着火或中毒（或者两个都）没了。
    [ForEach, RemovedAny<Burning, Poisoned>]
    static void Clear(ref StatusReplica status, Maybe<Burning> burning, Maybe<Poisoned> poisoned) =>
        status = new StatusReplica(burning.HasValue, poisoned.HasValue);
}
```

- **每一行是“或”：** 一行只要有一个自己拥有的组件在这个 tick 之后被写过（或被移除），就通过；其他组件不必都有。
  一张表至少要有集合里的一列才会参与；这几列在这个 tick 之后都没人写过，整张表直接跳过。
- **和其他条件是“与”：** 一个方法或过滤条件里所有的 `ChangedAny` 特性或调用并成一个集合，所有的 `RemovedAny` 并成另一个，
  这些集合再和 `With`、`Without`、`Changed`、`Removed` 等其他条件取“与”。
- **一个过滤条件只有一个 tick：** 过滤条件里的 `Changed`、`Removed`、`ChangedAny` 和 `RemovedAny` 都从同一个 tick 往后看
  （否则抛 `ArgumentException`），`Since(tick)` 会一起移动它们。
- 2 到 9 个组件，每个都要实现 `ITracked`。和 `[Changed<T>]` 一样，方法会声明对每个组件的读取。

### 所有客户端共用一个过滤条件 [#per-client]

每个客户端确认到的 tick 都不一样：有的是最新的，有的丢了几个包，有的刚连上。一个过滤条件就能服务所有客户端：建一次，
放进字段，对每个客户端用它确认到的 tick 调一次 `Since(ackTick)`：

```csharp
// 不被追踪：它的查询元素不会打 tick。
public record struct NetId(int Value) : IComponent;

public static class Replication
{
    // 单位的同步副本里任何一部分在客户端的 tick 之后被写过，这个单位对该客户端就是脏的。
    public static readonly QueryFilter Dirty = QueryFilter.Create().ChangedAny<Health, Armor, Position>(0);
}
```

```csharp
world.CreateEntity(new NetId(1), new Health(100), new Armor(5), new Position(0, 0));
var knight = world.CreateEntity(new NetId(2), new Health(100), new Armor(5), new Position(0, 0));
var archer = world.CreateEntity(new NetId(3), new Health(100), new Armor(5), new Position(0, 0));
world.Update();
ulong before = world.ChangeTick;
knight.SetArmor(8);
world.Update();
ulong after = world.ChangeTick;
archer.SetPositionIfChanged(3, 4);

// 每个客户端确认到的 tick：一个刚连上，一个落后，一个是最新的。
ulong[] acked = [0, before, after];
for (int client = 0; client < acked.Length; client++)
{
    ulong mark = world.ChangeTick;   // 这次打包时的 tick
    // 用 Read 而不是 Query：发送不会打 tick。
    foreach (var item in world.Read<NetId, Position>(Replication.Dirty.Since(acked[client])))
        Console.WriteLine($"client {client}: unit {item.NetId.Value} at ({item.Position.X}, {item.Position.Y})");

    acked[client] = mark;            // 实际服务器里：等客户端确认这个包之后再更新
}
```

刚连上的客户端拿到全部三个单位，落后的拿到骑士和弓箭手，最新的只拿到弓箭手。被追踪组件的 `Query` 元素算作写入，所以循环
用 `Read` 遍历，它的元素不打 tick。每种同步副本一个过滤条件就够了，不必每个客户端一个：过滤条件
是值，换个 tick 再用不分配任何内存。

## 被销毁的实体：销毁日志 [#destroy-log]

被销毁的实体没有行，任何过滤条件都找不到它，可客户端还是得知道它离开了。把 `WorldOptions.DestroyLogCapacity` 设成一个容量，
World 就会用一个环形缓冲记下最近被销毁的实体，以及各自被销毁时的变更 tick；`world.DestroyedSince(since, into, out count)`
列出在 `since` 及之后被销毁的实体。规则和 `Since(tick)` 一样，所以客户端确认到的那个 tick，既用来取变化，也用来取
销毁。每个读取方各记各的 tick，多少个客户端都共用同一份日志。

```csharp
public static class Despawns
{
    // 告诉每个客户端：它确认的 tick 之后，有哪些实体离开了。
    public static void Send(World world, ReadOnlySpan<ulong> acked, Span<EntityId> gone)
    {
        for (int client = 0; client < acked.Length; client++)
        {
            if (!world.DestroyedSince(acked[client], gone, out int count))
            {
                // 这个客户端需要的记录已经被环形缓冲覆盖了：只能把完整状态重新发一遍。
                Console.WriteLine($"client {client}: too far behind, resend everything");
                continue;
            }

            for (int i = 0; i < count; i++)
                Console.WriteLine($"client {client}: despawn {gone[i]}");
        }
    }
}
```

```csharp
// 容量要装得下客户端两次读取之间最长间隔里的销毁数。
using var zone = new World(new WorldOptions { DestroyLogCapacity = 4096 });
var gone = new EntityId[4096];                  // 所有客户端共用一个缓冲：4,096 个 id 装得下任何一次结果
var goblin = zone.CreateEntity(new Health(30));
ulong[] zoneAcks = [zone.ChangeTick];
goblin.Destroy();
Despawns.Send(zone, zoneAcks, gone);            // client 0: despawn 0v1
```

- **容量怎么定：** 读取方两次读取之间最长间隔里的销毁数，也就是每秒销毁数乘以允许客户端落后的最长时间。环形缓冲在
  `new World` 时一次分配好，每条记录 16 字节；日志关闭时（0，默认值），销毁不为它付任何代价。
- **返回 `false` 就要全量重发：** 读取方需要的记录被覆盖了。`DestroyedSince` 什么都不写，读取方把完整状态重新发一遍。
  `world.DestroyLogOldestTick` 是日志还能回答的最早 tick（环形缓冲第一次覆盖记录之前是 0）。日志容量撑不住真实客户端的
  延迟，客户端就会一遍又一遍地全量重发。
- **`count`** 是被销毁的实体数，写进 `into` 的是最早的 `min(count, into.Length)` 个，从旧到新。长度为 `DestroyLogCapacity`
  的 span 总能装下全部。
- **id 带着版本：** 每个 id 都是死掉的那一代实体，索引被复用后，新实体的版本不同，客户端那边的 id 映射不会错。
- **什么算销毁：** `IsAlive` 变成 false 的那一刻。`Destroy`、`DestroyEntities`、[层级](/zh/docs/guide/hierarchy)或
  [关系](/zh/docs/guide/indexes-and-relations#target-policies)的级联销毁、`MoveEntities` 移出这个 World；带着
  [清理组件](/zh/docs/guide/cleanup-and-disable)的实体在最后一个清理组件被移除时（在那之前它还活着，带着 `Retired`
  标签）；`Restore` 和 `Load` 时，之前活着、之后不在了的每个实体。`Dispose` 不记录任何东西，日志本身也不进快照和存档。
- **线程：** 在所有者线程上调用，或者在并行阶段的系统里调用。日志关闭时调用会抛 `InvalidOperationException`。

## 完整例子 [#full-example]

一千个单位，把血量和熄灭的火同步给客户端：第一次更新发送所有行，之后只发送被写过的行，`Burning` 被移除时只报告一次。把这几个
文件放进一个引用了 EasyEcs 的控制台项目（`dotnet add package EasyEcs`），用 `dotnet run` 运行。

```csharp title="Components.cs" doccheck=example
// 被追踪：每次写入都记下 tick，[Changed<Health>] 据此找到被写过的行。
public record struct Health(int Value) : IComponent, ITracked;
```

<Accordion title="Systems.cs">

```csharp title="Systems.cs" doccheck=example
using EasyEcs;

// 着火的单位每个 tick 掉 10 点血，直到火熄灭。
public class BurnSystem : EcsSystem
{
    [ForEach]
    static void Burn(Entity unit, ref Burning burning, ref Health health)
    {
        health.Value -= 10;
        burning.Ticks--;
        if (burning.Ticks == 0)
        {
            unit.RemoveBurning();
        }
    }
}

// 发送自本系统上次运行以来血量被写过的单位。
[UpdateAfter<BurnSystem>]
public class ReplicateHealthSystem : EcsSystem
{
    // Health 用 `in` 读：用 `ref` 会算作一次写入。
    [ForEach, Changed<Health>]
    static void Send(in Health health, ref Replica replica, ref Reduce<Sent> sent)
    {
        replica.Health = health.Value;
        sent.Value.Rows++;
    }
}

// 告诉客户端火熄灭了：访问自上次运行以来失去 Burning 的单位。
[UpdateAfter<BurnSystem>]
public class ReplicateFireOutSystem : EcsSystem
{
    [ForEach, Removed<Burning>]
    static void FireOut(Entity unit, in Health health)
    {
        Console.WriteLine($"  {unit}: the fire went out at {health.Value} hp");
    }
}
```

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();
world.AddSingleton<Sent>();
world.AddSystem<BurnSystem>();

world.AddSystem<ReplicateFireOutSystem>();

var units = new Entity[1000];
world.CreateEntities(units, new Health(100), new Replica(100));

for (int tick = 1; tick <= 4; tick++)
{
    // 系统外的写入同样算数。
    if (tick == 3)
    {
        units[42].SetHealth(75);
    }

    world.Update();
    Console.WriteLine($"tick {tick}: sent {world.Sent.Rows} of {units.Length} rows");
}

// 在系统外，按之前记下的 tick 过滤。
ulong mark = world.ChangeTick;
units[7].SetHealth(1);
units[8].SetHealth(1);
var writtenSinceMark = QueryFilter.Create().Changed<Health>(mark);
Console.WriteLine($"written since the mark: {world.Count<Health>(writtenSinceMark)}");
```

第一次运行访问所有行：对它来说每一行都是新的。第 2 个 tick，着火的单位被写入并失去 `Burning`，所以它既被发送，也被报告
一次；第 3 个 tick 只发送了在系统外被写过的那个单位；第 4 个 tick 没有任何写入，也就什么都不访问。

## 怎么用得快 [#how-to-use-it-fast]

- **只读就用 `in`。** 只读不写的 `ref` 参数会把访问到的每一行都标记成已变化，下游所有 `[Changed<T>]` 读取方都得把它们全部过一遍。
- **值大多不变时，用 `Mut<T>` 写。** `SetIfChanged` 只给值真的变了的行打 tick，下游读取方只访问真正的变化，而不是写入方
  访问过的每一行。
- **所有客户端共用一个 `ChangedAny` 过滤条件**，用 `Since(ackTick)` 移动 tick，不要每个客户端、每个组件各跑一遍。
- **优先写成系统，而不是查询。** `[Changed<T>]` 方法在碰到任何一行之前，会先跳过没人写过的表、4,096 行的块和 64 行的字。
  `Query` 会交出 ref，所以访问到的行都会被打上 tick；不能打 tick 的读取方（存盘、发包）用 `world.Read<T1..Tn>` 遍历，
  或者用 `WriteMask => 0` 的结构体 job。
- **过滤条件放进 `static readonly` 字段**，用 `Since(mark)` 移动它的 tick，不要每次调用都新建一个。
- **tick 要在一次更新刚结束时取。** 两次更新之间的写入共用一个 tick，在中间取的 tick 会把它之前的写入也一起选进来。

写入很少，或者写入集中在相邻的行，几乎整个遍历都能跳过。1,000 次写入分散在 10 万行里时，大部分 64 行的字都会被碰到，
这时省下的主要是那些不必执行的方法调用。

## 开销 [#what-it-costs]

- **内存：** 每张含该组件的表多一列隐藏的 8 字节 tick。
- **每次写入：** 记一个 tick，并更新所在 64 行字的摘要；成段的行用一次向量化填充写完。
- **每次遍历：** 用一次加载跳过没人写过的表，再跳过没写过的 4,096 行块和 64 行字（每次 SIMD 比较 4 个），直接从摘要里取出一个字中被写过的行。
- **一次移除：** 和一次写入开销相同，一个 tick 加上所在字的摘要。
- **一次 `Mut<T>` 写入：** 给它的行打 tick：单线程且不做结构变更的方法直接打，会做结构变更或并行运行的方法先查一次实体记录
  （实体可能被搬走了）；`Value` 和值没变的 `SetIfChanged` 不打 tick，
  `SetIfChanged` 要比较两个值，O(`T` 的大小)。
- **`ChangedAny` / `RemovedAny` 的集合：** 集合里的列在这个 tick 之后都没人写过的表直接跳过，之后和 `Changed` 一样按字和块跳过。
- **销毁日志：** `new World` 时一次分配，每条记录 16 字节；每次销毁写一条记录。`DestroyedSince` 是 O(报告的实体数)，
  不分配内存。关闭时（默认），销毁不为它付任何代价。
- **没有 `ITracked` 的组件零开销：** 这些检查是 JIT 期常量。

所有功能的开销汇总在[性能指南](/zh/docs/performance#the-few-rows-that-changed-changedt)。

## 常见陷阱 [#pitfalls]

| 错误 | 后果 | 谁能发现 |
| --- | --- | --- |
| 通过 `in` 修改组件里的集合 | 这一行没被打上 tick，`[Changed<T>]` 漏掉它 | [EECS011](/zh/docs/guide/analyzer#eecs011) |
| `[Removed<T>]` 方法同时要求有 `T` | 要求一行既有 `T` 又没有 `T`，没有行能满足 | [EECS016](/zh/docs/guide/analyzer#eecs016) |
| `[Removed<T>]` 方法既没有组件参数也没有 `[With<U>]` | 没有任何东西说明方法要遍历什么 | [EECS003](/zh/docs/guide/analyzer#eecs003) |
| 只读的参数写成了 `ref` | 访问到的每一行都算作已变化 | [EECS025](/zh/docs/guide/analyzer#eecs025) |
| `ref` 参数只在部分行上写入（提前 `return`、写在 `if` 里） | 访问到的每一行都算作已变化，没动过的行也一样 | [EECS053](/zh/docs/guide/analyzer#eecs053)：改用 [`Mut<T>`](#set-if-changed) 参数 |
| 接收方还没有这些值，却用 `LoadEntitiesInto(..., markWritten: false)` 加载 | 加载的行不算变化，靠 `[Changed<T>]` 的同步永远不会发出去 | 代码审查：给新客户端同步时，自己发送完整状态 |
| 指望 `[Removed<T>]` 报告被销毁的实体 | 它们没有行，任何过滤条件都访问不到 | 从[销毁日志](#destroy-log)读（`WorldOptions.DestroyLogCapacity`、`DestroyedSince`） |
| 销毁日志的容量小于客户端最长延迟内的销毁数 | 这个客户端每次读 `DestroyedSince` 都返回 false，一遍又一遍地全量重发 | 代码审查：容量按每秒销毁数乘以允许的延迟来定；关注 `DestroyLogOldestTick` |
| 每个 tick 都重算、但很少变的值用 `ref` 参数写 | 访问到的每一行都算作已变化，下游每个 `[Changed<T>]` 读取方都要全部过一遍 | 代码审查：改用 [`Mut<T>`](#set-if-changed) 参数加 `SetIfChanged` |
| 对带托管字段、又没实现 `IEquatable<T>` 的组件调 `SetIfChanged` | 抛 `NotSupportedException`；也不会生成 `SetXIfChanged` | [EECS040](/zh/docs/guide/analyzer#eecs040)：改成 record struct 或实现 `IEquatable<T>` |
| 想要“任意一个变了就算”，却写了好几个 `[Changed<T>]` | 只有每个都变了的行才通过 | 代码审查：用 `[ChangedAny<T1, …, Tn>]` |
| 一个过滤条件里的 `Changed`、`Removed`、`ChangedAny`、`RemovedAny` 用了不同的 tick | 抛 `ArgumentException`：一个过滤条件只有一个 tick | 运行时 |

## 和其他库的对比 [#compared]

其他库检测变化，靠的是你自己添加、自己清除的脏标签；检测移除，要么靠事件（每次移除一个回调，比如 Friflo 的
`OnComponentRemoved`），要么靠每个 tick 手动完成的响应式集合（DefaultEcs 的 `WhenRemoved<T>()`），要么干脆不支持。
在 EasyEcs 里，变化和移除都是数据，由下一次遍历直接选出来。
