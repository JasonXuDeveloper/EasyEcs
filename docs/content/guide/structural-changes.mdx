seoTitle: "Structural changes during iteration in a C# ECS"
description: Create, destroy, add and remove components in the middle of a pass. EasyEcs applies them at once, with no command buffer, visiting each entity at most once.
icon: Shuffle
---

A structural change is anything that changes which components an entity has, or which entities exist: creating
(`CreateEntity`, `Instantiate`, `Clone`), destroying, adding a component (`Set`, `GetOrAdd` of a missing one) or
removing one. EasyEcs applies them **immediately**, even in the middle of a pass: there is no command buffer to
record into and play back, so the death system marks a unit `Dead` where it decides, and the very next system already
sees the corpse.

## When to use it [#when-to-use-it]

<Callout type="idea" title="Use it for">
  Changing entities where the decision is made: set `Dead` in the death system, destroy an expired projectile in its
  own loop, spawn a projectile in the system that fires it, add `Stunned` in the hit that stuns. Tags for states that
  come and go: removing a component and adding it back moves nothing.
</Callout>

<Callout type="warn" title="Skip it for">
  Keeping a `ref` (other than the method's own `ref` parameters) across a structural change. Changing structure in a
  batch method, a parallel method or a job that implements `INoStructuralChanges`: their structure is frozen, and a
  change throws. A value that changes every tick: a field is cheaper than a component added and removed each tick.
</Callout>

## How to use it [#how-to-use-it]

<Steps>
<Step>

### Take the `Entity` (or the `World`) [#take-the-entity]

A `[ForEach]` method changes structure through its `Entity` parameter, or creates entities through its `World`
parameter. The generator sees the parameter and gives the method a pass that notices the changes.

```csharp
public record struct Lifetime(int Ticks) : IComponent;
public record struct Projectile(EntityId Owner) : IComponent;
public record struct Weapon(int Cooldown) : IComponent;

[EcsSystem]
public ref struct ExpireSystem
{
    [ForEach]
    static void Expire(Entity shot, ref Lifetime life)
    {
        if (--life.Ticks <= 0) shot.Destroy();         // destroyed now, in the middle of the pass
    }
}

[EcsSystem]
public ref struct FireSystem
{
    [ForEach, Without<Dead>]
    static void Fire(Entity shooter, ref Weapon weapon, in Position at, World world)
    {
        if (weapon.Cooldown-- > 0) return;
        weapon.Cooldown = 10;
        world.CreateEntity(at, new Lifetime(30), new Projectile(shooter.Id));   // not visited by passes already running
    }
}
```

</Step>
<Step>

### Run them in one update [#run-them]

```csharp
var world = new World();
world.AddSystem<FireSystem>();
world.AddSystem<ExpireSystem>();                     // sees this update's new projectiles
world.CreateEntity(new Position(0, 0), new Weapon(0));
world.Update();
int shots = world.Count<Projectile>();               // 1
```

</Step>
</Steps>

### Adding and removing while iterating [#during-a-pass]

Inside `[ForEach]` methods, `ForEach` jobs and `Query` loops you can create and destroy entities and add or remove
components, of the visited entity or any other. The rules:

- **A pass visits each entity at most once.**
- **Entities that stop matching before their turn are skipped**: destroyed, a queried component removed, or an
  excluded one added.
- **Entities that join a matching table during the pass are not visited by it**: created, or moved into a matching
  table. The next pass sees them.
- **An entity that gets a queried component back without moving** (its row only sets a presence bit) is visited if
  the pass has not reached its row yet.

```mermaid
flowchart LR
    A["pass reaches a row"] --> B{"still matches?"}
    B -- no --> C["skip"]
    B -- yes --> D["call the method"]
    D --> E["changes apply now"]
    E --> F["next row"]
    C --> F
```

### Refs across a change [#refs-across-a-change]

- **The method's own `ref` parameters stay writable** when the body changes the visited entity's table: the pass
  copies those writes to the entity's new row after the body returns. `in` parameters keep showing the values from
  before the change.
- **Any other `ref`** (from `entity.Get<T>()`, a `Query` item, or another entity) is guaranteed only until the next
  structural change: write through it before the change, or get it again afterwards ([EECS047](/en/docs/guide/analyzer#eecs047) reports a use
  after a change in the same block).
- **Code that handles one entity** (a request, a message) gets the same guarantee as a method's own `ref` parameters
  from a [`[ForEntity]`](/en/docs/guide/queries#run-on-one-entity) method (or a job run with `entity.Run`): its refs stay the entity's values across its
  own structural changes, and the components in its `WriteMask` are carried to the new row when it returns.

```csharp
[EcsSystem]
public ref struct HitSystem
{
    [ForEach, Without<Dead>]
    static void Hit(Entity unit, ref Health hp)
    {
        hp.Value -= 10;
        if (hp.Value <= 0) unit.SetDead();   // the row moves to the table with Dead
        hp.Value = Math.Max(hp.Value, 0);    // still the entity's Health: carried over to the new row
    }
}
```

The details, and why a `ref` must never cross an `await`, are in [ref and await](/en/docs/guide/refs-and-await).

### Passes that freeze the structure [#frozen-passes]

Some passes hold refs or spans into the tables for longer than one call, so they freeze the world's structure while
they run, and a change throws `InvalidOperationException` instead of tearing rows:

- **batch methods** (`Span<T>` parameters) and `ForEachBatch` jobs;
- **jobs that implement `INoStructuralChanges`**, including the ones the generator writes for methods that take no
  `Entity` or `World`;
- **parallel methods**, `ForEachParallel` / `ForEachEntityParallel` and [parallel stages](/en/docs/guide/threading#parallel-systems).

The analyzer reports a structural change in a method that promised none ([EECS013](/en/docs/guide/analyzer#eecs013))
and one made from another thread ([EECS014](/en/docs/guide/analyzer#eecs014)).

### Keeping tables dense [#keeping-tables-dense]

Tables stay dense on their own. Outside a pass, the table's last row fills a destroyed entity's row at once. Inside a
pass, a row that leaves becomes a tombstone the pass skips, and the tombstones are closed when the last pass ends,
also when a job throws. A query enumerator abandoned without `Dispose` (a `foreach` always disposes it) leaves its
pass open until the next `Update()`, which closes it. There is nothing to call and nothing to monitor.

### Many entities at once [#bulk]

For changes to whole sets of entities, the bulk forms take the structural gate once:

```csharp
var wave = new Entity[1_000];
world.CreateEntities(wave, new Position(0, 0), new Lifetime(60));
int expired = world.DestroyAll<Lifetime>(QueryFilter.Create().With<Dead>());
```

`SetAll`, `RemoveAll`, `DisableAll` and `EnableAll` change a component on every match a whole 64-row word at a time:
[Bulk changes](/en/docs/guide/bulk). The calls that take a filter end in `All`; the ones that take a list of ids end in
`Entities`. `DestroyEntities(ids)` destroys a list you collected (stale ids and repeats are skipped) with one gate pass
and one cascade:

```csharp
var ids = new List<EntityId>();
foreach (var item in world.Read<Lifetime>()) if (item.Lifetime.Ticks == 0) ids.Add(item.Entity.Id);
int gone = world.DestroyEntities(System.Runtime.InteropServices.CollectionsMarshal.AsSpan(ids));
```

Entities created one at a time (a start-up that loads them, a loop that builds each from data) grow their table by
doubling. Reserve it first: `Reserve<T1, …, Tn>(count)` grows the table of exactly those components and the
entity storage once, to what the loop needs, so the next `count` creations with those components grow nothing:

```csharp
world.Reserve<Position, Lifetime>(100_000);
for (int i = 0; i < 100_000; i++) world.CreateEntity(new Position(i, 0), new Lifetime(60));
```

`CreateEntities` reserves on its own. `Reserve(prefab, count)` does the same for a prefab's instances
([Prefabs](/en/docs/guide/prefabs)), and `EnsureEntityCapacity(n)` sizes only the entity storage, for entities spread
over many tables. Entities that a [group](/en/docs/guide/groups) puts in another table grow that one.

### What moves a row [#row-moves]

A row move copies every component of the entity to another table, so it is the part of a structural change that
costs. Most changes need none:

| Change | Row moves |
| --- | --- |
| `Set` of a component the entity has | None: a write (a [grouped](/en/docs/guide/groups) component with a new value moves to its group's table) |
| `SetIfChanged` with the value the entity has | None, and no write: nothing is stamped or re-indexed |
| `SetIfChanged` with another value | As `Set` |
| Adding a component the table has a column for (removed earlier, or a tag that comes and goes) | None: a presence bit |
| Adding a component the table has no column for | One, to the table that has it |
| `Set(a, b, …)` of several components the table lacks | At most one, whatever their number |
| `Instantiate(prefab)`, `Instantiate(prefab, in c1, …, in cn)` | None: one row copy into the final table |
| `Instantiate(prefab)`, then `Set` of a component the prefab lacks | The copy, then one move |

So spawning from a prefab with the values each instance needs (its position, its `ChildOf`) costs the copy and
nothing more ([prefabs](/en/docs/guide/prefabs#instantiate-with-values)).

`SetIfChanged` is a structural change only when it adds the component (or does what `Set` does to a grouped or a
disabled one). The analyzer cannot know which, so it counts `SetIfChanged`, like `Set`, as a call that may change
structure: a `[ForEach]` method that calls it on an entity takes the `Entity` or the `World`
([EECS013](/en/docs/guide/analyzer#eecs013)). To write a tracked component of the visited entity only when its value
changes, take it as `Mut<T>` instead ([change tracking](/en/docs/guide/change-tracking)).

## Full example [#full-example]

A turret that fires every other tick and wears down until it dies: the shots are created and destroyed in the middle
of passes, and the `Dead` tag is set where the death is decided. Put the files in a console project that references
EasyEcs (`dotnet add package EasyEcs`) and run it with `dotnet run`.

<Accordions>
<Accordion title="Components.cs">

```csharp title="Components.cs" doccheck=example
using EasyEcs;

// A turret: a weapon on a cooldown, and health that wears down every tick.
public record struct Weapon(int Cooldown) : IComponent;
public record struct Health(int Value) : IComponent;

// A shot: who fired it, and how many ticks it has left.
public record struct Projectile(EntityId Owner) : IComponent;
public record struct Lifetime(int Ticks) : IComponent;

// A tag: the turret is out of health.
public struct Dead : IComponent;
```

</Accordion>
<Accordion title="Systems.cs">

```csharp title="Systems.cs" doccheck=example
using EasyEcs;

// The turret loses 30 health a tick, and is tagged Dead where that is decided.
[EcsSystem]
public ref struct WearSystem
{
    [ForEach(SimdMode = SimdMode.Off), Without<Dead>]   // prints where it changes structure: one row at a time
    static void Wear(Entity turret, ref Health hp)
    {
        hp.Value -= 30;
        if (hp.Value <= 0)
        {
            // The row moves to the table with Dead, now.
            turret.SetDead();
            // hp is still this turret's Health: the write is carried to its new row.
            hp.Value = 0;
            Console.WriteLine($"  {turret} is dead");
        }
    }
}

// Fires every other tick. A turret tagged Dead earlier in this update no longer matches.
[EcsSystem, UpdateAfter<WearSystem>]
public ref struct FireSystem
{
    [ForEach, Without<Dead>]
    static void Fire(Entity turret, ref Weapon weapon, World world)
    {
        if (weapon.Cooldown > 0)
        {
            weapon.Cooldown--;
            return;
        }

        weapon.Cooldown = 1;
        var shot = world.CreateEntity(new Projectile(turret.Id), new Lifetime(3));
        Console.WriteLine($"  {turret} fires {shot}");
    }
}

// Counts down every shot, including the ones fired earlier in this update,
// and destroys a shot in the middle of its own pass.
[EcsSystem, UpdateAfter<FireSystem>]
public ref struct ExpireSystem
{
    [ForEach(SimdMode = SimdMode.Off)]   // prints where it changes structure: one row at a time
    static void Expire(Entity shot, ref Lifetime life)
    {
        life.Ticks--;
        if (life.Ticks == 0)
        {
            Console.WriteLine($"  {shot} expires");
            shot.Destroy();
        }
    }
}
```

</Accordion>
<Accordion title="Program.cs">

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();
world.AddSystem<WearSystem>();
world.AddSystem<FireSystem>();
world.AddSystem<ExpireSystem>();

var turret = world.CreateEntity(new Weapon(0), new Health(100));

for (int tick = 1; tick <= 5; tick++)
{
    Console.WriteLine($"tick {tick}");
    world.Update();
    int shots = world.Count<Projectile>();
    Console.WriteLine($"  hp {turret.Health.Value}, shots in flight {shots}");
}
```

</Accordion>
</Accordions>

It prints:

```text
tick 1
  Entity 0v1 fires Entity 1v1
  hp 70, shots in flight 1
tick 2
  hp 40, shots in flight 1
tick 3
  Entity 0v1 fires Entity 2v1
  Entity 1v1 expires
  hp 10, shots in flight 1
tick 4
  Entity 0v1 is dead
  hp 0, shots in flight 1
tick 5
  Entity 2v1 expires
  hp 0, shots in flight 0
```

A shot fired on tick 1 is already counted down by `ExpireSystem` in the same update, so it expires on tick 3, not 4.
On tick 4 the turret is tagged `Dead` in `WearSystem`, and `FireSystem`, which runs next, no longer visits it.

## How to use it fast [#how-to-use-it-fast]

| Instead of | Do | Why |
| --- | --- | --- |
| A command buffer played back later | The change, where it is decided | No recording, no playback, no allocation |
| Adding and removing a component each tick | A field, or a tag for a state that lasts several ticks | A tag the table's mask already has only flips a presence bit |
| `Set(a)` then `Set(b)` | `Set(a, b)` | Shorter, the same cost |
| `Instantiate(prefab)` then `Set` of what the prefab lacks | `Instantiate(prefab, in c1, …, in cn)` | One row copy into the final table, no move |
| Creating a known number of entities one by one | `CreateEntities`, or `Reserve<T1, …, Tn>(count)` before the loop | One growth instead of a doubling per full table ([EECS031](/en/docs/guide/analyzer#eecs031)) |
| A loop of single changes over a filter | [Bulk changes](/en/docs/guide/bulk), `DestroyAll<T>(filter)` | One gate pass, whole 64-row words at once ([EECS030](/en/docs/guide/analyzer#eecs030)) |
| An `Entity` parameter the method only reads | Keep it read-only (`Id`, `Has`, `Get`) | The pass skips structural bookkeeping |

## What it costs [#what-it-costs]

- **A pass that may change structure** checks one storage version per entity, so it notices changes; a method that
  cannot change structure skips even that.
- **Removing a component and adding it back:** one presence bit. **Gaining a component the table has no column for:**
  one row copy, once per new combination (the move plan is cached).
- **`Instantiate` with given components:** one row copy, the target table cached per prefab table and set of given
  components. **`SetIfChanged` with an equal value:** a comparison, no change at all.
- **Destroying:** O(components); the hole is filled at once outside a pass, or closed when the last pass ends.
- **Growing:** a full table doubles, copying its rows; a reservation (`Reserve`, `CreateEntities`) grows it
  once, to the rows it needs.
- **No allocation** after warm-up: there is no buffer to grow.

## Pitfalls [#pitfalls]

| Mistake | What happens | Caught by |
| --- | --- | --- |
| A change through a component's link in a method with no `Entity` or `World` | The pass keeps refs into moved rows | [EECS013](/en/docs/guide/analyzer#eecs013) |
| A change in a batch method | `InvalidOperationException`: the spans point into the tables | [EECS013](/en/docs/guide/analyzer#eecs013), and at run time |
| A change in a parallel method | `InvalidOperationException`: the structure is frozen while chunks run | [EECS010](/en/docs/guide/analyzer#eecs010), and at run time |
| A change from another thread | Races with the owner thread | [EECS014](/en/docs/guide/analyzer#eecs014) |
| `INoStructuralChanges` on a job that changes structure | `InvalidOperationException` at the change | At run time |
| A `ref` from `Get<T>()` used after a change | It may point at a stale copy or another entity's row | [EECS047](/en/docs/guide/analyzer#eecs047) (warning) in one block: get it again |
| Expecting a new entity in the pass that created it | It is visited by the next pass | By design |
| `World.Update()` inside a system | The system runs again inside its own run, until the stack overflows | [EECS034](/en/docs/guide/analyzer#eecs034) |
| `Update()` while a query of the same world iterates | The update moves rows the query has not reached behind it, so the loop misses them | [EECS051](/en/docs/guide/analyzer#eecs051) |
