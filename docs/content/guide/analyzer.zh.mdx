EasyEcs 分析器和源生成器一起打包发布，违反 [ECS 原则](/zh/docs/ecs-principles)的代码编译不过。正确性规则（EECS002 到 EECS024，以及
EECS035、EECS036）除了两条警告都是错误；这两条针对的是能跑、但有代价的写法（EECS017、EECS020）。生成器会跳过无效输入，由分析器报出来，
所以“没生成”一定意味着“报了错”。性能规则（EECS025 到 EECS034，以及 EECS039、EECS046、EECS052、EECS053）找的是能跑、但做了多余工作的代码，级别说明是哪一种
（[D29](/zh/docs/decisions#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)）：警告表示这样写有代价
（EECS025 到 EECS032，以及 EECS046、EECS052、EECS053）；建议（信息级别）表示代价相同、只是写法更简洁（EECS033、EECS039）；错误表示代码根本不能这样写（EECS034，在系统里执行World 更新）。用法规则（EECS037、EECS038，以及 EECS040 到 EECS045、EECS047 到 EECS051）找的是能编译、但做的不是它看起来在做的事的调用和声明：运行时会抛异常或根本行不通的报错误，写入会丢失、或 ref 可能指向错误的行的报警告。向量循环规则说明方法为什么一行一行地跑（EECS055，建议），并在必须向量化的方法没有向量化时让构建失败（EECS056）；EECS057 保证[归约](/zh/docs/guide/threading#reductions)是它的单例唯一的写入，EECS058 不让 `Scratch<T>` 的内存存进 World，EECS059 不让 `Lookup<T>`（或瓦片）读本次遍历要写的组件；线程规则（EECS060、EECS061）找出多线程代码会竞争或丢失的写入；部件规则（EECS062 到 EECS069）检查生成器按特性（`[Sum]`、`[LookupKey]`、`[Group]`）写入成员的类型和设置特性，并为手写的归约或键建议对应的特性；EECS070 让 `Emit<T>` 的记录保持行的顺序，EECS071 找出一次运行无法重现的随机数；瓦片规则（EECS072、EECS073）拒绝光环装不下的网格瓦片，以及会共用一张纹理的两个瓦片。系统规则（EECS074 到 EECS077）让系统保持为只有静态成员、钩子有效的 `ref struct`，并拒绝在需要系统的地方给出的非系统类型。声明规则（EECS080 到 EECS085）为手写的代码（单实体 job、销毁所访问实体的遍历）建议能生成它的特性，并拒绝无法生效的特性。参数规则（EECS086 到 EECS089）把让方法只能单线程运行的代码指向按块做同样工作的参数：逐行累加的单例改用 `Reduce<T>`，通过 `World` 读取其他实体改用 `Lookup<T>`，追加到单例列表的记录改用 `Emit<T>`，抽了两次的随机流各用一个自己的流。一条规则如果只有一种机械的改法，IDE 会把它作为代码修复提供出来（EasyEcs.CodeFixes，同一个包），而且只在改完能编译时才提供。

## 什么时候看 [#when-to-use-it]

<Callout type="idea" title="适合">
  编译报出以 `EECS` 开头的错误或警告时：从下表跳到对应小节。每一节都说明这条规则保护的是什么、会拒绝怎样的代码、怎么改，以及 IDE
  能不能自动改。
</Callout>

<Callout type="warn" title="不要">
  用 `#pragma` 压掉 `EECS` 错误：生成器已经跳过了规则所指的方法或类型，它需要的代码根本不存在。警告可以压掉，代价就是它们描述的那些；建议（信息级别）只在 IDE 里显示，
  在 `.editorconfig` 里写 `dotnet_diagnostic.EECS033.severity = warning` 可以让整个项目把它当警告报出来。用法错误（EECS040 到
  EECS045、EECS048 到 EECS051）指出的是运行时会拒绝的调用：`#pragma` 只应该出现在测试这种拒绝的测试代码里。
</Callout>

一个错误只报一条诊断：两条规则看到同一段代码时，由修法能消掉另一条情形的那条来报。改了又丢掉的副本报 EECS038，不再同时报
EECS025 或 EECS015；过滤条件让它永远不跑的方法报 EECS016 或 EECS049，不再同时报参数的代价；系统的实例钩子报 EECS075，不再同时报
EECS076（[D60](/zh/docs/decisions#d60-one-diagnostic-per-mistake)）。

## EECS002 [#eecs002]

**`[ForEach]` 参数无效。** 错误。代码修复：给按值传入的组件或单例加上 `in` 或 `ref`。

每个参数都必须是以下之一：实现 `IComponent` 或 `ISingletonComponent` 的 `ref` / `in` / `ref readonly` 结构体，`IComponent`
结构体的 `Span<T>` / `ReadOnlySpan<T>`，它的 `Maybe<T>` 或 `ReadOnlyMaybe<T>`（可选组件），`Mut<T>`，`ref Reduce<T>`
（[归约](/zh/docs/guide/threading#reductions)；不带 `ref` 时部分结果只是一份副本），[`Scratch<T>`](/zh/docs/guide/threading#scratch)，
组件的 [`Lookup<T>`](/zh/docs/guide/threading#lookups)，`Entity`，或者 `World`。
[系统之外](/zh/docs/guide/systems#foreach-outside-systems)的 `[ForEach]` 方法还可以接收任意其他类型的值，由生成的入口从调用方传进来。

```csharp doccheck=expect-EECS002
[EcsSystem]
public ref struct MoveSystem
{
    [ForEach] static void Move(ref Position p, float dt) { }   // 系统的方法拿不到调用方传的值
}
```

组件和单例用 `ref`（写）或 `in` / `ref readonly`（读）传入，其他值变成数据：

```csharp
public record struct DeltaTime(float Seconds) : ISingletonComponent;   // 这个值变成一个单例

[EcsSystem]
public ref struct MoveSystem
{
    [ForEach]
    static void Move(ref Position p, in Velocity v, in DeltaTime dt)
    {
        p.X += v.X * dt.Seconds;
        p.Y += v.Y * dt.Seconds;
    }
}
```

## EECS003 [#eecs003]

**组件数量无效。** 错误。没有代码修复。

`[ForEach]` 方法接收 1 到 9 个组件（单例、`Entity`、`World` 和 runner 的其他值不算，`Maybe<T>` 和 `ReadOnlyMaybe<T>` 算），或者在 `[With<T>]`（其次是
`[Changed<T>]`）指明要查询哪个组件时一个都不接收。`[Removed<T>]` 不算指明：它选出的实体已经没有 `T` 了，所以方法还需要一个组件参数
或者 `[With<U>]`。

```csharp doccheck=expect-EECS003
[EcsSystem]
public ref struct CorpseCleanupSystem
{
    [ForEach] static void Remove(Entity e) => e.Destroy();   // 哪些实体？没有组件指明
}
```

用过滤条件指明组件。完全没有组件就用 `[OnUpdate]`；超过 9 个，就把多出来的条件挪到 `[With<T>]`，或者拆开方法：

```csharp doccheck=expect-EECS030
[EcsSystem]
public ref struct CorpseCleanupSystem
{
    [ForEach, With<Dead>]                          // 过滤条件指明查询什么
    static void Remove(Entity e) => e.Destroy();
}
```

这个方法的整个方法体只是一次结构变化，所以接着 [EECS030](#eecs030) 会要求改成在 `[OnUpdate]` 里批量调用
`World.DestroyAll<Dead>()`。

## EECS004 [#eecs004]

**系统里的泛型 `[ForEach]` 方法。** 错误。没有代码修复。

系统每次更新自己运行它的 `[ForEach]` 方法，泛型方法拿不到类型实参。泛型系统没问题（每个封闭类型都是一个独立的系统），系统之外的泛型
`[ForEach]` 方法也没问题，它们的入口从调用方拿类型实参。

```csharp doccheck=expect-EECS004
[EcsSystem]
public ref struct ClampSystem
{
    [ForEach] static void Clamp<T>(ref T value) where T : struct, IComponent { }   // T 是什么？
}
```

把泛型放到系统上，而不是方法上：

```csharp
public interface IClamped { int Value { get; set; } }

[EcsSystem]
public ref struct ClampSystem<T> where T : struct, IComponent, IClamped   // AddSystem<ClampSystem<Armor>>()
{
    [ForEach] static void Clamp(ref T value) => value.Value = Math.Max(value.Value, 0);
}
```

## EECS005 [#eecs005]

**系统之外的实例 `[ForEach]` 方法。** 错误。代码修复：方法体没用到实例成员时，把方法改成 static。

不是 `[EcsSystem]` 的类型里，`[ForEach]` 方法会得到一个接收 World 的生成入口（`Physics.Move(world)`），没有实例可以调用这个方法。

```csharp doccheck=expect-EECS005
public class Physics
{
    [ForEach] void Move(ref Position p, in Velocity v) { p.X += v.X; p.Y += v.Y; }   // 在哪个 Physics 上调用？
}
```

改成 static，或者挪进系统：

```csharp
public static class Physics                                   // Physics.Move(world) 在整个 World 上跑一遍
{
    [ForEach] public static void Move(ref Position p, in Velocity v) { p.X += v.X; p.Y += v.Y; }
}
```

## EECS006 [#eecs006]

**ECS 数据必须是结构体。** 错误。代码修复：把类改成结构体，前提是这个类只声明了一次、没有基类，也没有结构体不能有的成员（`protected`、
`virtual`、`abstract`、终结器）。

组件和单例按值存在列里。接口可以继承这些标记接口，类不能实现它们。

```csharp tab="报告" doccheck=expect-EECS006
public class Wallet : IComponent { public int Gold; }
```

```csharp tab="修正"
public record struct Wallet(int Gold) : IComponent;
```

## EECS007 [#eecs007]

**系统把状态存在静态字段里。** 警告。代码修复：只由初始化器和静态构造函数写入的字段加上 `readonly`。

系统只是一组静态函数的名字，它唯一能存状态的地方就是静态成员：可变的静态字段、可写的静态自动属性或静态的类字段事件。这样的状态，
其他系统、查询和存档都看不到；它被进程里的所有 World 共享；系统被移除再添加后它还留着。`readonly` 静态字段（常量、查找表、可复用的
临时缓冲）和 `const` 是允许的。实例字段由 [EECS075](#eecs075) 报告。

```csharp doccheck=expect-EECS007
[EcsSystem]
public ref struct SpawnSystem
{
    static int _spawned;                                   // 所有 World 共享，存档看不到
    [OnUpdate]
    static void OnUpdate() => _spawned++;
}
```

每个实体的状态放进组件，每个 World 的状态放进[单例](/zh/docs/guide/singletons)：

```csharp
public record struct Spawned(int Count) : ISingletonComponent;

[EcsSystem]
public ref struct SpawnSystem
{
    [OnUpdate]
    static void OnUpdate(World world) => world.GetOrAddSpawned().Count++;
}
```

## EECS008 [#eecs008]

**系统不能引用系统。** 错误。没有代码修复。

系统的代码够到了另一个系统：调用它的方法或 `[ForEntity]` 入口，读它的字段，或者用 `World.System<T>()` / `World.TryGetSystem<T>(out …)`
找它。互相调用的系统耦合在一起：谁都不能单独移除、调整顺序或测试，调度器也看不到这次调用碰了什么。另一个系统的 `const` 是一个值，允许使用；
两个系统都要用的辅助函数放进单独的静态类。`System<T>` 和 `TryGetSystem<T>` 是给工具、测试和承载 World 的代码用的。

```csharp doccheck=expect-EECS008
[EcsSystem]
public ref struct KillSystem
{
    [ForEach, Without<Dead>]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }
}

[EcsSystem]
public ref struct ScoreSystem
{
    [OnUpdate]
    static void OnUpdate(World world) => world.System<KillSystem>().Enabled = false;   // 两个系统再也没法分开改
}
```

写出另一个系统要读的数据（组件或单例），再给两者排好顺序（[ECS 原则第 3 条](/zh/docs/ecs-principles#3-systems-never-reference-systems)）：

```csharp
public record struct Score(int Deaths) : ISingletonComponent;

[EcsSystem]
public ref struct KillSystem
{
    [ForEach, Without<Dead>]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }
}

[EcsSystem, UpdateAfter<KillSystem>]                       // 读 KillSystem 写下的 Dead
public ref struct ScoreSystem
{
    // 一次遍历销毁所有尸体并返回数量：每个只算一次
    [OnUpdate]
    static void OnUpdate(World world) => world.GetOrAddScore().Deaths += world.DestroyAll<Dead>();
}
```

## EECS009 [#eecs009]

**批量 `[ForEach]` 混用了 span 和逐实体参数。** 错误。没有代码修复。

接收组件 span 的方法拿到的是整段连续的行，所以逐实体参数（`ref` / `in` 组件、`Mut<T>`、`Maybe<T>`、`Entity`）在这次调用里没有
唯一的值；`World` 也可能在 span 还指着行的时候改动它们。没有组件 span 的 `EntitySpan` 则没有可描述的那段行。批量方法写入时按整段
打 tick：`Span<T>` 就是它的写入方式。

```csharp doccheck=expect-EECS009
[EcsSystem]
public ref struct DriftAllSystem
{
    [ForEach] static void Drift(Span<Position> p, in Velocity v) { }   // 一段行里 v 没有唯一的值
}
```

所有组件都用 span 接收（写用 `Span<T>`，读用 `ReadOnlySpan<T>`），另外可以加单例，以及表示这段行里实体的 `EntitySpan`；或者写成逐实体方法：

```csharp
[EcsSystem]
public ref struct DriftAllSystem
{
    [ForEach]
    static void Drift(Span<Position> p, ReadOnlySpan<Velocity> v)   // 两个 span 的第 i 个元素是同一个实体
    {
        for (int i = 0; i < p.Length; i++)
        {
            p[i].X += v[i].X;
            p[i].Y += v[i].Y;
        }
    }
}
```

## EECS010 [#eecs010]

**`[ForEach(Parallel = true)]` 不能在多个线程上跑。** 错误。代码修复：去掉 `Parallel = true`；没用到任何实例成员的实例方法，
改成 `static`。

并行方法会同时在多个线程上跑一块块的行，所以它不能做结构变更（static、不接收 `World`、`Entity` 只用来读：`Id`、`Has`、`Get` 等；不能调 `entity.Run`，它要做所有者线程上遍历的簿记，它的 job 也可能改结构），
必须逐实体运行（不能是批量方法），也不能写单例（`ref` 单例会在块之间产生竞争）。要读其他实体，用
[`Lookup<T>`](/zh/docs/guide/threading#lookups) 代替 `World`；它在并行方法里是允许的。

```csharp doccheck=expect-EECS010
[EcsSystem]
public ref struct KillSystem
{
    [ForEach(Parallel = true)]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }   // 结构变更
}
```

单例改用 `in`；结构变更挪进一个顺序执行的系统，让它对并行系统写下的数据做反应；或者去掉 `Parallel = true`：

```csharp
public record struct Regen(int PerTick) : ISingletonComponent;

[EcsSystem]
public ref struct RegenSystem
{
    [ForEach(Parallel = true), Without<Dead>]
    static void Regenerate(ref Health hp, in Regen regen) => hp.Value += regen.PerTick;   // 单例只读
}
```

## EECS011 [#eecs011]

**通过只读参数写数据。** 错误。代码修复：改用 `ref` 接收（`ReadOnlySpan<T>` 改成 `Span<T>`）；并行方法里的单例不提供修复，因为那里的
`ref` 单例会触发 EECS010。

`[ForEach]` 方法用 `in` 接收组件或单例（或者用 `ReadOnlySpan<T>` 接收组件），却修改了它通过引用持有的数据：在集合上调用会改动它的方法
（`Add`、`Remove`、`Clear`、`Insert`、`Push`、`Enqueue`、`Sort` 等），给元素赋值（`grid.Cells[i] = x`），或者改它持有的类的成员
（`holder.Owner.Gold++`）。编译器允许，因为只读的只是引用本身；但这次写入被当成读来调度（读同一份数据的并行系统会和它竞争），也不会
打上变更标记，`[Changed<T>]` 系统和值索引都看不到它。

```csharp tab="报告" doccheck=expect-EECS011
public record struct Grid(List<int> Cells) : ISingletonComponent;

[EcsSystem]
public ref struct GridSystem
{
    [ForEach] static void Mark(in Position p, in Grid grid) => grid.Cells.Add((int)p.X);   // 写的是 'in'，却改了
}
```

```csharp tab="修正"
public record struct Grid(List<int> Cells) : ISingletonComponent;

[EcsSystem]
public ref struct GridSystem
{
    [ForEach] static void Mark(in Position p, ref Grid grid) => grid.Cells.Add((int)p.X);   // ref：按写来调度
}
```

返回新值的调用（`string`、不可变集合和冻结集合）算读。规则只看直接作用在参数成员上的修改；复制到局部变量里的引用，或者在你自己类的
方法里做的修改，都不会追踪。组件里放集合是允许的，[ECS 原则第 8 条](/zh/docs/ecs-principles#8-choose-how-to-hold-a-collection)
说明什么时候该改用实体。

## EECS012 [#eecs012]

**按值持有 `DynamicBuffer<T>`。** 错误。代码修复：加 `in`；或者在每个调用方都传变量时，连同调用方的实参一起改成 `ref`。重写方法和接口
方法的签名是共享的，不提供修复。

[`DynamicBuffer<T>`](/zh/docs/guide/dynamic-buffers) 指向它的列表，所以值的副本指向同一个列表：通过副本写入永远不会被标记为变更，
把副本存起来又会让第二个实体（或快照）拿到同一个列表。规则会报出：`DynamicBuffer<T>` 类型的字段或属性，按值传递的参数或返回值，
不是 `ref` 局部变量的局部变量，对已有缓冲的赋值，以及把已有缓冲传给 `Set`、`CreateEntity` 或其他会把它存起来的泛型方法。

```csharp
public record struct Loot(int Item);
```

```csharp doccheck=expect-EECS012
public static class Bags
{
    public static void Share(Entity player, Entity other)
    {
        var bag = player.Read<DynamicBuffer<Loot>>();                // 一个副本
        other.Set(player.Read<DynamicBuffer<Loot>>());               // 两个实体，一个列表
    }
}
```

通过实体去拿缓冲：`ref` / `in` 参数，`ref var bag = ref entity.Get<DynamicBuffer<T>>()`，`entity.Read<DynamicBuffer<T>>()`。新的
组件值写 `new DynamicBuffer<T>()`（或 `default`），它不持有列表；[预制体](/zh/docs/guide/prefabs)用 `SetBuffer(…)` 或生成的
`SetLoot(…)` 填元素：

```csharp
public static class Bags
{
    public static int Items(Entity player) => player.Read<DynamicBuffer<Loot>>().Count;   // 通过实体读

    public static void Give(Entity player, Loot loot)
    {
        ref var bag = ref player.Get<DynamicBuffer<Loot>>();                               // ref 局部变量：被追踪的写入
        bag.Add(loot);
    }

    public static Entity Spawn(World world) => world.CreateEntity(new DynamicBuffer<Loot>());   // 新的空缓冲
}
```

## EECS013 [#eecs013]

**承诺不做结构变更的 `[ForEach]` 方法做了结构变更。** 错误。没有代码修复。

一个 static、不接收 `Entity` 或 `World`（或者 `Entity` 只用来读）的 `[ForEach]` 方法，在生成器看来不会改变结构，所以遍历时每次调用后
都不再重新检查存储，系统也会和其他系统同处一个[并行阶段](/zh/docs/guide/threading#parallel-systems)。如果它还是通过别处拿到的句柄或
World 改了结构，两件事都会出错：遍历还拿着指向已移动行的引用，并行阶段里的变更会抛异常。

在这样的方法里，规则会报出对 `Entity` 结构成员（`Set`、`Remove`、`Destroy`、`GetOrAdd`、`Clone`、`Disable`、`Enable`、
`Link`、`Unlink`、`Run`（它的 job 可能改结构），以及生成的 `SetX`、`GetOrAddX`、`RemoveX`）或 `World` 结构成员（`CreateEntity`、`CreateEntities`、
`Instantiate`、`Reserve`、`DestroyEntities`、`DestroyAll`、`SetAll`、`RemoveAll`、`DisableAll`、`EnableAll`、`Load`、`LoadKeeping`、`SaveWithout`、`SaveEntitiesWith`、`SaveEntitiesWithout`、`LoadEntities`、`LoadEntitiesInto`、`MoveEntities`、
`GroupBy`、`RemoveTypes`、单例、系统、`Update`、`Capture`、`Restore` 等）的调用。方法自己创建的 World（局部变量里的 `new World()`）
不算。

```csharp
public record struct Target(EntityId Id) : IComponent;
public struct Doomed : IComponent;                // 标签
public static class Arena { public static readonly World Main = new(); }
```

```csharp doccheck=expect-EECS013
[EcsSystem]
public ref struct SpawnEffects
{
    [ForEach] static void Spawn(in Position p) => Arena.Main.CreateEntity(p);   // 没有 Entity 或 World 参数
}
```

把 `Entity` 或 `World` 作为参数接收，再通过它改（系统随之单独运行，遍历也能察觉这次变更）；或者把变更记成数据，交给另一个系统去做：

```csharp
[EcsSystem]
public ref struct MarkTargets
{
    [ForEach, With<Target>]
    static void Mark(Entity hunter, in Target target, World world)
    {
        hunter.RemoveTarget();                                       // 通过参数改：这个系统单独运行
        if (world.TryGetEntity(target.Id, out var prey)) prey.SetDoomed();   // 遍历也能察觉这一次
    }
}
```

规则只看方法自身的代码：在它调用的辅助方法里做的变更不会追踪。不过在并行阶段或并行 `[ForEach]` 里，运行时照样会为此抛异常
（[World 同步了什么](/zh/docs/guide/threading#what-the-world-synchronizes)）。

## EECS014 [#eecs014]

**在其他线程上做结构变更。** 错误。没有代码修复。

World 的结构属于它的所有者线程。对于交给 `Task.Run`、`Task.ContinueWith`、`TaskFactory.StartNew`、`new Task`、`Parallel.*`、
`ThreadPool.QueueUserWorkItem`（及其同类）、`new Thread` 或 `new Timer`，或者订阅到 `System.Timers.Timer.Elapsed` 的 lambda 或匿名方法，
以及以方法组形式交给它们的同一类型里的方法（`Task.Run(Spawn)`），如果其中的结构调用（EECS013 列出的那些成员）改的 World 或实体可能同时被
另一个线程修改，规则就会报出来：

- `Parallel.*` 同时在多个线程上运行委托，所以从外面捕获的任何 World 或实体都会竞争（`worlds[i]` 这种每项一个 World 的不算）；
- 交接写在循环里，委托会对同一个捕获的 World 或实体运行多次；
- 交接外层的代码（所在方法，或者对字段来说是所在类型）也在改同一个 World 的结构。

```csharp doccheck=expect-EECS014
public static class Spawner
{
    public static void Start(World world, Entity[] players)
    {
        Task.Run(() => world.CreateEntity(new Position(0, 0)));      // 调用方也在改这个 World
        world.CreateEntity(new Position(1, 1));

        Parallel.For(0, players.Length, i => players[i].Destroy());  // 一个 World 的实体，同时在多个线程上
    }
}
```

交给某个线程、从此由它拥有的 World（每线程一个 World、在委托里新建的 World）不会报；调用方立刻等待的交接（`await`、`Wait()`、
`Result`、`GetAwaiter().GetResult()`）也不会报：没有东西和它并行。把变更作为数据，经由所有者线程上某个系统消费的队列交过去
（[来自其他线程的输入](/zh/docs/guide/threading#input-from-other-threads)），或者给另一个线程它自己的 World：

```csharp
public static class WorldThreads
{
    // 每线程一个 World：各线程拥有自己的 World，什么都不共享
    public static Thread[] Start(World[] worlds)
    {
        var threads = new Thread[worlds.Length];
        for (int i = 0; i < worlds.Length; i++)
        {
            var zone = worlds[i];                                       // 每次迭代一个变量
            threads[i] = new Thread(() => { for (int t = 0; t < 1_000; t++) zone.Update(); });
            threads[i].Start();
        }

        return threads;
    }
}
```

和 EECS013 一样，规则只看委托自身的代码（方法组则往下看一层，即那个方法本身），它追踪不到的接收者（某个方法的返回值）不会报。

## EECS015 [#eecs015]

**通过 ref 写被索引的组件。** 错误。代码修复（代码只读时）：`Get<T>()` 改成 `Read<T>()`，`ref` 局部变量改成 `ref readonly`，
`[ForEach]` 参数改成 `in` / `ReadOnlySpan<T>`。

[值索引](/zh/docs/guide/indexes-and-relations#value-indexes)追踪的是 `Set`、`CreateEntity` 和 `CreateEntities`；通过 `ref` 写入会
背着它改掉键。对于实现了 `IIndexed<TKey>` 的组件（或者 `IGroup`，它的[分组](/zh/docs/guide/groups)也是一种键），规则会报出：

- 在实体上调用 `Get<T>()`、`GetOrAdd<T>()` 或 `TryGetRef<T>()`；
- 绑定到它的 `ref` 局部变量，或者通过查询项给它（或它的字段）赋值；
- `[ForEach]` 方法或 `IForEach*` job 里它的 `ref`、`Span<T>`、`Mut<T>` 或 `Maybe<T>` 参数（`Maybe<T>` 给出的是 `ref`；只读就用
  `ReadOnlyMaybe<T>`）。

```csharp
public partial record struct Zone([LookupKey] int Id) : IComponent;
public record struct Portal(int To) : IComponent;
```

```csharp doccheck=expect-EECS015
[EcsSystem]
public ref struct TakePortals
{
    [ForEach] static void Take(ref Zone zone, in Portal portal) => zone = new Zone(portal.To);   // 索引里还是旧区域
}
```

用 `in`、`ReadOnlySpan<T>`、[`ReadOnlyMaybe<T>`](/zh/docs/guide/systems#read-only-maybe)（部分实体没有它时）、`Read<T>()` 或生成的属性读，
用 `Set`（或生成的 `SetX`）写：

```csharp
[EcsSystem]
public ref struct TakePortals
{
    [ForEach]
    static void Take(Entity player, in Zone zone, in Portal portal)
    {
        if (zone.Id != portal.To) player.SetZone(portal.To);         // Set：索引立刻把玩家移过去
    }
}
```

## EECS016 [#eecs016]

**`[Removed<T>]` 方法要求了 `T`。** 错误。没有代码修复。

`[Removed<T>]` 访问的是失去了 `T`、而且现在仍然没有 `T` 的实体。把 `T` 作为参数，或者在同一个方法上用 `[With<T>]`、`[Changed<T>]`
要求它，等于要的是有 `T` 的实体：没有一行能同时满足两者，方法永远不会运行。

```csharp
public record struct Burning(int Ticks) : IComponent, ITracked;
public record struct Replica(int Health, bool Burning) : IComponent;
```

```csharp doccheck=expect-EECS016
[EcsSystem]
public ref struct ReplicateFire
{
    [ForEach, Removed<Burning>]
    static void Out(in Burning burning, ref Replica replica) => replica.Burning = false;   // 实体已经没有 Burning
}
```

读实体的其他组件（行里还保留着它们），“重新添加”或“被写入”放到另一个带 `[Changed<T>]` 的方法里处理：

```csharp
[EcsSystem]
public ref struct ReplicateFire
{
    [ForEach, Changed<Burning>]
    static void Lit(ref Replica replica) => replica.Burning = true;

    [ForEach, Removed<Burning>]                       // 行里的其他组件还在
    static void Out(ref Replica replica) => replica.Burning = false;
}
```

## EECS017 [#eecs017]

**组件里存了 `Entity` 句柄。** 警告。代码修复：在所有用法改完仍能编译时（`.Id`、比较、赋值），把 `Entity` 字段改成 `EntityId`。

`Entity` 持有对它所在 World 的引用，所以带 `Entity` 字段（或者字段的结构体里含有 `Entity`，不论来自本程序集还是别的程序集）的组件或单例，
以及元素含有 `Entity` 的 `DynamicBuffer<T>`，都是托管类型：它的列要被垃圾回收器扫描，每次写入都要付写屏障，
行不能整块复制，[存档](/zh/docs/guide/saves)写不了它，[迁移](/zh/docs/guide/migration-and-unload#entityid-rewriting)也不会改写它。

```csharp doccheck=expect-EECS017
public record struct Chase(Entity Prey) : IComponent;          // 托管列
```

存 `EntityId`（8 字节，非托管；句柄可以隐式转换成它），需要句柄时用 `world.TryGetEntity(id, out var entity)` 换回来，顺便还能知道
实体是否还活着：

```csharp
public record struct Chase(EntityId Prey) : IComponent;

[EcsSystem]
public ref struct ChaseSystem
{
    [ForEach]
    static void Follow(ref Position p, in Chase chase, World world)
    {
        if (world.TryGetEntity(chase.Prey, out var prey)) p = prey.Position;   // 已经没了：id 什么也找不到
    }
}
```

## EECS019 [#eecs019]

**系统顺序成环。** 错误。没有代码修复。

`[UpdateBefore<T>]` 和 `[UpdateAfter<T>]` 说明两个系统谁先运行；环是不可能满足的，添加闭合这个环的系统时 `AddSystem` 会抛异常。
分析器会报出它在本次编译的系统之间看到的环。

```csharp doccheck=expect-EECS019
[EcsSystem, UpdateAfter<B>] public ref struct A { }
[EcsSystem, UpdateAfter<A>]
public ref struct B { }   // A 在 B 之后，B 又在 A 之后
```

去掉其中一个顺序约束：

```csharp
[EcsSystem] public ref struct Movement { }
[EcsSystem, UpdateAfter<Movement>] public ref struct Collision { }
[EcsSystem, UpdateAfter<Collision>] public ref struct Damage { }
```

## EECS020 [#eecs020]

**系统对另一个分组的系统排序。** 警告。没有代码修复。

顺序约束只在一个分组内生效：`World.Update()` 和 `World.Update<TGroup>()` 分别运行各自的分组，先后由调用方决定，所以对另一个分组里的
系统排序永远不会生效。

```csharp doccheck=expect-EECS020
public struct Late : ISystemGroup;
[EcsSystem, UpdateInGroup<Late>] public ref struct Sweep { }
[EcsSystem, UpdateAfter<Sweep>]
public ref struct Movement { }   // Movement 在默认分组里运行
```

只给同一分组的系统排序，或者把系统挪进对方的分组：

```csharp
public struct Late : ISystemGroup;
[EcsSystem, UpdateInGroup<Late>] public ref struct Sweep { }
[EcsSystem, UpdateInGroup<Late>, UpdateAfter<Sweep>] public ref struct Recycle { }
```

## EECS021 [#eecs021]

**`[ForEach]` 入口与另一个方法签名相同。** 错误。没有代码修复。

在系统之外，生成器会为每个 `[ForEach]` 方法写一个重载：先接收 `World`（对 `[Changed<T>]` / `[Removed<T>]` 还要接收变更 tick），
再接收方法的其他值。如果类型里已经有同签名的方法，或者另一个 `[ForEach]` 重载的入口也是这个签名，两者就会冲突。

```csharp doccheck=expect-EECS021
public static class Healing
{
    [ForEach] static void Heal(ref Health hp) => hp.Value++;
    public static void Heal(World world) { }        // 入口 Heal(World) 已经存在
}
```

给其中一个改名：

```csharp
public static class Healing
{
    [ForEach] static void Heal(ref Health hp) => hp.Value++;     // Healing.Heal(world)
    public static void HealAll(World world) => Healing.Heal(world);   // 生成的入口
}
```

`WriteX()` 改成 `.X`，方法从不写入的 `Mut<T>` 改成 `in T`。

`ref` 参数（批量方法里的 `Span<T>`）会把它的类型放进系统的写集合：任何[并行阶段](/zh/docs/guide/threading#parallel-systems)

用 `in` 读：

```csharp
[EcsSystem]
public ref struct ArmorBonus

    [ForEach]
    static void Apply(in Armor armor, ref Health health) => health = new Health(health.Value + armor.Value);
```

**方法没有用到的 `[ForEach]` 参数。** 警告。代码修复：组件改成 `[With<T>]` 过滤条件（已有 `[With<T>]` 或 `[Changed<T>]`

用过滤条件要求这个组件：

## EECS027 [#eecs027]

**参数一次就能拿到的数据，却每行查一次。** 警告。代码修复：把查找的组件或单例改成参数（`in T`，查找里有写入时用 `ref T`），
并把这个类型的每次查找都换成这个参数。

规则覆盖 `[ForEach]` 方法和手写 job 的 `Execute`；job 把组件作为它接口的另一个类型实参传入。

`[ForEach]` 方法的参数按表或按遍解析一次：组件是循环顺着走的一列，单例是循环开始前取好的 `ref`。通过被访问的 `Entity`
（`entity.Velocity`、`entity.Has<T>()`、`entity.TryGet<T>(...)`）或 `World`（`World.Clock`）查同样的数据，每一行都要重新查一遍：
实体记录、所在的表、对应的列。规则只报告每一行都会执行的查询（不在分支、循环里，也不在提前 `return` 之后），并且排除方法自己
添加或移除的组件。带索引的组件也算在内：`in` 参数或 [`ReadOnlyMaybe<T>`](/zh/docs/guide/systems#read-only-maybe) 读它们，
既不用逐行查找，也不会产生 EECS015 禁止的写入。

```csharp doccheck=expect-EECS027
[EcsSystem]
public ref struct Drift
{
    [ForEach]
    static void Move(Entity entity, ref Position position) =>
        position = new Position(position.X + entity.Velocity.X, position.Y + entity.Velocity.Y);
}
```

代码修复在每个类型的第一次查找上提供，前提是这个类型的每次查找都是 `Get`、`Read` 或生成的属性（实体没有该组件时它们会抛异常，
所以改成必须有这个组件，不会改变方法会处理的任何一行）；`TryGet` 或存在性判断、有调用方的方法、批处理方法，以及已经有 9 个组件的方法不提供。

把组件作为参数（`in`、`ref`，部分实体没有它时用 `Maybe<T>`；判断有没有某个组件，用 `Maybe<T>` 或者拆成 `[With<T>]` /
`[Without<T>]` 两个方法；带索引的组件用 `in` 或 `ReadOnlyMaybe<T>`），单例也作为参数：

```csharp
[EcsSystem]
public ref struct Drift
{
    [ForEach]
    static void Move(ref Position position, in Velocity velocity) =>
        position = new Position(position.X + velocity.X, position.Y + velocity.Y);
}
```

## EECS028 [#eecs028]

**每次更新都会执行的代码里有分配。** 警告。无代码修复。

`[ForEach]` 方法对访问到的每个实体都执行一次，`[OnUpdate]` 每次更新执行一次，所以它们分配的内存每个 tick 都会变成垃圾，
由此触发的回收会让整个进程停顿。规则会指出每一个会分配的表达式：对象或数组、捕获变量的 lambda、实例方法组、LINQ、运行时拼出来的
字符串（`$"..."`、`+`、`string.Format`、`ToString()`）、装箱，以及对接口做 `foreach`。不报告的情况：`throw` 里的代码、会被编译器
去掉的调用（`[Conditional]`，例如 `Debug.Assert`）、控制台输出（写入本身比字符串更贵），以及自己标了 `[UpdateInterval]` 的系统的
`[OnUpdate]`（执行频率是作者选的）。规则同样覆盖手写 job 的 `Execute`，以及本来就要分配的冷调用：`TrimExcess`、`Capture()`、
`Describe`、`DescribeTables` 和 `DescribeSchedule` 属于定时器、命令或测试，不属于每次更新。

```csharp doccheck=expect-EECS028
[EcsSystem]
public ref struct Steer
{
    [ForEach]
    static void Aim(in Position position, ref Velocity velocity)
    {
        var path = new List<Position> { position };   // 每个实体、每次更新都新建一个列表
        velocity = new Velocity(-path[0].X, -path[0].Y);
    }
}
```

值放在结构体、span 和 `stackalloc` 里；一行要填充的列表用 [`Scratch<T>`](/zh/docs/guide/threading#scratch) 参数，每个线程一个、用前清空，`[ForEach]` 方法的消息会指出它；传数值，不传字符串：

```csharp
[EcsSystem]
public ref struct Steer
{
    [ForEach]
    static void Aim(in Position position, ref Velocity velocity)
    {
        Span<Position> path = stackalloc Position[1];
        path[0] = position;
        velocity = new Velocity(-path[0].X, -path[0].Y);
    }
}
```

## EECS030 [#eecs030]

**对查询结果逐个实体做结构变化。** 警告。代码修复：改成批量调用。

逐个实体做结构变化，每次调用只移动（或翻转）一行，每次都要经过结构闸门。`SetAll`、`RemoveAll`、`DisableAll`、`EnableAll`
和 `DestroyAll` 会一起修改一张表里所有匹配的行，一次处理整字的行（[批量修改](/zh/docs/guide/bulk)）。规则报告这样的
`foreach`：遍历 `world.Query<...>()`，循环体只有一个这类调用，作用在 item 的实体上，且每一行用的值都一样。对查询已经要求的

```csharp doccheck=expect-EECS030
foreach (var item in world.Query<Health>(QueryFilter.Create().With<Dead>()))
    item.Entity.Destroy();
```

一次调用：

```csharp
world.DestroyAll<Health>(QueryFilter.Create().With<Dead>());
```

`[ForEach]` 方法的整个方法体只是对自己实体的这样一个调用时，它就是同一个循环，只是由生成器写出来。调用参数不用任何参数、
方法的过滤条件都能放进 `QueryFilter`（没有 `[Changed<T>]` 或 `[Removed<T>]`，没有分帧）时，规则会报告它。没有代码修复：
调用要挪进系统的 `[OnUpdate]`，方法本身删掉。

```csharp doccheck=expect-EECS030
[EcsSystem]
public ref struct CorpseSystem
{
    [ForEach, With<Dead>]
    static void Bury(Entity entity) => entity.Destroy();
}
```

每次更新一次调用：

```csharp
[EcsSystem]
public ref struct CorpseSystem
{
    [OnUpdate]
    static void OnUpdate(World world) => world.DestroyAll<Dead>();
}
```

## EECS031 [#eecs031]

**在计数循环里逐个创建实体。** 警告。代码修复：改成批量调用，或在循环前预留容量。

逐个创建时，表和实体存储按倍增扩容；如果 World 从没装过这么多实体，被丢弃的数组可能触发一次完整的垃圾回收
（[D28](/zh/docs/decisions#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap)）。`CreateEntities` 和
`Instantiate(prefab, span)` 一遍就能创建完；每个实体的值各不相同时，先用 `Reserve` 预留空间。规则不报告这些循环：
次数是小于 4,096 的常量，或者遍历的是用这样的常量创建的数组（没有数组会进入大对象堆）；前面已经预留过容量；只在分支里或内层循环里创建；
在系统里（运行中的 World会复用已有的行）。这样的循环里用相同的值调用 `Instantiate(prefab)` 或 `Instantiate(prefab, in c1..cn)`
也会报告，修复是改成批量形式 `Instantiate(prefab, entities, in c1..cn)`。

```csharp doccheck=expect-EECS031
var wave = new Entity[50_000];
for (int i = 0; i < wave.Length; i++)
    wave[i] = world.CreateEntity(new Position(0, 0), new Health(100));
```

值都一样时用一次调用，不一样时先预留：

```csharp
var spawned = new Entity[50_000];
world.CreateEntities(spawned, new Position(0, 0), new Health(100));

world.Reserve<Position, Health>(spawned.Length);
for (int i = 0; i < spawned.Length; i++)
    world.CreateEntity(new Position(i, 0), new Health(100));
```

## EECS033 [#eecs033]

每个成员都调用对应的泛型 API：调用相同，代价也相同，所以这条规则是建议而不是警告。只有当该成员在当前编译里确实生成了、而且行为完全相同（包括返回的引用种类）时，规则才会建议：

## EECS035 [#eecs035]

**无效的 `[ForEach(Slices = N)]`。** 错误。没有代码修复。

分帧的方法每次系统运行只访问每张匹配表的一片，所以每一行每 N 次运行被访问一次。`Slices` 至少为 1。`[Changed<T>]`、
`[Removed<T>]`、`[ChangedAny<…>]` 或 `[RemovedAny<…>]` 方法选的是系统上次运行以来变过的行，而每次运行都会把这个 tick 往前推：
这次没访问到的那几片里的行，变更就永远丢了。

```csharp doccheck=expect-EECS035
[EcsSystem]
public ref struct SendFire
{
    [ForEach(Slices = 4), Changed<Burning>]
    static void Send(in Burning burning, ref Replica replica) => replica.Burning = burning.Ticks > 0;   // 四个分帧里有三个会丢掉变化
}
```

每次运行都读变更：变更过滤条件本来就只访问写过的行。要分帧的是没有变更过滤条件、对每个实体都很重的逐行工作：

```csharp
[EcsSystem]
public ref struct SendFire
{
    [ForEach, Changed<Burning>]
    static void Send(in Burning burning, ref Replica replica) => replica.Burning = burning.Ticks > 0;
}
```

切法和节奏见[分帧](/zh/docs/guide/systems#slices)。

## EECS036 [#eecs036]

**无法按键建索引的组件。** 错误。没有代码修复。

World 按键给 `IIndexed<TKey>` 或 `IUniqueIndexed<TKey>` 组件建索引，并用这个索引检查唯一组件的每一次写入。规则报出行不通的声明：

- **`EntityId` 键。** 加载和迁移会在拷完行之后才改写 `EntityId` 的值，来不及先检查，所以关系键不能是唯一的。
- **第二个键。** 一个组件只建一个索引：它身上的第二个 `IIndexed<TKey>` 或 `IUniqueIndexed<TKey>`，无论唯一与否，永远建不了索引，
  `world.Index` 会为它抛异常。
- **特性声明不了的键或分组。** `[LookupKey]` / `[UniqueKey]` 成员的类型不是自身的 `IEquatable`、和结构体声明的索引接口类型不同、旁边还有第二个键，
  或旁边又手写了 `Key`；`[Group]` 成员不是 `int` 或基于 `int` 的枚举，或者有第二个。

```csharp doccheck=alone,expect-EECS036
public partial record struct Mount([UniqueKey] EntityId Rider) : IComponent;
```

关系用 `[LookupKey]`（`IIndexed<EntityId>`）建索引；第二个键放到单独的组件里：


## EECS037 [#eecs037]

**job 的 `WriteMask` 与 `Execute` 实际写入的不一致。** 警告。代码修复：改成 `Execute` 需要的 `WriteMask`。

第 `k - 1` 位，`-1` 表示全部，也是默认值）。循环会给它列出的[追踪变化的组件](/zh/docs/guide/change-tracking)在访问的每一行上打 tick，

这次变化；`Execute` 只读的追踪组件仍会在每一行上被打 tick，`[Changed<T>]` 系统就会去处理没人改过的行。规则用与 EECS025 相同的判定，


```csharp doccheck=expect-EECS037
public struct Recharge : IForEach<Shield>
{
    public void Execute(ref Shield shield) => shield = new Shield(shield.Value + 1);
    public static int WriteMask => 0;   // 写了 Shield，却从不打 tick
}
```

写明 `Execute` 写了什么：

```csharp
public struct Recharge : IForEach<Shield>
{
    public void Execute(ref Shield shield) => shield = new Shield(shield.Value + 1);
    public static int WriteMask => 0b1;
}
```

`[ForEach]` 方法不需要这些：生成器根据参数写出它的 job。

## EECS053 [#eecs053]

**追踪变化的组件以 `ref` 传入，却只在部分行上写入。** 警告。代码修复：`Mut<T>`。

[追踪变化的组件](/zh/docs/guide/change-tracking)（`ITracked`，以及所有 `DynamicBuffer<T>`）的 `ref` 参数会给方法访问到的每一行打 tick，
不管写没写。方法只在部分行上写它（提前 `return`、写在 `if` 里、循环可能一次都不执行），没动的行也被打了 tick，于是每个 `[Changed<T>]`
系统都会再访问它们一遍：同步把它们再发一次，存档把它们再写一次。[`Mut<T>`](/zh/docs/guide/change-tracking#set-if-changed)
参数只给它写过的行打 tick：通过 `Write()`，或者值确实变了的 `SetIfChanged`
（[D66](/zh/docs/decisions#d66-a-ref-written-on-some-rows)）。

规则沿着方法的控制流检查：逐实体的 `[ForEach]` 方法里，追踪变化的组件的 `ref` 参数，只要有一条从开头出发的路径不写它就走到结尾或
`return`，就报出来。抛异常的路径不算；在 `finally` 里写这个参数的方法不报。方法从来不写的参数归 [EECS025](#eecs025)。批量方法不报：
它的 span 按整段行打 tick，而 `Mut<T>` 是逐实体的参数。

```csharp
public record struct Location(int X, int Y) : IComponent, ITracked;
```

```csharp tab="报告" doccheck=expect-EECS053
[EcsSystem]
public ref struct RespawnSystem
{
    [ForEach]
    static void Respawn(ref Health health, ref Location location)
    {
        if (health.Value > 0) return;   // 活着的直接返回，它们的 Location 照样被打 tick
        health = new Health(100);
        location = new Location(0, 0);
    }
}
```

```csharp tab="修正"
[EcsSystem]
public ref struct RespawnSystem
{
    [ForEach]
    static void Respawn(ref Health health, Mut<Location> location)
    {
        if (health.Value > 0) return;
        health = new Health(100);
        location.Write() = new Location(0, 0);
    }
}
```

修复把参数改成 `Mut<T>`，对它的每次写入改成 `x.Write()`，每次读取改成 `x.Value`，方法做的事不变。参数除了 `ref` 还有别的修饰符
（`scoped ref`）、有代码调用这个方法、方法体在 `nameof` 里用到参数或重新绑定它（`x = ref other`）时，不提供修复。如果几乎每一行都走写入的
路径，又没有系统读这个组件的 `[Changed<T>]`，`ref` 每段行打一次 tick 反而更便宜：在那里压掉这条警告。

## EECS054 [#eecs054]

**不合法的 `[ForEach(ChunkRows = N)]`。** 错误。代码修复：去掉 `ChunkRows`；之前跳过这个方法的生成器会重新生成它。

`ChunkRows` 是[并行方法](/zh/docs/guide/threading#chunk-rows)的一个线程每次取的行数：0 表示由运行时按测得的每行开销决定，大于 0 则指定
（向上取整到 64）。没有 `Parallel = true` 的方法只在一个线程上跑，没有块可言；负数没有意义。

```csharp tab="报告" doccheck=expect-EECS054
[EcsSystem]
public ref struct PlanRoutes
{
    const int Steps = 4_096;

    [ForEach(ChunkRows = 64)]   // 单线程：没有块可设大小
    static void Plan(in Position from, ref Velocity heading)
    {
        float x = from.X;
        for (int i = 0; i < Steps; i++) x = MathF.Sqrt(x * x + 1);   // 重活：每行几微秒
        heading = new Velocity(x, from.Y);
    }
}
```

```csharp tab="修正"
[EcsSystem]
public ref struct PlanRoutes
{
    const int Steps = 4_096;

    [ForEach(Parallel = true, ChunkRows = 64)]
    static void Plan(in Position from, ref Velocity heading)
    {
        float x = from.X;
        for (int i = 0; i < Steps; i++) x = MathF.Sqrt(x * x + 1);   // 重活：每行几微秒
        heading = new Velocity(x, from.Y);
    }
}
```

改成并行（像这里，几百行重活），或者去掉 `ChunkRows`。轻量的行两者都不需要：保持默认的块（[什么时候设](/zh/docs/guide/threading#chunk-rows)）。

## EECS055 [#eecs055]

**一行一行执行的 `[ForEach]` 方法。** 建议（信息级别）。没有代码修复。

符合条件的 `[ForEach]` 方法会被生成器写成[向量循环](/zh/docs/guide/systems#vector-loops)。一个看起来就是为向量循环写的方法（静态、
只接收由普通值组成的组件、单例和值），只要缺了一个条件，就会收到这条消息，消息里写出第一个原因：组件对方法在它身上做的工作来说太宽、有 `bool`
字段、循环没有向量版本的调用、写入的目标不是 lane。方法只用到宽组件的少数字段时，消息末尾会列出它们：把它们拆成自己的组件。它相当于 Burst 的
Inspector：构建时就知道哪个方法保持标量、为什么，[`DescribeSchedule()`](/zh/docs/guide/systems#vector-loops) 还会列出每个方法的循环。
方法照样正确运行，只是一行一行地跑。

```csharp tab="报告" doccheck=expect-EECS055
public struct Ship : IComponent { public float X, Y, Z, VX, VY, VZ, Fuel, Heat; }   // 8 个字段

[EcsSystem]
public ref struct Burn
{
    // “component Ship has 8 fields (a vector loop splits up to 4), and gathering the 1 field it uses takes ... permutes
    // per 16 rows, more than its 1 vector operation gains; it uses 1 of Ship's 8 fields (Fuel): move it into a
    // component of its own (a component of one field gets a vector loop)”
    [ForEach]
    static void Spend(ref Ship ship) => ship.Fuel -= 0.01f;
}
```

```csharp tab="修正"
public struct Ship : IComponent { public float X, Y, Z, VX, VY, VZ, Heat; }
public struct Fuel : IComponent { public float Value; }   // Spend 修改的数据，放进它自己的组件

[EcsSystem]
public ref struct Burn
{
    [ForEach]
    static void Spend(ref Fuel fuel) => fuel.Value -= 0.01f;
}
```

按消息改，或者给本来就该保持标量的方法（行很少，或者方法体循环接不了）加 `[ForEach(SimdMode = SimdMode.Off)]` 让它不再提示。
它是建议级别，只在 IDE 里显示；`.editorconfig` 里写 `dotnet_diagnostic.EECS055.severity = warning`，构建时就会列出所有保持标量的方法。

## EECS057 [#eecs057]

第二个 `Reduce<T>`，或者同一个方法的 `ref T` 参数，在同一遍里也写 `T`：一个结果会悄悄覆盖另一个。

```csharp tab="报告" doccheck=alone,expect-EECS057
    [ForEach, With<Dead>]   // 第二个 Reduce<Census>：阵亡者的总和会覆盖存活者的
    static void Fallen(in Health health, ref Reduce<Census> census) => census.Value.Health += health.Value;
}
```


## EECS058 [#eecs058]

**把临时内存存进了 World。** 错误。没有代码修复。

[`Scratch<T>`](/zh/docs/guide/threading#scratch) 的值属于运行方法的线程，这个线程接下来运行的行（任何一遍的）都会复用它。把它持有的东西
（列表、数组、span、持有它们的结构体）的引用存进组件、单例、`Maybe`、`Mut` 或 `Reduce`，就把这块内存交给了实体：之后的行会在实体不知情时改掉它，
并行遍历时还是在别的线程上改。

```csharp tab="报告" doccheck=expect-EECS058
public struct Route : IComponent
{
    public int[] Steps;
}

[EcsSystem]
public ref struct ChartRoutes
{
    [ForEach(Parallel = true)]
    static void Chart(in Position position, ref Route route, Scratch<int[]> steps)
    {
        steps.Value ??= new int[16];
        for (int i = 0; i < steps.Value.Length; i++) steps.Value[i] = (int)position.X + i;
        route.Steps = steps.Value;   // 这个线程的下一行会改写这个实体的路线
    }
}
```

```csharp tab="修正"
public record struct Route(int First, int Last) : IComponent;

[EcsSystem]
public ref struct ChartRoutes
{
    [ForEach(Parallel = true)]
    static void Chart(in Position position, ref Route route, Scratch<int[]> steps)
    {
        var buffer = steps.Value ??= new int[16];
        for (int i = 0; i < buffer.Length; i++) buffer[i] = (int)position.X + i;
        route = new Route(buffer[0], buffer[^1]);   // 这一行的结果，拷进它自己的组件
    }
}
```

把这一行算出的东西拷进组件自己的存储（值，或者[动态缓冲](/zh/docs/guide/dynamic-buffers)），或者一开始就把数据放在组件里。

## EECS059 [#eecs059]

（`ref`、`Mut`、可写的 `Maybe` 或 span 参数）时，会读到一些写入之前的行、一些写入之后的行，并行时还会读到别的线程正在写的行。

```csharp tab="报告" doccheck=expect-EECS059
            position = new Position((position.X + leader.Value.X) / 2, (position.Y + leader.Value.Y) / 2);

}
```


通过参数读实体自己的 `T`，把结果写进另一个组件，再在之后的系统里拷回去（双缓冲，就是 GPU 的乒乓），或者把这件事拆成两个系统。

## EECS060 [#eecs060]

**在多个线程上运行的代码写共享内存。** 警告。没有代码修复。

`[ForEach(Parallel = true)]` 方法，以及由 `ForEachParallel`、`ForEachEntityParallel`、`ForEachBatchParallel` 或 `world.ForParallel` 运行的 job 的 `Execute`，会同时在多个线程上跑，
每个线程一块行。静态字段或自动属性、上下文参数引用的对象、job 字段持有的对象（每一块的 job 副本共享它），对所有线程都是同一块内存：
自增会丢更新，列表的 `Add` 会把列表写坏，普通写入最后留下哪个取决于时机。规则不报：每个线程都写同一个常量、`[ThreadStatic]` 字段、
并发集合、`Interlocked` 和 `Volatile` 调用、`lock` 里的写入、数组和列表的元素（不同的行可以各占不同的元素）以及局部变量。

```csharp tab="报告" doccheck=expect-EECS060
public static class HitStats
{
    public static int Hits;
}

[EcsSystem]
public ref struct TakeHits
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health)
    {
        health = new Health(health.Value - 1);
        HitStats.Hits++;   // 每个线程都对同一个 int 自增：更新会丢
    }
}
```

```csharp tab="修正"
public partial struct Hits : ISingletonComponent
{
    [Sum] public int Count;
}

[EcsSystem]
public ref struct TakeHits
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health, ref Reduce<Hits> hits)
    {
        health = new Health(health.Value - 1);
        hits.Value.Count++;   // 这一块的部分计数，这一遍结束时合并
    }
}
```

总数放进 [`Reduce<T>`](/zh/docs/guide/threading#reductions) 单例；每个实体的结果放进它这一行的组件，由这一遍之后的系统读取。
每行一次 `Interlocked` 调用也能消掉这条警告，代价是每行都争抢同一条缓存行。

## EECS086 [#eecs086]

**每次更新都会重置、再逐行累加的单例。** 建议（信息级别）。没有代码修复。

这一遍的每一行都写同一个 `ref` 单例参数，于是有两个后果。方法不能并行，因为每一块都会争用这个单例（[EECS010](#eecs010)）。
它的向量循环也没有通道来放这个单例。[`ref Reduce<T>`](/zh/docs/guide/threading#reductions) 参数给每一块一个自己的部分结果，
从 `T` 的单位元开始，遍历结束时把各个部分结果合并进 `T`。和、最小值、最大值都一样，但方法可以用 `Parallel = true`，也能进向量循环。

这一遍的结果会替换 `T`。所以这条规则只报告系统代码在 `[OnCreate]` 之外重置的单例：整体赋值、给字段赋常量、`AddSingleton`、
`RemoveSingleton`，或者生成的 `SetX`、`RemoveX`。这样的单例存的是一遍的结果，归约让它的重置变得多余。跨更新增长的总数（分数、
到目前为止的死亡数）从不重置，这条规则不管它。

参数的每一次使用都在累加某个字段时才报告：`+=`、`-=`、`++`、`--`、`*=`、bool 的 `|=` 和 `&=`、对这个字段取 `Math.Max` 或
`Math.Min`，或者 `if (x > s.F) s.F = x;`。每个字段只能用一种方式累加，消息会给出声明它们的特性。

```csharp tab="报告" doccheck=alone,expect-EECS086

{
    public int Alive;
    public int Strongest;
}

[EcsSystem]
public ref struct CountCrowd
{
    [OnUpdate]
    static void OnUpdate(World world) => world.Crowd = default;   // 每次更新重新计数

    [ForEach]
    static void Count(in Health health, ref Crowd crowd)
    {
        crowd.Alive++;
        crowd.Strongest = Math.Max(crowd.Strongest, health.Value);
    }
}
```

```csharp tab="修正"
public partial struct Crowd : ISingletonComponent
{
    [Sum] public int Alive;
    [Max] public int Strongest;
}

[EcsSystem]
public ref struct CountCrowd
{
    [ForEach(Parallel = true)]
    static void Count(in Health health, ref Reduce<Crowd> crowd)
    {
        crowd.Value.Alive++;
        crowd.Value.Strongest = Math.Max(crowd.Value.Strongest, health.Value);
    }
}
```

没有代码修复，因为另一个方法里的重置也得一起删掉。它是建议，只在 IDE 里显示，而且要等完整分析结束才出现，因为重置可能在任何一个文件里。

## EECS087 [#eecs087]

**通过 `World` 读取其他实体的组件。** 警告。没有代码修复。

接收 `World` 的 `[ForEach]` 方法可能做结构变更。所以它的系统在自己的阶段里单独运行，遍历它的行时也要做结构变更需要的检查。
假设这个方法用 `World` 只是为了找到其他实体（`TryGetEntity`、`GetEntity`），并从它们身上读取自己不写的组件。那么每个组件一个
[`Lookup<T>`](/zh/docs/guide/threading#lookups) 参数就能做同样的事，不需要 `World`：`lookup[id]` 是 `ReadOnlyMaybe<T>`，`Read(id)`
是 `ref readonly`，`Has(id)` 判断有没有。系统按这些组件的读者调度，和不写它们的系统共用一个阶段，方法也可以并行。

```csharp tab="报告" doccheck=alone,expect-EECS087
public record struct Quarry(EntityId Id) : IComponent;
public record struct Heading(float X, float Y) : IComponent;

[EcsSystem]
public ref struct Pursuit
{
    [ForEach]
    static void Steer(in Position position, in Quarry quarry, ref Heading heading, World world)
    {
        heading = default;
        if (world.TryGetEntity(quarry.Id, out var target))
        {
            var at = target.Read<Position>();
            heading = new Heading(at.X - position.X, at.Y - position.Y);
        }
    }
}
```

```csharp tab="修正"
public record struct Quarry(EntityId Id) : IComponent;
public record struct Heading(float X, float Y) : IComponent;

[EcsSystem]
public ref struct Pursuit
{
    [ForEach(Parallel = true)]
    static void Steer(in Position position, in Quarry quarry, ref Heading heading, Lookup<Position> positions)
    {
        var at = positions[quarry.Id];
        heading = at.HasValue ? new Heading(at.Value.X - position.X, at.Value.Y - position.Y) : default;
    }
}
```

还会写另一个实体、做结构变更、或者读取自己也写的组件（[EECS059](#eecs059)）的方法，保留 `World`。

## EECS088 [#eecs088]

**同一个流的两次 `EntityRandom` 抽取。** 警告。代码修复：给后一次抽取一个方法里没有用过的流。

[`EntityRandom`](/zh/docs/reference/entityrandom) 的数是种子、实体、tick 和流的纯函数。同一遍里对同一个实体、用同一个流抽两次，
得到的是同样的比特：方向的 X 永远等于 Y，命中骰永远等于伤害骰。循环里的抽取也一样：如果循环不改变它的流和实体，每次迭代都拿到同一个数。
把迭代加进流里（`stream + (uint)i`），这种情况没有唯一的机械改法。这条规则检查 `[ForEach]`、`[ForEntity]` 方法和 job 的 `Execute`，
在那里每一行每次更新抽一次。有意比较两次抽取的测试不报告。

```csharp tab="报告" doccheck=alone,expect-EECS088
public record struct Sway(float X, float Y) : IComponent;

[EcsSystem]
public ref struct Flutter
{
    [ForEach(Parallel = true)]
    static void Step(ref Sway sway, Entity entity, in EntityRandom random) =>
        sway = new Sway(random.Range(entity.Id, 0, -1f, 1f), random.Range(entity.Id, 0, -1f, 1f));   // X == Y
}
```

```csharp tab="修正"
public record struct Sway(float X, float Y) : IComponent;

[EcsSystem]
public ref struct Flutter
{
    [ForEach(Parallel = true)]
    static void Step(ref Sway sway, Entity entity, in EntityRandom random) =>
        sway = new Sway(random.Range(entity.Id, 0, -1f, 1f), random.Range(entity.Id, 1, -1f, 1f));
}
```

`if` 的两个分支、`switch` 的不同分支里的抽取不会一起执行，可以共用一个流。

## EECS089 [#eecs089]

**逐行追加到单例列表里的记录。** 建议（信息级别）。没有代码修复。

单例持有的列表、通过 `ref` 参数填充，就是每一行都在写的同一个列表。方法不能并行，列表也随着记录进来不断翻倍扩容。
[`Emit<T>`](/zh/docs/reference/emit) 参数给每一块行一个池化的列表，遍历结束时按块的顺序把这些列表追加到 `Emitted<T>`。
记录还是那些记录、顺序还是行的顺序，单线程和多线程都一样。遍历之后的系统读取 `world.GetSingleton<Emitted<T>>().Items` 并清空它（[EECS070](#eecs070)）。

```csharp tab="报告" doccheck=alone,expect-EECS089
public record struct Shot(EntityId From, float Power);
public record struct Gun(float Power) : IComponent;
public struct Volley : ISingletonComponent { public List<Shot> Shots; }

[EcsSystem]
public ref struct Fire
{
    [ForEach]
    static void Pull(Entity entity, in Gun gun, ref Volley volley) => volley.Shots.Add(new Shot(entity.Id, gun.Power));
}
```

```csharp tab="修正"
public record struct Shot(EntityId From, float Power);
public record struct Gun(float Power) : IComponent;

[EcsSystem]
public ref struct Fire
{
    [ForEach(Parallel = true)]
    static void Pull(Entity entity, in Gun gun, Emit<Shot> shots) => shots.Add(new Shot(entity.Id, gun.Power));
}
```

没有代码修复，因为列表的读者得改为读取 `Emitted<T>`。

## 从类系统迁移 [#migration-fix]

为 EasyEcs 4.7 及更早版本写的代码让系统继承 `EcsSystem` 基类，这个基类已经不存在了，所以编译器在基类上报 CS0246。IDE 在这个错误上
提供一个修复，把类改写成 `[EcsSystem]` ref struct（[迁移指南](/zh/docs/migration#v4-8-systems)）：

- 每个成员改成 static，`private` / `protected` 改成 `internal`；
- `OnCreate`、`OnUpdate` 和 `OnDestroy` 的重写改成 `[OnCreate]`、`[OnUpdate]` 和 `[OnDestroy]` 方法；
- `World` 改成 `World world` 参数，`RunCount`、`LastRunTick`、`Enabled`、`Error` 和 `Stats` 改为通过 `SystemHandle system` 参数读取，
  参数只加到用到它（或调用了用到它的方法）的方法上。

```csharp tab="之前" doccheck=skip
public class WaveSystem : EcsSystem
{
    protected override void OnUpdate()
    {
        if (RunCount % 600 == 0) World.GetOrAddWave().Number++;
    }
}
```

```csharp tab="之后"
public record struct Wave(int Number) : ISingletonComponent;

[EcsSystem]
internal ref struct WaveSystem
{
    [OnUpdate]
    static void OnUpdate(World world, SystemHandle system)
    {
        if (system.RunCount % 600 == 0) world.GetOrAddWave().Number++;
    }
}
```

只有在类之外不需要跟着改任何东西时才提供这个修复：没有构造函数参数（它们改成宿主设置的
[`[NotSaved]`](/zh/docs/guide/saves#not-saved) 单例），没有抽象基类（共用的代码放进静态类或泛型系统），也没有读系统簿记的
`[ForEach]` 方法。

## 未使用成员警告 [#never-used]

生成的代码通过 `UnsafeAccessor` 按名字调用 `[ForEach]`、`[ForEntity]` 和钩子方法，IDE 的“私有成员未使用”分析器不把这算作使用。
包里的一个抑制器只在这些方法上隐藏这类警告：EECSS01 对应 IDE0051（从未使用），EECSS02 对应 IDE0052（从未读取）。Rider 和 ReSharper
改为读取这些特性带的 JetBrains `[MeansImplicitUse]`（[D107](/zh/docs/decisions#d107-never-used-warnings)）。其他成员上什么都不抑制，
所以没有方法调用的私有辅助函数照样会报。
