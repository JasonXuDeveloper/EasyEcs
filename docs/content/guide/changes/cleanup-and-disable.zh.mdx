服务器里有四种常见的生命周期需求，每种都用数据解决。持有 socket 的会话必须恰好关闭一次，哪怕它是被批量销毁的：
**清理组件**让实体留下来，直到某个系统把资源释放掉。被眩晕暂停的冷却必须保留剩余时间：**`Disable<T>()`** 隐藏组件但保留它的值。
回到对象池的子弹要退出所有系统，但不能被销毁：用**标签**加 `Without<T>` 整体关闭实体。欢迎新玩家的系统得认出谁是新来的：
用 **`Spawned` 标签**标记它们。

## 什么时候用 [#when-to-use-it]

<Callout type="idea" title="适合">
  清理组件：World 之外、必须恰好释放一次的东西（socket、座位、租约、文件句柄、另一个服务里的名额）。`Disable<T>()`：
  暂停一段时间、值要保留的组件（眩晕期间的冷却、过场动画期间的 AI 行为）。标签：暂时搁置的整个实体（对象池、休眠区域、
  正在重连的玩家）。
</Callout>

<Callout type="warn" title="不适合">
  World 自己管理的状态不需要清理组件：销毁实体就释放了。能用一个系统会读的标签表达的状态，不必用 `Disable<T>()`：标签更清楚。
  “默认跳过”的整实体禁用是有意不提供的，见[禁用整个实体](#disable-an-entity)。
</Callout>

## 怎么用 [#how-to-use-it]

### 清理组件 [#cleanup-components]

对持有 `ICleanupComponent` 的实体调用 `Destroy` 不会释放它，而是让它退休。它失去其他所有组件，得到 `Retired` 标签（`entity.IsRetired`），一直活到最后一个清理组件被移除：

```csharp
public record struct Seat(int Number) : ICleanupComponent;   // World 之外的资源
public record struct Seats(int Released) : ISingletonComponent;
```

```csharp title="ReleaseSeats.cs"
[EcsSystem]
public ref struct ReleaseSeats
{
    [ForEach, With<Retired>, With<Seat>]                    // 只处理已退休的实体   // [!code highlight]
    static void Release(Entity entity, ref Seats seats)
    {
        seats.Released++;                                     // 在这里归还座位
        entity.RemoveSeat();                                  // 最后一个清理组件没了：实体被释放
    }
}
```

```csharp
world.AddSingleton<Seats>();
world.AddSystem<ReleaseSeats>();
var guest = world.CreateEntity(new Seat(7), new Health(10));

guest.Destroy();                       // 退休：仍然存活，带 Retired 标签，Health 没了
world.Update();                        // ReleaseSeats 释放它：guest.IsAlive 为 false
```

- 所有销毁途径都会让这类实体“退休”：`Destroy`、`DestroyAll<T>()`、[层级](/zh/docs/guide/hierarchy)级联、
  [目标策略](/zh/docs/guide/indexes-and-relations#target-policies)。
- 申请资源的系统用 `Without<Retired>` 过滤：退休的实体还留着清理组件，不过滤的话，它离开以后还可能再申请一次：

```csharp
public record struct NextSeat(int Number) : ISingletonComponent;

[EcsSystem]
public ref struct AssignSeats
{
    [ForEach, Without<Retired>]                            // 已经离开的实体不再分配座位 // [!code highlight]
    static void Assign(ref Seat seat, ref NextSeat next)
    {
        if (seat.Number != 0) return;                        // 已经有座位
        next.Number++;
        seat = new Seat(next.Number);                        // 在这里占座
    }
}
```

- 再次销毁已退休的实体没有任何效果。从存活实体上移除清理组件，就只是移除而已。
- 退休的实体会离开它所在的索引，它的子实体也随之而去。它的其他组件被拿掉，但不算移除：`[Removed<T>]` 不会访问它，
  就像不会访问任何已销毁的实体一样（[移除检测](/zh/docs/guide/change-tracking#removal-detection)）。
- 退休的实体不会被带回来：过滤条件没写 `Retired`（`With<Retired>()`）时 `SetAll` 不会碰它，`Clone()` 会抛异常，
  `MoveEntities` 会跳过它。清理组件的 `RemoveAll` 会处理到它，因为释放它靠的就是这个。
- `MoveEntities` 不带走清理组件：原实体带着它们退休，另一个 World 里的新实体没有它们。
- 清理组件不能被禁用（`Disable<T>()` 会抛异常）：它必须留着等待释放。

### 清理组件还是销毁日志 [#cleanup-or-destroy-log]

[销毁日志](/zh/docs/guide/change-tracking#destroy-log)（`WorldOptions.DestroyLogCapacity`、`world.DestroyedSince`）同样能对实体离开做出反应。
两者解决的是不同的问题：

| | 清理组件 | 销毁日志 |
| --- | --- | --- |
| 用来 | 在实体离开前，拿组件最后的值执行代码：关掉它的 socket，还回它的座位 | 告诉读者哪些实体走了：向客户端同步，或者维护你自己在 World 之外的索引 |
| 读者拿到什么 | 实体本身，还活着，带 `Retired` 标签和它的清理组件 | 只有 `EntityId`：实体已经没了，值也跟着没了 |
| 读者数量 | 只有一条释放路径：最后一个清理组件移除时实体才释放 | 任意多个，各自从自己的 tick 读起（每个客户端读到它确认过的 tick） |
| 会不会漏 | 不会：实体一直等它的系统来处理 | 落后超过环大小的读者会被告知要重新同步（`DestroyedSince` 返回 `false`） |
| 开销 | 释放之前留着一行退休的数据 | 一个固定大小的环，每条记录 16 字节，默认关闭 |

会话持有 socket、客户端又要同步它的时候，两个一起用：清理组件关掉 socket，日志通知每个客户端会话没了。带清理组件的实体在真正释放时
（最后一个清理组件被移除）才记进日志，退休时不记，因为在那之前它还活着。

### 禁用组件 [#disable-a-component]

`Disable<T>()` 保留 `T` 的值，但把它藏起来：在 `Enable<T>()` 还回来之前，查询、`Has` 和 `Get` 都当实体没有 `T`。实体会得到
`Disabled<T>` 标签，可以直接查询。

```csharp
public record struct Cooldown(int Ticks) : IComponent;

[EcsSystem]
public ref struct TickCooldowns
{
    [ForEach]
    static void Tick(ref Cooldown cooldown) => cooldown.Ticks--;
}
```

```csharp
world.AddSystem<TickCooldowns>();
var caster = world.CreateEntity(new Cooldown(3));

caster.DisableCooldown();               // 被眩晕：冷却暂停，值保留 // [!code highlight]
world.Update();                         // TickCooldowns 跳过它
bool paused = caster.IsCooldownDisabled;
int stunnedCasters = world.Count<Disabled<Cooldown>>();

caster.EnableCooldown();                // 回来时 Ticks 仍是 3
```

| 调用 | 效果 |
| --- | --- |
| 生成的 `DisableX()` / `Disable<T>()` | 隐藏 `T`，保留值，加上 `Disabled<T>`。实体没有 `T` 时返回 false |
| 生成的 `EnableX()` / `Enable<T>()` | 还回保留的值。`T` 没被禁用时返回 false |
| 生成的 `IsXDisabled` / `IsDisabled<T>()` | 实体是否带有 `Disabled<T>` |
| 对被禁用的 `T` 调用 `Set(new T(...))` | 替换它：重新启用，值是新的 |
| 对被禁用的 `T` 调用 `GetOrAdd<T>()` | 带着保留的值重新启用（和 `Enable` 一样），不是默认值 |
| 对被禁用的 `T` 调用 `Remove<T>()` / `world.RemoveAll<T>(filter)` | 丢弃它：没有可启用的了 |
| `world.DisableAll<T>(filter)` / `EnableAll<T>(filter)` | 对所有匹配实体做同样的事，见[批量操作](/zh/docs/guide/bulk) |

禁用对 `[Removed<T>]` 来说算一次移除，启用对 `[Changed<T>]` 来说算一次写入，所以[同步](/zh/docs/guide/change-tracking#removal-detection)
两边都能看到。被索引的组件在禁用期间离开索引。保留的值在挪行、克隆、快照和存档中都不会丢。

### 禁用整个实体 [#disable-an-entity]

EasyEcs 没有“查询默认跳过”的禁用实体。用一个标签加 `Without<T>` 实现，而且在需要的地方明确写出来：

```csharp
public struct Inactive : IComponent;                         // 整个实体关闭
public struct Bullet : IComponent;

[EcsSystem]
public ref struct MoveBullets
{
    [ForEach, Without<Inactive>]                             // 要跳过它的系统自己说明 // [!code highlight]
    static void Move(ref Position p, in Velocity v)
    {
        p.X += v.X;
        p.Y += v.Y;
    }
}
```

```csharp
var bullet = world.CreateEntity(new Position(0, 0), new Velocity(1, 0), new Bullet());
world.Update();                                              // 子弹飞行
bullet.SetInactive();                                        // 回到对象池：第一次之后只翻转一个位
bullet.SetPosition(5, 5).RemoveInactive();                   // 重新使用
int pooled = world.Count<Bullet>(QueryFilter.Create().With<Inactive>());   // 存档、清理、统计都能看到所有实体
```

为什么用标签（[决策 D8](/zh/docs/decisions#d8-no-whole-entity-disable)）：默认排除会让每个查询都依赖一个它没写出来的状态。
必须看到所有实体的存档、清理或统计，都得记得重新把它们包含进来，忘了就悄无声息地出错。标签是生成器和读代码的人都看得见的数据。

| | Friflo.Engine.ECS | DefaultEcs | EasyEcs |
| --- | --- | --- | --- |
| 做法 | `entity.Enabled = false`：一个隐藏标签，查询默认跳过，除非 `WithDisabled()` | `entity.Disable()`：实体离开所有实体集合 | 自己的标签加 `Without<T>` |
| 开关一次 | 把行挪到另一个原型（archetype） | 更新每个集合 | 翻转一个存在位（第一次之后） |
| 遍历时跳过被禁用的实体 | 跳过它们所在的原型 | 它们不在任何集合里 | 表里没有时零开销；混在一起时每 64 行测一次 |

实测：每次操作有 100 个单位切换状态（大多数保持不变），以及有 10,000 个（频繁切换），然后汇总醒着的单位（`DisableComparison`）：

### 区分新实体：`Spawned` 标签 [#spawned-tag]

EasyEcs 没有 `Added<T>` 过滤条件。`[Changed<T>]` 已经会选中新得到 `T` 的行（添加和写入一样会打 tick）。如果系统必须区分新实体
和被写过的实体，就让创建方加一个标签，响应的系统再把它去掉（[决策 D4](/zh/docs/decisions#d4-no-addedt-filter)）：

```csharp
public struct Spawned : IComponent;
public record struct Greeted(int Count) : ISingletonComponent;

[EcsSystem]
public ref struct GreetNewcomers
{
    [ForEach, With<Spawned>, With<Health>]
    static void Greet(Entity entity, ref Greeted greeted)
    {
        greeted.Count++;                                     // 只做一次的工作
        entity.RemoveSpawned();                              // 翻转一个位：只欢迎一次
    }
}
```

```csharp
world.AddSingleton<Greeted>();
world.AddSystem<GreetNewcomers>();
world.CreateEntity(new Health(100), new Spawned());          // 创建方声明它是新的
world.Update();
```

标签是显式的，能查询，随 World 一起存盘，开销只是翻转一个存在位。

## 完整例子 [#full-example]

玩家占着一张桌子的座位（World 之外的资源），还有一个技能冷却，眩晕期间冷却暂停。玩家离开时，一个系统先把座位还回去，然后实体
才被释放。把这几个文件放进一个引用了 EasyEcs 的控制台项目（`dotnet add package EasyEcs`），用 `dotnet run` 运行。

<Accordions>
<Accordion title="Components.cs">

```csharp title="Components.cs" doccheck=example
using EasyEcs;

// 清理组件：对带着它的实体调用 Destroy 会让实体退休并留下来，直到某个系统把它移除。
public record struct Seat(int Number) : ICleanupComponent;

public record struct Cooldown(int Ticks) : IComponent;

// 已经还回去的座位数。
public record struct Seats(int Released) : ISingletonComponent;
```

</Accordion>
<Accordion title="Systems.cs">

```csharp title="Systems.cs" doccheck=example
using EasyEcs;

// 所有冷却倒数。被禁用的冷却对这个方法不可见，所以会暂停。
[EcsSystem]
public ref struct CooldownSystem
{
    [ForEach]
    static void Tick(ref Cooldown cooldown)
    {
        if (cooldown.Ticks > 0)
        {
            cooldown.Ticks--;
        }
    }
}

// 归还已退休玩家的座位。最后一个清理组件被移除后，实体才被释放。
[EcsSystem]
public ref struct ReleaseSeatsSystem
{
    [ForEach, With<Retired>, With<Seat>]
    static void Release(Entity player, ref Seats seats)
    {
        seats.Released++;
        player.RemoveSeat();
    }
}
```

</Accordion>
<Accordion title="Program.cs">

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();
world.AddSingleton<Seats>();
world.AddSystem<CooldownSystem>();
world.AddSystem<ReleaseSeatsSystem>();

Entity player = world.CreateEntity(new Seat(7), new Cooldown(3));

// 眩晕：冷却对查询不可见，但值保留着。
player.DisableCooldown();
world.Update();
int stunned = world.Count<Disabled<Cooldown>>();
Console.WriteLine($"stunned: has cooldown {player.HasCooldown}, stunned players {stunned}");

// 恢复：保留的值回来了，暂停期间那次更新不算数。
player.EnableCooldown();
world.Update();
Console.WriteLine($"resumed: {player.Cooldown.Ticks} ticks left");

// 玩家离开。它留着座位并带上 Retired 标签，其他组件全部移除。
player.Destroy();
Console.WriteLine($"retired: alive {player.IsAlive}, tagged {player.IsRetired}");

world.Update();
int released = world.Seats.Released;
Console.WriteLine($"after the update: alive {player.IsAlive}, seats released {released}");
```

</Accordion>
</Accordions>

输出：

```text
stunned: has cooldown False, stunned players 1
resumed: 2 ticks left
retired: alive True, tagged True
after the update: alive False, seats released 1
```

冷却从 3 变成 2：眩晕期间的那次更新跳过了它。从 `Destroy` 到下一次更新之间，玩家还活着，但只有 `ReleaseSeatsSystem` 看得到
它，因为只有它要求了 `Retired`。

## 怎么用得快 [#how-to-use-it-fast]

| 别这样 | 这样做 | 原因 |
| --- | --- | --- |
| 在每个销毁的地方各自释放资源 | 一个清理组件加一个系统 | 只有一条释放路径，批量销毁和级联也覆盖 |
| 移除再加回组件来暂停它 | `Disable<T>()` / `Enable<T>()` | 值保留下来；用 `Set` 得先把值存到别处 |
| 对大量实体循环调用 `Disable` | `world.DisableAll<T>(filter)` | 按 64 行一批（一个存在位字）整块处理（[批量操作](/zh/docs/guide/bulk)） |
| 每个系统都判断的标志字段 | 标签加 `Without<T>` | 没有这个标签的表完全不用判断 |

1 万个持有外部资源的会话，每次操作 1,000 个断开、1,000 个连入，对比用清理组件和在销毁前手动释放普通组件（`CleanupBenchmark`）；
以及 10 万个实体批量禁用、启用，对比逐个操作（`BulkBenchmark`）：

## 开销 [#what-it-costs]

- **清理组件：** 退休的实体在释放前保留 id 和一行（只剩清理组件）；没有清理组件的 World，销毁时零开销。
- **`Disable<T>()`：** O(1)。一张表里第一次禁用会把行挪一次，挪到带 `Disabled<T>` 列的表；之后禁用、启用都只是翻转存在位。
- **标签：** 每行一个存在位；第一次之后只是翻转。没有 `Inactive` 行的表直接跳过判断。
- **`Spawned`：** 和其他标签一样：加上翻一个位，去掉再翻一个位。

## 常见陷阱 [#pitfalls]

| 错误 | 后果 | 谁能发现 |
| --- | --- | --- |
| 清理系统没写 `With<Retired>` | 把存活实体的资源也释放了 | 代码审查 |
| 从不移除最后一个清理组件 | 退休的实体永远留着 | 在统计里看 `world.Count<Retired>()` |
| 对清理组件或 `ChildOf` 调用 `Disable<T>()` | 抛 `InvalidOperationException` | [EECS048](/zh/docs/guide/analyzer#eecs048) |
| 对被禁用的组件 `Set`，以为它还是禁用状态 | `Set` 会用新值重新启用它；要拿回保留的值用 `Enable` | 设计如此 |
| 系统忘了写 `Without<Inactive>` | 池里的实体还在动 | 代码审查 |
| 指望 `[Changed<T>]` 区分新建和写入 | 两者都算写入 | 用 `Spawned` 标签 |
| 只为了通知客户端实体没了而加清理组件 | 每个调用了 `Destroy` 的实体都会退休、等系统处理，而且只有一个读者看得到 | 用[销毁日志](/zh/docs/guide/change-tracking#destroy-log)：多个读者，只给 id |
| 指望销毁日志里有退休实体的值 | 日志只记 id，而且在实体释放时才记 | 先用清理组件读出这些值 |
