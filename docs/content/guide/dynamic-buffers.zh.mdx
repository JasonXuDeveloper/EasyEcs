服务器里有大量只属于某个实体的小列表：背包里的物品 id、路径上的路点、单位这一 tick 挨的伤害、玩家排队的指令。
`DynamicBuffer<T>` 把这样的列表做成一个组件。添加、查询、作为 `[ForEach]` 参数，都和普通组件一样；而且对列表的每次
写入都会被追踪，`[Changed<DynamicBuffer<T>>]` 能精确找出需要同步或存盘的那些背包。

## 什么时候用 [#when-to-use-it]

<Callout type="idea" title="适合">
  只有主人自己用、变了才需要同步或存盘的纯值列表：背包里的物品 id 或堆叠、路点、最近发生的事件、待执行的指令。
  [关系](/zh/docs/guide/indexes-and-relations#relations)的链接也是动态缓冲，元素类型是 `IRelation`。
</Callout>

<Callout type="warn" title="不适合">
  元素自带状态、系统要逐个查询的物品（有耐久度的剑）：每件做成一个实体，指向它的主人。数量少且有固定上限的值
  （四个冷却槽）：在非托管组件里放一个固定长度的 `[InlineArray]` 数组，完全不产生 GC 对象。
</Callout>

## 怎么用 [#how-to-use-it]

<Steps>
<Step>

### 声明元素类型 [#declare-the-element]

元素是普通结构体或枚举（比如地形的方块 `DynamicBuffer<Block>`），不实现 `IComponent`；`DynamicBuffer<Loot>` 才是组件。

```csharp
public record struct Loot(int Item);
public record struct Sent(int Items) : IComponent;
public struct Player : IComponent;
```

枚举元素和结构体元素生成同样的成员（`chunk.Block`、`WriteBlock()`，见下文）；一字节的枚举每个元素只占一个字节，正好装体素地形的方块：

```csharp
public enum Block : byte { Air, Stone, Water }
public struct Chunk : IComponent;

public static class Chunks
{
    public static int Water(Entity chunk)
    {
        int water = 0;
        foreach (var block in chunk.Block)                     // 只读：不打 tick
            if (block == Block.Water) water++;
        return water;
    }
}
```

</Step>
<Step>

### 用空缓冲创建实体 [#create-entities]

`new DynamicBuffer<T>()` 还没有列表。每个实体第一次写入时才得到自己的列表，所以一个值就能创建一整波实体。

```csharp
var players = new Entity[1_000];
world.CreateEntities(players, new DynamicBuffer<Loot>(), new Sent(), new Player());
foreach (var p in players) p.WriteLoot().EnsureCapacity(8);   // 预留满背包的空间：之后不再扩容
```

</Step>
<Step>

### 通过 `ref` 写入 [#write-through-a-ref]

写入方法都按 `ref` 接收缓冲，所以和普通被追踪组件一样，每次写入都会打上 tick。

```csharp title="Pickup.cs"
[EcsSystem]
public ref struct Pickup
{
    [ForEach, With<Player>]
    static void Collect(ref DynamicBuffer<Loot> bag) // [!code highlight]
    {
        if (bag.Count == 8) bag.RemoveAt(0);         // 背包满了就丢掉最早的物品
        bag.Add(new Loot(1));
    }
}
```

</Step>
<Step>

### 响应变化了的列表 [#react-to-changes]

`[Changed<DynamicBuffer<Loot>>]` 方法只访问系统上次运行后被写过的背包。用 `in` 读取，不算写入。

```csharp title="SendBags.cs"
[EcsSystem]
public ref struct SendBags
{
    [ForEach, Changed<DynamicBuffer<Loot>>] // [!code highlight]
    static void Send(in DynamicBuffer<Loot> bag, ref Sent sent)
    {
        int items = 0;
        foreach (var loot in bag) items += loot.Item;
        sent = new Sent(items);
    }
}
```

```csharp
world.AddSystem<Pickup>();
world.AddSystem<SendBags>();
world.Update();
```

</Step>
</Steps>

### 列表该怎么存 [#choosing-how-to-hold-a-list]

| 列表 | 存成 |
| --- | --- |
| 只有主人自己用、变了才同步或存盘的纯值：物品 id 或堆叠、路点、本 tick 受到的伤害 | **`DynamicBuffer<T>`** |
| 元素自带状态（耐久度、带计时的 buff），系统要逐个查询或修改 | **每件一个实体**，用 [`EntityId`](/zh/docs/guide/indexes-and-relations#entityid-keys) 链接指向主人 |
| 数量少且有固定上限（4 个冷却槽、最近 8 次输入） | 非托管组件里的**固定长度 `[InlineArray]` 数组** |
| 存盘时整体读写的数据（任务进度、设置） | **组件里的集合**，通过 `ref` 修改 |

玩家背包里的物品 id 是缓冲；一把有耐久和附魔的剑是指向主人的实体。包括只读数据和不可变数据在内的完整对照表，见
[ECS 原则第 8 条](/zh/docs/ecs-principles#8-choose-how-to-hold-a-collection)。

### 读和写 [#reading-and-writing]

| 读（`in`、`Read<T>()` 或 `ref`） | 写（只能用 `ref`：`ref` 参数、`Get<T>()`、`TryGetRef<T>`） |
| --- | --- |
| `Count`、`Capacity`、`bag[i]`（只读）、`AsReadOnlySpan()`、`foreach` | `Add`、`AddRange`、`Insert`、`RemoveAt`、`RemoveAtSwapBack`、`Clear`、`SetCount`、`EnsureCapacity`、`TrimExcess`、`AsSpan()`（可写） |

写入方法是 `ref DynamicBuffer<T>` 上的扩展方法，在 `in` 参数或 `Read<T>()` 上调用会直接编译失败：列表不可能绕过追踪被修改。

在系统之外，通过实体拿到缓冲：

只要有代码写出 `DynamicBuffer<Loot>`，生成器就会给这个元素（结构体或枚举）生成具名成员：

| 生成的成员 | 等价于 |
| --- | --- |
| `e.Loot` | `e.Read<DynamicBuffer<Loot>>()`：`ref readonly`，不打 tick |
| `e.HasLoot` | `e.Has<DynamicBuffer<Loot>>()` |
| `e.WriteLoot()` | `e.Get<DynamicBuffer<Loot>>()`：`ref`，算一次写入 |
| `e.GetOrAddLoot()` | `e.GetOrAdd<DynamicBuffer<Loot>>()`：没有就先加一个空缓冲 |
| `e.RemoveLoot()` | `e.Remove<DynamicBuffer<Loot>>()` |

```csharp
ref var bag = ref player.WriteLoot();                          // ref 局部变量：一次被追踪的写入
bag.Add(new Loot(7));
bag.Insert(0, new Loot(1));                                    // 插到最前面：后面的元素各后移一位
bag.AddRange([new Loot(2), new Loot(3)]);                      // 传一个 span：一次复制，最多扩容一次
bag.RemoveAtSwapBack(1);                                       // O(1)：用最后一个元素填空位
foreach (ref var loot in bag.AsSpan()) loot = new Loot(loot.Item * 10);   // 原地修改元素
bag.TrimExcess();                                              // 背包缩小后，把多余的容量还回去

int held = player.Loot.Count;                                  // 只读：不打 tick
ReadOnlySpan<Loot> items = player.Loot.AsReadOnlySpan();       // 只读地拿到所有元素
ref var stash = ref hero.GetOrAddLoot();                       // 英雄没有缓冲时先加一个空的
```

关系的缓冲没有 `WriteX()` 和 `GetOrAddX()`：链接带索引，只能通过
[`Link`](/zh/docs/guide/indexes-and-relations#relations) / [`Unlink`](/zh/docs/guide/indexes-and-relations#relations) 修改。

### 原地写整个缓冲：`SetCount` [#set-count]

`SetCount(n)` 设置元素个数，并返回要写的 span：超过 `n` 的元素去掉，新增的元素是 `default`。一次算出整个列表的代码（一条路径、
一个生成的地形）直接写进缓冲，不用先填一个 span，也不用复制：

```csharp
public record struct Waypoint(float X, float Y);
public record struct Destination(float X, float Y) : IComponent, ITracked;

[EcsSystem]
public ref struct PathSystem
{
    const int Steps = 8;

    [ForEach, Changed<Destination>]
    static void Plan(in Position from, in Destination to, ref DynamicBuffer<Waypoint> path)
    {
        var points = path.SetCount(Steps);                     // 整条路径原地写好
        for (int i = 0; i < points.Length; i++)
        {
            float t = (i + 1) / (float)Steps;
            points[i] = new Waypoint(from.X + (to.X - from.X) * t, from.Y + (to.Y - from.Y) * t);
        }
    }
}
```

这个 span 就是缓冲的 `AsSpan()`：下一次改变元素个数或容量的调用之前有效。

一次计算里要反复改写的缓冲是例外。同一批格子要读写很多遍时，比如 32 层、每层都更新同样的 256 字节，先在 `stackalloc` 出来的 span
里算，最后通过 `SetCount` 返回的 span 复制一次进去。这样每一遍都在方法独占、留在缓存里的内存上跑。每个元素只写一次的计算，还是直接写进 span。

```csharp
public record struct Shade(byte Level);

[EcsSystem]
public ref struct ShadeSystem
{
    const int Cells = 256;                                     // 16 × 16 的一根柱子
    const int Layers = 32;

    [ForEach, With<Chunk>]
    static void Darken(in DynamicBuffer<Block> blocks, ref DynamicBuffer<Shade> shade)
    {
        // 同样 256 格算 32 遍：在栈上算，最后复制一次进缓冲
        Span<byte> light = stackalloc byte[Cells];
        light.Fill(15);
        var solid = blocks.AsReadOnlySpan();
        for (int layer = Layers - 1; layer >= 0; layer--)
            for (int i = 0; i < Cells; i++)
                if (solid[layer * Cells + i] != Block.Air && light[i] > 0) light[i]--;
        var levels = shade.SetCount(Cells);
        for (int i = 0; i < Cells; i++) levels[i] = new Shade(light[i]);
    }
}
```

### 不要复制 [#copies]

列表放在组件引用的一个对象里。复制一个 `DynamicBuffer<T>` 值，副本指向的还是同一个列表：通过副本写入不会打 tick，
把副本存到别处还会让两个实体共用一个列表。分析器会拒绝所有复制（[EECS012](/zh/docs/guide/analyzer#eecs012)）：

```csharp doccheck=expect-EECS012
public static class Bags
{
    public static int Items(Entity player)
    {
        var copy = player.Read<DynamicBuffer<Loot>>();   // EECS012：复制了缓冲
        return copy.Count;
    }
}
```

用 `ref`、`in` 参数、`ref` 局部变量和 `Get` / `Read`。新值写 `new DynamicBuffer<T>()`（或 `default`），里面没有列表。

### 移动、移除、快照和预制体 [#lifecycle]

- 行移到另一张表（加了组件）时，列表跟着走。
- 移除这个组件或销毁实体，列表随之丢弃；再加回组件，从空列表开始。
- `world.Capture()` 复制元素，`Restore` 再复制回去：World 和它的[快照](/zh/docs/guide/snapshots)永远不共用列表。
- `world.Instantiate(prefab)` 和 `entity.Clone()` 给新实体一份自己的列表，元素相同。[预制体](/zh/docs/guide/prefabs)用
  `SetBuffer(...)` 设置元素：

```csharp
var chest = new Prefab().SetBuffer(new Loot(1), new Loot(2));
var opened = world.Instantiate(chest);                        // 自己的列表：Loot 1、Loot 2
```

- [`Save`](/zh/docs/guide/saves) 会写出元素：非托管元素按原始行写，托管元素走 Nino。

### 反复出现又消失的缓冲：缓冲池、`MaxPooledLength` 和 `FillPool` [#pool]

缓冲销毁时（实体被销毁、组件被移除、空缓冲调用 `TrimExcess`），它的列表清空后进入这个元素类型的池；同类型的下一个缓冲写入第一个元素时
（`Add`、`SetCount`、`EnsureCapacity`），直接从池里取，不再分配，不论在哪个线程。Actor 加载又卸载、单位生成又被击杀、玩家周围的地形
加载又卸载：预热之后，这些缓冲都不分配。每个元素类型有两个静态设置决定池的行为：

<TypeTable
  type={{
    'DynamicBuffer<T>.MaxPooledLength': {
      type: 'static int',
      description: '销毁的缓冲最多还回多长的列表（按元素个数）；更长的交给 GC。0 表示不入池。',
      default: '4 KB 能放下的元素个数（一字节的枚举是 4,096）',
    },
    'DynamicBuffer<T>.FillPool(lists)': {
      type: 'static void',
      description: '现在就分配 MaxPooledLength 个元素的空列表，直到池里有这么多个（池里已有的也算）。',
      default: '不预留',
    },
  }}
/>

<Callout type="idea" title="适合">
  `MaxPooledLength`：超过 4 KB、成批出现又消失的缓冲（地形的方块、大信箱）。保持默认的话，每个销毁的列表都交给 GC，每个新缓冲都重新分配。
  `FillPool`：知道自己峰值的服务器，连第一次涨到峰值也不想分配。
</Callout>

<Callout type="warn" title="不适合">
  缓冲和实体同生共死（一直在线的玩家的背包），或者不超过 4 KB：默认的池已经在回收它们。也别远超峰值去预留：这些列表进程活多久就占多久。
</Callout>

两者都对整个进程生效，所有 World、所有线程共用：启动时、在 World 用到这个类型之前设一次。先设容量，因为 `FillPool`
按调用时的容量分配列表。一个体素服务器，每片地形 8,192 个方块，玩家周围最多同时加载 512 片地形：

```csharp
const int ChunkBlocks = 16 * 16 * 32;
const int PeakChunks = 512;

DynamicBuffer<Block>.MaxPooledLength = ChunkBlocks;           // 整个地形的列表都能还回池里
DynamicBuffer<Block>.FillPool(PeakChunks);                    // 峰值在第一个 tick 之前就分配好

using var server = new World();
var loaded = new Entity[PeakChunks];
server.CreateEntities(loaded, new DynamicBuffer<Block>(), new Chunk());
foreach (var chunk in loaded) chunk.WriteBlock().SetCount(ChunkBlocks);   // 每个都拿一个预留的列表
```

- **池里存多少：** 最多是没人取用期间销毁的那些缓冲的列表，也就是峰值个数、每个 `MaxPooledLength` 个元素。512 个 8,192 字节的方块列表是
  4 MB，进程活多久就占多久。
- **跨线程：** 每个线程自己留几个列表，其余的按批和所有线程共享的池交换，每批加一次锁。所有者线程从销毁的缓冲收回的列表，也能给
  [并行 `[ForEach]`](/zh/docs/guide/threading#parallel-foreach-methods) 在辅助线程上的第一次写入用。

池省下多少：1,000 个 Actor 各带一个信箱，卸载再重新加载，见[下文](#how-to-use-it-fast)的 `BufferChurnBenchmark` 表；为什么上限按元素类型设置：
见 [D65](/zh/docs/decisions#d65-buffer-pool-capacity)。

## 完整例子 [#full-example]

英雄每个 tick 往能装四件东西的背包里捡一件带编号的物品，同步系统统计有变化的背包。宝箱也有背包，但没有谁写它。把这几个文件
放进一个引用了 EasyEcs 的控制台项目（`dotnet add package EasyEcs`），用 `dotnet run` 运行。

<Accordions>
<Accordion title="Components.cs">

```csharp title="Components.cs" doccheck=example
using EasyEcs;

// 背包里的一个元素：任意 struct 都行。DynamicBuffer<Loot> 才是组件。
public record struct Loot(int Item);

// 标签：会捡东西的实体。
public struct Collector : IComponent;

// 下一件掉落物品的编号。
public record struct Drops(int Next) : ISingletonComponent;

// 从开始到现在发送过多少次背包。
public record struct Synced(int Bags) : ISingletonComponent;
```

</Accordion>
<Accordion title="Systems.cs">

```csharp title="Systems.cs" doccheck=example
using EasyEcs;

// 每个拾取者捡起下一件物品。背包满了就先扔掉最旧的一件。
[EcsSystem]
public ref struct PickupSystem
{
    const int BagSize = 4;

    // 背包按 `ref` 传入：写它就是一次被追踪的变更。
    [ForEach, With<Collector>]
    static void Pick(ref DynamicBuffer<Loot> bag, ref Drops drops)
    {
        if (bag.Count == BagSize)
        {
            bag.RemoveAt(0);
        }

        drops.Next++;
        bag.Add(new Loot(drops.Next));
    }
}

// 只发送自本系统上次运行以来被写过的背包。
[EcsSystem, UpdateAfter<PickupSystem>]
public ref struct SyncBagsSystem
{
    [ForEach, Changed<DynamicBuffer<Loot>>]
    static void Sync(ref Synced synced)
    {
        synced.Bags++;
    }
}
```

</Accordion>
<Accordion title="Program.cs">

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();
world.AddSingleton<Drops>();
world.AddSingleton<Synced>();
world.AddSystem<PickupSystem>();
world.AddSystem<SyncBagsSystem>();

// 空的缓冲还没有列表：每个实体在第一次写入时才得到自己的列表。
Entity hero = world.CreateEntity(new DynamicBuffer<Loot>(), new Collector());
Entity chest = world.CreateEntity(new DynamicBuffer<Loot>());

// 现在就留够一整包的容量，之后列表不会再扩容。
hero.WriteLoot().EnsureCapacity(4);

for (int i = 0; i < 6; i++)
{
    world.Update();
}

// hero.Loot 是读取（Read<T>），不算变更。
Console.Write("hero's bag:");
foreach (var loot in hero.Loot)
{
    Console.Write($" {loot.Item}");
}

Console.WriteLine();
Console.WriteLine($"the chest holds {chest.Loot.Count} items");
Console.WriteLine($"bags synced: {world.Synced.Bags}");
```

</Accordion>
</Accordions>

## 怎么用得快 [#how-to-use-it-fast]

| 别这样 | 这样做 | 原因 |
| --- | --- | --- |
| 让列表从空开始慢慢长 | 知道大小时调用一次 `EnsureCapacity(n)` | 容量之内的 `Add` 不分配 |
| 每个 tick 新建列表 | `Clear()` 后重新填充 | `Clear` 保留容量：每 tick 重填的列表长到稳定大小后不再分配 |
| 不在乎顺序还用 `RemoveAt(i)` | `RemoveAtSwapBack(i)` | O(1)，而不是 O(count) |
| 用 `ref` 参数只读 | 改成 `in` 参数 | `ref` 会给行打 tick，下游每个 `[Changed<T>]` 读取方都要访问它（[EECS025](/zh/docs/guide/analyzer#eecs025)） |
| 只写一遍的整个缓冲，先在栈上填好一个 span 再 `AddRange` | 直接写 `SetCount(n)` 返回的 span | 元素只过一遍，也不用在栈上开一个缓冲那么大的空间 |
| 在缓冲的 span 上反复读改写很多遍 | 在 `stackalloc` 的 span 上算完，再复制一次进 `SetCount(n)` 返回的 span | 每一遍都在方法自己的内存上跑，缓冲只写一次 |
| `Add` 之后还用之前的 span | 可能扩容的调用之后重新取 span | `Add`、`AddRange`、`Insert`、`SetCount`、`EnsureCapacity`、`TrimExcess` 都可能换数组 |
| 超过 4 KB、反复出现又消失的缓冲（地形、大信箱） | 启动时把 [`MaxPooledLength`](#pool) 调到它们的长度 | 新缓冲重用销毁缓冲的列表，不再分配 |
| World 涨到已知峰值的途中不断分配列表 | 启动时、设好 `MaxPooledLength` 之后调用 [`FillPool(peak)`](#pool) | 列表在第一个 tick 之前就付清 |
| 只在部分行写入的 `ref` 缓冲 | 改成 [`Mut<DynamicBuffer<T>>`](/zh/docs/guide/change-tracking#set-if-changed)（`x.Write().Add(…)`） | 只给写过的行打 tick（[EECS053](/zh/docs/guide/analyzer#eecs053)） |

10 万个装 8 件物品的背包，每 tick 有 1,000 个交易一件物品，再由一个 `[Changed]` 系统发送变化的背包
（`DynamicBufferBenchmark`），对比把背包存成被追踪组件里的 `List<T>`：

## 开销 [#what-it-costs]

- **内存：** 列中每行一个引用，外加每个实体一个对象和一个数组，第一次写入时才创建。没有内联容量，每个列表都在堆上。
- **每次写入：** 给这一行打一次 tick，和其他[被追踪组件](/zh/docs/guide/change-tracking#what-it-costs)一样。
- **容量之内的添加** 不分配；扩容时数组翻倍（至少 4 个元素）。
- **缓冲销毁时**（实体被销毁、组件被移除），它的列表清空后交给同一元素类型、下一个写入第一个元素的缓冲，不论在哪个线程；超过
  `MaxPooledLength` 的列表交给 GC，池里最多保留峰值数量的列表（[缓冲池](#pool)）。
- **空缓冲不持有列表**，预制体给实例的空缓冲（不带元素的 `SetBuffer<T>()`）也一样：写入第一个元素时才从池里取列表。`LoadEntities`
  和 `Load` 把每个缓冲读进池里取来的列表，再把这个列表直接交给实体，不再复制一遍。
- **`TrimExcess`** 把曾经变大的列表多余的空间还回去。缓冲为空时，它把列表还给池：缓冲不再持有列表，任何 `T` 缓冲的下一次
  首次写入会重用它。只在实体活跃时才用的临时缓冲（模拟一阵一阵跑、中间会休眠的那一步），空闲期间就不占内存。
- **并行方法** 可以接收 `ref DynamicBuffer<T>`：每个块只写自己那些实体的列表。

## 常见陷阱 [#pitfalls]

| 错误 | 后果 | 谁能发现 |
| --- | --- | --- |
| 把缓冲复制到局部变量、字段或另一个实体 | 一个列表两个主人；通过副本的写入不被追踪 | [EECS012](/zh/docs/guide/analyzer#eecs012) |
| 在 `in` 参数或 `Read<T>()` 上调用 `Add` | 编译不过：写入需要 `ref` | 编译器 |
| `Add` 之后继续用之前的 `AsSpan()`（或 `SetCount` 返回的 span） | span 还指着旧数组 | 代码审查：重新取 span |
| 用 `ref` 参数读取缓冲 | 访问到的每一行都算作已变化 | [EECS025](/zh/docs/guide/analyzer#eecs025) |
| `ref` 缓冲只在部分行写入（提前 `return`、`if` 里的 `Add`） | 访问到的每一行都算作已变化，没动过的也算 | [EECS053](/zh/docs/guide/analyzer#eecs053)：改用 `Mut<DynamicBuffer<T>>` |
| 超过 `MaxPooledLength` 的缓冲反复出现又消失 | 每个销毁的列表都交给 GC，每个新缓冲都要分配 | 启动时调高 [`MaxPooledLength`](#pool)；创建它们的系统的 `TotalAllocated`（[诊断](/zh/docs/guide/diagnostics)）能看出来 |
| 先 `FillPool`，后调高 `MaxPooledLength` | 预留的列表还是旧长度，第一次填满时扩容 | 代码审查：先设容量 |
| `FillPool` 远超峰值 | 内存一直被占着：列表数 × 容量 | 按实测的峰值预留 |
| 纯值列表的每个元素都建一个实体 | 每件物品一个实体、一行、一条索引 | 纯值用缓冲 |
