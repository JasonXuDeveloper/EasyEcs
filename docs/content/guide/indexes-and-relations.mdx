Queries find entities by the components they have. A server also needs them by value: the player named "alice", the
units in zone 3, the top ten scores, the items a player owns, the members of a party. Mark a component's key with
`[IndexKey]` and the world keeps an index of it: every `Set` re-indexes the entity at once, so a lookup never catches up
and never scans. Relations are indexes too: a component holding an `EntityId` answers "who points at this entity", and
an `IRelation` buffer links one entity to many.

## When to use it [#when-to-use-it]

<Callout type="idea" title="Use it for">
  Lookups by key (a player by name, units by zone), ordered walks (leaderboards, deadlines, matchmaking brackets),
  reverse links (the items of an owner, the arrows of an archer) and many-to-many links (party members, followers).
</Callout>

<Callout type="warn" title="Skip it for">
  A key you only filter by in a full pass: a plain `[ForEach]` reads it anyway. Few keys holding many entities each
  that you walk whole (16 zones of 100,000 players): [groups](/en/docs/guide/groups) put each key in its own tables
  and walk them at full speed. A dictionary you would keep in sync by hand: the index is that dictionary.
</Callout>

## How to use it [#how-to-use-it]

### Value indexes [#value-indexes]

Mark the member the entity is found by with `[IndexKey]` (on a positional parameter, a field or a property of a
`partial` struct): the generator adds `IIndexed<TKey>` with an explicit `Key` returning it. `world.Index<T, TKey>()`
creates the index on first use; the generated `world.XIndex` property returns the same one. A key computed from several
members is written by hand: implement `IIndexed<TKey>` and its `Key` ([below](#direct-index) a cell's `(X, Y)`).

<Tabs items={['You write', 'The generator writes']}>
<Tab value="You write">

```csharp
public partial record struct Callsign([IndexKey] string Value) : IComponent;
public partial record struct Zone([IndexKey] int Id) : IComponent;
```

</Tab>
<Tab value="The generator writes">

```csharp doccheck=skip
partial record struct Callsign : IIndexed<string>
{
    readonly string IIndexed<string>.Key => Value;
}

partial record struct Zone : IIndexed<int>
{
    readonly int IIndexed<int>.Key => Id;
}
```

</Tab>
</Tabs>

The key is explicit, so it stays out of the record's members and its `ToString()`. The struct, and every type it is
nested in, is `partial` so the generator can add to it ([EECS062](/en/docs/guide/analyzer#eecs062), with a code fix).
A `Key` written by hand that returns one member is reported with the attribute as its fix
([EECS067](/en/docs/guide/analyzer#eecs067)), and two keys on one component are
[EECS036](/en/docs/guide/analyzer#eecs036).

```csharp
var alpha = world.CreateEntity(new Callsign("alpha"), new Zone(1));
world.CreateEntity(new Callsign("bravo"), new Zone(1));

var zones = world.ZoneIndex;                        // world.Index<Zone, int>(): keep it in a local or a field
int inOne = zones.Count(1);                         // O(1)
foreach (var e in zones.Find(1)) { /* every entity in zone 1 */ }
int toVisit = zones.Find(1).Count;                  // O(1): how many the loop sees, to size a buffer first
int occupied = zones.KeyCount;                      // O(1): how many zones hold an entity (an admin metric)
if (world.CallsignIndex.TryFind("alpha", out var found)) { /* any entity with that key */ }

alpha.SetZone(2);                                   // a Set: the index moves alpha at once // [!code highlight]
int inTwo = zones.Count(2);                         // 1
```

Read an indexed component with `in`, `Read<T>()` or the generated property (`alpha.Zone`, a `ref readonly`), and write
it with `Set` or the generated `SetX`. A write through a `ref` would change the key behind the index's back, so the
analyzer rejects it ([EECS015](/en/docs/guide/analyzer#eecs015)). A component has one index, with one key type.

`Find(key).Count` (also on `world.Children(parent)`) is how many entities had the key when the lookup ran, without a
walk: size a buffer from it rather than walking the matches twice. An entity destroyed during the loop is skipped by the
walk but still counted. `KeyCount` is how many distinct keys some entity holds (how many cells of a map are
occupied), kept as entities come and go; a relation index has `TargetCount`, the distinct targets its links point at.

### A component as its own key [#self-key]

A key can be the whole component: a shop found by its id, an actor found by its address. Put `[IndexKey]` (or
`[UniqueKey]`) on the struct itself, and the generator makes the component `IIndexed` of itself:

<Tabs items={['You write', 'The generator writes']}>
<Tab value="You write">

```csharp
[IndexKey] public readonly partial record struct Shop(long Id) : IComponent;
```

</Tab>
<Tab value="The generator writes">

```csharp doccheck=skip
partial record struct Shop : IIndexed<Shop>
{
    readonly Shop IIndexed<Shop>.Key => this;     // explicit: a public Key property would recurse in ToString()
}
```

</Tab>
</Tabs>

```csharp
var shop = world.CreateEntity(new Shop(7));
if (world.ShopIndex.TryFind(new Shop(7), out var found)) { /* the shop with id 7 */ }
```

On a record struct, a public `Key => this` property joins the generated `ToString()`, which prints `Key`, which prints
`Key` again, until the stack overflows. The generated explicit implementation keeps `Key` out of the record's members;
a `Key` written by hand that returns the value itself or one member is reported with the attribute as its fix
([EECS067](/en/docs/guide/analyzer#eecs067)). The
[Actors sample](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Actors) builds on this: one type per
kind of actor is its key, its system group and the group's filter.

### Ordered walks and ranges [#ordered-index]

When the key compares (`IComparable<TKey>`: a score, a level, a deadline), the same index walks in key order:

| Call | Visits |
| --- | --- |
| `Range(min, max)` | keys from `min` to `max` (inclusive), ascending |
| `RangeDescending(min, max)` | the same keys, descending |
| `Ascending()` / `Descending()` | every indexed entity in key order |

```csharp
public partial record struct Score([IndexKey] int Points) : IComponent;
```

```csharp
for (int i = 0; i < 100; i++) world.CreateEntity(new Score(i * 10));

int shown = 0;
foreach (var leader in world.ScoreIndex.Descending())         // the top of the leaderboard first
{
    if (++shown > 10) break;
}
foreach (var rival in world.ScoreIndex.Range(400, 500)) { /* a matchmaking bracket */ }
```

The first ordered walk sorts the keys once; from then on the index keeps them sorted as keys appear and disappear.

### `EntityId` keys: one link per entity [#entityid-keys]

A component holding an `EntityId` and indexed by it is a link: each arrow has one owner, and the index answers which
arrows an owner has. Store the `EntityId`, not the `Entity` handle ([EECS017](/en/docs/guide/analyzer#eecs017)): the id
is 8 bytes, unmanaged and saved with the world, and a handle converts to it implicitly.

```csharp
public partial record struct OwnedBy([IndexKey] EntityId Owner) : IComponent;
public struct Arrow : IComponent;
```

```csharp
var archer = world.CreateEntity(new Health(10));
for (int i = 0; i < 3; i++) world.CreateEntity(new OwnedBy(archer), new Arrow());

int quiver = world.OwnedByIndex.Count(archer);                // 3: an array access, no hashing
foreach (var arrow in world.OwnedByIndex.Find(archer)) { /* each arrow of the archer */ }
```

An `EntityId` carries the entity's version, so a link to a destroyed entity never matches a later entity that reuses
its index. To turn an id back into a handle, `world.TryGetEntity(id, out var entity)` also says whether it still lives.
The parent-child link is built in: see [Hierarchy](/en/docs/guide/hierarchy).

### Unique keys: one entity per key [#unique-keys]

Some keys name one entity and must never name two: an account id, a session token, the occupant of a grid cell.
Mark the key `[UniqueKey]` instead of `[IndexKey]` (the generator adds `IUniqueIndexed<TKey>`), and the world refuses
every write that would give a key to a second entity. `Get(key)` returns the one entity of a key (and throws when none has it), `TryGet(key, out
entity)` says whether one has it; `Find`, `Count`, `TryFind` and the ordered walks work as on any index.

```csharp
public partial record struct Account([UniqueKey] long Id) : IComponent;
```

```csharp
var ada = world.CreateEntity(new Account(1001));
var bo = world.CreateEntity(new Account(2002));

var accounts = world.AccountIndex;                      // world.Index<Account, long>()
Entity holder = accounts.Get(1001);                     // ada: O(1), throws when no entity has the key
bool taken = accounts.TryGet(3003, out _);              // false: nobody has 3003

try
{
    bo.SetAccount(1001);                                // ada holds 1001 // [!code highlight]
}
catch (InvalidOperationException)
{
    // refused before anything changed: bo still has 2002, ada still has 1001
}
```

- **Every write is checked**, before it changes anything: `Set` and the generated `SetX`, `CreateEntity`,
  `CreateEntities`, `GetOrAdd` (it claims the default value's key), `Enable` / `EnableAll`, `SetAll`, `Instantiate`
  (with or without [given components](/en/docs/guide/prefabs#instantiate-with-values)), `Clone`, and the arrivals of
  `LoadEntities`, `LoadEntitiesInto` and `MoveEntities` ([migration](/en/docs/guide/migration-and-unload#unique-keys)).
  A write that would repeat a key throws `InvalidOperationException` naming the component, the key and the entity
  that holds it. A `Load` of a save that gives one key to two entities throws `InvalidDataException`.
- **A refused write leaves the world as it was.** The entity keeps its value and its table, a call with several
  components writes none of them, and a batch (`CreateEntities`, `SetAll`, `EnableAll`, a load) creates or changes
  no entity.
- **Batches cannot repeat a key.** `CreateEntities`, `SetAll` over more than one entity, `Instantiate(prefab, span)`
  of more than one entity, and `Clone` would give every copy the same key: they throw unless the key is null.
- **Writing an entity's own key again is fine.** `ada.SetAccount(1001)` changes nothing.
- **Moving a key: change its holder first.** Give `ada` another key, then give `bo` hers. To swap two keys, go
  through a free one: `ada` to a spare key, `bo` to 1001, `ada` to 2002.
- **Destroy, `Remove` and `Disable` free the key.** A disabled component holds no key while disabled, and enabling it
  again throws if another entity took the key meanwhile (the component stays disabled).
- **A null key is no key.** Any number of entities may hold a `string` key that is null; no lookup finds them, and
  `TryGet(null, out _)` is false. A default value key (`0`) is a key like any other.
- **`EntityId` keys cannot be unique.** Loads and moves rewrite `EntityId`s after they copy the rows, too late to check
  them first, so `IUniqueIndexed<EntityId>` is rejected ([EECS036](/en/docs/guide/analyzer#eecs036)): index such a
  link with `IIndexed<EntityId>`. EECS036 also rejects a unique component with a second key type.
- **Each world has its own keys.** Two worlds may each have an entity with account 1001.

The index of a unique component is eager: each world creates it with the first table that holds the component, so
the first write is already checked. An `IIndexed` index is built by its first lookup, which is free for a world that
never looks; a unique index cannot wait, since every write before that lookup could let a duplicate in. The
generator registers how to create each unique component's index when its assembly loads. For a unique component
it cannot see (a generic one, closed at run time), the first write throws `InvalidOperationException` until one
`world.Index<T, TKey>()` call, in any world, registers it.

#### Direct-mapped keys: `IDirectIndexed<TKey>` [#direct-index]

A unique key that maps onto a small, bounded range of slots (a tile or a chunk around the players, a room, a seat, a
small id) can skip the hash on its lookups. Implement `IDirectIndexed<TKey>` instead of `IUniqueIndexed<TKey>` and
say how many slots there are and which slot a key takes: the index keeps an array of slots beside the hash, so `Get`,
`TryGet` and the uniqueness check of every write read one array entry. The hash stays the index: a key whose slot is
out of range, or held by another key (a collision), is found through it, and `Find`, `Count` and the ordered walks
work as on any unique index.

<Callout type="idea" title="Use it for">
  Keys a world holds at once that fall on distinct slots: grid coordinates modulo the side of the loaded area, tiles
  of a bounded map, player slots, small ids. The lookup a tick makes thousands of times (the blocks around a body,
  the tile a unit stands on) then reads one array entry instead of probing the hash.
</Callout>

<Callout type="warn" title="Skip it for">
  Sparse keys or huge ranges (account ids, tokens, names): the array would be as long as the range and mostly empty,
  and a modulo would make most keys collide. Keys looked up a few times per tick: the hash probe is already O(1).
</Callout>

<TypeTable
  type={{
    Slots: {
      type: 'static abstract int',
      description: 'The length of the slot array, read once when a world creates the index. It costs Slots times the key size plus 12 bytes.',
    },
    'SlotOf(TKey key)': {
      type: 'static abstract int',
      description: 'The slot of a key, 0 to Slots - 1; any other value leaves the key to the hash. Called on every lookup and every write of a key: a few instructions, no state.',
    },
  }}
/>

```csharp
public record struct Tile(int X, int Y) : IComponent, IDirectIndexed<(int, int)>
{
    public (int, int) Key => (X, Y);

    // The tiles loaded at once lie within 64 of each other, so a coordinate modulo 64 gives each its own slot.
    static int IDirectIndexed<(int, int)>.Slots => 64 * 64;
    static int IDirectIndexed<(int, int)>.SlotOf((int, int) key) => (key.Item2 & 63) * 64 + (key.Item1 & 63);
}
```

```csharp
world.CreateEntity(new Tile(3, 5));

var tiles = world.TileIndex;                            // world.Index<Tile, (int, int)>()
bool here = tiles.TryGet((3, 5), out var tile);         // true: one array entry // [!code highlight]
bool far = tiles.TryGet((67, 5), out _);                // false: its slot holds (3, 5), and no key of it is in the hash alone
world.CreateEntity(new Tile(67, 5));                    // a collision: correct, found through the hash
```

- **Everything else is a unique index.** The same writes are checked, the same exceptions thrown, the same `Find`,
  `Count` and ordered walks; only `Get`, `TryGet` and the check of a write read the slot first.
- **Collisions are correct, only slower.** The second key of a slot lives in the hash alone and costs a probe; a slot
  function whose keys collide often gains nothing over `IUniqueIndexed<TKey>`.
- **The slot function is pure arithmetic.** It runs on every lookup and write of a key; a modulo by a power of two
  (`& 63`) or the key itself is enough.
- **Registered by the generator**, as unique indexes are: no reflection, so Native AOT keeps it.

`VoxelServer` keys its chunks this way: a chunk's slot is its position modulo 64, the chunks loaded around the
players are never 64 apart, and the lookup physics, water and AOI make for every body reads one entry
([the data](/en/docs/samples/voxel-server#data)).

### Relations: many links per entity [#relations]

An entity holds one component of each type, so an `EntityId` key gives each entity one link. A relation gives it any
number: its elements implement `IRelation` and live in a [`DynamicBuffer<T>`](/en/docs/guide/dynamic-buffers), and
`world.Relations<T>()` finds the entities linking to a target.

```csharp
public record struct MemberOf(EntityId Target) : IRelation;
```

```csharp
var red = world.CreateEntity();
var blue = world.CreateEntity();
var knight = world.CreateEntity().Link(new MemberOf(red)).Link(new MemberOf(blue));   // in two parties

var parties = world.Relations<MemberOf>();                    // keep it in a local or a field
int members = parties.Count(red);                             // O(1)
foreach (var member in parties.Find(red)) { /* each member of red */ }
int links = parties.Find(red).Count;                          // O(1): the links the loop walks, to size a buffer
int withMembers = parties.TargetCount;                        // O(1): how many parties have a member
bool inBlue = knight.Links<MemberOf>(blue);
knight.Unlink<MemberOf>(blue);                                // leaves blue
```

`Link` adds the buffer if the entity has none, then appends the link and indexes it. Read the links with
`Read<DynamicBuffer<T>>()` or an `in` parameter; write them with `Link`, `Unlink` or a `Set` of a whole
buffer, so the index follows (a `ref` write is [EECS015](/en/docs/guide/analyzer#eecs015)).

Once some code names `DynamicBuffer<MemberOf>` (a `[ForEach]` parameter, a `Read`), the generator adds named members
for the relation:

| Generated | Same as |
| --- | --- |
| `e.LinkMemberOf(target)` | `e.Link(new MemberOf(target))`, returns the entity |
| `e.UnlinkMemberOf(target)` | `e.Unlink<MemberOf>(target)`, returns how many links went |
| `e.LinksMemberOf(target)` | `e.Links<MemberOf>(target)` |
| `e.MemberOf` / `e.HasMemberOf` / `e.RemoveMemberOf()` | the links (`ref readonly DynamicBuffer<MemberOf>`), whether it has any, drop them all |
| `world.MemberOfIndex` | `world.Relations<MemberOf>()` |

```csharp
public record struct PartyCount(int Parties) : IComponent;

[EcsSystem]
public ref struct CountParties
{
    [ForEach]
    static void Count(in DynamicBuffer<MemberOf> parties, ref PartyCount count) => count = new PartyCount(parties.Count);
}
```

```csharp
var paladin = world.CreateEntity(new PartyCount()).LinkMemberOf(red).LinkMemberOf(blue);
bool withBlue = paladin.LinksMemberOf(blue);                  // true
paladin.UnlinkMemberOf(blue);                                 // 1 link went
int linked = paladin.MemberOf.Count;                          // 1
int inRed = world.MemberOfIndex.Count(red);                   // the knight and the paladin
```

`LinkX` takes what builds a link: one overload per public constructor, or, without one, every field and
auto-property with a public `set` or `init` (`struct Ally : IRelation { public EntityId Target { get; init; } public
int Weight; }` gets `e.LinkAlly(target, weight)`). A relation gets no `WriteX()` or `GetOrAddX()`: its links are
indexed, so they change only through the calls above.

### When the target is destroyed [#target-policies]

What happens to links when their target dies is a rule of your game, and the index can apply it inside every destroy:

| `TargetPolicy` | The links to a destroyed entity | Example |
| --- | --- | --- |
| `Keep` (the default) | stay, findable by the dead id (which no later entity has); a system of yours cleans them | an audit trail |
| `Remove` | go: the component is removed from its entities, a relation drops the links | an owner loses its pet |
| `Destroy` | the linking entities are destroyed too, and what links to them in turn | a summon dies with its summoner |

```csharp
world.OwnedByIndex.WhenTargetDestroyed(TargetPolicy.Destroy);       // arrows go with their archer
world.Relations<MemberOf>().WhenTargetDestroyed(TargetPolicy.Remove); // a disbanded party leaves no links

archer.Destroy();
int arrowsLeft = world.Count<Arrow>();                              // 0
```

`WhenTargetDestroyed` is set per world and per index. A rule that holds in every world is declared on the type:
`[WhenTargetDestroyed(policy)]` on a relation or a component indexed by an `EntityId` gives each world that policy from
its first table holding the component, so the first destroy already follows it and no setup call can be forgotten. A
world's own `WhenTargetDestroyed` call replaces it.

```csharp
[WhenTargetDestroyed(TargetPolicy.Destroy)]                         // a summon dies with its summoner, in every world
public partial record struct SummonedBy([IndexKey] EntityId Summoner) : IComponent;

[WhenTargetDestroyed(TargetPolicy.Remove)]                          // a closed guild leaves no links
public record struct InGuild(EntityId Target) : IRelation;
```

`ChildOf`, the [hierarchy](/en/docs/guide/hierarchy) link, is `Destroy` from the start. The attribute on a type that
links to no entity is reported ([EECS068](/en/docs/guide/analyzer#eecs068)).

### Symmetric relations: one link on each side [#symmetric-relations]

A friendship, a trade, a duel: some links are the same seen from either end. A relation is one-way (its owner links
to its target), so a symmetric one is two links, one on each side, written together. Keep both writes in one place,
and let `TargetPolicy.Remove` clean up when one side is destroyed: the destroyed entity's own links go with it, and
the index drops the other side's link to it.

```csharp
public record struct Friend(EntityId Target) : IRelation;

public static class Friendships
{
    // A friendship is two links, one on each player, so both sides change together.
    public static void Befriend(Entity a, Entity b)
    {
        if (a.Links<Friend>(b)) return;
        a.Link(new Friend(b));
        b.Link(new Friend(a));
    }

    public static void Unfriend(Entity a, Entity b)
    {
        a.Unlink<Friend>(b);
        b.Unlink<Friend>(a);
    }
}
```

```csharp
var friends = world.Relations<Friend>();
friends.WhenTargetDestroyed(TargetPolicy.Remove);          // a player who leaves leaves no links behind

var ana = world.CreateEntity();
var ben = world.CreateEntity();
Friendships.Befriend(ana, ben);
int bensFriends = friends.Count(ben);                      // 1: ana links to ben

ana.Destroy();                                             // ana's link goes with her, ben's link to her is dropped
bool stillLinked = ben.Links<Friend>(ana);                 // false
```

Each side reads its own friends from its buffer, and since every link has its mirror, `friends.Count(player)` (the
links to the player) is also the number of friends the player has. `Unfriend` removes both links the same way.

### Driving a system from an index [#index-driven-foreach]

A `[ForEach]` method can walk an index for each entity it visits: a hazard hurts the units of its zone, a guild totals
its members. Take the `World` (or an `Entity`) as a parameter to reach the index; the system then runs alone, which
an index needs, since it belongs to the world's owner thread.

```csharp
public record struct Hazard(int Zone, int Damage) : IComponent;

[EcsSystem]
public ref struct BurnZones
{
    [ForEach]
    static void Burn(in Hazard hazard, World world)
    {
        foreach (var unit in world.ZoneIndex.Find(hazard.Zone)) // [!code highlight]
        {
            ref var health = ref unit.TryGetRef<Health>(out bool found);   // one lookup
            if (found) health.Value -= hazard.Damage;
        }
    }
}
```

The walk visits only the units of that zone, however many units the world holds. Destroying entities during a `Find`
loop is allowed. Changing the indexed component of that index during the loop is not: a key that empties hands its id
array to the next key that grows, so the walk could read another key's entities. Collect first, then change.

## Full example [#full-example]

Units found by team, by name and by level, arrows that belong to an archer, and heroes in several parties at once.
Put the files in a console project that references EasyEcs (`dotnet add package EasyEcs`) and run it with
`dotnet run`.

<Accordions>
<Accordion title="Components.cs">

```csharp title="Components.cs" doccheck=example
using EasyEcs;

// Value indexes: Key is the value an entity is found by.
public partial record struct Team([IndexKey] int Id) : IComponent;

// A unique key: no two players have one name.
public partial record struct PlayerName([UniqueKey] string Value) : IComponent;

// An int key compares, so this index can also walk a range of levels in order.
public partial record struct Level([IndexKey] int Value) : IComponent;

// A link: each arrow has one owner, and the index lists the arrows of an owner.
[WhenTargetDestroyed(TargetPolicy.Destroy)]                       // destroying the archer destroys its arrows
public partial record struct OwnedBy([IndexKey] EntityId Owner) : IComponent;

public struct Arrow : IComponent;

// A relation: an entity can hold many of these, one per party it is in.
public record struct MemberOf(EntityId Target) : IRelation;
```

</Accordion>
<Accordion title="Program.cs">

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();

// ---- Value indexes ----
for (int i = 0; i < 9; i++)
{
    world.CreateEntity(new Team(i % 3), new Level(i + 1));
}

world.CreateEntity(new PlayerName("alice"), new Level(42));

// The generated property is world.Index<Team, int>(): keep it in a local or a field.
var teams = world.TeamIndex;
Console.WriteLine($"team 0: {teams.Count(0)} units");

// Changing Team inside a loop over the team index is not allowed:
// collect the units first, then change them.
var moving = new List<Entity>();
foreach (var unit in teams.Find(1))
{
    moving.Add(unit);
}

// A Set moves the entity to its new key at once.
foreach (var unit in moving)
{
    unit.SetTeam(2);
}

Console.WriteLine($"team 1: {teams.Count(1)} units, team 2: {teams.Count(2)} units");

// A unique key finds one entity.
if (world.PlayerNameIndex.TryGet("alice", out var alice))
{
    Console.WriteLine($"alice is level {alice.Level.Value}");
}

Console.Write("levels 3 to 6:");
foreach (var unit in world.LevelIndex.Range(3, 6))
{
    Console.Write($" {unit.Level.Value}");
}

Console.WriteLine();

// ---- One link per entity: arrows and their owner ----
Entity archer = world.CreateEntity(new Team(0));
for (int i = 0; i < 3; i++)
{
    world.CreateEntity(new OwnedBy(archer), new Arrow());
}

var arrows = world.OwnedByIndex;
Console.WriteLine($"the archer owns {arrows.Count(archer)} arrows");

// ---- Many links per entity: parties ----
Entity red = world.CreateEntity();
Entity blue = world.CreateEntity();
Entity hero = world.CreateEntity();
hero.Link(new MemberOf(red));
hero.Link(new MemberOf(blue));
world.CreateEntity().Link(new MemberOf(red));

var parties = world.Relations<MemberOf>();
Console.WriteLine($"red has {parties.Count(red)} members, blue has {parties.Count(blue)}");

hero.Unlink<MemberOf>(blue);
Console.WriteLine($"after the hero left: blue has {parties.Count(blue)}");

archer.Destroy();
Console.WriteLine($"arrows left after the archer died: {world.Count<Arrow>()}");
```

</Accordion>
</Accordions>

It prints:

```text
team 0: 3 units
team 1: 0 units, team 2: 6 units
alice is level 42
levels 3 to 6: 3 4 5 6
the archer owns 3 arrows
red has 2 members, blue has 1
after the hero left: blue has 0
arrows left after the archer died: 0
```

The units of team 1 are collected before their team changes, so the walk never reads a key that is being emptied.
The arrows go with the archer because of `TargetPolicy.Destroy`; without it they would keep a link to a destroyed
entity.

## How to use it fast [#how-to-use-it-fast]

| Instead of | Do | Why |
| --- | --- | --- |
| `world.Index<T, TKey>()` in a hot loop | Keep the index in a local or a field (or use `world.XIndex`) | Creation is cold; the property is O(1) but still a lookup |
| `Set` with the key the entity already has | `unit.SetZoneIfChanged(id)`, or compare first | A `Set` that keeps the key re-links nothing, but it is still a write |
| A scan comparing a key | `Find(key)` / `Count(key)` | O(1), then O(1) per match |
| A dictionary from key to entity checked by hand before each write | `IUniqueIndexed<TKey>`, `Get` / `TryGet` | One hash probe per write, checked on every path that writes |
| A hand-written grid of entity ids beside a unique index | [`IDirectIndexed<TKey>`](#direct-index) | One array entry per lookup, kept by every write, with the hash behind it |
| Sorting a query's results each tick | `Range` / `Descending` | The keys stay sorted as they change |
| Walking many big keys whole | [`GroupBy`](/en/docs/guide/groups) | A group's rows are contiguous in their own tables |

## What it costs [#what-it-costs]

- **Nothing until you ask.** The index is built by its first lookup (one walk of the matching tables); a world that
  never calls `Index` or `Relations` pays nothing. A [unique](#unique-keys) index is the exception: it exists from
  the first table holding its component.
- **Unique keys:** `Get` and `TryGet` are one hash probe; a write of a unique component adds one probe before it
  changes anything. `SetAll`, `EnableAll` and `Load` add one claiming pass over their rows; `Clone`, `Instantiate`,
  `LoadEntities`, `LoadEntitiesInto` and `MoveEntities` one probe per row and unique component. None of it allocates
  once warm.
- **Direct keys:** `Get`, `TryGet` and the check of a write read one slot; a key out of range, or in a slot another
  key holds, adds the hash probe. The slot array costs `Slots` times the key size plus 12 bytes, allocated with the
  index.
- **Memory:** one node per indexed entity, and one array of ids per key; a unique key keeps its one entity in the
  key's own record, with no array, so `Get` reads that record alone. A relation keeps one 20-byte link per element,
  recycled, and 8 bytes in its target's list.
- **`Count`** is a hash probe, or an array access for an `EntityId` key; **`Find`** adds one step per entity, and its
  `.Count` none.
- **A `Set` that changes the key** unlinks and links the entity (a few array writes; a hash probe for non-entity keys).
- **Ordered walks:** the first one sorts the keys; then each new or vanished key costs O(log keys) plus a block move.
- **Allocation:** only when the index sees a new key or a larger entity id, never per lookup.
- **Target policies:** O(1) per destroyed entity and O(1) per link it had.

## Pitfalls [#pitfalls]

| Mistake | What happens | Caught by |
| --- | --- | --- |
| Writing an indexed component through `ref`, `Get<T>()` or a query item | The index keeps the old key | [EECS015](/en/docs/guide/analyzer#eecs015) |
| Storing an `Entity` handle in a component | A managed column, write barriers, not saved | [EECS017](/en/docs/guide/analyzer#eecs017) |
| Giving entities the indexed component or a new key inside a `Find` loop over it | The walk can read another key's entities (removing the component and destroying entities are fine) | [EECS042](/en/docs/guide/analyzer#eecs042): collect first, then change |
| A public `Key => this` on a record struct | `ToString()` prints `Key` forever: a stack overflow | [EECS043](/en/docs/guide/analyzer#eecs043) (with a code fix): `[IndexKey]` on the struct, or `Shop IIndexed<Shop>.Key => this;` |
| `[IndexKey]` or `[UniqueKey]` on a struct (or in a type) that is not `partial` | Compile error: the generator cannot add the key | [EECS062](/en/docs/guide/analyzer#eecs062) (with a code fix) |
| A hand-written `Key` that returns one member | Works, but a public `Key` joins the record's `ToString()` and equality members | [EECS067](/en/docs/guide/analyzer#eecs067) (with a code fix): `[IndexKey]` on the member |
| `[WhenTargetDestroyed]` on a type that links to no entity | Compile error: no target to watch | [EECS068](/en/docs/guide/analyzer#eecs068) |
| Using an index from another thread | Indexes belong to the owner thread | [Threading](/en/docs/guide/threading#what-the-world-synchronizes) |
| Indexing one component by two key types | `InvalidOperationException`: one index per component | At run time |
| A `null` key (the default of a `string`) | The entity is indexed nowhere | By design |
| A unique key another entity holds | `InvalidOperationException`; nothing changes | At run time: `TryGet` first, or move the key from its holder first |
| Moving a unique key to its new holder before taking it from the old one | `InvalidOperationException` | Change the old holder first |
| `Clone`, `CreateEntities` or `Instantiate(prefab, span)` of several entities with a unique key | `InvalidOperationException`: the copies would share it | Give each entity its own key |
| `IDirectIndexed<TKey>` over sparse keys or a huge range (account ids) | A slot array as long as the range, mostly empty, or most keys colliding | Plain `IUniqueIndexed<TKey>` |
| A slot function whose keys held at once collide (a modulo smaller than the loaded area) | Lookups go to the hash: no gain | Make `Slots` cover the keys a world holds at once |
| `IUniqueIndexed<EntityId>`, or a unique component with a second key type | Compile error | [EECS036](/en/docs/guide/analyzer#eecs036): `IIndexed<EntityId>` for links |
| A symmetric link written on one side only | One player is the other's friend, not the reverse | One helper writes both sides ([symmetric relations](#symmetric-relations)) |
