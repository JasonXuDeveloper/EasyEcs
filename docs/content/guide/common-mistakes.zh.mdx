EasyEcs 里出的问题，大多来自面向对象的写法习惯，或者其他 ECS 库的习惯。分析器在编译期就能拦下其中一半左右；其余的能编译、能运行，
只是悄悄做错了事。下面每一条都是：你可能会这样写，为什么不对，应该怎么写。

## 数据 [#data]

### 改的是组件的副本 [#copy]

```csharp doccheck=expect-EECS038
var hp = hero.Health;             // 行的一份副本
hp.Value -= 10;                   // 表里还是旧值
```

生成的属性和 `Get<T>()` 一样返回 `ref`，而 `var` 会把它指向的值复制出来。保留 `ref`，或者直接通过属性来写：

```csharp
ref var health = ref hero.Health;
health.Value -= 10;
hero.Health.Value -= 10;          // 一样，写在一行里
```

之后没有代码再读这个副本时，由 [EECS038](/zh/docs/guide/analyzer#eecs038) 发现（警告，带代码修复）。详见[副本与 ref](/zh/docs/guide/refs-and-await#copies-and-refs)。

### 组件里存 `Entity` [#entity-in-component]

```csharp doccheck=expect-EECS017
public record struct Follow(Entity Leader) : IComponent;
```

`Entity` 持有对 World 的引用：这一列变成托管类型（要被 GC 扫描，不能整块复制），存档写不了它，迁移也不会改写它。存 `EntityId`，
需要时再查：

```csharp
public record struct Follow(EntityId Leader) : IComponent;
```

由 [EECS017](/zh/docs/guide/analyzer#eecs017) 发现（警告）。详见 [id、版本号与回收](/zh/docs/guide/entities-and-components#entityid)。

### 存下标而不是 id [#raw-index]

```csharp
public record struct OwnerSlot(int Index) : IComponent;
```

```csharp
var owned = world.CreateEntity(new OwnerSlot(hero.Id.Index));   // 指向之后复用这个下标的随便哪个实体
```

id 会被回收：主人销毁后，这个下标会分给下一个新建的实体。`EntityId` 还带着版本号，主人一旦不在，`TryGetEntity` 就什么也找不到：

```csharp
public record struct Owner(EntityId Id) : IComponent;
```

```csharp
var item = world.CreateEntity(new Owner(hero.Id));
if (world.TryGetEntity(item.Owner.Id, out var owner)) { /* 还活着 */ }
```

没有规则能发现。详见 [id、版本号与回收](/zh/docs/guide/entities-and-components#entityid)。

### 该用标签的地方用了标志位 [#flags]

```csharp
public record struct Mobility(bool Rooted) : IComponent;

public class MoveRooted : EcsSystem
{
    [ForEach] static void Move(ref Position p, in Velocity v, in Mobility m)
    {
        if (m.Rooted) return;                  // 每一行都要访问、都要判断
        p.X += v.X; p.Y += v.Y;
    }
}
```

标志位让每个关心它的系统都得访问每一行、再做分支。标签是没有字段的组件：查询直接跳过整张表，添加或移除它本身就是状态的变化：

```csharp
public struct Rooted : IComponent;

public class MoveFree : EcsSystem
{
    [ForEach, Without<Rooted>]                 // 被定身的实体根本不会被访问
    static void Move(ref Position p, in Velocity v) { p.X += v.X; p.Y += v.Y; }
}
```

如果状态每个 tick 都在翻转，字段比搬表便宜：见 [ECS 原则第 5 条](/zh/docs/ecs-principles#5-choose-the-cheapest-representation-for-frequent-changes)。

### 为了暂停而移除组件 [#remove-to-pause]

```csharp
public record struct Cooldown(int Ticks) : IComponent;
```

```csharp
var caster = world.CreateEntity(new Cooldown(30));
var kept = caster.Cooldown;             // 把值先存到别处
caster.RemoveCooldown();                // 被眩晕
caster.Set(kept);                       // 之后再放回去
```

这段时间里值总得有地方放，读这份暂存的每一处都是你要维护的代码。`DisableCooldown()`（即 `Disable<T>()`）让组件对查询、`Has` 和 `Get` 不可见，
值留在行里，`EnableCooldown()` 再把它还回来：

```csharp
caster.DisableCooldown();               // 被眩晕：冷却暂停
caster.EnableCooldown();                // 眩晕结束：还是原来的值
```

没有规则能发现。详见[禁用组件](/zh/docs/guide/cleanup-and-disable#disable-a-component)。

### record struct 键上写了公开的 `Key => this` [#public-key]

```csharp doccheck=expect-EECS043
public readonly record struct Market(long Id) : IActor<Market>
{
    public Market Key => this;          // 公开属性：会进 record 的 ToString()
}
```

record struct 的 `ToString()` 会打印所有公开属性。`Key` 返回 record 自己，打印它又要打印它的 `Key`，再打印 `Key`……
第一次写日志或在调试器里查看这个值，栈就溢出了。显式实现 `Key`，让它只属于接口：

```csharp
public readonly record struct Market(long Id) : IActor<Market>
{
    Market IIndexed<Market>.Key => this;
}
```

由 [EECS043](/zh/docs/guide/analyzer#eecs043) 发现（带代码修复）。完整的写法见 [Actors 示例](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Actors)。

### 用 `AddSingleton` 重置单例 [#add-singleton-reset]

```csharp
public record struct Round(int Number, int Tick) : ISingletonComponent;
```

```csharp
world.SetRound(1, 0);
world.AddSingleton<Round>();       // 抛异常：World 里已经有 Round
```

`AddSingleton<T>()` 只添加 World 里还没有的单例。已经有时它会抛 `InvalidOperationException`，不会悄悄换回默认值、
让所有系统读到一个没人设置过的值。要换值就直接替换：

```csharp
world.SetRound(2, 0);              // 下一回合，从 tick 0 开始
```

没有规则能发现；异常信息里写明了该用哪个调用。详见[添加、读、写](/zh/docs/guide/singletons#add-read-write)。

## 系统 [#systems]

### 系统里存状态 [#state-in-system]

```csharp doccheck=expect-EECS007
public class WaveSystem : EcsSystem
{
    private int _wave;
    protected override void OnUpdate() => _wave++;
}
```

这个字段别的代码读不到、存不了档、拍不了快照，系统一移除就没了。每个 World 一份的状态放进单例：

```csharp
public record struct Wave(int Number) : ISingletonComponent;

public class WaveSystem : EcsSystem
{
    protected override void OnUpdate() => World.GetOrAddWave().Number++;
}
```

由 [EECS007](/zh/docs/guide/analyzer#eecs007) 发现。详见 [ECS 原则第 2 条](/zh/docs/ecs-principles#2-systems-are-stateless)。

### 一个系统调用另一个系统 [#system-calls-system]

```csharp doccheck=expect-EECS008
public class LootSystem : EcsSystem { }

public class KillRewards : EcsSystem
{
    protected override void OnUpdate() { if (World.TryGetSystem(out LootSystem loot)) loot.Enabled = false; }
}
```

互相调用的系统没法单独移除、调整顺序或测试。一个写数据（标签、组件、单例），另一个排在它后面读：

```csharp
public struct Looted : IComponent;

public class LootSystem : EcsSystem
{
    protected override void OnUpdate() => World.SetAll(new Looted(), QueryFilter.Create().With<Dead>().Without<Looted>());
}

[UpdateAfter<LootSystem>]
public class KillRewards : EcsSystem
{
    [ForEach, With<Looted>]
    static void Reward(in Health hp) { }
}
```

由 [EECS008](/zh/docs/guide/analyzer#eecs008) 发现。详见 [ECS 原则第 3 条](/zh/docs/ecs-principles#3-systems-never-reference-systems)。

### 只读却写成 `ref` 参数 [#ref-that-reads]

```csharp
public record struct Speed(float Value) : IComponent;
```

```csharp doccheck=expect-EECS025
public class Throttle : EcsSystem
{
    [ForEach] static void Apply(ref Velocity v, ref Speed max)   // max 只是读
    {
        v = new Velocity(Math.Min(v.X, max.Value), Math.Min(v.Y, max.Value));
    }
}
```

`ref` 参数声明的是写。开启 `ParallelSystems` 时，写 `Speed` 的系统没法和任何碰 `Speed` 的系统同处一个阶段；如果 `Speed` 被追踪，
每一行还会被算作改过。只读就用 `in`：

```csharp
public class Throttle : EcsSystem
{
    [ForEach] static void Apply(ref Velocity v, in Speed max)
    {
        v = new Velocity(Math.Min(v.X, max.Value), Math.Min(v.Y, max.Value));
    }
}
```

由 [EECS025](/zh/docs/guide/analyzer#eecs025) 发现（警告，带代码修复）。详见[并行系统](/zh/docs/guide/threading#parallel-systems)。

### 对没有追踪的组件用 `[Changed<T>]` [#changed-untracked]

```csharp doccheck=skip
public record struct Gold(int Amount) : IComponent;
public record struct Hud(int Gold) : IComponent;

public class ShowGold : EcsSystem
{
    [ForEach, Changed<Gold>] static void Show(in Gold gold, ref Hud hud) => hud = new Hud(gold.Amount);
}
```

变更 tick 要占一列，所以只有声明要它的组件才有。给组件加上 `ITracked`：

```csharp
public record struct Gold(int Amount) : IComponent, ITracked;
public record struct Hud(int Gold) : IComponent;

public class ShowGold : EcsSystem
{
    [ForEach, Changed<Gold>] static void Show(in Gold gold, ref Hud hud) => hud = new Hud(gold.Amount);
}
```

由 C# 编译器发现（这个特性要求 `ITracked`，报 CS0315）。详见[标记组件](/zh/docs/guide/change-tracking#mark-the-component)。

### 通过 `ref` 读被追踪的组件 [#read-tracked-by-ref]

```csharp doccheck=expect-EECS025
int before = player.Get<Gold>().Amount;      // Get<T>() 算写：这一行被当成改过
```

`Get<T>()` 会给行打上标记，下次更新时每个 `[Changed<Gold>]` 系统都会访问它。用生成的属性（被追踪组件的属性是
`ref readonly`）、泛型代码里的 `Read<T>()` 或 `in` 参数来读：

```csharp
int amount = player.Gold.Amount;             // ref readonly：不打标记
```

由 [EECS025](/zh/docs/guide/analyzer#eecs025) 发现（警告，带代码修复）。详见[什么算写入](/zh/docs/guide/change-tracking#what-counts-as-a-write)。

### 只偶尔写入，却用 `ref` 拿追踪组件 [#ref-writes-every-row]

```csharp
public record struct Facing(int Direction) : IComponent, ITracked;   // 值变了才发给客户端
```

```csharp
public class Face : EcsSystem
{
    [ForEach]
    static void Turn(ref Facing facing, in Velocity velocity)      // 访问到的每一行都打 tick
    {
        int direction = velocity.X >= 0 ? 0 : 4;
        if (facing.Direction != direction) facing = new Facing(direction);
    }
}
```

追踪组件的 `ref` 参数不管方法有没有真的写，都算一次写入；`Query` 的查询项也一样（枚举器会给访问到的每一行打 tick）。结果每个
`[Changed<Facing>]` 读者都要访问所有实体，复制时把没人改过的值也发了出去。分析器看不出来，因为方法确实写了其中一些行。改用
`Mut<T>`：它只给写入的行打 tick，`SetIfChanged` 只在值不同时才写：

```csharp
public class Face : EcsSystem
{
    [ForEach]
    static void Turn(Mut<Facing> facing, in Velocity velocity) =>
        facing.SetIfChanged(new Facing(velocity.X >= 0 ? 0 : 4));
}
```

在系统外面，用 `in` 参数、`Read<T>()` 或生成的属性读，用 `entity.SetIfChanged(...)`（或生成的 `SetFacingIfChanged(...)`）写。
“有时写”的 `ref` 没有规则能发现；从来不写的那种由 [EECS025](/zh/docs/guide/analyzer#eecs025) 发现。详见
[什么算写入](/zh/docs/guide/change-tracking#what-counts-as-a-write)。

### 只读追踪组件的 `Query` 循环 [#query-that-reads]

```csharp
public record struct Rating(int Value) : IComponent, ITracked;   // 变了就同步给客户端
```

```csharp doccheck=expect-EECS046
int total = 0;
foreach (var item in world.Query<Rating>())
    total += item.Rating.Value;    // 每一行 Rating 都被打 tick，当作写过
```

`Query` 的元素给出的是 `ref`，枚举器会给走过的每一行打 tick：求个总数、找个实体、发一次同步，都会让每个
`[Changed<Rating>]` 读者去访问没人改过的行。`world.Read<…>()` 只读地走同样的行，不打 tick：

```csharp
int total = 0;
foreach (var item in world.Read<Rating>())
    total += item.Rating.Value;
```

由 [EECS046](/zh/docs/guide/analyzer#eecs046) 发现（警告，带代码修复）。详见
[只读的循环](/zh/docs/guide/queries#read)。

### `[Removed<T>]` 方法接收了 `T` [#removed-takes-t]

```csharp
public record struct Burning(int Ticks) : IComponent, ITracked;
public record struct Glow(bool On) : IComponent;
```

```csharp doccheck=expect-EECS016
public class Extinguish : EcsSystem
{
    [ForEach, Removed<Burning>] static void Out(in Burning burning, ref Glow glow) => glow = new Glow(false);
}
```

`[Removed<Burning>]` 访问的实体已经没有 `Burning` 了，这个方法永远不会运行。读行里的其他组件：

```csharp
public class Extinguish : EcsSystem
{
    [ForEach, Removed<Burning>] static void Out(ref Glow glow) => glow = new Glow(false);
}
```

由 [EECS016](/zh/docs/guide/analyzer#eecs016) 发现。详见[移除检测](/zh/docs/guide/change-tracking#removal-detection)。

### 以为 `[Removed<T>]` 能报告被销毁的实体 [#removed-destroyed]

```csharp
public record struct Avatar(int Skin) : IComponent, ITracked;
public record struct Despawns(int Count) : ISingletonComponent;
```

```csharp
public class CountDespawns : EcsSystem
{
    [ForEach, With<Position>, Removed<Avatar>]       // 只有移除：被销毁的实体已经没有行了
    static void Count(ref Despawns despawns) => despawns = new Despawns(despawns.Count + 1);
}
```

`[Removed<T>]` 访问的是还活着、但失去了 `T` 的实体。被销毁的实体已经没有行可访问，客户端永远收不到它消失的消息。打开 World 的
销毁日志，每个客户端用自己确认过的 tick 去读：

```csharp
using var server = new World(new WorldOptions { DestroyLogCapacity = 4_096 });   // 客户端最多可能落后这么多次销毁
var gone = new EntityId[4_096];                                          // 只分配一次，所有客户端共用
ulong acked = server.ChangeTick;                                          // 客户端最后确认的 tick
server.Update();
if (server.DestroyedSince(acked, gone, out int destroyed))
{
    for (int i = 0; i < destroyed; i++) Console.WriteLine($"despawn {gone[i]}");
}
else
{
    Console.WriteLine("too far behind: send the whole state");
}
```

没有规则能发现。详见[销毁日志](/zh/docs/guide/change-tracking#destroy-log)。

### 以为 `Count` 或 `Query` 会照顾分片 [#count-a-slice]

```csharp
public struct Npc : IComponent;
```

```csharp doccheck=expect-EECS044
var quarter = QueryFilter.Create().With<Npc>().Slice(0, 4);
int thinking = world.Count<Position>(quarter);   // ArgumentException：Count 需要所有匹配的行
```

分片是对每张表的切分，只有 `[ForEach]` 那类遍历（`ForEach`、`ForEachEntity`、`ForEachBatch` 及其并行形式）认它。`Query`、
`Read`、`Count`、`Any`、`DestroyAll`、`entity.Run` 和批量调用需要所有匹配的行，遇到分片的过滤条件会直接抛异常，而不是只回答一部分。
计数时去掉分片；分片系统访问了多少，看它的统计：

```csharp
int npcs = world.Count<Position>(QueryFilter.Create().With<Npc>());   // 全部；一个分片大约 npcs / 4 个
```

打开 `MeasureSystems` 后，`[ForEach(Slices = N)]` 方法的 `system.Stats.LastEntities` 就是它那一份。过滤条件在同一个方法或类型里构造时由
[EECS044](/zh/docs/guide/analyzer#eecs044) 发现，否则运行时报错。详见
[分片](/zh/docs/guide/systems#slices)。

### 给 `[Changed<T>]` 方法分片 [#slice-changed]

```csharp doccheck=expect-EECS035
public class SendGold : EcsSystem
{
    [ForEach(Slices = 4), Changed<Gold>]
    static void Send(in Gold gold, ref Hud hud) => hud = new Hud(gold.Amount);
}
```

`[Changed<T>]` 方法访问系统上次运行以来写过的行，而每次运行都会把这个标记往前推：一次运行跳过的那三片，变更就丢了。它本来就只访问
变过的行，去掉 `Slices` 即可。如果重的是变更引发的工作，就把这份工作记成数据，再用一个没有变更过滤条件的分片方法去摊开：

```csharp
public class SendGold : EcsSystem
{
    [ForEach, Changed<Gold>]
    static void Send(in Gold gold, ref Hud hud) => hud = new Hud(gold.Amount);
}
```

由 [EECS035](/zh/docs/guide/analyzer#eecs035) 发现。

### 每种 actor 手写一个分组 [#group-per-actor]

```csharp
public struct In<TActor> : IComponent;                  // 某一种 actor 的标签
public readonly record struct Shop(long Id) : IComponent;
public readonly record struct Guild(long Id) : IComponent;
```

```csharp
[With<In<Shop>>] public struct ShopGroup : ISystemGroup;      // 每多一种 actor 就多写一个结构体
[With<In<Guild>>] public struct GuildGroup : ISystemGroup;
```

每加一种 actor 都要把分组再写一遍，而泛型接口没法用特性带上过滤条件：C# 不允许特性里出现类型参数（`[With<In<TSelf>>]` 是 CS8968）。
接口 `ISystemGroupWith<T>` 和 `ISystemGroupWithout<T>` 可以写类型参数，所以一个泛型接口就能让每种 actor 类型同时成为自己的键组件、分组和过滤条件：

```csharp
public interface IActor<TSelf> : IComponent, IIndexed<TSelf>, ISystemGroup, ISystemGroupWith<In<TSelf>>
    where TSelf : struct, IActor<TSelf>, IEquatable<TSelf>;

public readonly record struct Shop(long Id) : IActor<Shop> { Shop IIndexed<Shop>.Key => this; }
public readonly record struct Guild(long Id) : IActor<Guild> { Guild IIndexed<Guild>.Key => this; }
```

没有规则能发现。详见[分组过滤](/zh/docs/guide/systems#group-filters)。

## 结构 [#structure]

### 结构变更之后还拿着 `ref` [#ref-after-change]

```csharp doccheck=expect-EECS047
ref var life = ref hero.Health;
hero.SetStunned();                 // 行搬到了另一张表
life.Value -= 10;                  // 写的是旧位置
```

添加组件、禁用组件或销毁实体会搬动行，之前拿到的 `ref` 还指着旧位置。变更之后重新取：

```csharp
hero.SetStunned();
hero.Health.Value -= 10;
```

ref、变更和使用在同一个块里时，由 [EECS047](/zh/docs/guide/analyzer#eecs047)（警告）发现。详见[变更前后的 ref](/zh/docs/guide/structural-changes#refs-across-a-change)。

### 跨 `await` 拿着 `ref` [#ref-across-await]

```csharp doccheck=skip
ref var stamina = ref hero.Health;
await Task.Delay(100);
stamina.Value -= 10;
```

编译器会拒绝（CS9217），而且有道理：等待期间这一行什么都可能发生。保留 `Entity`，在 `await` 之后、回到所有者线程上再取一次组件：

```csharp
await Task.Delay(100);
if (hero.HasHealth) hero.Health.Value -= 10;
```

由 C# 编译器发现。详见 [ref 与 await](/zh/docs/guide/refs-and-await#across-await)。

### 通过 `ref` 写被索引的键 [#indexed-by-ref]

```csharp
public record struct Zone(int Id) : IComponent, IIndexed<int> { public int Key => Id; }
```

```csharp doccheck=expect-EECS015
public static class Portals
{
    public static void Enter(Entity player) => player.Get<Zone>() = new Zone(2);
}
```

索引追踪的是 `Set`；通过 `ref` 写会背着它改掉键，查找时玩家还在旧区域。用 `Set` 或生成的 `SetX` 写：

```csharp
public static class Portals
{
    public static void Enter(Entity player) => player.SetZone(2);
}
```

由 [EECS015](/zh/docs/guide/analyzer#eecs015) 发现。详见[值索引](/zh/docs/guide/indexes-and-relations#value-indexes)。

### 唯一键先给了新主人 [#rekey-order]

```csharp
public record struct Seat(int Number) : IComponent, IUniqueIndexed<int> { public int Key => Number; }
```

```csharp
var alice = world.CreateEntity(new Seat(1));
var bob = world.CreateEntity(new Seat(2));
bob.SetSeat(1);       // InvalidOperationException：alice 还占着 1 号座位
alice.SetSeat(2);
```

唯一索引在存入之前就检查每一次写入，所以任何时刻都不会有两个实体持有同一个键。先把键空出来，再交出去：先改（或移除）当前的持有者，
再改新的那个。互换要经过一个空闲的键：

```csharp
var carol = world.CreateEntity(new Seat(11));
var dave = world.CreateEntity(new Seat(12));
carol.SetSeat(-1);    // 没人占用的键
dave.SetSeat(11);
carol.SetSeat(12);
```

被拒绝的写入什么都不改：实体保留原来的键，World 保持原样。运行时报错。详见[唯一键](/zh/docs/guide/indexes-and-relations#unique-keys)。

### 复制带唯一键的实体或预制体 [#unique-copies]

```csharp
var usher = new Prefab().Set(new Seat(0), new Health(100));
var ushers = new Entity[10];
world.Instantiate(usher, ushers);   // InvalidOperationException：十个实体，一个键
```

唯一键每复制一份，就多一个持有者。带键实体的 `Clone()` 会抛异常；预制体带着键时，第二次 `Instantiate(prefab)`、以及一次实例化多个的
`Instantiate(prefab, entities)` 也会。键不要放进预制体，每个实例各给一个：

```csharp
var guest = new Prefab().Set(new Health(100));
var guests = new Entity[10];
for (int i = 0; i < guests.Length; i++)
    guests[i] = world.Instantiate(guest, new Seat(100 + i));   // 每个实例一个键
```

null 键（`string` 键的默认值）不算键：预制体可以带着它，每个实例都拿到它。运行时报错。详见[预制体](/zh/docs/guide/prefabs)。

### 启用一个已被别人拿走的唯一键 [#disabled-unique]

```csharp
var regular = world.CreateEntity(new Seat(5));
regular.DisableSeat();                   // 禁用的键不算键：5 号座位空出来了
var walkIn = world.CreateEntity(new Seat(5));
regular.EnableSeat();                    // InvalidOperationException：walkIn 占着 5 号座位
```

被禁用的组件保留值，但会离开索引，所以它关着的时候键可能被别人拿走。启用时要重新认领这个键，别的实体持有它就会失败，组件保持禁用。
`EnableAll` 先检查所有行，失败的方式一样。启用前先查一下这个键；冲突时给其中一个换个键：`Set` 一次调用就存入空闲的键并启用组件：

```csharp
if (world.SeatIndex.TryGet(5, out var holder) && holder != regular)
    regular.SetSeat(6);                  // 换一个键，启用
else
    regular.EnableSeat();
```

运行时报错。详见[禁用组件](/zh/docs/guide/cleanup-and-disable#disable-a-component)。

### 复制 `DynamicBuffer<T>` [#buffer-copy]

```csharp
public record struct Loot(int Item);
```

```csharp doccheck=expect-EECS012
public static class Inventory
{
    public static void Give(Entity player, Loot loot)
    {
        var bag = player.Read<DynamicBuffer<Loot>>();    // 共享同一个列表的副本
        bag.Add(loot);                                   // 这次写入不会被标记
    }
}
```

缓冲指向它的列表：通过副本写的还是同一个列表，却不会把实体标记为改过；把副本存起来，两个实体就共用一个列表。通过实体去拿：

```csharp
public static class Inventory
{
    public static void Give(Entity player, Loot loot)
    {
        ref var bag = ref player.Get<DynamicBuffer<Loot>>();
        bag.Add(loot);
    }
}
```

由 [EECS012](/zh/docs/guide/analyzer#eecs012) 发现。详见[动态缓冲](/zh/docs/guide/dynamic-buffers)。

### 销毁父实体，却以为子实体还在 [#parent-destroy]

```csharp
var ship = world.CreateEntity(new Position(0, 0));
var turret = world.CreateEntity(new Position(1, 0), new ChildOf(ship));
ship.Destroy();                    // 炮塔跟着一起被销毁
```

`ChildOf` 默认是 `TargetPolicy.Destroy`：销毁父实体会销毁它的整棵子树。子实体怎么处理，为整个 World 定一次：

```csharp
world.ChildOfIndex.WhenTargetDestroyed(TargetPolicy.Remove);   // 孤儿变成根
```

没有规则能发现。详见[级联策略](/zh/docs/guide/hierarchy#cascade-policy)。

### 一个实体一个实体地做结构变更 [#loop-of-changes]

```csharp
public struct Fighter : IComponent;
```

```csharp doccheck=expect-EECS030
foreach (var item in world.Query<Fighter>())
    item.Entity.SetFrozen();       // 每个实体一次结构变更
```

每次调用搬一行。`SetAll`、`RemoveAll`、`DisableAll` 和 `EnableAll` 把一张表的行一起搬：

```csharp
int frozen = world.SetAll(new Frozen(), QueryFilter.Create().With<Fighter>());
```

由 [EECS030](/zh/docs/guide/analyzer#eecs030) 发现（警告，带代码修复）。详见[批量变更](/zh/docs/guide/bulk)。

### `CreateEntity` 之后紧接着 `Set` [#set-after-create]

```csharp doccheck=expect-EECS052
var bullet = world.CreateEntity(new Position(0, 0));
bullet.Set(new Velocity(1, 0));    // 新实体又被搬了一次
```

`CreateEntity` 把实体放进它拿到的那些组件对应的表；下一行的 `Set` 又把它搬到另一张表，如果那张表没有别人用，还要顺路建出来。
把所有组件都交给创建调用：

```csharp
var bullet = world.CreateEntity(new Position(0, 0), new Velocity(1, 0));
```

`Instantiate(prefab)` 之后再 `Set` 也一样：把实例自己的组件直接传给 `Instantiate`。由
[EECS052](/zh/docs/guide/analyzer#eecs052) 发现（警告，带代码修复）。详见
[创建实体](/zh/docs/guide/entities-and-components#create-entities)。

### 在查询循环里更新 World [#update-in-loop]

```csharp doccheck=expect-EECS051
foreach (var item in world.Query<Health>())
{
    item.Health.Value -= 1;
    world.Update();                // 循环还在走表，所有系统就跑了一遍
}
```

`world.Update()` 假定没有循环在走这个 World：它会跑所有系统，还会填掉循环里结构变更留下的空洞，把循环还没走到的行挪进已经走过的位置，
循环就漏掉了这些行。循环结束后再更新：

```csharp
foreach (var item in world.Query<Health>())
    item.Health.Value -= 1;
world.Update();
```

由 [EECS051](/zh/docs/guide/analyzer#eecs051) 发现；在系统里由 [EECS034](/zh/docs/guide/analyzer#eecs034) 发现。详见
[遍历时增删实体和组件](/zh/docs/guide/structural-changes#during-a-pass)。

### 只用 `Children` 收集子树 [#children-only]

```csharp
var subtree = new List<EntityId> { hero.Id };
foreach (var child in world.Children(hero)) subtree.Add(child.Id);   // 孙实体漏掉了
```

`Children` 只列一层。按这个组存档或搬走，孙实体会留在原地，跟着原来的实体一起销毁。`Descendants` 深度优先走完每一层：

```csharp
var group = new List<EntityId>();
world.Descendants(hero).AddTo(group, includeRoot: true);   // 英雄，然后是子实体、孙实体……
```

没有规则能发现。详见[迁移层级](/zh/docs/guide/hierarchy#moving)。

### 恢复的记录又被存了回去 [#record-written-back]

```csharp
public record struct Bank(long Gold) : IComponent, ITracked;        // 需要持久化：变了就存
public record struct Connection(int Socket) : IComponent;           // 只在运行时存在
```

```csharp
static Entity Activate(World world, ReadOnlySpan<byte> record)
{
    var actor = world.CreateEntity(new Connection(9), new Bank(0));  // 新 actor 的默认值
    world.LoadEntitiesInto(record, [actor]);                         // 算一次写入：存盘系统把 Bank 写回去
    return actor;
}
```

加载算写入，所以保存或同步 `[Changed<Bank>]` 行的系统每次激活都会把记录原样写回它的来处。加载时传 `markWritten: false`：存储里的
`Bank` 覆盖默认值，并且算作从未写过，代码改它之前保存系统都会跳过这个 actor：

```csharp
static Entity Restore(World world, ReadOnlySpan<byte> record)
{
    var actor = world.CreateEntity(new Connection(9), new Bank(0));  // 和新 actor 一样的默认值
    world.LoadEntitiesInto(record, [actor], markWritten: false);     // Bank 是存储里的值，不算变更
    return actor;
}
```

没有规则能发现。详见[记录](/zh/docs/guide/migration-and-unload#records)。

### 每个 tick 都调 `TrimExcess` [#trim-every-tick]

```csharp
while (running)
{
    world.Update();
    world.TrimExcess();   // 丢掉的表下一个 tick 又会建回来
}
```

`TrimExcess` 丢掉空表，把其余的表缩到现在装着的大小。运行中的 World 每个 tick 都在清空、填满表（死亡、出生、状态），下一个 tick
又得重新分配：零分配的稳态变成了反复分配，而且每次调用还要走一遍所有的表和缓存的查询。高峰过后、在安静的时候再调：

```csharp
world.Update();
if (world.DefaultUpdateCount % 12_000 == 0 && world.EntityCount < 10_000)   // 20 Hz 下每十分钟一次，而且要等空闲时
    world.TrimExcess();
```

在 `OnUpdate` 或 `[ForEach]` 方法里由 [EECS028](/zh/docs/guide/analyzer#eecs028) 发现（警告）；宿主的循环里没有规则能发现。详见[高峰过后还回内存](/zh/docs/guide/diagnostics#trim)。

## 线程 [#threads]

### 在其他线程上改 World [#other-thread]

```csharp doccheck=expect-EECS014
public static class Network
{
    public static void OnJoin(World world)
    {
        Task.Run(() => world.CreateEntity(new Position(0, 0)));
        world.CreateEntity(new Position(1, 1));
    }
}
```

World 的结构属于它的所有者线程，World 也不会加锁来共享它。把输入放进队列，由所有者线程上的系统把它变成实体；或者给每个线程一个
自己的 World。

由 [EECS014](/zh/docs/guide/analyzer#eecs014) 发现。详见[来自其他线程的输入](/zh/docs/guide/threading#input-from-other-threads)。

### 在并行方法里做结构变更 [#parallel-change]

```csharp doccheck=expect-EECS010
public class Reap : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }
}
```

一块块的行同时在多个线程上运行，谁都不能搬行。并行的部分只改值，结构变更交给顺序执行的方法：

```csharp
public class Reap : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }
}
```

由 [EECS010](/zh/docs/guide/analyzer#eecs010) 发现。详见并行 [`[ForEach]`](/zh/docs/guide/threading#parallel-foreach-methods) 方法。

### 在并行方法里调 `entity.Run` [#run-in-parallel]

```csharp
public struct Mend : IForEachEntity<Health>
{
    public static int WriteMask => 1;

    public void Execute(Entity target, ref Health hp) => hp.Value += 1;
}
```

```csharp doccheck=expect-EECS010
public class HealAll : EcsSystem
{
    [ForEach(Parallel = true), With<Health>]
    static void Heal(Entity e)
    {
        var mend = new Mend();
        e.Run<Health, Mend>(ref mend);  // 要做所有者遍历的簿记，job 还可能改结构
    }
}
```

`entity.Run` 用来在所有者线程上处理发给单个实体的请求或消息。它要做所有者线程上遍历的簿记，它的 job 也可能改结构，所以并行方法不能调它。
`[ForEach]` 方法本来就拿到了 job 会拿到的 `ref`，直接通过它们写：

```csharp
public class HealAll : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Heal(ref Health hp) => hp.Value += 1;
}
```

由 [EECS010](/zh/docs/guide/analyzer#eecs010) 发现。详见[`entity.Run`](/zh/docs/guide/queries#run-on-one-entity)。
