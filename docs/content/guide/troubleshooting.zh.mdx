## 为什么结构变更报 “started while another one was running”？ [#structural-change-running]

```text
InvalidOperationException: A structural change started while another one was running on this world: structural
changes are made by the world's owner thread, one at a time
```

一个 World 上有两个结构变更（创建、销毁、`Set`、`Remove`、添加单例或系统）重叠了。要么是所有者在改的同时另一个线程也在改，要么是
某个变更内部（你自己包在 EasyEcs 调用外面的回调）又发起了一个。EasyEcs 检查的是一个普通标志，能抓住很多这类竞争，但不是全部。

**修法：**同一时刻只让一个线程改 World。其他线程把改动作为数据交出来，经由一个队列，由所有者线程上的系统读空
（[来自其他线程的输入](/zh/docs/guide/threading#input-from-other-threads)、[托管](/zh/docs/guide/hosting#requests)），
或者每个线程各用一个 World。

## 为什么结构变更报 “while the world's structure is frozen”？ [#structure-frozen]

```text
InvalidOperationException: A structural change was made while the world's structure is frozen (systems or a parallel
[ForEach] running on several threads, or a batch job holding spans into the tables)
```

变更发生时，有别的代码正把表固定住：`ParallelSystems` 的并行阶段、`[ForEach(Parallel = true)]` 方法、批处理方法或
`ForEachBatch` job（span 指向列内部），或者标记了 `INoStructuralChanges` 的 job。分析器能看到的变更它会报
（[EECS010](/zh/docs/guide/analyzer#eecs010)、[EECS013](/zh/docs/guide/analyzer#eecs013)）；这一个是经由它追踪不到的辅助
方法或句柄发生的。

**修法：**把变更记成数据（标签、组件、请求实体），在一个单独运行的系统或 `[ForEach]` 方法里执行：带 `Entity` 或 `World` 参数的
方法，或者 `OnUpdate`。

## 为什么实体 “not alive”？ [#entity-not-alive]

```text
InvalidOperationException: Entity is not alive (destroyed, or a default handle)
```

在一个实体已被销毁的句柄上（它的 id 可能已经归了别的实体，版本号把两者区分开），或者在 `default(Entity)` 上调用了 `Get`、
`GetOrAdd`、`Set`、`Remove` 或 `Clone`。询问类调用不会抛异常，而是回答 false：`IsAlive`、`Has<T>()` 和 `TryGet<T>()`；
对这样的句柄调用 `Destroy` 什么也不做。

**修法：**实体可能在你拿到句柄之后死掉的地方，先查 `entity.IsAlive`；组件里存 `EntityId`，用
`world.TryGetEntity(id, out var entity)` 解析（[实体与组件](/zh/docs/guide/entities-and-components)）。

## 为什么 `Clone` 说实体 “is retired”？ [#clone-retired]

```text
InvalidOperationException: The entity is retired: it is only kept alive (tagged Retired) until its cleanup components
are removed, and cannot be cloned
```

带[清理组件](/zh/docs/guide/cleanup-and-disable#cleanup-components)的实体 `Destroy` 之后仍然活着，带上 `Retired` 标签，
直到某个系统释放了这些组件持有的资源。它还活着，`IsAlive` 为 true，但不会再被带回来：`Clone()` 拒绝它，`MoveEntities` 跳过它，
过滤条件里没写 `Retired` 时 `SetAll` 也不碰它。

**修法：** 在销毁之前克隆；句柄可能指向退休实体的地方，先看 `entity.IsRetired`。

## 为什么 `Get<T>()` 说实体没有这个组件？ [#no-component]

```text
InvalidOperationException: Entity has no Mana component
```

`Get<T>()`（以及生成的 `entity.Mana`）要求组件存在；被移除或[被禁用](/zh/docs/guide/cleanup-and-disable)的组件都算不存在。
**修法：**可有可无的地方用 `TryGet<T>(out var value)` 或生成的 `TryGetMana(out …)`，要默认值就用 `GetOrAdd<T>()`；在
`[ForEach]` 方法里用 [`Maybe<T>`](/zh/docs/guide/systems#maybe) 参数，或者按 `[With<T>]` / `[Without<T>]` 拆成两个方法。

## 为什么单例 “not added to this world”？ [#singleton-not-added]

```text
InvalidOperationException: Singleton Clock was not added to this world: set it before the systems that read it run
(world.SetClock(...) or world.AddSingleton<Clock>()), or use GetOrAddClock() where a default is meant
```

代码读了一个没人添加过的单例：`world.GetSingleton<T>()`、生成的 `world.Clock`、`world.SingletonRef<T>()`，或者把 `Clock`
当参数的 `[ForEach]` 方法。参数在系统运行时解析，所以第一次 `Update()` 就会抛异常，哪怕一个匹配的实体都没有。World 不会凭空造一个单例，
因为默认值很少是对的：步长为零的时钟会让所有实体原地不动，却没有任何报错指向漏掉的初始化（[单例](/zh/docs/guide/singletons#in-systems)）。

**修法：**在建 World 的地方、第一次 `Update()` 之前添加它（`world.SetClock(…)`、`world.AddSingleton<Clock>()`），
默认值合适的地方用 `GetOrAddSingleton<T>()` / `GetOrAddClock()`。

## 为什么 `AddSingleton` 说单例 “was added to this world already”？ [#singleton-exists]

```text
InvalidOperationException: Singleton Clock was added to this world already: replace its value with
world.SetClock(...) or world.Clock = ..., or use GetOrAddClock() to take it as it is
```

`AddSingleton<T>()` 只添加 World 里还没有的单例。已经有时它拒绝执行，不会把所有系统都在读的值重置成 `default`
（[单例](/zh/docs/guide/singletons#api)）。

**修法：** 用 `world.SetClock(…)`（或 `world.Clock = …`）替换值；代码只需要它存在时，用 `GetOrAddClock()` 原样取用。

## 为什么 `Maybe<T>.Value` 会抛异常？ [#maybe-empty]

```text
InvalidOperationException: The entity has no Mana (check HasValue)
```

方法访问的实体没有 `T`。**修法：**读 `Value` 之前先检查 `HasValue`（[`Maybe<T>`](/zh/docs/guide/systems#maybe)）。

## 为什么 `AddSystem` 说系统 “already belongs to a world”？ [#system-in-a-world]

```text
InvalidOperationException: ReceiveSpawns already belongs to a world
```

一个系统实例只属于一个 World。**修法：**每个 World 各建一个实例（`world.AddSystem<T>()` 每次都新建）。另外，同一个系统类型可以
在一个 World 里添加两次，那样它每次更新会运行两次。

## 为什么 `AddSystem` 报顺序成环？ [#ordering-cycle]

```text
InvalidOperationException: [UpdateBefore] / [UpdateAfter] form a cycle among A, B
```

列出的这些系统之间的顺序无法同时满足。分析器会报它在一次编译里看到的环（[EECS019](/zh/docs/guide/analyzer#eecs019)）；这个环跨了
程序集。**修法：**去掉其中一条顺序。

## 为什么 `Descendants` 报 “The ChildOf links form a cycle”？ [#childof-cycle]

```text
InvalidOperationException: The ChildOf links form a cycle
```

`world.Descendants(root)` 遇到了已经访问过的实体：某个实体成了自己的祖先，因为一次 `SetChildOf(…)` 把父实体挂到了它自己的
某个后代下面。EasyEcs 不在换父时检查（那样每次 `Set` 都要往上走一遍），所以遍历走到环的时候才发现。

**修法：**把 `child` 挂到 `parent` 下之前，从 `parent` 沿 `ChildOf` 往上走，碰到 `child` 就拒绝。实体要挂到自己的后代下面时，
先解除挂接（`RemoveChildOf()`）（[换父实体、解除挂接](/zh/docs/guide/hierarchy#reparent)）。

## 为什么有的组件不能禁用？ [#cannot-disable]

```text
InvalidOperationException: ChildOf cannot be disabled: remove it instead
```

`Disable<T>()` 让值保留、但对查询隐藏。[清理组件](/zh/docs/guide/cleanup-and-disable)和 `ChildOf` 不能这样隐藏：World 要一直看到
它们，才能完成销毁、维持层级。**修法：**移除这个组件，或者禁用另一个系统会过滤的组件。

## 为什么 `Capture`、`Restore`、`Save`、`Load`、`MoveEntities`、`RemoveTypes`、`TrimExcess` 要等遍历结束？ [#during-a-pass]

```text
InvalidOperationException: Capture cannot run while a query or system iterates the world: call it between updates
InvalidOperationException: MoveEntities cannot run while a query or system iterates the world: call it between updates
```

消息里写着被拒绝的调用：`Capture`、`Restore`、存档和加载（`Save`、`SaveWithout`、`SaveEntities`、`SaveEntitiesWith`、`SaveEntitiesWithout`、`Load`、
`LoadKeeping`、`LoadEntities`、`LoadEntitiesInto`）、`MoveEntities`、`GroupBy`、`RemoveTypes` 或 `TrimExcess`。它们要读、重写或丢弃整张表，
而查询的 `foreach` 或正在运行的系统正在遍历这些表；分析器在它看得到的遍历里会报出这些调用（[EECS041](/zh/docs/guide/analyzer#eecs041)）。
**修法：**在两次更新之间、任何查询循环之外调用它们（[快照](/zh/docs/guide/snapshots)、[存档](/zh/docs/guide/saves)、
[卸载](/zh/docs/guide/migration-and-unload#remove-types)、[修剪](/zh/docs/guide/diagnostics#trim)）。遍历期间创建实体、实例化预制体（带成员的也可以）
和其他结构变更都没问题。`Restore` 也会拒绝另一个 World
的快照（`ArgumentException`），以及 `RemoveTypes` 丢掉其中某些表之前拍的快照。

## 为什么存档加载不了？ [#save-refused]

```text
InvalidDataException: Not an EasyEcs save (or one of another format version)
InvalidDataException: The size of Stock changed (8 bytes saved, 12 now): its saves cannot be loaded (…)
InvalidDataException: The fields of Stock changed since the save: its saves cannot be loaded (…)
InvalidDataException: Stock was saved as raw rows and is written by its Nino formatter now: its saves cannot be loaded
InvalidDataException: Types of this process share the save id … (…): unload or rename one of them (…)
InvalidDataException: A damaged save: …
```

加载时，每个组件都要和读取它的代码对上，加载被拒绝时 World 保持原样。

- **Not an EasyEcs save：**这些字节是别的东西、被截断了，或者是另一个存档格式版本写的（EasyEcs 4.3 及更早版本的存档）。
- **大小或字段变了：**存档之后，原始行组件的字段被增、删、改名或改了类型，或者 `[NinoType]` 组件的改动超出了它的 Nino 格式允许的范围。
  结构会变的组件标成 `VersionTolerant` 或 `Keyed` 格式的 `[NinoType]`，或者保留旧类型、再用系统转换（[代码改了之后](/zh/docs/guide/saves#versioning)）。
- **原始行与 Nino：**存档之后，给非托管组件加上或去掉了 `[NinoType]`。
- **存档 id 冲突：**进程里两个类型的 id 相同：带命名空间的全名相同（同一插件的两个版本同时加载），或者某个 `[NinoFormerName]` 正好是
  另一个类型的名字。先卸载旧版本，或者给其中一个改名。
- **A damaged save：**某个计数或 id 越界，或者缓冲比它的字节还长：字节已损坏。

## 为什么写入时说唯一键已被占用？ [#unique-key-taken]

```text
InvalidOperationException: Seat is unique: entity … has key 5 already (change that entity's key first)
InvalidOperationException: Seat is unique: key 0 would be given to several entities at once
InvalidDataException: The save holds key 5 of unique Seat twice
InvalidOperationException: Seat is unique, but its module registered no index (…): call world.Index<T, TKey>() once before writing it
```

这个组件实现了 `IUniqueIndexed<TKey>`，而这次写入会让第二个实体拿到别人已有的键。写入在改动任何东西之前就做了检查，所以实体和
World 都保持原样。

- **已经有这个键：**另一个实体持有这个键。要转移一个键，先改持有者，再改新的那个；互换要经过一个空闲的键
  （[转移唯一键](/zh/docs/guide/common-mistakes#rekey-order)）。启用一个被禁用的组件会重新认领它的键，期间键被别人拿走了，也会这样失败。
- **一次给多个实体：**一次调用会把同一个键写进很多行：带键的 `CreateEntities` 或 `SetAll`、预制体带着键时的
  `Instantiate(prefab, entities)`，或者 `Clone()`。给每个实体各自的键（[复制唯一键](/zh/docs/guide/common-mistakes#unique-copies)）。
- **存档里有重复的键：**存档是没有唯一约束的代码写的，或者被改过。先用旧代码的 World 加载并把键修好，或者迁移期间先去掉约束。
- **没有注册索引：**生成器会为它能看到的每个唯一组件注册索引。它看不到的类型（反射创建的，或者在没用生成器编译的程序集里）需要
  每个 World 在第一次写入前调一次 `world.Index<T, TKey>()`。

## 为什么 `Count` 或 `Query` 遇到分片过滤条件会抛异常？ [#sliced-filter]

```text
ArgumentException: A sliced filter (QueryFilter.Slice) applies to ForEach passes only: this call needs every matching row. (Parameter 'filter')
```

`QueryFilter.Slice(index, of)` 把每张表切成几份，只有 `ForEach`、`ForEachEntity`、`ForEachBatch` 及其并行形式会按份访问。
`Query`、`Read`、`Count`、`Any`、`DestroyAll`、`entity.Run`、`SetAll` 和其他批量调用需要所有匹配的行，所以拒绝它。**修法：**给这些
调用传不带 `Slice` 的过滤条件；分片系统访问了多少，看 `system.Stats.LastEntities`（[分片](/zh/docs/guide/systems#slices)）。

## 为什么 `DestroyedSince` 说没有销毁日志？ [#no-destroy-log]

```text
InvalidOperationException: The world keeps no destroy log: set WorldOptions.DestroyLogCapacity to its capacity
```

销毁日志默认是关的：每条记录 16 字节，和 World 一起分配。**修法：**用 `new WorldOptions { DestroyLogCapacity = n }` 创建 World，`n` 是最慢的
读者两次读取之间可能发生的销毁次数。`DestroyedSince` 返回 `false`，说明这个读者落后的比日志装得下的还多：把完整状态重新发给它
（[销毁日志](/zh/docs/guide/change-tracking#destroy-log)）。

## 为什么我的系统从不运行？ [#system-does-not-run]

按顺序检查：

1. **它被添加到了这个 World：**`world.Systems` 列出所有系统。
2. **它是启用的：**`Enabled` 为 true，且 `Error` 为 null。`SystemErrorPolicy.Disable` 下，异常会把它关掉；设
   `Enabled = true` 会清掉错误并重试。
3. **它的分组被更新了：**带 `[UpdateInGroup<G>]` 的系统只在 `world.Update<G>()` 时运行，`world.Update()` 永远不会跑它。
4. **它的间隔到了：**`[UpdateInterval(N)]` 时，它在所属分组每第 N 次更新时运行，第一次是第 N 次，再按它的 `Phase` 偏移。
5. **它的过滤条件能匹配：**用 `world.Count<T…>(filter)` 数一数方法需要的实体。分组的过滤条件对分组里所有方法都生效：分组结构体上的
   `[With<T>]`、`[Without<T>]`、`[WithAny<T>]`，以及分组自己或它实现的任何接口带来的 `ISystemGroupWith<T>` / `ISystemGroupWithout<T>`
   （泛型 actor 接口就带着它们）。被禁用的组件算不存在。
6. **确实有东西可看：**`[Changed<T>]` 方法只访问它的系统上次运行以来被写过的行，`[Removed<T>]` 方法只访问那之后失去 `T` 的实体
   （[变更追踪](/zh/docs/guide/change-tracking#ticks)）。

`WorldOptions.MeasureSystems` 会在 `system.Stats.Runs` 里统计每次运行，能分清“从没跑过”和“跑了但什么都没做”。

## 为什么 `entity.Run` 返回 `false`？ [#run-false]

`entity.Run<T…, TJob>(ref job, filter)` 只在实体接得住时才跑 job，以下情况不跑，返回 `false`：

1. **实体已经不在了：**拿到句柄之后被销毁了，或者是 `default(Entity)`。`Run` 不会像 `Get` 那样抛异常。
2. **缺少 job 要的组件：**`TJob` 之前的每个类型实参都必须存在（被禁用的组件算不存在）。用 `entity.Has<T1, T2>()` 检查。
3. **不满足过滤条件：**有 `Without<T>` 排除的组件、缺 `WithAny` 要的组件、`Changed<T>(tick)` 之后没被写过、不在指定的分组里。
   去掉过滤条件再跑一次，就能和前两种情况分开。

**修法：**把 `false` 当成请求的结果（actor 没了、单位死了），而不是错误；实体可能已被替换时，按 `EntityId` 重新查找
（[`entity.Run`](/zh/docs/guide/queries#run-on-one-entity)）。

## 为什么我的系统没有并行？ [#not-parallel]

开了 `ParallelSystems`，系统只有在访问集已知、且不冲突时才会共享一个阶段。带 `World` 参数或不只当身份用的 `Entity` 参数、有实例 `[ForEach]` 方法、
重写了 `OnUpdate`，或者一个 `[ForEach]` 方法都没有的系统，都单独运行。一个写另一个读或写的东西，两个系统就冲突；`ref` 参数即使
方法体只读也算写：改用 `in`（[并行系统](/zh/docs/guide/threading#parallel-systems)）。顺序（`[UpdateAfter<T>]`）也会把后面的
系统放进后面的阶段。

## 为什么并行遍历说索引 “is not built yet”？ [#index-not-built]

```text
InvalidOperationException: The index of Unit by Team is not built yet, and building it now, while a parallel stage or pass runs, would change it under the threads reading it. Find it through a Lookup<Unit> parameter (its index is built before the pass), or look it up once on the owner thread before the update.
```

值索引由第一次查找建立。在多个线程上跑的代码（并行 `[ForEach]` 方法、并行阶段里的系统、`world.ForParallel`）通过 `World` 去查，
就会在别的线程读它的同时建它，所以查找会拒绝。**修法：**用 [`Lookup<T>`](/zh/docs/guide/threading#lookups) 参数，在它上面调
`TryFind`、`Find` 或 `Count`：生成的 job 会在遍历前建好索引。或者在更新前，在所有者线程上查一次这个键，之后的遍历就有索引了。

## 为什么 `Lookup<T>` 说它 “holds no index”？ [#lookup-no-index]

```text
InvalidOperationException: This Lookup<Unit> holds no index by Team: a [ForEach] method gets one when it calls TryFind, Find or Count on the parameter itself (the index is then built before the pass)
```

生成器按方法体里对这个参数的调用来准备 `Lookup<T>` 的索引。在别处发起的调用（参数被传进的辅助方法里）指向的索引，job 并不知道。
**修法：**在 `[ForEach]` 方法本身里，用这个键类型对参数调 `TryFind`、`Find` 或 `Count`，再把结果传给辅助方法
（[查找](/zh/docs/guide/threading#lookups)）。

## 为什么瓦片在加载或读取时抛异常？ [#tile-throws]

```text
ArgumentOutOfRangeException: Layers 0 to 20 of a GasCube tile of 16 layers
InvalidOperationException: The DynamicBuffer<Gas> of … holds 200 cells; a GasCube tile has 4096
InvalidOperationException: GasCube is a 16 x 16 x 16 tile with a halo of 20: a halo of 20 is wider than its rows (16 cells)
ArgumentOutOfRangeException: Outside the padded tile: a cell, row or layer past the halo
InvalidOperationException: The tile was loaded without its mask (mask: false): it has no active rows
```

- **层：**`Pad(from, to)` 要求 `0 <= from < to <= Height`。
- **格子：**瓦片的缓冲要有 `Width × Depth × Height` 个格子；创建瓦片时就填到这个长度（[网格](/zh/docs/guide/grids)）。
- **形状：**`ITileShape` 的宽、深（1 到 64）、高和光环对不上；分析器在声明处报告这个形状（[EECS072](/zh/docs/guide/analyzer#eecs072)）。
- **超出加载后的瓦片：**游标或 `padded[x, y, z]` 读到了光环之外。让每个偏移都在 `Halo` 之内，或者声明更大的光环。
- **没有掩码：**`Rows(...)` 走掩码里的活跃行；用 `mask: false` 加载的瓦片一行都没有。带掩码加载，或者自己走每一行
  （[高瓦片](/zh/docs/guide/grids#layers)）。

## 为什么我的方法没有得到向量循环？ [#no-vector-loop]

只有参数和方法体能变成通道的方法，生成器才写向量循环：组件里是同一种大小的数，没有 `Entity`、`World`、`Mut<T>`、span、`Scratch<T>`、
`Lookup<T>`、`Emit<T>` 或 `Tile` 参数，没有它无法向量化的调用。否则方法逐行运行，结果正确，只是慢一些。**修法：**读出原因，改掉它点名的东西：
看起来是为向量循环写的方法，[EECS055](/zh/docs/guide/analyzer#eecs055)（建议，在 IDE 里显示）会点名原因；`SimdMode = SimdMode.Require`
把它变成构建错误（[EECS056](/zh/docs/guide/analyzer#eecs056)）；`world.DescribeSchedule()` 打印每个方法拿到的循环
（`SystemInfo.Loops`，[向量循环](/zh/docs/guide/systems#vector-loops)）。

## 为什么我的并行方法只在一个线程上跑？ [#parallel-one-thread]

并行 `[ForEach]` 方法把行切成块，每块至少 1,024 行（写被追踪的组件时 4,096 行），不到两块就在调用线程上跑。辅助线程帮不上忙的遍历，
也在那里跑。几百个很重的行于是只有一块。**修法：**把 [`ChunkRows`](/zh/docs/guide/threading#chunk-rows) 设成一个线程每次拿的行数
（从 行数 ÷ 线程数 ÷ 4 开始，不低于 64）；轻的行保持默认。

## 为什么浮点总和在不同运行或机器上不一样？ [#float-total]

浮点的 `Reduce<T>` 求和按块舍入，默认块大小跟着线程数走，所以换台机器就切出别的块。**修法：**设
[`ChunkRows`](/zh/docs/guide/threading#chunk-rows)：这样每次运行、任何线程数下总和都一样，只是不与同一方法 `Parallel = false` 时的总和逐位相同
（[归约](/zh/docs/guide/threading#reductions)）。整数总和、最小值和最大值怎样都是精确的。

## 为什么 `EntityRandom` 抽出同样的数？ [#random-repeats]

一次抽取是 (seed, entity, tick, stream) 的纯函数。tick 不推进，就会再抽出上一步的数；同一步里同一实体对同一个流抽两次，结果相等
（[EECS088](/zh/docs/guide/analyzer#eecs088)）。**修法：**每一步把 `World.EntityRandom.Tick` 推进一次，放在推进模拟时钟的那个系统里；
一行里的每次抽取用自己的流（[随机数](/zh/docs/guide/threading#entity-random)）。

## 为什么某个生成成员不见了？ [#member-missing]

生成器把 `entity.Health`、`SetHealth(…)`、`world.Clock` 等写成 C# 14 扩展成员。以下情况它什么都不生成：

- 项目的语言版本低于 C# 14（`<LangVersion>` 设得比 .NET 10 默认值低）。
- 类型是泛型，或者嵌套在生成代码看不到的类型里。
- 接收者已经有同名成员：叫 `Id` 的组件不会得到 `entity.Id`（句柄自己就有），你自己写的同名成员优先。
- 组件带索引（`IIndexed<TKey>`）：没有 `GetOrAddX()`，`entity.X` 是只读的；用 `SetX(…)` 写。

泛型 API 始终可用：`Get<T>()`、`Read<T>()`、`Set(…)`、`Has<T>()`、`Remove<T>()`、`GetSingleton<T>()`
（[生成成员](/zh/docs/guide/entities-and-components)）。

## 为什么通过 `ref` 写的值不见了？ [#ref-lost]

`entity.Get<T>()` 或查询项给出的 `ref`，只在 World 下一次结构变更之前有效（变更可能搬动行），也绝不能跨 `await`。通过旧 `ref`
写入，落在了实体已经不用的内存上。变更之后通过句柄重新读（[ref 与 await](/zh/docs/guide/refs-and-await)）。

被追踪或带索引的组件，通过 `entity.X` 和 `Read<T>()` 拿到的是只读的：写入走 `Set(…)`，被追踪的组件也可以用生成的 `WriteX()`，
这样变更才会被打上 tick（[变更追踪](/zh/docs/guide/change-tracking#write-as-usual)）。

## 为什么加载后某个组件不见了？ [#save-dropped-data]

存档按 Nino 类型 id（带命名空间的全名的哈希）记录每个类型，加载时跳过这个进程里没有的类型。存档之后被改名或挪了命名空间的组件，加载时
就当作不存在：数据被丢弃，也不报错。给改了名的类型标上 `[NinoFormerName("旧命名空间.旧名字")]`，旧的行就能读回来
（[代码改了之后](/zh/docs/guide/saves#versioning)）。

## 为什么 `MoveEntities` 留下了某个实体？ [#move-skipped]

`MoveEntities` 会跳过搬不了的 id，返回值只数搬走的：失效的 id、重复给出的 id，以及已经退休、只为[清理组件](/zh/docs/guide/cleanup-and-disable#cleanup-components)
留着的实体（带 `Retired` 标签）。被跳过的 id 在 `moved` 里对应的位置是 `default`。没放进这组的子实体不算跳过：它会随搬走的父实体一起被销毁。
搬走的实体还会把清理组件留在原处、留在退休的原实体上，让这个 World 的系统只释放一次资源；新实体没有这些组件。

**修法：** 拿返回值和 id 个数比较；用 `world.Descendants(root).AddTo(ids, includeRoot: true)` 收集整棵子树
（[迁移层级](/zh/docs/guide/hierarchy#moving)）；搬完之后在目标 World 里给它加上自己的资源组件。

## 为什么生成器看不到另一个生成器加上的接口？ [#other-generators]

组件、单例和系统的 EasyEcs 接口（`IComponent`、`ITracked`、`IIndexed<TKey>` 等）必须写在你自己的代码里。所有源生成器读的是
同一份输入，谁也看不到别人的输出，所以另一个生成器给 partial 类型加上 `IComponent` 时，EasyEcs 的生成器并不知道它是组件：不会为它
生成成员，加载存档时也要等进程用过这个类型才找得到它。把接口写在你自己的声明上；另一个生成器照样可以往同一个 partial 类型里加成员。

## 为什么 actor 键在 `ToString` 里栈溢出？ [#key-tostring-overflow]

record struct 自己就是自己的键（`IIndexed<TSelf>`，actor 写法），又把 `Key` 写成公开属性 `public Shop Key => this;` 时，
`ToString()` 会打印所有公开属性：`Key` 打印 record，record 又打印 `Key`，直到栈溢出。写一行日志、做一次字符串插值，或者在调试器里看一眼这个值，
都会触发。

**修法：**在类型上用 `[IndexKey]` 声明键，生成器会显式实现 `Key`（也可以手写 `Shop IIndexed<Shop>.Key => this;`）。索引照样找得到它，`ToString()` 却看不到它了
（[常见错误](/zh/docs/guide/common-mistakes#public-key)）。
