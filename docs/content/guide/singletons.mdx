Some state belongs to the whole world, not to an entity: the tick clock, the match configuration, a score, a spatial
grid. A singleton is a struct that implements `ISingletonComponent`, with exactly one value per world. It is where
world-level state goes, since systems keep none ([EECS007](/en/docs/guide/analyzer#eecs007)), and because it lives in
the world, two worlds on two threads never share it.

## When to use it [#when-to-use-it]

<Callout type="idea" title="Use it for">
  World-level state that systems read or write: the clock and delta time, configuration loaded at startup, counters
  and totals, a spatial grid or a lookup table, the queue of input a system drains each tick.
</Callout>

<Callout type="warn" title="Skip it for">
  Static fields: every world in the process would share them. Per-entity data: that is a component. A list of things
  that each have their own state (players in a match): those are entities with a tag, which queries and indexes can
  select.
</Callout>

## How to use it [#how-to-use-it]

<Steps>
<Step>

### Declare it [#declare]

```csharp
public record struct Clock(long Tick, float DeltaTime) : ISingletonComponent;
public record struct Score(int Deaths) : ISingletonComponent;
```

</Step>
<Step>

### Add, read and write [#add-read-write]

```csharp
var world = new World();
world.SetClock(0, 1f / 30);                              // generated: adds it, or overwrites it
world.Clock.Tick++;                                       // generated: a ref, throws if not added
ref var score = ref world.GetOrAddScore();                // adds a default value if missing
score.Deaths++;
```

</Step>
<Step>

### Take it in a system [#in-systems]

A `[ForEach]` method takes a singleton as a `ref` or `in` parameter. It is resolved once per pass, not once per
entity. The singleton must exist by then: a system whose singleton was never added throws
`InvalidOperationException` on its first run, even when no entity matches, so add it where the world is built.

```csharp
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Die(Entity unit, in Health hp, ref Score score)
    {
        if (hp.Value > 0) return;
        unit.SetDead();
        score.Deaths++;
    }
}

public class ClockSystem : EcsSystem
{
    protected override void OnUpdate() => World.Clock.Tick++;   // in OnUpdate: through the system's World
}
```

</Step>
</Steps>

### The API [#api]

| Call | Generated member | Effect |
| --- | --- | --- |
| `ref T AddSingleton<T>()` | | Adds it (`default`); throws `InvalidOperationException` if the world has it already |
| `ref T GetSingleton<T>()` | `world.Clock` | A ref; throws if it was not added |
| `ref T GetOrAddSingleton<T>()` | `world.GetOrAddClock()` | A ref, adding `default` first if missing |
| `GetOrAddSingleton<T>() = value` | `world.SetClock(tick, deltaTime)` | Sets the value, adding it if missing |
| `bool HasSingleton<T>()` | `world.HasClock` | Whether it exists |
| `bool TryGetSingleton<T>(out T)` | | A copy, if present |
| `bool RemoveSingleton<T>()` | `world.RemoveClock()` | Removes it; false if it was not added |
| `SingletonRef<T> SingletonRef<T>()` | | A [stable handle](#stable-handles); throws if it was not added |

```csharp
world.SetScore(0);                                        // generated from the record's constructor
bool has = world.HasClock;
if (world.TryGetSingleton<Clock>(out var copy)) Console.WriteLine(copy.Tick);
world.RemoveScore();
```

The generated members follow the rules of [generated members](/en/docs/guide/entities-and-components#generated-members):
`SetX` has one overload per public constructor, and a singleton without fields gets no `GetOrAddX`.

### Stable handles [#stable-handles]

A singleton's storage never moves, unlike component rows. `world.SingletonRef<T>()` returns a `SingletonRef<T>`
(it throws if the singleton was not added) whose `Value` is a `ref T` with no lookup at all, valid for as long as the singleton
exists. Take it once at setup and keep it, in a field of your host or a local of a loop.

```csharp
var clock = world.SingletonRef<Clock>();     // once, at setup
clock.Value.Tick++;                          // later: a ref, no lookup
```

- A reset is a write: `world.SetClock(…)` or `world.Clock = default` keeps the storage, so the handle sees the new
  value. `AddSingleton<T>()` on an existing singleton throws instead of resetting it.
- `RemoveSingleton<T>()` detaches it: writes through the old handle no longer reach the world, also after the
  singleton is added again. Take a new handle then.
- [Snapshots](/en/docs/guide/snapshots) restore singletons into the same storage, so handles keep working after a
  `Restore`.
- Generated `[ForEach]` jobs resolve each singleton parameter once per pass; parallel jobs, which are copied to
  other threads, carry a `SingletonRef<T>`.

### Singletons and threads [#threads]

- A singleton belongs to its world, so one world per thread shares nothing.
- With `WorldOptions.ParallelSystems`, a system that takes a singleton by `ref` writes it: it never shares a stage
  with another system that reads or writes the same singleton. Take it by `in` when the system only reads it.
- A `[ForEach(Parallel = true)]` method takes singletons only by `in`: every chunk would race on a `ref`
  ([EECS010](/en/docs/guide/analyzer#eecs010)).
- A singleton that holds a collection (a grid of cells, a queue) and is changed through an `in` parameter is scheduled
  as a read: [EECS011](/en/docs/guide/analyzer#eecs011) asks for `ref`.

## Full example [#full-example]

A clock, a configuration and a score as singletons: poison hurts three units each tick, and the death system counts
the dead. Put the files in a console project that references EasyEcs (`dotnet add package EasyEcs`) and run it with
`dotnet run`.

<Accordions>
<Accordion title="Components.cs">

```csharp title="Components.cs" doccheck=example
using EasyEcs;

public record struct Health(int Value) : IComponent;
public struct Dead : IComponent;

// World-level state: one value per world.
public record struct Clock(long Tick) : ISingletonComponent;
public record struct Poison(int DamagePerTick) : ISingletonComponent;
public record struct Score(int Deaths) : ISingletonComponent;
```

</Accordion>
<Accordion title="Systems.cs">

```csharp title="Systems.cs" doccheck=example
using EasyEcs;

// Advances the clock once per update, through the system's World.
public class ClockSystem : EcsSystem
{
    protected override void OnUpdate()
    {
        World.Clock.Tick++;
    }
}

// Reads the configuration by `in`: resolved once per pass, not once per unit.
[UpdateAfter<ClockSystem>]
public class PoisonSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Hurt(ref Health hp, in Poison poison)
    {
        hp.Value -= poison.DamagePerTick;
    }
}

// Writes the score by `ref`, reads the clock by `in`.
[UpdateAfter<PoisonSystem>]
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Die(Entity unit, in Health hp, ref Score score, in Clock clock)
    {
        if (hp.Value > 0)
        {
            return;
        }

        unit.SetDead();
        score.Deaths++;
        Console.WriteLine($"  tick {clock.Tick}: {unit} dies");
    }
}
```

</Accordion>
<Accordion title="Program.cs">

```csharp title="Program.cs" doccheck=example
using EasyEcs;

using var world = new World();

// Add the singletons where the world is built:
// a system that takes one throws on its first run otherwise.
world.SetClock(0);
world.SetPoison(25);
world.SetScore(0);

world.AddSystem<ClockSystem>();
world.AddSystem<PoisonSystem>();
world.AddSystem<DeathSystem>();

world.CreateEntity(new Health(50));
world.CreateEntity(new Health(75));
world.CreateEntity(new Health(100));

// A handle the host keeps: its Value is a ref, with no lookup.
var score = world.SingletonRef<Score>();

for (int i = 0; i < 2; i++)
{
    world.Update();
}

Console.WriteLine($"after tick {world.Clock.Tick}: {score.Value.Deaths} dead");

// Configuration changed from outside: the next pass reads the new value.
world.Poison.DamagePerTick = 50;
world.Update();

Console.WriteLine($"after tick {world.Clock.Tick}: {score.Value.Deaths} dead");
```

</Accordion>
</Accordions>

It prints:

```text
  tick 2: Entity 0v1 dies
after tick 2: 1 dead
  tick 3: Entity 2v1 dies
  tick 3: Entity 1v1 dies
after tick 3: 3 dead
```

The host reads the score through the `SingletonRef<Score>` it took once, and the systems see the configuration it
changes on the next update: with the poison doubled, both remaining units die on tick 3.

## How to use it fast [#how-to-use-it-fast]

| Instead of | Do | Why |
| --- | --- | --- |
| `GetSingleton<T>()` (or `World.X`) per entity inside a loop | A singleton parameter of the `[ForEach]` method | Resolved once per pass ([EECS027](/en/docs/guide/analyzer#eecs027) in a `[ForEach]` method) |
| A lookup on every call from host code | A `SingletonRef<T>` kept from setup | No lookup |
| `ref` for a singleton the system only reads | `in` | Lets the system share a parallel stage ([EECS025](/en/docs/guide/analyzer#eecs025)) |
| A static field | A singleton | Per world, saved and snapshotted with it |

## What it costs [#what-it-costs]

- **Storage:** one small box per singleton type in each world that has it; nothing per entity.
- **`GetSingleton`, `HasSingleton`:** a bounds check, one array load and a null check, with no type check; O(1).
- **`SingletonRef<T>.Value`:** one field load.
- **A `[ForEach]` parameter:** resolved once per pass.
- **Adding or removing** a singleton goes through the world's structural gate, like any structural change.

## Pitfalls [#pitfalls]

| Mistake | What happens | Caught by |
| --- | --- | --- |
| State kept in a system field instead | Invisible to other systems, lost on remove, shared by worlds if static | [EECS007](/en/docs/guide/analyzer#eecs007) |
| A class implementing `ISingletonComponent` | Does not compile | [EECS006](/en/docs/guide/analyzer#eecs006) |
| `AddSingleton<T>()` to reset a singleton the world has | `InvalidOperationException`; the value stays | Replace it with `world.SetX(…)` |
| Reading a singleton before it was added (`world.X`, `GetSingleton<T>()`, a `[ForEach]` parameter) | `InvalidOperationException`, naming the call that adds it | Add it at setup, or use `GetOrAddX()` where the default is right |
| A `ref` singleton in a parallel method | Races between chunks | [EECS010](/en/docs/guide/analyzer#eecs010) |
| `AddSingleton` or `RemoveSingleton` in a batch method, a parallel method or a parallel stage | `InvalidOperationException`: both go through the structural gate, and the structure is frozen there | [EECS010](/en/docs/guide/analyzer#eecs010), [EECS013](/en/docs/guide/analyzer#eecs013), and at run time |
| Changing a collection in a singleton through `in` | Scheduled as a read | [EECS011](/en/docs/guide/analyzer#eecs011) |
| Writing through a `SingletonRef<T>` after `RemoveSingleton` | The write reaches nothing | Take a new handle after re-adding |
| A list of players in a singleton | Duplicates what entities and queries give | Make them entities with a tag |
