The EasyEcs analyzer ships in the package next to the source generator, so code that breaks the
[ECS principles](/en/docs/ecs-principles) does not build. The correctness rules (EECS002 to EECS024, EECS035 and
EECS036) are errors except three warnings for code that works but costs (EECS017, EECS018, EECS020). The generator skips invalid input and the
analyzer reports it, so "not generated" always means "reported". The performance rules (EECS025 to EECS034, EECS039, EECS046, EECS052, EECS053) find code
that works and does more than it needs, and the severity says what kind
([D29](/en/docs/decisions#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)): a warning
means the code costs (EECS025 to EECS032, EECS046, EECS052, EECS053), a suggestion (Info) means the same cost written shorter (EECS033, EECS039), and an
error means code that cannot work (EECS034, a world update inside a system). The usage rules (EECS037, EECS038 and
EECS040 to EECS045, EECS047 to EECS051) find calls and declarations that compile but do not do what they say: an error where the runtime
throws or the code cannot work, a warning where a write is lost or a ref can point at the wrong row. The vector-loop
rules say why a method runs one row at a time (EECS055, a suggestion) and fail the build when a method that must
vectorize does not (EECS056); EECS057 keeps a [reduction](/en/docs/guide/threading#reductions) the only write of its
singleton; the thread rules (EECS060, EECS061) find writes that code on several threads races on or loses; EECS070 keeps the records of an `Emit<T>` in row order, and EECS071 finds random numbers a run cannot repeat. Where a rule has one mechanical answer, the IDE offers it as a code fix (EasyEcs.CodeFixes, in the
same package), and only when the result compiles.

## When to read it [#when-to-use-it]

<Callout type="idea" title="Read it for">
  A build error or warning whose id starts with `EECS`: jump to its section from the table below. Each section says
  what the rule protects, the code it rejects, the fix and whether the IDE can apply it.
</Callout>

<Callout type="warn" title="Do not">
  Suppress an `EECS` error with `#pragma`: the generator skipped the method or type the rule names, so the code it
  needs does not exist. The warnings can be suppressed, at the cost they describe; a suggestion (Info) shows in the
  IDE only, and `dotnet_diagnostic.EECS033.severity = warning` in `.editorconfig` raises one for a whole project. A
  usage error (EECS040 to EECS045, EECS048 to EECS051) names a call the runtime refuses: a `#pragma` only belongs around a test of that
  refusal.
</Callout>

One mistake gets one diagnostic: where two rules see the same code, the one whose fix removes the other's case reports
it. A copy changed and dropped is EECS038, not also EECS025 or EECS015; a method its filters never run is EECS016 or
EECS049, not also a cost of its parameters; a parallel instance method is EECS010, not also EECS029
([D60](/en/docs/decisions#d60-one-diagnostic-per-mistake)).

## EECS002 [#eecs002]

**Invalid `[ForEach]` parameter.** Error. Code fix: adds `in` or `ref` to a component or singleton taken by value.

Every parameter must be a `ref` / `in` / `ref readonly` struct implementing `IComponent` or `ISingletonComponent`, a
`Span<T>` / `ReadOnlySpan<T>` of an `IComponent` struct, a `Maybe<T>` or `ReadOnlyMaybe<T>` of one (an optional
component), a `Mut<T>`, a `ref Reduce<T>` ([reductions](/en/docs/guide/threading#reductions); without `ref` its
partial result would be a copy), a [`Scratch<T>`](/en/docs/guide/threading#scratch), a
[`Lookup<T>`](/en/docs/guide/threading#lookups) of a component, an `Entity`, or the `World`. A `[ForEach]` method [outside a system](/en/docs/guide/systems#foreach-outside-systems) may also take
values of any other type: its generated entry point takes them from the caller.

```csharp doccheck=expect-EECS002
public class MoveSystem : EcsSystem
{
    [ForEach] static void Move(ref Position p, float dt) { }   // a system's method gets no caller's value
}
```

Pass components and singletons by `ref` (write) or `in` / `ref readonly` (read), and turn other values into data:

```csharp
public record struct DeltaTime(float Seconds) : ISingletonComponent;   // the value becomes a singleton

public class MoveSystem : EcsSystem
{
    [ForEach]
    static void Move(ref Position p, in Velocity v, in DeltaTime dt)
    {
        p.X += v.X * dt.Seconds;
        p.Y += v.Y * dt.Seconds;
    }
}
```

## EECS003 [#eecs003]

**Invalid component count.** Error. No code fix.

A `[ForEach]` method takes between 1 and 9 components (singletons, `Entity`, `World` and a runner's other values do
not count; a `Maybe<T>` or `ReadOnlyMaybe<T>` does), or none when a `[With<T>]` (else a `[Changed<T>]`) names the component to query.
`[Removed<T>]` names none: the entities it selects no longer have `T`, so the method also needs a component parameter
or a `[With<U>]`.

```csharp doccheck=expect-EECS003
public class CorpseCleanupSystem : EcsSystem
{
    [ForEach] static void Remove(Entity e) => e.Destroy();   // which entities? no component names them
}
```

Name the component with a filter. With no component at all, use `OnUpdate`; with more than 9, move the extra
requirements to `[With<T>]` or split the method:

```csharp doccheck=expect-EECS030
public class CorpseCleanupSystem : EcsSystem
{
    [ForEach, With<Dead>]                          // the filter names what to query
    static void Remove(Entity e) => e.Destroy();
}
```

This method's whole body is one structural change, so [EECS030](#eecs030) then asks for the bulk call
`World.DestroyAll<Dead>()` in `OnUpdate`.

## EECS004 [#eecs004]

**Generic `[ForEach]` method in a system.** Error. No code fix.

A system runs its `[ForEach]` methods itself, once per update, so a generic method would get no type arguments.
Generic systems are fine (each closed type is a system of its own), and so are generic `[ForEach]` methods outside
systems, whose entry points take the type arguments from the caller.

```csharp doccheck=expect-EECS004
public class ClampSystem : EcsSystem
{
    [ForEach] static void Clamp<T>(ref T value) where T : struct, IComponent { }   // which T?
}
```

Make the system generic instead of the method:

```csharp
public interface IClamped { int Value { get; set; } }

public class ClampSystem<T> : EcsSystem where T : struct, IComponent, IClamped   // AddSystem<ClampSystem<Armor>>()
{
    [ForEach] static void Clamp(ref T value) => value.Value = Math.Max(value.Value, 0);
}
```

## EECS005 [#eecs005]

**Instance `[ForEach]` method outside a system.** Error. Code fix: makes the method static, when its body uses no
instance member.

A `[ForEach]` method of a type that is no `EcsSystem` gets a generated entry point that takes the world
(`Physics.Move(world)`), and there is no instance to call the method on.

```csharp doccheck=expect-EECS005
public class Physics
{
    [ForEach] void Move(ref Position p, in Velocity v) { p.X += v.X; p.Y += v.Y; }   // on which Physics?
}
```

Make it static, or move it into a system:

```csharp
public static class Physics                                   // Physics.Move(world) runs it once over the world
{
    [ForEach] public static void Move(ref Position p, in Velocity v) { p.X += v.X; p.Y += v.Y; }
}
```

## EECS006 [#eecs006]

**ECS data must be a struct.** Error. Code fix: changes the class to a struct, for a class declared once, with no base
class and no member a struct cannot have (`protected`, `virtual`, `abstract`, a finalizer).

Components and singletons are stored by value in columns. Interfaces may extend the markers; classes may not
implement them.

```csharp tab="Reported" doccheck=expect-EECS006
public class Wallet : IComponent { public int Gold; }
```

```csharp tab="Fixed"
public record struct Wallet(int Gold) : IComponent;
```

## EECS007 [#eecs007]

**Systems must be stateless.** Error. Code fix: `readonly` for a private field that only its initializer and the
constructors write.

A system has a mutable field, a settable auto-property or a field-like event (static ones included), or a member
writes a primary-constructor parameter (a hidden field). State in a system is invisible to other systems, queries and
saves, it is lost or duplicated when the system is removed or added again, and a static one is shared by every world.
`readonly` fields (dependencies, reusable scratch buffers), `init`-only properties and computed properties are
allowed.

```csharp doccheck=expect-EECS007
public class SpawnSystem : EcsSystem
{
    private int _spawned;                                  // state no one else can see or save
    protected override void OnUpdate() => _spawned++;
}
```

Move per-entity state into a component and per-world state into a [singleton](/en/docs/guide/singletons):

```csharp
public record struct Spawned(int Count) : ISingletonComponent;

public class SpawnSystem : EcsSystem
{
    protected override void OnUpdate() => World.GetOrAddSpawned().Count++;
}
```

## EECS008 [#eecs008]

**Systems must not reference systems.** Error. No code fix.

A field, auto-property, event or primary-constructor parameter of a system has a system type (an array of systems or
a type argument included), or a system looks another one up with `World.TryGetSystem<T>(out …)`. Systems that call each other
are coupled: neither can be removed, reordered or tested alone. `TryGetSystem` is for tools, tests and the code that
hosts the world.

```csharp doccheck=expect-EECS008
public class KillSystem : EcsSystem { }

public class ScoreSystem(KillSystem kills) : EcsSystem
{
    private readonly KillSystem _kills = kills;            // the two can no longer change apart
}
```

Write the data the other system reads (a component or a singleton) and order the two
([ECS principles, rule 3](/en/docs/ecs-principles#3-systems-never-reference-systems)):

```csharp
public record struct Score(int Deaths) : ISingletonComponent;

public class KillSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }
}

[UpdateAfter<KillSystem>]                                  // it reads the Dead that KillSystem wrote
public sealed class ScoreSystem : EcsSystem
{
    // One pass destroys the corpses and says how many there were: each is counted once.
    protected override void OnUpdate() => World.GetOrAddScore().Deaths += World.DestroyAll<Dead>();
}
```

## EECS009 [#eecs009]

**Batch `[ForEach]` mixes spans and per-entity parameters.** Error. No code fix.

A method that takes component spans receives whole runs of rows, so a per-entity parameter (a `ref` / `in` component,
a `Mut<T>`, a `Maybe<T>`, an `Entity`) has no single value for the call, and the `World` could change rows while the
spans point into them. An `EntitySpan` without component spans has no run to describe. A batch method stamps the runs
it writes as a whole: `Span<T>` is its write.

```csharp doccheck=expect-EECS009
public class DriftAllSystem : EcsSystem
{
    [ForEach] static void Drift(Span<Position> p, in Velocity v) { }   // v has no single value for a run of rows
}
```

Take every component as a span (`Span<T>` to write, `ReadOnlySpan<T>` to read), singletons besides, and an
`EntitySpan` for the run's entities; or write a per-entity method:

```csharp
public class DriftAllSystem : EcsSystem
{
    [ForEach]
    static void Drift(Span<Position> p, ReadOnlySpan<Velocity> v)   // element i of both spans is one entity
    {
        for (int i = 0; i < p.Length; i++)
        {
            p[i].X += v[i].X;
            p[i].Y += v[i].Y;
        }
    }
}
```

## EECS010 [#eecs010]

**`[ForEach(Parallel = true)]` cannot run on several threads.** Error. Code fix: removes `Parallel = true`; for an
instance method that uses nothing of its system, makes it `static` (the fix of [EECS029](#eecs029), which leaves a
parallel method to this rule).

A parallel method runs chunks of rows on several threads at once, so it must make no structural change (static, no
`World`, its `Entity` used only to read: `Id`, `Has`, `Get`, ...; not `entity.Run`, which does the owner's pass
bookkeeping and whose job may change structure), run per entity (not a batch method) and write no singleton (a `ref`
singleton would race between chunks). To read other entities, take a
[`Lookup<T>`](/en/docs/guide/threading#lookups) instead of the `World`; it is allowed in parallel.

```csharp doccheck=expect-EECS010
public class KillSystem : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Kill(Entity e, in Health hp) { if (hp.Value <= 0) e.SetDead(); }   // a structural change
}
```

Take singletons as `in`, move structural changes into a sequential system that reacts to data the parallel one
writes, or drop `Parallel = true`:

```csharp
public record struct Regen(int PerTick) : ISingletonComponent;

public class RegenSystem : EcsSystem
{
    [ForEach(Parallel = true), Without<Dead>]
    static void Regenerate(ref Health hp, in Regen regen) => hp.Value += regen.PerTick;   // reads the singleton only
}
```

## EECS011 [#eecs011]

**Write through a read-only parameter.** Error. Code fix: takes the parameter by `ref` (a `ReadOnlySpan<T>` becomes a
`Span<T>`); none for a singleton of a parallel method, since a `ref` singleton there is EECS010.

A `[ForEach]` method takes a component or singleton as `in` (or a component as `ReadOnlySpan<T>`) and changes data it
holds by reference: it calls a mutating method on a collection (`Add`, `Remove`, `Clear`, `Insert`, `Push`,
`Enqueue`, `Sort`, ...), assigns an element (`grid.Cells[i] = x`) or a member of a class it holds
(`holder.Owner.Gold++`). The compiler allows it because only the reference is read-only, but the write is scheduled as
a read (parallel systems that read the same data race with it) and never stamped, so `[Changed<T>]` systems and value
indexes miss it.

```csharp tab="Reported" doccheck=expect-EECS011
public record struct Grid(List<int> Cells) : ISingletonComponent;

public class GridSystem : EcsSystem
{
    [ForEach] static void Mark(in Position p, in Grid grid) => grid.Cells.Add((int)p.X);   // 'in', but written
}
```

```csharp tab="Fixed"
public record struct Grid(List<int> Cells) : ISingletonComponent;

public class GridSystem : EcsSystem
{
    [ForEach] static void Mark(in Position p, ref Grid grid) => grid.Cells.Add((int)p.X);   // ref: scheduled as a write
}
```

Calls that return a new value (`string`, immutable and frozen collections) are reads. The rule sees changes made
directly on the parameter's members; a reference copied into a local, or changed inside a method of your own class,
is not followed. Collections in components are allowed;
[ECS principles, rule 8](/en/docs/ecs-principles#8-choose-how-to-hold-a-collection) says when to prefer entities.

## EECS012 [#eecs012]

**`DynamicBuffer<T>` held by value.** Error. Code fix: adds `in`, or `ref` together with each caller's argument when
every caller passes a variable; none for an override or an interface's method, whose signature is shared.

A [`DynamicBuffer<T>`](/en/docs/guide/dynamic-buffers) refers to its list, so a copy of the value refers to the same
list: writes through the copy are never stamped as changed, and storing the copy gives a second entity (or a snapshot)
the same list. The rule reports a `DynamicBuffer<T>` field or property, a by-value parameter or return, a local that
is not a `ref` local, an assignment of an existing buffer, and an existing buffer passed to `Set`, `CreateEntity` or
another generic method that stores it.

```csharp
public record struct Loot(int Item);
```

```csharp doccheck=expect-EECS012
public static class Bags
{
    public static void Share(Entity player, Entity other)
    {
        var bag = player.Read<DynamicBuffer<Loot>>();                // a copy
        other.Set(player.Read<DynamicBuffer<Loot>>());               // two entities, one list
    }
}
```

Reach the buffer through its entity: `ref` / `in` parameters, `ref var bag = ref entity.Get<DynamicBuffer<T>>()`,
`entity.Read<DynamicBuffer<T>>()`. A new component value is `new DynamicBuffer<T>()` (or `default`), which holds no
list; a [prefab](/en/docs/guide/prefabs) gets its elements with `SetBuffer(…)` or the generated `SetLoot(…)`:

```csharp
public static class Bags
{
    public static int Items(Entity player) => player.Read<DynamicBuffer<Loot>>().Count;   // read through the entity

    public static void Give(Entity player, Loot loot)
    {
        ref var bag = ref player.Get<DynamicBuffer<Loot>>();                               // a ref local: a tracked write
        bag.Add(loot);
    }

    public static Entity Spawn(World world) => world.CreateEntity(new DynamicBuffer<Loot>());   // a new, empty buffer
}
```

## EECS013 [#eecs013]

**Structural change in a `[ForEach]` method that promises none.** Error. No code fix.

A `[ForEach]` method that is static and takes no `Entity` or `World` (or uses its `Entity` only to read) cannot change
structure as far as the generator can see, so it walks the rows without re-checking storage after each call, and the
system shares a [parallel stage](/en/docs/guide/threading#parallel-systems) with other systems. A structural change
made anyway, through a handle or a world kept elsewhere, breaks both: the pass keeps refs into rows that moved, and a
change inside a parallel stage throws.

The rule reports a call to a structural member of `Entity` (`Set`, `Remove`, `Destroy`, `GetOrAdd`, `Clone`,
`Disable`, `Enable`, `Link`, `Unlink`, `Run` (its job may change structure), and the generated `SetX`, `GetOrAddX`, `RemoveX`) or `World`
(`CreateEntity`, `CreateEntities`, `Instantiate`, `Reserve`, `DestroyEntities`, `DestroyAll`, `SetAll`, `RemoveAll`, `DisableAll`,
`EnableAll`, `Load`, `LoadKeeping`, `SaveWithout`, `SaveEntitiesWith`, `SaveEntitiesWithout`, `LoadEntities`, `LoadEntitiesInto`, `MoveEntities`, `GroupBy`, `RemoveTypes`, singletons, systems, `Update`,
`Capture`, `Restore`, ...) in such a method. A world the method creates itself (`new World()` in a local) is its own.

```csharp
public record struct Target(EntityId Id) : IComponent;
public struct Doomed : IComponent;                // a tag
public static class Arena { public static readonly World Main = new(); }
```

```csharp doccheck=expect-EECS013
public class SpawnEffects : EcsSystem
{
    [ForEach] static void Spawn(in Position p) => Arena.Main.CreateEntity(p);   // no Entity or World parameter
}
```

Take the `Entity` or the `World` as a parameter and make the change through it (the system then runs alone, with a
pass that notices the change), or record the change as data for a system that makes it:

```csharp
public class MarkTargets : EcsSystem
{
    [ForEach, With<Target>]
    static void Mark(Entity hunter, in Target target, World world)
    {
        hunter.RemoveTarget();                                       // through the parameter: this system runs alone
        if (world.TryGetEntity(target.Id, out var prey)) prey.SetDoomed();   // and its pass notices this one too
    }
}
```

The rule sees the method's own body: a change made in a helper method it calls is not followed. Inside a parallel
stage or a parallel `[ForEach]` the runtime still throws for it
([what the world synchronizes](/en/docs/guide/threading#what-the-world-synchronizes)).

## EECS014 [#eecs014]

**Structural change on another thread.** Error. No code fix.

A world's structure belongs to its owner thread. The rule reports a structural call (the members EECS013 lists) in a
lambda or anonymous method handed to `Task.Run`, `Task.ContinueWith`, `TaskFactory.StartNew`, `new Task`,
`Parallel.*`, `ThreadPool.QueueUserWorkItem` (and its relatives), `new Thread` or `new Timer`, or subscribed to
`System.Timers.Timer.Elapsed`, and in a method of the same type handed to one of them as a method group
(`Task.Run(Spawn)`), when the world or entity it changes can be changed by another thread at the same time:

- `Parallel.*` runs the delegate on several threads at once, so any world or entity captured from outside it races
  (`worlds[i]`, a world per item, does not);
- the hand-off sits in a loop, so the delegate runs several times over the same captured world or entity;
- the code around the hand-off (the method, or the type for a field) changes the same world's structure too.

```csharp doccheck=expect-EECS014
public static class Spawner
{
    public static void Start(World world, Entity[] players)
    {
        Task.Run(() => world.CreateEntity(new Position(0, 0)));      // the caller changes this world too
        world.CreateEntity(new Position(1, 1));

        Parallel.For(0, players.Length, i => players[i].Destroy());  // entities of one world, several threads at once
    }
}
```

A world handed to a thread that then owns it (a world per thread, a world created inside the delegate) is not
reported, and neither is a hand-off the caller waits for at once (`await`, `Wait()`, `Result`,
`GetAwaiter().GetResult()`): nothing runs beside it. Hand the change to the owner thread as data, through a queue its
system drains ([input from other threads](/en/docs/guide/threading#input-from-other-threads)), or give the other
thread its own world:

```csharp
public static class WorldThreads
{
    // A world per thread: each thread owns its world, nothing is shared.
    public static Thread[] Start(World[] worlds)
    {
        var threads = new Thread[worlds.Length];
        for (int i = 0; i < worlds.Length; i++)
        {
            var zone = worlds[i];                                       // one variable per iteration
            threads[i] = new Thread(() => { for (int t = 0; t < 1_000; t++) zone.Update(); });
            threads[i].Start();
        }

        return threads;
    }
}
```

Like EECS013, the rule sees the delegate's own body (a method group's method, one level down), and a receiver it
cannot follow (a method's result) is not reported.

## EECS015 [#eecs015]

**Indexed component written through a ref.** Error. Code fix, where the code only reads: `Read<T>()` for
`Get<T>()`, `ref readonly` for a `ref` local, `in` / `ReadOnlySpan<T>` for a `[ForEach]` parameter.

A [value index](/en/docs/guide/indexes-and-relations#value-indexes) follows `Set`, `CreateEntity` and
`CreateEntities`; a write through a `ref` changes the key behind its back. For a component implementing
`IIndexed<TKey>` (or `IGroup`, whose [group](/en/docs/guide/groups) is a key too), the rule reports:

- `Get<T>()`, `GetOrAdd<T>()` or `TryGetRef<T>()` on an entity;
- a `ref` local bound to it, or an assignment to it (or a field of it) through a query item;
- a `ref`, `Span<T>`, `Mut<T>` or `Maybe<T>` parameter of it in a `[ForEach]` method or an `IForEach*` job (a
  `Maybe<T>` hands out a `ref`; take a `ReadOnlyMaybe<T>` to read it).

```csharp
public record struct Zone(int Id) : IComponent, IIndexed<int> { public int Key => Id; }
public record struct Portal(int To) : IComponent;
```

```csharp doccheck=expect-EECS015
public class TakePortals : EcsSystem
{
    [ForEach] static void Take(ref Zone zone, in Portal portal) => zone = new Zone(portal.To);   // the index keeps the old zone
}
```

Read it with `in`, `ReadOnlySpan<T>`, [`ReadOnlyMaybe<T>`](/en/docs/guide/systems#read-only-maybe) (when some entities
lack it), `Read<T>()` or the generated property, and write it with `Set` (or the generated `SetX`):

```csharp
public class TakePortals : EcsSystem
{
    [ForEach]
    static void Take(Entity player, in Zone zone, in Portal portal)
    {
        if (zone.Id != portal.To) player.SetZone(portal.To);         // a Set: the index moves the player at once
    }
}
```

## EECS016 [#eecs016]

**`[Removed<T>]` method that requires `T`.** Error. No code fix.

`[Removed<T>]` visits entities that lost `T` and still lack it. Taking `T` as a parameter, or requiring it with
`[With<T>]` or `[Changed<T>]` on the same method, asks for entities that have `T`: no row passes both, so the method
would never run.

```csharp
public record struct Burning(int Ticks) : IComponent, ITracked;
public record struct Replica(int Health, bool Burning) : IComponent;
```

```csharp doccheck=expect-EECS016
public class ReplicateFire : EcsSystem
{
    [ForEach, Removed<Burning>]
    static void Out(in Burning burning, ref Replica replica) => replica.Burning = false;   // the entity lacks Burning
}
```

Read the entity's other components (the row keeps them), and handle "added again" or "written" in another method with
`[Changed<T>]`:

```csharp
public class ReplicateFire : EcsSystem
{
    [ForEach, Changed<Burning>]
    static void Lit(ref Replica replica) => replica.Burning = true;

    [ForEach, Removed<Burning>]                       // the other components of the row are still there
    static void Out(ref Replica replica) => replica.Burning = false;
}
```

## EECS017 [#eecs017]

**A component stores an `Entity` handle.** Warning. Code fix: an `Entity` field becomes an `EntityId` when every use
still compiles (`.Id`, a comparison, an assignment).

An `Entity` holds a reference to its world, so a component or singleton with an `Entity` field (or a field of a struct
that holds one, from this assembly or another), and a `DynamicBuffer<T>` whose elements hold one, are managed: the column
is scanned by the garbage collector, every store pays a write barrier, rows are not copied as blocks,
[saves](/en/docs/guide/saves) cannot write it and [migration](/en/docs/guide/migration-and-unload#entityid-rewriting)
does not rewrite it.

```csharp doccheck=expect-EECS017
public record struct Chase(Entity Prey) : IComponent;          // a managed column
```

Store the `EntityId` (8 bytes, unmanaged; a handle converts to it implicitly) and turn it back into a handle with
`world.TryGetEntity(id, out var entity)`, which also says whether the entity still lives:

```csharp
public record struct Chase(EntityId Prey) : IComponent;

public class ChaseSystem : EcsSystem
{
    [ForEach]
    static void Follow(ref Position p, in Chase chase, World world)
    {
        if (world.TryGetEntity(chase.Prey, out var prey)) p = prey.Position;   // gone: the id finds nothing
    }
}
```

## EECS018 [#eecs018]

**A system's schedule is not a constant.** Warning. Code fix: `=> 5` for an auto-property `{ get; } = 5`.

`UpdateInterval` and `UpdatePhase` are read every update, so a value that changes makes the system skip or repeat
runs. An auto-property with a constant initializer is reported too: it reads a field set when the system is built,
and `=> 5` says the constant.

```csharp doccheck=expect-EECS018
public class SaveSystem : EcsSystem
{
    public override int UpdateInterval => World.EntityCount > 1000 ? 4 : 1;
}
```

Return a constant. To stop and resume a system, set `Enabled`:

```csharp
public class SaveSystem : EcsSystem
{
    public override int UpdateInterval => 60;    // every 60th update
    public override int UpdatePhase => 30;       // half a cycle after the others with the same interval
}
```

## EECS019 [#eecs019]

**Systems ordered in a cycle.** Error. No code fix.

`[UpdateBefore<T>]` and `[UpdateAfter<T>]` say which of two systems runs first; a cycle cannot hold, and `AddSystem`
throws when the system that closes it is added. The analyzer reports the cycles it sees between the systems of the
compilation.

```csharp doccheck=expect-EECS019
[UpdateAfter<B>] public class A : EcsSystem { }
[UpdateAfter<A>] public class B : EcsSystem { }   // A after B after A
```

Remove one of the orderings:

```csharp
public class Movement : EcsSystem { }
[UpdateAfter<Movement>] public class Collision : EcsSystem { }
[UpdateAfter<Collision>] public class Damage : EcsSystem { }
```

## EECS020 [#eecs020]

**A system ordered against another group.** Warning. No code fix.

Orderings apply within one group: `World.Update()` and `World.Update<TGroup>()` run their groups separately, in the
order the caller calls them, so an ordering against a system of another group never applies.

```csharp doccheck=expect-EECS020
public struct Late : ISystemGroup;
[UpdateInGroup<Late>] public class Sweep : EcsSystem { }
[UpdateAfter<Sweep>] public class Movement : EcsSystem { }   // Movement runs in the default group
```

Order systems of one group, or move the system into the other's group:

```csharp
public struct Late : ISystemGroup;
[UpdateInGroup<Late>] public class Sweep : EcsSystem { }
[UpdateInGroup<Late>, UpdateAfter<Sweep>] public class Recycle : EcsSystem { }
```

## EECS021 [#eecs021]

**A `[ForEach]` entry point has the signature of another method.** Error. No code fix.

Outside a system, the generator writes an overload of each `[ForEach]` method that takes the `World` (and the change
tick, for `[Changed<T>]` / `[Removed<T>]`) followed by the method's other values. If the type already has a method
with that signature, or another `[ForEach]` overload's entry point has it, the two collide.

```csharp doccheck=expect-EECS021
public static class Healing
{
    [ForEach] static void Heal(ref Health hp) => hp.Value++;
    public static void Heal(World world) { }        // the entry point Heal(World) exists already
}
```

Rename one of them:

```csharp
public static class Healing
{
    [ForEach] static void Heal(ref Health hp) => hp.Value++;     // Healing.Heal(world)
    public static void HealAll(World world) => Healing.Heal(world);   // the generated entry point
}
```

## EECS022 [#eecs022]

**A type out of reach of the generated code.** Error. Code fix: makes the type internal, with every private or
protected type that contains it, in each part of a partial type that states an accessibility.

The generator writes the jobs of `[ForEach]` methods outside the user's type and calls the methods through
`UnsafeAccessor`, so private methods and private systems are fine. The types of the parameters (and return), and the
type of a `[ForEach]` method outside a system, must be internal or public, as must every type containing them; a
`file` type is out of reach of any other file.

```csharp tab="Reported" doccheck=expect-EECS022
public class HealSystem : EcsSystem
{
    private struct Regen : IComponent { public int Amount; }      // the generated job cannot name it
    [ForEach] static void Heal(ref Health hp, in Regen r) => hp.Value += r.Amount;
}
```

```csharp tab="Fixed"
public class HealSystem : EcsSystem
{
    internal struct Regen : IComponent { public int Amount; }
    [ForEach] static void Heal(ref Health hp, in Regen r) => hp.Value += r.Amount;
}
```

## EECS023 [#eecs023]

**A filter on a struct that is no system group.** Error. Code fix: removes the filter.

`[With<T>]`, `[Without<T>]` and `[WithAny<T>]` on an `ISystemGroup` struct join every `[ForEach]` method of the
group's systems. On any other struct, such as a component, they do nothing.

```csharp doccheck=expect-EECS023
[Without<Dead>] public struct Armor : IComponent { public int Value; }   // filters nothing
```

Put the filter on the methods, or on their group:

```csharp
public struct Armor : IComponent, IClamped { public int Value { get; set; } }
[Without<Dead>] public struct Alive : ISystemGroup;            // every [ForEach] of the group skips Dead entities
```

## EECS024 [#eecs024]

**`[ForEach]` on a local function.** Error. No code fix.

The generator writes a job for each `[ForEach]` method and calls it from outside its type; a local function has no
name outside its method.

```csharp doccheck=expect-EECS024
public static class Report
{
    public static int Alive(World world)
    {
        int alive = 0;
        [ForEach, With<Health>] static void Count(ref int alive) => alive++;   // nothing can call it
        return alive;
    }
}
```

Make it a method of a system, or a static method of a type (its entry point takes the world):

```csharp
public static class Report
{
    [ForEach, With<Health>] static void Count(ref int alive) => alive++;

    public static int Alive(World world)
    {
        int alive = 0;
        Report.Count(world, ref alive);             // the generated entry point
        return alive;
    }
}
```

## EECS025 [#eecs025]

**A write access that only reads.** Warning. Code fix: `in` for a component or singleton, `ReadOnlySpan<T>` for a
span, `Read<T>()` for `Get<T>()`, `.X` for `WriteX()`, `in T` for a `Mut<T>` the method never writes.

A `ref` parameter (a `Span<T>` in a batch method) puts its type in the system's write set: no
[parallel stage](/en/docs/guide/threading#parallel-systems) runs the system beside one that reads the type. On a
[tracked component](/en/docs/guide/change-tracking) it also stamps every row the method visits, so `[Changed<T>]`
systems visit rows nobody changed. `entity.Get<T>()` and the generated `entity.WriteX()` stamp the row the same way.
The rule looks at every use: an assignment, `++`, a `ref` or `out` argument, a method that is not `readonly`, a `ref`
local or a `this ref` extension (`DynamicBuffer<T>.Add`) is a write, and keeps the access. A `Mut<T>` parameter used
only through `.Value` reads, and is reported the same way.

```csharp
public record struct Armor(int Value) : IComponent, ITracked;
```

```csharp doccheck=expect-EECS025
public class ArmorBonus : EcsSystem
{
    [ForEach]
    static void Apply(ref Armor armor, ref Health health) => health = new Health(health.Value + armor.Value);   // armor is only read
}
```

Read it by `in`:

```csharp
public class ArmorBonus : EcsSystem
{
    [ForEach]
    static void Apply(in Armor armor, ref Health health) => health = new Health(health.Value + armor.Value);
}
```

## EECS026 [#eecs026]

**A `[ForEach]` parameter the method does not use.** Warning. Code fix: a component becomes a `[With<T>]` filter (or
goes, when a `[With<T>]` or `[Changed<T>]` already requires it); an `Entity`, `World`, `EntitySpan`, singleton,
`Maybe<T>` or `ReadOnlyMaybe<T>` goes.

Each parameter costs something on every row or every pass: a component's column is loaded and advanced, a singleton is
resolved and scheduled as an access, an `Entity` builds a handle for every row and, like the `World`, makes the system
[run alone](/en/docs/guide/threading#parallel-systems). A component the method only requires is a filter. An unused
`ref` of a tracked component is reported without a fix: it stamps every row it visits, and `[With<T>]` would not. An
unused `Mut<T>` stamps nothing until it is written, so it gets the `[With<T>]` fix like an `in` parameter.
A method with an empty body is left alone while it is being written.

```csharp
public record struct Survivors(int Count) : ISingletonComponent;
```

```csharp doccheck=expect-EECS026
public class CountSurvivors : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Count(in Health health, ref Survivors survivors) => survivors = new Survivors(survivors.Count + 1);
}
```

Require the component with a filter:

```csharp
public class CountSurvivors : EcsSystem
{
    [ForEach, With<Health>, Without<Dead>]
    static void Count(ref Survivors survivors) => survivors = new Survivors(survivors.Count + 1);
}
```

## EECS027 [#eecs027]

**A lookup per row that a parameter makes once.** Warning. Code fix: takes the looked-up component or singleton as
a parameter (`in T`, or `ref T` when a lookup writes it) and turns every lookup of the type into that parameter.

The rule covers `[ForEach]` methods and the `Execute` of a hand-written job; a job takes the component as another
type argument of its interface.

A `[ForEach]` method's parameters are resolved once per table or per pass: a component is a column the loop walks, a
singleton a `ref` taken before the loop. The same data looked up through the visited `Entity` (`entity.Velocity`,
`entity.Has<T>()`, `entity.TryGet<T>(...)`) or through the `World` (`World.Clock`) repeats the search on every row:
the entity's record, its table, the column. The rule reports only lookups that run on every row (not in a branch,
a loop or after an early `return`), of components the method does not add or remove itself. Indexed components count
too: an `in` parameter or a [`ReadOnlyMaybe<T>`](/en/docs/guide/systems#read-only-maybe) reads them without the
lookup and without the write EECS015 forbids.

```csharp doccheck=expect-EECS027
public class Drift : EcsSystem
{
    [ForEach]
    static void Move(Entity entity, ref Position position) =>
        position = new Position(position.X + entity.Velocity.X, position.Y + entity.Velocity.Y);
}
```

The fix is offered on the first lookup of each type, when every lookup of the type is a `Get`, a `Read` or a generated
property (which throw for an entity without it, so requiring the component changes no row the method runs on); not
for a `TryGet` or a presence test, a method with callers, a batch method or a method with 9 components already.

Take the component as a parameter (`in`, `ref`, or `Maybe<T>` when some entities lack it; a presence test is a
`Maybe<T>` or a `[With<T>]` / `[Without<T>]` split; for an indexed component `in` or `ReadOnlyMaybe<T>`), and a
singleton as a parameter too:

```csharp
public class Drift : EcsSystem
{
    [ForEach]
    static void Move(ref Position position, in Velocity velocity) =>
        position = new Position(position.X + velocity.X, position.Y + velocity.Y);
}
```

## EECS028 [#eecs028]

**An allocation in code that runs every update.** Warning. No code fix.

A `[ForEach]` method runs for every entity it visits and `OnUpdate` once per update, so what they allocate is garbage
of every tick, and the collections it causes pause the world. The rule names each allocating expression: an object or
array, a lambda that captures, a method group of an instance, LINQ, a string built at run time (`$"..."`, `+`,
`string.Format`, `ToString()`), boxing, and `foreach` over an interface. Left out: code inside a `throw`, calls the
compiler removes (`[Conditional]`, such as `Debug.Assert`), console output (the write costs more than its string),
and the `OnUpdate` of a system that overrides `UpdateInterval` (its author chose that cadence). The rule also covers
the `Execute` of a hand-written job, and the cold calls that allocate by design: `TrimExcess`, `Capture()`,
`Describe`, `DescribeTables` and `DescribeSchedule` belong to a timer, a command or a test, not to every update.

```csharp doccheck=expect-EECS028
public class Steer : EcsSystem
{
    [ForEach]
    static void Aim(in Position position, ref Velocity velocity)
    {
        var path = new List<Position> { position };   // a list for every entity, every update
        velocity = new Velocity(-path[0].X, -path[0].Y);
    }
}
```

Keep values in structs, spans and `stackalloc`; keep a reusable collection in a component or a singleton taken by
`ref`; pass numbers, not strings:

```csharp
public class Steer : EcsSystem
{
    [ForEach]
    static void Aim(in Position position, ref Velocity velocity)
    {
        Span<Position> path = stackalloc Position[1];
        path[0] = position;
        velocity = new Velocity(-path[0].X, -path[0].Y);
    }
}
```

## EECS029 [#eecs029]

**An instance `[ForEach]` method that uses no instance member.** Warning. Code fix: makes it `static`.

An instance method could reach the `World` through its system, so the generator treats it as one that may change
structure: its system runs alone in a parallel stage, and its rows are walked with the checks a structural change
needs. A static method that takes no `Entity` or `World` is proven not to change structure
([EECS013](#eecs013)).

```csharp doccheck=expect-EECS029
public class MoveSystem : EcsSystem
{
    [ForEach]
    void Move(ref Position position, in Velocity velocity) =>
        position = new Position(position.X + velocity.X, position.Y + velocity.Y);
}
```

Make it static:

```csharp
public class MoveSystem : EcsSystem
{

    static void Move(ref Position position, in Velocity velocity) =>
        position = new Position(position.X + velocity.X, position.Y + velocity.Y);
}
```

## EECS030 [#eecs030]

**A structural change entity by entity over a query.** Warning. Code fix: the bulk call.

A structural change through each entity of a query moves (or flips) one row per call, through the structural gate each
time. `SetAll`, `RemoveAll`, `DisableAll`, `EnableAll` and `DestroyAll` change every matching row of a table
together, whole words of rows at once ([bulk changes](/en/docs/guide/bulk)). The rule
reports a `foreach` over `world.Query<...>()` whose body is one such call on the item's entity with the same value for
every row. A `Set` of a component the query already requires writes a value instead of moving a row, and is left alone.

```csharp doccheck=expect-EECS030
foreach (var item in world.Query<Health>(QueryFilter.Create().With<Dead>()))
    item.Entity.Destroy();
```

One call:

```csharp
world.DestroyAll<Health>(QueryFilter.Create().With<Dead>());
```

A `[ForEach]` method whose whole body is such a call on its entity is the same loop, written by the generator. The rule
reports it when the call's arguments use no parameter and the method's filters are ones a `QueryFilter` holds (no
`[Changed<T>]` or `[Removed<T>]`, no slices). There is no code fix: the call moves into the system's `OnUpdate` and
the method goes.

```csharp doccheck=expect-EECS030
public class CorpseSystem : EcsSystem
{
    [ForEach, With<Dead>]
    static void Bury(Entity entity) => entity.Destroy();
}
```

One call per update:

```csharp
public class CorpseSystem : EcsSystem
{
    protected override void OnUpdate() => World.DestroyAll<Dead>();
}
```

## EECS031 [#eecs031]

**Entities created one by one in a counted loop.** Warning. Code fix: the bulk call, or a reservation before the loop.

Created one by one, a table and the entity storage grow by doubling, and in a world that has never held them the
discarded arrays can set off a full garbage collection ([D28](/en/docs/decisions#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap)).
`CreateEntities` and `Instantiate(prefab, span)` create them in one pass; `Reserve` reserves room when each
entity gets values of its own. The rule leaves out loops of a constant count under 4,096, or over an array created
with one (no array reaches the large object heap), loops after a reservation, loops that create only under a branch or
in an inner loop, and loops in a system (a running world reuses its rows). `Instantiate(prefab)` and
`Instantiate(prefab, in c1..cn)` with the same values in such a loop are reported too; the fix is the batch form,
`Instantiate(prefab, entities, in c1..cn)`.

```csharp doccheck=expect-EECS031
var wave = new Entity[50_000];
for (int i = 0; i < wave.Length; i++)
    wave[i] = world.CreateEntity(new Position(0, 0), new Health(100));
```

One call when the values are the same; a reservation when they are not:

```csharp
var spawned = new Entity[50_000];
world.CreateEntities(spawned, new Position(0, 0), new Health(100));

world.Reserve<Position, Health>(spawned.Length);
for (int i = 0; i < spawned.Length; i++)
    world.CreateEntity(new Position(i, 0), new Health(100));
```

## EECS032 [#eecs032]

**Query work the world does in one call.** Warning. Code fix: `Any`, or `Count` for a loop that only counts.

`Count` sums the row counts of the matching tables and `Any` stops at the first table with a row; neither visits a
row. A filter skips whole tables and words of rows that a test in the loop visits one by one. The rule reports
`Count<...>()` compared with 0 or 1 as a presence test, a `foreach` over a query that only counts, and a loop whose
first statement skips rows by a component test of the item's entity (no fix: the filter goes where the query is made).

```csharp tab="Reported" doccheck=expect-EECS032
bool anyDead = world.Count<Dead>() > 0;
```

```csharp tab="Fixed"
bool someoneDied = world.Any<Dead>();
foreach (var item in world.Query<Health>(QueryFilter.Create().With<Burning>())) { }   // the filter, not a test in the loop
```

## EECS033 [#eecs033]

**A generic call with a generated member of the same meaning.** Info. Code fix: the generated member.

The generator writes [named members](/en/docs/guide/entities-and-components#generated-members) for every component, singleton,
buffer element and query shape, each calling the generic API: the same call at the same cost, which is why this rule
is a suggestion and not a warning. The rule offers the member only where it is generated in
that compilation and does the same thing, including the kind of reference it returns: `Get<T>()` of a tracked
component becomes `WriteX()` (its `entity.X` is read-only), and a buffer's member is offered only while other code
still names `DynamicBuffer<T>` (the generator writes buffer members for the elements code names that way).

| Generic | Generated |
| --- | --- |
| `entity.Get<Health>()`, `entity.Read<Health>()` | `entity.Health` (or `WriteHealth()` for a tracked component) |
| `entity.Has<Health>()`, `entity.Has<Dead>()` | `entity.HasHealth`, `entity.IsDead` |
| `entity.TryGet<Health>(out h)`, `entity.GetOrAdd<Health>()` | `entity.TryGetHealth(out h)`, `entity.GetOrAddHealth()` |
| `entity.Set(new Health(100))`, `entity.Set(new Dead())` | `entity.SetHealth(100)`, `entity.SetDead()` |
| `entity.SetIfChanged(new Armor(5))` | `entity.SetArmorIfChanged(5)` (a component a world watches: tracked, indexed or grouped) |
| `entity.Remove<Health>()`, `Disable<T>()`, `Enable<T>()`, `IsDisabled<T>()` | `entity.RemoveHealth()`, `DisableHealth()`, `EnableHealth()`, `IsHealthDisabled` |
| `world.GetSingleton<Clock>()`, `HasSingleton`, `GetOrAddSingleton`, `RemoveSingleton` | `world.Clock`, `HasClock`, `GetOrAddClock()`, `RemoveClock()` |
| `world.Index<Zone, int>()`, `world.Relations<Friend>()` | `world.ZoneIndex`, `world.FriendIndex` |
| `item.Component1` | `item.Health` |

```csharp tab="Reported" doccheck=expect-EECS033
int hpGeneric = player.Get<Health>().Value;
```

```csharp tab="Fixed"
int hp = player.Health.Value;
```

## EECS034 [#eecs034]

**A system runs a world update.** Error. No code fix.

`World.Update()` and `World.Update<TGroup>()` run systems. Called from a system, `Update()` runs the system again
inside its own run until the stack overflows, and a group's update runs other systems in the middle of a stage, under
its change tick. A stable `[ForEach]` method that calls it is [EECS013](#eecs013).

```csharp doccheck=expect-EECS034
public class CatchUp : EcsSystem
{
    protected override void OnUpdate() => World.Update();
}
```

The code that hosts the world runs its updates and groups, in the order they belong:

```csharp
while (running) world.Update();
```

## EECS035 [#eecs035]

**Invalid `[ForEach(Slices = N)]`.** Error. No code fix.

A sliced method visits one slice of each matching table per run of its system, so every row once per N runs. `Slices`
is 1 or more. A `[Changed<T>]`, `[Removed<T>]`, `[ChangedAny<…>]` or `[RemovedAny<…>]` method selects the rows changed
since its system last ran, and every run moves that tick forward: the rows of the slices a run did not visit would
lose their changes for good.

```csharp doccheck=expect-EECS035
public class SendFire : EcsSystem
{
    [ForEach(Slices = 4), Changed<Burning>]
    static void Send(in Burning burning, ref Replica replica) => replica.Burning = burning.Ticks > 0;   // three slices in four lose their changes
}
```

Read the changes every run: a change filter already visits only the written rows. Slice the work that has no change
filter, the per-row work that is heavy for every entity:

```csharp
public class SendFire : EcsSystem
{
    [ForEach, Changed<Burning>]
    static void Send(in Burning burning, ref Replica replica) => replica.Burning = burning.Ticks > 0;
}
```

[Slices](/en/docs/guide/systems#slices) describes the cut and the cadence.

## EECS036 [#eecs036]

**A component that cannot be indexed by its key.** Error. No code fix.

A world indexes an `IIndexed<TKey>` or `IUniqueIndexed<TKey>` component by its key, and checks every write of a
unique one against that index. The rule reports two declarations that cannot work:

- **An `EntityId` key.** Loads and moves rewrite `EntityId` values after they copy the rows, too late to check them
  first, so a relation key cannot be unique.
- **A second key.** A component is indexed once: a second `IIndexed<TKey>` or `IUniqueIndexed<TKey>` on it, unique or
  not, could never be indexed, and `world.Index` throws for it.

```csharp doccheck=expect-EECS036
public record struct Mount(EntityId Rider) : IComponent, IUniqueIndexed<EntityId> { public EntityId Key => Rider; }
```

Index a relation with `IIndexed<EntityId>`, and give a second key a component of its own:

```csharp
public record struct Mount(EntityId Rider) : IComponent, IIndexed<EntityId> { public EntityId Key => Rider; }
```

[Unique keys](/en/docs/guide/indexes-and-relations#unique-keys) explains what a unique index checks.

## EECS037 [#eecs037]

**A job's `WriteMask` does not match what `Execute` writes.** Warning. Code fix: the `WriteMask` that `Execute` needs.

A hand-written job (`IForEach<...>`, `IForEachEntity<...>`, `IForEachBatch<...>`) says which components it writes with
`static int WriteMask` (bit `k - 1` for component `k`, `-1` for all of them, the default). The loop stamps the
[tracked](/en/docs/guide/change-tracking) components it names on every row it visits, and carries the others over
when `Execute` moves the entity. A tracked component that `Execute` writes and `WriteMask` leaves out is never stamped,
so `[Changed<T>]` systems miss the change; one that `Execute` only reads is stamped on every row anyway, so they visit
rows nobody changed. The rule compares a constant `WriteMask` (or the default) with the writes it sees in `Execute`, by
the same test as EECS025, and leaves a computed `WriteMask` and the bits of `SelfStamped` alone.

```csharp
public record struct Shield(int Value) : IComponent, ITracked;
```

```csharp doccheck=expect-EECS037
public struct Recharge : IForEach<Shield>
{
    public void Execute(ref Shield shield) => shield = new Shield(shield.Value + 1);
    public static int WriteMask => 0;   // Shield is written and never stamped
}
```

Name what `Execute` writes:

```csharp
public struct Recharge : IForEach<Shield>
{
    public void Execute(ref Shield shield) => shield = new Shield(shield.Value + 1);
    public static int WriteMask => 0b1;
}
```

A `[ForEach]` method needs none of this: the generator writes its job from the parameters.

## EECS038 [#eecs038]

**A changed copy of a component is dropped.** Warning. Code fix: `ref var` (`Get<T>()`, a generated property, a

`entity.Get<T>()`, the generated `entity.X`, a singleton `world.X` and a query item's component return a `ref`, and
`var` copies what it points at; `TryGet` hands out a copy too. A field written on that copy and never read again is
a change that reaches no table: the entity keeps its old value. The rule reports a local initialized from one of
these and written afterwards (an assignment, `++`, a compound assignment, a call of a method of the struct that is
not `readonly`), when no later code reads, returns, captures or passes it, in a method, a lambda or a local function.

```csharp
public struct Mana : IComponent { public int Value; }
```

```csharp doccheck=expect-EECS038
var mana = hero.Get<Mana>();   // a copy of the row
mana.Value -= 10;              // lost
```

Keep the `ref`:

```csharp
ref var mana = ref hero.Get<Mana>();
mana.Value -= 10;
```

## EECS039 [#eecs039]

**A `Mut<T>` of a component that is not tracked.** Suggestion (Info). Code fix: `ref T`.

[`Mut<T>`](/en/docs/guide/change-tracking#set-if-changed) stamps only the rows a `[ForEach]` method writes, which only means
something for a component with `ITracked`. For any other component it is the same write as a `ref` parameter,
written longer (`.Value`, `.Write()`). The rule reports a `Mut<T>` of an untracked `T` used only through `.Value`

```csharp doccheck=expect-EECS039
public class Clamp : EcsSystem
{
    [ForEach]
    static void Apply(Mut<Health> health)

        if (health.Value.Value > 100) health.Write() = new Health(100);

}
```

Take it by `ref`:

```csharp
public class Clamp : EcsSystem
{
    [ForEach]
    static void Apply(ref Health health)
    {
        if (health.Value > 100) health = new Health(100);
    }
}
```

A `Mut<T>` that the method never writes is reported by [EECS025](#eecs025), with `in T` as its fix.

## EECS040 [#eecs040]

**`SetIfChanged` on a type it cannot compare.** Error. No code fix.

`entity.SetIfChanged(value)` and `Mut<T>.SetIfChanged(value)` compare the new value with the stored one, without

```csharp
public struct Nickname : IComponent, ITracked { public string Text; }
```

```csharp doccheck=expect-EECS040
hero.SetIfChanged(new Nickname { Text = "Ada" });   // NotSupportedException: no way to compare
```

Make it a `record struct` (records implement `IEquatable<T>`), or implement `IEquatable<T>`:

```csharp
public record struct Callsign(string Text) : IComponent, ITracked;   // compared through IEquatable<Callsign>
```

```csharp
hero.SetIfChanged(new Callsign("Ada"));
```

## EECS041 [#eecs041]

**A call a pass refuses.** Error. No code fix.

While a query or `[ForEach]` pass walks a world's tables, the calls that rebuild or replace them throw
`InvalidOperationException`: `TrimExcess`, `Capture`, `Restore`, `Save`, `SaveWithout`, `Load`, `LoadKeeping`, `SaveEntities`, `SaveEntitiesWith`, `SaveEntitiesWithout`, `LoadEntities`, `LoadEntitiesInto`,
`MoveEntities` (of the world walked, as source or target), `GroupBy` and `RemoveTypes`. The rule reports one of them
on the world a `foreach` over its `Query` walks, and on the world of a `[ForEach]` method or a job's `Execute`.

```csharp doccheck=expect-EECS041
foreach (var item in world.Query<Health>())
{
    if (item.Health.Value <= 0) world.TrimExcess();   // throws: a pass is walking the tables
}
```

Decide in the pass and act after it:

```csharp
bool trim = false;
foreach (var item in world.Query<Health>())
    trim |= item.Health.Value <= 0;
if (trim) world.TrimExcess();
```

## EECS042 [#eecs042]

**An indexed component changed while its index is walked.** Error. No code fix.

`index.Find(key)`, the ordered walks of an index (`Ascending`, `Descending`, `Range`, ...), `world.Children(parent)`,
`world.Descendants(root)` and a relation index's `Find(target)` read the index's own lists as they go. Giving an
entity the indexed component or a new key (`Set`, `SetIfChanged`, `GetOrAdd`, `Enable`, `SetAll`, `EnableAll`, a
creation with the component, the generated `SetX`; `Link` for a relation) adds it to a key, and a key that
emptied hands its list to the keys that grow next: the walk skips entities or visits others. The rule reports such a
change inside a `foreach` over a walk of the same component's index. Removing the component, dropping links and
destroying entities leave holes the walk steps past, and a change followed by a `break`, `return` or `throw` ends the

```csharp
public record struct Team(int Id) : IComponent, IIndexed<int> { public int Key => Id; }
```

```csharp doccheck=expect-EECS042
foreach (var member in world.TeamIndex.Find(1))
    member.SetTeam(2);   // moves the entity out of the array being walked
```

Collect first, then change:

```csharp
var moving = new List<Entity>();
foreach (var member in world.TeamIndex.Find(1)) moving.Add(member);
foreach (var member in moving) member.SetTeam(2);
```

## EECS043 [#eecs043]

**A record struct key that prints itself.** Error. Code fix: implement `Key` explicitly.

A component that is its own key (`IIndexed<TSelf>` or `IUniqueIndexed<TSelf>` with `Key => this`) works, but on a
`record struct` a public `Key` is one of the properties `ToString()` prints. `Key` returns the record, which prints
its `Key`, which prints its `Key`: the first log line or debugger view overflows the stack.

```csharp doccheck=expect-EECS043
public readonly record struct Market(long Id) : IComponent, IIndexed<Market> { public Market Key => this; }
```

Implement `Key` explicitly, so it belongs to the interface only (the fix also rewrites `.Key` reads):

```csharp
public readonly record struct Market(long Id) : IComponent, IIndexed<Market> { Market IIndexed<Market>.Key => this; }
```

## EECS044 [#eecs044]

**A sliced filter where every row is needed.** Error. No code fix.

[`QueryFilter.Slice(index, of)`](/en/docs/guide/systems#slices) cuts each table into `of` parts, and only
passes (`ForEach`, `ForEachEntity`, `ForEachBatch` and their parallel forms) take one. `Query`, `Read`, `Count`, `Any`,
`DestroyAll`, `entity.Run` and the bulk calls need every matching row, so they throw `ArgumentException` for a
sliced filter. The rule follows the filter through locals and `static readonly` fields, and also reports a constant
`Slice` call that throws `ArgumentOutOfRangeException` (`of` below 1, `index` outside `0..of - 1`).
`Slice(0, 1)` is the whole table and is not sliced.

```csharp doccheck=expect-EECS044

int count = world.Count<Health>(half);   // ArgumentException
```

Count without the slice:

```csharp
int count = world.Count<Health>();
```

## EECS045 [#eecs045]

**A tag the world keeps, written by hand.** Error. No code fix.

`Retired` marks an entity kept for its [cleanup components](/en/docs/guide/cleanup-and-disable#cleanup-components), and `Disabled<T>` marks a
component [hidden from queries](/en/docs/guide/cleanup-and-disable#disable-a-component). The world adds and removes them in `Destroy`,
`Disable<T>()` and `Enable<T>()`, together with what they stand for: `Retired` with the destroy hooks and the
destroy log, `Disabled<T>` with the hidden value. Written directly (`Set`, `GetOrAdd`, `Remove`, `SetIfChanged`,
`Disable` and `Enable` of the tag itself, `CreateEntity`, `CreateEntities`, `Instantiate`, `SetAll`, `RemoveAll`,
`DisableAll`, `EnableAll`, `Prefab.Set`), the tag says something the world never did. Reading them (`Has`,
`IsDisabled`, `With` / `Without` filters, `[With<Retired>]`) is how they are meant to be used.

```csharp doccheck=expect-EECS045
hero.Remove<Disabled<Health>>();   // the tag goes, the value stays hidden
```

Call the world's own operation:

```csharp
hero.Enable<Health>();
```

## EECS046 [#eecs046]

**A query loop that only reads tracked components.** Warning. Code fix: `Read<T1..Tn>`.

A `Query` item hands out its components by `ref` and stamps every row it visits of a
[tracked component](/en/docs/guide/change-tracking), because it cannot tell a read from a write. A loop that only
reads (a total, a replication send, a search) then makes every `[Changed<T>]` system visit rows nobody changed.
`world.Read<T1..Tn>()` walks the same rows with `ref readonly` components and stamps nothing
([Read](/en/docs/guide/queries#read)). The rule reports a `foreach` over `world.Query<...>()` of at least one tracked
component whose body uses the item only through `Entity` and component reads; a write, a `ref` taken to a component
or the item passed on keeps the `Query`.

```csharp
public record struct Rating(int Value) : IComponent, ITracked;
```

```csharp doccheck=expect-EECS046
int total = 0;
foreach (var item in world.Query<Rating>())
    total += item.Rating.Value;   // every Rating row is stamped as written
```

Read it:

```csharp
int total = 0;
foreach (var item in world.Read<Rating>())
    total += item.Rating.Value;
```

## EECS047 [#eecs047]

**A ref used after a structural change.** Warning. No code fix.

`Get<T>()`, `Read<T>()`, the generated `entity.X` and a query item's components are refs into a table's row. A
structural change moves rows: a `Set` of a component the entity lacks, `Disable`, `Destroy`, a creation and an update
move entities between tables, swap the last row of a table into a hole and grow columns into new arrays. A ref taken
before it then reads or writes the old place, which may hold another entity's value. The rule follows one block in
order: a `ref` local bound to an entity's component (or a query item's), then a change that always runs, then a use
of the local; in a `foreach` over a query, a change of the item's entity followed by a read of `item.Component1` or
a generated `item.X`. `Remove<T>()` and `Enable<T>()` flip a bit of the row and move nothing; a `Set` of the
component the ref points at writes it in place.

```csharp doccheck=expect-EECS047
ref var health = ref hero.Get<Health>();
hero.Set(new Burning(3));   // hero moves to the table with Burning
health.Value -= 5;          // writes the row hero left
```

Change the structure first, then take the ref:

```csharp
hero.Set(new Burning(3));
ref var health = ref hero.Get<Health>();
health.Value -= 5;
```

## EECS048 [#eecs048]

**A component that cannot be disabled.** Error. No code fix.

[`Disable<T>()`](/en/docs/guide/cleanup-and-disable#disable-a-component) hides a component and keeps its value. A
[cleanup component](/en/docs/guide/cleanup-and-disable#cleanup-components) is what keeps a retired entity alive until
its resources are released, and `ChildOf` is what a parent's destruction follows to find its
[children](/en/docs/guide/hierarchy): hidden, either would be forgotten. `Disable<T>()` and `DisableAll<T>()` throw
`InvalidOperationException` for them, and the generator writes no `DisableX` for them. The rule reports both calls.

```csharp doccheck=expect-EECS048
unit.Disable<ChildOf>();   // InvalidOperationException
```

Remove it: the entity leaves its parent, and the parent's destruction no longer reaches it.

```csharp
unit.Remove<ChildOf>();
```

## EECS049 [#eecs049]

**Filters no entity passes.** Error. No code fix.

A `[ForEach]` method visits the entities that pass all of its filters and those of its
[group](/en/docs/guide/systems#system-groups): its component parameters, `[With<T>]`, `[Changed<T>]`, the group's
`[With<T>]` and `ISystemGroupWith<T>` require a component; `[Without<T>]` and `ISystemGroupWithout<T>` exclude it. A component
both required and excluded leaves no entity to visit, so the method never runs and nothing says so. The rule
reports the excluding filter.

```csharp doccheck=expect-EECS049
public struct Living : ISystemGroupWithout<Dead>;

[UpdateInGroup<Living>]
public class ReviveSystem : EcsSystem
{
    [ForEach, With<Dead>] static void Revive(ref Health health) => health.Value = 1;   // Living excludes Dead
}
```

Move the system out of the group that excludes what it needs:

```csharp
public class ReviveSystem : EcsSystem
{
    [ForEach, With<Dead>] static void Revive(ref Health health) => health.Value = 1;
}
```

## EECS050 [#eecs050]

**A second group in one filter.** Error. No code fix.

`QueryFilter.InGroup<T>(group)` (and the generated `InX(group)`) keeps the one
[group](/en/docs/guide/groups) a filter walks the tables of. Naming another one, of another component or another
constant value, throws `ArgumentException` when the filter is built. The rule reports the second call of a chain.

```csharp
public record struct Zone(int Id) : IComponent, IGroup { public int Group => Id; }
```

```csharp doccheck=expect-EECS050
var border = QueryFilter.Create().InGroup<Zone>(1).InGroup<Zone>(2);   // ArgumentException
```

Walk each group with its own filter:

```csharp
int count = world.Count<Health>(QueryFilter.Create().InGroup<Zone>(1))
          + world.Count<Health>(QueryFilter.Create().InGroup<Zone>(2));
```

## EECS051 [#eecs051]

**A world update during a pass.** Error. No code fix.

A pass (a `foreach` over `Query` or `Read`, a `[ForEach]` method, a job's `Execute`) counts itself on the world, and
the structural changes made during it leave holes it closes at its end. `world.Update()` assumes no pass is running: it
runs every system while the loop holds its place in the tables, and it closes the holes, moving rows the loop has not
reached into rows it has passed, so the loop misses them. The rule reports an update of the world
a `foreach` walks; inside a system, [EECS034](#eecs034) reports it.

```csharp doccheck=expect-EECS051
foreach (var item in world.Query<Health>())
{
    item.Health.Value -= 1;
    world.Update();   // runs every system while this loop walks the tables
}
```

Update after the loop:

```csharp
foreach (var item in world.Query<Health>())
    item.Health.Value -= 1;
world.Update();
```

## EECS052 [#eecs052]

**A component added right after the entity is created.** Warning. Code fix: create it with the component.

`CreateEntity` and `Instantiate` place the entity in the table of the components they are given. A `Set` of another
component on the next statement moves it again: a second row copy, and a table on the way that nothing else may
use. Given to the creation, the component lands in the final table with the others
([D59](/en/docs/decisions#d59-analyzer-rules)). The rule reports a creation stored in
a local and followed directly by `local.Set(value)` or a generated `local.SetX(...)` of a component it was not given,
when the value does not depend on the entity or on a call; the fix moves the value into the creation. A grouped
component, the world's own tags and a creation that already has nine components are left alone.

```csharp doccheck=expect-EECS052
var bullet = world.CreateEntity(new Position(0, 0));
bullet.Set(new Velocity(1, 0));   // a second move, to the table with Velocity
```

Create it with the component:

```csharp
var bullet = world.CreateEntity(new Position(0, 0), new Velocity(1, 0));
```

## EECS053 [#eecs053]

**A tracked component written by `ref` on only some rows.** Warning. Code fix: `Mut<T>`.

A `ref` parameter of a [tracked component](/en/docs/guide/change-tracking) (`ITracked`, every `DynamicBuffer<T>`)
stamps every row the method visits, written or not. A method that writes it on some rows only (an early `return`, a
write inside an `if`, a loop that may not run) stamps the rows it left alone too, so every `[Changed<T>]` system
visits them again: a replication sends them, a save writes them. A [`Mut<T>`](/en/docs/guide/change-tracking#set-if-changed)
parameter stamps only the rows it writes, through `Write()` or a `SetIfChanged` that changed the value
([D66](/en/docs/decisions#d66-a-ref-written-on-some-rows)).

The rule follows the method's control flow: it reports a `ref` parameter of a tracked component in a per-entity
`[ForEach]` method when a path from the start reaches the end or a `return` without writing it. Paths that throw do
not count, and a method that writes the parameter in a `finally` is left out. A parameter the method never writes is
[EECS025](#eecs025)'s. Batch methods are left out: their spans stamp whole runs of rows, and `Mut<T>` is a
per-entity parameter.

```csharp
public record struct Location(int X, int Y) : IComponent, ITracked;
```

```csharp tab="Reported" doccheck=expect-EECS053
public class RespawnSystem : EcsSystem
{
    [ForEach]
    static void Respawn(ref Health health, ref Location location)
    {
        if (health.Value > 0) return;   // the living pass through, and their Location is stamped all the same
        health = new Health(100);
        location = new Location(0, 0);
    }
}
```

```csharp tab="Fixed"
public class RespawnSystem : EcsSystem
{
    [ForEach]
    static void Respawn(ref Health health, Mut<Location> location)
    {
        if (health.Value > 0) return;
        health = new Health(100);
        location.Write() = new Location(0, 0);
    }
}
```

The fix makes the parameter a `Mut<T>`, each write of it `x.Write()` and each read `x.Value`, so the method keeps
what it does. It is not offered when the parameter has another modifier than `ref` (`scoped ref`), when code calls
the method, or when the body names the parameter in `nameof` or rebinds it (`x = ref other`). Where nearly every
row takes the writing path and nothing reads `[Changed<T>]` of the component, the `ref`'s one stamp per run is the
cheaper write: suppress the warning there.

## EECS054 [#eecs054]

**Invalid `[ForEach(ChunkRows = N)]`.** Error. Code fix: removes `ChunkRows`; the generator, which skipped the method,
writes it again.

`ChunkRows` is the rows a thread of a [parallel method](/en/docs/guide/threading#chunk-rows) takes at a time: 0 lets
the runtime choose from the row count, more sets it (rounded up to 64). A method without `Parallel = true` runs on one
thread and has no chunks, and a negative count means nothing.

```csharp tab="Reported" doccheck=expect-EECS054
public class PlanRoutes : EcsSystem
{
    const int Steps = 4_096;

    [ForEach(ChunkRows = 64)]   // one thread: no chunks to size
    static void Plan(in Position from, ref Velocity heading)
    {
        float x = from.X;
        for (int i = 0; i < Steps; i++) x = MathF.Sqrt(x * x + 1);   // heavy: microseconds per row
        heading = new Velocity(x, from.Y);
    }
}
```

```csharp tab="Fixed"
public class PlanRoutes : EcsSystem
{
    const int Steps = 4_096;

    [ForEach(Parallel = true, ChunkRows = 64)]
    static void Plan(in Position from, ref Velocity heading)
    {
        float x = from.X;
        for (int i = 0; i < Steps; i++) x = MathF.Sqrt(x * x + 1);   // heavy: microseconds per row
        heading = new Velocity(x, from.Y);
    }
}
```

Run it in parallel (as here, for a few hundred heavy rows), or drop `ChunkRows`. Light rows need neither: keep the
default chunks ([when to set it](/en/docs/guide/threading#chunk-rows)).

## EECS055 [#eecs055]

**A `[ForEach]` method that runs one row at a time.** Suggestion (Info). No code fix.

The generator turns a [`[ForEach]` method into a vector loop](/en/docs/guide/systems#vector-loops) when it qualifies.
A method that looks meant for one (static, on one thread, taking only components of number fields, singletons and
values) but misses a condition gets this message, which names the first reason: a component of 5 fields, two lane
types, a call the loop has no vector form of, a write to something that is not a lane. It is the counterpart of
Burst's inspector: the build says which method stayed scalar and why. The method still runs correctly, row by row.

```csharp tab="Reported" doccheck=expect-EECS055
public struct Body : IComponent { public float X, Y, Z, Mass; public int Squad; }   // 5 fields, float and int

public class Sink : EcsSystem
{
    [ForEach]   // "component Body has 5 fields (a vector loop splits up to 4)"
    static void Fall(ref Body body) => body.Y -= body.Mass * 0.01f;
}
```

```csharp tab="Fixed"
public struct Body : IComponent { public float X, Y, Z, Mass; }   // 4 floats: one vector per field
public struct Squad : IComponent { public int Value; }             // the int in a component of its own

public class Sink : EcsSystem
{
    [ForEach]
    static void Fall(ref Body body) => body.Y -= body.Mass * 0.01f;
}
```

Change what the message names, or set `[ForEach(Simd = SimdMode.Off)]` on a method that should stay scalar (a few
rows, or a body the loop cannot take) to silence it. As a suggestion it shows in the IDE only;
`dotnet_diagnostic.EECS055.severity = warning` in `.editorconfig` lists every scalar method in the build.

## EECS056 [#eecs056]

**A required vector loop that the method does not qualify for.** Error. No code fix.

`[ForEach(Simd = SimdMode.Require)]` says the method must get its vector loop: a hot path whose speed depends on it.
When the method does not qualify, the build fails with the reason EECS055 would give, so a later edit (a call the
loop has no vector form of, a field of another type) cannot slow it down without anyone noticing.

```csharp tab="Reported" doccheck=expect-EECS056
public struct Charge : IComponent { public float Value; }

public class Recharge : EcsSystem
{
    [ForEach(Simd = SimdMode.Require)]   // "Math.Clamp is not supported"
    static void Fill(ref Charge charge) => charge.Value = Math.Clamp(charge.Value + 0.1f, 0f, 1f);
}
```

```csharp tab="Fixed"
public struct Charge : IComponent { public float Value; }

public class Recharge : EcsSystem
{
    [ForEach(Simd = SimdMode.Require)]
    static void Fill(ref Charge charge) => charge.Value = MathF.Min(MathF.Max(charge.Value + 0.1f, 0f), 1f);
}
```

Change what the message names, or set `SimdMode.Auto` (the default) to accept the loop of one row at a time.

## EECS057 [#eecs057]

**A reduction whose result another write replaces.** Error. No code fix.

A [`Reduce<T>` parameter](/en/docs/guide/threading#reductions) gives each chunk of rows a partial result and replaces
singleton `T` with the combined result when the pass ends. A second `Reduce<T>` of the same method or system, or a
`ref T` parameter of the same method, writes `T` in the same pass: one result would silently replace the other.

```csharp tab="Reported" doccheck=expect-EECS057
public struct Census : ISingletonComponent, IReduction<Census>
{
    public long Health;
    public static Census Identity => default;
    public static Census Combine(Census left, Census right) => new() { Health = left.Health + right.Health };
}

public class CountUnits : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Alive(in Health health, ref Reduce<Census> census) => census.Value.Health += health.Value;

    [ForEach, With<Dead>]   // a second Reduce<Census>: the dead's total would replace the living's
    static void Fallen(in Health health, ref Reduce<Census> census) => census.Value.Health += health.Value;
}
```

```csharp tab="Fixed"
public struct Census : ISingletonComponent, IReduction<Census>
{
    public long Health;
    public static Census Identity => default;
    public static Census Combine(Census left, Census right) => new() { Health = left.Health + right.Health };
}

public struct Casualties : ISingletonComponent, IReduction<Casualties>
{
    public long Health;
    public static Casualties Identity => default;
    public static Casualties Combine(Casualties left, Casualties right) => new() { Health = left.Health + right.Health };
}

public class CountUnits : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Alive(in Health health, ref Reduce<Census> census) => census.Value.Health += health.Value;

    [ForEach, With<Dead>]
    static void Fallen(in Health health, ref Reduce<Casualties> fallen) => fallen.Value.Health += health.Value;
}
```

Reduce each result into a singleton of its own, and read the last result with `in T` in a later system.

## EECS058 [#eecs058]

**Scratch memory stored into the world.** Error. No code fix.

A [`Scratch<T>`](/en/docs/guide/threading#scratch) value belongs to the thread running the method, and the next row
that thread runs, of any pass, reuses it. A reference to what it holds (a list, an array, a span, a struct holding
one) stored into a component, a singleton, a `Maybe`, a `Mut` or a `Reduce` hands that memory to the entity: later
rows change it under the entity, on another thread in a parallel pass.

```csharp tab="Reported" doccheck=expect-EECS058
public struct Route : IComponent
{
    public int[] Steps;
}

public class ChartRoutes : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Chart(in Position position, ref Route route, Scratch<int[]> steps)
    {
        steps.Value ??= new int[16];
        for (int i = 0; i < steps.Value.Length; i++) steps.Value[i] = (int)position.X + i;
        route.Steps = steps.Value;   // the next row on this thread rewrites this entity's route
    }
}
```

```csharp tab="Fixed"
public record struct Route(int First, int Last) : IComponent;

public class ChartRoutes : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Chart(in Position position, ref Route route, Scratch<int[]> steps)
    {
        var buffer = steps.Value ??= new int[16];
        for (int i = 0; i < buffer.Length; i++) buffer[i] = (int)position.X + i;
        route = new Route(buffer[0], buffer[^1]);   // the row's result, copied into its own component
    }
}
```

Copy what the row produced into the component's own storage (values, or a
[dynamic buffer](/en/docs/guide/dynamic-buffers)), or keep the data in a component from the start.

## EECS059 [#eecs059]

**A lookup of a component the pass writes.** Error. No code fix.

A [`Lookup<T>`](/en/docs/guide/threading#lookups) reads `T` of any entity as it was before the pass, so nothing may
write `T` while the pass runs. A method that writes `T` itself (a `ref`, `Mut`, writable `Maybe` or span parameter)
would read some rows before their write and some after, and in parallel, rows another thread is writing.

```csharp tab="Reported" doccheck=expect-EECS059
public class Flock : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Follow(ref Position position, in Target target, Lookup<Position> positions)
    {
        var leader = positions[target.Id];   // another chunk may be moving the leader right now
        if (leader.HasValue)
            position = new Position((position.X + leader.Value.X) / 2, (position.Y + leader.Value.Y) / 2);
    }
}
```

```csharp tab="Fixed"
public record struct NextPosition(float X, float Y) : IComponent;

public class Flock : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Follow(in Position position, in Target target, ref NextPosition next, Lookup<Position> positions)
    {
        var leader = positions[target.Id];   // every leader where it was before the pass
        next = leader.HasValue
            ? new NextPosition((position.X + leader.Value.X) / 2, (position.Y + leader.Value.Y) / 2)
            : new NextPosition(position.X, position.Y);
    }
}

public class MoveFlock : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Move(ref Position position, in NextPosition next) => position = new Position(next.X, next.Y);
}
```

Read the entity's own `T` through its parameter, write the result into another component and copy it back in a
later system (double buffering, the GPU's ping-pong), or split the work into two systems.

## EECS060 [#eecs060]

**Code running on several threads writes shared memory.** Warning. No code fix.

A `[ForEach(Parallel = true)]` method, and the `Execute` of a job run by `ForEachParallel` or `ForEachEntityParallel`,
run on several threads at once, one chunk of rows each. A static field or auto-property, an object a context parameter
refers to, or the object a job's field holds (every chunk's copy of the job shares it) is the same memory for all of
them: an increment loses updates, a list's `Add` corrupts the list, and which plain write is kept depends on timing.
The rule leaves out a constant every thread writes, `[ThreadStatic]` fields, concurrent collections, `Interlocked` and
`Volatile` calls, writes inside a `lock`, elements of arrays and lists (rows may own different elements) and locals.

```csharp tab="Reported" doccheck=expect-EECS060
public static class HitStats
{
    public static int Hits;
}

public class TakeHits : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health)
    {
        health = new Health(health.Value - 1);
        HitStats.Hits++;   // every thread increments the same int: updates are lost
    }
}
```

```csharp tab="Fixed"
public struct Hits : ISingletonComponent, IReduction<Hits>
{
    public int Count;
    public static Hits Identity => default;
    public static Hits Combine(Hits left, Hits right) => new() { Count = left.Count + right.Count };
}

public class TakeHits : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health, ref Reduce<Hits> hits)
    {
        health = new Health(health.Value - 1);
        hits.Value.Count++;   // this chunk's partial count, combined when the pass ends
    }
}
```

A total goes into a [`Reduce<T>`](/en/docs/guide/threading#reductions) singleton; a result per entity goes into a
component of its row, which a system after the pass reads. An `Interlocked` call per row also silences the rule,
at the cost of a contended cache line on every row.

## EECS061 [#eecs061]

**A parallel job's field read after the pass.** Warning. Code fix: runs the job on one thread (`ForEach` /
`ForEachEntity`), when the call passes no `chunkRows`.

`ForEachParallel` and `ForEachEntityParallel` run a copy of the job per chunk and merge nothing back: the job passed by
`ref` keeps the values it had before the call. A field `Execute` writes (a sum, a count, a flag) and the caller reads
afterwards holds its old value. The rule reports the call when the first use of the job after it reads such a field.
Jobs that merge their chunks' copies back (the generated jobs of methods with a `Reduce<T>` parameter) are left out.

```csharp tab="Reported" doccheck=expect-EECS061
public struct TotalHealth : IForEach<Health>, INoStructuralChanges
{
    public long Sum;

    public static int WriteMask => 0;

    public void Execute(ref Health health) => Sum += health.Value;
}

public static class Reports
{
    public static long Total(World world)
    {
        var total = new TotalHealth();
        world.ForEachParallel<Health, TotalHealth>(ref total);
        return total.Sum;   // still 0: each chunk summed into its own copy
    }
}
```

```csharp tab="Fixed"
public struct TotalHealth : IForEach<Health>, INoStructuralChanges
{
    public long Sum;

    public static int WriteMask => 0;

    public void Execute(ref Health health) => Sum += health.Value;
}

public static class Reports
{
    public static long Total(World world)
    {
        var total = new TotalHealth();
        world.ForEach<Health, TotalHealth>(ref total);   // one thread: the job is written back
        return total.Sum;
    }
}
```

For a total over many rows on all cores, write a `[ForEach(Parallel = true)]` method with a
[`Reduce<T>`](/en/docs/guide/threading#reductions) parameter instead: each chunk keeps a partial result and the pass
combines them.

## EECS070 [#eecs070]

**Records read or reordered by the pass that emits them.** Error. No code fix.

An [`Emit<T>`](/en/docs/reference/emit) parameter gives each chunk of rows its own list and appends the lists to
singleton `Emitted<T>` in chunk order when the pass ends, so the records come out in row order on any number of
threads. The same method taking `Emitted<T>` would read the records while they are being added: none of this pass's
in parallel, some of them on one thread. A second `Emit<T>` of the same `T` would order its records one way on one
thread (interleaved row by row) and another in parallel (each chunk's lists one after the other).

```csharp tab="Reported" doccheck=expect-EECS070
public record struct Hit(EntityId Target, int Amount);
public record struct Aim(EntityId Target) : IComponent;

public class Strike : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(in Aim aim, Emit<Hit> hits, in Emitted<Hit> sent)
    {
        if (sent.Items.Count < 100) hits.Add(new Hit(aim.Target, 1));   // sees none of this pass's hits
    }
}
```

```csharp tab="Fixed"
public record struct Hit(EntityId Target, int Amount);
public record struct Aim(EntityId Target) : IComponent;

public class Strike : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(in Aim aim, Emit<Hit> hits) => hits.Add(new Hit(aim.Target, 1));
}

[UpdateAfter<Strike>]
public class ApplyHits : EcsSystem
{
    protected override void OnUpdate()
    {
        ref var hits = ref World.GetSingleton<Emitted<Hit>>().Items;
        foreach (ref readonly var hit in hits.AsReadOnlySpan())
            if (World.TryGetEntity(hit.Target, out var target)) target.Get<Health>().Value -= hit.Amount;
        hits.Clear();   // the passes append: the reader clears
    }
}
```

Read the records in a system after the pass, and emit each kind of record through one parameter.

## EECS071 [#eecs071]

**Random numbers a `[ForEach]` method cannot repeat.** Warning. Code fix: draws from
[`EntityRandom`](/en/docs/reference/entityrandom) (adds `Entity entity` and `in EntityRandom random` when the method
lacks them), for `NextSingle`, `NextDouble` and `Next` in a per-row method.

`Random.Shared` is seeded differently on every run, and in a parallel pass its numbers go to rows in the order the
threads happen to ask, so a replay, a test or another machine sees other results. A `new Random()` per row
allocates, is seeded from the clock unless given a seed, and a seed given gives every row the same numbers.
`EntityRandom` is a pure function of a seed, the entity, the tick and a stream: the same numbers on every run, on any
number of threads. The fix gives each draw of the method its own stream.

```csharp tab="Reported" doccheck=expect-EECS071
public class Wander : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Step(ref Velocity velocity) =>
        velocity = new Velocity(Random.Shared.NextSingle() * 2 - 1, velocity.Y);   // another run, other numbers
}
```

```csharp tab="Fixed"
public class Wander : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Step(ref Velocity velocity, Entity entity, in EntityRandom random) =>
        velocity = new Velocity(random.Range(entity.Id, 0, -1f, 1f), velocity.Y);
}
```

The world needs the singleton (`world.SetEntityRandom(seed, 0)`), and the system that advances the simulation's clock
advances its `Tick`, so each step draws new numbers.
