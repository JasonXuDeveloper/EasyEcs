大多数系统写成普通的 `[ForEach]` 方法就够快。这一页讲剩下的少数：每个 tick 遍历所有行、每行做真正的运算、或者更新一张网格的系统。
这里汇总这些写法，说明每种借自高性能计算的哪件工具（OpenMP、MPI、Burst、GPU），并链接到完整讲解它的小节，每种写法只讲一次。

## 什么时候用 [#when-to-use-it]

<Callout type="idea" title="适合">
在 [`MeasureSystems`](/zh/docs/guide/systems#measuring-systems) 里占了 tick 大头的系统：对每一行做运算、几百行重活、
按邻居更新的一张格子网格（水、光照、热量、寻路场）。
</Callout>

<Callout type="warn" title="不适合">
没人测过是热点的系统，以及每行的活是查找和分支（遍历索引、读另一个实体的位置）：向量和更细的块帮不上忙。普通的 `[ForEach]`
方法是好读的默认写法。
</Callout>

## 怎么用 [#how-to-use-it]

按顺序一步步来，每步之后都测一次；哪一步够了就停。

<Step>

### 让生成器向量化：向量循环 [#vector-loops]

静态的逐实体 `[ForEach]` 方法（单线程或 `Parallel`），组件都是 1 到 4 个同一宽度的 lane 时，生成器会为它写一个向量循环（CPU 支持时用
`Vector512`，否则用 `Vector<T>`），把其中的 `if` 变成掩码，再加一段标量收尾：这就是 Burst 为 Unity job 做的事，只是在编译期完成。
你写的代码仍是标量的，除 `FloatMode.Fast` 外结果与标量代码逐位相同。哪些方法符合条件、生成的代码对照、怎样改写一个保持标量的方法：
[向量循环](/zh/docs/guide/systems#vector-loops)。
Native AOT 下发布时加上 `<IlcInstructionSet>native</IlcInstructionSet>`（或 `x86-64-v4` 这样的级别）：默认的基线没有 `Vector512`（[FAQ](/zh/docs/faq#native-aot)）。

- **多个字段：** `Position { X, Y, Z }` 由解交错加载和交错存储拆成每个字段一个向量（AVX2、AVX-512）；没有这些指令时逐行运行。
- **方法体：** lane 类型之间的转换、`Math.Clamp`、`Round`、`CopySign`、`Lerp` 以及其他有精确向量形式的 `Math` / `MathF`
  函数；`Sin`、`Cos`、`Exp`、`Log`、`Log2` 和 `Hypot` 只在 `FloatMode.Fast` 下，它的近似会改变结果。循环表达不了、位于条件之下的
  调用是冷分支：只有某个 lane 走进它的向量才运行原方法。
- **数据：** `byte` 和 `short` lane（每个 `Vector512` 64 行和 32 行）、`Vector2` / `Vector3` / `Vector4` 字段、作为拥有 `T` 的行的
  lane 掩码的 `Maybe<T>`，以及在 AVX-512 上最多 16 个字、方法只用其中若干 4 字节字段的组件（置换代价超过运算时，EECS055 会说出该拆出
  哪些字段）。
- **合计：** `Combine` 对每个字段求和、取 `Min` 或 `Max` 的 [`Reduce<T>`](/zh/docs/guide/threading#reductions) 每个 lane 一个累加器，
  按 lane 顺序合并；浮点求和只在 `FloatMode.Fast` 下。
- **不进循环的：** `Scratch<T>`、`Lookup<T>`、`Emit<T>` 和 `Tile` 参数让方法逐行运行，这对它们正合适：每行一次查找或追加没有向量写法。
- **系统得到了什么：** `world.DescribeSchedule()` 每个方法打印一行（`SystemInfo.Loops`）：循环、它的形状，或者保持标量的原因。
- **为什么没有：** [EECS055](/zh/docs/guide/analyzer#eecs055) 像 Burst 的 Inspector 一样说出方法保持标量的第一个原因；热路径上的
  `[ForEach(SimdMode = SimdMode.Require)]` 把它变成构建错误（[EECS056](/zh/docs/guide/analyzer#eecs056)），`SimdMode.Off` 不再提示。

</Step>

<Step>

### 把行分给多个线程：并行方法 [#parallel]

`[ForEach(Parallel = true)]` 把行切成块交给线程池，就像 OpenMP 的 `#pragma omp parallel for`：
[并行方法](/zh/docs/guide/systems#parallel-methods)。线程从一个共享计数器领块，就像 `schedule(dynamic, n)`；默认的 `n`
适合大量轻量行。几百行重活（每行几微秒）设 `ChunkRows = 64`，每个线程才都有活干：[块大小](/zh/docs/guide/threading#chunk-rows)。
读写互不冲突的系统本来就会同时运行，不需要这些：[并行系统](/zh/docs/guide/threading#parallel-systems)。

对所有行求总数（计数、总和、包围盒）用 `Reduce<T>` 参数：每块累加进自己的部分结果，每行没有锁也没有原子操作，部分结果按行的顺序合并进
单例，整数精确，`ChunkRows` 固定时浮点可复现：[归约](/zh/docs/guide/threading#reductions)。并行方法写静态计数器报
[EECS060](/zh/docs/guide/analyzer#eecs060)，`ForEachParallel` 之后读 job 字段报 [EECS061](/zh/docs/guide/analyzer#eecs061)。

每行的工作列表（搜索的候选、边界）用 `Scratch<T>`：每个方法、每个线程一个，就像 OpenMP 的 `threadprivate`，每个线程只分配一次，由行自己清空；
上限固定的小缓冲用 `stackalloc` 的 span：[临时空间](/zh/docs/guide/threading#scratch)。读另一个实体的组件用 `Lookup<T>`，就是 MPI 的单边 `Get`：
每次读取看到的都是这一遍之前的值，所以方法能保持并行：[查找](/zh/docs/guide/threading#lookups)。一遍里产生、交给后面系统的记录（命中、数据包）
用 `Emit<T>`：每块各自追加，按行的顺序合并：[发出记录](/zh/docs/guide/threading#emit)。随机数来自 `EntityRandom`，它是实体、tick 和流的纯函数，
所以并行的一遍在任何线程数下都抽到同样的数：[随机数](/zh/docs/guide/threading#entity-random)。这些每行都不加原子操作：
[运行器怎样同步](/zh/docs/guide/threading#runner-contract)。不是行的数据（`Emitted<T>` 的记录、一段下标）通过
[`world.ForParallel`](/zh/docs/guide/threading#for-parallel) 跑在同一个运行器上。

</Step>

<Step>

### 自己写向量：批处理方法 [#batch]

生成器让方法保持标量时（多个字段、查找表、整数技巧），[批处理方法](/zh/docs/guide/systems#batch-methods)拿到一段连续的行的
span，方法自己用 `Vector<T>` 或 `Vector128<T>` 循环：相当于 Burst job 里手写的 Unity.Mathematics `float4`。VoxelServer
示例里的火焰伤害就是这样的循环：[数据是一列时用 SIMD](/zh/docs/samples/voxel-server#simd)。

</Step>

<Step>

### 给网格着色：瓦片、着色器、模板掩码、乒乓缓冲、光环 [#grid]

下一个值由邻居决定的网格（水、光照、热量）可以像 GPU 绘制那样运行。网格切成瓦片，每块一个实体：一个组件是瓦片的形状和键
（`ITile<TKey>`），一个 `DynamicBuffer<T>` 装它的格子。接收 `Tile<TCell, TTile>` 参数的 `[ForEach]` 方法就是着色器；生成器找邻居、
声明读取，并让方法保持并行。`tile.Pad()` 把瓦片连同一圈邻居的边拷进线程的一张纹理（MPI 的光环交换），`padded.Rows(reads)`
只访问模板可能改变的行（每行一位，用 `TrailingZeroCount` 找到），`At(row).Load128` 用向量采样周围的格子，这一遍之后的提交系统就是乒乓缓冲。
怎样声明瓦片、写着色器、提交、让安静的瓦片休眠，以及完整例子：[网格瓦片](/zh/docs/guide/grids)。

#### 光环、邻居范围和边界 [#grid-halo]

形状的 `Halo`（模板读多远）、`Neighborhood`（面、棱、角：五点、九点和 27 点模板）和 `Boundary`（没有邻居处填充、钳制还是镜像）决定这一圈里放什么：
[更宽的光环、棱和角](/zh/docs/guide/grids#halo)。`ChangedEdges` 和 `Facing` 让安静的瓦片休眠：[让安静的瓦片休眠](/zh/docs/guide/grids#sleep)。

</Step>

</Steps>

## 对照：OpenMP、MPI、Burst、GPU [#mapping]

| 你熟悉的 | 在 EasyEcs 里 | 在哪 |
| --- | --- | --- |
| OpenMP `parallel for` | `[ForEach(Parallel = true)]` | [并行方法](/zh/docs/guide/systems#parallel-methods) |
| OpenMP `schedule(dynamic, n)` | `ChunkRows = n`（不设时用默认大小） | [`ChunkRows`](/zh/docs/guide/threading#chunk-rows) |
| OpenMP `reduction(+: x)`、MPI `Allreduce` | 归约进单例 `T : IReduction<T>` 的 `Reduce<T>` 参数 | [归约](/zh/docs/guide/threading#reductions) |
| OpenMP 的 `private` / `threadprivate` 临时空间 | `Scratch<T>` 参数（从 `default` 开始，不是一份拷贝：没有 `firstprivate`） | [临时空间](/zh/docs/guide/threading#scratch) |
| OpenMP `sections` / task | 同一阶段的系统，读写互不冲突时同时运行 | [并行系统](/zh/docs/guide/threading#parallel-systems) |
| 拥有一块子区域的 MPI rank | 每线程一个 World（每个区域或地图一个 World） | [每线程一个 World](/zh/docs/guide/threading#recommended-one-world-per-thread) |
| MPI 把实体发给另一个 rank | `SaveEntities` / `MoveEntities` | [迁移](/zh/docs/guide/migration-and-unload#save-entities) |
| MPI 单边的 `MPI_Get`、Unity 的 `ComponentLookup`（`[ReadOnly]`） | `Lookup<T>` 参数：任意实体在这一遍之前的 `T` | [查找](/zh/docs/guide/threading#lookups) |
| Unity 的 `NativeStream`、GPU 的流压缩 | `Emit<T>` 参数：每块一份记录，按行的顺序合并进 `Emitted<T>` | [发出记录](/zh/docs/guide/threading#emit) |
| cuRAND 的 Philox，基于计数器的生成器 | `EntityRandom`：（种子、实体、tick、流）的纯函数 | [随机数](/zh/docs/guide/threading#entity-random) |
| Kokkos 的 `RangePolicy`、Unity 的 `IJobParallelForBatch` | `world.ForParallel(count, ref job)` 配 `IForRange` / `IForSpan<T>` job | [ForParallel](/zh/docs/guide/threading#for-parallel) |
| MPI 光环交换（幽灵格子） | `Tile<TCell, TTile>.Pad`：瓦片四周填上邻居朝向它的边 | [网格瓦片](/zh/docs/guide/grids) |
| Burst 自动向量化 | `[ForEach]` 方法的向量循环 | [向量循环](/zh/docs/guide/systems#vector-loops) |
| Burst 里手写 `float4` / Unity.Mathematics | 用 `Vector<T>` / `Vector128<T>` 的批处理方法 | [批处理方法](/zh/docs/guide/systems#batch-methods) |
| Burst `IJobParallelFor` 的 batch count | `ChunkRows` | [`ChunkRows`](/zh/docs/guide/threading#chunk-rows) |
| Burst Inspector | EECS055，以及 `SimdMode = SimdMode.Require`（EECS056） | [分析器](/zh/docs/guide/analyzer#eecs055) |
| GPU 片元着色器、纹理采样 | 接收 `Tile<TCell, TTile>` 的 `[ForEach]` 方法，用 `Load128` 读周围的格子 | [网格瓦片](/zh/docs/guide/grids) |
| GPU 模板缓冲 | `padded.Rows(reads)`：每行一位，用 `TrailingZeroCount` 访问 | [网格瓦片](/zh/docs/guide/grids) |
| GPU 乒乓渲染目标 | 两个缓冲，读一个写一个，再提交 | [网格瓦片](/zh/docs/guide/grids#commit) |
| Burst 的 `FloatMode.Fast` | `[ForEach(FloatMode = FloatMode.Fast)]`：向量近似，浮点合计按 lane 的顺序相加 | [向量循环](/zh/docs/guide/systems#float-mode) |

## 怎么用得快 [#how-to-use-it-fast]

- 先测：[`MeasureSystems`](/zh/docs/guide/systems#measuring-systems) 指出占了 tick 的系统，BenchmarkDotNet 用例证明改动有效；
  每种写法的小节都链接了它自己的基准表。
- 先让数据合适，再写代码：向量循环要每个组件的 lane 大小相同、最多 4 个字段，网格要每个格子一个字节或一个 `int`（每个 `Vector128` 16 或 4 个格子），
  这样活就是一列上的同一种形状。
- 每个格子的中间结果放在寄存器、栈上（`[SkipLocalsInit]` 下的 `stackalloc`）或瓦片的纹理里，最后拷进缓冲一次：一遍里反复读写一个缓冲，
  比栈上的 span 慢得多。

## 常见陷阱 [#pitfalls]

| 错误 | 后果 | 谁能发现 |
| --- | --- | --- |
| 优化没人测过的系统 | 代码更难读，什么也没省下 | [`MeasureSystems`](/zh/docs/guide/systems#measuring-systems) |
| 想向量化的方法里混用不同大小的 lane（`float` 和 `double`、`int` 和 `byte`） | 保持标量 | [EECS055](/zh/docs/guide/analyzer#eecs055)；`SimdMode = SimdMode.Require` 让它报错 |
| 并行方法写共享计数器 | 更新丢失 | [EECS060](/zh/docs/guide/analyzer#eecs060)：改用 [`Reduce<T>`](/zh/docs/guide/threading#reductions) |
| 大量轻量行也设 `ChunkRows` | 同样的活要领更多次块 | 基准（[`ChunkRows`](/zh/docs/guide/threading#chunk-rows)） |
| 在并行方法里手动读另一块瓦片的格子 | 每行一次查找，每个格子都有边界情况 | 代码审查：`Tile<TCell, TTile>` 参数一次填好瓦片（[网格瓦片](/zh/docs/guide/grids#pitfalls)） |
