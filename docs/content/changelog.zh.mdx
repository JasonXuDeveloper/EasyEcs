## 4.8.0 [#v4-8-0]

### 新功能 [#v4-8-0-new]

- 枚举元素的 `DynamicBuffer`（`DynamicBuffer<Block>`）现在和结构体元素一样有生成的具名成员：`chunk.Block`、`HasBlock`、
  `WriteBlock()`、`GetOrAddBlock()`、`RemoveBlock()`，以及预制体的 `SetBlock(…)`。见[动态缓冲](/zh/docs/guide/dynamic-buffers)。
- `DynamicBuffer<T>.PoolCapacity` 按元素类型设置：缓冲被销毁或移除时，最长多少个元素的列表还给回收池（默认是 4 KB 能放下的个数）。
  大缓冲反复出现又消失时调高它，比如玩家周围加载又卸载的区块，新缓冲就会重用旧列表，不再分配。见[动态缓冲](/zh/docs/guide/dynamic-buffers#pool)。
- 分析器规则 [EECS053](/zh/docs/guide/analyzer#eecs053)（警告，有代码修复）：`[ForEach]` 方法以 `ref` 传入追踪变化的组件（`ITracked`、
  `DynamicBuffer<T>`），却有路径不写它（提前 `return`、写在 `if` 里），访问到的每一行都会被打 tick，`[Changed<T>]` 系统就会看到它根本没改过的行。
  修复改成 `Mut<T>`（写入改成 `x.Write()`，读取改成 `x.Value`），只给写过的行打 tick。
- `buffer.SetCount(n)` 设置 `DynamicBuffer<T>` 的元素个数，新增的元素为 `default`，并返回要写的 span，于是整个缓冲可以原地写好，不用先在栈上填好再用
  `AddRange` 复制进去。见[动态缓冲](/zh/docs/guide/dynamic-buffers#set-count)。
- `ReadOnlyMaybe<T>`：`[ForEach]` 方法的可选组件参数，方法只读它：`Value` 是 `ref readonly`，被追踪的组件永远不打 tick，带索引的组件也能用
  （EECS015 接受它，带索引组件的 `Maybe<T>` 仍然报错）。`Maybe<T>` 可以转换成它。见[系统](/zh/docs/guide/systems#read-only-maybe)。
- `world.SaveEntitiesWithout(output, ids, set)` 保存一组实体，写 `ComponentSet` 以外的所有组件：加载后会重新算出的数据不进存档。见
  [迁移与卸载](/zh/docs/guide/migration-and-unload#save-entities-without)。
- `DynamicBuffer<T>.ReservePool(lists)` 在启动时往 `T` 的回收池里放入这么多个容量为 `PoolCapacity` 的空列表，世界增长到的那些实体（玩家周围的区块）
  的缓冲在服务器运行时从池里取列表，不再分配。见[动态缓冲](/zh/docs/guide/dynamic-buffers#pool)。

- 按一行写的 `[ForEach]` 方法，只要它的组件都只有 1 到 4 个同一类型的数值（`float`、`double`、`int`、`uint`、`long`、`ulong`），就以 SIMD
  循环运行：生成器根据方法体写出 `Vector<T>` 循环，和 Burst 编译 job 一样，`if`、`?:` 和 `return` 变成掩码。多字段的组件（`Position { X, Y, Z }`）
  由解交错加载和交错存储拆成每个字段一个向量（256 位用 AVX2，512 位用 permute；没有这些指令时逐行运行）。结果逐位相同；不符合条件的方法
  照旧逐行运行，代码不用改。见[向量循环](/zh/docs/guide/systems#vector-loops)和[决策](/zh/docs/decisions#d68-vector-loops-without-opting-in)。
- 分析器规则 [EECS055](/zh/docs/guide/analyzer#eecs055)（建议）说明数值组件的 `[ForEach]` 方法为什么没有得到向量循环（“component Body has 5
  fields”、“lane types float and int differ”），就像 Burst 的 Inspector。`[ForEach(Simd = SimdMode.Require)]` 让这种情况成为错误
  （[EECS056](/zh/docs/guide/analyzer#eecs056)），热点循环不会悄悄失去向量；`SimdMode.Off` 让方法保持标量且不再提示。见
  [向量循环](/zh/docs/guide/systems#vector-loops)。
- `Reduce<T>`：对所有行求总数的 `[ForEach]` 参数，按 `ref` 传入（OpenMP 的 `reduction`），例如
  `static void Count(in Health h, ref Reduce<Census> census) => census.Value.Alive++;`。`T` 是实现了 `IReduction<T>`（`Identity`、`Combine`）的单例。
  并行遍历的每一块，或单线程时的整遍，累加进自己的部分结果，每行没有锁也没有原子操作；部分结果按块的顺序合并后替换 `T`。整数结果精确；
  `ChunkRows` 固定时，浮点结果在任何线程数下都相同。分析器规则 [EECS057](/zh/docs/guide/analyzer#eecs057) 拒绝同一遍里对 `T` 的第二处写入。
  见[归约](/zh/docs/guide/threading#reductions)和[决策](/zh/docs/decisions#d69-reductions)。
- `Scratch<T>`：`[ForEach]` 参数，方法在当前线程上的工作内存（OpenMP 的 `threadprivate`），每个方法、每个线程一个 `T`，从不重置，所以每行要填的
  列表每个线程只分配一次（`scratch.Value ??= new()`）。分析器规则 [EECS058](/zh/docs/guide/analyzer#eecs058) 拒绝把它持有的东西存进组件或单例。
  见[临时空间](/zh/docs/guide/threading#scratch)和[决策](/zh/docs/decisions#d74-scratch)。
- `Lookup<T>`：`[ForEach]` 参数，读取任意实体在这一遍之前的组件 `T`（`lookup[id]`、`Read`、`Has`；带索引的 `T` 按键 `TryFind`、`Find`、`Count`），
  并行方法也能用。系统算作读 `T`；规则 [EECS059](/zh/docs/guide/analyzer#eecs059) 拒绝自己也写 `T` 的方法。见[查找](/zh/docs/guide/threading#lookups)
  和[决策](/zh/docs/decisions#d75-lookup)。
- `world.ForEachBatchParallel<T1..Tn, TJob>(ref job, filter, chunkRows)`：在多个线程上按每块里连续的行段运行 `IForEachBatch` job。见
  [查询](/zh/docs/guide/queries#on-several-threads-foreachparallel-and-foreachentityparallel)。
- `Emit<T>`：按值传入的 `[ForEach]` 参数，用于一次遍历产出的记录（交给后面的系统应用的命中、视野范围内的数据包）：
  `hits.Add(new Hit(target, power))` 追加到这个块自己的列表，不加锁、无原子操作，遍历结束时这些列表按块的顺序追加到单例 `Emitted<T>`，
  所以不管多少线程，记录都按行的顺序出来。遍历是追加；应用记录的系统清空它们。规则 [EECS070](/zh/docs/guide/analyzer#eecs070)
  拒绝同时读 `Emitted<T>` 或把同一种记录产出两次的方法。见[决策](/zh/docs/decisions#d78-emit)。
- `EntityRandom`：`[ForEach]` 方法（包括并行方法）用的确定性随机数：一个存放种子和 tick 的单例，加上（种子、实体、tick、流）的纯函数：
  `Bits`、`Float`、`Range`（整数和浮点）和 `Chance`。规则 [EECS071](/zh/docs/guide/analyzer#eecs071)（警告，有改为 `EntityRandom` 的代码修复）
  报告 `[ForEach]` 方法里的 `Random.Shared` 和 `new Random()`。见[决策](/zh/docs/decisions#d79-entity-random)。
- `world.ForParallel(count, ref job)` 对一段下标运行 `IForRange` job，`world.ForParallel(ref buffer, ref job)` 对一个列表的元素
  （`Emitted<T>` 的记录）运行 `IForSpan<T>` job，都在 World 的运行器上、用它的块；EECS060 和 EECS061 也检查这些 job。
  见[决策](/zh/docs/decisions#d80-for-parallel)。
- 分析器规则 [EECS060](/zh/docs/guide/analyzer#eecs060)（警告）：并行 `[ForEach]` 方法或 `ForEachParallel` 运行的 job 的 `Execute` 写了所有线程
  共享的内存（静态字段、上下文参数或 job 字段引用的对象），这些写入会竞争。规则 [EECS061](/zh/docs/guide/analyzer#eecs061)（警告，有代码修复）：
  `ForEachParallel` 之后读并行 job 的字段，而它给每块跑一个副本、什么都不合并回来；修复改为在一个线程上运行这个 job。
- `IDirectIndexed<TKey>`：键能映射到一段有界槽位上的唯一组件（网格格子、玩家周围的区块、小 id）声明 `static int Slots` 和
  `static int SlotOf(TKey key)`；它的索引在哈希旁边多存一个槽位数组，`Get`、`TryGet` 和写入的唯一性检查都只读一个数组元素。超出范围或
  槽位被占的键通过哈希找到，`Find`、`Count` 和有序遍历仍由哈希负责。见[直接映射的键](/zh/docs/guide/indexes-and-relations#direct-index)和
  [决策](/zh/docs/decisions#d71-direct-index)。
- `world.CollectIds<T1..Tn>(span, filter)` 按查询顺序把匹配实体的 id 写进 span，写满为止，返回写了多少个：给 `DestroyEntities`、
  `SaveEntities` 或会改结构的循环用的一批有上限的 id（一个 tick 里的前几个请求）。零分配。见[查询](/zh/docs/guide/queries#collect-ids)。
- `world.UpdateCount<TGroup>()`：到目前为止 `Update<TGroup>()` 的次数，分组里 `UpdateInterval` 就按它计数。见
  [系统](/zh/docs/guide/systems#system-groups)。
- [EECS027](/zh/docs/guide/analyzer#eecs027)（把查找的组件或单例改成参数）和 [EECS054](/zh/docs/guide/analyzer#eecs054)（去掉 `ChunkRows`）
  有了代码修复。
- `[ForEach(Parallel = true, ChunkRows = n)]` 指定并行方法的一个线程每次取多少行（向上取整到 64；`world.ForEachParallel` 等并行调用用
  `chunkRows:` 参数）。默认每块至少 1,024 行，方法写被追踪组件时至少 4,096 行，所以几百个重的行只落在一个线程上；现在它们会分到所有线程，
  写被追踪组件时也一样。分析器规则 [EECS054](/zh/docs/guide/analyzer#eecs054) 拒绝负数，以及没有 `Parallel` 的 `ChunkRows`。见
  [多线程与并行](/zh/docs/guide/threading#chunk-rows)和[决策](/zh/docs/decisions#d67-chunk-rows)。

### 性能 [#v4-8-0-performance]

- 缓冲回收池在线程之间共享：每个线程自己留几个列表，其余的按批和所有线程都能取用的池交换，所以拥有者线程从销毁的缓冲收回的列表，也能给并行
  `[ForEach]` 的第一次写入用，以前那里要分配。见[动态缓冲](/zh/docs/guide/dynamic-buffers#pool)。
- 预制体上的空缓冲（不带元素的 `SetBuffer<T>()`）不再给实例一个列表：实例写入第一个元素时从池里取，不再新建一个再扩容。
- `LoadEntities` 把缓冲读进来的那个列表直接交给加载出的实体，不再复制到另一个列表。
- 对空缓冲调用 `buffer.TrimExcess()` 会把列表还给回收池：缓冲不再持有列表，任何 `T` 缓冲的下一次首次写入会重用它，所以只在实体活跃时才用的临时缓冲，
  空闲期间不占内存。见[动态缓冲](/zh/docs/guide/dynamic-buffers#what-it-costs)。

- `world.Reserve(prefab, n)` 和 `Reserve<T1..Tn>(n)` 也会预留实体在行之外要用的东西：带索引组件的键，以及带清理组件的实体被销毁后等待所在的表。
  空闲 id 列表和索引的逐实体记录跟着实体记录（包括 `EnsureEntityCapacity`）一起增长，不再随销毁或建索引的实体一个个增长，所以预留了峰值的世界增长到峰值时不再分配。
  见[预制体](/zh/docs/guide/prefabs#reserve)。
- 唯一索引（[`IUniqueIndexed<TKey>`](/zh/docs/guide/indexes-and-relations)）把每个键对应的实体直接存在这个键自己的记录里，不再每个键一个数组：
  每个键不再分配数组，`Get` / `TryGet` 只读一条记录（[决策](/zh/docs/decisions#d71-direct-index)）。
- `SetAll` 对所有行都匹配的 64 行位字一次填好值，不再逐行写（不满的位字和带索引的组件仍逐行）。见
  [批量操作](/zh/docs/guide/bulk#what-it-costs)和[决策](/zh/docs/decisions#d72-setall-whole-words)。

### 需要修改代码的变更 [#v4-8-0-breaking]

- 分析器规则 [EECS027](/zh/docs/guide/analyzer#eecs027) 也会报告通过被访问的 `Entity` 逐行查带索引的组件；改成 `in` 参数，部分实体没有它时用
  `ReadOnlyMaybe<T>`。把警告当错误的构建会看到它：见[迁移指南](/zh/docs/migration#v4-8-analyzer)。
- 分析器规则 [EECS030](/zh/docs/guide/analyzer#eecs030) 也会报告整个方法体只是对自己实体做一次结构变更、每行都一样的 `[ForEach]` 方法
  （`[ForEach, With<Dead>] static void Bury(Entity e) => e.Destroy();`）：在 `OnUpdate` 里一次批量调用（`World.DestroyAll<Dead>()`）就能一次改完整张表（[迁移指南](/zh/docs/migration#v4-8-analyzer)）。
- 新的警告 [EECS060](/zh/docs/guide/analyzer#eecs060) 和 [EECS061](/zh/docs/guide/analyzer#eecs061) 报告在共享内存上竞争、或读了遍历从未写回的
  job 字段的并行代码；总数改用 `Reduce<T>` 参数（[迁移指南](/zh/docs/migration#v4-8-analyzer)）。
- 新的警告 [EECS071](/zh/docs/guide/analyzer#eecs071) 报告 `[ForEach]` 方法里的 `Random.Shared` 和 `new Random()`；修复改为从单例
  `EntityRandom` 抽取（[迁移指南](/zh/docs/migration#v4-8-analyzer)）。

### 修复 [#v4-8-0-fixes]

- 对带值索引、唯一索引或关系索引的世界调用 `Restore`、`Load` 和 `LoadEntities`，不再每次都重新分配：加载清空索引时把列表丢掉了，而不是留给下一次加载。
- 加载缺少所在表某个组件的实体（被 `Remove` 移除，存档里带存在位）时，重用上一次加载的存在位，不再每次分配。
- 加载两次保存之间会增长的世界（`Load`、`LoadKeeping`）时，id 记录按新 id 的个数精确增长，每次加载都要整体复制一遍；现在改为翻倍增长，
  `LoadEntities` 暂存新到实体的那个世界也按目标世界的大小创建，并同样翻倍增长。
- `Restore` 以及往已有快照里 `Capture` 时，每行的 `DynamicBuffer`（以及关系链接）复制进这一行已有的列表，不再每行新建一个列表、把旧的丢给 GC。

## 4.7.0 [#v4-7-0]

### 新功能 [#v4-7-0-new]

- `Mut<T>`：`[ForEach]` 参数，用于方法只在部分行上写的组件。`Value` 只读，`Write()` 和 `SetIfChanged(value)` 只给真正写了的行打 tick，
  所以 `[Changed<T>]` 的读取方只访问值真变了的行。遍历之外，`entity.SetIfChanged(value)` 和生成的 `SetHealthIfChanged(…)` 遇到相同的值直接跳过。
  见[变更追踪](/zh/docs/guide/change-tracking)。
- `[ChangedAny<T1..Tn>]` / `[RemovedAny<T1..Tn>]` 以及 `QueryFilter.ChangedAny<T1..Tn>(since)` / `RemovedAny`：2 到 9 个被追踪组件里
  至少有一个被写过、或被移除的行。一个过滤条件存在字段里，用 `filter.Since(ack)` 服务每个客户端。见[变更追踪](/zh/docs/guide/change-tracking)。
- `WorldOptions.DestroyLogCapacity` 和 `world.DestroyedSince(since, into, out count)`：某个读取方的 tick 以来销毁的实体，用来把实体的消失同步给确认 tick
  各不相同的客户端；读取方比日志还旧（`DestroyLogOldestTick`）时返回 false，需要重新同步。见[变更追踪](/zh/docs/guide/change-tracking)。
- `IUniqueIndexed<TKey>`：一个键只对应一个实体，用 `index.Get(key)` / `TryGet(key, out e)` 查找；会让第二个实体拿到已被占用的键的写入，
  在改动任何东西之前就抛异常。见[索引与关系](/zh/docs/guide/indexes-and-relations)。
- `index.Find(key).Count`、`world.Children(parent).Count`，以及关系的 `relations.Find(target).Count`：查找时拥有这个键的实体数（或指向目标的链接数），O(1)，不用把匹配遍历两遍就能确定缓冲区大小。
  `index.KeyCount` 和 `relations.TargetCount` 以 O(1) 给出不同键（或目标）的个数。见[索引与关系](/zh/docs/guide/indexes-and-relations#value-indexes)。
- `world.Descendants(root).AddTo(ids, includeRoot)` 把一棵子树追加到 `List<EntityId>`，每个父实体在它的子实体之前：正是 `MoveEntities` 和
  `SaveEntities` 要的那组实体，不用再写收集循环。见[层级](/zh/docs/guide/hierarchy#moving)。
- `world.Instantiate(prefab, in c1 … in cn)` 和 `Instantiate(prefab, entities, in c1 … in cn)`：实例带上最多九个自己的组件（父实体、位置、主人），
  只拷贝一次行。创建任何实体之前先检查唯一组件的键，给定的和预制体里的都查。见[预制体](/zh/docs/guide/prefabs)。
- `world.TrimExcess()` 把峰值留下的内存还回去：删掉空表，缩小其他表，释放存档、读档和迁移用的缓冲。见[调试与诊断](/zh/docs/guide/diagnostics)。
- `[ForEach(Slices = N)]` 把一个方法要处理的行分摊到系统的 N 次运行里；结构体 job 用 `QueryFilter.Slice(index, of)`，
  `EcsSystem.RunCount` 表示当前是第几次运行。见[系统](/zh/docs/guide/systems)。
- `SystemStats` 记录每次运行分配的字节数（`LastAllocated`、`TotalAllocated`）和 `[ForEach]` 方法访问的实体数（`LastEntities`、`TotalEntities`）；
  `world.DescribeSchedule()` 描述各个阶段、等待关系和只靠注册顺序的系统对，可以输出文本或 mermaid 流程图。见[调试与诊断](/zh/docs/guide/diagnostics)。
- 重启存档：`world.SaveWithout(output, in exclude)` 不写 `ComponentSet` 里的组件和单例，`world.LoadKeeping(input, in keep, markWritten)` 保留新进程设好的单例，
  `ComponentSet.WithSingleton<T>()` / `With(Type)` 可以加入单例。见[重启](/zh/docs/guide/saves#restart)。
- 分析器：[EECS035](/zh/docs/guide/analyzer#eecs035) 拒绝不合法的 `Slices`（小于 1，或者和 `Changed` / `Removed` 过滤一起用）；
  [EECS036](/zh/docs/guide/analyzer#eecs036) 拒绝无法按键建索引的唯一组件（`EntityId` 键，或者还有第二个索引键）；
  [EECS031](/zh/docs/guide/analyzer#eecs031) 也覆盖用相同值循环调用 `Instantiate`；[EECS033](/zh/docs/guide/analyzer#eecs033) 建议改用生成的 `SetXIfChanged(…)`；代码修复现在也覆盖 [EECS007](/zh/docs/guide/analyzer#eecs007)（`readonly`）、
  [EECS015](/zh/docs/guide/analyzer#eecs015)、[EECS017](/zh/docs/guide/analyzer#eecs017)（`EntityId`）、[EECS018](/zh/docs/guide/analyzer#eecs018)
  和 [EECS025](/zh/docs/guide/analyzer#eecs025)（`Mut<T>` 改为 `in T`）。
- `SaveEntities(output, a.Id, b.Id)` 和 `bag.AddRange(x, y)` 可以直接传值（`params` span，在栈上构造）。
  见[迁移](/zh/docs/guide/migration-and-unload#save-entities)。
- `world.Read<T1..Tn>(filter)` 遍历查询的行，只读不写：条目是 `ref readonly`，不打 tick，所以工具或请求处理函数读过的行，
  `[Changed<T>]` 的读取方不会当成写过。`Query` 照旧给它访问的被追踪组件的行打 tick。见[查询](/zh/docs/guide/queries#read)。
- `world.DestroyEntities(ids)` 销毁一组 id，只过一次结构闸门、只处理一次级联；失效的 id 和重复的 id 会跳过。
  见[结构变更](/zh/docs/guide/structural-changes#bulk)。
- `ChildOf` 和 `Retired` 像你自己的组件一样有生成成员：`entity.ChildOf`、`HasChildOf`、`TryGetChildOf`、`SetChildOf(parent)`、
  `SetChildOfIfChanged(parent)`、`RemoveChildOf()`、`world.ChildOfIndex`、预制体上的写入方法，以及 `entity.IsRetired`。
  见[层级](/zh/docs/guide/hierarchy#reparent)。
- 只把 `Entity` 当身份用（`Id`、`Version`、`IsAlive`、`==`、`EntityId`）的 `[ForEach]` 方法不再让系统单独运行：系统按其他参数调度。
  见[系统](/zh/docs/guide/systems)。

### 性能 [#v4-7-0-performance]

- 带组件刷出实体只拷贝一次行，不再是先 `Instantiate` 再 `Set`。见[决策 D41](/zh/docs/decisions#d41-instantiate-with-components)。
- 每个 tick 重算被追踪值的系统，不再让每个 `[Changed<T>]` 读取方访问每一行：用 `Mut<T>` 时只有值真变了的行才打 tick。
  见[决策 D46](/zh/docs/decisions#d46-mut-stamps-per-write)。
- `ChangedAny` 跳过它的组件都没写过的表、4,096 行的块和 64 行的位字。见[决策 D49](/zh/docs/decisions#d49-changedany-semantics)。
- 源生成器在 IDE 里每次按键做的工作更少，分析器在构建时分配更少：方法体里的类型名不再连同方法体一起绑定，比较符号也不再拼字符串。
  见[决策 D62](/zh/docs/decisions#d62-generators-bind-outside-bodies)。

### 修复 [#v4-7-0-fixes]

- 两条分析器规则看到的同一个错误会报两次，两个修法还互相抵消。现在只由一条规则报（EECS038 优先于 EECS025 和 EECS015，EECS016 和
  EECS049 优先于它们排除的参数的代价，EECS010 优先于 EECS029 和 EECS025，EECS032 和 EECS030 优先于 EECS046，EECS041 和 EECS013
  优先于 EECS028，EECS045 优先于 EECS030，EECS027 和 EECS052 优先于 EECS033，EECS002 优先于 EECS012），EECS010 也提供 EECS029 的
  “改成 static”。见 [D60](/zh/docs/decisions#d60-one-diagnostic-per-mistake)。

- 在查询循环里调用 `World.Update`（EECS051）后，循环结束时计数会变成负数，下一次更新前 `TrimExcess` 一直抛异常。
  现在这样的循环结束时不再留下计数。
- 嵌套的组件或缓冲元素和所在命名空间里另一个结构体同名时，仍会生成一部分成员（`DisableX`、`InX`、`world.XIndex`、缓冲的成员），
  和另一个类型的成员同名，调用时编译不过（有歧义）。这样的类型现在不生成任何成员，用泛型 API 访问。
- 关系的名字恰好是某个 `Entity` 成员的后缀时，会丢掉 `LinksX(target)`。
- 同一命名空间里两个结构体生成的成员同名时（标签 `Dead` 和组件 `IsDead`、`Target` 和 `HasTarget`、`Zone : IIndexed<int>` 和单例
  `ZoneIndex`），每次调用这个成员都有歧义。现在两个类型都不生成它，其他成员照常保留。
- internal 组件生成的属性（`entity.X`、`HasX`、`IsX`、`world.X`、`world.XIndex`）在看得到库内部成员的程序集（`InternalsVisibleTo`）里编译不过。
  现在这些成员是 public 的，所在的类和类型一样可见。
- 库和看得到它内部成员的程序集对同样的组件做 `Query` 或 `Read` 时，后者里查询项的命名成员有歧义。现在后者直接用库里的。
- 同一命名空间里的缓冲元素 `Loot` 和 `LootPrefab` 会生成两个同名的类，编译不过。生成的类换了名字，见[迁移指南](/zh/docs/migration#v4-7-generated-classes)。
- 组件名和 `Prefab` 的方法撞名时（`Buffer`，对应 `SetBuffer`），生成的预制体成员永远调不到：`prefab.SetBuffer(5)` 实际执行的是
  `Prefab.SetBuffer<int>`。现在不再生成这样的成员。
- 用自动属性写的组件或关系（`public int Hp { get; set; }`、`public EntityId Target { get; init; }`）没有 `SetX` 或 `AddX`。
  现在带公开 `set` 或 `init` 的自动属性和字段一样算进去。
- 只通过目标类型推断的创建（`Regen<Health> regen = new();`）或 `typeof` 闭合的泛型系统，代码要在运行时靠反射生成，
  Native AOT 下会失败；这两种写法现在在编译期就注册。
- 并行 pass（并行 `[ForEach]`、`ForEachParallel`，或者并行系统的一个阶段）可能卡死，调用方一直自旋，同时某一块（或某个系统）被执行两次：
  上一轮还没收尾的 helper 线程，会在下一轮任务更多时领走下一轮的任务。分片的并行 pass 每次运行的块数都不同，几秒内就会触发。
  现在每一轮开始前先关闭上一轮的领取。见[多线程与并行](/zh/docs/guide/threading#parallel-foreach-methods)。
- 写被追踪组件的并行 `[ForEach]` 可能漏打变更 tick：同一个 4,096 行块里的两个分块会争用这个块的变更摘要，`[Changed<T>]` 读取方可能跳过被写过的行。
  这类遍历现在按 4,096 行的整数倍切块。见[决策 D48](/zh/docs/decisions#d48-parallel-tracked-chunks)。
- `RemoveTypes` 删掉表之后，往旧快照里 `Capture(into)`，或者之后再 `Load`，可能复用另一张表（列不同）的副本。现在副本只给它自己的表复用。
  见[快照](/zh/docs/guide/snapshots)。
- 对实体还没有的被索引组件调用 `entity.GetOrAdd<T>()` 时不会通知值索引，`Find` 和 `Count` 要等下一次 `Set` 才能找到这个实体；
  现在默认值的键会进索引。见[索引与关系](/zh/docs/guide/indexes-and-relations)。
- `MoveEntities` 会把退休（因清理组件而保留）的实体复制到目标 World 并算作已移动，而源 World 里它还在：同一个实体存在了两份。
  这样的实体现在和失效的 id 一样被跳过。见[迁移](/zh/docs/guide/migration-and-unload#move-entities)。
- `MoveEntities` 移动持有清理组件的实体时，也把清理组件复制给了新实体，而原实体还留着它们等待释放，资源因此被释放两次。
  现在清理组件只留在原处。见[迁移](/zh/docs/guide/migration-and-unload#move-entities)。
- 过滤条件没写 `Retired` 的 `SetAll` 会处理到退休（因清理组件而保留）的实体，给它们加上组件，让它们重新出现在查询里。
  现在不会碰它们。见[批量变更](/zh/docs/guide/bulk)。
- 对退休（因清理组件而保留）的实体调用 `Clone()`，会再造出一个这样的实体，带着清理组件的副本；现在抛
  `InvalidOperationException`。见[清理组件](/zh/docs/guide/cleanup-and-disable#cleanup-components)。
- 销毁持有清理组件的实体时，它失去其他组件被算作移除，`[Removed<T>]` 方法和 `Removed<T>(since)` 过滤条件会访问它，而没有清理组件的
  已销毁实体从不会被访问。现在实体退休不再算移除；它被释放后由销毁日志报告。见[移除检测](/zh/docs/guide/change-tracking#removal-detection)。
- `LoadEntitiesInto` 接受目标里重复出现的同一个实体，第二个存档实体会覆盖第一个；现在抛 `ArgumentException`。
  见[迁移](/zh/docs/guide/migration-and-unload#records)。
- 在查询循环或系统里 `world.Instantiate(prefab)` 一个带成员的预制体会抛异常（`Snapshots cannot be captured or restored while a query iterates`），
  而不带成员的预制体在那里可以实例化。现在一组实体的副本和别的新行一样，生成器系统也能实例化它。见[预制体](/zh/docs/guide/prefabs)。
- 必须等遍历结束的调用（`Capture`、`Restore`、`Save`、`SaveWithout`、`SaveEntities`、`SaveEntitiesWith`、`Load`、`LoadKeeping`、
  `LoadEntities`、`LoadEntitiesInto`、`MoveEntities`、`GroupBy`、`RemoveTypes`、`TrimExcess`）拒绝时，要么报同一条关于快照的消息，要么各报各的：现在每个调用都在消息里写出自己的名字
  （`MoveEntities cannot run while a query or system iterates the world`）。见[排错](/zh/docs/guide/troubleshooting#during-a-pass)。

  [EECS029](/zh/docs/guide/analyzer#eecs029) 没用到系统任何成员的实例 `[ForEach]` 方法；
  [EECS030](/zh/docs/guide/analyzer#eecs030) 遍历查询逐个实体做结构变化；
  [EECS031](/zh/docs/guide/analyzer#eecs031) 在计数循环里逐个创建实体；[EECS032](/zh/docs/guide/analyzer#eecs032) 用
  `Count() > 0` 代替 `Any()`，以及在循环里计数或过滤。建议（信息级别，代价相同、写法更简洁）：
  [EECS033](/zh/docs/guide/analyzer#eecs033) 有同等含义生成成员的泛型调用（`entity.Get<Position>()` 写成 `entity.Position`）。错误：[EECS034](/zh/docs/guide/analyzer#eecs034) 系统调用
  `World.Update()`。每条规则为什么加、哪些没加：见[决策 D29](/zh/docs/decisions#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)。
- 新规则在改法机械时附带代码修复：`in`、`ReadOnlySpan<T>`、`Read<T>()`、`[With<T>]`、`static`、批量调用（`SetAll`、`RemoveAll`、
  `DisableAll`、`EnableAll`、`DestroyEntities`）、`CreateEntities` 或 `EnsureCapacity`、`Any` / `Count`，以及生成的成员。
  只有改完能编译时才提供。
- 每条分析器诊断都链接到[分析器规则](/zh/docs/guide/analyzer)页面上对应的小节。

### 需要修改代码的变更 [#v4-1-0-breaking]

完整步骤见[迁移指南](/zh/docs/migration#v4-0-to-v4-1)。

- `WorldOptions.Parallel` 改名为 `WorldOptions.ParallelSystems`：写成 `new WorldOptions { ParallelSystems = true }`。
- `Entity.Id` 是 `EntityId`，`Entity.Version` 已删除：读 `entity.Id.Index` 和 `entity.Id.Version`；组件里存 `EntityId`
  （组件里有 `Entity` 字段时 EECS017 会警告）。
- `EcsSystem.Priority` 已删除：用 `[UpdateBefore<T>]` / `[UpdateAfter<T>]` 排序。
- `World.SystemError` 事件已删除：用 `new WorldOptions { SystemErrors = SystemErrorPolicy.Disable }`，再读 `system.Error`。
- `world.DestroyEntity(entity)` 已删除：调用 `entity.Destroy()`。
- `entity.Add<T>()` 已删除：添加或替换写 `Set(new T(…))` 或生成的 `SetX(…)`，只在缺少时添加默认值用 `GetOrAdd<T>()`。
- `world.CompactArchetypes()` 和 `world.GetFragmentationStats()` 已删除：表自己保持紧凑。
- `IForEach` job 只接收组件：需要实体时改用 `IForEachEntity`。
- `Query` 的结果是 ref struct：循环里不能 `await`，元素不能存进字段、lambda 或 LINQ。
- 结构变更属于 World 的所有者线程；在并行阶段或并行 `[ForEach]` 里做结构变更会抛 `InvalidOperationException`。
  见[多线程与并行](/zh/docs/guide/threading)。
- EECS007（系统里有状态）和 EECS008（系统引用系统）改为错误，它们在 4.0 里是警告。把状态移进组件或单例，系统之间通过数据
  通信。
- `QueryEnumerator.Count` 和 `IsEmpty` 删除了：改用 `world.Count<…>(filter)` / `world.Any<…>(filter)`。
- `UpdateInterval` 和 `UpdatePhase` 应当返回常量，否则 EECS018 会警告。
- 指向表的 ref 可能因为其他实体的结构变更而失效；遍历顺序按表的行；`AddSingleton` 原地重置已有的单例组件；失效的句柄
  `Has` / `TryGet` 返回 false。见[ref 与 await](/zh/docs/guide/refs-and-await)。
