What to change in your code when you upgrade EasyEcs, one version step per section, newest first. Each section
lists every rename, removal and behavior change of its step, with the code to write instead. Upgrading across several versions? Apply the sections in order, oldest first. The
[changelog](/en/docs/changelog) lists everything each release added; the [API reference](/en/docs/api) is the
current API.

## v4.7 → v4.8 [#v4-7-to-v4-8]

Code written for 4.7 compiles unchanged, and saves of 4.7 load. Two analyzer rules report more code, and three
warnings are new: a build that treats warnings as errors fails on them until the code changes.

### Analyzer rules that report more: EECS027, EECS030 and EECS053 [#v4-8-analyzer]

[EECS027](/en/docs/guide/analyzer#eecs027) now also reports a per-row lookup of an indexed component through the visited
`Entity`, which it used to leave alone because a `Maybe<T>` of one is an error
([EECS015](/en/docs/guide/analyzer#eecs015)). Take it as an `in` parameter, or a
[`ReadOnlyMaybe<T>`](/en/docs/guide/systems#read-only-maybe) when some entities lack it:

```csharp
public record struct Guild(int Id) : IComponent, IIndexed<int> { public int Key => Id; }
public record struct Morale(int Value) : IComponent;
```

```csharp tab="4.7" doccheck=expect-EECS027
public class Rally : EcsSystem
{
    [ForEach, With<Guild>]
    static void Raise(Entity member, ref Morale morale) => morale.Value += member.Guild.Id;   // a lookup per row
}
```

```csharp tab="4.8"
public class Rally : EcsSystem
{
    [ForEach]
    static void Raise(ref Morale morale, in Guild guild) => morale.Value += guild.Id;
}
```

[EECS030](/en/docs/guide/analyzer#eecs030) now also reports a `[ForEach]` method whose whole body is one structural
change of its entity, the same for every row. Move the change into one bulk call in `OnUpdate`:

```csharp tab="4.7" doccheck=expect-EECS030
public class CorpseSystem : EcsSystem
{
    [ForEach, With<Dead>]
    static void Bury(Entity entity) => entity.Destroy();                // one change, entity by entity
}
```

```csharp tab="4.8"
public class CorpseSystem : EcsSystem
{
    protected override void OnUpdate() => World.DestroyAll<Dead>();
}
```

[EECS053](/en/docs/guide/analyzer#eecs053) is new: a tracked component taken by `ref` that some path leaves unwritten.
Its code fix takes it as a `Mut<T>`.

[EECS060](/en/docs/guide/analyzer#eecs060) is new: a parallel `[ForEach]` method, or the `Execute` of a job run by
`ForEachParallel`, that writes a static field or a shared object. A total becomes a
[`ref Reduce<T>`](/en/docs/guide/threading#reductions) parameter:

```csharp
public struct Hits : ISingletonComponent, IReduction<Hits>
{
    public int Count;
    public static Hits Identity => default;
    public static Hits Combine(Hits left, Hits right) => new() { Count = left.Count + right.Count };
}
```

```csharp tab="4.7" doccheck=expect-EECS060
public static class HitStats
{
    public static int Hits;
}

public class TakeHits : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health)
    {
        health = new Health(health.Value - 1);
        HitStats.Hits++;   // lost updates
    }
}
```

```csharp tab="4.8"
public class TakeHits : EcsSystem
{
    [ForEach(Parallel = true)]
    static void Hit(ref Health health, ref Reduce<Hits> hits)
    {
        health = new Health(health.Value - 1);
        hits.Value.Count++;
    }
}
```

[EECS061](/en/docs/guide/analyzer#eecs061) is new: a parallel job's field read after `ForEachParallel` (each chunk
ran a copy). Its code fix runs the job with `ForEach`; for all cores, use a `Reduce<T>` parameter as above.

### New public type [#v4-8-new-types]

`ReadOnlyMaybe<T>`, `Reduce<T>`, `IReduction<T>`, `Scratch<T>`, `Lookup<T>`, `LookupExtensions`, `IDirectIndexed<TKey>`, `SimdMode` and `Interleaved` are new in `namespace EasyEcs`. A file that imports another namespace with a type of that name gets
CS0104 (ambiguous reference): qualify the name, or alias it with a `using` directive.

## v4.6 → v4.7 [#v4-6-to-v4-7]

Calls, types and generated members are [renamed](#v4-7-renames): the compiler finds each use, and saves of 4.6 still
load. Beyond that, code written for 4.6 compiles unchanged unless a system declares a member named `RunCount`, a file imports another
namespace with a type of the same name as one of the new ones, or code names a [generated class](#v4-7-generated-classes). Three calls behave differently, and parallel passes that
write tracked components cut their rows differently. The [new analyzer rules](#v4-7-analyzer) report code that throws or
loses writes.

### `SaveEntities` refuses a set that names a singleton [#v4-7-save-entities]

A `ComponentSet` holds singletons too (`WithSingleton<T>()`), and `With(Type)` now accepts a singleton type instead of
throwing. A save of entities writes no singletons, so `SaveEntitiesWith(output, ids, set)` throws `ArgumentException` for a set
that names one. A set built with `With(typeof(...))` from a list of types that mixes components and singletons now
fails at the save, not at `With`. Keep the components of a record in a set of their own:

```csharp tab="4.6" doccheck=skip
static readonly ComponentSet Record = ComponentSet.Create().With(typeof(Bank)).With(typeof(Rates));  // Rates: a singleton, refused by With
```

```csharp tab="4.7"
public record struct Bank(long Gold) : IComponent;

private static readonly ComponentSet Record = ComponentSet.Create().With<Bank>();
```

A whole-world `SaveWithout(output, in exclude)` and `LoadKeeping(input, in keep)` are where sets with singletons go
([restart](/en/docs/guide/saves#restart)).

### `AddSingleton` throws when the singleton exists [#v4-7-add-singleton]

`world.AddSingleton<T>()` on a world that has `T` already throws `InvalidOperationException` instead of resetting it to
`default`: a second add was most often a setup run twice, or an add after a `Load` that had brought the singleton,
and the reset silently lost its value. A reset says so now: write the value with the generated `world.SetX(…)` (or
`world.X = default`), which keeps the storage, so `SingletonRef<T>` handles still reach it. Where the singleton may
exist already (after a `Load`), check `world.HasX` first or take it as it is with `GetOrAddX()`.

```csharp tab="4.6" doccheck=skip
world.AddSingleton<RoundClock>();  // a new round: back to tick 0 (and on a world without RoundClock, adds it)
```

```csharp tab="4.7"
public record struct RoundClock(long Tick) : ISingletonComponent;

public static class Round
{
    public static void Restart(World world) => world.SetRoundClock(0);   // adds it if missing, else replaces the value
}
```

### `EcsSystem.RunCount` [#v4-7-run-count]

`EcsSystem` has a public `long RunCount` (the runs before the current one, which `[ForEach(Slices = N)]` uses). A
member of that name in a system hides it: warning CS0108, an error where warnings are errors. Rename the member, or
read the base property where it means the same.

```csharp tab="4.6" doccheck=skip
public class Spawner : EcsSystem
{
    private static long RunCount;                    // hides EcsSystem.RunCount in 4.7
    protected override void OnUpdate() => RunCount++;
}
```

```csharp tab="4.7"
public class Spawner : EcsSystem
{
    protected override void OnUpdate()
    {
        if (RunCount % 10 == 0) { /* every tenth run */ }
    }
}
```

### Parallel passes that write tracked components [#v4-7-parallel-chunks]

A parallel `[ForEach]` method (or a `ForEachParallel` job) that writes a tracked component cuts its rows into chunks
of a multiple of 4,096 rows, 4,096 at least, instead of 1,024 at least: two chunks inside one 4,096-row block raced on
its change summary and could drop stamps ([D48](/en/docs/decisions#d48-parallel-tracked-chunks)). Nothing to change in
code; a table of 4,096 rows or fewer now runs as one chunk, so a small parallel pass may use fewer threads than
before. Passes that write no tracked component chunk as before.

### Renamed calls [#v4-7-renames]

Calls, types and generated members of 4.6 say in their names what they do now. The old names are gone, so the
compiler points at every use to change ([D64](/en/docs/decisions#d64-names-of-4-7)):

| 4.6 | 4.7 | Why |
|---|---|---|
| `world.SaveEntities(output, ids, set)` | `world.SaveEntitiesWith(output, ids, set)` | the set is what the record writes; `SaveEntities(output, ids)` without a set stays |
| `world.EnsureCapacity<T1, …, Tn>(count)` | `world.Reserve<T1, …, Tn>(count)` | `count` is how many more entities, not a total; `EnsureEntityCapacity(total)` and `DynamicBuffer.EnsureCapacity(capacity)` are totals and stay |
| `world.EnsureCapacity(prefab, count)` | `world.Reserve(prefab, count)` | the same |
| `world.DestroyEntities<T1, …, Tn>(filter)` | `world.DestroyAll<T1, …, Tn>(filter)` | the filter's calls end in `All`, like `SetAll` and `RemoveAll` |
| `e.RemoveMemberOf(target)` (a relation's generated member) | `e.UnlinkMemberOf(target)` | `e.RemoveMemberOf()` drops the whole buffer; one missing argument no longer drops every link |
| `e.AddMemberOf(target)` (a relation's generated member) | `e.LinkMemberOf(target)` | a link is made, not a component added; `LinkX` / `UnlinkX` / `LinksX` read as one family |
| `entity.AddRelation(r)` / `RemoveRelation<T>(target)` / `HasRelation<T>(target)` | `entity.Link(r)` / `Unlink<T>(target)` / `Links<T>(target)` | the same family, generic |
| `ITrackChanges` | `ITracked` | a marker that says what the component is, like `IIndexed` |
| `IGroupWith<T>` / `IGroupWithout<T>` | `ISystemGroupWith<T>` / `ISystemGroupWithout<T>` | they filter a system group, not an `IGroup` (the component that splits tables) |
| `Destroyed` (the tag), `entity.IsDestroyed` | `Retired`, `entity.IsRetired` | the entity is alive, kept for its cleanup components; "destroyed" now means gone. Saves of 4.6 load: the tag keeps its saved name |
| `world.GetSystem<T>()` (null when absent) | `world.TryGetSystem<T>(out T system)` | the miss is in the signature; keep the reference `AddSystem` returns where you can |
| `world.Describe()` | `world.DescribeTables()` | what it describes; `entity.Describe()` and `DescribeSchedule()` stay |
| `ColumnInfo.Without` | `ColumnInfo.Absent` | not the `Without` filter: the rows of the table that lack the component |
| `system.Stats.Last` / `Total` / `Average` | `LastTime` / `TotalTime` / `AverageTime` | the stats also hold counts and bytes |
| `world.UpdateCount` | `world.DefaultUpdateCount` | it counts the default group's updates only |
| `SystemAccess.RunsAlone()` | `SystemAccess.RunAlone()` | an instruction; `SystemInfo.RunsAlone` (a fact) stays |
| `TargetRules` (the class of `WhenTargetDestroyed`) | `TargetPolicyExtensions` | only code that names the class changes |
| a hand-written job's `static int Writes` | `static int WriteMask` | a bit mask, like `SelfStamped` |
| `LoadEntitiesInto(input, into: …)` | `LoadEntitiesInto(input, targets: …)` | only a named argument changes |

`world.DestroyEntities(ids)` now destroys a list of ids in one call, like `SaveEntities` and `MoveEntities`. A call of
4.6 with type arguments does not compile against it, so none changes meaning silently.

The restart calls new in 4.7 have their names from the start: `world.SaveWithout(output, in exclude)` and
`world.LoadKeeping(input, in keep, markWritten)` ([restart](/en/docs/guide/saves#restart)).

### Generated classes [#v4-7-generated-classes]

The classes that hold the generated members have a suffix that begins with `Ecs`, so two types' classes never share
a name (`Loot`'s and `LootPrefab`'s did):

| 4.6 | 4.7 |
|---|---|
| `HealthEcsExtensions` | `HealthEcsExtensions` (unchanged) |
| `HealthPrefabExtensions` | `HealthEcsPrefabExtensions` |
| `LootBufferExtensions` | `LootEcsBufferExtensions` |
| `LootPrefabBufferExtensions` | `LootEcsPrefabBufferExtensions` |

Calls through the members (`prefab.SetHealth(100)`, `e.WriteLoot()`) do not change. Only code that names a class
does: a static call (`HealthPrefabExtensions.SetHealth(prefab, 100)`), a `using static` directive or a `cref`.

### New analyzer rules: EECS037 to EECS052 [#v4-7-analyzer]

Code that compiled with 4.6 can fail the build with 4.7. The new errors name code that throws or cannot work:
[EECS040](/en/docs/guide/analyzer#eecs040) to [EECS045](/en/docs/guide/analyzer#eecs045) (`SetIfChanged` of a type
it cannot compare, a call a pass refuses, an indexed component added to while its index is walked, a record struct
key that prints itself, a sliced filter given to a whole-row call, a `Retired` or `Disabled<T>` tag written by
hand), [EECS048](/en/docs/guide/analyzer#eecs048) to [EECS051](/en/docs/guide/analyzer#eecs051) (`Disable` of a cleanup component or `ChildOf`, a `[ForEach]`
method whose filters no entity passes, a second `InGroup` in one filter, `world.Update()` inside a query loop), and
[EECS036](/en/docs/guide/analyzer#eecs036) now also reports a plain component with two index keys. The new
warnings name a write that is lost, a ref that may point at the wrong row or work done twice:
[EECS037](/en/docs/guide/analyzer#eecs037) (a job's `WriteMask`), [EECS038](/en/docs/guide/analyzer#eecs038) (a
changed copy), [EECS046](/en/docs/guide/analyzer#eecs046) (a `Query` loop that only reads tracked components: loop
over `Read`), [EECS047](/en/docs/guide/analyzer#eecs047) (a ref used after a structural change: take it again) and
[EECS052](/en/docs/guide/analyzer#eecs052) (a `Set` right after `CreateEntity` or `Instantiate`: give the component to the creation).
[EECS039](/en/docs/guide/analyzer#eecs039) is a suggestion. Most have a code fix; a build that treats warnings as
errors fails on the warnings until the code changes.

### `MeasureSystems` measures more [#v4-7-measure-systems]

With `WorldOptions.MeasureSystems`, every run also reads the thread's allocation counter twice (and every helper chunk
of a parallel `[ForEach]`), and each `[ForEach]` pass counts its matches once when it starts, for the new `SystemStats`
fields. A world that measures pays that on every update; without `MeasureSystems` nothing changed.

### New public types [#v4-7-new-types]

`Mut<T>`, `IUniqueIndexed` / `IUniqueIndexed<TKey>`, `UniqueIndexExtensions`, `ChangedAnyAttribute<…>`,
`RemovedAnyAttribute<…>`, `ScheduleInfo`, `GroupInfo`, `StageInfo`, `SystemInfo`, `StageWait` and `SystemPair` are
new in `namespace EasyEcs`, and so are the renamed `ITracked`, `ISystemGroupWith<T>`, `ISystemGroupWithout<T>`,
`Retired` and `TargetPolicyExtensions`. A file that imports another namespace with a type of one of these names gets CS0104
(ambiguous reference): qualify the name, or alias it with a `using` directive.

## v4.3 → v4.4 [#v4-3-to-v4-4]

The save format changed, and EasyEcs builds on Nino 4.0.0-rc.6. Code written for 4.3 compiles unchanged; what needs
attention is saved data and the Nino package reference.

### Saves of 4.3 and earlier do not load [#v4-4-saves]

A save now records each type by its Nino type id instead of its name, and writes unmanaged `[NinoType]` components
through their formatter. `Load`, `LoadEntities` and `LoadEntitiesInto` refuse the bytes of an earlier version with
`InvalidDataException: Not an EasyEcs save (or one of another format version)`, and leave the world as it was.

Write again what must outlive the upgrade: load it with the 4.3 build, move it into a format of your own (or keep the
4.3 build as the tool that reads it), and save it with 4.4. Saves that only live as long as a process (hot reload,
handing a player to another server of the same build) need nothing.

### Nino 4.0.0-rc.6 [#v4-4-nino]

EasyEcs references `Nino.Serialization` 4.0.0-rc.6. A project that generates formatters references the same version
of `Nino.Generator`:

```xml tab="4.3"
<PackageReference Include="Nino.Generator" Version="4.0.0-rc.4" />
```

```xml tab="4.4"
<PackageReference Include="Nino.Generator" Version="4.0.0-rc.6" />
```

### Unmanaged `[NinoType]` components are written by Nino [#v4-4-ninotype]

An unmanaged component marked `[NinoType]` was saved as raw rows, like any unmanaged component. It is now written by
its Nino formatter, value by value, so its format decides how it may change between builds
([when the code changed](/en/docs/guide/saves#versioning)). Keep the attribute where the shape will change; remove it
where raw rows (one block per column) are what you want:

```csharp tab="4.3" doccheck=skip
[NinoType]
public partial record struct Speed(float Value) : IComponent;   // saved as raw rows
```

```csharp tab="4.4"
using Nino.Core;

public record struct Speed(float Value) : IComponent;            // raw rows

[NinoType(format: NinoFormat.VersionTolerant)]
public partial record struct Rank(int Tier, int Points) : IComponent;   // by its formatter: may gain members
```

## v4.2 → v4.3 [#v4-2-to-v4-3]

The analyzer gained performance rules ([EECS025 to EECS034](/en/docs/guide/analyzer#eecs025)). Code written for 4.2
compiles unchanged unless a system calls `World.Update()`, or the build treats warnings as errors.

### New warnings: EECS025 to EECS032 [#v4-3-warnings]

Each names code that works but costs, with the fix in its [section of the analyzer rules](/en/docs/guide/analyzer)
and, where the change is mechanical, a code fix in the IDE. Apply the fix, or suppress the rule where the code is
deliberate, with the reason next to it. With a tracked `Armor` and a `Seen` counter:

```csharp
public record struct Armor(int Value) : IComponent, ITracked;
public record struct Seen(int Count) : IComponent;
```

```csharp doccheck=system
#pragma warning disable EECS026 // the write access is the point: it stamps the rows a [Changed<T>] system reacts to
[ForEach] static void Touch(ref Armor armor, ref Seen seen) => seen.Count++;
#pragma warning restore EECS026
```

Or turn a rule down for a whole project in `.editorconfig`:

```ini title=".editorconfig"
dotnet_diagnostic.EECS028.severity = suggestion
```

### `World.Update()` in a system is an error: EECS034 [#v4-3-update-in-a-system]

It ran the system again inside its own run. Run updates and groups from the code that hosts the world.

```csharp tab="4.2" doccheck=expect-EECS034
public class CatchUp : EcsSystem
{
    protected override void OnUpdate() => World.Update();
}
```

```csharp tab="4.3"
while (running) world.Update();   // in the host loop
```

### The suggestion EECS033 [#v4-3-suggestion]

EECS033 shows in the IDE only and never fails a build: the generated member is the same call at the same cost, only
shorter. `dotnet_diagnostic.EECS033.severity = warning` in `.editorconfig` turns it into a warning.

## v4.1 → v4.2 [#v4-1-to-v4-2]

One behavior changed; code written for 4.1 compiles unchanged.

### A missing singleton throws in `[ForEach]` methods [#v4-2-missing-singleton]

A `[ForEach]` singleton parameter resolves through `world.SingletonRef<T>()`, which used to add the singleton with
its default value. Both now throw `InvalidOperationException`, like `world.X` and `GetSingleton<T>()`, on the
system's first run, even when no entity matches. The message names the fix:

```text
Singleton Clock was not added to this world: set it before the systems that read it run
(world.SetClock(...) or world.AddSingleton<Clock>()), or use GetOrAddClock() where a default is meant
```

Add every singleton your systems read where the world is built, before the first `Update()`, also in tests. With
this singleton and system:

```csharp
public record struct Clock(long Tick, float DeltaTime) : ISingletonComponent;

public class Ticker : EcsSystem
{
    [ForEach] static void Advance(in Clock clock, ref Position position) => position.X += clock.DeltaTime;
}
```

In 4.1 the first update added a default `Clock`, with no step. In 4.2, set it first, or call
`world.GetOrAddClock()` where the default is right:

```csharp tab="4.1"
var world = new World();
world.AddSystem<Ticker>();
world.Update();
```

```csharp tab="4.2"
var world = new World();
world.SetClock(Tick: 0, DeltaTime: 1f / 30);
world.AddSystem<Ticker>();
world.Update();
```

A world restored with `Load` already holds the singletons of its save; add only the ones the save did not hold. See
[singletons in systems](/en/docs/guide/singletons#in-systems).

## v4.0 → v4.1 [#v4-0-to-v4-1]

A few APIs changed (listed first). Other code written for 4.0 compiles unchanged unless it stores `Query` results in
fields, uses them across `await`, captures them in lambdas, uses them in iterators or LINQ, or passes them as generic
arguments: they are ref structs now. The storage moved from one column per component type (indexed by entity id) to
archetype tables (one row per entity, columns 64-byte aligned), which changes a few behaviors.

### Renamed and removed APIs [#v4-1-api]

- **`WorldOptions.Parallel` is `WorldOptions.ParallelSystems`.** The option runs systems side by side; the new name
  keeps it apart from `[ForEach(Parallel = true)]`, which splits one method's rows over threads. Rename the
  initializer: `new WorldOptions { ParallelSystems = true }`.
- **`Entity.Id` is an `EntityId`** (index + incarnation, 8 bytes, unmanaged) instead of an `int`, and the
  `Entity.Version` field is gone: read `entity.Id.Index` and `entity.Id.Version`. `world.GetEntity`,
  `TryGetEntity` and `IsAlive` take an `EntityId`; a handle converts to one implicitly, so `world.GetEntity(entity)`
  compiles. Store `EntityId`s, not `Entity` handles, in components: a handle holds its world, which makes the column
  managed (scanned by the GC, not copied as a block, not serializable), and the new warning
  [EECS017](/en/docs/guide/analyzer#eecs017) points at such fields.
- **`EcsSystem.Priority` is gone.** Systems run in registration order; order them by what they depend on with
  `[UpdateBefore<TSystem>]` / `[UpdateAfter<TSystem>]` on the class. A cycle is
  [EECS019](/en/docs/guide/analyzer#eecs019), an order against a system of another group
  [EECS020](/en/docs/guide/analyzer#eecs020).
- **The `World.SystemError` event is gone.** A system's exception propagates out of `Update` (the default), or, with
  `new WorldOptions { SystemErrors = SystemErrorPolicy.Disable }`, switches the system off and stays in
  `system.Error` for the application to read from `world.Systems`. Enable the system again to retry.
- **Systems need no `partial`.** The generated code lives outside the system's type, so EECS001 is gone; `partial`
  still compiles.
- **`UpdateInterval` and the new `UpdatePhase` should be constants**: they are read every update, and the warning
  [EECS018](/en/docs/guide/analyzer#eecs018) points at overrides that compute them. To stop and resume a system, set
  `Enabled`.
- **`world.DestroyEntity(entity)` is gone**: it did what `entity.Destroy()` does. Call `entity.Destroy()`, or
  `world.DestroyAll<T…>(filter)` for every match at once.
- **`IForEach` jobs receive only the components.** `Execute(int entityId, ref T1 c1, …)` became
  `Execute(ref T1 c1, …)`, so a pass never loads the entity rows for them. A job that needs the entity implements
  `IForEachEntity<…>` (`Execute(Entity entity, ref T1 c1, …)`) and runs with `world.ForEachEntity`.
- **`CompactArchetypes()` and `GetFragmentationStats()` are gone.** Tables stay dense on their own, and passes now
  end even when a job throws, so there is nothing to compact and nothing to monitor (the ratio was always 0 between
  updates). Delete the calls.
- **`entity.Add<T>()` is gone.** It did what `Set` and `GetOrAdd` do, and reset a component the entity already had,
  unlike adding in other ECS libraries. Write the generated `entity.SetX(…)` (`SetDead()` for a tag) or
  `entity.Set(new T(…))` to add or replace a value, and `ref var c = ref entity.GetOrAdd<T>()` to add a default
  value only when it is missing and fill it through the ref.
- **`world.Systems` is a `SystemList`** (allocation-free `foreach` and `Count`) instead of a new `IReadOnlyList`;
  `foreach` loops compile unchanged.
- **`QueryEnumerator.Count` / `IsEmpty` are gone**: use `world.Count` / `world.Any` with the same filter.
- **`entity.Remove<…>()` returns the entity** for chaining; calls that ignore it compile unchanged.
- **`RemoveSingleton<T>()` returns `bool`** (false when the singleton was not added). Calls that ignore the result
  compile unchanged.

### Behavior changes [#v4-1-behavior]

- **Stale and `default` handles answer questions with false.** `Has<T>()` and `TryGet<T>()` used to throw for a
  destroyed entity (and `default(Entity).Has<T>()` threw a `NullReferenceException`); they now return false, like
  `IsAlive`. `Get`, `GetOrAdd`, `Set` and `Remove` still throw, now `InvalidOperationException` for `default`
  handles too.
- **Structural changes belong to the world's owner thread.** 4.0 serialized creates, destroys, `Add` / `Set` /
  `Remove` and singleton or system changes from any thread with a compare-and-swap lock. 4.1 checks a plain owner
  flag instead: a change made while another runs, or inside a parallel stage of systems or a parallel `[ForEach]`,
  throws `InvalidOperationException`; two threads of your own changing one world at once are not caught reliably.
  Make structural changes on the thread that calls `Update` (other threads hand them over as data through a queue a
  system drains: [input from other threads](/en/docs/guide/threading#input-from-other-threads)), or give each thread
  its own world. Two analyzer errors point at such code: [EECS013](/en/docs/guide/analyzer#eecs013), a structural
  change in a `[ForEach]` method that takes no `Entity` or `World` (for example through a handle a component holds:
  take the `Entity` as a parameter), and [EECS014](/en/docs/guide/analyzer#eecs014), a structural change in a
  lambda handed to `Task.Run`, `Parallel.*`, `ThreadPool` or a `Thread` that races with other changes of the same
  world.
- **EECS007 and EECS008 are errors.** Mutable state in a system ([EECS007](/en/docs/guide/analyzer#eecs007)) and a
  system referencing a system ([EECS008](/en/docs/guide/analyzer#eecs008)) were warnings in 4.0; code that triggers
  them no longer builds. Move the state into a component or singleton, and communicate through data. Every rule of
  4.1 is an error except the warnings EECS017, EECS018 and EECS020 named above.
- **Iteration semantics are stricter.** A pass visits each entity at most once: entities created or moved into a
  matching archetype during the pass are not visited by it (one that only gets a queried component back keeps its
  row and is visited if the pass has not reached it); entities destroyed or losing a queried component before their
  turn are skipped. `Without<T>` filters that only existed to stop a job from revisiting what it produced are no
  longer needed (they still work).
- **Refs move more often.** A `ref` from `entity.Get<T>()` or a `Query` item can now be invalidated by a structural
  change of *another* entity (a row filled by a table's last row, a table that grows), not only by entity-capacity
  growth. The documented rule was already "a ref is valid until the next structural change"; code that relied on
  refs surviving changes must re-read through `entity.Get<T>()`. The `ref` parameters of `[ForEach]` methods and
  `ForEach` jobs stay writable when the body changes the visited entity's archetype. See
  [refs and await](/en/docs/guide/refs-and-await).
- **Removing a component keeps the entity's row.** `Has<T>()`, `Get<T>()` and every query treat the component as
  absent; adding it back is a bit flip.
- **`Query` results are ref structs.** `QueryEnumerator<…>` and `QueryItem<…>` hold refs into the current table, so
  a `foreach` over a query cannot contain an `await` and an item cannot be stored. Read what you need, or keep
  `item.Entity`, then await outside the loop.
- **Iteration order** follows table rows, not entity ids, and can change when rows are moved or filled. Never rely
  on it.
- **`EnsureEntityCapacity` / `InitialEntityCapacity`** pre-size the entity records only; archetype tables grow on
  their own.
- **`ParallelSystems` keeps subclasses it cannot see alone.** A system class that derives from a generated system
  without adding `[ForEach]` methods of its own (for example to override `OnUpdate`) now runs alone (it never shares
  a stage with another system), as its `OnUpdate` may touch anything. Give the subclass a `[ForEach]` method (it is
  then generated) to run it beside others again.
- **`AddSingleton<T>()` on an existing singleton resets it in place.** It used to replace the storage, which left
  `SingletonRef<T>` handles taken before pointing at a detached copy; they now see the reset value.
- **`Entity.GetHashCode()` is deterministic** (`Index ^ (Version << 20)`) instead of `HashCode.Combine` (randomized
  per process). Equality is unchanged; only code that persisted hash codes across processes could notice.

## v3.x → v4.0 [#v3-to-v4-0]

v4 targets **.NET 10 only**, moves the whole API into the `EasyEcs` namespace with standard ECS vocabulary, makes
systems synchronous and generates the repetitive parts (arity overloads, per-entity jobs).

### Namespaces [#v4-0-namespaces]

`EasyEcs.Core`, `EasyEcs.Core.Components` and `EasyEcs.Core.Systems` become one namespace: `using EasyEcs;`.

### Entities and components [#v4-0-entities-and-components]

v3 had three handle types (`Entity` value, `EntityRef`, `ComponentRef<T>`). v4 has one: `Entity`, a version-checked
16-byte handle. Component access returns `ref T` directly. Since 4.1 the generator also writes a named member for
each component (`e.Position`, `e.SetPosition(…)`, `e.HasPosition`), which current code prefers over the generic
calls in this table ([generated members](/en/docs/guide/entities-and-components#generated-members)).

| v3 | v4 |
| --- | --- |
| `Context` | `World` |
| `EntityRef e = ctx.CreateEntity()` | `Entity e = world.CreateEntity()` or `world.CreateEntity(new Position(..), new Velocity(..))` |
| `e.Value.AddComponent<T>().Value.X = 1` | `e.GetOrAdd<T>().X = 1` (`ref T`), or `e.Set(new T(..))` |
| `e.Value.AddComponents<A, B>()` | `e.Set(new A(..), new B(..))` (add or overwrite values, one transition) |
| `e.Value.GetComponent<T>().Value` | `e.Get<T>()` (`ref T`) |
| `e.Value.TryGetComponent<T>(out ComponentRef<T> r)` | `e.TryGet<T>(out T value)` / `ref var x = ref e.GetOrAdd<T>()` |
| `e.Value.HasComponent<T>()` | `e.Has<T>()` |
| `e.Value.RemoveComponent(s)<..>()` | `e.Remove<..>()` |
| `ctx.DestroyEntity(e)` | `e.Destroy()` |
| `ctx.GetEntityById(id)` / `TryGetEntityById` | `world.GetEntity(id)` / `TryGetEntity` |
| `ctx.AllEntities` | `world.Entities` |
| `ctx.GroupOf<T..>()` → `GroupResult` | `world.Query<T..>(filter)` → `QueryItem` (`item.Entity`, `item.Component1..n`) |
| `ctx.CountOf<T..>()` / `AnyOf<T..>()` | `world.Count<T..>(filter)` / `world.Any<T..>(filter)` |
| `new Context(new Context.Options(parallel, levels, capacity))` | `new World(new WorldOptions { ParallelSystems = .., MaxDegreeOfParallelism = .., InitialEntityCapacity = .. })` (parallel is **off** by default) |

### Singletons [#v4-0-singletons]

| v3 | v4 |
| --- | --- |
| `AddSingletonComponent<T>()` / `GetSingletonComponent<T>().Value` | `AddSingleton<T>()` / `GetSingleton<T>()` / `GetOrAddSingleton<T>()` (all `ref T`) |
| `TryGetSingletonComponent<T>(out SingletonComponentRef<T>)` | `TryGetSingleton<T>(out T value)` |

Singletons are now **per world** (v3 shared them process-wide). A `[ForEach]` method takes a singleton as a
`ref` / `in` parameter (resolved once per pass), so systems rarely call `GetSingleton` themselves.

### Systems [#v4-0-systems]

v3 systems implemented `IInitSystem` / `IExecuteSystem` / `IEndSystem` with `UniTask` methods. v4 systems derive
from `EcsSystem` and override synchronous hooks; the UniTask dependency is gone.

```csharp tab="v3" doccheck=skip
public class S : SystemBase, IInitSystem, IExecuteSystem
{
    public UniTask OnInit(Context ctx) { ...; return UniTask.CompletedTask; }
    public UniTask OnExecute(Context ctx) { ...; return UniTask.CompletedTask; }
}
```

```csharp tab="v4"
public partial class S : EcsSystem
{
    // when added to the world
    protected override void OnCreate() { }

    // every update (World property available)
    protected override void OnUpdate() { }

    // per entity, after OnUpdate
    [ForEach] static void Step(ref Position p, in Velocity v) => p = new Position(p.X + v.X, p.Y + v.Y);
}
```

- `ctx.Init()` is gone: `OnCreate` runs when the system is added. `await ctx.Update()` becomes `world.Update()`;
  `await ctx.DisposeAsync()` becomes `world.Dispose()` (`OnDestroy` in reverse order).
- `IExecuteSystem.ExecuteFrequency` becomes `EcsSystem.UpdateInterval`; `AddSystem<T>()` returns the system;
  `GetSystem<T>()` and `Enabled` were added; `RemoveSystem<T>()` now returns `bool` (whether a system was removed).
- Exceptions: `world.SystemError` (system, exception); without a subscriber the exception propagates. (4.1 replaced
  the event, see [v4.0 → v4.1](/en/docs/migration#v4-1-api).)

### Behavioral changes [#v4-0-behavior]

1. **Entity ids are recycled.** `Entity.Id` is unique only among live entities; keep the `Entity` handle (id +
   version). Equality includes the version.
2. **Stale handles are rejected**: access and structural changes throw; `Destroy` of a stale handle is ignored.
3. **Removing a component or destroying an entity releases managed references** held by the component.
4. **Components and singletons must be structs**: the analyzer reports [EECS006](/en/docs/guide/analyzer#eecs006)
   for classes.
5. Never call `CompactArchetypes()` while iterating (it rewrites rows). 4.1 removed it.
6. **Systems should be stateless and independent**: the analyzer warns about mutable fields on systems
   ([EECS007](/en/docs/guide/analyzer#eecs007): move the state into a component or singleton) and about systems
   referencing other systems ([EECS008](/en/docs/guide/analyzer#eecs008): communicate through data). See
   [ECS principles](/en/docs/ecs-principles).
7. **`IEvent`, `IEventHandler<T>` and `Publish` are removed.** Write state changes as data (a tag or a field) and
   let later systems query them.
8. **`ParallelSystems` is safe by construction.** v3 ran every system of one priority at once and left data races to
   you. v4 runs systems of one priority together only when their generated access does not conflict (`ref` = write,
   `in` = read); systems with an `Entity` / `World` parameter, instance `[ForEach]` methods, an `OnUpdate` override
   or no `[ForEach]` method run alone. The result equals a sequential update. See
   [threading](/en/docs/guide/threading#parallel-systems).

## v2.x → v3.0 [#v2-to-v3-0]

v3.0 was a complete redesign around **zero-allocation immediate execution** for high-performance servers: callbacks
and the command buffer are gone, every operation runs at once and returns its result. The code in this section is
v2 and v3 code; none of it compiles against v4.

### Breaking changes [#v3-0-breaking]

**No more callbacks.** v2 deferred every operation and handed the result to a callback; v3 executes at once and
returns it.

```csharp tab="v2" doccheck=skip
context.CreateEntity(entity => {
    entity.AddComponent<Position>(pos => {
        pos.Value.X = 10;
        entity.AddComponent<Velocity>(vel => {
            vel.Value.X = 5;
        });
    });
});
```

```csharp tab="v3" doccheck=skip
var entity = context.CreateEntity();
var pos = entity.AddComponent<Position>();
pos.Value.X = 10;
var vel = entity.AddComponent<Velocity>();
vel.Value.X = 5;
```

| v2 | v3 | Notes |
| --- | --- | --- |
| `void CreateEntity(Action<EntityRef>)` | `EntityRef CreateEntity()` | Returns the entity |
| `void AddComponent<T>(Entity, Action<ComponentRef<T>>)` | `ComponentRef<T> AddComponent<T>(Entity)` | Returns the component ref |
| `void AddComponent<T>(Action<ComponentRef<T>>)` | `ComponentRef<T> AddComponent<T>()` | On the `Entity` struct |
| `void AddSingletonComponent<T>(Action<...>)` | `SingletonComponentRef<T> AddSingletonComponent<T>()` | Returns the ref |
| `void AddSystem<T>()` | `void AddSystem<T>()` | Unchanged (immediate) |
| `void RemoveSystem<T>()` | `void RemoveSystem<T>()` | Unchanged (immediate) |

**Execution model.** v2 queued operations into a command buffer, executed them at the end of the frame and invoked
the callbacks after. v3 executes every operation at once, thread-safe through the .NET 8 `Lock`, with no command
buffer and no callbacks.

**Version tracking.** v3 adds a version to the entity, incremented on destroy. `EntityRef` and `ComponentRef`
validate it on access and throw if the entity was destroyed.

```csharp doccheck=skip
public struct Entity
{
    public readonly int Id;
    public readonly int Version;  // new: increments on destroy
    // ...
}
```

### Modifying components and holding refs [#v3-0-refs]

Components are structs. Write through the `ComponentRef` (`health.Value.HP = 100`) or through
`ref var h = ref health.Value`; `var h = health.Value` copies the component, and the changes to the copy are lost.

A `ref` stays valid only until the component arrays are resized. Component data lives in
`Context.Components[typeIndex][entityId]`, and only `CreateEntity` (when the capacity is exceeded) resizes those
arrays, so a `ref` held across `CreateEntity` may dangle and crash or read the wrong data. `AddComponent`,
`RemoveComponent` and `DestroyEntity` only change which archetype list an entity belongs to, and
`CompactArchetypes` only removes tombstones from the archetype lists: none of them moves component data, so refs
survive them (destroying the entity whose component a `ref` points at is still a logic error). Singletons are
stored apart and are not affected by `CreateEntity` or `CompactArchetypes`.

```csharp doccheck=skip
var health = entity.AddComponent<Health>();
ref var h = ref health.Value;
h.HP = 100;                  // safe
context.CreateEntity();      // may resize every component array
h.HP = 50;                   // unsafe: h may point to the old array
health.Value.HP = 50;        // safe: the ComponentRef finds the current location
```

During `GroupOf` iteration, `DestroyEntity`, `AddComponent` and `RemoveComponent` are safe (tombstones handle
them); `CreateEntity` leaves the iterator working but invalidates `ref` locals, so read through
`result.Component1.Value` when the loop creates entities; `CompactArchetypes` breaks the iterator itself and must
run outside the loop. Rule of thumb: when unsure, write `compRef.Value.field`, and keep `ref` for short local code
that creates no entity.

Adding a component or a singleton the entity or context already has erases its data (the component is
reinitialized to default). Check first:

```csharp doccheck=skip
if (!entity.TryGetComponent<Health>(out var health))
{
    health = entity.AddComponent<Health>();
}
health.Value.HP = 100;
```

### Thread safety [#v3-0-threads]

v2's command queue was thread-safe and the callbacks ran on the main thread at the end of the frame. In v3 every
operation is thread-safe through the .NET 8 `Lock`, entity id allocation is lock-free (`Interlocked`), and several
threads can create and modify entities at once:

```csharp doccheck=skip
Parallel.For(0, 1000, i => {
    var entity = context.CreateEntity();
    entity.AddComponent<Position>();
});
```

v4.1 changed this: structural changes belong to the world's owner thread (see
[v4.0 → v4.1](/en/docs/migration#v4-1-behavior)).

### What changed for performance [#v3-0-performance]

v2 allocated a closure on every `CreateEntity` call and four on every `AddComponent` call, so a world that kept
creating entities kept producing garbage. v3 allocates nothing after warm-up: its arrays are allocated up front and
grow only once, with no closures. The rest of the hot path changed too:

| Operation | v2 | v3 |
| --- | --- | --- |
| Tag bitwise operations | scalar operations | one SIMD instruction |
| Archetype queries | a scan of every archetype | a cached match |
| Bounds checks | on every access | removed behind invariants (`Unsafe`) |

For what EasyEcs measures today, see [performance](/en/docs/performance).

Iteration became safe to modify: v2 had undefined behavior when an entity changed during iteration (entities could
be skipped or visited twice); v3 marks removed slots with a tombstone (-1) and reads a fresh span after a resize, so
the behavior is predictable.

### New in v3.0 [#v3-0-new]

- **Cross-platform SIMD**: AVX2 on x86 / x64, AdvSimd (NEON) on ARM, a scalar fallback elsewhere.
- **Up to 65,536 component types** (the component index became a `ushort` instead of a `byte`): the first 256 inline
  (32 bytes, two `Vector128`), the rest in an overflow array.
- **Archetype query cache**: the first `GroupOf` of a shape builds the cache in O(N), later ones look it up in O(1).
- **Manual defragmentation**: `GetFragmentationStats()` returns `(totalSlots, alive, ratio)`, and
  `CompactArchetypes()` removes the tombstones (during loading screens, for example when the ratio passes 0.5).
- **Pre-allocation**: `new Context(new Context.Options(parallel: true, levelOfParallelism: -1, initialEntityCapacity: 10_000))`
  (`-1` uses all cores), and `context.EnsureEntityCapacity(100_000)` later.

### Performance tips for v3 [#v3-0-tips]

- Pre-allocate the entity capacity: `context.EnsureEntityCapacity(expected)`.
- Check fragmentation and compact between levels, outside any `GroupOf` loop: `CompactArchetypes()` invalidates
  `GroupOf` iterators but not component refs.
- Add and remove components with `AddComponents` / `RemoveComponents`: one archetype transition instead of three.
- Run systems in parallel: `new Context(new Context.Options(parallel: true))`.
- Create entities in a plain loop: the lock is taken once per operation.
- Modify components in place: `result.Component1.Value.X += 1`, or a `ref` local when the loop creates no entity.

### Troubleshooting v3 [#v3-0-troubleshooting]

| Symptom | Cause | Fix |
| --- | --- | --- |
| "Entity has been destroyed" exception | A stale `EntityRef` / `ComponentRef` used after the entity was destroyed; versioning detects it | Do not cache refs across frames; look the entity up again with `context.TryGetEntityById(id, out var entity)` |
| Tests fail after the upgrade | Assertions inside callbacks | Create the entity, then assert: `var entity = context.CreateEntity(); Assert.NotNull(entity);` |
| Component changes do not persist | The component value was copied to a local (structs) | Write `health.Value.HP = 100`, or through `ref var h = ref health.Value` |
| Crash or corrupted data with `ref` | A `ref` held across `CreateEntity`, which may resize the arrays | Keep the `ComponentRef` and write through `.Value`; `AddComponent`, `RemoveComponent` and `CompactArchetypes` are safe with refs |
| Iteration behaves differently | v3 skips tombstones of entities added or removed during iteration | Usually nothing: iteration is safe now |

In short: remove every callback, use the returned values, and expect every operation to run at once, thread-safe and
without allocations after warm-up. For questions, open an
[issue on GitHub](https://github.com/JasonXuDeveloper/EasyEcs/issues).
