Actors on an ECS world: entities that answer messages addressed to their key, each kind of actor with its own
systems, loaded from storage when first needed and saved only when they change. A shop sells until it runs out and
closes; a bank pays interest. Every code block on this page is included from
[`samples/Actors`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Actors), which CI builds and runs,
comparing its output with the one shown below. Read the [GameLoop](/en/docs/samples/game-loop) and
[SaveLoad](/en/docs/samples/save-load) samples first.

## What you learn [#what-you-learn]

- **One type per kind of actor**: `Shop` and `Bank` implement one interface, `IActor<TSelf>`, and so are at once the
  actor's key component ([value index](/en/docs/guide/indexes-and-relations#value-indexes)), the
  [system group](/en/docs/guide/systems#system-groups) of the kind and that group's
  [filter](/en/docs/guide/systems#group-filters) (`ISystemGroupWith<In<Shop>>`).
- **A message is a job on one entity**: [`entity.Run(ref job, filter)`](/en/docs/guide/queries#run-on-one-entity)
  gives the job its components in one lookup, refuses a closed shop through a `static readonly` filter, and keeps
  the job's refs valid when the job closes the shop in the middle.
- **Activation and records**: an actor's entity is made when it is first needed, and its
  [record](/en/docs/guide/migration-and-unload#records) is loaded onto it with
  `LoadEntitiesInto(..., markWritten: false)`, so loading is not a change.
- **Save what changed**: the persistent components are `ITracked`
  ([change tracking](/en/docs/guide/change-tracking)); the host saves only the actors written since its last save.

## Run it [#run-it]

```bash
dotnet run --project samples/Actors
```

## The data [#data]

An actor kind is one type that does three jobs through one interface. The key is implemented explicitly
(`Shop IIndexed<Shop>.Key => this;`): a public `Key => this` property on a record struct would make its
`ToString()` print `Key` forever. `Stock` and `Balance` persist; `Sales` and `Closed` live only in memory.

## Messages [#messages]

`Buy` and `Deposit` are jobs; `Mailman` finds the actor by key in its index and runs the job on it. A `Buy` that
sells the last item adds `Closed` in the middle of the job: a structural change, and the job's refs still point at
the shop's values.

## Activation [#activation]

`Activate` returns the active actor, or makes one from the kind's prefab and loads its record. A new actor has no
record: its defaults are its first state, and the next save writes them.

## Output [#output]

```text
activated: shop 1 has 2, shop 2 (new) has 5, bank 7 has 1000
saved after activation: 1
buy 1 at shop 1: sold, 1 left, closed: False
buy 1 at shop 1: sold, 0 left, closed: True
buy 1 at shop 1: refused, 0 left, closed: True
deposit 50 at bank 7: True
deposit 50 at bank 8: False
after the updates: shop 1 has 3 (sold 2), bank 7 has 1060
saved after the messages: 3
restarted: shop 1 has 3 (sold 0), bank 7 has 1060
```

Only the new shop is saved after activation: the two records loaded with `markWritten: false` are not changes. The
third order is refused by the filter (the shop closed on the second one), and bank 8 was never activated. After the
restart the shop has its saved stock but no sales: `Sales` lives only in memory.
