Actors on an ECS world: entities that answer messages addressed to their key, each kind of actor with its own
systems, loaded from storage when first needed and saved only when they change. A shop sells until it runs out and
closes; a bank pays interest. Every code block on this page is included from
[`samples/Actors`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Actors), which CI builds and runs,
comparing its output with the one shown below. Read the [GameLoop](/en/docs/samples/game-loop) and
[SaveLoad](/en/docs/samples/save-load) samples first.

## Run it [#run-it]

```bash
dotnet run --project samples/Actors
```

## The data [#data]

An actor kind is one type that does three jobs through one interface: `Shop` and `Bank` implement `IActor<TSelf>`, and
so are at once the actor's key component ([value index](/en/docs/guide/indexes-and-relations#value-indexes)), the
[system group](/en/docs/guide/systems#system-groups) of the kind and that group's
[filter](/en/docs/guide/systems#group-filters) (`ISystemGroupWith<In<Shop>>`): an attribute cannot name a type
parameter, so the interface declares the filter once for every kind. The key is implemented explicitly
(`Shop IIndexed<Shop>.Key => this;`): a public `Key => this` property on a record struct would make its
`ToString()` print `Key` forever. `Stock` and `Balance` persist and are `ITracked` ([change tracking](/en/docs/guide/change-tracking)); `Sales` and
`Closed` live only in memory.

## Messages [#messages]

A message is a job on one entity: `Buy` and `Deposit` are jobs, and `Mailman` finds the actor by key in its index and
runs the job on it with [`entity.Run(ref job, filter)`](/en/docs/guide/queries#run-on-one-entity), which gives the job
its components in one lookup and refuses a closed shop through a `static readonly` filter. A `Buy` that sells the
last item adds `Closed` in the middle of the job: a structural change, and the job's refs still point at the shop's
values. `Mailman` reads the stock before it runs a `Buy`: the job's `WriteMask` stamps `Stock` whenever
the job runs, so a refused order that ran it would make the next save store an unchanged shop.

## The systems of each kind [#systems]

Each system belongs to the group of its kind, so `world.Update<Shop>()` runs the shop systems over the shops only.
`InterestSystem` writes through [`Mut<Balance>`](/en/docs/guide/change-tracking#set-if-changed): `SetIfChanged`
stamps only a balance that grew.

## Saving what changed [#saving]

The save group has one system, over every kind of actor. Its `[Changed<T>]` methods select the rows written since it
last ran, so each run lists the actors written since the previous save, and its own run is the mark. Saving a record
rewrites tables, which a pass refuses ([EECS041](/en/docs/guide/analyzer#eecs041)), so the system lists the actors in
the `Unsaved` singleton and the host saves them after `world.Update<Saving>()`.

## Activation [#activation]

`Activate` returns the active actor, or makes one from the kind's prefab and loads its
[record](/en/docs/guide/migration-and-unload#records) (a `ComponentSet` of the persistent components) onto it with
`LoadEntitiesInto(..., markWritten: false)`, so loading is not a change. A new actor has no
record: its defaults are its first state, and the next save writes them.

## The program [#program]

Activations, messages, the group updates, saves and a restart. The storage is a dictionary standing in for a

## Output [#output]

```text
activated: shop 1 has 2, shop 2 (new) has 5, bank 7 has 1000
saved after activation: 1
buy 1 at shop 1: sold, 1 left, closed: False
buy 1 at shop 1: sold, 0 left, closed: True
buy 1 at shop 1: refused, 0 left, closed: True
deposit 50 at bank 7: True
deposit 50 at bank 8: False
after the updates: shop 1 has 3 (sold 2), bank 7 has 1060
saved after the messages: 2
restarted: shop 1 has 3 (sold 0), bank 7 has 1060
```

Only the new shop is saved after activation: the two records loaded with `markWritten: false` are not changes. The
third order is refused before its job runs (the shop sold out on the second one and closed), and bank 8 was never
activated. After the messages shop 1 and bank 7 are saved; shop 2, saved after activation and not written since, is
not. After the restart the shop has its saved stock but no sales: `Sales` lives only in memory.
