A server splits its game into zones (maps, rooms, matches) that share nothing, and gives each zone a world of its
own on a thread of its own. Here every zone is the same small game of 20,000 units, and there is one zone per
processor, all updated at once. Every code block on this page is included from
[`samples/MultiWorld`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/MultiWorld), which CI builds
and runs.

## Run it [#run-it]

```bash
dotnet run -c Release --project samples/MultiWorld                    # 1000 updates per zone
dotnet run -c Release --project samples/MultiWorld -- --updates 200
```

## The data [#data]

Three components of a unit and the zone's `Tally` [singleton](/en/docs/guide/singletons): singletons are per world,
so each zone counts the deaths of its own world only.

<include lang="csharp" meta='title="Components.cs"'>../../../samples/MultiWorld/Components.cs</include>

## The systems [#systems]

Units move by their velocity; those farther than the safe radius from the centre lose one health per tick, and the
dead come back at the centre. Each [system](/en/docs/guide/systems) has one job and reads and writes components only,
so the same three systems serve every zone. `MoveSystem` is the hot loop of every zone, so it is a
[batch method](/en/docs/guide/systems#batch-methods): one call per run of rows, the positions and velocities read as
`Vector<float>` lanes.

<include lang="csharp" meta='title="Systems.cs"'>../../../samples/MultiWorld/Systems.cs</include>

## One zone [#zone]

`Zone.Run` is everything one thread does: build a world, create the units with one `world.CreateEntities` call,
update it, report a `ZoneResult`, and dispose the world. No other thread ever sees it, so nothing is locked and
nothing is shared ([one world per thread](/en/docs/guide/threading#recommended-one-world-per-thread)).

<include lang="csharp" meta='title="Zone.cs"'>../../../samples/MultiWorld/Zone.cs</include>

## The program [#program]

One thread per processor, each running one zone and writing only its own slot of the results; the main thread waits
for all of them and prints.

## Output [#output]

On a 4-core machine. The deaths are the same on every run; the times and the throughput depend on the machine.

```text
zone  0: 20,000 units,  51,430 deaths,  169.3 ms
zone  1: 20,000 units,  51,428 deaths,  188.4 ms
zone  2: 20,000 units,  51,429 deaths,  165.6 ms
zone  3: 20,000 units,  51,426 deaths,  150.6 ms
4 worlds on 4 threads, 80,000 units, 1000 updates each
253 ms, 316.2 M entity-updates/s
```

The zones differ only by their starting directions, so their deaths differ by a few; the time of the whole run is
close to the time of one zone, because the zones run side by side. This is a demonstration, not a measurement: CI
runs the sample without comparing its output, and the numbers come from the BenchmarkDotNet suite
(`MultiWorldBenchmark`, see [performance](/en/docs/performance)).
