A server splits its map into zones and gives each zone a world of its own on a thread of its own: every core busy,
nothing shared, no locks. But a map has borders, and a unit standing next to one must still see the units beyond it.
Here four zones lie side by side along a strip of 8,000 units. Between two updates the zones exchange their border
rows: each unit within sight of a border is copied into the neighbor zone as a read-only **ghost row**, and each unit
that walked over a border moves to the zone it now stands in. The program then runs the same map as one world and
checks that the zones counted the same sightings. Every code block on this page is included from
[`samples/MultiWorld`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/MultiWorld), which CI builds
and runs.

<Callout type="info" title="Ghost rows and halos">
  The idea comes from MPI codes that split a grid over processes: each process keeps a copy of the cells along its
  neighbors' edges (**ghost cells**, the **halo**) and refreshes them by a **halo exchange** between two steps. A
  ghost row is the same for entities: a copy of a neighbor's row, read here, written only by its owner.
</Callout>

## Run it [#run-it]

```bash
dotnet run -c Release --project samples/MultiWorld                    # 200 updates
dotnet run -c Release --project samples/MultiWorld -- --updates 50
```

## The data [#data]

A unit is a `Position` and a `Velocity`. A ghost is a `Position` and the `Ghost` tag, nothing more: it carries what the
neighbors read and no `Velocity`, so the systems that move units never write it. The zone's `Tally`
[singleton](/en/docs/guide/singletons) counts the sightings of its own world only.

## The systems [#systems]

`SightSystem` counts, for every unit of the zone, the units within sight. It is a pair method: its `[Neighbor]`
parameter makes the generator write the neighbor search from the distance test, and the neighbors are every entity
with a `Position`, so the ghosts are seen like the zone's own units. `[Without<Ghost>]` keeps the ghosts from
looking: what a ghost sees is counted by the zone that owns it. `MoveSystem` and `BounceSystem` read and write units
only, by their `Velocity`. Each [system](/en/docs/guide/systems) has one job and knows nothing of zones, so the same
three serve every zone and the map as one world.

## The map and one zone [#zone]

`Map` says where the zones are and where each unit starts. `Zone.Create` builds one zone's world with the three
systems, sight first so that it reads what the last exchange left; `Zone.Run` updates it and waits at the exchange
after every update. Between two exchanges only its thread touches the world
([one world per thread](/en/docs/guide/threading#recommended-one-world-per-thread)).

<include lang="csharp" meta='title="Zone.cs"'>../../../samples/MultiWorld/Zone.cs</include>

## The border [#border]

`Border.Exchange` runs while every zone waits, so the one thread that runs it may touch every world; it is host code,
since a system belongs to one world and the border to two. It throws away the last ghosts (`DestroyAll<Ghost>`),
moves each unit that crossed into the zone it stands in with
[`MoveEntities`](/en/docs/guide/migration-and-unload#move-entities) (every component goes with it), then copies each
unit within sight of a border into the neighbor zone as a ghost. The ghosts are new entities at every exchange: hold
on to a ghost's position, never to its id.

<include lang="csharp" meta='title="Border.cs"'>../../../samples/MultiWorld/Border.cs</include>

## The program [#program]

One thread per zone. A `Barrier` stops them after each update and runs the exchange on the last thread to arrive,
then lets them all go on. The main thread waits for them, prints each zone, then runs the map as one world.

## Output [#output]

The same on every run and every machine: the zones and the one world count the same sightings, and the process exits
with 1 if they do not.

```text
zone 0: 1,803 units,  79 ghosts,   357 arrivals,  3,377,596 sightings
zone 1: 1,999 units, 158 ghosts,   915 arrivals,  3,795,928 sightings
zone 2: 1,998 units, 161 ghosts,   914 arrivals,  3,806,712 sightings
zone 3: 2,200 units,  81 ghosts,   558 arrivals,  4,163,422 sightings
4 zones on 4 threads: 15,143,658 sightings in 200 updates
one world:            15,143,658 sightings
the zones saw what one world sees
```

The middle zones hold about twice the ghosts of the end ones, since they have two borders. Without the ghosts the
zones would miss the sightings across a border, and the last line would say so. This is a demonstration, not a
measurement: the speed of worlds side by side comes from the BenchmarkDotNet suite (`MultiWorldBenchmark`, see
[performance](/en/docs/performance)).
