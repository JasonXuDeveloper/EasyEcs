一个仿 Minecraft 服务器的方块世界：每秒 20 tick；玩家周围加载区块，走远后存进区域文件，玩家回来时再读回；水按 Minecraft
的规则扩散和退去，站在水里的东西会被冲走；挖下的方块变成掉落物，谁走过都能捡；僵尸夜里出现，追它看见的玩家，白天在露天会着火；
只把变了的东西发给客户端；服务器停机时存档。50 个 bot 玩一分钟游戏时间。本页所有代码都直接引用自
[`samples/VoxelServer`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/VoxelServer)。CI 会构建并运行它，
拿输出和下面的结果逐行比对。

它写的是服务器，但里面没有一处只属于服务器：同一个 World 也能放在客户端。客户端跑同样的区块、水和刚体，在服务器的包到达之前先预测；
每个 tick 之后，渲染层读位置和方块画出来。见[客户端与服务器](#client-and-server)。

## 运行 [#run-it]

```bash
dotnet run -c Release --project samples/VoxelServer                      # 50 个 bot，一分钟游戏时间
dotnet run -c Release --project samples/VoxelServer -- --players 2000    # 一大群人
dotnet run -c Release --project samples/VoxelServer -- --realtime        # 像原版服务器一样每秒 20 tick
dotnet run -c Release --project samples/VoxelServer -- --schedule        # 系统的运行顺序
```

## 数据 [#data]

先是方块、区块和它的水，然后是会动的东西、玩家、僵尸和掉落物，最后是单例。注释说明每个值的含义和谁来写。区块是实体：它的键 `Chunk` 是
[唯一索引](/zh/docs/guide/indexes-and-relations#unique-keys)（`world.ChunkIndex`），8,192 个方块和对应的水是两个字节缓冲，
高度图和水的流向是另外两个，由区块从前两个算出来。

<include lang="csharp" meta='title="Components.cs"'>../../../samples/VoxelServer/Components.cs</include>

时间也是数据：僵尸的 `Cooldown` 和 `Burning` 记着它们结束的 tick，掉落物的 `Dropped` 记着它掉下的 tick，所以没有什么要每个 tick 倒数。
每个 tick 给每个实体加一减一的值，是系统在白干活；结束的 tick 写一次，到用的时候比较一下就够了。

规则是常量和几个纯函数；地形负责方块的位置、区块的生成，以及所有系统共用的读取。`Nearby` 读取一个物体周围的方块、水和高度图：
它在唯一索引里查一次物体所在的区块，之后同一区块的方块直接从缓冲读，所以物理每个物体只查一次，而不是每个方块查一次；
“这个方块上面是不是天空”也只是读高度图的一个字节，不用扫一整列。未加载的区块读出来是石头，所以什么都不会掉出世界。

## 玩家周围的区块 [#chunks]

玩家需要的区块由下面的 [`InterestSystem`](#interest) 请求，记成 `LoadRequest` 实体，每个区块一个：请求是 `IUniqueIndexed`，
第二个要它的玩家能找到它，就不再重复请求。遍历期间不能加载或保存实体（EECS041），所以由 `ChunkReadSystem` 在遍历之后的
`OnUpdate` 里处理这些请求，每个 tick 最多 `Rules.MaxRequests` 个，只销毁处理过的，其余的等下一个 tick。卸载过的区块用
`LoadEntities` 从区域文件读回，里面的僵尸和掉落物也一起回来；从没见过的区块就生成，方块和水各用一次 `AddRange` 写进缓冲。
不管哪种，它都一次拿到以后每个区块都有的东西：`Viewers`；这个 tick 的 `Fresh` 标签（客户端整块收到它，而不是收到方块变化）；
`Flowing`（它的水走一步）；以及存档里没存的高度图和流向。

<include lang="csharp" meta='title="Systems/Chunks.cs"'>../../../samples/VoxelServer/Systems/Chunks.cs#load</include>

区块创建时就带上它以后会有的所有组件和标签，`Flowing` 也在内，这是有原因的：表里已经有列的组件，来去只是翻一个
[存在位](/zh/docs/guide/structural-changes#during-a-pass)，区块留在原来的表里。第一次加上的标签会把实体搬到另一张表，
而遍历不会访问开始之后才加入匹配表的实体：一个系统要是唤醒正在访问的区块旁边的区块，遍历就会漏掉其中一些。

卸载是反过来的同一套做法。区块的 `Viewers` 记着视野里有它的玩家数，由 `InterestSystem` 随视野变化增减，并记下它最近一次归零的 tick。
`Slices = 20` 让每个 tick 检查二十分之一的区块，五秒都没人看着的打上 `Unloading` 标签；`ChunkSaveSystem` 再把每个区块连同其中的实体
写成一条记录并销毁，所以没有玩家的地方什么都不跑。`SaveEntitiesWithout` 不存高度图和流向，加载后的区块会重新算。
有玩家站着的区块（比如刚在那里重生的玩家）不会卸载。区域文件是一个装着类的单例；
[`Host/RegionFiles.cs`](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/VoxelServer/Host/RegionFiles.cs)
代替磁盘，用的是从共享 `ArrayPool` 租来的数组。

<include lang="csharp" meta='title="Systems/Chunks.cs"'>../../../samples/VoxelServer/Systems/Chunks.cs#unload</include>

## 每个客户端拥有什么 [#interest]

客户端拥有它的玩家周围那个正方形里已加载的区块，以及其中的实体。两者是同一件事：兴趣（interest），由一个系统 `InterestSystem` 维护。
视野是以玩家的 `ViewCenter` 为中心的一个正方形区块范围，所以它是一个值，不是一串区块；不管发生什么，客户端多出和少掉的
都是两个正方形的差：走进下一个区块是一行宽的一条区块，重生则是整个正方形。

| 发生了什么 | 客户端收到什么 | 方法 |
| --- | --- | --- |
| 玩家跨进另一个区块，或出现 | 多出的那条区块整块发送，带着其中的实体（没加载的记成 `LoadRequest`）；少掉的那条让客户端忘掉 | `Look`，`[With<Player>, Changed<InChunk>]` |
| 实体跨进另一个区块，或刚被创建 | 看得见新区块、看不见旧区块的玩家收到出现包，反过来的收到消失包 | `Moved`，`[Changed<InChunk>]` |
| 一个区块加载完 | 区块和其中的实体，发给周围的玩家 | `Loaded`，`[With<Fresh>]` |
| 实体被销毁，玩家离开 | 看得见它所在区块的玩家收到消失包；离开的玩家的视野被释放 | `Gone` 和 `Left`，`[With<Retired>]` |

谁看得见一个区块是数出来的，从不搜索：每个玩家的视野都是 `Rules.PlayerVision`，所以看得见一个区块的玩家，就是以它为中心的正方形里的
视野中心；`ViewCenter` 带索引，`world.ViewCenterIndex.Count(chunk)` 以 O(1) 数出中心落在某个区块的玩家。一次跨区块只访问两个正方形之间
的那一条，五个区块，每个区块的 `Viewers` 跟着增减，每个 tick 都准确。待在原区块的实体和玩家在这里没有任何开销，不管过多少个 tick。

<include lang="csharp" meta='title="Systems/Interest.cs"'>../../../samples/VoxelServer/Systems/Interest.cs#interest</include>

每种变化本来就是数据。`InChunk` 是一个带索引的组件，挂在所有会动的东西上，所以 `world.InChunkIndex.Find(chunk)` 列出一个区块里的实体，
`Count(chunk)` 数出它们。`GridSystem` 让它保持最新：`[Changed<Position>]` 只访问这个 tick 移动过的实体，`SetInChunkIfChanged`
只在实体跨进另一个区块时才写，所以 `InterestSystem` 和所有响应 `[Changed<InChunk>]` 的系统每秒只看到几次跨区块，而不是每个 tick 都有。

<include lang="csharp" meta='title="Systems/Movement.cs"'>../../../samples/VoxelServer/Systems/Movement.cs#grid</include>

跨区块时要知道客户端原先在哪个区块看见这个实体；被销毁的实体也要知道，而那时它的组件已经没了。`Visible` 记着这个区块，它是一个
[清理组件](/zh/docs/guide/cleanup-and-disable)：销毁带清理组件的实体时，实体会退休而不是消失，只留下清理组件，直到某个系统去掉最后一个。
`ViewCenter` 也是清理组件，所以离开的玩家会一直处于退休状态，直到它的视野被释放。

僵尸在自己的 `Vision` 范围内追人，35 格（Minecraft 里它的追踪距离）：每个预制体设置自己的，视野更远的 Boss 只是多一个预制体，不用写新代码。

<include lang="csharp" meta='title="Program.cs"'>../../../samples/VoxelServer/Program.cs#prefabs</include>

`ZombieTargetSystem` 通过视野中心的索引找最近的玩家（这个索引里只有玩家），只要玩家还在范围内就一直追它，就像原版的怪物保留目标一样。它每秒看两次，
每个 tick 只看十分之一的僵尸（`Slices`），所以尸潮再大，每个 tick 的开销也一样。

<include lang="csharp" meta='title="Systems/Zombies.cs"'>../../../samples/VoxelServer/Systems/Zombies.cs#target</include>

在 ECS 里，“谁在谁附近”的常规答案是一个从格子到其中实体的索引，由移动它们的系统维护，由需要邻居的系统读取。
这里的格子是区块，因为区块本来就是加载的单位，也是客户端拥有的单位。

## 水 [#water]

水不是一种方块，而是方块旁边的第二个网格：每个方块一个字节的 `DynamicBuffer<Fluid>`。方块一变，不管是谁改的，`BlockUpdateSystem`
都会从方块缓冲的变化看到，所以挖掘本身不用知道水，也不用知道天空。它先算区块的高度图，16 个向量，每个 16 列：从下往上，
每一层把方块实心的通道改写成这一层的高度，32 层走完，每个通道就是它那一列的顶，没有分支。然后唤醒这个区块和四个邻居的水（`Flowing`）。

<include lang="csharp" meta='title="Systems/Water.cs"'>../../../samples/VoxelServer/Systems/Water.cs#wake</include>

规则是 Minecraft 的简化版（两个泉眼之间不会生出新水源，水向四面扩散而不是流向最近的落差）：水下面的空格变成下落的水；水旁边、脚下踩着实心方块的空格，水位比它低一级；其余的都变空，所以泉眼没了水就会退。
它照片元着色器的写法写：`Shade` 只从一个方块自己和六个邻居的水位算出它的下一个水位，别的都不看；一次算 16 个方块，即区块的一行，
一个 `Vector128<byte>`。

为什么按区块算，而不是整个世界一个网格？水随区块加载、存档和下发，而且只有还可能变的区块才走一步：静止的湖不会再被访问。
所以着色器运行之前，先把区块复制进一张带填充的纹理：它的水和方块，外加四周区块一格宽的一圈，着色器采样这张纹理就没有边界情况。
只复制和计算水够得着的那几层（两次向量化搜索 `IndexOfAnyExcept` 找出它们）。字节通道是整数运算：每台机器上的水都一样。

这一步写进第二个缓冲 `NextFluid`，就像 GPU 交替使用两个缓冲；等所有区块都走完，`WaterCommitSystem` 再把它拷成水：
每个区块都用邻居这一步之前的水来算，与区块的访问顺序无关。同一次遍历还写下每个方块的 `Current`，即水朝周围更低的水倾斜的方向，
存成两层字节；并数出区块里的水（`FluidCount`，一次向量化的 `Count`）。两个缓冲都原地写：`SetCount` 定好大小，着色器直接写
`AsSpan()`，不用从栈上拷贝。一步下来什么都没变，就去掉 `Flowing`。

<include lang="csharp" meta='title="Systems/Water.cs"'>../../../samples/VoxelServer/Systems/Water.cs#flow</include>

`FloatSystem` 把站在水里的东西（玩家、僵尸和掉落物）托起来，顺着所在方块的流向推走，水位越低推得越弱：泉眼旁边或下落的水里是全力，
水流末端只有八分之一。它遍历区块，按 `FluidCount` 跳过干的区块，其余的通过按区块索引的实体找到其中的物体，所以物体所在区块的水
就是循环自己这一行：读一次水位、一次流向，不用查找。

<include lang="csharp" meta='title="Systems/Water.cs"'>../../../samples/VoxelServer/Systems/Water.cs#float</include>

## 移动 [#movement]

行走把输入变成速度。每一行只依赖它自己，方法也不持有 `World`，所以是并行方法；运行器会给拆分计时，只在它让遍历更快时才保留。

<include lang="csharp" meta='title="Systems/Movement.cs"'>../../../samples/VoxelServer/Systems/Movement.cs#walk</include>

物理让每个物体在方块间移动，通过 `Mut<Position>` 写位置：`SetIfChanged` 只在位置变了时才给这一行打 tick，所以站着不动的物体不会被下发。
静止的物体（站在地上、没有速度、脚下仍有地面）查一次方块就跳过。它留在单线程，因为它通过 `World`（区块索引）读方块，
而并行方法不能持有 World（EECS010）。水和浮起也一样，它们读周围的区块。

## 挖掘与掉落物 [#items]

挖一下，方块变成空气和一个掉落物（像 Minecraft 一样，草变成泥土），挖的人 `Score` 加一（见[排行榜](#leaderboard)）。
缓冲通过 `chunk.Block[slot]` 读、`chunk.WriteBlock()` 写，所以只有挖掘会给区块打 tick，周围的水也是通过这次打 tick 被唤醒的。

<include lang="csharp" meta='title="Systems/Items.cs"'>../../../samples/VoxelServer/Systems/Items.cs#dig</include>

过了拾取延迟，掉落物归站在它上面的任何玩家，通过视野中心的索引找到。同类的堆先长满，空格子装剩下的，装不下的留在地上。
先读背包再写，所以背包满了不会被打 tick。掉落物记着它掉下的 tick（`Dropped`），这个组件带有序索引，所以 `ItemExpirySystem`
用 `DroppedIndex.Range(...)` 从最早的掉落物开始走，遇到第一个还没到期的就停：一个 tick 只访问到期的掉落物，而不是所有掉落物。

`[Changed<Health>]`，只访问上次运行以来被写过的血量，也就是刚被打或被烧的实体，而不是每个 tick 遍历所有实体。`Mut<T>` 只为重生的玩家写血量、位置和背包。

## 数据是网格或一列时用 SIMD [#simd]

这个服务器里有三种数据适合 SIMD：

- **带着色器的网格**：就是上面的水。每个方块的下一个水位和流向都是它邻居的同一个函数，网格又是字节缓冲，所以一条指令算 16 个方块。
- **沿一个轴归约的网格**：高度图，256 列各自的顶，一条指令算 16 列，每层一次 `ConditionalSelect`，没有分支。
- **一列相同的变化**：火焰伤害（按它自己的 [`UpdateInterval`](/zh/docs/guide/systems#update-interval)）给每只着火的僵尸扣一点血。
  [批量方法](/zh/docs/guide/systems#batch-methods)把一段连续的行当成 span 拿到，`Vector<int>` 在 AVX2 上一条指令改
  8 个（Arm 上 4 个）。JIT 不会自己把这些循环向量化，所以方法里手写；整数通道在每台机器上结果都一样。

搜索和计数字节由 .NET 自己向量化：`IndexOfAnyExcept` 找出有水的层，`Count` 数出一个区块里的水。计时器不在其中：冷却、
掉落物的存在时间和着火都是它们结束的 tick，所以根本没有要倒数的列，向量化与否都谈不上。

其他系统对每个实体做的事都不一样：物理查每个物体周围的方块，找目标遍历索引，追击读另一个实体的位置。查找加分支的循环用向量帮不上忙，
而位置是 `Vector3`，三个挨着的 float，不是三列。批量方法也只在一个线程上跑（EECS010），提速靠的是向量循环，不是多线程。

## 自动排好序的排行榜 [#leaderboard]

## 和原版服务器的区别 [#vanilla]

- 一天 30 秒，掉落物存在 15 秒，着火扣血的频率是原版的四倍，这样一分钟的运行就能全看到。
- 服务器根据玩家的输入移动玩家；原版服务器信任客户端的移动再做校验。
- 同一个距离决定玩家周围加载和模拟哪些区块，以及它看见哪些实体：它那些区块里的实体。原版服务器按实体种类的范围追踪每个实体，每个 tick 检查。
- 没有刷怪上限、光照等级、远处怪物消失、心跳，也没有玩家加入或离开。

## 没用到的功能，以及原因 [#not-used]

- **按区块 `GroupBy`**。按区块拆表能让“一个区块里的实体”在内存里连续，但实体每跨一次区块，它的行就要搬到另一张表，
  每个走动的实体每秒都要搬好几次。`InChunk` 索引在跨区块时只更新一次索引，别的什么都不花。
- **用清理组件在卸载时保存区块**。退休的实体会失去其他组件，缓冲也在其中，到那时已经没东西可存了。区块在销毁之前保存。
  （消失包倒是靠一个清理组件 `Visible` 发的：它要留住的只是一个区块位置。）
- **用销毁日志下发消失**。日志里只有被销毁实体的 id 和时间，没有它在哪里，而消失包要发给看得见它所在区块的玩家。`Visible` 正好把区块留到需要的时候为止。
- **给每个玩家存一份区块或实体集合**。客户端拥有的是它视野中心周围那个正方形里的区块和其中的实体，每人一份集合只是重复正方形和网格，
  还要在附近每次跨区块时都改写：一千人的人群里，每次跨区块就要改一千份。视野中心和索引以 O(1) 数出同样的东西。
- **每个计时器一个计数器**。冷却、着火或掉落物的存在时间每个 tick 倒数一次，就是每个实体每个 tick 写一次；结束的 tick 只写一次，
  有序索引还能找出到期的掉落物，不用访问其他的。
- **并行的物理、水和找目标**。它们通过 World 的索引读数据，见[移动](#movement)。

## 客户端与服务器 [#client-and-server]

联网游戏通常这样分工：服务器掌握世界、下发变化，客户端负责显示。两边都可以用这套 ECS：

- **服务器上**，就像这个示例：系统每个 tick 计算世界，`Send` 系统把变化（`[Changed<T>]`、视野多出和少掉的那条区块、跨区块和退休的实体）编成包。
- **客户端上**，收到的包写进一个组件相同的 World。同样的 `PhysicsSystem` 和 `FloatSystem` 在两个包之间预测本地玩家，
  渲染系统读 `Position` 和区块的方块来画：在 [Godot](/zh/docs/samples/godot) 里，节点在 `_PhysicsProcess` 中
  `World.Update()` 之后立刻绘制。

两边都要用的组件和系统放进一个共享项目，就像 [HotReload 示例](/zh/docs/samples/hot-reload)里的 Contracts。
