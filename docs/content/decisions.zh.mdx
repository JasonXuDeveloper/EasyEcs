## D1. 状态变化即数据：没有事件和回调 [#d1-state-changes-are-data-no-events-or-callbacks]

**决定。** 组件被添加、移除或写入时，不会调用任何用户代码。需要别人响应的变化，要么是一个组件（`Dead` 标签、消息实体），
要么是一次被追踪的写入（`[Changed<T>]`、`[Removed<T>]`）。

**原因。** 回调在另一个系统内部执行：控制流被藏起来，可能重入触发它的代码，调度器也看不到它的读写，系统就无法安全并行。
做成数据之后，效果的先后就是调度的先后，生成器知道每一次访问，测试和快照也能看到这些“事件”。

**比较过。** 组件事件（Friflo、Arch、DefaultEcs）；EasyEcs 曾经有过，后来删掉了。

## D2. 结构变更立即生效：没有命令缓冲 [#d2-structural-changes-apply-at-once-no-command-buffers]

**决定。** 添加、移除、创建和销毁立刻生效，查询进行到一半也一样：遍历期间被移除的行变成墓碑，最后一个遍历结束时 World 关闭墓碑，
遍历永远看不到行在脚下移动。

**原因。** 延后的变更等于一个更晚的“第二版本” World，每个读者都得考虑它；立即生效的变更怎么写就怎么执行。墓碑的代价是每个被访问行
一次 id 检查，遍历之外没有任何开销。

**比较过。** 查询结束后回放的命令缓冲（Friflo、Arch、DefaultEcs）。

## D3. 并行 job 也没有命令缓冲 [#d3-no-command-buffer-for-parallel-jobs]

**决定。** 并行 `[ForEach]` 方法和并行阶段不做结构变更（EECS010）。并行 job 只写数据，排在它后面、运行在所有者线程上的系统根据这些数据做结构变更：

```csharp
public record struct Poison(int DamagePerTick) : IComponent;

public class PoisonSystem : EcsSystem
{
    [ForEach(Parallel = true)]                                    // 数据，在所有核心上
    static void Hurt(ref Health hp, in Poison poison) => hp.Value -= poison.DamagePerTick;
}

[UpdateAfter<PoisonSystem>]
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]                                      // 结构，随后在所有者线程上
    static void Die(Entity entity, in Health hp) { if (hp.Value <= 0) entity.SetDead(); }
}
```

**原因。** 每线程一个记录器会把 D2 去掉的延后路径又带回来，还得定义线程之间的顺序，回放的开销也藏在阶段背后。上面的写法用的是用户本来就看得懂的调度，
批量操作（`SetAll`、`RemoveAll`）又让后续那一遍很便宜。

**比较过。** 阶段结束时回放的每线程命令缓冲（曾列入 4.1 路线图，实现前放弃）。

## D4. 没有 `Added<T>` 过滤 [#d4-no-addedt-filter]

**决定。** 没有“自某个 tick 以来获得了 `T`”的过滤。`[Changed<T>]` 已经会选出新获得 `T` 的行（添加和写入一样会打 tick）。
系统确实需要区分“新组件”和“被写过的组件”时，由创建者加一个标签，由响应的系统去掉：

```csharp
public struct Spawned : IComponent;                                  // 标签："上次 Greet 之后新出现的"

public class GreetSystem : EcsSystem
{
    [ForEach, With<Spawned>]
    static void Greet(Entity entity, ref Health health)
    {
        health = new Health(health.Value + 10);                      // 首次处理：新手奖励
        entity.RemoveSpawned();                                       // 然后翻一个位
    }
}
```

```csharp
world.CreateEntity(new Health(100), new Spawned());                  // 创建者声明它是新的
```

**原因。** 标签是显式的、可查询的、会随 World 一起存档，代价只是翻一个存在位。内置过滤则要给每个被追踪的行多存一个变更 tick
（每行多 8 字节，每次添加多一次写），每种组件还要多一列伴随列，而标签已经能满足需求。

**比较过。** Bevy 的 `Added<T>`、DefaultEcs 的 `WhenAdded`（曾列入 4.1 路线图，实现前放弃）。

## D5. 按依赖而不是优先级给系统排序 [#d5-order-systems-by-dependencies-not-priorities]

**决定。** 系统按注册顺序运行。`[UpdateBefore<T>]` / `[UpdateAfter<T>]` 只在分组内移动声明它的那个系统。阶段由排序图和读写集决定：
两个系统互不排在对方之前、访问也不冲突时，才一起跑。出现环时 `AddSystem` 抛异常（World 保持不变），分析器能看到时报 EECS019；
跨分组的排序不起作用（EECS020）。`Priority` 已删除。

**原因。** 来自多个程序集的整数优先级会撞车，也说明不了系统为什么排在那里；排序约束直接写明依赖。两套机制并存只会让一件事有两种做法。
只移动声明者能保持其他系统的注册顺序，加一条排序不会打乱无关的系统。

**比较过。** 优先级与排序并存（否决：重叠）；按字典序的拓扑排序（否决：会打乱无关系统）。tick 时间不变：ParallelSystems 四轮
改前 292-345 μs、改后 278-325 μs；WorldSimulation 改前 1,774 μs、改后 1,731 μs。

## D6. 移除组件不搬行 [#d6-removing-a-component-keeps-the-row]

**决定。** 移除只清掉这一行在该列上的存在位；只有添加表里没有对应列的组件才会搬行。

**原因。** 来来去去的状态（眩晕、着火、死亡）第一次之后只需翻一个位，查询一次测 64 行，`[Removed<T>]` 也就是一行普通的数据（tick 说明是什么时候）。

**比较过。** 每次移除都搬行（经典原型模型）：每次状态变化一次复制。

## D7. 连续的列，而不是分页 [#d7-contiguous-columns-not-pages]

**决定。** 列是连续数组。

**原因。** 分页的遍历速度一样，却给每次句柄访问多加一层间接；省下的只是表扩容时的那次复制，而 `InitialEntityCapacity` 和
`Reserve` 本来就能消掉它。

## D8. 没有整实体禁用 [#d8-no-whole-entity-disable]

**决定。** 没有“被禁用的实体”这种默认被查询跳过的东西。用一个标签加 `Without<T>` 显式实现；`Disable<T>()` 则是保留单个组件的值、
同时对查询隐藏它：

```csharp
public struct Inactive : IComponent;                        // 整个实体关掉
public struct Bullet : IComponent;

public class BulletSystem : EcsSystem
{
    [ForEach, With<Bullet>, Without<Inactive>]              // 要跳过它的系统自己写明
    static void Move(ref Position p, in Velocity v) => p = new Position(p.X + v.X, p.Y + v.Y);
}
```

```csharp
var bullet = world.CreateEntity(new Bullet(), new Position(0, 0), new Velocity(4, 0));
world.Update();                                             // 子弹飞行
bullet.SetInactive();                                       // 回到对象池：翻一个位，不搬行
bullet.SetPosition(10, 20).RemoveInactive();                // 重新启用

int pooled = world.Count<Bullet>(QueryFilter.Create().With<Inactive>()); // 存档、清理、统计都能看到全部实体
```

用途：对象池（子弹、特效）、断线重连期间留在内存里的玩家、没有玩家时 NPC 休眠的区域。

**原因。** 默认排除会让每个查询都依赖一个它没写出来的状态：必须看到全部实体的存档、清理或计数得记着把它们加回来，忘了也不会报错。
标签是生成器和读代码的人都看得见的数据，这正是 ECS 原则的要求。

**比较过。** Friflo（`entity.Enabled = false`：原型里的隐藏标签，除非 `WithDisabled()`，否则查询跳过）；DefaultEcs
（`entity.Disable()`：实体离开所有实体集）。按场景比较：

| | Friflo | DefaultEcs | EasyEcs |
| --- | --- | --- | --- |
| 关闭或打开一个实体 | 把它的行搬到另一个原型 | 更新每个实体集 | 翻一个存在位（第一次之后） |
| 遍历时越过被禁用的实体 | 跳过它们的原型 | 它们不在任何集里 | 表里没有被禁用实体时零开销（看计数，不读位）；混在一起时每 64 行测一次 |

对象池和特效切换频繁，翻位比搬行划算。只有大量实体长期禁用、又和启用的实体混在同一张表里时，EasyEcs 才比 Friflo 多出每 64 行一次的测试；
真有影响时，按休眠状态 `GroupBy` 就能把它们拆到单独的表里。在系统分组上加过滤（在 `ISystemGroup` 结构体上写 `[Without<Inactive>]`）
会作用到分组内所有系统的每个 `[ForEach]`，过滤只需写一次。

## D9. 内置存档，基于 Nino [#d9-saves-are-built-in-with-nino]

**决定。** `World.Save` / `Load` 和 `SaveEntities` / `LoadEntities` 直接写表，托管值交给 Nino。非托管行按规范布局写出并附带字段哈希，
结构体改了在加载时就能发现；生成器记录 `EntityId` 字段的位置，迁移时据此改写成新实体。

**原因。** 改写引用、按类型名加载、重复加载时复用行（0 B 分配）都需要 World 的表和生成器配合；用户在 `Query` 上自己写做不到。
（4.0 之前存档由用户自己负责。）

## D10. `MoveEntities` 直接复制行，不经过编码 [#d10-moveentities-copies-rows-without-encoding]

**决定。** `world.MoveEntities(target, ids)` 把一组实体的行复制到本线程的另一个 World，改写组内的 id，再销毁原实体。它和 `LoadEntities`、
预制体组共用一个核心：按列复制一段段连续的行。

**原因。** 测出编码确实占了搬迁的相当一部分才保留它：1,000 个实体往返 150 μs，走 `SaveEntities` + `LoadEntities` 要 207 μs；
没有层级时单程 32 μs 对 71 μs。

## D11. 预制体里的 id 指向它的成员 [#d11-ids-in-a-prefab-name-its-members]

**决定。** 预制体里的 `EntityId` 字段指向它所在组的某个成员（`member.Id`），每次实例化都会改写；其他 id 一律变成 `EntityId.Null`。
指向 World 里实体的关系在实例化之后再设置。

**原因。** 预制体不属于任何 World：World 里某个实体的 id 可能恰好等于某个成员的 id，两者无法区分。

## D12. 目标策略按索引选择开启 [#d12-target-policies-are-opt-in-per-index]

**决定。** 在 `EntityId` 索引或关系索引上调用 `WhenTargetDestroyed(TargetPolicy.Remove / Destroy)`，决定销毁一个实体时指向它的链接怎么处理；
默认是 `Keep`（链接保留，可以按已失效的 id 找到）。`ChildOf` 是 `Destroy`，可以改。

**原因。** 选择开启能让没设策略的 World 销毁实体时和以前完全一样。`ChildOf` 的规则内联检查：走通用规则列表时级联基准要 650 μs，
内联后 557 μs 变为 561-578 μs。

**比较过。** 在组件类型上加标记接口（否决：那样索引就得泛型地创建，需要反射；在索引上调用方法对 AOT 安全，而且按 World 生效，
和 `GroupBy<T>()` 一样）。

## D13. 每个 World 一个所有者线程 [#d13-one-owner-thread-per-world]

**决定。** World 的系统、查询和结构变更都在它的所有者线程上执行；并行阶段和并行 `[ForEach]` 是仅有的并行，由生成器证明安全。
其他线程把工作投递给所有者线程。

**原因。** 任何热路径上都没有锁；规则三行就能说清（[多线程与并行](/zh/docs/guide/threading)）。

## D14. 没有共享组件 [#d14-no-shared-components]

**决定。** 没有 `SetSameAs` 之类的共享值。共享数据放在单例里，组件只存指向它的 id。

**原因。** 共享值本质上是一个引用，一次写入会同时改掉很多实体，变更追踪和调度器都看不到。

## D15. 只支持 .NET 10 [#d15-net-10-only]

**决定。** EasyEcs 只面向 `net10.0`。凡是 .NET 10 能跑的地方它都能跑，包括面向 `net10.0` 的 Godot 4 .NET 项目
（[Godot 示例](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Godot)）；不支持 Unity 的 Mono 和 IL2CPP，也不支持更老的运行时。

**原因。** 它依赖 C# 14 扩展成员、`Vector256`、放在 POH 上的列以及当前 JIT 的行为，这些老运行时都没有。
Unity 支持要等到 Unity 能运行 .NET 10（[路线图](/zh/docs/roadmap#unity)）。

## D16. 不需要 `partial`：生成的代码不放进用户的类型 [#d16-no-partial-generated-code-lives-outside-the-users-type]

**决定。** 生成器把 `[ForEach]` 方法的 job 写进单独的 `file` 类，通过 `[UnsafeAccessor]` 调用这个方法（不管是不是私有）。
系统的更新逻辑和访问集是一个 `SystemCode`，由模块初始化器注册（弱引用持有，可回收的程序集才能卸载）；runner 的入口是它所在类型上的
C# 14 静态扩展成员。生成的代码无法引用的类型（私有组件、私有 runner 类型）报 EECS022。

**原因。** 系统就是普通的类：它和外层类型都不用写 `partial`，类体里也不生成任何东西，生成的成员不会和用户的冲突。`UnsafeAccessor`
编译出来就是直接调用（机器码相同，可内联），tick 时间没有变化（ForEachSystemWrite、ParallelSystems 在误差范围内）。

**比较过。** partial 类（缺失时报 EECS001，成员注入用户类型）；指向方法的委托或函数指针（每行一次间接调用，无法内联）；启动时反射（不支持 AOT）。

## D17. 卸载时把类型移出 World，组件位复用 [#d17-unloading-removes-types-from-worlds-bits-are-reused]

**决定。** `world.RemoveTypes(assembly or context)` 把一个程序集的系统、单例、索引、分组和组件移出 World。实体保留；含有它的列的表连同引用这些表的
所有缓存一起丢弃。可回收的上下文卸载后，EasyEcs 忘掉它的存档名称；没有存活的 World 再引用它的组件位时，这些位会被复用。
重新加载靠 `Save` 和 `Load` 保留数据，它们按类型 id 映射类型。

**原因。** 长时间运行的服务端热重载游戏逻辑时，不能留下任何东西把旧程序集钉住（列数组、迁移边、查询缓存的键、注册表），反复重载也不能让掩码不断变长。
丢弃表是 `Dispose` 之外唯一会删除表的地方，稳态代码没有任何额外开销（CreateAddDestroy、Prefab、WorldSimulation 在误差范围内）。

**比较过。** 在内存里把旧类型的行迁移成新类型（每个字段都需要类型映射；`Save` / `Load` 已经按类型 id 和字段哈希做了映射）；从不复用位
（每重载一次，掩码就多出一批组件）。

## D18. 查询调用不用拦截器；过滤条件不持有引用 [#d18-no-interceptors-for-query-calls-filters-carry-no-references]

**决定。** 查询调用不做拦截。`QueryFilter` 把五个集合的前 256 位内联存放，255 之后的位存成一个驻留 id，因此不持有任何对象引用，
构建器每次调用只复制一次。

**原因。** 拦截器只替换调用绑定的方法，调用参数照样要求值，在调用处构建的过滤条件怎么都会被构建；按调用点缓存查询项省下的只是调用本来就有的那次备忘查找。
真正的开销在过滤条件本身：五个各带溢出引用的掩码让每次构建器调用都经过 `BulkMoveWithWriteBarrier` 复制两次，还要清零调用方栈帧。
去掉引用后，用调用处构建的 `QueryFilter.Create().With<Npc>().Without<Dead>().Without<Frozen>()` 统计 16 个实体从 124 ns 降到 76 ns，
过滤条件放在静态字段里仍是 24 ns（`CallSiteBenchmark`）。热调用仍然建议把过滤条件提出去。

**比较过。** 拦截器配静态过滤条件、每个调用点缓存查询项（参数求值让它失去意义）；对在调用处构建过滤条件给出分析器警告
（大多数调用是冷的；文档已经教了静态字段的写法）。

## D19. 标签属性不可赋值 [#d19-no-settable-tag-properties]

**决定。** 标签生成的 `IsX` 是只读的；`SetX()` 添加标签，`RemoveX()` 移除标签。

**原因。** `entity.IsDead = true`（Entitas 风格）在 ECS 代码持有实体的地方写不出来：C# 14 不允许给 `foreach` 变量（CS1654）、
索引器结果（CS1612）或 `in` 参数的字段（CS8332）上的结构体扩展属性赋值，按值接收还是 `in` 接收都一样。一个在局部变量上能编译、
在 `foreach (var e in hits)` 或 `link.Target` 上却不能编译的成员会教错东西；方法在哪里都能用，结构变更也始终是一次显式调用。

## D20. 泛型系统注册所在程序集用到的封闭类型 [#d20-generic-systems-register-the-closed-types-their-assembly-names]

**决定。** 泛型系统的代码是一个以系统类型参数为参数的泛型类。它的模块初始化器为所在程序集里出现过的每个封闭类型注册一个实例
（`AddSystem<CountOf<Health>>()`、`new CountOf<Health>()`、基类型 `CountOf<Health>` 及其泛型基类），其他封闭类型则注册泛型定义，
由 `AddSystem` 在第一次使用时用 `MakeGenericType` 封闭。系统自己的泛型 `[ForEach]` 方法仍报 EECS004。

**原因。** 模块初始化器无从知道程序会用哪些类型参数，系统类里又不生成任何东西（D16）。系统所在程序集里出现过的封闭类型不需要运行时生成代码，
Native AOT 能保留它们；只在其他程序集里出现的封闭类型在 JIT 下照样能用。runner 两者都不需要：入口本身是泛型的，调用方的类型参数在编译期就封闭了 job。
系统自己的泛型方法则没有调用方来提供类型参数。

**比较过。** 只用反射（任何值类型参数都会破坏 Native AOT，而组件都是结构体）；系统上的虚泛型钩子（需要 `partial` 或每个元数一个基类）；
扫描被引用程序集里的封闭用法（生成的代码对系统所在程序集是 file 级私有的）。

## D21. .NET 10 新特性，测得出收益才用 [#d21-net-10-features-only-where-they-measure]

**决定。** 4.1 考虑过的每个 .NET 10 / C# 14 特性都做了原型，用 BenchmarkDotNet 和前一个提交对比（两边各跑两轮，全程 0 字节分配），
只有净收益才保留：

| 特性 | 结论 | 数据 |
| --- | --- | --- |
| `Vector512`（和 `Vector<T>`） | 保留：没有墓碑的表统计行字里的置位数，AVX-512 下每步 8 个字，否则用 `Vector<T>`（AVX2 4 个，Arm64 2 个） | CountBenchmark，10 万需要测位的行：48.9-54.5 μs -> 1.21-1.27 μs；只用 `Vector<T>` 2.4 μs，逐字 5.2 μs；对 `Vector512` 按下标循环 7.6 μs（改为展开） |

| 备忘的各路改为一个数组里的结构体 | 保留 | 静态过滤条件 21.6-21.9 -> 19.0-19.8 ns，无过滤条件 36.8-39.1 -> 35.3-35.5 ns |
| 备忘用 `[InlineArray]`（所有签名的各路内联在一个扁平数组里） | 放弃 | 快 1-2 ns（20.3-20.6 / 38.9-39.5 ns），但签名下标是进程级的，每个 World 要为进程里的每个签名占约 750 字节（200 个签名 150 KB），每新增一路还要整体复制 |

## D22. 并行运行用线程池，划算时才唤醒助手线程 [#d22-parallel-runs-use-the-thread-pool-and-wake-helpers-only-when-they-pay]

**决定。** 并行 `[ForEach]` 和一个阶段的并行系统在调用线程加上可复用的 `IThreadPoolWorkItem` 助手上运行，按匹配行数切块。
每个 job 和阶段都测量自己的运行：有助手的运行会给出耗时和各任务线程时间之和，只要助手能让一次运行比工作量快五分之一就保留。
一旦改为单独运行，就在一个从 16 翻倍到 1,024 次运行的周期之后试探四次带助手的运行；单独运行变慢到 1.5 倍时立即试探。
没有自旋，没有专用线程，没有分配。

**原因。** 唤醒一个停泊的线程池线程要几微秒到几百微秒，烧掉的 CPU 也差不多，所以服务器 tick 之间的小遍历带助手并不更快，CPU 却翻倍。
4 核虚拟机上 60 Hz 的 tick、单次 10 万行遍历：遍历中位数 123 -> 111 μs，每 tick CPU 436 -> 290 μs（串行：108 μs、229 μs）。BDN：
ParallelSystems 804-808 -> 746-768 μs，ParallelForEach 294-308 -> 267-271 μs，BattleServer 和 Runner 不变。

**比较过。**
- 一组专用助手线程，每次运行后自旋约 50 μs：只有遍历首尾相接时才赢（BenchmarkDotNet 的循环）。放到服务器 tick 里就输了：
  中位数 130 对 135 μs，但 p90 170 对 190 μs，每 tick CPU 990 对 760 μs。
- `ThreadPool.UnfairSemaphoreSpinLimit`：能消除首尾相接的差距，但它是进程级的，会让线程池线程在 tick 之间一直自旋（每 16 ms tick 49 ms CPU），
  所以留给应用自己决定。
- 用带静态委托的 `Parallel.For` 当运行器（`ParallelRunnerBenchmark`，`ParallelForEachBenchmark` 的转向遍历，4 核、机器负载 10 到 30）：
  1,000 行时运行器 18 µs、0 B，`Parallel.For` 24 到 42 µs、1.5 到 1.9 KB；10,000 行时两者在噪声范围内持平；100,000 行时 `Parallel.For`
  快 15% 到 40%，但在这种负载的噪声范围内（运行之间相差 2 倍）。在空闲机器上重跑还没做。它每次调用还会分配，也不能传状态（[D69](#d69-reductions)）。

## D23. 按块维护变更摘要；移除单独汇总 [#d23-change-summaries-per-block-removals-summarized-apart]

**决定。** 被追踪的列为每个 64 行的字保存一个 32 字节的条目（最新 tick、处于它的行、其余行的上界、缺组件的行的 tick 上界），
为每个 4,096 行的块用位掩码记下处于块内最新 tick 的字，另加其余字的上界。`Changed<T>` 遍历用一次位扫描找到下一个被写过的字；
`Removed<T>` 遍历按移除上界跳过字、按单独的移除摘要跳过块，`T` 的写入不会让它去访问那些字。

**原因。** BDN，对比按字维护的摘要：RemovalComparison 10 次移除 1.07-1.09 -> 0.87 μs；ChangeTracking `Changed` 写 10 行
609-650 -> 514 ns；ChangeTrackingComparison 612-636 -> 497-573 ns。BattleServer、WorldSimulation 和写 1,000 行的场景不变。

**剩下的差距。** Friflo 报告 10 次移除只要 0.70 μs：它在回调里随时收集被移除的 id，读的时候不再有额外开销。EasyEcs 把移除当作数据（D1）：
一次遍历约 90 ns，每个有移除的字再加约 30 ns，花在读摘要和行上。到 1,000 次移除时两者持平（71 对 73 μs）。

**比较过。** 把字的摘要和块的摘要交错存放（没有收益：10 万行的摘要放得进 L2）；用单独的辅助函数逐行记字（更慢：每次查询 tick 600 μs）；
为一次移除的打 tick 和移除记录只查一次列和字（测不出收益，已回退）。

## D24. 索引的每个键用一个数组存它的实体 [#d24-an-indexs-key-holds-its-entities-in-one-array]

**决定。** 值索引和关系索引把每个键的实体放在一个 id 数组里（`IndexHead`）。实体离开留下的空位由这个键的下一个实体补上，
实体不会移动，不管循环中销毁了什么，每个实体都只会被找到一次；清空的键的数组会被复用。`CreateEntities` 只查一次键就把整批实体加进索引。

**原因。** 用每实体节点串起来的链表，每个实体要一次依赖读取。BDN：IndexBenchmark 710 -> 156 μs；ValueQueryComparison 648 -> 225 μs
（Friflo 323 μs）；RelationComparison 26.8 -> 23.4 μs（Friflo 26.5 μs）；级联不变，0 字节。

## D25. 为没有墓碑的表单独编译结构性行循环 [#d25-structural-row-loops-are-compiled-for-tables-without-tombstones]

**决定。** 可能做结构变更的 `[ForEach]` 用编译了两份的行循环处理每张表：一份给有墓碑的表（每行检查 id），一份给没有墓碑的表（不检查）。
调用时没有墓碑的表只能通过结构变更产生墓碑，而结构变更会让存储版本加一并结束这个循环。

**原因。** StructuralChangeComparison，每 tick 杀死 10 万单位中的 10 个：85.7 -> 80.9 μs（三轮；Friflo 的命令缓冲 77 μs）；
杀死 1,000 个和 BattleServer 不变。

**比较过。** 把看到的存储版本放在寄存器里，而不是每行重新读：82 -> 108 μs（job 调用之后剩下的被调用者保存寄存器太少，
一个列引用溢出到栈上，每行往返一次）。

## D26. 在代码会重复写类型名的地方生成成员，并建议使用它们 [#d26-generated-members-and-a-suggestion-to-use-them]

**决定。** 查询元素的组件有名字：`item.Position` 代替 `item.Component1`，按代码实际调用的每种 `Query<…>` 形状生成。
缓冲元素在预制体上有写方法：`prefab.SetLoot(…)`，基于 `Prefab.SetBuffer<T>(params ReadOnlySpan<T>)`。凡是代码调用泛型 API
的地方，分析器都建议改用生成的成员（EECS033，信息级别，带代码修复）：`entity.Get<Position>()` 写成 `entity.Position`，
`Has<T>()` 写成 `HasX` 或 `IsX`，`Set(new T(…))` 写成 `SetX(…)`，`GetSingleton<T>()` 写成 `world.X`，`Index<T, TKey>()`
写成 `world.XIndex`，`item.Component1` 写成 `item.Position`，以及生成器写出的其他成员。多类型的 `Disable` / `Enable` 和多类型
批量调用不做。

**原因。**
- **查询元素。** `Component1..n` 让读代码的人去数类型参数。命名成员是对同一个 ref 的内联 getter，零开销。每种形状一个文件，
  程序集只输出它用到的形状；按组件和位置各生成一个扩展块的话，每个组件要 45 个块。
- **预制体缓冲。** 没有 `SetBuffer` 时，预制体只能持有空缓冲：要填就得复制一个缓冲值，而 EECS012 拒绝这样做。关系没有预制体写方法，
  因为配方里的链接会指向预制体自己的行。
- **建议。** 文档、示例和模板都写生成的成员，两种写法混在一起比只用任何一种都难读。只有在意思完全相同的地方才建议改写：
  该类型在当前编译里确实生成了这个成员（通过绑定替换后的代码来确认），而且返回的引用种类相同：追踪组件的属性是
  `ref readonly`，所以它的 `Get<T>()` 改写成 `WriteX()`（被索引的组件没有写方法，它的 `Get<T>()` 保持原样）。缓冲区的成员只在代码写着 `DynamicBuffer<T>` 时才存在，所以当这个调用是
  最后一处这样的写法时不提建议。级别是信息：IDE 里的建议，不会让构建失败，因为泛型代码需要泛型 API，而两种写法编译出来是同一个调用。
  分析器对方法调用的操作回调本来就为 EECS025 和 EECS034 运行，这条建议只是给每次调用多一次符号检查。

**比较过。**
- **`Disable<T1..Tn>()`、`RemoveAll<T1..Tn>()` 等多类型调用。** 一张表第一次禁用之后，每次调用都是原地翻位。n 次调用就是 n 次进闸门，
  每次几纳秒；而跨多个类型的批量调用还得给“有其中任意一个”定义含义，单类型调用不需要。没有实现。
- **用警告而不是建议。** 那样会让把警告当错误的构建只因写法不同就失败。
- **把 `SingletonRef<T>.Value` 改写成 `world.X`。** `SingletonRef<T>` 记住了单例的槽位，改写后每次访问都要多查一次。不提建议。

## D27. 读取缺失的单例一律抛异常 [#d27-reading-a-missing-singleton-throws-everywhere]

**决定。** 读 World 里没有的单例，一律抛 `InvalidOperationException`：`world.X`、`GetSingleton<T>()`、`SingletonRef<T>()`，
因此也包括 `[ForEach]` 方法的单例参数，在系统第一次运行时抛出。异常信息写明单例的名字和添加它的调用（`world.SetClock(...)`、
`AddSingleton<Clock>()`，确实要默认值时用 `GetOrAddClock()`）。只有 `GetOrAddSingleton<T>()` / `GetOrAddX()` 会添加默认值，
调用它的代码自己写明了这一点。

**原因。**
- **漏掉的初始化在出错的地方暴露。** 4.2 之前，`[ForEach]` 参数会添加默认值的单例，而 `world.X` 会抛异常。漏写 `SetClock(...)`
  的 World 于是跑在一个步长为零的时钟上：实体原地不动，测试因为错误的原因通过，没有任何线索指向漏掉的那一行。现在第一次
  `Update()` 就报出单例的名字和该加的调用。
- **所有读取一个规则。** 同一个单例，在 `OnUpdate` 里读和作为参数接收，行为却不一样；现在读就是读，只有名字里带 `GetOrAdd` 的调用才会添加。
- **热路径上没有额外开销。** job 在创建时解析单例，每次遍历一次；检查的还是原来添加前就有的那次判空，抛异常放在冷路径方法里。

**比较过。**
- **`[ForEach]` 参数继续添加默认值。** 小程序里省一行初始化，真实服务器里却把漏掉的那一行藏了起来，而大多数单例（时钟、配置、刷怪器）的默认值都是错的。
- **分析器检查没有任何代码添加的单例参数。** 初始化是宿主代码，常常在另一个程序集里，或者来自 `Load`、`LoadEntities`、插件；
  编译期检查要么漏掉这些，要么误报正确的代码。
- **在 `AddSystem` 时检查。** 系统常常先于单例添加，或者单例要等 `Load` 才带进来；第一次运行是单例必须存在的最早时刻。
- **用 `GetOrAddX()` 显式要默认值**（采用）：默认值本来就对的地方，比如从零开始的计数器，一次调用就说清楚了。

## D28. 预留只扩到需要的大小；实体存储放在固定对象堆 [#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap]

**决定。** 预留把表扩到需要的行数（向上取整到整个存在位字，即 64 行），把实体存储扩到需要的 id 数；如果容量翻倍更大，就按翻倍扩。
不再扩到下一个 2 的幂。预留包括 `Reserve<T1..Tn>(count)`（正好有这些组件的那张表）、`Reserve(prefab, count)`、
`EnsureEntityCapacity`、`CreateEntities`、`InitialEntityCapacity` 和恢复快照。由预留定下大小、不小于 85,000 字节的实体存储数组分配在
固定对象堆（POH）上，和非托管列放在一起；翻倍扩容的中间数组仍然放在大对象堆（LOH）。

**原因。**
- **启动时的开销是一次回收，不是创建本身。** 在从没放过实体的 World 里创建 10 万个实体（Doraku/Ecs.CSharp.Benchmark 的做法：每次调用
  一个新 World，只测一次），批量创建要 11.8 到 12.6 ms；把这些数组改成小对象（调大 `DOTNET_GCLOHThreshold`）后，同样的行只要
  1.2 到 1.6 ms。.NET 在上次回收之后 LOH 上的分配超过预算时会触发一次完整回收，POH 单独算一份预算；两次迭代之间的回收过后，
  两边的预算都是 3 MiB（在被测调用里用 `GC.GetGenerationBudget` 读到）。`CreateEntities(new Entity[100_000], ...)` 在 LOH 上放了
  1.6 MB 的句柄数组和 2 MB 的实体数组（131,072 条记录），一共 3.7 MB，于是每次调用都要付一次后台 gen2 回收；后台回收期间大对象
  分配会被限流，在这台 4 核机器上一次要 5 到 15 ms（关掉后台回收 `DOTNET_gcConcurrent=0` 时是 4.8 ms）。
- **两处改动让两边都不超预算。** 按预留的大小分配，10 万个实体省下 0.6 MB；实体记录放到 POH，把 1.6 MB 挪到另一份预算：LOH 上只剩
  句柄和实体行（2.4 MB），POH 上是实体记录加一到三个 int 列（2.0 到 2.8 MB），不再触发回收。批量创建（一、二、三个组件）从
  11.8 / 12.6 / 12.6 ms 降到 2.7 / 2.5 / 2.7 ms，分配从 5.03 / 5.53 / 6.03 MB 降到 4.20 / 4.58 / 4.96 MB。
- **逐个创建的实体用 `Reserve<T1..Tn>`。** `EnsureEntityCapacity` 只扩实体记录，表还是从 64 行开始翻倍，分配了最终大小的两倍：
  以前 2.67 / 3.32 / 3.99 ms、4.53 / 5.53 / 6.53 MB，预留好表之后 1.94 / 2.71 / 2.60 ms、2.67 / 3.05 / 3.44 MB（Friflo 对 store 和
  archetype 都调 `EnsureCapacity`：11 到 12 ms；Arch 调 `EnsureCapacity`：3.4 到 4.2 ms）。
- **固定住的数组本来也不会移动。** 两个堆默认都不压缩；句柄不做边界检查直接按下标访问实体记录，这个数组从来不搬；GC 扫描固定数组里的
  引用和普通数组一样。翻倍时丢掉的数组留在 LOH，需要时还能压缩（`GCSettings.LargeObjectHeapCompactionMode`），不会永久留下空洞。
- **热路径不受影响。** 不扩容的 World 走的还是原来的代码；预留只多一次比较。一张表经过很多次小的预留，仍然按翻倍增长
  （先 100 行再 30 行：128，然后 256）。

**比较过。**
- **实体记录和列分页**（像 Arch 那样 16 KB 一块）：小对象不会触发完整回收，但每次句柄访问都要多一次间接寻址（D7）。
- **所有大的实体记录数组都放 POH**，翻倍的中间数组也放：不预留、三个组件、10 万个实体的启动会超两次 POH 预算（10.0 ms，原来 6.6 ms）。
- **实体行也放 POH：** 实体记录、实体行加两个 int 列在 POH 上就已经超过 3 MiB。
- **World 释放时把数组还给池**，给下一个 World 用：实体记录不能还，释放后的 World 的句柄仍会不做检查地按下标访问它；池还会占着进程
  已经用完的内存。
- **只传数量的 `CreateEntities(count, values)`**，不要句柄 span：批量调用带着 span 已经在两边预算之内，不需要。

## D29. 性能规则只在代价测得出、修复行为不变时才加 [#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same]

**决定。** 分析器用 EECS025 到 EECS034 报告能跑、但做了多余工作的代码，级别说明是哪一种：警告表示这样写有代价（基准测试测出它比修复后的写法慢，
或者会分配）；建议（信息级别）表示修复后代价相同，只是写法更简洁；错误表示代码根本不能这样写。只有修复后行为不变的规则才会加入，
而且只有分析器已经绑定过替换代码时才提供代码修复。测不出代价、或者修复会改变行为的候选都放弃了。

| 规则 | 级别 | 测量结果（100,000 个实体） |
| --- | --- | --- |
| EECS025 只读的写访问 | 警告 | 追踪组件用 `ref` 306 µs，用 `in` 271 µs；不追踪的组件两者一样（270 / 276 µs）：代价在写集合上 |
| EECS026 没用到的参数 | 警告 | 每行一样（41 / 46 µs）；`Entity` 或 `World` 让系统单独运行，追踪组件的 `ref` 给每一行打 tick |
| EECS027 每行查一次 | 警告 | `entity.Read<T>()` 258 µs，参数 40 µs；`Has<T>()` 208 µs，`Maybe<T>` 86 µs；通过 `World` 取单例 105 µs，参数 48 µs |
| EECS028 每次更新都分配 | 警告 | 每个 tick 都产生垃圾；见[不该做的](/zh/docs/performance#dont)清单 |
| EECS029 实例 `[ForEach]` 方法 | 警告 | 实例方法 104 µs，静态方法 41 µs |
| EECS030 对查询结果逐个实体做结构变化 | 警告 | `BulkBenchmark`：逐个实体的耗时是 `SetAll` / `RemoveAll` 的 19.1 倍，是 `DisableAll` / `EnableAll` 的约 99 倍 |
| EECS031 计数循环里逐个创建 | 警告 | 只对新 World 有效（[D28](#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap)）；`MicroBenchmarks.Churn` 的耗时是 `ChurnBatch` 的 2.1 倍 |
| EECS032 手写计数和判断 | 警告 | `Count() > 0` 429 ns，`Any()` 18.6 ns；循环里判断 `Has<T>()` 332 µs，过滤条件 59.5 µs |
| EECS033 生成的成员 | 信息 | 同一个调用，代价相同（[D26](#d26-generated-members-and-a-suggestion-to-use-them)） |
| EECS034 系统里执行 World 更新 | 错误 | 递归，或者在阶段进行到一半时运行系统 |

每一对都由 `AccessBenchmark` 测量（BenchmarkDotNet，共享的 4 核 2.1 GHz Xeon，.NET 10.0.13）；所有写法都零分配。

**原因。**
- **警告会让把警告当错误的构建失败**，所以每条警告在任何触发的地方都必须是对的。规则报告之前会检查每一处用法：EECS025 把赋值、
  `++`、`ref` 或 `out` 实参、非 `readonly` 方法、`ref` 局部变量和 `this ref` 扩展方法都算作写入；EECS027 只报告每一行都会执行、
  而且方法自己不改的组件的查询；EECS028 不报告 `throw`、`[Conditional]` 调用、控制台输出，以及自己设置了 `UpdateInterval`
  的系统的 `OnUpdate`；EECS030 不报告覆盖查询已要求组件的 `Set`，也不报告分组组件的 `Set`（在 `SetAll` 里它的行同样逐个移动）；
  EECS031 不报告小于 4,096 的常量次数和用这样的常量创建的数组（没有数组会进入大对象堆），也不报告预留过容量之后的循环、只在分支里或内层循环里的创建，
  以及系统里的循环（运行中的 World 会复用已有的行）；EECS032 只报告和 0 或 1 比较的 `Count`、只计数的循环，以及作为循环第一条语句的判断。
- **只要有代价就是警告，不论大小。** 预留容量在 World 第一次长到这么大时收益最大，`Any` 和过滤条件的收益与循环本来要访问的行数成正比；
  但在规则触发的地方，原来的写法都比修复后的慢，所以和其他规则一样是警告。只有 EECS033 是建议：生成的成员调用的就是泛型 API，
  改的只是代码长短，不是代价。
- **修复就是规则的证明。** 每个替换在提供之前都会在原位置绑定一遍：成员没有生成、过滤条件编译不过、或者有调用方按 `ref` 传参给这个方法，
  就不提供修复。

**比较过。**
- **一次一个地添加或移除多个组件**（`e.Set(a); e.Set(b);` 写成 `e.Set(a, b)`）：逐个 500.7 µs，合并 480.7 µs；两个 16 字节的组件
  是 290.1 对 308.7 µs。转换缓存之后，第二次移动和第一次一样便宜。放弃。创建之后紧跟 `Set` 是另一回事，测出来是有代价的
  （[D59](#d59-analyzer-rules)）。
- **把标签作为参数而不是 `[With<T>]`**：37.7 对 38.6 µs；代价在它声明的访问上，而任何没用到的参数 EECS026 都已经报告了。
- **对不追踪的组件用 `[Changed<T>]`**：特性的约束已经让它编译失败（CS0315）。
- **对结构变化或很小的工作用 `Parallel = true`**：结构变化是 EECS010；一遍算不算小取决于运行时的实体数量。
- **并行阶段内系统之间的冲突、多余的排序**：阶段是运行时按宿主添加系统的顺序划分的；多余的 `[UpdateAfter<T>]` 没有代价。
- **从别的线程调用 `World.Update`**：World 可以在拥有它的任意一个线程上运行（每个线程一个 World），和所有者线程竞争的结构调用由 EECS014 报告。
- **`OnUpdate` 里手写的 `Query` 循环、热路径上的 `Capture` 或 `Describe`、循环里的值索引查询**：`Query` 是正式支持的 API，
  它的代价 EECS030 和 EECS032 已经指出；每个 tick 拍快照正是回滚的做法；索引查询是 O(1)，`[ForEach]` 方法也没法把它提到循环外。不加规则。
- **每次调用都构建 `QueryFilter`，而不是放进 `static readonly` 字段**：过滤条件是不含引用的小结构体
  （[D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)）；测不出代价。不加规则。

## D30. 存档按 Nino 类型 id 记录类型；标了 `[NinoType]` 的非托管组件由 Nino 写出 [#d30-saves-record-types-by-nino-type-id]

**决定。** 存档（格式 2）按 Nino 类型 id 记录每个组件、缓冲元素和单例的类型：也就是 Nino 用带命名空间的全名、或 `[NinoFormerName]`
保留的旧名字算出的哈希。普通的非托管组件和以前一样按原始行写；标了 `[NinoType]` 的非托管组件由它的格式化器逐行写出。行的写法和当前
进程不一致，或者进程里两个类型 id 相同，加载都会拒绝，报错写明改法。格式 1 的存档（4.3 及更早）一律拒绝。

**原因。**
- **改名是存档数据最常遇到的变化**，而存档里记名字，每次改名都会悄悄丢数据。Nino 本来就有这条规则（`[NinoFormerName]` 让类型改名后
  id 不变，它自己的多态数据也靠这个），EasyEcs 直接沿用，不再另造一个改名特性或映射表。
- **非托管组件也需要演进。** 原始行只能读回到结构完全相同的类型；以后要加字段的组件，标上 `[NinoType]` 表明这一点，能改什么由它的
  格式决定（`VersionTolerant` 可以追加成员，`Keyed` 可以任意改成员）。保持原始行的组件仍然整块拷贝。
- **代价只落在主动选择的地方。** 两张原始行表里的 100,000 个实体，存档前后分别是 271 µs 和 262 µs，读档 1,052 µs 和 1,003 µs；一个带
  四个组件的实体经字节往返一次，2.25 µs 和 2.22 µs；全部 0 B。每个类型只花 4 字节记 id，不再写名字。
- **不转换旧存档。** 为格式 1 保留读取器，名字查找就得在以后每个版本里一直留着，而这些数据只要重新写一次就行
  （步骤见[迁移指南](/zh/docs/migration#v4-4-saves)）。

**比较过。**
- **记名字，再加一张改名映射**（`World.RenameType("Old", typeof(New))`）：在 Nino 之外又多一套机制，而且配在代码里，不在类型上。
- **用 Nino 的类型注册表查找**：它在进程级缓存类型，可回收插件的类型就永远卸载不了；EasyEcs 自己算 id，插件卸载时一并忘掉。
- **所有非托管组件都走 Nino**：整列整块拷贝正是存档快的原因，而大多数组件的结构从来不变。

## D31. 只存需要持久化的部分：存档时用组件集合，读档时读到已有实体上 [#d31-a-record-of-what-persists]

**决定。** `SaveEntitiesWith(output, ids, set)` 只写 `ComponentSet` 里的组件，`LoadEntitiesInto(input, entities)` 把一组实体的存档读到
已经存在的实体上，存档里第 i 个实体读到传入的第 i 个实体上，每个实体最多换一次表。`ComponentSet` 是建一次就留着的位掩码
（`With<T>()`、`With(Type)`）；存档时每张表的行按 O(组内实体数) 选出。

**原因。**
- **Actor 只持久化实体的一部分**：余额要撑过重启，连接和计时器不用，而这些运行时组件往往根本没有 Nino 格式化器。集合按每次存档指定
  记录的内容，同一个实体可以分别写进几个存储。
- **实体先于记录存在。** Actor 激活后先拿到实体、开始处理消息，记录还在从数据库加载；用 `LoadEntities` 会再建一个实体，记录里的
  `EntityId` 字段也会改写成指向它。
- **每个实体只搬一次。** 记录带来的组件用一次转换加上（签名按表缓存），再写入值，所以索引、分组和变更 tick 的表现和一次 `Set` 全部组件
  一样。
- **测量结果**（`MigrationBenchmark`，预热后，0 B）：存一个实体四个组件里的两个，104 ns；读回到带着另外两个组件的实体上，722 ns；
  而把整个实体经字节发出去再重新创建要 2.22 µs。

**比较过。**
- **在组件类型上标 `[Persistent]`**：全局只能选一次，可同一个实体的不同存档需要不同的组件。
- **读档时再过滤**：存档照样要写运行时组件，也照样需要它们的格式化器。
- **先 `LoadEntities`，再手动把组件拷到 Actor 上**：每个实体搬两次，多一个临时实体，`EntityId` 字段指向的还是那个临时实体。

## D32. 已销毁缓冲的列表按线程池化 [#d32-the-lists-of-dead-buffers-are-pooled-per-thread]

**决定。** `DynamicBuffer<T>` 的值销毁时（组件被移除、实体被销毁、表被丢弃、被禁用的值被丢掉），把列表清空，放进当前线程上该元素类型
的池里；第一次写入先从池里取，取不到才分配。池里只留没人取用期间销毁的列表，超过 4 KB 的列表不留。

**原因。**
- **带缓冲的实体每次出现都要分配。** 带着信箱加载、随后又卸载的 Actor，每次要分配两次：1,000 个各有 4 条消息的 Actor 卸载再加载，
  以前是 76.4 µs、85.9 KB，现在是 76.9 µs、0 B（`BufferChurnBenchmark`）；其他缓冲基准测试没有变化。
- **按线程就是按 World。** 缓冲在结构变更里销毁，结构变更都在 World 的所有者线程上执行，所以一个 World 的列表会回到这个 World（或同一
  线程上另一个 World）的缓冲里，不用加锁。
- **和行一样有上界。** 池最多涨到同时销毁的列表数，这也是表的容量会保持的峰值；4 KB 的上限把曾经变得很大的列表交给 GC。

**比较过。**
- **释放行时回收**：搬行时会先拷贝引用，那时列表还在用。
- **固定数量的池**（256 个）：超过这个数的反复创建销毁又会分配，而峰值本来就受持有这些列表的实体数限制。

## D33. 单个实体运行遍历的 job：`entity.Run` [#d33-one-entity-runs-a-passs-job]

**决定。** `entity.Run<T1..Tn, TJob>(ref job)` 和 `Run(ref job, filter)` 在单个实体上运行 `IForEachEntity` job，保证和遍历一样：
`Writes` 打上变更 tick；job 自己做结构变更后 ref 依然有效（写过的组件会带到新行，job 抛异常时也一样）；`INoStructuralChanges` 冻结结构。
过滤条件直接在这一行上检查。

**原因。**
- **一次处理一个实体的代码**（一个请求、一条发给 Actor 的消息），否则要通过句柄逐个查组件，每次结构变更后再重新取 ref。
  用 job，所有组件只查一次表，规则也和系统一样。
- **不比它替代的代码慢。** 在 10,000 个实体上调用 1,000 次，1、3 或 5 个组件，有无过滤、有无结构变更，对照通过句柄手写的同样工作
  （`SingleEntityBenchmark`）：耗时是手写的 0.69 到 1.06 倍，0 B。1.04 和 1.06 的两组（有过滤又有结构变更，3 和 5 个组件）在误差范围内。
- **线程规则仍归所有者线程。** 结构闸门空闲时（所有者线程不在任何区域里），用普通的标志写入冻结结构；在并行区域里，区域的冻结已经持有；
  分析器把 `Run` 当作结构变更调用报出（[EECS010](/zh/docs/guide/analyzer#eecs010)、EECS013、EECS014）。

**比较过。**
- **通过查询缓存检查过滤条件：** 每次调用都要按过滤条件查一次表集合，比 job 本身还贵；检查这一行所在表的掩码和存在位，过滤条件每个组件 O(1)。
- **像遍历一样用 Interlocked 冻结和计数：** 每次调用约 12 ns；结构闸门空闲时只有所有者线程会碰它们。

## D34. 通过接口给分组加过滤条件 [#d34-group-filters-through-interfaces]

**决定。** 系统分组自己实现、或通过它的某个接口继承了 `IGroupWith<T>` / `IGroupWithout<T>`，就和在分组上写 `[With<T>]` /
`[Without<T>]` 一样带上过滤条件。生成器把这些接口和特性一起读出来，运行时什么都不变。

**原因。**
- **泛型分组没法用特性写出过滤条件。** C# 不允许类型参数做特性的类型实参（CS8968），所以 `[With<Inbox<TActor>>]` 写不到
  `IActorGroup<TActor>` 上。接口可以带类型参数，一个接口就能给每种 actor 类型各配一个分组。
- **同样的过滤，同样的开销。** 接口最终变成分组里每个 `[ForEach]` 方法相同的 `With` / `Without`，每个方法只构建一次；遍历时分不出
  它们来自哪里。
- **其他程序集的类型也能用。** 框架可以提供标签和接口，封闭类型由用户写（`struct Map : IActor<Map>` 按 `In<Map>` 过滤）。

**比较过。**
- **特性里传 `Type` 参数**（`[GroupWith(typeof(Inbox<>))]`，再用分组的类型实参封闭）：特性同样不能接受绑定到分组类型实参的开放泛型，
  绑定规则还得我们自己发明。
- **把过滤条件写在分组的静态成员里：** 生成器就得执行代码；接口只是符号。

## D35. 读记录时可以不算变更 [#d35-a-record-can-load-without-counting-as-a-change]

**决定。** `LoadEntitiesInto(input, entities, markWritten: false)` 读记录时不打 tick：记录里的每个组件加载后 tick 都为 0（从未写过），
不管是覆盖原值还是新加的；记录里没有的组件保留各自的 tick。默认仍是 `true`。

**原因。**
- **恢复出来的记录不是新变化。** 否则按 `[Changed<T>]` 保存或同步的系统，会把刚从数据库读出来的数据原样写回去。
- **被覆盖的值的 tick 描述的是一个已经不存在的值。** 保留它，预制体的默认值就算写入过，按预制体创建的 actor 每次激活都会把刚读到的
  记录再存一遍。
- **读档本来就要决定 tick**（每个实体搬一次表，再写值）；清掉它们没有额外开销。

**比较过。**
- **保留被覆盖值的 tick**：恢复的 actor 每类就得多一个不带持久化组件的预制体。
- **读完再清掉整行的 tick**：记录里没有的组件，之前的写入也会一起丢掉。
- **单独的 `RestoreEntitiesInto`：** 和原调用只差一点；用参数在调用处写明更清楚。

## D36. 不加：并行的 span 方法、行的最后写入 tick、公开读写集、多个 World 共享并行预算 [#d36-not-added]

**决定。** 权衡了四个需求，都没有加。

**原因。**
- **span 方法上的 `[ForEach(Parallel = true)]`。** 10 万个实体，`ParallelForEachBenchmark`：重的转向计算，并行批处理 766 µs，逐实体并行
  727 µs；轻的漂移计算分别是 54.5 µs 和 55.6 µs（单线程 107 µs）。多线程时逐实体遍历已经跑满内存带宽，所以 span 方法仍然只在一个线程上跑
  （EECS010）。`World.ForEachBatchParallel` 是因为另一个原因才有的：并行归约把部分结果放在每段行的局部变量里（[D69](#d69-reductions)）。
- **`entity.LastWriteTick<T>()`。** `entity.Run(ref job, QueryFilter.Create().Changed<T>(tick))` 就能回答单个实体“之后有没有写过”，
  不用公开 tick 列。
- **公开 `SystemAccess`。** 读写集是调度器做决定的依据；公开就把它的形状冻结进了 API，而调度器之外已经没有用处。
- **多个 World 共享一个并行预算。** 宿主给每个 World 设 `WorldOptions.MaxDegreeOfParallelism` 即可；共享预算意味着跨 World 共享状态，
  而每个 World 只属于一个所有者线程。

## D37. EasyEcs 包自带 Nino 的生成器 [#d37-the-easyecs-package-brings-ninos-generator]

**决定。** EasyEcs 引用 `Nino` 包（运行时加生成器），不再只引用 `Nino.Serialization`（只有运行时）。`Nino.Generator` 通过
`buildTransitive` 提供分析器，所以引用了 EasyEcs 的项目，`[NinoType]` 组件不用自己加包就能生成格式化器。

**原因。**
- **只装一个包。** 存档是内置功能；以前托管组件还要再引用一个包，版本要和 EasyEcs 用的 Nino 一致，漏了就在运行时 `Save` 抛异常。
- **版本不会错开。** 生成器总是和 EasyEcs 构建时的运行时一致；手动引用更旧的版本会在还原时报 `NU1605`，而不是悄悄用另一个 Nino 编译。
- **代价很小。** 没有 `[NinoType]` 类型的项目里，生成器只写一个空的 internal 注册类。

**比较过。**
- **继续用 `Nino.Serialization`，在文档里说明要再加一个包**：用户正是在这一步漏掉的。
- **把 Nino 的生成器打进 EasyEcs 包**：等于复制别人的分析器，还要手动保持同步。

## D38. 隐藏列不再按组件泛型 [#d38-the-hidden-columns-are-not-generic-over-their-component]

**决定。** 被追踪组件的变更 tick 列和禁用组件的标记，改用非泛型类型（`ChangeTick`、`DisabledTag`），每个所属组件一个位，
用所属组件的 `Type` 描述（它的上下文卸载时一起释放）。公开的 `Disabled<T>` 保留：它的位就是 `T` 的禁用标记位。

**原因。**
- **Native AOT 零警告。** 以前 `ChangeTicks<T>` 和组件走同一条泛型注册路径，AOT 编译器会看到没有尽头的
  `ChangeTicks<ChangeTicks<...>>`（以及 `Disabled<Disabled<...>>`）：凡是有被追踪组件的程序都会报 IL3054，内置的 `ChildOf` 也算，
  “警告即错误”的构建直接失败。
- **运行时没有变化。** tick 列本来就是按位找到的 8 字节非托管行；现在这个位来自组件自己注册时的静态字段。

**比较过。**
- **在包里压掉 IL3054：** 库压不掉用户构建里的警告，而且对编译器来说这个递归是真的。
- **每张表在列之外另放一个 tick 数组：** 搬行、快照、存档都要多一条存储路径。

## D39. 整个读档可以不打变更 tick，系统可以从现在开始算 [#d39-a-whole-load-can-leave-the-change-ticks-alone]

**决定。** `world.Load(input, markWritten: false)` 清掉每个加载行的变更 tick（不算写入，也不算移除），和
`LoadEntitiesInto(..., markWritten: false)` 对一条记录的做法一样。`AddSystem(system, changesFromNow: true)` 把新系统的上次运行设为当前 tick，
并把 World 的 tick 往前推一格，所以它第一次运行只看到之后的写入。两者的默认行为都不变。

**原因。**
- **重启不是新消息。** 否则接着跑存档的进程，每个 `[Changed<T>]` 系统在第一个 tick 都会把所有东西存一遍或同步一遍。
- **读档之后才加的系统不需要别的处理。** 新系统第一次运行从 tick 1 开始看，清掉的行 tick 为 0。
- **`changesFromNow` 管另一种情况：** 系统加到一个行已经被代码写过（或者按默认方式读档）的 World 上，不该把这些历史当成变化。

**比较过。**
- **只做 `changesFromNow`：** 读档前就跑过的系统仍然会看到每个加载的行。
- **只设上次运行、不推进 tick：** 同一个 tick 里之后的写入会被漏掉。

## D40. 销毁的实体记进日志，每个读取方按自己的 tick 读 [#d40-a-destroy-log-read-by-tick]

**决定。** `WorldOptions.DestroyLogCapacity = n` 维护一个环形缓冲，记下最近销毁的 n 个实体：每条是 `EntityId` 加销毁时的变更 tick（16 字节），
在 `new World` 时一次分配好。id 不再存活时写一条记录：`Destroy`、`DestroyEntities`、级联销毁、`MoveEntities` 搬出本 World、
实体最后一个清理组件被移除，以及 `Restore` 或 `Load` 去掉的实体。`world.DestroyedSince(since, into, out count)` 报告 `since`
及之后的记录；读取方需要的记录已被覆盖时返回 false，读取方重新同步。默认关闭。

**原因。**
- **实体消失是同步唯一看不到的变化。** 销毁的实体没有行，`[Removed<T>]` 报告不了；以前的办法（先打一个同步会读的标签，同步完再销毁）
  只适合一个读取方，客户端各自确认到不同 tick 时就不行了。
- **标记由读取方保存，World 不为读取方存任何东西。** 每个客户端一个 tick，和 `QueryFilter.Since` 用的是同一种标记，所以一份日志能服务任意多个客户端，
  客户端连上或断开都不用改 World。
- **有界，而且不骗人。** 长期运行的服务器不可能留下每一次销毁；落后于环形缓冲的读取方会被明确告知（`DestroyLogOldestTick`），而不是拿到残缺的列表。
- **和 `IsAlive` 一致。** 句柄说“已不存活”和日志说“已销毁”永远对得上，被清理组件留住的实体也一样（最后一个清理组件移除时才记录）。
- **测量**（`DestroyLogBenchmark`，`DestroyLog` 取 0 和 4,096，两种都是 0 B）：10 轮各创建并销毁 1,000 个实体，逐个销毁不开日志 219 µs、开日志 250 µs，
  整张表一起销毁 124 和 144 µs。每轮再给 16 个客户端读记录（868 µs，对比 215 µs）是复制本身的开销：每个客户端最多拷贝 4,000 条记录。

**比较过。**
- **World 里给每个读取方存一个游标：** World 里多了每个客户端的状态，要跟着连接创建和释放。
- **无界列表：** 内存随运行时长增长。
- **把销毁的行留成过滤条件能看到的墓碑：** 每个查询都要为已经不在的行买单。
- **持有清理组件的实体在销毁时就记录：** 日志会报告还活着（退休，带 `Retired` 标签）的实体。
- **`Restore` 和 `Load` 时清空日志：** 每次回滚后所有读取方都要重新同步；记下它们去掉的实体，读取方就能保持精确。

## D41. 带组件的实例化一次拷贝直接落到最终的表 [#d41-instantiate-with-components]

**决定。** `world.Instantiate(prefab, in c1 … in cn)`（以及整波的形式）把预制体的行和给定的组件一起直接拷进它们并集对应的表：
一次行拷贝，不经过中间表。目标表按（预制体的表，组件签名）缓存。给定的值覆盖预制体里的值，或者新加上去；预制体里被禁用、又被给定的组件会启用，
和 `Set` 一样。预制体组也支持：先创建整组，再把组件设到传入的那个预制体对应的实体上（多搬一次）。

**原因。**
- **每个实例都有点不一样，才是常态：** 带父实体的子实体、带主人的投射物、放在某个位置的单位。先 `Instantiate` 再 `Set` 会拷两次行，
  还可能建出一张别处都不用的表。
- **第一次之后每次刷出只查一次。** 缓存同时给出目标表和列的拷贝计划。
- **测量**（`PrefabBenchmark`，`InstantiateThenSetChild` 对比 `InstantiateWithChild` 和 `InstantiateBatchWithChild`，刷出 1,000 个带父实体的实例，0 B）：
  先刷出再设置 `ChildOf` 要 109–115 µs，直接给出 `ChildOf` 要 85–93 µs，批量形式 46–47 µs。

**比较过。**
- **沿着预制体所在表的 `AddBits` 转移边走：** 会在 World 里建出一张只有预制体组件的表（没人用），每个组件还要走一条边。
- **不支持预制体组：** 带父实体刷出一组很常见（首领和护卫挂在一个小队下）；给那一个实体多搬一次，比再加一个 API 划算。

## D42. 内存只在要求时归还：`TrimExcess` [#d42-trimexcess-on-request-only]

**决定。** 表满了就翻倍，从不自己缩小。`world.TrimExcess()` 删掉所有空表（空掩码的那张表和存活快照持有行的表除外），压紧表的注册表，
忘掉被删表的转移边和缓存的匹配结果，把其他表缩到行数向上取整的 2 的幂（至少 64），并释放存档、读档、迁移和预制体查找用的缓冲。
快照按新的表顺序重新编号，照样能恢复。实体记录（`Meta`）和值索引的节点保持原长度。

**原因。**
- **峰值不是常态。** 为一次活动装过 10 万实体的 World，会一直留着这些行，空表也一直在每个查询的匹配列表里；长期运行的服务器需要把它们还回去。
- **缩不缩只有宿主能定。** 宿主知道空闲时刻什么时候到（一波怪之后、两局之间）；World 自己缩了，实体回来时就会在某个 tick 里分配。
- **容量取 2 的幂**，和其他表的扩容规则一致：紧接着的添加不会马上又重新分配。
- **`Meta` 不缩。** 句柄访问实体记录时不做边界检查；把它缩小，每次访问都要付出代价。
- **测量**（`TrimBenchmark`，16 张和 256 张表）：把 100,000 个实体的峰值留下的内存还回去，要 47 µs 和 199 µs（31 KB 和 181 KB：新的、更小的数组）；
  没有可还的内存时 54 ns 和 145 ns。

**比较过。**
- **低于某个填充率就自动缩：** 在阈值附近来回抖动，还会出现没人要求的分配。
- **注册表里留空洞：** 每次遍历表都要检查。
- **清掉所有转移边：** 每张保留下来的表下一次结构变更都要重新查找。
- **让快照失效：** 回滚用的快照环每次整理都会坏掉。
- **精确到行数，或者“保留 N 次更新用量”的参数：** 整理后的第一次添加又要扩容；参数则把宿主本来就在做的决定写死成策略。

## D43. 系统报告分配了多少、访问了多少；调度是一份描述 [#d43-stats-and-schedule]

**决定。** 打开 `MeasureSystems` 后，`SystemStats` 新增 `LastAllocated` / `TotalAllocated`（这次运行在自己线程上分配的字节数，
加上它的并行 `[ForEach]` 在辅助线程上跑的块）和 `LastEntities` / `TotalEntities`（每个 `[ForEach]` 遍历开始时按它的过滤条件数出的匹配数）。
`world.DescribeSchedule()` 返回一组以名字表示的记录（分组、阶段、系统及其读写集、等待关系、只靠注册顺序的系统对），带 `ToString()` 和 `ToMermaid()`。

**原因。**
- **系统变慢，要么是活多了，要么是在分配。** 光看时间分不出来；字节数和实体数能分出来，而且是在线服务器上按系统分出来。
- **循环保持原样。** 实体数是每次遍历开始时的一次 `Count`；在行循环里计数，不管统计开没开，每一行都要付出代价。关闭时每次遍历只多一次字段判断。
- **在哪里分配就在哪里数。** 每次运行、每个辅助块前后各调一次 `GC.GetAllocatedBytesForCurrentThread`，数到的正好是这个系统的工作，并行阶段也一样。
- **给描述，不给读写集。** 调度器的 `SystemAccess` 仍然是内部的（[D36](#d36-not-added)）；读的人需要的是名字和阶段，记录的形状可以变，不牵动调度器。
- **测量**（`ParallelSystemsBenchmark` 的 `Measure` 取 false 和 true，`IntrospectionBenchmark.Schedule`，每次更新 0 B）：100,000 个实体的一次更新，单线程不统计 349–358 µs、统计 369–372 µs（+4–6%），
  并行阶段 232–257 µs 和 275 µs。`DescribeSchedule` 要 94 µs、26 KB：是给工具用的调用。

**比较过。**
- **在循环里数访问的行：** 每次遍历的每一行都有开销。
- **把匹配表的行数加起来：** 逐行测试的过滤条件（`Without`、`Changed`）下是错的。
- **只数调用线程，或者用进程级计数器：** 前者漏掉并行辅助线程，后者把别的系统、别的 World 也算进来。

## D44. 分片：按 64 行位字切分的过滤条件，由系统的运行次数选片 [#d44-slices]

**决定。** `[ForEach(Slices = N)]` 传入 `QueryFilter.Slice(RunCount % N, N)`，其中 `EcsSystem.RunCount` 是系统已完成的运行次数。
每张表从遍历开始时的行数出发，按 64 行的整数倍切分；匹配结果里的第 i 张表从第 (index + i) mod N 片开始。`ForEach` 系列调用遵守分片；
`Query`、`Count`、`Any`、`DestroyAll`、`entity.Run` 和批量调用遇到分片过的过滤条件直接抛异常。`[Changed<T>]` / `[Removed<T>]` 方法不能分片（EECS035）。

**原因。**
- **尖峰变成缓坡。** 处理大量实体的系统（重新给目标打分、扫描会话）每次更新只花约 1/N，而不是全压在一次更新上。
- **按位字切保住快速路径。** 切在存在位字上，遍历用来跳过的 64 行测试和摘要不会被拆开；不足 64 行的表算一片，轮转则把很多小表分散到各片。
- **状态是系统本来就有的数据。** 运行次数作为调度器的簿记放在系统上，不在用户代码里，也不在 World 里。
- **只数一片的 `Count` 几乎从来不是想要的。** 需要全部行的调用直接抛异常，而不是只回答一片。
- **测量**（`SlicesBenchmark`，100,000 个实体，Slices 取 1 和 4，0 B）：分片后的一次更新 72 µs，对比 287 µs（稳定遍历）；83 对比 322 µs（带实体句柄）；
  36 对比 113 µs（并行）。把每行都访问一遍的四次更新要 295、319 和 127 µs：分片的代价分别是 3%、几乎为零和 12%。

**比较过。**
- **精确到行的切分：** 位字被拆到两片里，只能逐行测试。
- **每个 `ForEach` 加一个带分片参数的重载：** 为一个过滤条件字段多出一倍 API。
- **把分片状态放在 World 里：** 分片方式不同的系统会共用它。
- **让 `Count` 和 `Query` 也遵守分片：** 悄悄地只回答一部分。
- **允许 `Changed` / `Removed`：** 每次运行都推进系统的上次运行 tick，其他片的行会丢掉它们的变更。

## D45. 唯一键：标记接口、预先建好的索引、写入前先占键 [#d45-unique-keys]

**决定。** 实现 `IUniqueIndexed<TKey>` 的组件，在每个 World 里从第一张含它的表出现起就有索引；任何会让第二个实体拿到别人已有的键的写入，
都在改动任何东西之前抛出 `InvalidOperationException`（存档里同一个键出现两次则是 `InvalidDataException`）。索引的工厂由生成的模块初始化器注册
（或者由第一次 `world.Index<T, TKey>()` 注册）。引用类型键为 null 表示没有键。`EntityId` 键不能是唯一键（EECS036）。

**原因。**
- **唯一性属于类型。** 账号 id、会话令牌在每个 World 里都唯一；做成按 World 的选项，就会有某个 World 接受重复。
- **事先检查，从不回滚。** 每条路径（Set、创建、`Instantiate`、`Clone`、`SetAll`、`Enable`、读档、搬移）都在存值或搬行之前占好键，
  索引、分组和变更 tick 永远看不到做了一半的写入。
- **必须预先建好，因为懒建的索引没法检查。** 普通索引在第一次查找时才建；唯一索引必须看到第一次写入。
- **不用反射。** 标记接口是一次 JIT 能折叠掉的类型判断，工厂是生成的，Native AOT 什么都不用配。
- **测量**（`IndexBenchmark`，100 次换键和 100 次查找，0 B）：`IIndexed<long>` 24.6–24.9 µs，`IUniqueIndexed<long>` 25.2–25.4 µs：
  占用检查大约每次写入 6 ns。

**比较过。**
- **对键类型做反射：** AOT 警告，每个类型一次冷启动。
- **用默认接口方法或访问者拿键：** 每次写入一次虚调用。
- **先写，冲突了再回滚：** 索引和分组会看到中间状态。
- **`EntityId` 键：** 读档和搬移在拷完行之后才改写它们，来不及事先检查。

## D46. `Mut<T>` 只给写了的行打 tick，行不会动时直接按行打 [#d46-mut-stamps-per-write]

**决定。** 对调度器和变更 tick 的继承来说，`Mut<T>` 参数算作对 `T` 的写入，但行循环不给它的列打 tick：`Write()`（以及真正存了值的
`SetIfChanged`）给它写的那一行打 tick。单线程且不做结构变更的方法按一段段连续的行遍历，每个 `Mut<T>` 知道自己的表和行，写入时直接给这一行打
tick；会做结构变更的方法和并行的逐实体方法里，写入前先查出实体当前所在的行。批量方法仍然用 span（EECS009），被索引和分组的组件仍然用 `Set`
（EECS015）。每条路径都写入的 `ref` 参数，分析器不会建议改成 `Mut<T>`（EECS025 不变）；有路径不写入的是 EECS053
（[D66](#d66-a-ref-written-on-some-rows)）。

**原因。**
- **重算了不等于变了。** 每个 tick 经 `ref` 写一遍目标的系统会给每一行打 tick，于是每个 `[Changed<T>]` 读取方都要访问每一行；
  `Mut<T>` 只给值真变了的行打 tick。
- **行不会动的地方，行是已知的。** 不做结构变更的遍历里，整个调用期间访问到的行就是实体的行；方法体里的结构变更会搬走实体，所以那里要查行。
- **写入的开销就是它本身。** 大多数行都要写的地方，普通 `ref`（每段行一次批量打 tick）更便宜；哪种情况只有数据知道，所以分析器不出声。
- **测量**（`ChangeTrackingWriteBenchmark`，每个 tick 重算 100,000 个目标，其中 10% 会变）：只算写入方，`ref` 用 110 µs，`Mut<T>` 用
  135 µs（每行一次比较，对比一次批量打 tick）；加上下游的 `[Changed<T>]` 读取方，分别是 162 µs 和 172 µs，读取方从 52 µs 降到 37 µs。
  每次写入都查实体时，写入方要 348 µs。

**比较过。**
- **每次写入都查实体：** 在上面的测量里是按行打 tick 的 2.6 倍。
- **每行一个“写过”掩码，遍历后合并：** 每行多一份存储，还要多遍历一遍。
- **EECS025 建议从 `ref` 改成 `Mut<T>`：** 大多数行都写的地方，改完反而更慢。

## D47. `SetIfChanged` 用 `IEquatable<T>` 比较，没有就比字节 [#d47-setifchanged-equality]

**决定。** `entity.SetIfChanged(value)`、`Mut<T>.SetIfChanged(value)` 和生成的 `SetXIfChanged(…)` 在组件实现了 `IEquatable<T>` 时用它比较
（record struct 都实现了），否则比较非托管组件的字节；没实现 `IEquatable<T>` 的托管组件抛 `NotSupportedException`。生成器只给能比较的、
被追踪、被索引或分组的非标签组件生成 `SetXIfChanged`。

**原因。**
- **不装箱。** 结构体的 `IEquatable<T>` 会被去虚化；类型判断都是 JIT 时的常量。
- **比字节只会往安全的方向错。** 字节相同就是值相同；按别的规则相等的值（`-0.0` 和 `0.0`）算作变了：多打一次 tick，绝不会漏打。
- **只在有意义的地方生成。** 不追踪、不索引的组件，跳过相同的写入什么也省不下。

**比较过。**
- **所有结构体都用 `EqualityComparer<T>.Default`：** 没有 `IEquatable<T>` 的结构体会走 `ValueType.Equals`，装箱还要反射。
- **所有类型都比字节：** 对引用和自定义了相等性的类型是错的。
- **强制要求 `IEquatable<T>`：** 普通的非托管结构体就用不了了。

## D48. 并行写被追踪组件时按 4,096 行切块 [#d48-parallel-tracked-chunks]

**决定。** 写被追踪组件的并行 `[ForEach]`（或 `ForEachParallel` job）按 4,096 行的整数倍切块，最少 4,096 行，每块都结束在表里块大小的整数倍处（分片也一样，分片可能从任意一个 64 行位字开始）；
其他并行遍历仍按 64 行对齐、每块至少 1,024 行。

**原因。**
- **块摘要是共享的。** 被追踪列每 4,096 行共用一个变更 tick 摘要，更新它是一次普通的读-改-写。同一块里的两个分块会在上面竞争，丢掉一次更新，
  于是 `[Changed<T>]` 读取方可能跳过被写过的行。按块对齐后，每个块只有一个写入方。
- **代价是小表的分块变少。** 表要更大才会被分给多个线程。
- **测量**（`ParallelForEachBenchmark`，100,000 个实体，0 B）：不写被追踪组件的遍历分块不变，耗时和 4.6 相同，差异在噪声以内
  （并行 623–666 µs，之前 742–783 µs）。

**比较过。**
- **原子更新摘要：** 每次遍历的每次写入都多一次 interlocked 操作，不管是不是并行。
- **每个分块各自一份摘要，遍历后合并：** 每块多占内存，每次并行遍历多一次合并。

## D49. `ChangedAny`：每种一个 OR 集合，每个过滤条件一个 tick [#d49-changedany-semantics]

**决定。** `QueryFilter.ChangedAny<T1..Tn>(since)` 选出其中至少一个组件在 `since` 及之后被写过的行；一行凭它自己有的组件入选。
一个过滤条件的所有 `ChangedAny` 调用合成一个集合，所有 `RemovedAny` 调用合成另一个，各集合之间、以及和其他过滤条件之间都是 AND。
一个过滤条件只有一个 tick，`Since` 一次挪动它的全部变更过滤条件。集合里的列自 tick 以来都没被打过 tick 的表整张跳过，没有任何列写过的位字和块也跳过。

**原因。**
- **同步时，一个单位的任何一部分变了就要发。** 几个 `[Changed<T>]` 的意思是全部都变；每个组件各查一次，同一行会访问两次，还得去重。
- **一个 tick 就够了。** 过滤条件按用途存一份，带着每个客户端确认过的 tick 跑。
- **集合放在过滤条件外面。** 过滤条件只存这对集合的一个驻留 id（4 字节，没有集合时为 0），每对新集合查找一次，之后不分配：
  没有集合的过滤条件（最常见的情况）大小不变，检查表时先看行计划的一个标志，再做集合的工作。
- **每种一个集合就够了。** 多个独立的 OR 集合要让每个过滤条件带一个列表，而没有需求用得上。
- **测量**（`ChangeTrackingBenchmark`、`CountBenchmark`、`SparseBenchmark`，对比 4.6）：没有集合的过滤条件开销不变，
  每个用例的差异都在 ±7% 以内，也就是这些测量本身的波动。

**比较过。**
- **多个独立的 OR 集合：** 每个过滤条件状态更多，找不到用处。
- **每个组件一个 tick：** 每个客户端每个组件一个过滤条件，而客户端只有一个确认 tick。
- **每个组件跑一次查询再合并：** 同一行访问两次。

## D50. 重启存档可以不写某些类型，重启读档可以保留单例 [#d50-restart-saves]

**决定。** `world.SaveWithout(output, in exclude)` 写出整个 World，但不写 `ComponentSet` 里的组件和单例；`world.LoadKeeping(input, in keep, markWritten)`
让 `keep` 里的单例保持 World 现在的样子（跳过存档里的值）。`ComponentSet` 用第二个掩码存单例（`WithSingleton<T>()`；`With(Type)` 两种都接受）。
`SaveEntitiesWith` 拒绝含单例的集合；`LoadKeeping` 拒绝含组件的 `keep`。

**原因。**
- **重启要带上的是状态，不是周围的运行时。** 连接、缓存和旧版本的配置不能带回来，而且常常没有格式化器。
- **新进程先设好自己的配置。** 把旧 World 读进来会把旧配置一并带回；保留这个单例只要一个集合，建一次就行。
- **每个集合只说调用能做到的事。** 实体组存档不写单例，读档会替换所有实体，所以写了调用做不到的内容的集合直接被拒绝，而不是被悄悄忽略。
- **测量**（`SnapshotBenchmark`，`SaveWithout` 对比 `Save`，`LoadKeeping` 对比 `Load`，100,000 个实体，跑两次）：去掉一个组件和单例的存档用 225–250 µs，整个 World 存档是 232–235 µs；保留单例的读档用 906–934 µs，完整读档是 954–969 µs。挑出不要的部分没有可测的开销。

**比较过。**
- **单独的 `SingletonSet` 类型：** 一次重启要建两个集合。
- **“保留”组件表示不加载它：** 读档会替换实体，保留下来的组件不属于任何实体。
- **`SaveEntitiesWith` 忽略集合里的单例：** 集合做的比它写的少，却不吭声。

## D51. 不加：运行条件、按时间的间隔、必需组件、实体映射表、Meter、校验和、部分快照 [#d51-not-added]

**决定。** 4.7 权衡了七个需求，都没有加。

**原因。**
- **运行条件**（`[RunIf]`，每个系统一个谓词）。系统分组让每种节奏有自己的 `Update<TGroup>()`，什么时候跑哪个分组由宿主决定；系统内部，
  `Enabled` 和 `OnUpdate` 里提前返回就够了。每个系统一个谓词，就是调度器看不见的代码。
- **`UpdatePeriod` / 系统时间**（以秒为单位的间隔）。时间归宿主的固定步长循环管；`UpdateInterval` 数的是更新次数，运行结果可复现，
  系统要时间就读一个时钟单例。
- **`[Requires<B>]`**（加 A 时自动加 B）。每种实体一个预制体，一次拷贝就带齐整套组件；隐式添加则是读代码的人看不到的结构变更。
- **实体映射表**（外部键到实体）。`IUniqueIndexed<TKey>` 就是这张表，而且每次写入都会维护它。
- **内置 `Meter`。** 数据都在 `SystemStats` 里；发布到 OpenTelemetry 是宿主自己几行代码的事（[调试与诊断](/zh/docs/guide/diagnostics)），
  EasyEcs 也就不必依赖指标库。
- **World 校验和**（帧同步里查不同步）。对 `world.Save` 的输出做哈希，用户代码里就能做；内置的话，每个用户都被绑死在一种算法和一种顺序上。
- **部分快照 API**（只拍部分组件）。用一个系统把需要的值拷进单例里的环形缓冲（[快照](/zh/docs/guide/snapshots)里的延迟补偿写法），
  只拷需要的东西，也不用多一条存储路径。

## D52. 只当身份用的 `Entity` 不让系统单独运行 [#d52-identity-entity]

**决定。** `[ForEach]` 方法的 `Entity` 参数只用于 `Id`、`Version`、`IsAlive`、`==` / `!=`，或转换成 `EntityId` 时，不给系统增加读写；
其他用法（`Has`、`Get`、别的调用、把句柄传出去）系统仍然单独运行。

**原因。**
- **身份碰不到组件。** id 和版本号就在句柄里；`IsAlive` 读的是实体记录，并行阶段里没有系统会改它（结构变更都单独运行）。
- **按实体做键很常见**（按实体的映射表、日志、回复发送方），这些系统只是拿句柄当名字，却丢了自己的阶段。
- **先看语法，保守判断。** 检查读的是方法体：证明不了无害的用法，照旧单独运行。

**比较过。**
- **把 `Has<T>` 当成读 `T`：** 存在位只在结构变更时改，但 `Get<T>` 是写，别的组件的泛型 `T` 也没法逐个调用确定；组件的读写还是只看参数这一条规则。

## D53. EasyEcs 自带的组件在 EasyEcs 里生成成员；两个类型共有的名字谁都不生成 [#d53-own-members]

**决定。** `ComponentGenerator` 在 EasyEcs 自己的编译里也为公开组件生成成员：`ChildOf` 拿到被索引组件的那些成员，但没有
`DisableChildOf` / `EnableChildOf`（它不能被禁用）；`Retired` 标签只有 `entity.IsRetired`（由 World 添加和移除）。
同一命名空间里两个结构体都会生成的成员名（标签 `Dead` 和组件 `IsDead` 的 `entity.IsDead`）两边都不生成；嵌套的组件或缓冲元素和所在命名空间里
另一个结构体同名时，一个成员都不生成。生成的类名是 `{类型}` 加一个以 `Ecs` 开头的后缀（`HealthEcsExtensions`、`HealthEcsPrefabExtensions`、
`LootEcsBufferExtensions`、`LootEcsPrefabBufferExtensions`），成员是 public 的，类和类型一样可见。

**原因。**
- **一个生成器，一种成员形状。** 用户读 `entity.ChildOf` 和读 `entity.Health` 一样；这些成员随包发布，引用方的程序集不用再为它们生成文件。
- **World 拒绝的事就不提供：** 一个永远抛异常的 `DisableChildOf` 只是一个只会失败的 API。
- **同名规则要覆盖每个名字。** 两个类型只要生成一个同名成员，每次调用都有歧义，所以嵌套的那个放弃全部成员：实体、World、过滤条件和预制体上的都不要。
  任何结构体都算，因为任何结构体都可以是缓冲的元素。
- **共有的名字没有主人。** 两个不同名的类型之间（`Shield` 的 `IsShieldDisabled` 和标签 `ShieldDisabled` 的），没有哪个理应保留它，
  读代码的人指的是哪个类型也猜不出来。每个类型只凭命名空间算出对方的名字，去掉共有的，所以两边不用看到对方的输出也会做出同样的决定，
  其他成员照常保留。
- **没有一个后缀是另一个的结尾。** 用 `PrefabExtensions` 和 `BufferExtensions` 时，`Loot` 的预制体缓冲类和 `LootPrefab` 的缓冲类都叫
  `LootPrefabBufferExtensions`。每个后缀都以同一个 `Ecs` 标记开头，类型名就在标记开始的地方结束。
- **成员 public，类按类型可见。** 看得到内部成员的程序集（`InternalsVisibleTo`）用不了 internal 的扩展属性，C# 会拒绝；internal 类里的
  public 成员能被同样的代码用到。

**比较过。**
- **手写 `ChildOf` 的成员：** 第二份实现，迟早和生成的对不上。
- **在每个引用方程序集里生成：** 每个程序集一个文件，互相可见的程序集之间还会重复。

## D54. 调用的名字说明它做什么 [#d54-names]

**决定。** 4.7 改了 4.6 的四个调用和一个生成成员的名字：`EnsureCapacity<T1..Tn>(count)` / `EnsureCapacity(prefab, count)` 改为
`Reserve`，`DestroyEntities<T1..Tn>(filter)` 改为 `DestroyAll`，`SaveEntities(output, ids, set)` 改为 `SaveEntitiesWith`，关系生成的
`RemoveX(target)` 改为 `UnlinkX(target)`。`DestroyEntities(ids)` 销毁一组 id。4.7 新增的重启调用在发布前是 `Save` 和 `Load` 的重载，
发布时叫 `SaveWithout` 和 `LoadKeeping`。旧名不保留别名。

**原因。**
- **改变含义的重载会把含义藏起来。** `Save(output, set)` 读起来像“存这些”，实际是不存它们；`Load(input, set)` 实际是保留单例。
  换个名字，调用处自己就说清楚了。
- **`count` 是再创建多少个，不是容量。** `EnsureCapacity` 读起来像 `List<T>.EnsureCapacity(total)`；`Reserve` 接收的是还要再创建多少个。
- **`DestroyEntities` 曾是两个调用的名字。** 按 id 和按过滤条件现在各有名字，`DestroyAll` 和 `SetAll`、`RemoveAll`、`DisableAll` 一致。
- **`RemoveX(target)` 和 `RemoveX()` 做的事不同。** 一个解除对某个目标的链接，另一个删掉整个缓冲区。
- **1.0 之前的规则，用在一个小版本上：** 编译器会找出每一处调用，[迁移指南](/zh/docs/migration#v4-7-renames)列出了每个名字的对应。

**考虑过的方案。**
- **保留一个版本的 `[Obsolete]` 别名：** 补全列表和文档里同一个调用有两个名字，而编译器本来就会指出要改的地方。

## D55. `Read` 遍历查询不打 tick；EECS046 指出应该这样写的循环 [#d55-read]

**决定。** `world.Read<T1..Tn>(filter)` 遍历查询的行，组件是 `ref readonly`，不打 tick；`Query` 照旧给它交出的被追踪组件打 tick。
分析器规则 EECS046（警告，有代码修复）报告只读取 item 的、带被追踪组件的 `Query` 循环。

**原因。**
- **`ref` 分不清读和写。** `Query` 的 item 交出 `ref T`，所以会给访问到的每一行被追踪组件打 tick；求和、状态页或发送同步数据，
  都会让每个 `[Changed<T>]` 读取方访问每一行。
- **第二种 item 类型，由生成器生成。** `ReadItem` / `ReadEnumerator` 和 `QueryItem` 来自同一个 `ArityGenerator` 模板，只是没有打 tick
  的那几行；生成的成员（`item.Health`）在它们上面是 `ref readonly`。
- **有了规则才会被用上。** 规则在这个仓库里找到的 17 个只读 `Query` 循环（测试、AOT 检查、一个示例）都改成了 `Read`。
- **实测**（`ChangeTrackingReadBenchmark`，100,000 个实体，每 tick 写 10 个，读一遍全部生命值，再跑 `[Changed<Health>]` 同步）：
  用 `Query` 每 tick 538 µs，用 `Read` 145 µs，两者都是 0 B。

**考虑过的方案。**
- **给 `Query` 加一个只读开关：** item 类型仍然交出 `ref T`，写入照样能编译，却不打 tick。
- **第一次写入时才打 tick：** `ref` 没有写入的钩子；在 `[ForEach]` 方法里，`Mut<T>` 就是这个钩子。

## D56. 不加：生成的 `AddSystems()`、从特性生成的缓存过滤条件、按组件的计数成员、命名的 `TryGetXRef` [#d56-not-added]

**决定。** 权衡过四个生成器功能，都没有加。

**原因。**
- **生成的 `world.AddSystems()`。** 系统按注册顺序运行，所以这个列表就是 tick 的顺序；写在构建 World 的地方，它就是调度的文档。
  生成的列表会按文件或名字固定一个顺序。
- **从特性生成的缓存过滤条件**（由字段上的 `[With<T>]` 生成一个 `QueryFilter` 字段）。`static readonly QueryFilter` 本来就只有一行，
  生成出来反而看不到它在哪里构建。
- **按组件的计数成员**（`world.CountPlayer()`）。`world.Count<Player>()` 字数一样多，意思也一样；每个组件多一个成员只会让补全列表变长，
  一行也没省。
- **命名的 `TryGetXRef`。** `entity.TryGetRef<T>(out found)` 本来就少用；常用的调用已经有命名成员（`TryGetX`、`entity.X`）。

## D57. 退休的实体按已经没了处理 [#d57-retired-is-gone]

**决定。** 对持有清理组件的实体调用 `Destroy` 会让它退休：保持存活、带 `Retired` 标签，直到清理组件被移除。释放之外的每个调用都把它当作
已经没了：过滤条件没写 `Retired` 时 `SetAll` 不碰它，`MoveEntities` 跳过它，`Clone` 抛异常，失去其他组件也不算移除（它们的变更 tick
被清零，而不是打上新 tick）。被移动的实体，清理组件留在退休的原实体上。`RemoveAll` 仍然会处理到退休的实体。名字和文档里的“销毁”
只表示已经没了：销毁日志在 id 被释放时记下它，退休的实体则是在最后一个清理组件被移除时。

**原因。**
- **一份资源只释放一次。** 清理组件代表 World 之外的东西（一个 socket、一个座位）。移动或克隆出它的副本，就会释放两次；
  退休的实体被移走，就会存在两份。
- **和被释放的实体答案一致。** 已销毁的实体没有行：哪个过滤条件都找不到它，由销毁日志报告。退休只是为了释放才保留这一行，
  所以 `[Removed<T>]` 读取方和批量写入看到的不能比被释放的实体更多。
- **`RemoveAll` 就是释放。** 退休的实体只有清理组件和 `Retired`，`RemoveAll` 别的组件根本碰不到它；`RemoveAll` 清理组件正是清理
  pass 释放它的方式。`DisableAll` 和 `EnableAll` 也碰不到它：清理组件不能被禁用。
- **代价很小。** `SetAll` 在过滤条件里加上 `Without<Retired>`：没有这个标签列的表，每行不多做任何测试。
  `BulkBenchmark.StunAndLift`（对 10 万个实体 `SetAll` + `RemoveAll`）前后测得一样，差别在运行噪声之内，两者都是 0 B。

**考虑过的方案。**
- **在批量遍历里逐行测试：** 每张表每行都多一个分支，而排除位在从没有过清理组件的表里毫无代价。
- **交给过滤条件（手写 `Without<Retired>`）：** 默认调用就会让退休的实体复活。

## D58. `AddSingleton` 拒绝已存在的单例 [#d58-add-singleton]

**决定。** World 里已经有 `T` 时，`AddSingleton<T>()` 抛 `InvalidOperationException`；重置是一次写入（`world.SetX(…)`、
`world.X = default`），`GetOrAddX()` 原样取用。

**原因。** 第二次添加多半是初始化跑了两遍，或者 `Load` 已经带回这个单例后又添加了一次，悄无声息的重置会丢掉它的值。名字说的是“添加”：
现在这个调用要么添加，要么说明为什么不能。写入不换存储，所以重置之后 `SingletonRef<T>` 句柄照样指向这个单例。

**考虑过的方案。** **保留重置并写进文档：** 它掩盖的错误要到后来某个值出错时才会显现。

## D59. 跨结构变更的 ref、行不通的过滤条件、搬两次的创建：对应的规则 [#d59-analyzer-rules]

**决定。** 用法规则和性能规则新增六条，EECS042 只报告往索引里加实体的修改。

| 规则 | 级别 | 为什么是这个级别 |
| --- | --- | --- |
| EECS047 结构变更之后还在用 ref | 警告 | ref 可能仍然正确（变更移动的是另一张表的行），所以规则只报它能追踪到的情况：同一个块，按顺序，ref、变更和使用之间没有分支、循环或 lambda |
| EECS048 对清理组件或 `ChildOf` 调用 `Disable` | 错误 | `Disable<T>()` 和 `DisableAll<T>()` 对它们抛 `InvalidOperationException` |
| EECS049 没有实体能通过的过滤条件 | 错误 | 一个组件既被要求（参数、`[With<T>]`、`[Changed<T>]`、分组的 `[With<T>]` 或 `ISystemGroupWith<T>`）又被排除（`[Without<T>]`、`IGroupWithout<T>`）：方法永远不会运行 |
| EECS050 一个过滤条件里的第二个分组 | 错误 | 换一个分组（另一个组件或另一个常量值）时 `InGroup` 抛 `ArgumentException` |
| EECS051 遍历进行中更新 World | 错误 | 循环还在走表，所有系统就跑了一遍；更新还会填掉遍历留下的空洞，把循环还没走到的行挪到它身后，循环就漏掉了它们 |
| EECS052 创建之后紧跟 `Set` | 警告，有代码修复 | `AccessBenchmark.CreateThenSet`：1,000 次只带一个组件的创建，再 `Set` 另一个组件，加上销毁，44.4 µs；同样的创建直接带两个组件 25.8 µs（1.73 倍），两者都是 0 B |

`AccessBenchmark` 跑在 [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same) 的那台机器上
（BenchmarkDotNet，共享的 4 核 2.1 GHz Xeon，.NET 10.0.13）。

**原因。**
- **每条规则指出的要么是运行时会拒绝的代码，要么是测出来的代价。** EECS048、EECS050 和 EECS051 是运行时会抛异常或破坏 World 状态的调用；
  EECS049 是能编译却永远不会运行的方法。它们和 EECS040 到 EECS045 一样是错误。EECS047 和 EECS052 是警告：代码在某些 World 里能工作，
  或者能工作但有代价。
- **EECS048 用自己的编号。** EECS045 说的是手写 World 自己的标签；这里调用本身是 World 的，被拒绝的是组件。修法也不同（移除组件）。
- **EECS047 只看直线代码。** 一次变更会不会移动 ref 指向的行，取决于运行时的表；跨分支和循环，规则会报出变更和使用从不一起执行的代码。
  它跳过不移动行的调用：`Remove` 和 `Enable`（一个存在位）、对 ref 持有的那个组件 `Set`（原地写入）、只复制或调度的成员
  （`Capture`、`Save`、`AddSystem` 等），以及销毁查询项的实体（遍历期间留下墓碑）。
- **EECS042 只报告加入。** 索引遍历会跳过空洞：遍历期间移除组件、断开关系、销毁实体都是允许的，层级自己的级联也会在关系遍历中删除链接。
  会破坏遍历的是增长的键：之前变空的列表会交给下一个增长的键，而它可能正是正在读的列表。修改之后紧跟 `break`、`return` 或 `throw` 时，
  遍历在读下一个列表之前就结束了，所以也不报。关系遍历（`Find(target)`）和 `Descendants` 与 `Find(key)` 一样覆盖。
- **EECS052 是代价，两次 `Set` 不是。** 一次一个地添加两个组件，和一次调用的代价差不多（D29，已放弃）；创建之后再 `Set`，行要放两次，
  第一张表可能只在这一刻存在。修复在能绑定时把值移进创建调用：值来自方法调用或该实体、分组组件、World 自己的标签、已经带了九个组件的创建，
  都不修。

**考虑过的方案。**
- **每次调用时内联构造过滤条件**（`world.Count<T>(QueryFilter.Create().With<U>())`）：过滤条件是不含引用的小结构体
  （[D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)），构造它也没有测出代价（D29）。不加规则。
- **带流分析的 EECS047**，跨分支和循环：报得更多，每一条却更不确定，而这条警告会让把警告当错误的构建失败。放弃。
- **把 EECS048 并进 EECS045**：一个编号对应两种原因和两种修法。放弃。

## D60. 一个错误一条诊断 [#d60-one-diagnostic-per-mistake]

**决定。** 两条分析器规则报同一段代码时，一条让给另一条：由修法能消掉另一条情形的那条来报。没有合并或删除规则，编号不变。

| 代码 | 报告 | 让出 | 为什么是它 |
| --- | --- | --- | --- |
| `var t = e.Get<T>(); t.V = 1;`（改了又丢掉的副本） | EECS038 | EECS025、EECS015 | 修法是保留 ref（或用 `Set`）；改成 `Read` 写入照样丢 |
| `[ForEach, Without<P>] static void A(ref P p, ...)` | EECS049（`[Removed<T>]` 时是 EECS016） | `p` 上的 EECS025、EECS026、EECS015 | 方法永远不跑，参数的代价无从谈起 |
| `[ForEach(Parallel = true)] void A(ref P p)` | EECS010，附“改成 static” | EECS029 | 修法相同；挡住构建的是这条错误 |
| `[ForEach(Parallel = true)] static void A(..., ref Clock c)` | EECS010 | EECS025 | 它的消息已经说了“改成 `in`” |
| 只计数、或对每个实体做同一个修改的查询循环 | EECS032、EECS030 | EECS046 | 修法去掉了循环，没有可读的了 |
| `[ForEach]` 方法或 job 里的 `w.TrimExcess()` | EECS041、EECS013 | EECS028 | 调用在那里会抛异常，分配根本不会发生 |
| 查询循环里的 `item.Entity.Remove<Retired>()` | EECS045 | EECS030 | 换成 `RemoveAll<Retired>` 是同一个错误 |
| `[ForEach]` 方法或 job 每行都 `e.Get<Q>()` | EECS027 | EECS033 | 修法把这次查找拿掉了 |
| `var e = w.CreateEntity(a); e.Set(b);` | EECS052 | EECS033 | 修法把 `Set` 并进创建 |
| `[ForEach] static void A(DynamicBuffer<T> items, ...)` | EECS002 | EECS012 | 修法相同（`in` / `ref`）；EECS002 是错误 |

**原因。**
- **一个错误两条诊断，读起来像两个问题**，两个修法还可能互相抵消（EECS025 的 `Read` 和 EECS038 的 `ref var`）。让出只发生在另一条规则
  已经报告的代码上，每条规则自己的情形照报，`GeneratorTests.OneMistakeIsReportedOnce` 把这些情形固定下来。
- **方法要求什么，只有一份来源。** EECS016、EECS049、参数代价规则和系统生成器读同一个列表（`Symbols.Requirements`：方法的过滤条件、
  查询的参数、所属组的过滤条件）；分析器各文件和生成器各自复制过的判断（`IsStable`、`SystemOf`、`JobInterface`、`IsDisableable`、
  `IsWorldTag`、`AlwaysRuns` 等）都放进了 `Symbols`。

**考虑过的做法。**
- **把 EECS016 并进 EECS049**（都是没有实体能通过的过滤条件）：EECS016 的原因和措辞不同（`[Removed<T>]` 访问的是失去 T 的实体），
  编号也要稳定。分开保留，读同一个列表。
- **把 EECS029 并进 EECS010**：EECS029 也管顺序执行的方法，在那里它是代价而不是错误。保留；EECS010 提供它的修法。
- **保留为两条诊断的：** 组件里存实体的 buffer 字段（EECS012 是复制 buffer，EECS017 是存 `Entity`：两个错误、两个修法），每处写出
  `DynamicBuffer<Pair>` 的 EECS017，EECS034 旁的 EECS026，以及 EECS032 的存在性判断或另一个表达式上 EECS033 旁的 EECS046（修法可以叠加）。

## D61. 要等遍历结束的调用共用一个检查；带成员的预制体不在其中 [#d61-one-pass-guard]

**决定。** 遍历进行中不能运行的调用（`Capture`、`Restore`、各种存档和加载、`MoveEntities`、`GroupBy`、`RemoveTypes`、`TrimExcess`）
都走同一个检查 `ThrowIfIterating(call)`，异常消息写出被拒绝的调用。实例化带成员的预制体不在其中：它和 `CreateEntities` 一样只是追加行，
系统可以在自己的遍历里做。`LoadEntities` 和 `LoadEntitiesInto` 仍然拒绝。

**原因。**
- **拒绝要说清拒绝的是什么。** `Save`、`Load`、`MoveEntities` 和 `GroupBy` 抛的都是同一条关于快照的消息，`RemoveTypes` 和
  `TrimExcess` 又各有各的说法。调用名是传给检查的常量；消息只在 `NoInlining` 的抛出辅助方法里拼，通过检查的调用不分配。
- **拒绝放在需要它的调用里。** 它原来在到达（arrival）共用的行拷贝里，于是只追加新行的带成员预制体（每次放置都递增
  `StorageVersion`，遍历中的搬行留下墓碑）被拒绝，而不带成员的预制体可以。现在它放在要读或重写整张表的公开调用里。
- **一件事一个核心。** 同一次审查把各处“这个组件位有没有索引”的写法换成 `IndexOf(bit)`（分组有 `GroupingOf(bit)`），把给行补回组件的
  两个循环（一次 `Set` 多个组件、带组件的 `Instantiate`）合成 `GiveBack`，并用它替掉和快照调用同名的私有 `Restore` 重载；`GetSingleton`
  和 `SingletonRef` 的单例检查共用一个辅助方法。
- **测量**（BenchmarkDotNet，分支对比它的基线，交替运行，每次三个进程）：`RemoveMany`（`GiveBack` 路径）45.8–46.8 µs，基线
  45.2–47.8 µs；`ToggleComponent` 149–158 µs，基线 148–150 µs；`RekeyAndLookup` 24.0–25.3 µs，基线 25.6–31.5 µs；
  `RekeyAndLookupUnique` 26.7–29.9 µs，基线 26.6–29.4 µs（`IndexOf` 路径）；`Churn`、`DestroyLog`、`Bulk`、`Relation` 都在彼此误差内。
  都不分配。

**比较过。**
- **让 `LoadEntities` 和 `LoadEntitiesInto` 在遍历中运行**（它们的到达和带成员预制体一样）：加载读的是网络或存储的输入，宿主在两次更新之间处理；
  放宽这个约定是另一项变更。
- **把 `Capture()` 换成 `Capture(WorldSnapshot into = null)`**：少一个重载，但二进制不兼容，所有 cref 都要改，没有收益。保留。
- **整列和实体组的行用同一个写入方法**（`WriteColumn` / `WriteRows`）：整张表每列一次块拷贝，实体组每行一次拷贝。分开保留。
- **组件和关系用同一个目标规则类**：它们的 `Apply` 不同（移除组件、去掉链接），共同的只有两个一行的成员。保留。

## D62. 生成器在成员体外绑定类型名，比较符号不拼字符串 [#d62-generators-bind-outside-bodies]

**决定。** 生成器的转换在成员体里找到的类型名（`DynamicBuffer<T>`、封闭的泛型系统、`Query<…>` / `Read<…>` 的组件）单独绑定：
在外层类型的左大括号处做推测绑定（`Symbols.TypeNamed`），不在原处调用 `GetSymbolInfo`。生成器和分析器里的符号判断都用
`Symbols.Named(symbol, "Ns.Type<T>")` 逐级比较符号的名字，不再写 `ToDisplayString() == …`。C# 版本检查读解析选项，模块初始化器的检查读程序集名，都不读编译。

**原因。**
- **每次按键都会重跑所有转换。** 新的编译会让每个文件里每个候选节点的语义转换重跑。绑定成员体里的节点会先绑定整个成员体并做可空分析；
  在成员体里某个位置做推测绑定也一样。在类型的大括号处，名字看到的 using、命名空间和类型参数都相同（方法的类型参数除外，生成的代码本来也引用不到）。
- **每次编辑、每个候选都拼字符串。** `ToDisplayString` 每次编辑都为每个候选的每个接口拼一个字符串；生成器和分析器每次运行要问上千次。`Named` 什么都不分配。
- **测量**（`GeneratorBenchmark`：对战服务器加 40 个模块的组件、缓冲、系统和查询循环；分支和它的基线背靠背运行）：改一个方法体
  228 ms / 26.9 MB 对 149 ms / 16.8 MB，改另一个文件 249 ms / 26.9 MB 对 147 ms / 16.6 MB，首次运行 271 ms / 67.8 MB 对
  232 ms / 58.5 MB。分析器在构建里的份额（`CompileAndAnalyze` 减 `Compile`）分配 35 MB 对 42 MB，时间在误差内。

**比较过。**
- **少生成文件**（每个命名空间一个而不是每个类型一个）：驱动会把每个新文件和所有缓存的文件比一遍，但那里的时间主要是垃圾回收的；减少分配后就没了。不做。
- **分析器从生成类的类名直接找到生成成员的类型**，不遍历命名空间：523 ms / 34.6 MB 对 569 ms / 33.3 MB，在误差内。不做。
- **成员体里的 `Query` 调用也检查接收者**：需要绑定整个调用。多个都是组件的结构体组成的 `Query` 或 `Read` 视为 World 的；同名的其他调用只多出一个用不到的项文件。

## D63. 较新的 Roslyn 特性：不用拦截器，其余已在用或不需要 [#d63-roslyn-features]

**决定。** 生成器使用 `ForAttributeWithMetadataName`（`[ForEach]`）、给用户代码从不引用的内容（系统代码、`SavedTypes`）用实现输出（implementation output）、
C# 14 扩展成员和泛型特性。不用拦截器，也不用嵌入式特性定义。

**原因。**
- **拦截器没有可去掉的东西。** `entity.Get<T>()`、`Has<T>()`、`Set<T>()`、`CreateEntity(new A(), new B())` 和 `world.Index<T, TKey>()`
  读的是按类型或签名的静态只读字段（`ComponentType<T>.Bit`、`ComponentSignature<…>`），JIT 分层编译后就是常量：拦截后的方法体是同样的代码。
  系统通过模块初始化器注册，没有要替换的反射。
- **查询调用**：拦截器跳不过调用的参数（[D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)）。把常量过滤条件链上的每个调用都拦截、
  各自返回该调用点的静态过滤条件，统计 16 个实体用 25 ns，在调用处构建过滤条件是 76 ns（`CallSiteBenchmark`，按生成器会生成的样子手写）；这正是
  `static readonly` 过滤条件的结果（24 ns），而后者不需要开启任何选项，也没有隐藏的代码。
- **嵌入式特性**：特性随 EasyEcs.Core 发布，使用生成器的项目都引用它。

**比较过。** 在上面每个候选处使用拦截器；系统代码用 `RegisterSourceOutput`（IDE 会在每次按键时生成它）；在后初始化阶段输出特性源码。

## D64. 4.7 的命名：名字说明它是什么 [#d64-names-of-4-7]

**决定。** 4.7 发布前做了一轮命名审查，在 [D54](#d54-names) 之外又改了这些名字：`ITrackChanges` → `ITracked`，
`IGroupWith<T>` / `IGroupWithout<T>` → `ISystemGroupWith<T>` / `ISystemGroupWithout<T>`，`Destroyed` 标签 → `Retired`
（`entity.IsRetired`），`GetSystem<T>()` → `TryGetSystem<T>(out T)`，`world.Describe()` → `DescribeTables()`，
`ColumnInfo.Without` → `Absent`，`SystemStats.Last` / `Total` / `Average` → `LastTime` / `TotalTime` / `AverageTime`，
`UpdateCount` → `DefaultUpdateCount`，`SystemAccess.RunsAlone()` → `RunAlone()`，`TargetRules` → `TargetPolicyExtensions`，
`AddRelation` / `RemoveRelation` / `HasRelation` → `Link` / `Unlink` / `Links`（生成成员是 `LinkX(target)`），job 的
`Writes` / `OwnStamps` → `WriteMask` / `SelfStamped`，以及参数 `LoadEntitiesInto(input, targets)` 和 `QueryFilter.Slice(index, of)`。
4.7 新增的名字发布时就用新名：`WorldOptions.DestroyLogCapacity`、`GroupInfo`。不保留别名；4.6 的存档照样能读。

**原因。**
- **一个词，一个意思。** “Group”既指系统分组，又指 `IGroup` 组件；“Without”既是过滤条件，又是一个计数；“Destroyed”既指被释放的实体，
  又指为了清理组件而活着的实体（[D57](#d57-retired-is-gone)）。现在各有各的词，“销毁”只表示已经没了。
- **签名说明会找不到。** World 里没有这个系统时，`GetSystem<T>()` 返回 null。`TryGetSystem` 把这一点写进签名；仓库里没有调用需要会抛异常的版本，
  所以没有加：添加系统的代码留着 `AddSystem` 返回的引用。
- **建立链接不是加组件。** `AddX(target)` 读起来像 `SetX`；`LinkX` / `UnlinkX` / `LinksX` 和泛型的 `Link` / `Unlink` / `Links`
  是一组。泛型名字短，也有代价：名为 `Link`、`Unlink` 或 `Links` 的组件拿不到 `entity.X` 属性（实体上已有的名字，生成器会跳过），
  其他成员照常生成。
- **名字带上单位和种类。** `TimeSpan` 统计以 `Time` 结尾，和次数、字节数放在一起不会混；容量叫 `Capacity`；位掩码叫 `Mask`；
  指令（`RunAlone()`）用动词，事实（`SystemInfo.RunsAlone`）不用。
- **存档照样能读。** 存档按类型全名的哈希记录类型；`Retired` 标了 `[NinoFormerName("EasyEcs.Destroyed")]`，沿用旧 id，
  所以 4.6 存档里的退休实体读出来仍是退休的（用一份 4.6 存档的字节测试过）。
- **1.0 之前的规则：** 编译器会找出每一处用法，[迁移指南](/zh/docs/migration#v4-7-renames)列出了每个名字。

**考虑过的方案。**
- **保留一个版本的 `[Obsolete]` 别名：** 和 D54 一样，编译器已经能指出的改动，不值得在补全列表里放两个名字。
- **在 `TryGetSystem` 旁边再加一个会抛异常的 `GetSystem`：** 没有调用需要它。
- **关系只有生成成员（没有泛型 `Link<T>`）：** 那么对关系类型写的泛型代码（`Link<T>(in T)`）就没有入口。
- **给 `Retired` 一个新的存档 id：** 每份带退休实体的存档都会读不了。
- **把 `entity.Describe()` 和 `DescribeSchedule()` 也改名：** 它们的名字已经说明了描述的是什么。

## D65. 缓冲池的上限按元素类型设置 [#d65-buffer-pool-capacity]

**决定。** `DynamicBuffer<T>.PoolCapacity` 设置 `T` 的缓冲在销毁或移除时，最长多少个元素的列表会还给本线程的池。
它是元素类型上的静态属性，整个进程生效，默认是 4,096 字节的元素；设为 0 则不池化。

**原因。**
- **池属于元素类型。** 释放的列表进入按 `T` 划分的线程静态池，同一线程上的所有 World 共用，所以上限放在池所在的地方。
- **一个大小不适合所有用途。** 4 KB 能让小背包、路径这类缓冲走池，又不会占着大列表。大小固定且较大、频繁创建和释放的缓冲，
  比如玩家周围加载、卸载的区块方块，原来进不了池，每次都要分配。只对这个类型调大上限，这种反复创建就不再分配
  （`EasyEcs.Benchmark` 的 `ChunkChurnBenchmark`，对比池化与不池化）。
- **占用有上限。** 池里最多留住“没人取用期间死掉的列表数”这么多个，所以占用是这个峰值乘以容量，而且只对调大了上限的类型。

**考虑过的方案。**
- **放进 `WorldOptions`：** 池由一个线程上的多个 World 共用，按 World 设置说不清用哪个 World 的值。
- **所有类型共用一个字节上限：** 为区块调大后，其他元素类型的大列表也会被留住。
- **调大默认值：** 不需要的类型也会留住大列表；默认仍是 4 KB。

## D66. 以 `ref` 传入、只在部分行上写入的追踪变化组件报警告 [#d66-a-ref-written-on-some-rows]

**决定。** EECS053 报出逐实体 `[ForEach]` 方法里追踪变化的组件（`ITracked`、`DynamicBuffer<T>`）的 `ref` 参数：只要有一条路径
不写它就走到方法结尾或 `return`。修复把参数改成 `Mut<T>`（写入改成 `x.Write()`，读取改成 `x.Value`）。每条路径都写的 `ref` 仍然不报
（[D46](#d46-mut-stamps-per-write)）；批量方法不报。

**原因。**
- **这些 tick 是错的，不只是贵。** 方法提前返回跳过的行也被当作写过，每个 `[Changed<T>]` 读者都把它当作变化：我们自己的示例里，复活系统
  对活着的玩家提前返回，结果每个 tick 都把每个玩家的位置发给每个客户端。`Mut<T>` 让 tick 保持真实。
- **是代码的形状说明了问题，不是数据。** D46 不动 `ref`，因为只有数据才知道大多数行会不会变。不写入的路径在方法里看得见：走这条路径的行
  从不会被它改变。
- **测量**（`ChangeTrackingSomeRowsBenchmark`，100,000 个玩家，每个 tick 有 100 个复活，之后是 `[Changed<Position>]` 同步）：`ref` 用
  162 µs，`Mut<T>` 用 133 µs，同步从约 90 µs 降到约 7 µs；只算复活，`ref` 用 72 µs，`Mut<T>` 用 126 µs，所以没人按变化读的组件用 `ref`
  更便宜，规则页写明了这一点（那种情况压掉警告）。两者都是 0 B。机器同
  [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)。
- **检测用控制流图，并保持保守。** 从入口遍历 Roslyn 为方法建的图：含有写入的块终止这条路径（块总是整块执行），抛异常的分支不跟，常量条件
  只走它的那一支（`while (true)`），走到出口就说明有一条不写入的路径。`Uses.MayWrite` 不能证明是读取的都算写入；在 `finally` 里写这个参数
  的方法不报（遍历不会沿离开时经过的 finally 走）。

**考虑过的方案。**
- **只认直线代码的模式**（提前 `return`、一个 `if`）：漏掉 `switch`、`else if` 链和可能一次都不执行的循环，却省不了什么；图只需要把方法的块
  遍历一遍。
- **批量方法：** span 按整段行打 tick，span 也没有逐行的 `Mut<T>`；只写一段里部分行的情况需要另一种设计。不报。
- **修复里用 `SetIfChanged`：** 它要比较，而已经知道自己在改值的写入不需要比较；对没有 `IEquatable<T>` 的托管组件它还会抛异常。修复保持
  方法的写入还是写入。

## D67. 行少而重时的块大小 [#d67-chunk-rows]

**决定。** `[ForEach(Parallel = true, ChunkRows = n)]`（以及并行调用的 `chunkRows:` 参数）指定一个线程每次领多少行，向上取整到 64；不指定时
仍由运行时决定（每个线程约四块，至少 1,024 行，方法写被追踪组件时至少 4,096 行）。打 tick 的遍历，块可以切开一个 4,096 行的变更 tick 区块：
遍历开始前，把它覆盖的区块按这次遍历的 tick 打开（`Rest` 取原来的最新值，`Latest` 取这次的 tick，`Words` 清空），`BlockTicks.Raise`
往已打开的区块里置位时用原子 OR。

**原因。**
- **少量重的行只在一个线程上跑。** 最小块大小适合大量轻量的行，那时领一次块比算一行还贵。几百个每行要花几微秒的行（VoxelServer 里流动的
  区块）只成一块，其他线程都闲着。执行器本来就通过共享游标领块，也就是 OpenMP 的 `schedule(dynamic, n)`，只是 `n` 写死了。
- **4,096 行只是为了保护一次读-改-写。** 字摘要覆盖 64 行，所以 64 行倍数的块各自独占自己的字；只有区块摘要（64 个字）是共享的，靠普通的
  `Words |= words` 更新。先打开区块，遍历里的每个线程就都走同一 tick 的分支，那里的 OR 可以是原子的；读者的语义不变（`Words` 里的字在
  `Latest`，其余至多 `Rest`）。打开了却没被这次遍历写到的区块，只是失去原来 `Words` 的精度：从那以后的读者会访问它的所有字。
- **每 64 行一次原子操作。** `Raise` 只在一个字在某个 tick 第一次打 tick 时执行，不是每行一次，所以每写 64 行才付一次 lock 前缀，所有遍历
  都一样（共享和独占的情况走同一条代码路径）。
- **有能抓到竞争的测试。** `ChunksSplittingBlocksKeepChangeTicksExact` 以 64 行一块写 10,000 行中的每一行，重复 1,000 次，每次遍历后数
  `[Changed<T>]` 的行：不打开区块时，有些运行会丢掉一个字的行（10,000 行只剩 9,936）。

**考虑过的方案。**
- **调小默认最小块：** 轻量的行（常见情况）每几行就要领一次块；默认值仍按行数决定，行重的方法自己说明。
- **在 `Raise` 里做无锁的状态转换**（先 CAS `Latest`，再写字）：三个字段不用循环或哨兵值就没法一起变；遍历前打开区块两者都不需要。
- **每个线程一份区块摘要，遍历后合并：** 每个线程一个数组，每次遍历合并一次，换来的东西每 64 行一次原子 OR 已经给了。
- **guided 调度**（遍历快结束时块越来越小）：自适应执行器和 `ChunkRows` 已经覆盖目前测过的情况。

## D68. 向量循环无需开启 [#d68-vector-loops-without-opting-in]

**决定。** 生成器为每个符合条件的 `[ForEach]` 方法写出 `Vector<T>` 循环（[向量循环](/zh/docs/guide/systems#vector-loops)）：静态、逐实体、
非并行，没有 `Entity` / `World` / `Mut<T>` / `Maybe<T>`，组件有 1 到 4 个同一种基本类型的字段（多个字段由解交错加载和交错存储拆成每个字段一个向量，
`EasyEcs.Interleaved`），方法体只有算术、比较、分支和有精确向量对应的 `Math` 函数。默认开启（`SimdMode.Auto`）：看起来是为向量循环写的方法
保持标量时，EECS055 说明原因；`Simd = SimdMode.Require` 让这种情况成为错误（EECS056）；`SimdMode.Off` 让方法退出。最后一个完整向量之后的行，
以及没有向量单元时（多字段时还包括没有 shuffle 指令时：256 位的 AVX2、512 位的 permute）的所有行，都调用方法本身。
之后的步骤加上了 `Vector512`（硬件支持时，其余用 `Vector<T>`）、`Reduce<T>` 结果（通道累加器）、掩码字，以及
[D90](#d90-vector-loops-reach) 里的方法。

**原因。**
- **JIT 不会做。** .NET 10 的 Tier-1 代码里，`a[i] += b[i]`、`a[i] += b[i] * 0.5f`、截断、整数求和和 `a[i]++` 都是标量
  （`vaddss`、`vmulss`、比较加分支、`add`、`inc`）：边界检查去掉了，循环从不向量化。除非有谁写出向量循环，逐行方法就一条指令一行。
- **结果相同，所以不用开启。** 每条通道按标量代码的顺序执行同样的 IEEE 运算：不重排结合顺序，不加代码没写的融合乘加，`Vector.Min` /
  `Max` / `SquareRoot` / `Abs` 对 NaN、±0 和无穷大的结果与 `Math` 相同，移位的位数和 C# 一样取模。单元测试在两张表上以 1、7 和 1,003
  行运行三个内核，数据含 NaN、±0、无穷大和随机整数，逐位比较它与逐行调用方法的结果。变更 tick 和访问集合与逐行方法相同。开关只能让代码变慢。
- **测量**（`KernelBenchmark`，100,000 行，逐行 job 对比生成的循环）：随机数据上带分支的截断 472 µs → 29.4 µs，`h += v * dt`
  62.9 µs → 9.9 µs，整数自增 33.2 µs → 8.2 µs；1,000 行：1,372 ns → 309 ns、485 → 83 ns、399 → 62 ns。方法本来就符合条件的现有基准，代码
  未改：`AccessBenchmark` 的静态方法 38.7 → 8.0 µs，`SparseBenchmark.PassOverTheRest` 50.2 → 9.3 µs，`MaybeBenchmark.TwoMethods`
  35.9 → 9.6 µs；`SparseBenchmark.PassOverTheFew`（10 个分散的行）334 → 330 ns，短段不吃亏。全部 0 B。机器同
  [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)。
- **列本来就是 Burst 需要的样子。** Burst 从 `NativeArray` 得知数组互不别名，并遍历按组件连续存放的数组；EasyEcs 的列连续、64 字节对齐、
  从不互相别名，生成器在编译时就知道。翻译一个小的源码子集就够了，不需要从 IL 编译。
- **像 Burst 的 Inspector 一样说明原因。** 保持标量的方法结果是对的，不说就会把代价藏起来。只有一个判断（`Kernel.Vectorize`）给出循环或原因：
  生成器生成它返回的循环，分析器报告原因，所以“没有循环”和“被报告”是同一组方法。级别是建议而不是警告：标量代码不是错误。`Require`
  用于速度不能在之后的改动里悄悄丢掉的热路径。
- **支持多个字段，因为真实的组件就是这样。** `Position { X, Y, Z }` 是常见的形状；要求每个坐标轴一个组件会让其他所有系统都变差。256 位的
  解交错每个向量只多几条 shuffle，远比一行一行地跑便宜。超过 4 个字段、混合类型和分部结构体保持标量（EECS055 会说明）。

**考虑过的方案。**
- **像 Burst 的 `[BurstCompile]` 那样需要开启：** Burst 需要它，是因为它换了编译器，还允许 `FloatMode.Fast`。这里除了速度什么都不变，
  需要开启只会让大部分代码白白变慢，换不来安全。`SimdMode` 仍以 `Auto` 为默认值，只多了断言（`Require`）和退出（`Off`）。
- **留给用 `Vector<T>` 的批处理方法：** 规则覆盖不到的通道仍然用它，但这要求每个用户手写 SIMD；逐行方法表达的是同一件事。

## D69. 归约是一个参数，按块的顺序合并 [#d69-reductions]

**决定。** 一遍上的总数是 `[ForEach]` 方法的一个 `ref Reduce<T>` 参数，`T` 是为自己实现 `IReduction<T>` 的单例（静态的 `Identity` 和满足结合律的
`Combine`）（[归约](/zh/docs/guide/threading#reductions)）。并行遍历的每一块，或单线程时的整遍，累加进自己从 `Identity` 开始的副本；这一遍
结束时，World 的运行器按块的顺序（也就是行的顺序）合并这些副本，结果替换 `T`。系统按 `T` 的写者调度。EECS057 拒绝同一遍里对 `T` 的第二处写入。

**原因。**
- **并行方法原来没有办法产出总数。** 它不能写单例（EECS010），绕过去的办法要么竞争（静态计数器，EECS060），要么丢掉结果（`ForEachParallel`
  之后读 job 字段，EECS061）。每个服务器每个 tick 都要算总数：存活的单位、一种资源、人群的范围。
- **每行没有锁也没有原子操作。** 部分结果在这一块自己的 job 副本里；直到最后都不共享，最后每个副本合并一次。每行一次 `Interlocked`
  加法会让所有核都去写同一条缓存行。
- **结果确定。** 按块的顺序合并（而不是按块完成的顺序），整数结果精确，`ChunkRows` 固定时浮点结果每次运行、任何线程数下都相同；`Combine`
  不需要满足交换律（第一个和最后一个值、位的拼接）。
- **两种运行方式同一个写法。** 同一个参数在 `Parallel = false` 时也能用（每段连续的行一个局部变量），在系统之外的 `[ForEach]` 方法里也能用，
  所以把一遍改成并行只改一个特性参数，不改代码。
- **零分配。** 运行器为每种 job 类型保留一个 job 副本数组，只增长一次；稳定后的遍历不分配。
- **按 `ref` 传入的普通结构体，部分结果才留在寄存器里。** 归约方法按每块里连续的行运行（并行时是 `World.ForEachBatchParallel`，单线程时是
  批量循环），这段行的部分结果是一个局部变量。它按 `ref` 传给内联的方法时，JIT 把它留在寄存器里（浮点求和的块循环每行一条 `vaddss`）。
  最初的写法是持有指向这个局部变量的 `ref` 字段的 `ref struct`，它把局部变量钉在内存里：每行一次加载和一次存储，浮点求和串在存储转发上，
  比单线程遍历慢好几倍。不按 `ref` 传入的 `Reduce<T>` 会归约进一份副本，所以报 EECS002。

**考虑过的方案。** 用 `ReduceBenchmark` 测量（BenchmarkDotNet，1,000,000 行，每种两次运行，4 核，机器负载 10 到 30）：

| 写法 | 整数求和 | 浮点求和 | 每次调用分配 |
| --- | --- | --- | --- |
| 单线程 `ref` 上下文值 | 0.41 / 0.47 ms | 0.74 / 0.76 ms | 0 B |
| `ref Reduce<T>`，并行 | 0.37 / 0.46 ms | 0.74 / 0.77 ms | 0 B |
| 带 `ref` 字段的 `ref struct` 形式的 `Reduce<T>`（最初的写法） | | 3.3 到 4.6 ms | 0 B |
| 按遍历自己的块运行的 `Parallel.For`，部分结果按顺序累加 | 差不多 | 差不多 | 1.7 到 1.9 KB |
| 逐行的 `Parallel.For<TLocal>`，静态委托 | 2.4 到 3.5 ms | 3.3 到 6.8 ms | 1.7 到 2.1 KB |
| 每行一次 `Interlocked`（浮点用 CAS 循环） | 8 到 13 ms | 15 到 24 ms | 0 B |
| 每行一把锁 | 25 到 33 ms | | 0 B |

1,000 行时 `Reduce<T>` 约 0.45 µs，每种 `Parallel.For` 写法 3.5 到 13 µs。浮点求和跑 200 次，`Reduce<T>` 和按块的 `Parallel.For` 都只得到
1 种结果；逐行的 `Parallel.For<TLocal>` 最多得到 129 种，CAS 循环最多 137 种。

- **带 `localInit` / `localFinally` 的 `Parallel.For<TLocal>`：** .NET 的线程局部归约，也是现有工具里最接近的；不采用。它从不能做到 0 B，
  逐行的写法慢 5 到 9 倍，浮点结果不确定，而且没有传状态的重载，所以 `static` lambda 只能用静态状态（这一列、结果），静态状态不可重入：
  两个 World 不能同时归约。按遍历自己的块运行时时间跟得上、结果也确定，但照样每次调用都分配，照样需要静态状态。
- **每行一次 `Interlocked` 加法或一把锁：** 对整数是对的，但每一行都在争抢同一条缓存行：比上面的 `Reduce<T>` 慢 20 到 70 倍，浮点的 CAS 循环
  结果也不确定。
- **逐行把部分结果放在 job 字段里：** 逐行的并行 job 就会这样做；块的 job 副本里的字段每行都要加载、存储一次。并行归约以批处理 job 运行
  （`World.ForEachBatchParallel`），一段行的部分结果放在局部变量里。
- **按线程 id 索引的每线程槽位：** 加了填充防伪共享，但合并顺序会跟着线程而不是行，线程数变了还要调整大小。
- **按块完成的顺序合并：** 少一个数组，但浮点结果和不满足交换律的合并会取决于时机。
- **包装部分结果 `ref` 的 `ref struct`**（按值传入的 `Reduce<T>`）：读起来像 `Maybe<T>`，但部分结果留在内存里（见上）：浮点求和 3.3 到 4.6 ms。
- **向量循环里的归约：** 以后的一步（[D68](#d68-vector-loops-without-opting-in)）；整数精确，浮点只有重排结合顺序才行。

## D70. 没有加入的分析器候选规则 [#d70-analyzer-candidates-not-added]

**决定。** 加入 EECS060、EECS061 以及 EECS027、EECS054 代码修复的那次审查，也评估了下面这些规则和修复，没有加入。

**考虑过并放弃的方案。**
- **行很少或很轻的方法上设 `Parallel = true`：** 交给线程池值不值，取决于运行时的行数和每行的工作量，分析器看不到；运行器本来就会让
  小遍历在调用线程上跑（自适应地唤醒辅助线程）。[D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)
  的规定（只报测得出的代价）把它排除在外。
- **不是 64 倍数的 `ChunkRows`：** 运行时免费把它向上取整到 64（[D67](#d67-chunk-rows)），代码照写的意思工作；规则只会要求手动取整。
- **浮点上把 `Math` 改成 `MathF`：** `Sqrt`、`Abs`、`Min` 和 `Max` 两者都精确，改了没有收益；超越函数（`Sin`、`Exp`、`Pow`）的 `MathF`
  结果不同、精度更低，修复会改变行为，D29 不允许。
- **系统里的 `Parallel.For` 或 `Task.Run`：** 正当用法很常见（不碰 World 状态的计算，交出去的 I/O 再通过线程安全的队列读回来），规则多半会报
  正确的代码；这类代码真正的错误（在其他线程上做结构变更）归 EECS014 管。
- **EECS016 的代码修复（从 `[Removed<T>]` 方法上去掉 `[With<T>]` 或参数）：** 剩下的方法不接收任何组件，EECS003 会拒绝它，所以没有一处改动能让它
  编译；正确的改法（方法遍历哪个组件）只有作者知道。

## D71. 唯一键内联，以及直接映射的键 [#d71-direct-index]

**决定。** 唯一索引把每个键唯一的实体直接存在键的头部，每个键不再有 id 数组。键能映射到一段有界槽位上的唯一组件可以声明
`IDirectIndexed<TKey>`（`static Slots`、`static SlotOf(key)`）：它的索引在哈希旁边存一个 `Slots` 项的数组，每项存一个键和它的实体，
所以 `Get`、`TryGet` 和写入的唯一性检查都只读一项。槽位超出范围或被别的键占着的键通过哈希找到，哈希仍是 `Find`、`Count` 和有序遍历用的索引。
生成器随唯一索引一起登记槽位映射（`SavedTypes.DirectIndex`），不用反射。

**原因。**
- **一个唯一键只有一个实体。** 每个键一个数组只放一个 id，每出现一个新键就分配一次；改成内联后，`CreateUnique`（10,000 个键）从
  2,044 µs、3.15 MB 降到约 1,120 µs、2.33 MB，`RekeyAndLookupUnique` 从 34.4 µs 降到 14 到 21 µs（`IndexBenchmark`）。
- **网格查找是网格世界的热路径。** 体素服务器按坐标查区块：每个物体周围的方块、每个实体所在的区块、水的边，每个 tick 几千次。读一个槽位
  比唯一索引的哈希探测快约 2.1 倍，和它取代的手写网格一样快（`IndexBenchmark` 的 `LookupUnique`、`LookupDirect`、`LookupGrid`）；
  体素服务器的物理因此快了 5% 到 11%。
- **每次写入都会维护。** 槽位数组在哈希更新的地方一起更新（挂上、摘下、清空），所以创建、读档、搬移、`SetAll` 和销毁都保持它正确；
  手写的网格要在每条路径上自己更新。
- **任何槽位函数都正确。** 冲突或超出范围的键只多一次哈希探测，不会给出错误答案：每个槽位记着有几个属于它的键只在哈希里，所以查找在
  槽位上看到别的键时，知道要不要再问哈希。

**考虑过的方案。**
- **唯一索引旁边的手写网格**（体素服务器原来的做法）：查找一样快，但每个网格世界都要重复这段代码，漏掉一条写入路径网格就会过时。
- **用槽位数组取代哈希：** 超出范围的键无处可放，`Find`、`Count` 和有序遍历也都建立在哈希上。
- **用反射登记：** 不能裁剪，Native AOT 下不安全；生成器本来就会登记每个唯一组件。

## D72. `SetAll` 按整个位字填充 [#d72-setall-whole-words]

**决定。** 对所有行都匹配的 64 行位字，`SetAll` 用一次 `Span.Fill` 写入值。不满的位字，以及被索引关注的组件（索引必须看到每一行的写入），
仍然逐行写。

**原因。** 其他批量调用本来就按位字处理；写值是剩下的唯一一个逐行循环。`BulkBenchmark` 的 `StunAndLift`（100,000 个实体）两次运行
从 92 和 100 µs 降到 30 和 30 µs，两次都是 0 B。

**考虑过的方案。** 带索引的组件也整字填充：索引要把每一行挂到它的键上，整字填充会跳过它需要的更新。

## D73. 调研中没有加入的改动 [#d73-survey-items-not-added]

**决定。** 加入 `IDirectIndexed<TKey>`、`CollectIds` 和整字 `SetAll` 的那次调研，也测量了下面这些对体素服务器和核心库的改动，没有加入。

**考虑过并放弃的方案。**
- **唯一索引旁边的区块网格：** 被 `IDirectIndexed<TKey>`（[D71](#d71-direct-index)）取代，它读起来一样快，而且每次写入都会维护。
- **体素服务器只在实体所在区块变了时才写 `InChunk`：** 差别在噪声范围内。
- **按位字而不是逐位拷贝存在位：** A/B 测试结果互相矛盾（这次快、下次慢），没有证明有净收益。
- **只拷贝变化过的边的水光环：** 拷贝少了一半，但一步的时间仍在噪声范围内，而且每个休眠的区块要多花 4 KB 记住这些边。被计划中的推送光环设计取代：
  区块的边变了时推给邻居（[路线图](/zh/docs/roadmap#push-halo)）。

## D74. 每个线程的临时空间是一个参数 [#d74-scratch]

**决定。** `[ForEach]` 方法的 `Scratch<T>` 参数是方法在当前线程上的工作内存：每个方法、每个线程一个 `T`（每种生成的 job 类型一个
`[ThreadStatic]` 盒子），方法填充之前是 `default`，从不重置，线程结束时释放。它不给系统增加任何读写。EECS058 拒绝把它持有的引用存进组件、单例、
`Maybe`、`Mut` 或 `Reduce`；EECS028 不报它一次性的 `??= new()`。

**原因。**
- **并行方法原来没有地方放列表。** 每行 `new` 一个会分配（EECS028），共享一个会竞争（EECS060），手写 `[ThreadStatic]` 字段又是每个这样的方法都要重复的代码。
  OpenMP 的 `threadprivate` 就是同一个思路。
- **0 B，而且比分配快。** `ScratchBenchmark`（每行 24 个候选，10,000 和 100,000 行，并行）：比每行新建一个列表快约 1.8 倍，每个线程第一行之后 0 B。
- **重置交给用户。** 清空列表是行在需要时调用一次；由运行器重置的话，每个临时空间每行都要调一次，不管需不需要。

**考虑过的方案。**
- **手写的 `[ThreadStatic]` 列表：** 目前在 `ScratchBenchmark` 里比 `Scratch<T>` 快 17% 到 26%；正在尝试修复。
- **每行用 `ArrayPool<T>.Shared`：** 每行租一次、还一次，而且只能是数组。
- **`stackalloc`：** 上限事先知道的小缓冲最快，也推荐用它；大小会变、或者大到放不进栈的缓冲不行。
- **每个 World 一份临时空间：** World 的并行遍历跑在不属于任何 World 的线程上，所以 World 里还是得每个线程一份。

## D75. 对其他实体的查找是一个只读参数 [#d75-lookup]

**决定。** `[ForEach]` 方法的 `Lookup<T>` 参数读取任意实体在这一遍之前的组件 `T`（`this[id]`、`Read(id)`、`Has(id)`；带索引的 `T` 还能通过
`LookupExtensions` 按键 `TryFind`、`Find`、`Count`）。系统按 `T` 的读者调度，所以写 `T` 的系统落到别的阶段；EECS059 拒绝自己也写 `T` 的方法；
EECS010 接受它出现在并行方法里。方法通过参数查询的值索引在这一遍之前创建并建好（在所有者线程上、阶段之前）；其他还没建好的索引在并行区域里抛异常，
在单线程遍历里仍然延迟建立。

**原因。**
- **读另一个实体原来会把方法逼到一个线程上。** `World` 参数在并行时被拒绝（EECS010）。一个由调度器保证契约的只读视图（同一阶段没有 `T` 的写者，
  方法里也没有）不加锁就能让读取不发生竞争：就是 Unity 带 `[ReadOnly]` 的 `ComponentLookup`、MPI 的单边 `Get`。
- **单线程时也更快。** `LookupBenchmark`：单线程的 `Lookup<T>` 比 `World` 参数加 `TryGetEntity` 和 `TryGet` 快 10% 到 28%（10,000 和
  100,000 行的追击，以及唯一键查找）。在那台机器的负载下，并行没有测出额外收益。
- **索引不能在多个线程上自己建。** 在遍历之前建好，遍历期间的每次查找就都是读；通过别的方式碰到的索引抛异常，而不是去竞争。

**考虑过的方案。**
- **也能写的查找（不带 `[ReadOnly]` 的 Unity `ComponentLookup`）：** 两行可能从两个线程写同一个实体；对其他实体的写入仍然是数据（这一行的组件，由之后的系统读取）。
- **加锁延迟建立索引：** 每一遍第一次查找都要加锁，而这个索引本可以在遍历之前建好。

## D76. 系统按阶段运行，而不是按依赖图运行 [#d76-stages-not-a-dependency-graph]

**决定。** 并行更新保留阶段：一个系统要等它前一个阶段全部结束才开始，而不是等与它冲突的系统一结束就开始（TBB 的 flow graph、Unity 的
`JobHandle`、OpenMP 的 `depend`）。

**原因。**
- **在测过的世界里，阶段屏障没有代价。** 开启 `MeasureSystems`，用每个系统每 tick 的耗时（600 tick，100,000 个单位或实体，4 核）算出阶段的
  关键路径（每个阶段最慢的系统之和），以及用同样的排序和读写集合建出的依赖图的关键路径（每个系统在它冲突或排在其后的较早系统结束后立即开始，
  线程数不限以及 4 个线程）。空闲时间是真实的（`PlanningSystem`、`MoveBodies` 旁边的线程），但后面没有系统能用上它：BattleServer 中
  `SteeringSystem` 要等 `PlanningSystem`，之后的每个系统都要等单独运行的 `ZoneSystem`；ParallelSystems 的阶段就是整个更新；WorldSimulation
  每个阶段只有一个系统。

| 世界 | 阶段（多系统阶段） | 阶段路径 | 依赖图路径 | 阶段内最慢系统旁的空闲 |
| --- | --- | --- | --- | --- |
| BattleServer | 12（1） | 4,181 µs | 4,181 µs | 507 µs |
| ParallelSystems | 1（1） | 126 µs | 126 µs | 227 µs |
| WorldSimulation，开启 `ParallelSystems`，10,000 / 100,000 | 9（0） | 1,261 / 2,395 µs | 相同 | 0 |

- **单独运行的系统在任何调度里都是屏障。** `Entity` 或 `World` 参数、重写 `OnUpdate`、结构变更都会让系统单独运行：BattleServer 默认组 13 个系统中
  有 7 个，WorldSimulation 9 个中有 7 个。依赖图等它们的方式和阶段完全一样，而真实的服务器就是这样写的。
- **最好的情况收益也很小。** `BarrierBenchmark`（不在仓库里；100,000 行）：一个重系统旁边一条由三个轻系统组成的链，按阶段为 {重, 第一}、{第二}、
  {第三}；对照组把同样三遍放进一个系统、与重系统同一阶段（依赖图会采用的调度，用现在的运行器）：一次是 6.36 对 6.08 ms，另一次是 6.73 对 7.13 ms，都在各自的误差之内（±0.3 到 0.9 ms）。
- **依赖图每次更新都有开销。** 每个阶段一个变更 tick 保证了 `[Changed<T>]` 的精确（同一阶段的系统从不写另一个系统读的数据）；依赖图需要按层级给
  每个系统算 tick，每个系统的依赖计数要重置并原子递减，辅助线程要轮询就绪队列而不是一个游标，结构变更的冻结要跨越重叠的层级；D22 的自适应唤醒按
  每份工作决定，而依赖图里不再有这样的一份工作。

**考虑过的方案。** 用同样的读写集合和排序建依赖图，对每一对冲突系统保持确定的顺序（这里评估的设计）；按上面的数字放弃。如果某个阶段最慢的系统确实
让一条冲突的轻系统链在等待，把这条链的几遍放进一个系统（按顺序运行的多个 `[ForEach]` 方法）今天就能得到依赖图的调度；`DescribeSchedule` 和
`SystemStats` 能看出这样的阶段。如果某个世界的依赖图路径明显低于阶段路径，再重新测量。

## D77. 网格瓦片：一个自己加载光环的参数 [#d77-tiles]

**决定。** 由邻居更新的格子网格（水、光照、热量）切成瓦片，每块一个实体：一个实现 `ITile<TKey>` 的组件（静态成员给出形状：`Width`、
`Depth`、`Height`、`Faces`；键在值索引里；`Beside(key, face)` 给出邻居的键），以及装格子的 `DynamicBuffer<TCell>`。`[ForEach]` 方法接收
`Tile<TCell, TTile>` 参数，管线代码由生成器写：每个实体在索引里找一次瓦片的邻居，声明读取（索引、`DynamicBuffer<TCell>`），把形状和缓冲
加进方法的过滤条件，并让方法保持并行。`Load(from, to)` 把各层填进这个线程的一张纹理，外面一圈 `Halo` 格取自邻居朝向它的边（以及下面和上面的层），
每行记一位表示有不为零的格子，返回 `PaddedTile`：`Rows(reads)` 用 `TrailingZeroCount` 走模板可能改变的行，`At(row)` 是一个游标，它的
`Load128` / `Load256` / `LoadVector` 读相隔一个格子、一行或一层的向量。瓦片参数旁边写它的格子缓冲是 EECS059，即 `Lookup<T>` 的规则。

形状还说明模板读多远、多宽：`Halo`（光环的格数，最多到瓦片的边长）、`Neighbourhood`（只有面、面和棱、或全部 26 个邻居）和
`Boundary`（没有邻居处填充、钳制或镜像；周期网格就是一个会回绕的 `Beside`）。`Tile.Changes` / `Tile.Facing` 让网格把安静的瓦片休眠，
只唤醒朝向变化边的瓦片。瓦片每遍走一步。EECS072 报告瓦片装不下的形状，EECS073 报告一个方法里同一格子类型的两个瓦片。

**原因。**
- **每个网格都写同样的 80 行。** VoxelServer 的水要找四个邻居，用四个 `Lookup` 读它们的计数和缓冲，给 `stackalloc` 的纹理按每个面处理边界情况
  地填充，还要自己维护行掩码。用瓦片后，`Flow.cs` 只剩规则和它的行循环；形状是 `Chunk` 的四个成员。
- **和手写的循环一样快。** `WaterTileBenchmark`（400 个区块走一步，手写系统对瓦片系统，输出逐个区块比较，两轮）：瓦片 482–513 µs，手写 516–524 µs（1 个线程；4 个线程为 263 µs 对 263–269 µs），
  两者都是 0 B。
- **常见形状的加载有自己的循环。** 加上光环、邻域和边界之后，通用的加载（每个邻居槽位，每格一次填充或钳制）让水比第一版慢了最多 40 %。
  三处改动把它拉了回来：缺失的邻居读一个填充值的空白数组（每格没有分支），行通过每行算一次的 ref 拷贝，光环为 1、只有面、填充边界
  （水和拉普拉斯算子）走自己的循环，由常量条件选中；面邻域的邻居查找按面展开。这个循环编译两份，带行掩码和不带（`Masked` / `Unmasked`，一个 `typeof` 常量），所以只被采样的瓦片
  （水的方块）不测试任何格子，光环格子在搬运它的寄存器里测试。水的瓦片在 1 个线程上从 566–585 µs 降到 482–513 µs；第一版是 528–547 µs。
  通用加载的行循环把向量留在寄存器里（没有溢出）。
- **常量会折叠。** 形状是结构体类型参数的 static abstract 成员，所以 JIT 把每个步长、每次 `Offset` 检查和每个拷贝大小都编译成常量：
  一次采样就是从固定偏移的一条 `vmovdqu`。
- **方法是它自己的编译根。** 生成的、调用带瓦片方法的访问器是 `NoInlining | NoOptimization`：内联进作业小小的 `Execute` 时，方法用光了
  内联器的预算（大约是根大小的十倍），它的十一次 `Load128` 仍是调用。作为自己的根，它把这些全部内联（192 个内联，行循环里没有调用）。
  手写版本碰巧有同样的效果：含 `stackalloc` 的方法从不被内联。
- **从不返回的抛出辅助方法，每列一次 x 检查。** 游标的抛出辅助方法是 `[DoesNotReturn]` 而不是 `NoInlining`：JIT 把可能返回的方法调用
  编译成会破坏所有向量寄存器的调用，于是每次检查都把模板的向量溢出到栈上（9 点模糊的 Tier1 代码：之前 1,399 字节，之后 884 字节）。
  x 检查单独成句：dy 和 dz 是常量会折叠，同一列的加载（三行里的 x − 1）重复同一个比较，JIT 会去掉重复的，所以 9 点模糊每个向量检查
  三次而不是九次。1 个线程上 9 点模糊从 969 µs 降到 756–765 µs，拉普拉斯算子从 966 µs 降到 661–678 µs。
- **瓦片对手写模板。** `TileStencilBenchmark`（环面上 1,024 块 16 × 16 浮点的板，逐块比较输出，两轮）：9 点模糊用瓦片 756–765 µs，
  直接映射的键 679–690 µs，手写 389–432 µs（1 个线程；4 个线程为 406–428、389–403 和 253–269 µs）；拉普拉斯算子 661–678 µs 对
  385–397 µs（4 个线程为 381–393 对 249–273 µs）；全部 0 B。差距来自通用的加载（每块板约 200 ns：每个邻居槽位走同一个带行掩码的拷贝循环）
  和索引查找（约 150 ns）：每格这么便宜的模板，主要成本就是它们；每格做实事的模板（水）则不是。
- **安静的瓦片不花钱。** `TileActiveBenchmark`（1,024 块生命游戏板，16 个闪烁子，两轮）：一直运行 369–378 µs，带休眠和唤醒 10.7–11.6 µs
  （1 个线程；4 个线程为 222–226 µs 和 12.7–13.1 µs），两者都是 0 B。
- **纹理按线程分配，不在栈上。** 大小由类型参数决定的 `stackalloc` 不是常量；纹理是按格子类型和形状的 `[ThreadStatic]` 数组，在线程第一次
  加载时按所有层分配，之后复用（与 `Scratch<T>` 同一条规则，D74）。

**考虑过的。**
- **一次加载走多步（时间分块，深光环）：** 做过，放弃了。光环宽 k 时，一次加载就装下了只读一格远的模板 k 步需要的数据；原型在线程的两张
  纹理上来回运行这些步，每步区域缩小一圈。`TileStepsBenchmark`（1,024 块板上四步模糊；相对四遍普通遍历的比值，两轮）：两遍各两步在
  16 × 16 格时 1.55–1.58，32 × 32 时 1.70–1.86（1 个线程；4 个线程为 1.14–1.22 和 1.55–1.57），一遍四步 1.55–1.70 和 1.75–1.80
  （4 个线程为 1.08–1.10 和 1.60–1.61）。每一步还要算下一步读的光环格子，格子装得进缓存的网格上，省下的遍历比这更便宜。多步可能在远大于缓存的
  网格上划算；这里测过的都不是。
- **沿 y 的滑动窗口（2.5D 流式）：** 原型只保留三层带光环的层，在算第 y 层前才填第 y + 1 层。8 × 8 个 16 × 16 × Height 浮点区块上的
  7 点模板，两轮：Height 32 时整块 416–443 µs 对滑动 434–454 µs（1.03–1.04）；Height 256 时 3,821–4,091 µs 对 3,847–3,894 µs
  （0.95–1.01，在误差之内）。没有做：在这些大小下整块瓦片的纹理装得进缓存。
- **缓存邻居的 id：** `TileNeighbourBenchmark`（1,024 块板，8 个邻居，一遍只找邻居，两轮）：查索引 147–159 µs，直接映射的键 107 µs，
  从组件读 id 1.4–1.5 µs（1 个线程；4 个线程为 60–66、46–48 和 2.8–2.9 µs）。没有做：在模板遍历里查找约占五分之一的开销，而缓存需要
  表之外的每实体状态，并在每次创建、销毁和键变化时失效；实现 `IDirectIndexed<TKey>` 的键不用缓存就让每次查找变成一次数组读取。
- **生成的逐格内核（用户写 `Next(center, north, south, ...)`，生成器写循环）：** 没有做。C# 对 `byte` 的运算会提升成 `int`，标量函数体对不上
  字节通道；生成器的向量循环面向 `Vector<T>`（AVX2 上 32 字节），不是 16 格的一行；而且水按行归约（有水的行、变化的第一层和最后一层、
  变化的边），逐格函数表达不了。留在用户方法里的就是规则本身。
- **为写自己格子的瓦片新增一个分析器编号：** 这正是 EECS059 已经为 `Lookup<T>` 报告的误用（读这一遍写的东西），所以 EECS059 两者都管。
- **一个瓦片里多个字段、解交错：** 没有做。每个字段一个结构体、各自的缓冲和瓦片类型，纹理和掩码已经能处理；EECS073 拒绝一个方法里
  同一格子类型的两个瓦片，因为它们会共用线程的纹理。
- **周期边界模式：** 会回绕的 `Beside` 就是周期网格，不需要新增模式。

## D78. 遍历产出的记录是 `Emit<T>` 参数，按行的顺序追加 [#d78-emit]

**决定。** `[ForEach]` 方法的 `Emit<T>` 参数（按值传入，`T` 是结构体）追加记录：`Add(in T)`、`AddRange(span)`。并行遍历的每个块（单线程时是整次遍历）
追加到自己的列表，列表取自每个 `T` 一个的池；遍历结束时这些列表按块的顺序追加到单例 `Emitted<T>`（没有就先添加）的 `Items`（一个
`DynamicBuffer<T>`）。遍历只追加、从不清空：应用这些记录的系统清空它们。系统写 `Emitted<T>`（每次遍历一次），所以读它的系统等产出它的系统。
EECS070 拒绝同时接收 `Emitted<T>` 或同一个 `T` 有两个 `Emit<T>` 的方法。快照和存档会复制这些记录。

**原因。**
- **并行遍历原来只能输出到自己的行。** 产出命中给其他实体的战斗遍历、产出数据包的视野遍历，要么在每行写一条待处理记录、再扫一遍这些行，
  要么共用一个队列。`EmitBenchmark`（10,000 / 100,000 个攻击者中一半命中；4 核）：并行的 `Emit<T>` 在 10,000 个攻击者时用 10 到 16 µs，100,000 个时 103 到 121 µs（两轮），和同一个方法单线程差不多（每行的步骤很轻，受内存带宽限制），领先于手写的"写组件再扫描"
  （慢 1.3 到 2 倍）、`ConcurrentQueue`（慢 13 到 72 倍）和指向预分配数组的 `Interlocked` 游标（慢 5 到 23 倍），都是 0 B。
- **任何线程数下都按行的顺序。** 块本来就按行的顺序编号（`Reduce<T>` 合并的顺序，D69），按这个顺序拼接它们的列表，得到的就是单线程方法的记录，
  一条不差。回放、测试和核数不同的服务器看到同一个列表。
- **追加，而不是替换。** 一次更新里可以有几个系统产出同一种记录（近战和法术都产出伤害）；替换列表的遍历会在应用记录的系统运行之前丢掉前面系统的记录。
  知道记录已经应用的是应用它们的那一方，所以由它清空。
- **预热之后 0 B。** `Items` 没有列表时，第一个块的列表直接成为 `Items`；之后的列表复制进去再还给池，池把它们保持在一个块用过的最大长度
  （池按 `T` 分，每块取一次锁，不是每条记录一次）。

**名字。** GPU 的几何着色器、Flink 的算子和 Unity `NativeStream` 的写入端都把往输出流里加东西叫 `Emit`；`Emitted<T>` 就是产出的东西。
考虑过：`Output<T>`（也是参数方向的名字）、`Stream<T>`（`System.IO.Stream`）、`Events<T>`（事件系统，EasyEcs 没有：D1）、`Append<T>`
（一个动词，说不出和遍历的关系）。

**考虑过的方案。**
- **每次遍历替换列表：** 丢掉其他产出同一个 `T` 的系统的记录（见上）。
- **每次遍历把列表换进单例：** 第一版就是这样，单例的列表于是每次遍历都要重新增长（每 100 次更新 1.6 MB）；只在 `Items` 为空时直接拿走列表就避免了。
- **"写组件再扫描"的代码修复：** 没法可靠地识别（一个系统写组件、另一个系统收集，也是在 tick 之间保存状态的方式）；只有基准测试能说明它的代价。
- **每个线程一个列表：** 线程认领块的顺序取决于时机，记录的顺序就乱了。

## D79. 确定性随机数是纯函数 `EntityRandom` [#d79-entity-random]

**决定。** `EntityRandom` 是一个单例（`Seed`、`Tick`），加上一组（种子、实体 id、tick、流）的纯静态函数：`Bits`、`Float`（[0, 1)，步长 2^-24）、
`Range`（整数用乘法取高位，以及浮点）和 `Chance`。这些位是 SplitMix64 终结函数的四轮，每个输入一轮，先混合种子。EECS071 报告 `[ForEach]`
方法里的 `Random.Shared` 和 `new Random()`；修复改为从 `EntityRandom` 抽取，每个调用点一个流。

**原因。**
- **并行遍历原来抽不到可重现的数。** `Random.Shared` 按线程请求的顺序把数分给各行；带种子的 `Random` 是一个线程的状态。基于计数器的生成器
  （cuRAND 的 Philox、JAX 的 threefry）没有状态：同样的输入在任何线程、任何行的顺序下都得到同样的数。
- **哈希是测出来的。** `EntityRandomBenchmark`，100,000 个实体每个一个浮点数：四轮 SplitMix64 420 到 467 µs，7 轮的 Philox-4x32 慢 2.4 到 2.7 倍，
  10 轮（cuRAND 的默认）慢 3.9 到 4.0 倍，带种子的 `Random` 慢 2.2 到 2.3 倍，而且只在一个线程上可重现；`Random.Shared`（每个线程一个 xoshiro256**，没有要混合的输入）用时 0.8 倍。
  在并行遍历里（每行一次掷骰），`EntityRandom` 用了 266 到 440 µs，`Random.Shared` 157 到 270 µs：这是数能重现的代价。JIT 把整个函数内联进行循环
  （每轮三次乘法，没有调用）；Philox 的 32×32→64 乘法用 AVX2 就能向量化，64 位乘法要 AVX-512DQ，这对向量循环是个收益，这里没有测。
- **先混合种子。** 如果用 `seed ^ id`，种子 1 和 2 只是交换实体 1 和 2 的数。
- **每个调用点一个流。** 同样的四个输入得到同样的数，所以同一行同一个 tick 里抽两次需要两个流；修复会给它们编号。

**考虑过的方案。**
- **每个实体一个生成器状态（一个组件）：** 每次抽取一次写入，被追踪的组件要打 tick，存档也更大。
- **Philox 或 threefry：** 这里更慢；对相互独立的输入，四轮 64 位终结函数的质量对游戏和模拟足够（它不是密码学生成器，文档也没有这样说）。
- **只显式传种子：** 保留了（静态成员），另外加了单例，让 `[ForEach]` 方法只要一个 `in` 参数。

## D80. 对一段区间或一个列表的并行循环是 `world.ForParallel` [#d80-for-parallel]

**决定。** `world.ForParallel(count, ref job)` 对下标运行 `IForRange` job（`Execute(start, end)`），`world.ForParallel(ref buffer, ref job)` 对一个
`DynamicBuffer<T>`（`Emitted<T>` 的记录）的元素运行 `IForSpan<T>` job（`Execute(start, span)`），都在 World 的运行器上：并行 `[ForEach]` 的块
（每个线程约四块，1,024 到 `ParallelChunkRows` 之间 64 的整数倍，或 `chunkRows`）、同样的认领和唤醒帮手线程的方式，调用期间结构被冻结。
每块一个 job 副本，什么都不合并回来。EECS060 和 EECS061 检查这些 job。

**原因。**
- **记录需要在产出它们的遍历之后处理。** `ForParallelBenchmark`，4 核：每条记录一个重的步骤（几次平方根），在 10,000 / 100,000 条记录时比单线程快
  1.2 到 2 倍（机器是共用的，所以两轮的收益不同），和在同样的块上用静态委托的 `Parallel.For` 持平（两轮中彼此都在噪声范围内），后者每次调用分配 2 KB；ForParallel 不分配。轻的步骤（一次乘加）受内存带宽限制：10,000 条记录时比单线程慢 1.7 到 1.8 倍（分发块的开销超过了工作本身），100,000 条时是单线程用时的 0.9 到 1.2 倍；这样的步骤还是写成循环。
- **一个运行器。** 在 World 的运行器旁边再用 `Parallel.For`，会让两组帮手线程挤在同样的核上；运行器的自适应唤醒已经知道什么时候帮手划算。
- **小，而且和其他 API 一致。** 两个接口、两个调用；每块一个 span，和 `ForEachBatchParallel` 给的一样。

**考虑过的方案。**
- **合并 job 副本（在区间上归约）：** 对行求总数有 `Reduce<T>` 方法；在普通区间上就是第二套归约 API，没有用例需要它。
- **接收 `Span<T>`：** span 不能被运行器的工作项捕获（ref struct）；缓冲区，或者 job 持有的数组上的区间，就能覆盖这种用法。

## D81. 没有加入按键归约 [#d81-keyed-reductions]

**决定。** 不提供专门的按键（直方图）归约。最多几千个桶的直方图，是一个持有 `[InlineArray]` 计数的单例的 `Reduce<T>`（它的 `Combine` 把桶相加）；
桶更多时在一个线程上计数，或者每个键一个组件。计数顺带在一个每行都有实际工作的并行遍历里时，这个写法才划算；只做计数的遍历在一个线程上更快。

**原因。** `HistogramBenchmark`，100,000 行，4 核：每个线程一组桶、每个线程合并一次（候选的 API），1,024 个桶时 快 17% 到 24%，16,384 个桶时
慢 1.9 倍，65,536 个桶时 慢 2.8 到 2.9 倍（和单线程的普通循环相比）：清零并合并"线程数 × 桶数"的开销超过了数 100,000 行。`[InlineArray]` 桶上的 `Reduce<T>`
在 1,024 个桶时 比单线程慢 1.1 到 1.3 倍，4,096 个桶时 慢 3.1 倍；共享桶上每行一次 `Interlocked` 自增慢 4 到 27 倍。在按键 API 要服务的规模上，没有哪个候选明显胜出。

**发现的限制。** 64 KB 及以上（16,384 个 int）的 `Reduce<T>` 在第一次遍历时失败：生成的 job 把每块的副本放在数组里，而运行时不创建元素这么大的值类型数组
（`TypeLoadException`）。

**考虑过的方案。**
- **每个线程一组桶**（见上）和**每块一个稀疏列表**（排序后合并的键值对）：后者在同样的合并之外每块还要排序一次，所以没有实现。

## D82. 单个实体就是一个 `[ForEntity]` 方法 [#d82-for-entity]

**决定。** 标了 `[ForEntity]` 的静态方法在单个实体上运行：生成器写出 `entity.Run` 接收的 `IForEachEntity` job（`ref` 参数构成
`WriteMask`，过滤特性构成一个 `static readonly` 过滤条件，方法不做结构变更时实现 `INoStructuralChanges`），再在方法旁边写一个和方法同名的入口
`Owner.Method(entity, [since,] values…)`，返回方法有没有运行。

**原因。**
- **写成 job 的请求处理代码，一行活要四处声明。** 一个结构体、它的字段、一个必须和 `ref` 参数对得上的 `WriteMask`（EECS037 检查它）、一个过滤条件字段，
  再加上每个调用处创建 job、写全类型参数调 `Run`。系统之外的 `[ForEach]` 方法本来就有生成的 job 和入口
  （[D26](#d26-generated-members-and-a-suggestion-to-use-them)）；单个实体是同一个模式，只是把 `world.ForEach` 换成 `entity.Run`。
- **名字和 `[ForEach]` 成对。** `[ForEach]` 对每个匹配的行运行方法，`[ForEntity]` 对调用方给的那一个实体运行；两个特性都声明方法是什么，而不是
  何时运行。工作名 `[RunOn]` 读起来像调度（在某个线程、某次更新上运行），还暗示有一个目标类型参数；`[OneEntity]` 说的是数量，没有表示“运行”的词。
- **入口保持其他生成入口的形状。** 它是方法所在类型的静态成员，和方法同名，第一个参数是实体；带 `[Changed<T>]` / `[Removed<T>]` 的方法，
  第二个参数是往回看的起始 tick，和 `Since` 一样；方法和 runner 一样保持 private，把名字让给入口。
- **开销和手写 job 一样。** 生成的代码就是同一个 `entity.Run` 调用：`ForEntityBenchmark`（10,000 个单位里打 1,000 次，十分之一已死）：两轮分别是 9.80 和 9.96 µs，手写 job 加过滤条件字段是 10.04 和 9.97 µs，在误差之内，两者都是 0 B。

**考虑过的方案。**
- **`Entity` 上的扩展成员（`unit.TakeHit(30)`）：** 每个模块的每种请求都会出现在 `Entity` 的成员列表里，两个类型里同名的方法还会冲突；
  所属类型的名字说明了这是谁的请求。
- **返回方法的结果：** 结果已经通过 `ref` 值带出来，和 runner 一样；`bool` 只表示一件事：方法有没有运行。
- **转换调用后还读字段的 job：** 只有当 job 的每一处使用都是“创建，接着一次 `Run`”时，EECS080 才转换它；在字段里带回结果的 job 要变成带 `ref`
  参数的方法，调用处怎么改留给作者。

## D83. 系统的节奏是一个特性 [#d83-update-interval-attribute]

**决定。** 系统类上的 `[UpdateInterval(n, Phase = p)]` 决定系统多久运行一次；`UpdateInterval` 和 `UpdatePhase` 属性删掉了。生成器把这两个值
传给系统的生成代码，`AddSystem` 只读一次；派生系统没有自己声明时沿用基类的特性。EECS082 报告对旧属性的重写，修复会写出特性；EECS083 报告小于 1
的间隔和不在 0 到 n - 1 之间的相位。

**原因。**
- **节奏本来就该是常量，属性却表达不了。** EECS018 只能事后警告计算出来的重写；特性参数是编译期常量，这条警告和它的代码修复都不需要了。
- **每次更新少一次虚调用，但测不出来。** `RunSystem` 原来每次更新对每个系统做一次虚调用来读间隔，现在读的是添加系统时设好的字段。`OrderingBenchmark`
  （每次更新四个系统，10,000 个实体）：改前和改后，一轮是 6.96 和 7.21 µs，另一轮是 7.55 和 7.16 µs（按注册顺序；按特性排序：6.99 和 7.09，然后 7.96 和 7.02 µs），都在误差之内（±0.22 到 0.69 µs）：每个系统一次虚调用低于这个基准能分辨的范围，所以这次改动的理由是常量，而不是速度。两者都是 0 B。
- **不运行代码就能看到调度。** 工具、分析器（EECS028 不报告有节奏的系统的 `OnUpdate`）和读代码的人都在声明上看到它。

**考虑过的方案。**
- **属性和特性并存：** 同一件事两种说法，还得学两者的先后规则。这个破坏性变更每个系统改一行，代码修复替你改，迁移指南里有示例。
- **运行时决定节奏：** 要在运行时改变系统运行频率的服务器，把系统放进一个分组，到期时更新这个分组（[系统分组](/zh/docs/guide/systems#system-groups)），
  这也是 [D51](#d51-not-added) 推荐的、代替按时间间隔运行的做法。

## D84. `[Consume]` 能整批销毁时就整批销毁访问过的行 [#d84-consume]

**决定。** `[ForEach, Consume]` 在遍历结束时恰好销毁这次遍历访问过的行。不做结构变更的方法（以及批处理方法）之后，按方法自己的过滤条件做一次
`DestroyAll`：整表匹配、又没有清理组件的表一步释放。可能做结构变更的方法，在方法处理完每个实体后马上销毁它。遍历抛异常时，没处理完的行一个也不销毁。
带消费方法的系统在并行更新里单独运行；`[Consume]` 加 `Slices` 报 EECS085。

**原因。**
- **只有遍历改变不了匹配集合时，整批销毁才精确。** 方法不做结构变更，遍历之后匹配过滤条件的行恰好就是遍历访问过的行：期间没有实体被创建、移动或打标签。
  创建自己查询会匹配的实体的方法（会生成实体的 `Spawn`）用 `DestroyAll` 会把新实体也销毁，所以这类方法逐行销毁。
- **实测**（`ConsumeBenchmark`：每次操作创建 N 个事件实体，跑一遍处理并销毁它们；`HandWritten` 在方法体里调 `entity.Destroy()`，`EachRow` 是可能做结构变更的方法加
  `[Consume]`，`Bulk` 是不做结构变更的方法加 `[Consume]`）：

| 事件数 | `HandWritten` | `EachRow` | `Bulk` | 分配 |
| --- | --- | --- | --- | --- |
| 1,000 | 37.85 / 36.65 µs | 38.39 / 38.61 µs | 14.84 / 14.84 µs（0.39× / 0.41×） | 0 B |
| 100,000 | 3,923.61 / 3,946.63 µs | 3,878.94 / 3,908.39 µs | 1,499.03 / 1,392.84 µs（0.38× / 0.36×） | 0 B |

  （两轮，第一轮 / 第二轮）

  整批销毁的耗时约为逐行销毁的 0.4；逐行时 `[Consume]` 和手写的销毁开销相同，用不了整批销毁的方法什么也不损失。

- **抛异常之后剩下什么。** 整批销毁在遍历之后运行，异常会跳过它，所有事件都留到下一次运行，再被访问一次；逐行销毁的路径已经销毁了处理完的行，
  和手写代码一样。

**考虑过的方案。**
- **永远逐行销毁：** 简单，但本可以一次释放整张表的地方也要付逐行的开销。
- **记下访问过的 id 再销毁它们：** 对所有方法都精确，但要一个随遍历增长的缓冲区（每遍的内存没有上界），每个 id 还要查一次；而整批销毁不精确的那些方法，
  逐行销毁本来就是精确的。
- **和 `Slices` 一起消费：** 每次销毁都会挪动其他分片的行，事件可能要等很多次运行。

## D90. 向量循环覆盖并行方法、可选与窄通道、结构体值和宽行 [#d90-vector-loops-reach]

**决定。** [D68](#d68-vector-loops-without-opting-in) 的向量循环能接下真实系统写出的更多方法，并列出每个方法得到的循环：
- **并行方法。** `[ForEach(Parallel = true)]` 方法的每个块都让自己的行段走同一个循环。
- **`FloatMode.Fast` 数学。** `MathF.Sin`、`Cos`、`Exp`、`Log`、`Log2` 和 `Hypot`（以及 `double` 版本）采用 .NET 的向量近似
  （`Vector512.Sin`……）；在 `FloatMode.Exact` 下，EECS055 指出这个调用。
- **`Maybe<T>` 作为通道掩码。** 本行段可选列的存在位就是每个向量的通道掩码，`HasValue` 就是这个掩码，`Value` 的字段是只在有 `T` 的行上读（和写）的通道；
  对没有 `T` 的行读 `Value`，会把这个向量的行交给方法本身，按写法抛出异常。
- **窄通道。** `byte`、`sbyte`、`short` 和 `ushort` 组件每个 `Vector512` 处理 64 或 32 行。C# 按 `int` 计算它们，所以生成器把每个值跟踪为低位加上它所在的区间，
  只在区间证明窄通道就是 `int` 结果时才接受一个运算：回绕的 `+ - * & | ^ ~ <<`（`int` 结果的低位）、包住和或差的 `Math.Min` / `Max` 链对应
  `AddSaturate` / `SubtractSaturate`、与范围内常量的比较（饱和和与 255 比较不行）、精确值的右移和 `Abs`。窄通道的掩码字由方法本身运行。
- **结构体值。** `System.Numerics` 或 Godot 的 `Vector2` / `Vector3` / `Vector4` 字段（或其他由通道组成的结构体）给出自己的通道；`new T(...)`
  （record 的位置构造函数，或只给字段赋值的构造函数）、`with`、向量类型逐分量的运算符、`Min` / `Max` / `Abs` / `SquareRoot` 和结构体局部变量
  都变成每个通道一条语句，所以 Godot 示例的 `position = new Position(position.Value + velocity.Value * dt)` 是一个扁平循环。
- **冷分支。** 在循环能计算的条件下出现的调用（或其他循环表达不了的东西），会让有通道走进它的向量把行按顺序交给方法本身，发生在任何存储之前；其余向量仍是向量。
- **宽组件。** 在 AVX-512 上，循环不拆分的组件（超过 4 个通道、有其他类型的字段），当方法只用它在字边界上的 4 字节通道、一行最多 16 个字、并且置换划算时，
  得到 `Vector512` 循环：一个向量的 16 行按 K 个整向量载入，一棵剪枝过的双源置换树（`vpermt2ps`）收集每个用到的字段，只有含被写字的向量才置换并整块存回。
  作业的索引表是 `static readonly` 字段，一个 `static readonly bool` 检查运行时的布局（大小，以及每个用到的通道经 `with` 设置后出现在它的字里），
  所以生成器没有预料到的布局由方法本身运行。
- **检查器。** `DescribeSchedule()` 列出每个方法的循环（`SystemInfo.Loops`："Move: vector (Vector512 or Vector&lt;float&gt;), flat"、
  "Steer: vector (Vector512 only), wide component (permutes), masked words scalar"、"Spawn: scalar (it takes the Entity)"）；
  `tools/jitdisasm.sh` 打印循环的 Tier-1 代码（`DOTNET_JitDisasm`、`DOTNET_TC_CallCountingDelayMs=0`）。
- **拆分建议。** 当组件对循环来说太宽或太杂，而方法最多只用它一半的字段（最多 4 个、大小相同）时，EECS055 在末尾列出它们："it uses 3 of Body's
  12 fields (X, VX, Y): split them into a component of their own"。

**原因。**
- **`FloatMode.Exact` 是确定的，并且保持确定。** 每个通道都是标量代码的一次 IEEE 运算，顺序也相同：`+ - * /`、`Sqrt`、`Min` / `Max` 和各种转换
  在 x64 和 ARM64（AdvSimd）上都正确舍入，所以向量循环在每台机器上都给出标量代码的位。可能不同的是 `FloatMode.Fast`：重新排序的浮点求和，以及近似函数，
  每个函数用 160 万个随机输入对照 `MathF` 测量（`Sin` 和 `Cos` 在 ±100，`Exp` 在 ±80，`Log` 在 10^-30 到 10^30）：`Sin`、`Cos`、`Log` 和 `Log2`
  在 1 ulp 以内，`Exp` 在 2 以内（`Exp(0)` 是 `1 + 1 ulp`），`Hypot` 在所有试过的输入对上都相等；`double` 的 `Sin` 在 1 ulp 以内，`Exp` 和 `Log` 在 2 以内。
- **窄通道逐通道证明。** 一个单元测试把每一对 `byte`（和 `sbyte`）值、65,536 行，送进每个窄内核，有和没有缺组件的行都跑，并与方法本身逐位比较；
  把 `AddSaturate` 换成 `SubtractSaturate` 它就失败。区间证明不了的都保持标量，并给出原因。
- **宽行：在置换划算的地方。** 原型（BenchmarkDotNet，这台机器，AVX-512），置换树对比逐行循环，1,000 / 10,000 / 100,000 行：12 个字段用 3 个、11 个向量运算，
  标量时间的 0.48 / 0.60 / 0.85；8 个用 4 个、4 个运算 0.69 / 0.67 / 0.97；12 个用 3 个、3 个运算 0.89 / 1.03 / 1.10；16 个用 4 个、4 个运算
  1.07 / 0.96 / 0.94；8 个用 2 个、2 个运算 0.66 / 0.97 / 1.06。门槛就是它们之间的分界：每 16 行的置换少于方法体每个向量运算 8 次（31 次置换对 11 个运算
  会向量化，42 次对 4 个保持标量，并说明原因）。同样的行把用到的 3 个字段拆成自己的组件，跑出标量时间的 0.16 到 0.34：建议比置换更值。
- **冷分支只在走进时付出代价。** 原型 10,000 行，条件下的一个调用：7.75 µs → 没有行走进时 1.06 µs，0.1% 时 1.09，1% 时 1.94，10% 时 9.30（对比 12.74）。
- **生成的循环对比同一方法逐行执行**（`KernelBenchmark`，1,000 / 100,000 行，两轮）：带饱和的字节亮度 48 ns / 2.6 µs，对比
  3.1 µs / 311 µs；`Vector3` 移动 96 到 108 ns / 23 µs，对比 488 到 565 ns / 53 到 58 µs；`Maybe<T>` 掩码 261 到 298 ns / 24 µs，
  对比 1.5 µs / 148 到 156 µs（`MaybeBenchmark.OneMethod` 109 → 10 µs，与拆成两个方法一样快）；并行步进 274 到 294 ns / 23 到
  25 µs，对比 1.4 µs / 207 到 215 µs；冷分支在没有行走进时 87 ns / 10 µs、每 100 行一行走进时 281 到 287 ns / 27 µs，对比
  752 ns / 64 到 68 µs 和 773 到 811 ns / 83 到 85 µs；`FloatMode.Fast` 下的 `Sin` 与 `Exp` 1.8 µs / 178 µs，对比 7.2 µs /
  1.43 ms；12 个 float 的宽组件 898 到 916 ns / 186 到 196 µs，对比 1.6 到 1.8 µs / 209 到 217 µs。全部分配 0 B，分支之前已有的
  循环耗时不变。

**考虑过的。**
- **一行 8 或 16 个字的完整转置**（蝶形，每个字都移动）：标量时间的 1.07 到 2.05 倍（8 个字 1,000 行 983 对 531 ns，16 个字 2,666 对 1,301 ns）。
  剪枝树只移动用到的字。
- **gather。** .NET 10 没有 AVX-512 的 gather API；AVX2 一次 8 行的 gather 是标量时间的 0.8 到 1.18，在树划算的地方都比树慢。
- **跨步载入**（每个通道一次插入）：标量时间的 1.0 到 2.9 倍。
- **`[Lane]` / `[Hot]` 字段标记、`[Layout(Soa)]` 存储。** 方法已经说明了它用哪些字段，所以标记不提供生成器缺少的信息。数组结构的表是最快的形式
  （12 个字段用 3 个：1,000 行 97 对 765 ns，100,000 行 19.9 对 185 µs），但会改变每个交出一行 `ref` 的 API；拆分组件得到大部分收益（263 ns、30.7 µs），
  存储不变，所以 EECS055 改为这样建议。
- **把循环展开** 2 或 4 倍：1,000 行 37.4 → 33.1 / 34.1 ns，10,000 行 1,018 → 1,037 / 1,076 ns，100,000 行在噪声以内：没有稳定的收益，代码却翻倍。
- **留待以后：** 并行方法的掩码字（块交出的是整段行）、并行方法里的 `Maybe<T>` 和窄通道的 `Maybe<T>`、窄通道和宽行的掩码字（由方法本身运行）、
  `Atan2`、`Asin`、`Pow` 等（.NET 10 没有向量形式）、`Vector2.Clamp`（示例对每个字段用 `Math.Clamp`）。
