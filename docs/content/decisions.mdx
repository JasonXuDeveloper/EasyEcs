BenchmarkDotNet numbers where a measurement decided). A record is rewritten when the decision changes; a dropped
feature stays here with its reason, so it is not proposed again without new facts.

after the change on the machine of the time; they are history, not the current results. Current numbers are on

## D1. State changes are data: no events or callbacks [#d1-state-changes-are-data-no-events-or-callbacks]

**Decision.** Nothing calls user code when a component is added, removed or written. A change that others react to is
a component (a `Dead` tag, a message entity) or a tracked write (`[Changed<T>]`, `[Removed<T>]`).

**Why.** A callback runs inside another system: the control flow is hidden, it can re-enter the code that raised it,
and the scheduler cannot see what it reads and writes, so systems could not run in parallel safely. As data, the order
of effects is the schedule's, the generator knows every access, and tests and snapshots see the "events".

**Considered.** Component events (Friflo, Arch, DefaultEcs); EasyEcs had them once and removed them.

## D2. Structural changes apply at once: no command buffers [#d2-structural-changes-apply-at-once-no-command-buffers]

**Decision.** Adding, removing, creating and destroying take effect immediately, also in the middle of a query: removed
rows become tombstones while a pass runs, the world closes them when the last pass ends, and a pass never sees rows
shift under it.

**Why.** A deferred change is a second, later version of the world that every reader must reason about; an immediate
one reads as it is written. The tombstones cost one id check per visited row and nothing outside passes.

**Considered.** Command buffers played back after the query (Friflo, Arch, DefaultEcs).

## D3. No command buffer for parallel jobs [#d3-no-command-buffer-for-parallel-jobs]

**Decision.** Parallel `[ForEach]` methods and parallel stages change no structure (EECS010). A parallel job writes
data; a system after it, on the owner thread, makes the structural change from that data:

```csharp
public record struct Poison(int DamagePerTick) : IComponent;

public class PoisonSystem : EcsSystem
{
    [ForEach(Parallel = true)]                                    // data, on every core
    static void Hurt(ref Health hp, in Poison poison) => hp.Value -= poison.DamagePerTick;
}

[UpdateAfter<PoisonSystem>]
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]                                      // structure, after it, on the owner thread
    static void Die(Entity entity, in Health hp) { if (hp.Value <= 0) entity.SetDead(); }
}
```

**Why.** Per-thread recorders would bring back D2's deferred second path, with an order between threads to define and
a playback whose cost hides behind the stage. The pattern above uses the schedule the user already reads, and
bulk changes (`SetAll`, `RemoveAll`) make the follow-up pass cheap.

**Considered.** Per-thread command buffers played back when the stage ends (on the 4.1 roadmap, dropped before
implementation).

## D4. No `Added<T>` filter [#d4-no-addedt-filter]

**Decision.** There is no filter for "gained `T` since a tick". `[Changed<T>]` already selects rows that gained `T`
(adding stamps the tick, as a write does). When a system must tell a new component from a written one, the creator adds
a tag that the reacting system removes:

```csharp
public struct Spawned : IComponent;                                  // a tag: "new since the last Greet"

public class GreetSystem : EcsSystem
{
    [ForEach, With<Spawned>]
    static void Greet(Entity entity, in Health hp) => entity.RemoveSpawned();   // first-time work, then a bit flip
}
```

```csharp
world.CreateEntity(new Health(100), new Spawned());                  // the creator says it is new
```

**Why.** A tag is explicit, queryable, saved with the world and costs one presence bit flip. A built-in filter would
need a second change tick per tracked row (8 bytes more per row, one more store on every add) and a second companion
column per component type, for a need the tag covers.

**Considered.** Bevy's `Added<T>`, DefaultEcs' `WhenAdded` (on the 4.1 roadmap, dropped before implementation).

## D5. Order systems by dependencies, not priorities [#d5-order-systems-by-dependencies-not-priorities]

**Decision.** Systems run in registration order. `[UpdateBefore<T>]` / `[UpdateAfter<T>]` move only the system that
declares them, within its group. Stages come from the ordering graph and the read/write sets: two systems run together
when neither is ordered before the other and their access does not conflict. A cycle throws in `AddSystem` (the world
stays unchanged) and is reported by the analyzer when it can see it (EECS019); an ordering across groups does nothing
(EECS020). `Priority` was removed.

**Why.** Integer priorities from several assemblies collide and say nothing about why a system runs where it does; an
ordering names the dependency. Keeping both would give two mechanisms for one job. Moving only the declaring system
keeps the registration order of everything else, so adding one ordering never reshuffles unrelated systems.

**Considered.** Priorities alongside orderings (rejected: overlap); a lexicographic topological sort (rejected: it
reordered unrelated systems). Tick time unchanged: ParallelSystems 292-345 μs before, 278-325 μs after, over four
runs; WorldSimulation 1,774 μs before, 1,731 μs after.

## D6. Removing a component keeps the row [#d6-removing-a-component-keeps-the-row]

**Decision.** A removal clears the row's presence bit in its column; only adding a component the table has no column
for moves the row.

**Why.** States that come and go (stunned, burning, dead) then cost a bit flip after the first time, queries test 64
rows per word, and `[Removed<T>]` is a row like any other (its tick says when).

**Considered.** Moving the row on every removal (the classic archetype model): a copy per state change.

## D7. Contiguous columns, not pages [#d7-contiguous-columns-not-pages]

**Decision.** Columns are contiguous arrays.

**Why.** Paged columns iterate at the same speed but add an indirection to every handle access; all they save is the
copy when a table grows, which `InitialEntityCapacity` and `EnsureCapacity` remove.

## D8. No whole-entity disable [#d8-no-whole-entity-disable]

**Decision.** There is no "disabled entity" that queries skip by default. A tag and `Without<T>` do it explicitly;
`Disable<T>()` keeps one component's value while hiding it:

```csharp
public struct Inactive : IComponent;                        // the whole entity is off
public struct Bullet : IComponent;

public class BulletSystem : EcsSystem
{
    [ForEach, With<Bullet>, Without<Inactive>]              // the systems that skip it say so
    static void Move(ref Position p, in Velocity v) => p = new Position(p.X + v.X, p.Y + v.Y);
}
```

```csharp
var bullet = world.CreateEntity(new Bullet(), new Position(0, 0), new Velocity(4, 0));
bullet.SetInactive();                                       // back to the pool: a bit flip, no row moves
bullet.SetPosition(10, 20).RemoveInactive();                // reused

int pooled = world.Count<Bullet>(QueryFilter.Create().With<Inactive>()); // saves, cleanup, stats see everything
```

Uses: object pools (bullets, effects), players kept in memory while they reconnect, zones without players whose NPCs
sleep.

**Why.** Excluding by default would make every query depend on a state it does not name: a save, a cleanup or a count
that must see every entity has to remember to opt back in, and forgetting it fails silently. The tag is data the
generator and the reader both see, as the ECS principles ask.

**Considered.** Friflo (`entity.Enabled = false`: a hidden tag in the archetype, queries skip it unless
`WithDisabled()`); DefaultEcs (`entity.Disable()`: the entity leaves every entity set). Performance by case:

| | Friflo | DefaultEcs | EasyEcs |
| --- | --- | --- | --- |
| Switching an entity off or on | moves its row to another archetype | updates every set | flips a presence bit (after the first time) |
| Iterating past disabled entities | skips their archetype | they are in no set | free while a table has none (counts, no bits read); 64 rows per test when mixed |

Pools and effects switch often, where a bit flip beats a row move. Only many entities disabled for long, mixed with
enabled ones in one table, cost EasyEcs a word test per 64 rows that Friflo skips; `GroupBy` on a sleeping state
splits them into their own tables when that matters. A filter on a system group (`[Without<Inactive>]` on its
`ISystemGroup` struct) joins every `[ForEach]` of the group's systems, so the filter is written once.

## D9. Saves are built in, with Nino [#d9-saves-are-built-in-with-nino]

**Decision.** `World.Save` / `Load` and `SaveEntities` / `LoadEntities` write tables, with Nino for managed values.
Unmanaged rows are written in a canonical layout with a hash of their fields, so a changed struct is detected at load;
the generator records where `EntityId` fields are, so a migration can point them at the new entities.

**Why.** Rewriting references, loading by type name and reusing rows on repeated loads (0 B allocated) need the
world's tables and the generator; user code over a `Query` could not do them. (Until 4.0 saving was left to the user.)

## D10. `MoveEntities` copies rows without encoding [#d10-moveentities-copies-rows-without-encoding]

**Decision.** `world.MoveEntities(target, ids)` copies a group's rows into another world of the thread, rewrites the
ids inside the group and destroys the originals. It shares one core with `LoadEntities` and prefab groups, which copies
runs of consecutive rows column by column.

**Why.** It was kept only after measuring that encoding is a real share of a move: 1,000 entities there and back take
150 μs, against 207 μs through `SaveEntities` + `LoadEntities`; without a hierarchy one way takes 32 μs against 71 μs.

## D11. Ids in a prefab name its members [#d11-ids-in-a-prefab-name-its-members]

**Decision.** An `EntityId` field in a prefab names a member of its group (`member.Id`) and is rewritten on every
instance; any other id becomes `EntityId.Null`. Relations to a world's entities are set after instantiating.

**Why.** A prefab belongs to no world: an id of a world's entity may equal a member's, so the two cannot be told apart.

## D12. Target policies are opt-in, per index [#d12-target-policies-are-opt-in-per-index]

**Decision.** `WhenTargetDestroyed(TargetPolicy.Remove / Destroy)` on an `EntityId` index or a relation index decides
what destroying an entity does to the links to it; `Keep` is the default (the links stay, findable by the dead id).
`ChildOf` is `Destroy`, and may be changed.

**Why.** Opt-in keeps destroys of worlds without policies as they were. `ChildOf`'s rule is checked inline: through the
generic rule list the cascade benchmark took 650 μs instead of 557 μs; inline, 561-578 μs.

**Considered.** A marker interface on the component type (rejected: the index must be created generically, which needs
reflection; a call on the index is AOT-safe and per world, like `GroupBy<T>()`).

## D13. One owner thread per world [#d13-one-owner-thread-per-world]

**Decision.** A world's systems, queries and structural changes run on its owner thread; parallel stages and parallel
`[ForEach]` are the only parallelism, and the generator proves them safe. Another thread posts to the owner.

**Why.** No locks on any hot path; the rules fit in three lines ([threading](/en/docs/guide/threading)).

## D14. No shared components [#d14-no-shared-components]

**Decision.** No `SetSameAs`-style shared values. Shared data lives in a singleton, components hold an id into it.

**Why.** A shared value is a reference that one write changes for many entities, which change tracking and the
scheduler could not see.

## D15. .NET 10 only [#d15-net-10-only]

**Decision.** EasyEcs targets `net10.0`, no Unity or older runtimes.

**Why.** It relies on C# 14 extension members, `Vector256`, pinned object heap columns and current JIT behavior that
older runtimes lack.

## D16. No `partial`: generated code lives outside the user's type [#d16-no-partial-generated-code-lives-outside-the-users-type]

**Decision.** The generator writes a `[ForEach]` method's job in a `file` class of its own and calls the method,
private or not, through `[UnsafeAccessor]`. A system's update and access set are a `SystemCode` registered by a module
initializer (held weakly, so a collectible assembly can unload); a runner's entry point is a C# 14 static extension
member of its type. Types the generated code cannot name (a private component, a private runner type) are EECS022.

**Why.** A system is an ordinary class: no `partial` on it or on its outer types, nothing generated in its body, so
generated members cannot collide with the user's. `UnsafeAccessor` compiles to the direct call (the same machine
code, inlined), and the ticks did not move (ForEachSystemWrite, ParallelSystems within noise).

**Considered.** Partial classes (EECS001 when missing, members injected into the user's type); delegates or function
pointers to the methods (an indirect call per row, no inlining); reflection at startup (no AOT).

## D17. Unloading removes types from worlds; bits are reused [#d17-unloading-removes-types-from-worlds-bits-are-reused]

**Decision.** `world.RemoveTypes(assembly or context)` takes an assembly's systems, singletons, indexes, groupings and
components out of the world. Entities stay; tables that had one of its columns are dropped with every cache naming
them. When a collectible context unloads, EasyEcs forgets its save names, and its component bits are reused once no
live world mentions them. A reload keeps data through `Save` and `Load`, which map types by name.

**Why.** Game logic reloaded in a long-running server must leave nothing rooting the old assembly (column arrays,
transition edges, query cache keys, registries), and repeated reloads must not grow every mask. Dropping tables is
the one place a table is deleted outside `Dispose`, so steady-state code pays nothing (CreateAddDestroy, Prefab and
WorldSimulation within noise).

**Considered.** Migrating rows from the old types to the new ones in memory (needs a type map for every field; `Save`
/ `Load` already map by name and field hash); never reusing bits (the mask grows by every reloaded component).

## D18. No interceptors for query calls; filters carry no references [#d18-no-interceptors-for-query-calls-filters-carry-no-references]

**Decision.** Query calls are not intercepted. `QueryFilter` holds its five sets' first 256 bits inline and its bits
past 255 as an interned id, so it holds no object reference, and its builder copies it once per call.

**Why.** An interceptor replaces the method a call binds to, but the call's arguments are still evaluated, so a
filter built at the call is built either way; caching a query entry per call site would save only the memo lookup the
call already makes. The cost was the filter itself: five masks with an overflow reference each made every builder
call two copies through `BulkMoveWithWriteBarrier` and zeroed the caller's frame. Without references, counting 16
entities with `QueryFilter.Create().With<Npc>().Without<Dead>().Without<Frozen>()` built at the call takes 76 ns
against 124 ns, and with the filter in a static field 24 ns as before (`CallSiteBenchmark`). Hoisting stays the
advice for hot calls.

**Considered.** Interceptors with a static filter and a cached entry per site (the arguments make it moot); an
analyzer warning for filters built at the call (most calls are cold; the docs teach the static field).

## D19. No settable tag properties [#d19-no-settable-tag-properties]

**Decision.** A tag's generated `IsX` is read-only; `SetX()` adds the tag and `RemoveX()` removes it.

**Why.** `entity.IsDead = true` (Entitas style) cannot be written where ECS code holds its entities: C# 14 rejects
assigning an extension property of a struct on a `foreach` variable (CS1654), an indexer result (CS1612) or a field of
an `in` parameter (CS8332), with a by-value or an `in` receiver alike. A member that compiles on a local but not in
`foreach (var e in hits)` or on `link.Target` teaches the wrong thing; the methods work everywhere, and a structural
change stays a call.

## D20. Generic systems register the closed types their assembly names [#d20-generic-systems-register-the-closed-types-their-assembly-names]

**Decision.** A generic system's code is a generic class over the system's type parameters. Its module initializer
registers an instance for each closed type the assembly names (`AddSystem<CountOf<Health>>()`, `new CountOf<Health>()`,
a base type `CountOf<Health>`, and their generic bases), and the code's definition for any other closed type, which
`AddSystem` closes with `MakeGenericType` on first use. A generic `[ForEach]` method of a system stays EECS004.

**Why.** A module initializer cannot know the type arguments a program will use, and the system class gets nothing
generated in it (D16). Closed types named in the system's assembly need no runtime code generation, so Native AOT
keeps them; a closed type only another assembly names still works under the JIT. Runners need neither: their entry
points are generic, so the caller's type arguments close the job at compile time. A system's own generic method has
no caller to give it type arguments.

**Considered.** Reflection only (breaks Native AOT for every value-type argument, and components are structs); a
virtual generic hook on the system (needs `partial` or a base class per arity); scanning referenced assemblies for
closed uses (the generated code is file-local to the system's assembly).

## D21. .NET 10 features only where they measure [#d21-net-10-features-only-where-they-measure]

**Decision.** Of the .NET 10 / C# 14 features weighed for 4.1, each was prototyped and measured with
BenchmarkDotNet against the commit before it (two runs each side, 0 bytes allocated throughout), and kept only as a
net win:

| Feature | Verdict | Numbers |
|---|---|---|
| `Vector512` (and `Vector<T>`) | kept: a table without tombstones counts the set bits of its row words, 8 words per step with AVX-512, else `Vector<T>` (4 on AVX2, 2 on Arm64) | CountBenchmark, 100,000 rows that must be tested: 48.9-54.5 μs -> 1.21-1.27 μs; `Vector<T>` alone 2.4 μs, one word at a time 5.2 μs; an indexed lane loop over a `Vector512` 7.6 μs (unrolled instead) |
| `GetAlternateLookup` on the query cache | kept: probed with the call's bits and a ref to its filter, no key built or copied | a filter past the memo 92-106 ns -> 86-90 ns |
| the memo's ways as structs in one array | kept | a static filter 21.6-21.9 -> 19.0-19.8 ns, no filter 36.8-39.1 -> 35.3-35.5 ns |
| `[InlineArray]` for the memo (every signature's ways inline in one flat array) | dropped | 1-2 ns more (20.3-20.6 / 38.9-39.5 ns), but signature indices are process-wide, so every world holds about 750 bytes per signature of the process (150 KB for 200) and copies it all for each new way |
| `FrozenDictionary` for saved types (lock-free lookups, frozen on the first load after a change) | dropped | a one-entity save and load 2.32-2.33 μs -> 2.23-2.34 μs: within noise; a load resolves each type once, not per entity |
| `System.Threading.Lock`, `params ReadOnlySpan`, null-conditional assignment | kept | cold paths |
| `RegisterImplementationSourceOutput` | kept: a system's code and the saved-type registration are reached only through module initializers | IDEs skip them while typing |
| C# 14 in generated code | kept: EasyEcs targets net10.0 (default C# 14), so every generator asks for C# 14 and generated lambdas leave out parameter types | |
| `OverloadResolutionPriority`, `field` | no place: they change overload choice and syntax, not the IL; the API has no array and span overloads of one method, and the candidates' backing fields are written outside their properties | |
| first-class span conversions, `nameof(List<>)` | no place: the remaining `.AsSpan()` calls are `Fill` and `foreach (ref ...)`, which conversions do not reach; the generators target netstandard2.0 and compare type names | |

**Considered.** Widening the inline component mask to 512 bits (every filter, key and table mask grows by 32 bytes
for components 256-511, which the overflow already covers).

## D22. Parallel runs use the thread pool and wake helpers only when they pay [#d22-parallel-runs-use-the-thread-pool-and-wake-helpers-only-when-they-pay]

**Decision.** A parallel `[ForEach]` and a stage of parallel systems run on the calling thread plus reusable
`IThreadPoolWorkItem` helpers, in chunks sized by the matching rows. Each job and each stage measures its runs: a run
with helpers yields its time and its items' summed thread time, and helpers stay while they make a run a fifth faster
than its work. Once it runs alone, a probe of four runs with helpers comes after a period that doubles from 16 to
1,024 runs, or at once when runs alone turn 1.5x slower. No spinning, no dedicated threads, no allocation.

**Why.** Waking a parked pool thread takes from a few to a few hundred microseconds and burns about as much CPU, so a
small pass between server ticks ran no faster with helpers and cost twice the CPU. A 60 Hz tick of one 100,000-row
pass on a 4-core VM: median pass 123 -> 111 μs, CPU per tick 436 -> 290 μs (serial: 108 μs, 229 μs). BDN:
ParallelSystems 804-808 -> 746-768 μs, ParallelForEach 294-308 -> 267-271 μs, BattleServer and Runner unchanged.

**Considered.**
- A crew of dedicated helper threads that spin about 50 μs after a run: it won only when passes ran back to back
  (BenchmarkDotNet's loop). In a server tick it lost: median 130 against 135 μs, but p90 170 against 190 μs and CPU
  per tick 990 against 760 μs.
- `ThreadPool.UnfairSemaphoreSpinLimit`: closes the back-to-back gap, but it is process-wide and keeps pool threads
  spinning between ticks (49 ms CPU per 16 ms tick), so it stays the application's choice.

## D23. Change summaries per block; removals summarized apart [#d23-change-summaries-per-block-removals-summarized-apart]

**Decision.** A tracked column keeps, per 64-row word, one 32-byte entry (latest tick, the rows at it, a bound of the
others, and a bound of the ticks of rows lacking the component), and per 4,096-row block the words at the block's
latest tick as a bit mask with a bound for the rest. A `Changed<T>` pass finds the next written word with one bit
scan; a `Removed<T>` pass skips words by their removal bound and blocks by their own removal summaries, so writes of
`T` do not make it visit their words.

**Why.** BDN against the per-word summaries: RemovalComparison with 10 removals 1.07-1.09 -> 0.87 μs; ChangeTracking
`Changed`, 10 written, 609-650 -> 514 ns; ChangeTrackingComparison 612-636 -> 497-573 ns. BattleServer,
WorldSimulation and the 1,000-written cases are unchanged.

**What remains.** Friflo reports 10 removals in 0.70 μs: it collects the removed ids in a callback as they happen, so
reading them costs nothing extra. EasyEcs keeps removals as data (D1): its pass costs about 90 ns plus about 30 ns
per word with a removal, the loads of the summaries and rows. At 1,000 removals the two are even (71 against 73 μs).

**Considered.** Interleaving a word's summaries with its block's (no gain: the summaries of 100,000 rows fit in L2);
noting the word in a separate helper called per row (slower: 600 μs per query tick); finding the column and word of a
removal once for its stamp and its removal note (no measurable gain, reverted).

## D24. An index's key holds its entities in one array [#d24-an-indexs-key-holds-its-entities-in-one-array]

**Decision.** A value index and a relation index keep each key's entities in one id array (`IndexHead`). A leaving
entity leaves a hole the key's next entity fills, so entities never move and a loop finds each entity once, whatever
is destroyed during it; arrays of emptied keys are reused. `CreateEntities` indexes its entities with one key lookup.

**Why.** The lists linked through per-entity nodes cost one dependent load per entity. BDN: IndexBenchmark 710 ->
156 μs; ValueQueryComparison 648 -> 225 μs (Friflo 323 μs); RelationComparison 26.8 -> 23.4 μs (Friflo 26.5 μs);
cascades unchanged, 0 bytes.

## D25. Structural row loops are compiled for tables without tombstones [#d25-structural-row-loops-are-compiled-for-tables-without-tombstones]

**Decision.** A `[ForEach]` that may change structure runs each table through a row loop compiled twice: for a table
with tombstones (each row tests its id) and for one without (no test). A table without tombstones at the call gains
one only through a structural change, which bumps the storage version and ends the loop.

**Why.** StructuralChangeComparison, 10 of 100,000 units killed per tick: 85.7 -> 80.9 μs (three rounds; Friflo's
command buffer 77 μs); 1,000 killed and BattleServer unchanged.

**Considered.** Holding the storage version seen in a register instead of re-reading it per row: 82 -> 108 μs (the
job's call leaves too few callee-saved registers, a column ref spills and round-trips the stack every row).

## D26. Generated members where code would repeat a type; not for every call [#d26-generated-members-where-code-would-repeat-a-type-not-for-every-call]

**Decision.** The generator names three more things. A query item's components get names: `item.Position` for
`item.Component1`, generated per `Query<…>` shape the code calls. A buffer element gets writers on prefabs:
`prefab.SetLoot(…)`, on `Prefab.SetBuffer<T>(params ReadOnlySpan<T>)`. Code fixes are offered only when their result
compiles. Two proposals were dropped: multi-type `Disable` / `Enable` and bulk calls, and a hidden "use the generated
member" diagnostic.

**Why.**
- **Query items.** `Component1..n` makes the reader count the type arguments. The named member is an inlined getter
  over the same ref, so it costs nothing. One file per shape keeps an assembly's output to the shapes it uses; one
  extension block per component and position would mean 45 blocks per component.
- **Prefab buffers.** Before `SetBuffer`, a prefab could hold only an empty buffer: filling one meant copying a
  buffer value, which EECS012 rejects. A relation gets no prefab writer, because a recipe's links would name the
  prefab's own rows.

**Considered.**
- **`Disable<T1..Tn>()`, `RemoveAll<T1..Tn>()` and the other bulk calls.** After a table's first disable, each call
  flips presence bits in place. n calls cost n gate entries of a few nanoseconds, and a bulk call over several types
  needs a meaning for "has any of them" that one-type calls do not. Not built.
- **A hidden diagnostic with a fix from `entity.Get<Position>()` to `entity.Position`.** It is style, not
  correctness: the two compile to the same call. It would add an operation callback to every invocation in every
  user project. The docs teach the generated members; generic code needs the generic API.
