Why EasyEcs is the way it is: each record states what was decided, why, and what was weighed against it (with the
BenchmarkDotNet numbers where a measurement decided). A record is rewritten when the decision changes; a dropped
feature stays here with its reason, so it is not proposed again without new facts.

The numbers in these records are the measurements that decided each question, taken with BenchmarkDotNet before and
after the change on the machine of the time; they are history, not the current results. Current numbers are on
[Performance](/en/docs/performance) and [Comparison](/en/docs/comparison). What is planned next is on the
[roadmap](/en/docs/roadmap).

## D1. State changes are data: no events or callbacks [#d1-state-changes-are-data-no-events-or-callbacks]

**Decision.** Nothing calls user code when a component is added, removed or written. A change that others react to is
a component (a `Dead` tag, a message entity) or a tracked write (`[Changed<T>]`, `[Removed<T>]`).

**Why.** A callback runs inside another system: the control flow is hidden, it can re-enter the code that raised it,
and the scheduler cannot see what it reads and writes, so systems could not run in parallel safely. As data, the order
of effects is the schedule's, the generator knows every access, and tests and snapshots see the "events".

**Considered.** Component events (Friflo, Arch, DefaultEcs); EasyEcs had them once and removed them.

## D2. Structural changes apply at once: no command buffers [#d2-structural-changes-apply-at-once-no-command-buffers]

**Decision.** Adding, removing, creating and destroying take effect immediately, also in the middle of a query: removed
rows become tombstones while a pass runs, the world closes them when the last pass ends, and a pass never sees rows
shift under it.

**Why.** A deferred change is a second, later version of the world that every reader must reason about; an immediate
one reads as it is written. The tombstones cost one id check per visited row and nothing outside passes.

**Considered.** Command buffers played back after the query (Friflo, Arch, DefaultEcs).

## D3. No command buffer for parallel jobs [#d3-no-command-buffer-for-parallel-jobs]

**Decision.** Parallel `[ForEach]` methods and parallel stages change no structure (EECS010). A parallel job writes
data; a system after it, on the owner thread, makes the structural change from that data:

```csharp
public record struct Poison(int DamagePerTick) : IComponent;

[EcsSystem]
public ref struct PoisonSystem
{
    [ForEach(Parallel = true)]                                    // data, on every core
    static void Hurt(ref Health hp, in Poison poison) => hp.Value -= poison.DamagePerTick;
}

[EcsSystem, UpdateAfter<PoisonSystem>]
public ref struct DeathSystem
{
    [ForEach, Without<Dead>]                                      // structure, after it, on the owner thread
    static void Die(Entity entity, in Health hp) { if (hp.Value <= 0) entity.SetDead(); }
}
```

**Why.** Per-thread recorders would bring back D2's deferred second path, with an order between threads to define and
a playback whose cost hides behind the stage. The pattern above uses the schedule the user already reads, and
bulk changes (`SetAll`, `RemoveAll`) make the follow-up pass cheap.

**Considered.** Per-thread command buffers played back when the stage ends (on the 4.1 roadmap, dropped before
implementation).

## D4. No `Added<T>` filter [#d4-no-addedt-filter]

**Decision.** There is no filter for "gained `T` since a tick". `[Changed<T>]` already selects rows that gained `T`
(adding stamps the tick, as a write does). When a system must tell a new component from a written one, the creator adds
a tag that the reacting system removes:

```csharp
public struct Spawned : IComponent;                                  // a tag: "new since the last Greet"

[EcsSystem]
public ref struct GreetSystem
{
    [ForEach, With<Spawned>]
    static void Greet(Entity entity, ref Health health)
    {
        health = new Health(health.Value + 10);                      // first-time work: a welcome bonus
        entity.RemoveSpawned();                                       // then a bit flip
    }
}
```

```csharp
world.CreateEntity(new Health(100), new Spawned());                  // the creator says it is new
```

**Why.** A tag is explicit, queryable, saved with the world and costs one presence bit flip. A built-in filter would
need a second change tick per tracked row (8 bytes more per row, one more store on every add) and a second companion
column per component type, for a need the tag covers.

**Considered.** Bevy's `Added<T>`, DefaultEcs' `WhenAdded` (on the 4.1 roadmap, dropped before implementation).

## D5. Order systems by dependencies, not priorities [#d5-order-systems-by-dependencies-not-priorities]

**Decision.** Systems run in registration order. `[UpdateBefore<T>]` / `[UpdateAfter<T>]` move only the system that
declares them, within its group. Stages come from the ordering graph and the read/write sets: two systems run together
when neither is ordered before the other and their access does not conflict. A cycle throws in `AddSystem` (the world
stays unchanged) and is reported by the analyzer when it can see it (EECS019); an ordering across groups does nothing
(EECS020). `Priority` was removed.

**Why.** Integer priorities from several assemblies collide and say nothing about why a system runs where it does; an
ordering names the dependency. Keeping both would give two mechanisms for one job. Moving only the declaring system
keeps the registration order of everything else, so adding one ordering never reshuffles unrelated systems.

**Considered.** Priorities alongside orderings (rejected: overlap); a lexicographic topological sort (rejected: it
reordered unrelated systems). Tick time unchanged: ParallelSystems 292-345 μs before, 278-325 μs after, over four
runs; WorldSimulation 1,774 μs before, 1,731 μs after.

## D6. Removing a component keeps the row [#d6-removing-a-component-keeps-the-row]

**Decision.** A removal clears the row's presence bit in its column; only adding a component the table has no column
for moves the row.

**Why.** States that come and go (stunned, burning, dead) then cost a bit flip after the first time, queries test 64
rows per word, and `[Removed<T>]` is a row like any other (its tick says when).

**Considered.** Moving the row on every removal (the classic archetype model): a copy per state change.

## D7. Contiguous columns, not pages [#d7-contiguous-columns-not-pages]

**Decision.** Columns are contiguous arrays.

**Why.** Paged columns iterate at the same speed but add an indirection to every handle access; all they save is the
copy when a table grows, which `InitialEntityCapacity` and `Reserve` remove.

## D8. No whole-entity disable [#d8-no-whole-entity-disable]

**Decision.** There is no "disabled entity" that queries skip by default. A tag and `Without<T>` do it explicitly;
`Disable<T>()` keeps one component's value while hiding it:

```csharp
public struct Inactive : IComponent;                        // the whole entity is off
public struct Bullet : IComponent;

[EcsSystem]
public ref struct BulletSystem
{
    [ForEach, With<Bullet>, Without<Inactive>]              // the systems that skip it say so
    static void Move(ref Position p, in Velocity v) => p = new Position(p.X + v.X, p.Y + v.Y);
}
```

```csharp
var bullet = world.CreateEntity(new Bullet(), new Position(0, 0), new Velocity(4, 0));
world.Update();                                             // it flies
bullet.SetInactive();                                       // back to the pool: a bit flip, no row moves
bullet.SetPosition(10, 20).RemoveInactive();                // reused

int pooled = world.Count<Bullet>(QueryFilter.Create().With<Inactive>()); // saves, cleanup, stats see everything
```

Uses: object pools (bullets, effects), players kept in memory while they reconnect, zones without players whose NPCs
sleep.

**Why.** Excluding by default would make every query depend on a state it does not name: a save, a cleanup or a count
that must see every entity has to remember to opt back in, and forgetting it fails silently. The tag is data the
generator and the reader both see, as the ECS principles ask.

**Considered.** Friflo (`entity.Enabled = false`: a hidden tag in the archetype, queries skip it unless
`WithDisabled()`); DefaultEcs (`entity.Disable()`: the entity leaves every entity set). Performance by case:

| | Friflo | DefaultEcs | EasyEcs |
| --- | --- | --- | --- |
| Switching an entity off or on | moves its row to another archetype | updates every set | flips a presence bit (after the first time) |
| Iterating past disabled entities | skips their archetype | they are in no set | free while a table has none (counts, no bits read); 64 rows per test when mixed |

Pools and effects switch often, where a bit flip beats a row move. Only many entities disabled for long, mixed with
enabled ones in one table, cost EasyEcs a word test per 64 rows that Friflo skips; `GroupBy` on a sleeping state
splits them into their own tables when that matters. A filter on a system group (`[Without<Inactive>]` on its
`ISystemGroup` struct) joins every `[ForEach]` of the group's systems, so the filter is written once.

## D9. Saves are built in, with Nino [#d9-saves-are-built-in-with-nino]

**Decision.** `World.Save` / `Load` and `SaveEntities` / `LoadEntities` write tables, with Nino for managed values.
Unmanaged rows are written in a canonical layout with a hash of their fields, so a changed struct is detected at load;
the generator records where `EntityId` fields are, so a migration can point them at the new entities.

**Why.** Rewriting references, loading by type id and reusing rows on repeated loads (0 B allocated) need the
world's tables and the generator; user code over a `Query` could not do them. (Until 4.0 saving was left to the user.)

## D10. `MoveEntities` copies rows without encoding [#d10-moveentities-copies-rows-without-encoding]

**Decision.** `world.MoveEntities(target, ids)` copies a group's rows into another world of the thread, rewrites the
ids inside the group and destroys the originals. It shares one core with `LoadEntities` and prefab groups, which copies
runs of consecutive rows column by column.

**Why.** It was kept only after measuring that encoding is a real share of a move: 1,000 entities there and back take
150 μs, against 207 μs through `SaveEntities` + `LoadEntities`; without a hierarchy one way takes 32 μs against 71 μs.

## D11. Ids in a prefab name its members [#d11-ids-in-a-prefab-name-its-members]

**Decision.** An `EntityId` field in a prefab names a member of its group (`member.Id`) and is rewritten on every
instance; any other id becomes `EntityId.Null`. Relations to a world's entities are set after instantiating.

**Why.** A prefab belongs to no world: an id of a world's entity may equal a member's, so the two cannot be told apart.

## D12. Target policies are opt-in, per index [#d12-target-policies-are-opt-in-per-index]

**Decision.** `WhenTargetDestroyed(TargetPolicy.Remove / Destroy)` on an `EntityId` index or a relation index decides
what destroying an entity does to the links to it; `Keep` is the default (the links stay, findable by the dead id).
`ChildOf` is `Destroy`, and may be changed.

**Why.** Opt-in keeps destroys of worlds without policies as they were. `ChildOf`'s rule is checked inline: through the
generic rule list the cascade benchmark took 650 μs instead of 557 μs; inline, 561-578 μs.

**Considered.** A marker interface on the component type (rejected: the index must be created generically, which needs
reflection; a call on the index is AOT-safe and per world, like `GroupBy<T>()`).

## D13. One owner thread per world [#d13-one-owner-thread-per-world]

**Decision.** A world's systems, queries and structural changes run on its owner thread; parallel stages and parallel
`[ForEach]` are the only parallelism, and the generator proves them safe. Another thread posts to the owner.

**Why.** No locks on any hot path; the rules fit in three lines ([threading](/en/docs/guide/threading)).

## D14. No shared components [#d14-no-shared-components]

**Decision.** No `SetSameAs`-style shared values. Shared data lives in a singleton, components hold an id into it.

**Why.** A shared value is a reference that one write changes for many entities, which change tracking and the
scheduler could not see.

## D15. .NET 10 only [#d15-net-10-only]

**Decision.** EasyEcs targets `net10.0` only. It runs wherever .NET 10 runs, Godot 4 .NET projects that target
`net10.0` included ([the Godot sample](https://github.com/JasonXuDeveloper/EasyEcs/tree/master/samples/Godot)); not on Unity's Mono and IL2CPP or older runtimes.

**Why.** It relies on C# 14 extension members, `Vector256`, pinned object heap columns and current JIT behavior that
older runtimes lack. Unity support waits for a Unity that runs .NET 10 ([roadmap](/en/docs/roadmap#unity)).

## D16. No `partial`: generated code lives outside the user's type [#d16-no-partial-generated-code-lives-outside-the-users-type]

**Decision.** The generator writes a `[ForEach]` method's job in a `file` class of its own and calls the method,
private or not, through `[UnsafeAccessor]`. A system's hooks, methods and access set are a code struct in its
assembly's system set, registered by a module initializer (held weakly, so a collectible assembly can unload;
[D103](#d103-system-sets)); a runner's entry point is a C# 14 static extension member of its type. Types the generated code cannot name (a private component, a private runner type) are EECS022.

**Why.** A system is an ordinary type: no `partial` on it or on its outer types, nothing generated in its body, so
generated members cannot collide with the user's. `UnsafeAccessor` compiles to the direct call (the same machine
code, inlined), and the ticks did not move (ForEachSystemWrite, ParallelSystems within noise).

**Considered.** Partial classes (EECS001 when missing, members injected into the user's type); delegates or function
pointers to the methods (an indirect call per row, no inlining); reflection at startup (no AOT).

## D17. Unloading removes types from worlds; bits are reused [#d17-unloading-removes-types-from-worlds-bits-are-reused]

**Decision.** `world.RemoveTypes(assembly or context)` takes an assembly's systems, singletons, indexes, groupings and
components out of the world. Entities stay; tables that had one of its columns are dropped with every cache naming
them. When a collectible context unloads, EasyEcs forgets its save names, and its component bits are reused once no
live world mentions them. A reload keeps data through `Save` and `Load`, which map types by id.

**Why.** Game logic reloaded in a long-running server must leave nothing rooting the old assembly (column arrays,
transition edges, query cache keys, registries), and repeated reloads must not grow every mask. Dropping tables is
the one place a table is deleted outside `Dispose`, so steady-state code pays nothing (CreateAddDestroy, Prefab and
WorldSimulation within noise).

**Considered.** Migrating rows from the old types to the new ones in memory (needs a type map for every field; `Save`
/ `Load` already map by type id and field hash); never reusing bits (the mask grows by every reloaded component).

## D18. No interceptors for query calls; filters carry no references [#d18-no-interceptors-for-query-calls-filters-carry-no-references]

**Decision.** Query calls are not intercepted. `QueryFilter` holds its five sets' first 256 bits inline and its bits
past 255 as an interned id, so it holds no object reference, and its builder copies it once per call.

**Why.** An interceptor replaces the method a call binds to, but the call's arguments are still evaluated, so a
filter built at the call is built either way; caching a query entry per call site would save only the memo lookup the
call already makes. The cost was the filter itself: five masks with an overflow reference each made every builder
call two copies through `BulkMoveWithWriteBarrier` and zeroed the caller's frame. Without references, counting 16
entities with `QueryFilter.Create().With<Npc>().Without<Dead>().Without<Frozen>()` built at the call takes 76 ns
against 124 ns, and with the filter in a static field 24 ns as before (`CallSiteBenchmark`). Hoisting stays the
advice for hot calls.

**Considered.** Interceptors with a static filter and a cached entry per site (the arguments make it moot); an
analyzer warning for filters built at the call (most calls are cold; the docs teach the static field).

## D19. No settable tag properties [#d19-no-settable-tag-properties]

**Decision.** A tag's generated `IsX` is read-only; `SetX()` adds the tag and `RemoveX()` removes it.

**Why.** `entity.IsDead = true` (Entitas style) cannot be written where ECS code holds its entities: C# 14 rejects
assigning an extension property of a struct on a `foreach` variable (CS1654), an indexer result (CS1612) or a field of
an `in` parameter (CS8332), with a by-value or an `in` receiver alike. A member that compiles on a local but not in
`foreach (var e in hits)` or on `link.Target` teaches the wrong thing; the methods work everywhere, and a structural
change stays a call.

## D20. Generic systems register the closed types their assembly names [#d20-generic-systems-register-the-closed-types-their-assembly-names]

**Decision.** A closed generic system is a system of the set of every assembly that names it
(`AddSystem<Regen<Health>>()`, `[UpdateAfter<Regen<Health>>]`, `HasSystem`, `System`, `TryGetSystem` and
`RemoveSystem` of it): the generator closes the system's code struct over those type arguments in that assembly's set
([D103](#d103-system-sets)). A public generic system in a library gets a public code struct, named by
`[assembly: GenericSystemCode(typeof(Regen<>), typeof(__Regen_1_SystemCode<>))]`, so the generator of a referencing
assembly can close it there. A closed type no assembly names (made by reflection) has no code: `AddSystem` throws a
`NotSupportedException` naming the type and where to name it. A generic `[ForEach]` method of a system stays EECS004.

**Why.**
- **Native AOT and WebAssembly cannot make code at run time.** Closing a generic method over a value type with
  `MakeGenericMethod` fails there, and components are structs; every closed system named in source has its code
  compiled.
- **The assembly that names the type is the one that knows it.** A library cannot know the components a game closes
  it over; the game's own generator sees the call.
- **One path everywhere.** The JIT, Native AOT and WebAssembly run the same generated code; there is no fallback that
  works on one runtime only.
- **Runners need none of this:** their entry points are generic, so the caller's type arguments close the job at
  compile time. A system's own generic method has no caller to give it type arguments.

**Considered.**
- **Reflection at run time** (the earlier fallback for types closed in another assembly): breaks Native AOT for every
  value-type argument.
- **Scanning referenced assemblies for closed uses:** a library's generated code is internal to it; the public code
  struct is what a reference assembly keeps.
- **A virtual generic hook on the system:** systems have no instance (D102).

## D21. .NET 10 features only where they measure [#d21-net-10-features-only-where-they-measure]

**Decision.** Of the .NET 10 / C# 14 features weighed for 4.1, each was prototyped and measured with
BenchmarkDotNet against the commit before it (two runs each side, 0 bytes allocated throughout), and kept only as a
net win:

| Feature | Verdict | Numbers |
|---|---|---|
| `Vector512` (and `Vector<T>`) | kept: a table without tombstones counts the set bits of its row words, 8 words per step with AVX-512, else `Vector<T>` (4 on AVX2, 2 on Arm64) | CountBenchmark, 100,000 rows that must be tested: 48.9-54.5 μs -> 1.21-1.27 μs; `Vector<T>` alone 2.4 μs, one word at a time 5.2 μs; an indexed lane loop over a `Vector512` 7.6 μs (unrolled instead) |
| `GetAlternateLookup` on the query cache | kept: probed with the call's bits and a ref to its filter, no key built or copied | a filter past the memo 92-106 ns -> 86-90 ns |
| the memo's ways as structs in one array | kept | a static filter 21.6-21.9 -> 19.0-19.8 ns, no filter 36.8-39.1 -> 35.3-35.5 ns |
| `[InlineArray]` for the memo (every signature's ways inline in one flat array) | dropped | 1-2 ns more (20.3-20.6 / 38.9-39.5 ns), but signature indices are process-wide, so every world holds about 750 bytes per signature of the process (150 KB for 200) and copies it all for each new way |
| `FrozenDictionary` for saved types (lock-free lookups, frozen on the first load after a change) | dropped | a one-entity save and load 2.32-2.33 μs -> 2.23-2.34 μs: within noise; a load resolves each type once, not per entity |
| `System.Threading.Lock`, `params ReadOnlySpan`, null-conditional assignment | kept | cold paths |
| `RegisterImplementationSourceOutput` | kept: a system's code and the saved-type registration are reached only through module initializers | IDEs skip them while typing |
| C# 14 in generated code | kept: EasyEcs targets net10.0 (default C# 14), so every generator asks for C# 14 and generated lambdas leave out parameter types | |
| `OverloadResolutionPriority`, `field` | no place: they change overload choice and syntax, not the IL; the API has no array and span overloads of one method, and the candidates' backing fields are written outside their properties | |
| first-class span conversions, `nameof(List<>)` | no place: the remaining `.AsSpan()` calls are `Fill` and `foreach (ref ...)`, which conversions do not reach; the generators target netstandard2.0 and compare type names | |

**Considered.** Widening the inline component mask to 512 bits (every filter, key and table mask grows by 32 bytes
for components 256-511, which the overflow already covers).

## D22. Parallel runs use the thread pool and wake helpers only when they pay [#d22-parallel-runs-use-the-thread-pool-and-wake-helpers-only-when-they-pay]

**Decision.** A parallel `[ForEach]` and a stage of parallel systems run on the calling thread plus reusable
`IThreadPoolWorkItem` helpers, in chunks sized by the matching rows. Each job and each stage measures its runs: a run
with helpers yields its time and its items' summed thread time, and helpers stay while they make a run a fifth faster
than its work. Once it runs alone, a probe of four runs with helpers comes after a period that doubles from 16 to
1,024 runs, or at once when runs alone turn 1.5x slower. No spinning, no dedicated threads, no allocation.

**Why.** Waking a parked pool thread takes from a few to a few hundred microseconds and burns about as much CPU, so a
small pass between server ticks ran no faster with helpers and cost twice the CPU. A 60 Hz tick of one 100,000-row
pass on a 4-core VM: median pass 123 -> 111 μs, CPU per tick 436 -> 290 μs (serial: 108 μs, 229 μs). BDN:
ParallelSystems 804-808 -> 746-768 μs, ParallelForEach 294-308 -> 267-271 μs, BattleServer and Runner unchanged.

**Considered.**
- A crew of dedicated helper threads that spin about 50 μs after a run: it won only when passes ran back to back
  (BenchmarkDotNet's loop). In a server tick it lost: median 130 against 135 μs, but p90 170 against 190 μs and CPU
  per tick 990 against 760 μs.
- `ThreadPool.UnfairSemaphoreSpinLimit`: closes the back-to-back gap, but it is process-wide and keeps pool threads
  spinning between ticks (49 ms CPU per 16 ms tick), so it stays the application's choice.
- `Parallel.For` with static delegates as the runner (`ParallelRunnerBenchmark`, the steering pass of
  `ParallelForEachBenchmark`, at a machine load of 10 to 30 on 4 cores): at 1,000 rows the runner took 18 µs at 0 B,
  `Parallel.For` 24 to 42 µs at 1.5 to 1.9 KB; at 10,000 rows they were level within noise; at 100,000 rows
  `Parallel.For` came out 15 to 40 % faster, inside that load's noise (runs swung by 2x). Rerun with nothing else on
  the machine: 1,000 rows 17.4 µs at 0 B (serial 17.3 µs) against 20.9 to 22.6 µs at 1.7 KB; 10,000 rows 76 µs
  against 103 to 115 µs; 100,000 rows 871 µs against 862 to 948 µs, level within error. It also allocates per call and
  passes no state ([D69](#d69-reductions)).

## D23. Change summaries per block; removals summarized apart [#d23-change-summaries-per-block-removals-summarized-apart]

**Decision.** A tracked column keeps, per 64-row word, one 32-byte entry (latest tick, the rows at it, a bound of the
others, and a bound of the ticks of rows lacking the component), and per 4,096-row block the words at the block's
latest tick as a bit mask with a bound for the rest. A `Changed<T>` pass finds the next written word with one bit
scan; a `Removed<T>` pass skips words by their removal bound and blocks by their own removal summaries, so writes of
`T` do not make it visit their words.

**Why.** BDN against the per-word summaries: RemovalComparison with 10 removals 1.07-1.09 -> 0.87 μs; ChangeTracking
`Changed`, 10 written, 609-650 -> 514 ns; ChangeTrackingComparison 612-636 -> 497-573 ns. BattleServer,
WorldSimulation and the 1,000-written cases are unchanged.

**What remains.** Friflo reports 10 removals in 0.70 μs: it collects the removed ids in a callback as they happen, so
reading them costs nothing extra. EasyEcs keeps removals as data (D1): its pass costs about 90 ns plus about 30 ns
per word with a removal, the loads of the summaries and rows. At 1,000 removals the two are even (71 against 73 μs).

**Considered.** Interleaving a word's summaries with its block's (no gain: the summaries of 100,000 rows fit in L2);
noting the word in a separate helper called per row (slower: 600 μs per query tick); finding the column and word of a
removal once for its stamp and its removal note (no measurable gain, reverted).

## D24. An index's key holds its entities in one array [#d24-an-indexs-key-holds-its-entities-in-one-array]

**Decision.** A value index and a relation index keep each key's entities in one id array (`IndexHead`). A leaving
entity leaves a hole the key's next entity fills, so entities never move and a loop finds each entity once, whatever
is destroyed during it; arrays of emptied keys are reused. `CreateEntities` indexes its entities with one key lookup.

**Why.** The lists linked through per-entity nodes cost one dependent load per entity. BDN: IndexBenchmark 710 ->
156 μs; ValueQueryComparison 648 -> 225 μs (Friflo 323 μs); RelationComparison 26.8 -> 23.4 μs (Friflo 26.5 μs);
cascades unchanged, 0 bytes.

## D25. Structural row loops are compiled for tables without tombstones [#d25-structural-row-loops-are-compiled-for-tables-without-tombstones]

**Decision.** A `[ForEach]` that may change structure runs each table through a row loop compiled twice: for a table
with tombstones (each row tests its id) and for one without (no test). A table without tombstones at the call gains
one only through a structural change, which bumps the storage version and ends the loop.

**Why.** StructuralChangeComparison, 10 of 100,000 units killed per tick: 85.7 -> 80.9 μs (three rounds; Friflo's
command buffer 77 μs); 1,000 killed and BattleServer unchanged.

**Considered.** Holding the storage version seen in a register instead of re-reading it per row: 82 -> 108 μs (the
job's call leaves too few callee-saved registers, a column ref spills and round-trips the stack every row).

## D26. Generated members where code would repeat a type, and a suggestion to use them [#d26-generated-members-and-a-suggestion-to-use-them]

**Decision.** A query item's components have names: `item.Position` for `item.Component1`, generated per `Query<…>`
shape the code calls. A buffer element has writers on prefabs: `prefab.SetLoot(…)`, on
`Prefab.SetBuffer<T>(params ReadOnlySpan<T>)`. The analyzer suggests the generated member wherever code calls the
generic API (EECS033, Info, with a code fix): `entity.Get<Position>()` as `entity.Position`, `Has<T>()` as `HasX` or
`IsX`, `Set(new T(…))` as `SetX(…)`, `GetSingleton<T>()` as `world.X`, `Index<T, TKey>()` as `world.XIndex`,
`item.Component1` as `item.Position`, and the other members the generator writes. Multi-type `Disable` / `Enable` and
multi-type bulk calls are not built.

**Why.**
- **Query items.** `Component1..n` makes the reader count the type arguments. The named member is an inlined getter
  over the same ref, so it costs nothing. One file per shape keeps an assembly's output to the shapes it uses; one
  extension block per component and position would mean 45 blocks per component.
- **Prefab buffers.** Without `SetBuffer`, a prefab could hold only an empty buffer: filling one meant copying a
  buffer value, which EECS012 rejects. A relation gets no prefab writer, because a recipe's links would name the
  prefab's own rows.
- **The suggestion.** The docs, samples and templates write the generated members, and code that mixes both spellings
  reads worse than either. The rewrite is offered only where it means exactly the same call: the member must be
  generated for that type in that compilation (checked by binding the replacement), and it must return the same kind
  of reference: `Get<T>()` of a tracked component, whose property is `ref readonly`, becomes `WriteX()` (an indexed
  component has no writer, so its `Get<T>()` keeps its spelling).
  A buffer's members exist only while code names `DynamicBuffer<T>`, so the suggestion is not made where the call
  is the last such name. It is Info: a suggestion in the IDE that does not fail a build, since generic code needs the
  generic API and the two spellings compile to the same call. The analyzer's operation callback on invocations
  already runs for EECS025 and EECS034, so the suggestion adds one symbol check per call.

**Considered.**
- **`Disable<T1..Tn>()`, `RemoveAll<T1..Tn>()` and the other multi-type calls.** After a table's first disable, each
  call flips presence bits in place. n calls cost n gate entries of a few nanoseconds, and a bulk call over several
  types needs a meaning for "has any of them" that one-type calls do not. Not built.
- **A warning instead of a suggestion.** It would fail builds that treat warnings as errors over spelling alone.
- **Rewriting `SingletonRef<T>.Value` as `world.X`.** A `SingletonRef<T>` keeps the singleton's slot, so the
  rewrite would add a lookup per access. Not suggested.

## D27. Reading a missing singleton throws everywhere [#d27-reading-a-missing-singleton-throws-everywhere]

**Decision.** Every read of a singleton the world does not have throws `InvalidOperationException`: `world.X`,
`GetSingleton<T>()`, `SingletonRef<T>()`, and so a `[ForEach]` method's singleton parameter, on its system's first
run. The message names the singleton and the calls that add it (`world.SetClock(...)`, `AddSingleton<Clock>()`, or
`GetOrAddClock()` where a default is meant). `GetOrAddSingleton<T>()` / `GetOrAddX()` is the one read that adds the
default, and the code that calls it says so.

**Why.**
- **A forgotten setup fails where it happens.** Until 4.2 a `[ForEach]` parameter added the default singleton while
  `world.X` threw. A world built without its `SetClock(...)` then ran on a clock with no step: entities stood still,
  a test passed for the wrong reason, and nothing pointed at the missing line. Now the first `Update()` names the
  singleton and the call to add.
- **One rule for every read.** The same singleton read in an `[OnUpdate]` method and taken as a parameter behaved differently;
  now a read is a read, and only a call named `GetOrAdd` adds.
- **Nothing on the hot path.** A job resolves its singletons once per pass, when it is built; the check is the null
  test the old add made, and the throw is a cold method.

**Considered.**
- **Keep adding the default for `[ForEach]` parameters.** It saves a setup line in small programs and hides the
  forgotten one in real servers, where the default of most singletons (a clock, a configuration, a spawner) is wrong.
- **An analyzer rule for a singleton parameter no code adds.** The setup is host code, often in another assembly, or
  comes from `Load`, `LoadEntities` or a plugin; a compile-time check would miss those or flag correct code.
- **A check in `AddSystem`.** Systems are often added before their singletons, or before a `Load` brings them; the
  first run is the earliest point where the singleton has to exist.
- **`GetOrAddX()` as the explicit default** (chosen): where the default is right, such as a counter starting at
  zero, one call says it.

## D28. Reservations grow to what they need; entity storage on the pinned heap [#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap]

**Decision.** A reservation grows a table to the rows it needs, rounded up to whole presence words (64 rows), and the
entity storage to the ids it needs, or either to twice its capacity when that is more; not to the next power of two.
The reservations are `Reserve<T1..Tn>(count)` (the table of exactly those components), `Reserve(prefab,
count)`, `EnsureEntityCapacity`, `CreateEntities`, `InitialEntityCapacity` and a restore. An entity-storage array of
85,000 bytes or more that a reservation sizes is allocated on the pinned object heap, beside the unmanaged columns; the
steps of a doubling stay on the large object heap.

**Why.**
- **A start-up's cost was a collection, not the creation.** In a world that has never held entities, creating 100,000
  of them (the setup of Doraku/Ecs.CSharp.Benchmark: a fresh world per invocation, measured once) cost 11.8 to 12.6 ms
  in bulk, while the same rows cost 1.2 to 1.6 ms when the arrays were small objects (`DOTNET_GCLOHThreshold` raised). .NET
  starts a full collection once the allocations on the large object heap since the last one pass a budget, and,
  separately, those on the pinned object heap; after the collection between two iterations that budget is 3 MiB for
  each (`GC.GetGenerationBudget` in the measured call). `CreateEntities(new Entity[100_000], ...)` put the 1.6 MB
  handle array and a 2 MB entity array (131,072 records) on the large object heap, 3.7 MB, so every call paid a
  background gen2 collection; its throttling of large allocations made it cost 5 to 15 ms on the 4-core machine
  (4.8 ms as a blocking collection, `DOTNET_gcConcurrent=0`).
- **Both changes keep it under both budgets.** Sizes that a reservation names save 0.6 MB of the 100,000 entities;
  the entity records on the pinned heap move 1.6 MB to the other budget: the large object heap then holds the handles
  and the entity rows (2.4 MB), the pinned heap the records and one to three int columns (2.0 to 2.8 MB), and no
  collection runs. Bulk creation went from 11.8 / 12.6 / 12.6 ms to 2.7 / 2.5 / 2.7 ms (one, two, three components),
  5.03 / 5.53 / 6.03 MB to 4.20 / 4.58 / 4.96 MB.
- **`Reserve<T1..Tn>` for entities created one by one.** `EnsureEntityCapacity` sized only the records, so the
  table still doubled from 64 rows, allocating twice its final size: 2.67 / 3.32 / 3.99 ms and 4.53 / 5.53 / 6.53 MB
  before, 1.94 / 2.71 / 2.60 ms and 2.67 / 3.05 / 3.44 MB with the table reserved (Friflo with `EnsureCapacity` on its
  store and archetype: 11 to 12 ms; Arch with `EnsureCapacity`: 3.4 to 4.2 ms).
- **Pinning moves nothing that would have moved.** Neither heap compacts by default; handles index the record array
  without bounds checks and it is never moved; the collector scans a pinned array's references like any other. The
  arrays a doubling discards stay on the large object heap, which can still be compacted when asked to
  (`GCSettings.LargeObjectHeapCompactionMode`), so they leave no hole for good.
- **Warm paths are untouched.** A world that is not growing runs the same code; reservations add one comparison.
  Doubling still bounds a table that grows by many small reservations (two batches of 100 and 30 rows: 128, then 256).

**Considered.**
- **Pages for the records and columns** (Arch's chunks of 16 KB): small objects never set off a full collection, but
  every handle access would pay an indirection (D7).
- **Every large record array on the pinned heap**, doubling steps too: a start-up of 100,000 entities with three
  components and no reservation then crossed the pinned budget twice (10.0 ms against 6.6 ms).
- **The entity rows on the pinned heap as well:** the records, rows and two int columns already pass 3 MiB there.
- **Returning a disposed world's arrays to a pool** for the next world: the records cannot go, since handles of the
  disposed world still index them unchecked, and the pool would keep memory a process has finished with.
- **A count-only `CreateEntities(count, values)`** without the handle span: not needed once the bulk call stays under
  both budgets with the span.

## D29. Performance rules only where the cost is measured and the fix does the same [#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same]

**Decision.** The analyzer reports code that works but does more than it needs, as EECS025 to EECS034, and the
severity says which kind: a warning means the code costs (a benchmark shows it slower than its fix, or allocating);
a suggestion (Info) means the fix is the same cost written shorter; an error means the code cannot work. A rule ships
only when its fix does the same thing, and a code fix is offered only when the analyzer has bound the replacement.
Candidates without a measured cost, or with a fix that changes behavior, were dropped.

| Rule | Severity | Measured (100,000 entities) |
| --- | --- | --- |
| EECS025 a write access that only reads | Warning | a tracked `ref` 306 µs, `in` 271 µs; untracked equal (270 / 276 µs): the cost is the write set |
| EECS026 an unused parameter | Warning | per row equal (41 / 46 µs); an `Entity` or `World` makes the system run alone, a `ref` of a tracked component stamps every row |
| EECS027 a lookup per row | Warning | `entity.Read<T>()` 258 µs, a parameter 40 µs; `Has<T>()` 208 µs, `Maybe<T>` 86 µs; a singleton through the `World` 105 µs, a parameter 48 µs |
| EECS028 an allocation every update | Warning | garbage every tick; the [Don't](/en/docs/performance#dont) list |
| EECS030 a structural change per entity over a query | Warning | `BulkBenchmark`: entity by entity 19.1x the time of `SetAll` / `RemoveAll`, about 99x that of `DisableAll` / `EnableAll` |
| EECS031 creation one by one in a counted loop | Warning | a fresh world only ([D28](#d28-reservations-grow-to-what-they-need-entity-storage-on-the-pinned-heap)); `MicroBenchmarks.Churn` 2.1x the time of `ChurnBatch` |
| EECS032 counting and testing by hand | Warning | `Count() > 0` 429 ns, `Any()` 18.6 ns; a `Has<T>()` test in the loop 332 µs, a filter 59.5 µs |
| EECS033 the generated member | Info | the same call, the same cost ([D26](#d26-generated-members-and-a-suggestion-to-use-them)) |
| EECS034 a world update inside a system | Error | recursion, or systems run in the middle of a stage |

`AccessBenchmark` measures each pair (BenchmarkDotNet, a shared 4-core Xeon at 2.1 GHz, .NET 10.0.13); every variant
allocates nothing.

**Why.**
- **Warnings fail builds that treat warnings as errors**, so each must be right wherever it fires. The rules read
  every use before they report: EECS025 counts an assignment, `++`, a `ref` or `out` argument, a method that is not
  `readonly`, a `ref` local and a `this ref` extension as a write; EECS027 reports only lookups made on every row,
  of components the method does not change itself; EECS028 leaves out `throw`, `[Conditional]` calls, console
  output, and the `[OnUpdate]` method of a system with its own `UpdateInterval`; EECS030 leaves out a `Set` that overwrites
  a component the query requires and one of a grouped component (its rows move one by one in `SetAll` too); EECS031
  leaves out constant counts under 4,096 and arrays created with one (no array reaches the large object heap), loops
  after a reservation, creations under a branch or in an inner loop, and loops in systems (a running world reuses its
  rows); EECS032 reports `Count` compared with 0 or 1, a loop that only counts, and a test that is the loop's first
  statement.
- **Every cost is a warning, whatever its size.** A reservation pays most in a world growing to that size for the
  first time, and `Any` and filters in proportion to the rows a loop would visit; where the rules fire, the code is
  slower than its fix, so they are warnings like the others. Only EECS033 is a suggestion: the generated member calls
  the generic API, so it changes how long the code is, not what it costs.
- **The fix is the rule's proof.** Each replacement is bound in place before it is offered: a member that is not
  generated, a filter that does not compile or a caller that passes `ref` to the method means no fix.

**Considered.**
- **Several components added or removed one call at a time** (`e.Set(a); e.Set(b);` as `e.Set(a, b)`): 500.7 µs one
  by one against 480.7 µs together, and 290.1 against 308.7 µs for two 16-byte components. The second move is as
  cheap as the first once the transition is cached. Dropped. A `Set` right after a creation is another case, and is
  measured as one ([D59](#d59-analyzer-rules)).
- **A tag taken as a parameter instead of `[With<T>]`**: 37.7 against 38.6 µs; what costs is the access it
  declares, which EECS026 already reports for any unused parameter.
- **`[Changed<T>]` of an untracked component**: the attribute's constraint already fails it (CS0315).
- **`Parallel = true` on structural or tiny work**: structural work is EECS010; whether a pass is tiny depends on the
  entity counts at run time.
- **Conflicts between systems of a parallel stage and redundant orderings**: the stages are formed from the order the
  host adds systems in, at run time; a redundant `[UpdateAfter<T>]` costs nothing.
- **`World.Update` from another thread**: a world may run on any one thread that owns it (one world per thread), and
  EECS014 reports the structural calls that race with its owner.
- **Hand-written `Query` loops in `[OnUpdate]` methods, `Capture` or `Describe` on the hot path, value index lookups in loops**:
  `Query` is a supported API whose costs EECS030 and EECS032 already name; a snapshot per tick is how rollback works;
  an index lookup is O(1) and a `[ForEach]` method cannot hoist it. No rule.
- **A `QueryFilter` built per call instead of kept in a `static readonly` field**: a filter is a small struct with no
  references ([D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)); not measured as a cost. No rule.

## D30. Saves record types by Nino type id; Nino writes the unmanaged components marked `[NinoType]` [#d30-saves-record-types-by-nino-type-id]

**Decision.** A save (format 2) records each component, buffer element and singleton type by its Nino type id: the
hash Nino computes from the namespace-qualified name, or from the name `[NinoFormerName]` keeps. A plain unmanaged
component is written as its raw rows, as before; an unmanaged one marked `[NinoType]` is written by its formatter, row
by row. A load refuses rows written another way than the process writes them, and two types of the process that share
an id, with a message that names the fix. Format 1 saves (4.3 and earlier) are refused.

**Why.**
- **Renames are the change saved data meets most often**, and a name in the save made each one a silent loss of data.
  Nino already has the rule for it (`[NinoFormerName]` keeps a type's id across renames, also for its own polymorphic
  data), so EasyEcs follows that rule instead of adding a second rename attribute or map.
- **Unmanaged components need to change too.** A raw row can only load into the same shape; a component that will
  gain fields says so by marking itself `[NinoType]`, and its format decides what may change (`VersionTolerant`
  appended members, `Keyed` any member change). Components that stay raw keep the block copy.
- **The cost stays where it is chosen.** 100,000 entities in two raw tables save in 271 µs before and 262 µs after,
  load in 1,052 and 1,003 µs; one entity of four components goes through bytes and back in 2.25 and 2.22 µs; all
  0 B. A type costs four bytes for its id instead of its name.
- **No conversion of old saves.** A reader for format 1 would keep the name lookup in every later version, for data a
  build can write again once (the [migration guide](/en/docs/migration#v4-4-saves) has the steps).

**Considered.**
- **Names with a rename map** (`World.RenameType("Old", typeof(New))`): a second mechanism next to Nino's, configured
  in code instead of on the type.
- **Nino's type registry** for the lookup: it caches types process-wide, so a collectible plugin's types could never
  unload; EasyEcs computes the ids itself and forgets them with the plugin.
- **Every unmanaged component through Nino:** the block copy of a column is what makes a save fast, and most
  components never change shape.

## D31. A record of what persists: a component set to save, loading onto existing entities [#d31-a-record-of-what-persists]

**Decision.** `SaveEntitiesWith(output, ids, set)` writes only the components of a `ComponentSet`, and
`LoadEntitiesInto(input, entities)` loads a save of entities onto entities that exist, the i-th saved entity onto the i-th
given, each moving table at most once. A `ComponentSet` is a bit mask built once (`With<T>()`, `With(Type)`); the save
selects each table's rows in O(group).

**Why.**
- **An actor persists part of its entity**: a balance survives a restart, its connection and timers do not, and those
  runtime components often have no Nino formatter. A set names the record per save, so one entity can feed several
  stores.
- **The entity exists before its record arrives.** An actor is activated, gets its entity and starts handling
  messages while its record loads from a database; `LoadEntities` would create a second entity and rewrite the
  record's `EntityId` fields to it.
- **One move per entity.** The components a record brings are added with one transition (a signature cached per
  table), then written, so the indexes, groups and change ticks follow as with one `Set` of all of them.
- **Measured** (`MigrationBenchmark`, warm, 0 B): saving two of an entity's four components takes 104 ns, loading
  them onto an entity that holds the other two 722 ns, against 2.22 µs to send the whole entity through bytes and
  create it again.

**Considered.**
- **A `[Persistent]` attribute on component types:** one global choice, where different saves of one entity need
  different components.
- **Filtering at load time:** the save would still write, and need formatters for, the runtime components.
- **`LoadEntities`, then copying the components onto the actor by hand:** two moves per entity, a temporary entity,
  and `EntityId` fields that name the temporary one.

## D32. The lists of dead buffers are pooled per thread [#d32-the-lists-of-dead-buffers-are-pooled-per-thread]

**Decision.** A `DynamicBuffer<T>` whose value dies (its component removed, its entity destroyed, its table dropped,
a disabled value discarded) empties its list and keeps it in a pool of its element type on the current thread; a first
write takes a list from there before allocating one. The pool holds only lists that died while none were taken, and
drops a list of more than 4 KB.

**Why.**
- **Entities that come and go with buffers allocated per entity.** An actor loading with a mailbox and unloading
  again cost two allocations each time: 1,000 actors with four messages each, unloaded and loaded,
  took 76.4 µs and 85.9 KB before, 76.9 µs and 0 B after (`BufferChurnBenchmark`); the other buffer benchmarks did not
  move.
- **Per thread is per world.** Buffers die in structural changes, which run on the world's owner thread, so the lists
  of a world come back to the buffers of that world (or another world of the thread) with no lock.
- **Bounded like the rows.** The pool grows only to the most lists dead at once, the peak a table's capacity keeps
  as well, and the 4 KB cap leaves a list that once grew large to the collector.

**Considered.**
- **Recycling when rows are released:** a row move copies the reference first, so the list would still be in use.
- **A fixed number of pooled lists** (256): churn above it allocated again, and a peak is already bounded by the
  entities that held the lists.

## D33. One entity runs a pass's job: `entity.Run` [#d33-one-entity-runs-a-passs-job]

**Decision.** `entity.Run<T1..Tn, TJob>(ref job)` and `Run(ref job, filter)` run an `IForEachEntity` job on one
entity with what a pass guarantees: `Writes` stamp change ticks, the refs stay valid across the job's own structural
changes (written components are carried to the new row, also when the job throws), `INoStructuralChanges` freezes
the structure. The filter is tested on the row itself.

**Why.**
- **Code that handles one entity at a time** (a request, an actor's message) otherwise looks each component up
  through the handle and takes its refs again after every structural change. One job gets one lookup for all its
  components and the same rules as the systems.
- **No slower than the code it replaces.** 1,000 calls on 10,000 entities with 1, 3 or 5 components, with and without
  a filter and a structural change, against the same work through the handle (`SingleEntityBenchmark`): 0.69 to
  1.06 times the handwritten time, 0 B. The cases at 1.04 and 1.06 (a filter and a structural change, 3 and 5
  components) are within the run's error.
- **The thread rule stays the owner's.** A plain flag store freezes the structure when the gate is free (the owner
  outside any region); inside a parallel region the region's freeze is already held, and the analyzer reports `Run`
  as a structural call ([EECS010](/en/docs/guide/analyzer#eecs010), EECS013, EECS014).

**Considered.**
- **A filter tested through the query cache:** a lookup of the filter's table set per call, which cost more than the
  job; testing the row's table mask and presence bits is O(1) per filter component.
- **Interlocked freeze and pass counters, as passes use:** about 12 ns per call; the owner thread alone touches them
  when the gate is free.

## D34. Group filters through interfaces [#d34-group-filters-through-interfaces]

**Decision.** A system group that implements `IGroupWith<T>` or `IGroupWithout<T>`, itself or through one of its
interfaces, gets the same filter as `[With<T>]` / `[Without<T>]` on the group. The generator reads the interfaces with
the attributes; nothing changes at run time.

**Why.**
- **A generic group cannot name its filter in an attribute.** C# refuses a type parameter as the type argument of an
  attribute (CS8968), so `[With<Inbox<TActor>>]` cannot sit on `IActorGroup<TActor>`. Interfaces take type
  parameters, and one interface then gives every actor type a group of its own.
- **The same filter, the same cost.** The interfaces become the same `With` / `Without` of every `[ForEach]` method
  of the group, built once per method; a pass does not know where they came from.
- **Types from another assembly work.** A framework can ship the tag and the interface; the closed types are the
  user's (`struct Map : IActor<Map>` filters by `In<Map>`).

**Considered.**
- **A `Type` argument in the attribute** (`[GroupWith(typeof(Inbox<>))]` closed over the group): attributes cannot
  take open generic types bound to the group's arguments either, and the binding rule would be ours to invent.
- **Filters in a static member of the group:** the generator would have to evaluate code; interfaces are symbols.

## D35. A record can load without counting as a change [#d35-a-record-can-load-without-counting-as-a-change]

**Decision.** `LoadEntitiesInto(input, entities, markWritten: false)` loads the record without stamping it: every
component the record holds ends with tick 0 (never written), whether it replaces a value or adds one; the components
it does not hold keep their ticks. The default stays `true`.

**Why.**
- **A restored record is not news.** A system that saves or replicates `[Changed<T>]` rows would otherwise send what
  was just read from the database straight back.
- **A replaced value's tick describes a value that is gone.** Keeping it would make a default from a prefab count as
  written, so every activation of an actor made from its prefab would save the record it just read.
- **The load already decides the ticks** (one move per entity, then the values); clearing them costs nothing.

**Considered.**
- **Keeping the tick of a replaced value:** restored actors would need a second prefab per kind, one without the
  persistent components.
- **Clearing the row's ticks after the load:** components the record does not hold would lose their writes too.
- **A separate `RestoreEntitiesInto`:** the same call with one difference; a parameter says it where it is used.

## D36. Not added: parallel span methods, a row's last write tick, public access sets, a shared parallelism budget [#d36-not-added]

**Decision.** Four requests were weighed and left out.

**Why.**
- **`[ForEach(Parallel = true)]` on span methods.** 100,000 entities, `ParallelForEachBenchmark`: a heavy steering
  pass took 766 µs as a parallel batch and 727 µs per entity in parallel; a light drift took 54.5 µs and 55.6 µs
  (107 µs on one thread). On several threads the per-entity pass already reaches memory's speed, so a span method
  stays serial (EECS010). `World.ForEachBatchParallel` exists for another reason: a parallel reduction keeps its
  partial result in a local per run of rows ([D69](#d69-reductions)).
- **`entity.LastWriteTick<T>()`.** `entity.Run(ref job, QueryFilter.Create().Changed<T>(tick))` answers "was it
  written since?" for one entity without exposing the tick column.
- **Public `SystemAccess`.** The read and write sets are how the scheduler decides; publishing them freezes that shape
  into the API, and no use outside the scheduler remained.
- **One parallelism budget for several worlds.** The host sets `WorldOptions.MaxDegreeOfParallelism` per world;
  a shared budget would be state shared across worlds, which each belong to one owner thread.

## D37. The EasyEcs package brings Nino's generator [#d37-the-easyecs-package-brings-ninos-generator]

**Decision.** EasyEcs references the `Nino` package (runtime and generator) instead of `Nino.Serialization` (runtime
only). `Nino.Generator` ships its analyzer through `buildTransitive`, so every project that references EasyEcs gets
the formatters of its `[NinoType]` components without a package of its own.

**Why.**
- **One package to install.** Saves are built in; a managed component needed a second reference, at the same version
  as the Nino of EasyEcs, or `Save` threw at run time.
- **No drift.** The generator always matches the runtime EasyEcs was built with; an older explicit reference fails
  restore with `NU1605` instead of compiling against another Nino.
- **Little cost.** In a project without `[NinoType]` types the generator writes one empty internal registry.

**Considered.**
- **Keeping `Nino.Serialization` and documenting the second reference:** the step users missed.
- **Bundling Nino's generator inside the EasyEcs package:** a copy of another project's analyzer to keep in sync by
  hand.

## D38. The hidden columns are not generic over their component [#d38-the-hidden-columns-are-not-generic-over-their-component]

**Decision.** The change-tick column of a tracked component and the tag of a disabled one are non-generic types
(`ChangeTick`, `DisabledTag`), one bit per owner, each described by its owner's `Type` (released with it when its
context unloads). The public `Disabled<T>` stays: its bit is the tag bit of `T`.

**Why.**
- **Native AOT without warnings.** Registering `ChangeTicks<T>` through the same generic path as a component made the
  AOT compiler see `ChangeTicks<ChangeTicks<...>>` (and `Disabled<Disabled<...>>`) without end: IL3054 in every
  program with a tracked component, the built-in `ChildOf` included, which fails a build with warnings as errors.
- **Nothing changes at run time.** A tick column was already 8-byte unmanaged rows found by a bit; the bit now comes
  from a static field of the component's own registration.

**Considered.**
- **Suppressing IL3054 in the package:** a warning in users' builds cannot be suppressed from a library, and the
  recursion is real for the compiler.
- **A separate tick array per table outside the columns:** a second storage path for moves, snapshots and saves.

## D39. A whole load can leave the change ticks alone, and a system can start now [#d39-a-whole-load-can-leave-the-change-ticks-alone]

**Decision.** `world.Load(input, markWritten: false)` clears the change ticks of every loaded row (no write, no
removal), as `LoadEntitiesInto(..., markWritten: false)` does for a record. `AddSystem<T>(changesFromNow: true)`
sets the new system's last run to the current tick and moves the world's tick on, so its first run sees only later
writes. Both defaults stay as they were.

**Why.**
- **A restart is not news.** A process that resumes a saved world would otherwise save or replicate everything on the
  first tick of every `[Changed<T>]` system.
- **Systems added after the load need nothing more.** A new system's first run looks at ticks from 1; cleared rows
  have tick 0.
- **`changesFromNow` covers the other case:** a system switched on in a world whose rows were written by code (or a
  default load), which should not treat that history as changes.

**Considered.**
- **Only `changesFromNow`:** systems that already ran before the load would still see every loaded row.
- **Setting the last run without moving the tick:** writes made later in the same tick would be missed.

## D40. Destroyed entities go to a log each reader reads by its own tick [#d40-a-destroy-log-read-by-tick]

**Decision.** `WorldOptions.DestroyLogCapacity = n` keeps a ring of the last n destroyed entities, each an `EntityId` and the
change tick of its destruction (16 bytes), allocated once at `new World`. A record is written when an id stops being
alive: `Destroy`, `DestroyEntities`, cascades, `MoveEntities` out of the world, the removal of an entity's last cleanup
component, and the entities a `Restore` or `Load` takes away. `world.DestroyedSince(since, into, out count)` reports
those at or after `since`; when the ring has overwritten records the reader needs, it returns false and the reader
resynchronizes. Off by default.

**Why.**
- **Despawns are the one change replication could not see.** A destroyed entity has no row, so `[Removed<T>]` cannot
  report it; the workaround (a tag replication reads, destroy after it ran) works for one reader, not for clients
  that acknowledge at different ticks.
- **The reader keeps its mark, the world keeps nothing per reader.** One tick per client is the same mark
  `QueryFilter.Since` takes, so one log serves any number of clients, and a client that connects or leaves changes
  nothing in the world.
- **Bounded and honest.** A long-running server cannot keep every destroy; a reader that fell behind the ring is told
  so (`DestroyLogOldestTick`) instead of getting a partial list.
- **It follows `IsAlive`.** A handle that reports "not alive" and a log that says "destroyed" never disagree, also for
  an entity kept by cleanup components (logged when the last one goes).
- **Measured** (`DestroyLogBenchmark`, `DestroyLog` 0 and 4,096, 0 B either way): 10 rounds of 1,000
  creates and destroys take 219 µs without the log and 250 µs with it one by one, 124 and 144 µs a whole table at
  once. Reading the records for 16 clients every round (868 µs against 215) is the replication itself: up to 4,000
  records copied per client.

**Considered.**
- **A cursor per reader inside the world:** state per client in the world, to create and release with connections.
- **An unbounded list:** memory that grows with the uptime.
- **Keeping destroyed rows as tombstones a filter can see:** every query would pay for rows that are gone.
- **Logging at destroy time for entities held by cleanup components:** the log would report entities that are still
  alive (retired, tagged `Retired`).
- **Clearing the log on `Restore` and `Load`:** every reader would resynchronize after each rollback; logging what
  they take away keeps readers exact.

## D41. Instantiating with components lands in the final table in one copy [#d41-instantiate-with-components]

**Decision.** `world.Instantiate(prefab, in c1 … in cn)` (and the form for a wave) copies the prefab's row and the
given components straight into the table of their union: one row copy, no intermediate table. The target table is
cached per (prefab table, component signature). Given values replace the prefab's or add to them; a given component
the prefab holds disabled comes enabled, as with `Set`. Group prefabs are supported: the group is created, then the
entity of the prefab passed gets the components (one more move).

**Why.**
- **A spawn that differs per instance is the common case:** a child with its parent, a projectile with its owner, a
  unit at its position. `Instantiate` then `Set` copies the row twice and may create a table nothing else uses.
- **One lookup per spawn after the first.** The cache gives the target table and the column copy plan at once.
- **Measured** (`PrefabBenchmark`, `InstantiateThenSetChild` against `InstantiateWithChild` and
  `InstantiateBatchWithChild`, 1,000 spawns with a parent, 0 B): 109–115 µs to instantiate and then set
  `ChildOf`, 85–93 µs with `ChildOf` given, 46–47 µs for the batch form.

**Considered.**
- **Following the `AddBits` transition edges from the prefab's table:** it would create the prefab-only table in the
  world, unused, and walk one edge per component.
- **Refusing group prefabs:** a group spawn with a parent is common (a boss and its guards under a squad); one move
  for the one entity is cheaper than a second API.

## D42. Memory is given back on request only: `TrimExcess` [#d42-trimexcess-on-request-only]

**Decision.** Tables double when they fill and never shrink on their own. `world.TrimExcess()` drops every empty table
(except the empty-mask table and those a live `WorldSnapshot` holds rows of), compacts the table registry, forgets
the transition edges and cached matches of the dropped tables, shrinks the other tables to their rows rounded up to a
power of two (64 at least), and releases the buffers of saves, loads, migrations and prefab lookups. Snapshots are
renumbered to the new table order and keep restoring. The entity records (`Meta`) and value-index nodes keep their
length.

**Why.**
- **A peak is not the steady state.** A world that held 100,000 entities for one event keeps their rows and the empty
  tables in every query's match list; a long-running server needs a way to give that back.
- **Shrinking is a decision only the host can make.** It knows when a quiet moment comes (after a wave, between
  matches); a shrink the world made on its own would allocate in a tick when the entities return.
- **Power-of-two capacities** keep the growth rule of every other table: the next additions do not reallocate at
  once.
- **`Meta` stays.** Handles index the entity records without a bounds check; shrinking them would cost every access.
- **Measured** (`TrimBenchmark`, 16 and 256 tables): 47 µs and 199 µs (31 KB and 181 KB: the smaller arrays) to
  give back what a peak of 100,000 entities left; 54 ns and 145 ns when there is nothing left to give back.

**Considered.**
- **Automatic shrinking below a fill ratio:** churn around the threshold and allocations no one asked for.
- **Leaving holes in the registry:** every walk over tables would test for them.
- **Clearing every transition edge:** the next structural change of every kept table would search again.
- **Invalidating snapshots:** a rollback ring would break on each trim.
- **Exact sizes, or a "keep N updates' worth" parameter:** the first addition after a trim would grow again; a
  parameter would encode a policy the host already decides.

## D43. Systems report what they allocate and visit; the schedule is a description [#d43-stats-and-schedule]

**Decision.** With `MeasureSystems`, `SystemStats` adds `LastAllocated` / `TotalAllocated` (bytes the run allocated on
its thread, plus the helper threads of its parallel `[ForEach]` chunks) and `LastEntities` / `TotalEntities` (the
matches of each `[ForEach]` pass, counted with the pass's filter when it starts). `world.DescribeSchedule()` returns
records of names (groups, stages, systems with their reads and writes, waits, registration-only pairs) with
`ToString()` and `ToMermaid()`.

**Why.**
- **A slow system is either doing more or allocating.** Time alone does not say which; bytes and entities do, per
  system, on a live server.
- **The loops stay as they are.** The entity count is one `Count` per pass at its start; a counter in the row loop
  would cost every row, measured or not. Off, the stats cost one field test per pass.
- **Bytes where they are made.** `GC.GetAllocatedBytesForCurrentThread` around each run and each helper chunk counts
  exactly the system's work, also with parallel stages.
- **A description, not the access sets.** The scheduler's `SystemAccess` stays internal
  ([D36](#d36-not-added)); names and stages are what a reader needs, and the records can change shape without
  changing the scheduler.
- **Measured** (`ParallelSystemsBenchmark` with `Measure` false and true, `IntrospectionBenchmark.Schedule`, 0 B
  per update): one update of 100,000 entities takes 349–358 µs unmeasured and 369–372 µs measured on one thread
  (+4–6%), 232–257 µs and 275 µs with parallel stages. `DescribeSchedule` takes 94 µs and 26 KB: a call for tools.

**Considered.**
- **Counting visited rows in the loop:** a cost on every row of every pass.
- **Summing the rows of matching tables:** wrong for filters that test rows (`Without`, `Changed`).
- **The calling thread only, or the process-wide counter:** the first misses parallel helpers, the second counts
  other systems and other worlds.

## D44. Slices: a filter cut at 64-row words, chosen by the system's run count [#d44-slices]

**Decision.** `[ForEach(Slices = N)]` passes `QueryFilter.Slice(RunCount % N, N)`, where `SystemHandle.RunCount` counts
the system's completed runs. A table is cut at multiples of 64 rows from its row count when the pass starts; table i
of the match starts at slice (index + i) mod N. The `ForEach` family honours a slice; `Query`, `Count`, `Any`,
`DestroyAll`, `entity.Run` and the bulk calls throw for one. `[Changed<T>]` / `[Removed<T>]` methods cannot be
sliced (EECS035).

**Why.**
- **A spike becomes a slope.** A system over a large population (re-scoring targets, scanning sessions) costs about
  1 / N per update instead of everything on one.
- **Words keep the fast paths.** A cut on a presence word never splits the 64-row tests and summaries a pass skips by;
  a table under 64 rows is one piece, and the rotation spreads many small tables over the slices.
- **The state is data the system already has.** The run count lives on the system as the scheduler's bookkeeping,
  not in user code or the world.
- **A slice of a count is rarely meant.** The calls that need every row throw instead of answering for a slice.
- **Measured** (`SlicesBenchmark`, 100,000 entities, Slices 1 and 4, 0 B): one sliced update takes 72 µs against 287 µs
  (stable pass), 83 against 322 µs (with the entity) and 36 against 113 µs (parallel). The four updates that visit
  every row once take 295, 319 and 127 µs: cutting costs 3%, nothing and 12%.

**Considered.**
- **Row-exact cuts:** words split between slices, tested row by row.
- **An overload with a slice argument on every `ForEach`:** twice the API for one filter field.
- **Slice state in the world:** shared by systems that slice differently.
- **Honouring slices in `Count` and `Query`:** silently partial answers.
- **Allowing `Changed` / `Removed`:** each run moves the system's last-run tick, so the rows of the other slices would
  lose their changes.

## D45. Unique keys: a marker interface, an eager index, a claim before the write [#d45-unique-keys]

**Decision.** A component implementing `IUniqueIndexed<TKey>` is indexed from the first table holding it, in every
world, and every write that would give a second entity a key another one holds throws `InvalidOperationException`
before anything changes (a save holding a key twice: `InvalidDataException`). The index factory is registered by the
generated module initializer (or by the first `world.Index<T, TKey>()`). A null reference key is no key. `EntityId`
keys cannot be unique (EECS036).

**Why.**
- **Uniqueness belongs to the type.** An account id or a session token is unique in every world; a per-world option
  would let one world accept duplicates.
- **Checked before, never rolled back.** Each path (Set, create, `Instantiate`, `Clone`, `SetAll`, `Enable`, loads,
  moves) claims the keys before it stores or moves, so indexes, groups and change ticks never see a half-done write.
- **Eager, because a lazy index cannot check.** A plain index is built by its first lookup; a unique one must see the
  first write.
- **No reflection.** The marker is a type test the JIT folds, and the factory is generated, so Native AOT needs
  nothing.
- **Measured** (`IndexBenchmark`, 100 new keys and 100 lookups, 0 B): 24.6–24.9 µs with `IIndexed<long>`,
  25.2–25.4 µs with `IUniqueIndexed<long>`: the claim costs about 6 ns per write.

**Considered.**
- **Reflection over the key type:** AOT warnings and a cold start per type.
- **A default interface method or a visitor to reach the key:** a virtual call per write.
- **Writing, then rolling back on a collision:** partial changes visible to indexes and groups.
- **`EntityId` keys:** loads and moves rewrite them after the rows are copied, too late to check first.

## D46. `Mut<T>` stamps the row it writes, by row where rows cannot move [#d46-mut-stamps-per-write]

**Decision.** A `Mut<T>` parameter is a write of `T` for the scheduler and the carry-over of change ticks, but the row
loop does not stamp its column: `Write()` (and a `SetIfChanged` that stores) stamps the row it writes. A method that
changes no structure and runs on one thread walks runs of rows, and each `Mut<T>` knows its table and row, so a write
stamps the row directly; in a method that changes structure, or a parallel per-entity method, a write looks up the
entity's current row first. Batch methods keep spans (EECS009), indexed and grouped components keep `Set` (EECS015).
The analyzer does not suggest `Mut<T>` for a `ref` parameter that every path writes (EECS025 is unchanged); one that
some path leaves unwritten is EECS053 ([D66](#d66-a-ref-written-on-some-rows)).

**Why.**
- **A recomputed value is not a changed value.** A system that writes a target every tick through `ref` stamps every
  row, so every `[Changed<T>]` reader visits every row; `Mut<T>` stamps only the rows whose value changed.
- **The row is known where it cannot move.** In a pass that changes no structure the visited row is the entity's row
  for the whole call; a structural change in the body moves the entity, so there the row is looked up.
- **A write costs what it does.** Where most rows are written, the plain `ref` (one bulk stamp per run) is cheaper; only
  the data tells which applies, so the analyzer stays silent.
- **Measured** (`ChangeTrackingWriteBenchmark`, 100,000 aims recomputed per tick, 10% of them changing): the writer
  alone takes 110 µs through `ref` and 135 µs through `Mut<T>` (a comparison per row against a bulk stamp); with the
  downstream `[Changed<T>]` reader, 162 µs and 172 µs, the reader dropping from 52 µs to 37 µs. Looking the entity up
  on every write took the writer to 348 µs.

**Considered.**
- **Looking the entity up on every write:** 2.6 times the cost of the writer by row in the benchmark above.
- **A per-row "written" mask merged after the pass:** storage per row and a second pass.
- **An EECS025 suggestion from `ref` to `Mut<T>`:** a slower fix wherever most rows are written.

## D47. `SetIfChanged` compares with `IEquatable<T>`, else the bytes [#d47-setifchanged-equality]

**Decision.** `entity.SetIfChanged(value)`, `Mut<T>.SetIfChanged(value)` and the generated `SetXIfChanged(…)` compare
with `IEquatable<T>` when the component implements it (record structs do), else the bytes of an unmanaged component; a
managed component without `IEquatable<T>` throws `NotSupportedException`. The generator writes `SetXIfChanged` only
for components it can compare that are tracked, indexed or grouped, and not tags.

**Why.**
- **No boxing.** `IEquatable<T>` is devirtualized for a struct; the type tests are JIT-time constants.
- **Bytes are safe in one direction.** Equal bytes are equal values; values equal under other rules (`-0.0` and
  `0.0`) count as a change: one stamp too many, never one missed.
- **Only where it means something.** For an untracked, unindexed component, skipping an equal write saves nothing.

**Considered.**
- **`EqualityComparer<T>.Default` for every struct:** `ValueType.Equals` boxes and reflects for a struct without
  `IEquatable<T>`.
- **Bytes for every type:** wrong for references and for types with their own equality.
- **Requiring `IEquatable<T>`:** plain unmanaged structs could not use it.

## D48. Parallel writers of tracked components cut chunks at 4,096 rows [#d48-parallel-tracked-chunks]

**Decision.** A parallel `[ForEach]` (or `ForEachParallel` job) that writes a tracked component cuts its chunks at
multiples of 4,096 rows, 4,096 at least, each chunk ending on a multiple of its size in the table (also in a slice,
which may start at any 64-row word); other parallel passes keep 64-row-aligned chunks of 1,024 rows or more.

**Why.**
- **The block summary is shared.** Each 4,096-row block of a tracked column has one change-tick summary, updated with
  a plain read-modify-write. Two chunks inside one block could race on it and lose a raise, so a `[Changed<T>]`
  reader could skip rows that were written. Aligned chunks give each block one writer.
- **Fewer chunks for small tables is the price.** A table needs more rows before it is split across threads.
- **Measured** (`ParallelForEachBenchmark`, 100,000 entities, 0 B): passes that write no tracked component keep
  their chunks, and their times match 4.6 within noise (623–666 µs in parallel, 742–783 µs before).

**Considered.**
- **Atomic updates of the summaries:** an interlocked operation on every write of every pass, parallel or not.
- **Per-chunk summaries merged after the pass:** memory per chunk and a merge on every parallel pass.

## D49. `ChangedAny`: one OR set per kind, one tick per filter [#d49-changedany-semantics]

**Decision.** `QueryFilter.ChangedAny<T1..Tn>(since)` selects rows where at least one of its components was written
at or after `since`; a row qualifies through a component it has. Every `ChangedAny` call of a filter joins one set,
every `RemovedAny` call another, and the sets combine with each other and with the other filters by AND. A filter
has one tick, which `Since` moves for all its change filters. A table none of whose columns was stamped since
the tick is skipped whole, and words and blocks no column wrote.

**Why.**
- **Replication sends a unit when any of its parts changed.** Several `[Changed<T>]` filters mean all of them; a
  second query per component would visit a row twice and need a deduplication.
- **One tick is enough.** The filter is kept once per purpose and run with each client's acknowledged tick.
- **The sets live outside the filter.** A filter holds one interned id of its pair of sets (4 bytes, 0 without
  sets), found once per new pair and allocation-free after: filters without sets, the common case, keep their
  size, and table checks test one flag of the row plan before any set work.
- **One set per kind is enough.** Several independent OR sets would need a list per filter for a case no request
  needed.
- **Measured** (`ChangeTrackingBenchmark`, `CountBenchmark`, `SparseBenchmark`, against 4.6): filters without a
  set cost what they did, every case within 7% either way, the run-to-run noise of these measurements.

**Considered.**
- **Several independent OR sets:** more state per filter, no use found.
- **A tick per component:** a filter per client per component, where the client has one acknowledgement.
- **Running one query per component and merging:** rows visited twice.

## D50. A restart save leaves types out; a restart load keeps singletons [#d50-restart-saves]

**Decision.** `world.SaveWithout(output, in exclude)` writes the whole world without the components and singletons of a
`ComponentSet`; `world.LoadKeeping(input, in keep, markWritten)` keeps the singletons of `keep` exactly as the world has them
(the save's values are skipped). A `ComponentSet` holds singletons as a second mask (`WithSingleton<T>()`;
`With(Type)` takes either kind). `SaveEntitiesWith` refuses a set that names a singleton; `LoadKeeping` refuses a `keep` that names
a component.

**Why.**
- **A restart carries the state, not the runtime around it.** Connections, caches and the old version's configuration
  must not come back, and often have no formatter.
- **The new process sets its configuration first.** Loading the old world over it would bring the old configuration
  back; keeping the singleton is one set, built once.
- **Each set says what its call can do.** A save of entities writes no singletons and a load replaces every entity, so a set
  naming what the call cannot honour is refused instead of ignored.
- **Measured** (`SnapshotBenchmark`, `SaveWithout` against `Save`, `LoadKeeping` against `Load`, 100,000 entities over two
  runs): a save that leaves a component and the singleton out takes 225–250 µs against 232–235 µs for the whole
  world, and a load that keeps the singleton 906–934 µs against 954–969 µs. Choosing what to leave out costs nothing
  measurable.

**Considered.**
- **A separate `SingletonSet` type:** two sets to build for one restart.
- **Kept components meaning "not loaded":** the load replaces the entities, so a kept component would belong to none.
- **Ignoring singletons in `SaveEntitiesWith`:** a set that silently does less than it says.

## D51. Not added: run conditions, time-based intervals, required components, an entity map, a meter, a checksum, partial snapshots [#d51-not-added]

**Decision.** Seven requests were weighed for 4.7 and left out.

**Why.**
- **Run conditions** (`[RunIf]`, a predicate per system). System groups give each cadence its `Update<TGroup>()`, and
  the host decides when a group runs; inside a system, `Enabled` and an early return in an `[OnUpdate]` method cover the rest. A
  predicate per system would be code the scheduler cannot see.
- **`UpdatePeriod` / a system time** (intervals in seconds). The host's fixed-step loop owns time; `UpdateInterval`
  counts updates, which keeps runs deterministic, and a clock singleton gives systems the time.
- **`[Requires<B>]`** (adding B whenever A is added). A prefab per kind of entity gives the full set in one copy;
  hidden additions would be structural changes no reader of the code sees.
- **An entity map** (an external key to an entity). `IUniqueIndexed<TKey>` is that map, kept by every write.
- **A built-in `Meter`.** `SystemStats` holds the numbers; publishing them to OpenTelemetry is a few lines of the host's
  own ([diagnostics](/en/docs/guide/diagnostics)), and EasyEcs stays free of a metrics dependency.
- **A world checksum** (for lockstep desync checks). A hash of `world.Save` output does it in user code; a built-in
  one would fix an algorithm and an order for every user.
- **A partial-snapshot API** (capture some components only). A system that copies the needed values into a ring held
  by a singleton (the lag-compensation pattern of [snapshots](/en/docs/guide/snapshots)) copies exactly what is
  needed, with no new storage path.

## D52. An `Entity` used only as an identity does not make a system run alone [#d52-identity-entity]

**Decision.** A `[ForEach]` method whose `Entity` parameter is used only for `Id`, `Version`, `IsAlive`, `==` / `!=`
or converted to an `EntityId` adds nothing to its system's access; any other use (`Has`, `Get`, another call, passing
the handle on) keeps the system running alone.

**Why.**
- **An identity reaches no component.** The id and version are in the handle; `IsAlive` reads the entity's record,
  which no system of a parallel stage changes (structural changes run alone).
- **Keying by entity is common** (a per-entity map, a log, a reply to a sender), and those systems lost their stage
  for a handle they only named.
- **Syntax first, conservative.** The check reads the method's body: a use it cannot prove harmless keeps the old rule.

**Considered.**
- **Treating `Has<T>` as a read of `T`:** presence bits change only through structural changes, but `Get<T>` writes
  and a generic `T` of another component is not known per call; one rule for reads of components stays the parameters.

## D53. EasyEcs's own components get their members in EasyEcs; shared names go to neither type [#d53-own-members]

**Decision.** `ComponentGenerator` also runs for EasyEcs's public components inside EasyEcs itself: `ChildOf` gets
the members of an indexed component without `DisableChildOf` / `EnableChildOf` (it cannot be disabled), and the
`Retired` tag gets `entity.IsRetired` only (the world adds and removes it). A member name two structs of one
namespace would both get (the tag `Dead` and the component `IsDead`: `entity.IsDead`) is generated for neither; a
nested component or buffer element named like another struct of its namespace gets no members at all. Generated
classes are named `{Type}` + a suffix that begins with `Ecs` (`HealthEcsExtensions`, `HealthEcsPrefabExtensions`,
`LootEcsBufferExtensions`, `LootEcsPrefabBufferExtensions`), and their members are public in a class as visible as
the type.

**Why.**
- **One generator, one shape of members.** Users read `entity.ChildOf` as they read `entity.Health`; the members ship
  in the package and no referencing assembly generates a file for them.
- **What the world refuses is not offered:** a `DisableChildOf` that always throws would be an API that only fails.
- **A namesake rule must cover every name.** Two types emitting any member of the same name make every call of it
  ambiguous, so the nested one gives up all of them, on the entity, the world, the filter and the prefab. Any struct
  counts, since any struct can be a buffer's element.
- **A shared name has no owner.** Between two types with different names (`Shield`'s `IsShieldDisabled` and the tag
  `ShieldDisabled`'s), neither is the obvious one to keep it, and which type a reader means cannot be guessed. Each
  computes the other's names from the namespace alone and drops the shared ones, so both decide alike without
  seeing each other's output, and keep their other members.
- **No suffix ends another.** With `PrefabExtensions` and `BufferExtensions`, `Loot`'s prefab buffer class and
  `LootPrefab`'s buffer class were both `LootPrefabBufferExtensions`. One `Ecs` marker at the start of every suffix
  makes the type's name end where the marker begins.
- **Public members, visible class.** C# rejects an internal extension property from an assembly that sees the
  internals (`InternalsVisibleTo`); public members of an internal class reach exactly the same code.

**Considered.**
- **Hand-written members for `ChildOf`:** a second implementation that drifts from the generated ones.
- **Generating them in each referencing assembly:** a file per assembly and duplicates between assemblies that see
  each other.

## D54. A call's name says what it does [#d54-names]

**Decision.** 4.7 renames four calls of 4.6 and one generated member: `EnsureCapacity<T1..Tn>(count)` /
`EnsureCapacity(prefab, count)` are `Reserve`, `DestroyEntities<T1..Tn>(filter)` is `DestroyAll`,
`SaveEntities(output, ids, set)` is `SaveEntitiesWith`, and a relation's generated `RemoveX(target)` is
`UnlinkX(target)`. `DestroyEntities(ids)` destroys a list of ids. The restart calls new in 4.7 were overloads of
`Save` and `Load` before the release and ship as `SaveWithout` and `LoadKeeping`. No alias is kept.

**Why.**
- **An overload that changes the meaning hides it.** `Save(output, set)` read like "save these", and it left them out;
  `Load(input, set)` kept singletons. A different name makes the call site say it.
- **`count` is more entities, not a capacity.** `EnsureCapacity` read like `List<T>.EnsureCapacity(total)`; `Reserve`
  takes how many more will be created.
- **`DestroyEntities` named two calls.** Ids and a filter now each have their name, and `DestroyAll` matches `SetAll`,
  `RemoveAll`, `DisableAll`.
- **`RemoveX(target)` and `RemoveX()` did different things.** One unlinks a target, the other drops the whole buffer.
- **Pre-1.0 rule, applied to a minor version:** the compiler finds every call, and the
  [migration guide](/en/docs/migration#v4-7-renames) maps each name.

**Considered.**
- **`[Obsolete]` aliases for a release:** two names for one call in completion lists and docs, for a change the
  compiler already points at.

## D55. `Read` walks a query without stamping; EECS046 points at loops that should [#d55-read]

**Decision.** `world.Read<T1..Tn>(filter)` walks the rows of a query with `ref readonly` components and stamps
nothing; `Query` keeps stamping the tracked components it hands out. The analyzer rule EECS046 (warning, code fix)
reports a `Query` loop of a tracked component that uses its items only for reads.

**Why.**
- **A `ref` cannot tell a read from a write.** A `Query` item hands out `ref T`, so it stamps every visited row of a
  tracked component; a total, a status page or a replication send then made every `[Changed<T>]` reader visit every
  row.
- **A second item type, generated.** `ReadItem` / `ReadEnumerator` come from the same `ArityGenerator` template as
  `QueryItem`, without the stamping lines; generated members (`item.Health`) are `ref readonly` on them.
- **The rule is what makes it used.** The 17 read-only `Query` loops it found in this repository (tests, the AOT
  check, a sample) all became `Read`.
- **Measured** (`ChangeTrackingReadBenchmark`, 100,000 entities, 10 written per tick, a read of every health and the
  `[Changed<Health>]` replication): 538 µs per tick with `Query`, 145 µs with `Read`, 0 B both.

**Considered.**
- **A `readonly` flag on `Query`:** the item type would still hand out `ref T`, so a write would compile and not be
  stamped.
- **Stamping on first write only:** a `ref` gives no hook for a write; `Mut<T>` is that hook in `[ForEach]` methods.

## D56. Not added: a generated `AddSystems()`, cached filters from attributes, counting members, a named `TryGetXRef` [#d56-not-added]

**Decision.** Four generator features were weighed and left out.

**Why.**
- **A generated `world.AddSystems()`.** Systems run in registration order, so the list is the tick's order; read
  where the world is built, it is the schedule's documentation. A generated list would fix an order by file or name.
- **Cached filters from attributes** (a `QueryFilter` field generated from `[With<T>]` on a field). A
  `static readonly QueryFilter` is one line already, and a generated one hides where it is built.
- **Counting members per component** (`world.CountPlayer()`). `world.Count<Player>()` says the same in as many
  characters; one more member per component grows completion lists without saving a line.
- **A named `TryGetXRef`.** `entity.TryGetRef<T>(out found)` is the rare call; the named members cover the common
  ones (`TryGetX`, `entity.X`).

## D57. A retired entity is treated as gone [#d57-retired-is-gone]

**Decision.** `Destroy` on an entity that holds cleanup components retires it: it stays alive, tagged `Retired`,
until they go. Every call that is not its release treats it as gone: `SetAll` leaves it out unless the filter names
`Retired`, `MoveEntities` skips it, `Clone` throws, and losing its other components is no removal (their change ticks
are cleared, not stamped). A moved entity's cleanup components stay behind on the retired original. `RemoveAll` still
reaches retired entities. "Destroyed" in names and docs means gone only: the destroy log records an id when it is
freed, which for a retired entity is when its last cleanup component goes.

**Why.**
- **One release per resource.** A cleanup component stands for something outside the world (a socket, a seat). A
  copy of it, by a move or a clone, would be released twice; a retired entity moved away would exist twice.
- **The same answer as a freed entity.** A destroyed entity has no row: no filter finds it, the destroy log reports
  it. Retiring keeps the row only for the release, so `[Removed<T>]` readers and bulk writes must not see more of it
  than of a freed entity.
- **`RemoveAll` is a release.** A retired entity holds cleanup components and `Retired` only, so `RemoveAll` of
  anything else never meets it, and `RemoveAll` of a cleanup component is how a cleanup pass frees it.
  `DisableAll` and `EnableAll` cannot meet one either: cleanup components cannot be disabled.
- **Cheap.** `SetAll` adds `Without<Retired>` to its filter: a table without the tag's column tests nothing more
  per row. `BulkBenchmark.StunAndLift` (`SetAll` + `RemoveAll` over 100,000 entities) measured the same before and
  after, within the noise of the run, 0 B both.

**Considered.**
- **A per-row test in the bulk walk:** a branch per row for every table, where the excluded bit costs nothing in the
  tables that never held a cleanup component.
- **Leaving it to filters (`Without<Retired>` by hand):** the default call then revived retired entities.

## D58. `AddSingleton` refuses an existing singleton [#d58-add-singleton]

**Decision.** `AddSingleton<T>()` throws `InvalidOperationException` when the world has `T`; a reset is a write
(`world.SetX(…)`, `world.X = default`), and `GetOrAddX()` takes it as it is.

**Why.** A second add was a setup run twice or an add after a `Load` that brought the singleton, and the silent reset
lost its value. The name says "add": the call now does that or says why it cannot. Writes keep the storage, so
`SingletonRef<T>` handles still reach the singleton after a reset.

**Considered.** **Keeping the reset and documenting it:** the bug it hides shows only as a value gone wrong later.

## D59. Rules for refs across changes, filters that cannot work and creations moved twice [#d59-analyzer-rules]

**Decision.** Six analyzer rules join the usage and performance rules, and EECS042 reports only the changes that add
to an index.

| Rule | Severity | Why this severity |
| --- | --- | --- |
| EECS047 a ref used after a structural change | Warning | The ref can still be right (the change moved another table's rows), so the rule reports only what it can follow: one block, in order, with no branch, loop or lambda between the ref, the change and the use |
| EECS048 `Disable` of a cleanup component or `ChildOf` | Error | `Disable<T>()` and `DisableAll<T>()` throw `InvalidOperationException` for them |
| EECS049 filters no entity passes | Error | A component required (a parameter, `[With<T>]`, `[Changed<T>]`, the group's `[With<T>]` or `ISystemGroupWith<T>`) and excluded (`[Without<T>]`, `IGroupWithout<T>`): the method never runs |
| EECS050 a second group in one filter | Error | `InGroup` throws `ArgumentException` for another group, of another component or another constant value |
| EECS051 a world update during a pass | Error | Every system runs while the loop walks the tables, and the update closes the pass's holes, moving rows the loop has not reached behind it, so it misses them |
| EECS052 a `Set` right after a creation | Warning, code fix | `AccessBenchmark.CreateThenSet`: 1,000 creations of one component then a `Set` of another, and their destroy, 44.4 µs; the same creations with both components 25.8 µs (1.73x), 0 B both |

`AccessBenchmark` ran on the machine of [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)
(BenchmarkDotNet, a shared 4-core Xeon at 2.1 GHz, .NET 10.0.13).

**Why.**
- **Each rule names code the runtime refuses or a cost it measured.** EECS048, EECS050 and EECS051 are calls that
  throw or corrupt the world's state at run time; EECS049 is a method that compiles and never runs. They are errors
  like EECS040 to EECS045. EECS047 and EECS052 are warnings: the code works in some worlds, or works and costs.
- **EECS048 has its own id.** EECS045 is about the world's own tags written by hand; here the call is the world's,
  and the component is what it refuses. The fix differs too (remove the component).
- **EECS047 keeps to straight-line code.** Whether a change moves the row a ref points into depends on the tables at
  run time; across branches and loops the rule would report code whose change and use never run together. It skips
  the calls that move no row: `Remove` and `Enable` (a presence bit), a `Set` of the component the ref holds (written
  in place), the members that copy or schedule (`Capture`, `Save`, `AddSystem`, ...), and the destroy of a query
  item's entity (a tombstone during the pass).
- **EECS042 reports additions.** An index walk steps past holes: removing the component, dropping links and
  destroying entities during a walk are allowed, and the hierarchy's own cascade removes links during a relation
  walk. What breaks a walk is a key that grows: a list emptied earlier is handed to the next key that grows, and that
  can be the list being read. A change followed by `break`, `return` or `throw` ends the walk before it reads another
  list, so it is not reported either. Relation walks (`Find(target)`) and `Descendants` are covered like `Find(key)`.
- **EECS052 is a cost, unlike two `Set` calls.** Two components added one call at a time cost about what one call
  costs (D29, dropped); a creation followed by a `Set` places the row twice, and the first table may exist only for
  that moment. The fix moves the value into the creation when it can bind it: not for a value computed by a call or
  from the entity, a grouped component, the world's own tags, or a creation with nine components already.

**Considered.**
- **A filter built inline at every call** (`world.Count<T>(QueryFilter.Create().With<U>())`): a filter is a small
  struct with no references ([D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)), and building
  one was not measured as a cost (D29). No rule.
- **EECS047 with flow analysis** across branches and loops: more reports, each one less certain, for a warning that
  fails builds that treat warnings as errors. Dropped.
- **Folding EECS048 into EECS045**: one id for two different causes and fixes. Dropped.

## D60. One diagnostic per mistake [#d60-one-diagnostic-per-mistake]

**Decision.** Where two analyzer rules report the same code, one defers to the other: the rule whose fix removes the
other's case. No rule was merged or removed, and the ids stay as they are.

| Code | Reported | Deferring | Why that one |
| --- | --- | --- | --- |
| `var t = e.Get<T>(); t.V = 1;` (a copy changed and dropped) | EECS038 | EECS025, EECS015 | Keeping the ref (or `Set`) is the fix; `Read` would keep the lost write |
| `[ForEach, Without<P>] static void A(ref P p, ...)` | EECS049 (EECS016 for `[Removed<T>]`) | EECS025, EECS026, EECS015 on `p` | The method never runs; what its parameter costs is moot |
| `[ForEach(Parallel = true)] static void A(..., ref Clock c)` | EECS010 | EECS025 | Its message already says "take it as `in`" |
| A query loop that counts, or that changes each entity the same way | EECS032, EECS030 | EECS046 | The fix removes the loop, so there is nothing left to read |
| `w.TrimExcess()` in a `[ForEach]` method or a job | EECS041, EECS013 | EECS028 | The call throws there; its allocation never happens |
| `item.Entity.Remove<Retired>()` in a query loop | EECS045 | EECS030 | `RemoveAll<Retired>` would be the same mistake |
| `e.Get<Q>()` on every row of a `[ForEach]` method or job | EECS027 | EECS033 | The fix takes the lookup away |
| `var e = w.CreateEntity(a); e.Set(b);` | EECS052 | EECS033 | The fix folds the `Set` into the creation |
| `[ForEach] static void A(DynamicBuffer<T> items, ...)` | EECS002 | EECS012 | Same fixes (`in` / `ref`); EECS002 is the error |

**Why.**
- **Two diagnostics for one mistake read as two problems**, and two fixes can undo each other (`Read` for EECS025,
  `ref var` for EECS038). Deferring keeps every rule's own cases: a rule stays quiet only on code another rule
  reports, which `GeneratorTests.OneMistakeIsReportedOnce` pins.
- **One source of truth for what a method requires.** EECS016, EECS049, the parameter costs and the system generator
  read the same list (`Symbols.Requirements`: method filters, queried parameters, the group's filters), and the
  helpers the analyzer files and generators each had their own copy of (`IsStable`, `SystemOf`, `JobInterface`,
  `IsDisableable`, `IsWorldTag`, `AlwaysRuns`, ...) live in `Symbols`.

**Considered.**
- **Merging EECS016 into EECS049** (both are filters no entity passes): EECS016 has its own wording and cause
  (`[Removed<T>]` visits entities that lost T), and ids are stable. Kept apart, read from one list.
- **Kept as two diagnostics:** a component's buffer field that holds entities (EECS012 copies a buffer, EECS017 stores
  an `Entity`: two mistakes, two fixes), EECS017 at each place a `DynamicBuffer<Pair>` is named, EECS026 next to
  EECS034, and EECS046 next to EECS032's presence test or EECS033 on another expression (the fixes compose).

## D61. One guard for the calls that wait for a pass; a group prefab is not one [#d61-one-pass-guard]

**Decision.** The calls that cannot run while a pass iterates the world (`Capture`, `Restore`, the saves and loads,
`MoveEntities`, `GroupBy`, `RemoveTypes`, `TrimExcess`) go through one check, `ThrowIfIterating(call)`, whose message
names the refused call. Instantiating a prefab with members is not one of them: it appends rows like
`CreateEntities`, so a system may do it during its pass. `LoadEntities` and `LoadEntitiesInto` keep their refusal.

**Why.**
- **A refusal says what was refused.** One shared message about snapshots came out of `Save`, `Load`, `MoveEntities`
  and `GroupBy`, and `RemoveTypes` and `TrimExcess` each had a wording of their own. The name is a constant passed to
  the check; the message is built only by a `NoInlining` throw helper, so the calls that pass allocate nothing.
- **The refusal belongs to the calls that need it.** It sat in the shared row copy of arrivals, so a group prefab,
  which only appends new rows (each placement bumps `StorageVersion`, moves during a pass leave tombstones), was refused
  where a prefab without members worked. It now sits in the public calls that read or rewrite whole tables.
- **One core per job.** The same audit replaced the copies of "the index of this component bit, if any" with
  `IndexOf(bit)` (as `GroupingOf(bit)` is for groups), the two loops that give components back to rows (`Set` of
  several components, `Instantiate` with components) with `GiveBack`, a private `Restore` overload (a second meaning
  of the snapshot call) with that name, and the box checks of `GetSingleton` and `SingletonRef` with one helper.
- **Measured** (BenchmarkDotNet, the branch against its base, interleaved runs of three launches): `RemoveMany` (the
  `GiveBack` path) 45.8–46.8 µs against 45.2–47.8 µs; `ToggleComponent` 149–158 µs against 148–150 µs;
  `RekeyAndLookup` 24.0–25.3 µs against 25.6–31.5 µs, `RekeyAndLookupUnique` 26.7–29.9 µs against 26.6–29.4 µs (the
  `IndexOf` path); `Churn`, `DestroyLog`, `Bulk` and `Relation` within each other's error. Nothing allocates.

**Considered.**
- **Letting `LoadEntities` and `LoadEntitiesInto` run during a pass** (their arrival is the group prefab's): a load
  reads network or storage input, which a host handles between updates; widening the contract is a separate change.
- **Dropping `Capture()` for `Capture(WorldSnapshot into = null)`**: one overload fewer, but a binary break and every
  cref rewritten for no gain. Kept.
- **One writer for whole columns and for a group's rows** (`WriteColumn` / `WriteRows`): a whole table is one block
  copy per column, a group a copy per row. Kept apart.
- **One target rule class for components and relations**: their `Apply` differ (remove a component, drop a link);
  the shared part is two one-line members. Kept.

## D62. Generators bind type names outside member bodies and compare symbols without strings [#d62-generators-bind-outside-bodies]

**Decision.** The generators' transforms bind a type name they found in a member body (`DynamicBuffer<T>`, a closed
generic system, the components of `Query<…>` / `Read<…>`) alone, speculatively at the open brace of the enclosing type
(`Symbols.TypeNamed`), not with `GetSymbolInfo` where it stands. Every symbol test in the generators and the analyzer
is `Symbols.Named(symbol, "Ns.Type<T>")`, which walks the symbol's names, instead of `ToDisplayString() == …`. The C#
version check reads the parse options and the module initializer's check the assembly name, not the compilation.

**Why.**
- **A keystroke re-runs every transform.** A new compilation re-runs the semantic transform of every candidate node,
  in every file. Binding a node inside a body binds the whole body and runs its nullable analysis first; a speculative
  binding at a position in the body does too. At the type's brace a name sees the same usings, namespaces and type
  parameters (a method's type parameters excepted, which no generated code can name).
- **Strings per candidate per edit.** `ToDisplayString` builds a string for every interface of every candidate, on
  every edit; the generators and the analyzer both ask it thousands of times per run. `Named` builds nothing.
- **Measured** (`GeneratorBenchmark`: the battle server and 40 modules of components, buffers, systems and query
  loops; the branch against its base back to back): an edit in a method body 228 ms / 26.9 MB against 149 ms /
  16.8 MB, an edit in another file 249 ms / 26.9 MB against 147 ms / 16.6 MB, a first run 271 ms / 67.8 MB against
  232 ms / 58.5 MB. The analyzer's share of a build (`CompileAndAnalyze` minus `Compile`) allocates 35 MB against 42
  MB, its time within the error.

**Considered.**
- **Fewer generated files** (one per namespace instead of one per type): the driver checks each new file against every
  cached one, but its time there was mostly the collector's; fewer allocations removed it. Not done.
- **Resolving a generated member's type from its class name in the analyzer** instead of walking the namespace: 523 ms /
  34.6 MB against 569 ms / 33.3 MB, within the error. Not done.
- **A shared receiver check for `Query` calls** in a body: needs the call bound. A `Query` or `Read` of several structs
  that are all components is taken as a World's; a name-alike call adds an unused item file, nothing else.

## D63. Newer Roslyn features: interceptors for lambda passes only, the rest in use or not needed [#d63-roslyn-features]

**Decision.** The generators use `ForAttributeWithMetadataName` (`[ForEach]`), implementation output for what user code
never names (system code, `TypeRegistry`), C# 14 extension members and generic attributes. Interceptors replace one
call only, a lambda pass ([D112](#d112-lambda-passes)), where the call's argument is a body to compile and not a value
to compute. No embedded attribute definitions.

**Why.**
- **Elsewhere interceptors have nothing to remove.** `entity.Get<T>()`, `Has<T>()`, `Set<T>()`, `CreateEntity(new A(), new B())`
  and `world.Index<T, TKey>()` read a static readonly field per type or signature (`ComponentType<T>.Bit`,
  `ComponentSignature<…>`), a constant once the JIT tiers up: an intercepted body would be the same code. Systems
  register through a module initializer, with no reflection to replace.
- **Query calls**: an interceptor cannot skip the call's arguments
  ([D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)). Intercepting every call of a constant
  filter chain, each returning the site's static filter, counts 16 entities in 25 ns against 76 ns for the filter built
  at the call (`CallSiteBenchmark`, hand-written as the generator would emit it), which is what a `static readonly`
  filter gives (24 ns) with no opt-in and nothing hidden.
- **Embedded attributes**: the attributes ship in EasyEcs.Core, which every project using the generator references.

**Considered.** Interceptors at each candidate above; `RegisterSourceOutput` for system code (an IDE would then build
it on every keystroke); post-initialization attribute sources.

## D64. The names of 4.7: a name says what the thing is [#d64-names-of-4-7]

**Decision.** A naming review before 4.7 renames, beyond [D54](#d54-names): `ITrackChanges` → `ITracked`,
`IGroupWith<T>` / `IGroupWithout<T>` → `ISystemGroupWith<T>` / `ISystemGroupWithout<T>`, the `Destroyed` tag →
`Retired` (`entity.IsRetired`), `GetSystem<T>()` → `TryGetSystem<T>(out …)`, `world.Describe()` → `DescribeTables()`,
`ColumnInfo.Without` → `Absent`, `SystemStats.Last` / `Total` / `Average` → `LastTime` / `TotalTime` / `AverageTime`,
`UpdateCount` → `DefaultUpdateCount`, `SystemAccess.RunsAlone()` → `RunAlone()`, `TargetRules` →
`TargetPolicyExtensions`, `AddRelation` / `RemoveRelation` / `HasRelation` → `Link` / `Unlink` / `Links` with the
generated `LinkX(target)`, a job's `Writes` / `OwnStamps` → `WriteMask` / `SelfStamped`, and the parameters
`LoadEntitiesInto(input, targets)` and `QueryFilter.Slice(index, of)`. Names new in 4.7 ship renamed:
`WorldOptions.DestroyLogCapacity`, `GroupInfo`. No alias is kept; saves of 4.6 still load.

**Why.**
- **One word, one meaning.** "Group" named both a system group and an `IGroup` component; "Without" both a filter and
  a count; "Destroyed" both a freed entity and one kept alive for its cleanup components
  ([D57](#d57-retired-is-gone)). Each now has its own word, and "destroyed" means gone.
- **The signature tells the miss.** `GetSystem<T>()` returned null for a system the world does not have.
  `TryGetSystem` says so. The throwing `System<T>()` came with the system handles of 4.8
  ([D102](#d102-systems-are-ref-structs)), for code that knows the system was added.
- **A link is not a component added.** `AddX(target)` read like `SetX`; `LinkX` / `UnlinkX` / `LinksX` and the
  generic `Link` / `Unlink` / `Links` are one family. The generic names are short at a cost: a component named `Link`,
  `Unlink` or `Links` gets no `entity.X` property (the generator skips a name the entity already has), the other
  members stay.
- **Units and kinds in the name.** A `TimeSpan` stat ends in `Time` next to counts and bytes; a capacity is a
  `Capacity`; a bit mask is a `Mask`; an instruction (`RunAlone()`) is a verb and a fact (`SystemInfo.RunsAlone`) is not.
- **Saves keep loading.** A save names each type by a hash of its full name; `Retired` carries
  `[NinoFormerName("EasyEcs.Destroyed")]`, so it keeps the old id and a 4.6 save with retired entities loads them
  retired (tested with the bytes of a 4.6 save).
- **Pre-1.0 rule:** the compiler finds every use, and the [migration guide](/en/docs/migration#v4-7-renames) maps each
  name.

**Considered.**
- **`[Obsolete]` aliases for a release:** as in D54, two names in completion lists for a change the compiler points at.
- **Only named members for relations (no generic `Link<T>`):** generic code over relation types (`Link<T>(in T)`)
  would then have no entry point.
- **A new save id for `Retired`:** every save holding a retired entity would fail to load.
- **Renaming `entity.Describe()` and `DescribeSchedule()` too:** each already says what it describes.

## D65. The buffer pool's limit is a setting of each element type [#d65-buffer-pool-capacity]

**Decision.** `DynamicBuffer<T>.MaxPooledLength` sets the longest list, in elements, that a destroyed or removed buffer of
`T` gives back to its thread's pool. It is a static of the element type, process-wide, defaulting to 4,096 bytes of
elements; 0 pools none.

**Why.**
- **The pool belongs to the element type.** Freed lists go to a thread-static pool per `T`, shared by every world on
  that thread, so the limit lives where the pool does.
- **One size does not fit all.** 4 KB keeps small inventories and paths pooled without holding big lists. Buffers that
  come and go at one large size, such as the blocks of chunks loaded and unloaded around players, missed the pool
  and allocated each time. Raising the limit for that one type makes the churn free (`ChunkChurnBenchmark` in
  `EasyEcs.Benchmark`, pooled against unpooled).
- **What it keeps is bounded.** The pool holds at most as many lists as died while none were taken, so its memory is
  that peak times the capacity, for the types that raised it only.

**Considered.**
- **A `WorldOptions` setting:** the pool is shared by the worlds of a thread, so a per-world value would not say which
  world's limit applies.
- **One byte limit for every type:** raising it for chunks would also keep large lists of every other element type.
- **A larger default:** it would keep big lists for the types that do not need them; the default stays 4 KB.

## D66. A tracked component written by `ref` on some rows is a warning [#d66-a-ref-written-on-some-rows]

**Decision.** EECS053 reports a `ref` parameter of a tracked component (`ITracked`, `DynamicBuffer<T>`) in a
per-entity `[ForEach]` method when a path through the method reaches its end or a `return` without writing it, and
its fix turns the parameter into a `Mut<T>` (writes `x.Write()`, reads `x.Value`). A `ref` that every path writes stays
unreported ([D46](#d46-mut-stamps-per-write)); batch methods are left out.

**Why.**
- **The stamps are wrong, not only costly.** A row the method returned past is stamped as written, so every
  `[Changed<T>]` reader treats it as a change: our own samples sent every player's position to every client each
  tick, because the respawn system returned early for the living. `Mut<T>` keeps the stamps true.
- **The shape of the code says it, not the data.** D46 left `ref` alone because only the data tells whether most rows
  change. A path that does not write is visible in the method: the rows that take it are never changed by it.
- **Measured** (`ChangeTrackingSomeRowsBenchmark`, 100,000 players, 100 respawning per tick, then the
  `[Changed<Position>]` replication): 162 µs through `ref` and 133 µs through `Mut<T>`, the replication dropping from
  about 90 µs to about 7 µs; the respawn alone takes 72 µs through `ref` and 126 µs through `Mut<T>`, so a component
  nothing reads by change is cheaper by `ref`, which the rule's page says (suppress it there). 0 B both. Same machine as
  [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same).
- **The detection is the control flow graph, kept conservative.** Roslyn's graph of the method, walked from the entry:
  a block holding a write stops the walk (a block runs whole), a branch that throws is not followed, a constant
  condition takes its one branch (`while (true)`), and reaching the exit means a path without a write. Anything
  `Uses.MayWrite` cannot prove a read counts as a write, and a method that writes the parameter in a `finally` is left
  out (the walk does not follow a finally on the way out).

**Considered.**
- **Only straight-line patterns** (an early `return`, one `if`): misses `switch`, `else if` chains and loops that may
  not run, for no saving; the graph costs one walk of the method's blocks.
- **Batch methods:** a span stamps a whole run of rows, and there is no per-row `Mut<T>` for spans; a run written on
  some rows needs a different design. Left out.
- **`SetIfChanged` in the fix:** it compares, which a write that already knows it changes does not need, and it throws
  for a managed component without `IEquatable<T>`. The fix keeps the method's writes as writes.

## D67. Chunk size for few heavy rows [#d67-chunk-rows]

**Decision.** `[ForEach(Parallel = true, ChunkSize = n)]` (and `chunkSize:` on the parallel calls) sets the rows a
thread claims at a time, rounded up to 64; without it the runtime keeps choosing (about four chunks per thread, at
least 1,024 rows, 4,096 when the method writes a tracked component). Chunks of a stamping pass may split a 4,096-row
block of change ticks: before the pass, the blocks it covers are opened at its tick (`Rest` takes the previous latest,
`Latest` the pass's tick, `Words` none), and `BlockTicks.Raise` ORs a word into an open block atomically.

**Why.**
- **Few heavy rows ran on one thread.** The minimum chunk suits many light rows, where a claim costs more than a row.
  A few hundred rows of microseconds each (VoxelServer's flowing chunks) made one chunk: the other threads idled.
  The runner already claims chunks through a shared cursor, OpenMP's `schedule(dynamic, n)`; only `n` was fixed.
- **The 4,096 rows protected one read-modify-write.** Word summaries cover 64 rows, so chunks of multiples of 64 own
  their words; only the block summary (64 words) was shared, through a plain `Words |= words`. Opening the block
  first leaves every thread of the pass on the same-tick branch, where the OR can be atomic; readers keep their
  meaning (the words in `Words` are at `Latest`, the others at most `Rest`). An opened block the pass leaves alone
  only loses the precision of its previous `Words`: a reader since then visits all its words.
- **Atomic once per 64 rows.** `Raise` runs on a word's first stamp at a tick, not per row, so the lock prefix is
  paid once per 64 written rows, by every pass (one code path for the shared and the private case).
- **A test that catches the race.** `ChunksSplittingBlocksKeepChangeTicksExact` writes every row of 10,000 in chunks
  of 64, 1,000 times, and counts the `[Changed<T>]` rows after each pass: without opening the blocks it lost a word's
  rows (9,936 of 10,000) in some runs.

**Considered.**
- **A smaller default minimum:** light rows (the common case) would pay a claim per few rows; the default stays
  chosen from the row count, and heavy rows say so.
- **A lock-free transition inside `Raise`** (compare-and-swap of `Latest`, then the words): three fields cannot move
  together without a loop or a sentinel; opening the blocks before the pass needs neither.
- **Per-thread block summaries merged after the pass:** an array per thread and a merge per pass, for what one
  atomic OR per 64 rows already gives.
- **Guided scheduling** (chunks that shrink as the pass ends): the adaptive runner and `ChunkSize` cover the cases
  measured so far.

## D68. Vector loops without opting in [#d68-vector-loops-without-opting-in]

**Decision.** The generator writes a `Vector<T>` loop for every `[ForEach]` method that qualifies
([vector loops](/en/docs/guide/systems#vector-loops)): static, per entity, not parallel, no `Entity` / `World` /
`Mut<T>` / `Maybe<T>`, components of 1 to 4 fields of one primitive type (several fields split into one vector each
by deinterleaving loads and interleaving stores, `EasyEcs.Interleaved`), a body of arithmetic, comparisons, branches
and the `Math` functions with an exact vector counterpart. It is on by default (`SimdMode.Auto`): EECS055 names why a
method that looks meant for a loop stays scalar, `SimdMode = SimdMode.Require` makes that an error (EECS056) and
`SimdMode.Off` opts a method out. The rows after the last whole vector, and all rows without a vector unit (or,
for several fields, without the shuffles: AVX2 at 256 bits, permutes at 512), run the method itself.
Later steps took `Vector512` (where the hardware runs it, then `Vector<T>`),
`Reduce<T>` results (lane accumulators), masked words and the methods of [D90](#d90-vector-loops-reach).

**Why.**
- **The JIT does not do it.** In .NET 10 the Tier-1 code of `a[i] += b[i]`, `a[i] += b[i] * 0.5f`, a clamp, an int
  sum and `a[i]++` is scalar (`vaddss`, `vmulss`, compare and branch, `add`, `inc`): bounds checks go, loops are never
  vectorized. A per-row method stays one row per instruction unless something writes the vector loop.
- **The same results, so nothing to opt into.** Each lane runs the scalar code's IEEE operations in its order: no
  reassociation, no fused multiply-add the code did not write, `Vector.Min` / `Max` / `SquareRoot` / `Abs` equal to
  `Math`'s on NaN, ±0 and infinities, shifts masked as C# masks them. A unit test runs three kernels at 1, 7 and 1,003
  rows over two tables, with NaN, ±0, infinities and random ints, and compares the bits with the method called row by
  row. Change ticks and access sets are those of the per-row method. A switch would only let code be slower.
- **Measured** (`KernelBenchmark`, 100,000 rows, the per-row job against the generated loop): a clamp with a branch on
  random data 472 µs → 29.4 µs, `h += v * dt` 62.9 µs → 9.9 µs, an int increment 33.2 µs → 8.2 µs; 1,000 rows: 1,372 ns
  → 309 ns, 485 → 83 ns, 399 → 62 ns. Existing benchmarks whose methods qualify, unchanged: `AccessBenchmark`'s
  static method 38.7 → 8.0 µs, `SparseBenchmark.PassOverTheRest` 50.2 → 9.3 µs, `MaybeBenchmark.TwoMethods` 35.9 →
  9.6 µs; `SparseBenchmark.PassOverTheFew` (10 scattered rows) 334 → 330 ns, so short runs pay nothing. 0 B
  everywhere. Same machine as [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same).
- **Columns already are what Burst needs.** Burst learns from `NativeArray` that arrays do not alias and walks
  contiguous per-component arrays; EasyEcs columns are contiguous, 64-byte aligned and never alias, which the
  generator knows statically. Translating a small source subset is enough; a compiler from IL is not needed.
- **Say why, as Burst's inspector does.** A method left scalar is correct, so silence would hide the cost. One test
  (`Kernel.Vectorize`) gives the loop or the reason: the generator emits what it returns and the analyzer reports
  the reason, so "no loop" and "reported" are the same set. A suggestion, not a warning: scalar code is not a
  mistake. `Require` is for the hot path whose speed a later edit must not lose without failing the build.
- **Several fields, because real components have them.** `Position { X, Y, Z }` is the common shape; asking for
  one component per axis would make every other system worse. A 256-bit deinterleave costs a few shuffles per
  vector, far less than running the rows one at a time. Past 4 fields, mixed types and partial structs stay scalar
  (EECS055 says so).

**Considered.**
- **Opt-in, as Burst's `[BurstCompile]`:** Burst needs it because it changes the compiler and allows `FloatMode.Fast`.
  Here nothing changes but speed, so an opt-in would leave most code slow for no safety. `SimdMode` keeps `Auto` as
  the default and adds only the assertion (`Require`) and the way out (`Off`).
- **Leaving it to batch methods with `Vector<T>`:** still there for lanes the rule does not cover, but it asks every
  user to write SIMD by hand; a per-row method says the same thing.

## D69. Reductions are a parameter, combined in chunk order [#d69-reductions]

**Decision.** A total over a pass is a `ref Reduce<T>` parameter of a `[ForEach]` method, where `T` is a singleton that
implements `IReduction<T>` for itself (a static `Identity` and an associative `Combine`)
([reductions](/en/docs/guide/threading#reductions)). Each chunk of a parallel pass, or the whole pass on one thread,
accumulates into its own copy starting at `Identity`; when the pass ends the world's runner combines the copies in chunk
order, which is row order, and the result replaces `T`. The system is scheduled as a writer of `T`. EECS057 rejects a
second write of `T` in the same pass.

**Why.**
- **A parallel method had no way to produce a total.** It may not write a singleton (EECS010), and the ways around
  it race (a static counter, EECS060) or lose the result (a job field after `ForEachParallel`, EECS061). Every server
  computes totals each tick: the units alive, a resource, a crowd's extent.
- **No lock and no atomic per row.** The partial result lives in the chunk's own copy of the job; nothing is shared
  until the end, when each copy is combined once. An `Interlocked` add per row makes every core write one cache line.
- **Deterministic.** Combining in chunk order (not in the order chunks finish) makes integer results exact and a float
  result the same on every run and any thread count (the chunks follow the row count, [D125](#d125-scheduler-tuning));
  `Combine` need not be commutative (a first and last value, a concatenation of bits).
- **One shape for both runners.** The same parameter works with `Parallel = false` (a local per run of rows) and in a
  `[ForEach]` method outside a system, so making a pass parallel changes one attribute, not the code.
- **0 bytes.** The runner keeps an array of job copies per job type, grown once; steady passes allocate nothing.
- **A plain struct taken by `ref`, so the partial result stays in a register.** A reducing method runs over each
  chunk's runs of rows (`World.ForEachBatchParallel` in parallel; the batch loop on one thread), with the run's
  partial result in a local. Passed by `ref` to the inlined method, the JIT keeps that local in a register (the
  chunk loop of a float sum is one `vaddss` per row). A `ref struct` holding a `ref` field to the local, the first
  shape, pinned it in memory: a load and a store per row, a float sum chained through store forwarding and several
  times slower than the serial pass. A `Reduce<T>` not taken by `ref` would reduce into a copy, so it is EECS002.

**Considered.** Measured with `ReduceBenchmark` (BenchmarkDotNet, 1,000,000 rows, two runs each, 4 cores at a
machine load of 10 to 30):

| Variant | Integer sum | Float sum | Allocated per call |
| --- | --- | --- | --- |
| Serial `ref` context value | 0.41 / 0.47 ms | 0.74 / 0.76 ms | 0 B |
| `ref Reduce<T>`, parallel | 0.37 / 0.46 ms | 0.74 / 0.77 ms | 0 B |
| `Reduce<T>` as a `ref struct` with a `ref` field (the first shape) | | 3.3 to 4.6 ms | 0 B |
| `Parallel.For` over the pass's chunks, partial results summed in order | about the same | about the same | 1.7 to 1.9 KB |
| `Parallel.For<TLocal>` per row, static delegates | 2.4 to 3.5 ms | 3.3 to 6.8 ms | 1.7 to 2.1 KB |
| `Interlocked` per row (a CAS loop for floats) | 8 to 13 ms | 15 to 24 ms | 0 B |
| A lock per row | 25 to 33 ms | | 0 B |

At 1,000 rows `Reduce<T>` takes about 0.45 µs, every `Parallel.For` variant 3.5 to 13 µs. Over 200 runs of the float
sum, `Reduce<T>` and the chunked `Parallel.For` each gave 1 distinct result; the per-row `Parallel.For<TLocal>` gave
up to 129, the CAS loop up to 137.

- **`Parallel.For<TLocal>` with `localInit` / `localFinally`:** .NET's thread-local reduction, and the closest existing
  tool; rejected. It never runs at 0 B, its per-row form is 5 to 9 times slower, its float results are not
  deterministic, and it has no overload that passes state, so a `static` lambda needs static state (the column, the
  result), which is not reentrant: two worlds cannot reduce at once. Over the pass's own chunks it keeps up in time
  and is deterministic, but it still allocates per call and still needs the static state.
- **An `Interlocked` add or a lock per row:** correct for integers, but every row contends for one line: 20 to 70
  times slower than `Reduce<T>` above, and a float CAS loop is not deterministic.
- **The partial result in the job's field, per row:** what a per-row parallel job would do; a field of the chunk's
  job copy is a load and a store on every row. Parallel reductions run as batch jobs
  (`World.ForEachBatchParallel`), the run's partial result in a local.
- **Slots per thread, indexed by thread id:** padded against false sharing, but the combination order would follow
  the threads, not the rows, and a thread count change would resize them.
- **Combining in the order chunks finish:** one fewer array, but float results and non-commutative combines would
  depend on timing.
- **A `ref struct` wrapping a `ref` to the partial result** (`Reduce<T>` by value): reads like `Maybe<T>`, but keeps
  the partial result in memory (above): 3.3 to 4.6 ms for the float sum.
- **Reductions inside a vector loop:** a later step ([D68](#d68-vector-loops-without-opting-in)); exact for integers,
  and for floats only with reassociation.

## D70. Analyzer candidates not added [#d70-analyzer-candidates-not-added]

**Decision.** The audit that added EECS060 and EECS061 and the code fixes of EECS027 and EECS054 weighed these rules
and fixes too, and left them out.

**Considered and dropped.**
- **`Parallel = true` on a method over few or light rows:** whether the hand-off pays depends on the row count and the
  work per row at run time, which the analyzer cannot see; the runner already runs a small pass on the caller
  (adaptive helper waking). The cost rule of [D29](#d29-performance-rules-only-where-the-cost-is-measured-and-the-fix-does-the-same)
  (only a measured cost) excludes it.
- **`ChunkSize` that is not a multiple of 64:** the runtime rounds it up to 64 for free
  ([D67](#d67-chunk-rows)), so the code works as written; a rule would only ask for the rounding by hand.
- **`Math` to `MathF` on floats:** for `Sqrt`, `Abs`, `Min` and `Max` both are exact, so nothing is gained; for the
  transcendental functions (`Sin`, `Exp`, `Pow`) `MathF` returns different, less precise results, so the fix would
  change behavior, which D29 forbids.
- **`Parallel.For` or `Task.Run` inside a system:** legitimate uses (a computation that touches no world state, I/O
  handed off and read back through a thread-safe queue) are common, so the rule would mostly report correct code; what
  is wrong in such code (a structural change from another thread) is EECS014's.
- **A code fix for EECS016 (drop `[With<T>]` or the parameter from a `[Removed<T>]` method):** the method left would
  take no component, which EECS003 rejects, so no single edit makes it compile; the right change (which component the
  method runs over) is the author's.

## D71. Unique keys inline, and direct-mapped keys [#d71-direct-index]

**Decision.** A unique index keeps each key's one entity inline in the key's head, with no id array per key. A unique
component whose keys map onto a bounded range of slots may declare `IDirectMapped<TKey>` (`static Slots`,
`static SlotOf(key)`): its index keeps an array of `Slots` entries beside the hash, each holding a key and its
entity, so `Get`, `TryGet` and the uniqueness check of a write read one entry. A key whose slot is out of range or
held by another key is found through the hash, which stays the index for `Find`, `Count` and the ordered walks. The
generator registers the slot map with the unique index (`TypeRegistry.DirectIndex`), with no reflection.

**Why.**
- **A unique key has one entity.** An array per key held one id and cost an allocation per new key; inline,
  `CreateUnique` (10,000 keys) went from 2,044 µs and 3.15 MB to about 1,120 µs and 2.33 MB, and
  `RekeyAndLookupUnique` from 34.4 µs to 14 to 21 µs (`IndexBenchmark`).
- **Grid lookups are the hot path of grid worlds.** The voxel server looks a chunk up by position for the blocks
  around every body, the chunk every entity is in and the edges of the water, thousands of times a tick. A slot read
  is about 2.1 times faster than the hash probe of a unique index and as fast as the hand-written grid it replaces
  (`LookupUnique`, `LookupDirect`, `LookupGrid` in `IndexBenchmark`); the voxel server's physics ran 5 to 11 %
  faster with it.
- **Kept by every write.** The slot array is updated where the hash is (link, unlink, clear), so creation, loads,
  moves, `SetAll` and destruction keep it right; a grid kept by hand has to be updated on each of those paths.
- **Correct for any slot function.** A collision or an out-of-range key costs a hash probe, never a wrong answer: a
  slot counts the keys of it that only the hash holds, so a lookup that finds another key there knows whether the
  hash must be asked.

**Considered.**
- **The hand-written grid beside the unique index** (what the voxel server had): the same lookup speed, but code
  every grid world repeats, and a grid that a missed write path leaves stale.
- **A slot array instead of the hash:** out-of-range keys would have nowhere to go, and `Find`, `Count` and the
  ordered walks are built on the hash.
- **Registration by reflection:** not trimmable and not Native AOT safe; the generator already registers every
  unique component.

## D72. `SetAll` fills whole words [#d72-setall-whole-words]

**Decision.** `SetAll` writes a 64-row word whose rows all match with one `Span.Fill` of the value. A partial word,
and a component an index watches (the index must see each row's write), keep the row-by-row loop.

**Why.** The other bulk calls already worked a word at a time; the value write was the one per-row loop left.
`BulkBenchmark` `StunAndLift` (100,000 entities) went from 92 and 100 µs to 30 and 30 µs over two runs, 0 B both.

**Considered.** Filling indexed components too: the index links each row to its key, so a fill would skip the
updates it needs.

## D73. Survey items not added [#d73-survey-items-not-added]

**Decision.** The survey that added `IDirectMapped<TKey>`, `CollectIds` and the whole-word `SetAll` measured these
changes to the voxel server and the core too, and left them out.

**Considered and dropped.**
- **A chunk grid beside the unique index:** superseded by `IDirectMapped<TKey>` ([D71](#d71-direct-index)), which
  reads as fast and is kept by every write.
- **Writing the voxel server's `InChunk` only when an entity's chunk changed:** the difference stayed within noise.
- **Copying presence bits a word at a time** instead of bit by bit: contradictory A/B runs (faster in one, slower in
  the next), so no net win was shown.
- **A water halo that copies only the edges that changed:** half the copies, but the step's time stayed within noise,
  and it cost 4 KB more per sleeping chunk to remember the edges. Superseded by the planned push-halo design, where a
  chunk hands its edges to its neighbors when they change ([roadmap](/en/docs/roadmap#push-halo)).

## D74. Per-thread scratch is a parameter [#d74-scratch]

**Decision.** A `Scratch<T>` parameter of a `[ForEach]` method is the method's working memory on the running thread:
one `T` per method and thread (a `[ThreadStatic]` box per generated job type), `default` until the method fills it,
never reset, released when the thread ends. It adds no access to the system. EECS058 rejects storing what it holds
by reference into a component, a singleton, a `Maybe`, a `Mut` or a `Reduce`; EECS028 does not report its one-time
`??= new()`.

**Why.**
- **A parallel method had nowhere to keep a list.** A `new` per row allocates (EECS028), a shared list races
  (EECS060), and a hand-written `[ThreadStatic]` field is code every such method repeats. OpenMP's `threadprivate`
  is the same idea.
- **0 B and faster than allocating.** `ScratchBenchmark` (24 candidates per row, 10,000 and 100,000 rows, 1 and 4
  threads, two rounds): 2.1 to 2.5 times faster than a new list per row, 0 B after each thread's first row.
- **A method that loops or calls runs out of line.** Profile-guided inlining took such a method into the row loop,
  where its own loop shared the callee-saved registers with the row loop's refs, its end and the scratch box, ran out
  of them and kept its counter and running value on the stack (8 stack references in the row loop of
  `ScratchBenchmark.Scratch`). Every shape of the parameter tried (`ref T`, a class box, a plain struct, a thread-static
  lookup per row) was inlined and spilled the same way. A `Scratch<T>` method whose body has a loop or a call is therefore
  called through its accessor marked `MethodImpl(NoInlining)`: the method inlines into the accessor, which the row loop
  calls once per row, as the JIT calls a hand-written `[ThreadStatic]` method it does not inline. The accessor keeps
  the profile: it is instrumented and tiered like any method, and the method inlined into it brings its own (a guarded
  devirtualization inside it was checked in the Tier1 code), so a separate non-inlined wrapper was tried and dropped as
  a member that changed nothing. A method without a loop or
  a call (a counter) stays inlined: a call would cost it 10 to 50 %. Since then `Scratch<T>` and the hand-written
  `[ThreadStatic]` list are within the noise of each other: 406–414 µs against 428–468 µs (10,000 rows) and
  4,042–4,710 µs against 4,411–4,536 µs (100,000 rows) at 1 thread, 1,694–1,746 µs against 1,645–1,928 µs (100,000
  rows) at 4.
- **Reset is the user's.** Clearing a list is one call the row makes when it needs it; a reset by the runner would be
  a call per row for every scratch, needed or not.

**Considered.**
- **A hand-written `[ThreadStatic]` list:** as fast (see above), and the field and its lazy creation are code every
  such method would repeat.
- **`ArrayPool<T>.Shared` per row:** a rent and a return per row, and only arrays.
- **`stackalloc`:** the fastest for a small bound known up front, and recommended for it; not for a size that varies
  or a buffer too big for the stack.
- **A scratch per world:** a world's parallel pass runs on threads no world owns, so it would still need one per
  thread, inside the world.

## D75. Lookups of other entities are a read-only parameter [#d75-lookup]

**Decision.** A `Lookup<T>` parameter of a `[ForEach]` method reads component `T` of any entity (`this[id]`,
`Read(id)`, `Has(id)`; for an indexed `T`, `TryFind`, `Find` and `Count` by key through `LookupExtensions`), as it was
before the pass. The system is scheduled as a reader of `T`, so writers of `T` land in another stage; EECS059 rejects
a method that writes `T` itself; EECS010 accepts it in a parallel method. A value index the method queries through the
parameter is created and built before the pass (on the owner thread, before the stage); any other index not built
yet throws inside a parallel region, and still builds lazily in a serial pass.

**Why.**
- **Reading another entity forced the method onto one thread.** The `World` parameter is rejected in parallel
  (EECS010). A read-only view whose contract the scheduler enforces (no writer of `T` in the stage, none in the
  method) keeps the reads race-free without a lock: Unity's `ComponentLookup` with `[ReadOnly]`, MPI's one-sided `Get`.
- **Faster on one thread too.** `LookupBenchmark`: a serial `Lookup<T>` was 10 to 28 % faster than a `World`
  parameter with `TryGetEntity` and `TryGet` (the chase at 10,000 and 100,000 rows, and the unique find). In
  parallel it added nothing measurable under that machine's load.
- **An index must not build itself on several threads.** Building it before the pass keeps every lookup during the
  pass a read; an index reached any other way throws instead of racing.

**Considered.**
- **A lookup that also writes (Unity's `ComponentLookup` without `[ReadOnly]`):** two rows could write one entity
  from two threads; writes to other entities stay data (a component of the row, read by a later system).
- **Building indexes lazily under a lock:** a lock on the first lookup of every pass, for an index that can be built
  before it.

## D76. Systems run in stages, not as a dependency graph [#d76-stages-not-a-dependency-graph]

**Decision.** A parallel update keeps its stages: a system starts when the whole stage before its own has finished,
not as soon as the systems it conflicts with have (TBB's flow graph, Unity's `JobHandle`, OpenMP's `depend`).

**Why.**
- **The barriers cost the measured worlds nothing.** With `MeasureSystems`, each system's time per tick (600 ticks,
  100,000 units or entities, 4 cores) gave the critical path of the stages (the slowest system of each stage, summed)
  and the critical path of the dependency graph built from the same orderings and read/write sets (every system
  starting once the earlier systems it conflicts with or follows finish, on unbounded threads and on 4).
  The idle time is real (the threads beside `PlanningSystem`, beside `MoveBodies`), but no later system could use it:
  in BattleServer `SteeringSystem` waits for `PlanningSystem`, and every later system waits for `ZoneSystem`, which
  runs alone; in ParallelSystems the stage is the whole update; in WorldSimulation every stage holds one system.

| World | Stages (multi-system) | Stage path | Graph path | Idle beside the slowest of a stage |
| --- | --- | --- | --- | --- |
| BattleServer | 12 (1) | 4,181 µs | 4,181 µs | 507 µs |
| ParallelSystems | 1 (1) | 126 µs | 126 µs | 227 µs |
| WorldSimulation, `ParallelSystems` on, 10,000 / 100,000 | 9 (0) | 1,261 / 2,395 µs | same | 0 |

- **Systems that run alone are barriers in any schedule.** An `Entity` or `World` parameter, an `[OnUpdate]` method
  or a structural change makes a system run alone: 7 of BattleServer's 13 default systems, 7 of WorldSimulation's 9.
  A graph waits for them exactly as stages do, and real servers are written this way.
- **The best case is small.** `BarrierBenchmark` (outside the repository; 100,000 rows): a heavy system beside a
  chain of three light ones staged `{heavy, first}`, `{second}`, `{third}`, against the same three passes in one system
  beside the heavy one (the schedule a graph would run, on today's runner): 6.36 against 6.08 ms in one run, 6.73
  against 7.13 ms in a second, each inside its error (±0.3 to 0.9 ms).
- **A graph would cost on every update.** One change tick per stage is what keeps `[Changed<T>]` exact (a stage's
  systems never write what another one reads); a graph needs a tick per system computed from its level, per-system
  dependency counters reset and decremented atomically, a ready queue helpers poll instead of one cursor, and the
  freeze of structural changes held across overlapping levels; the adaptive waking of D22 decides per piece of work,
  which a graph no longer has.

**Considered.** A dependency graph from the same read/write sets and orderings, deterministic for every conflict
pair (the design evaluated here); dropped on the numbers above. Where a stage's slowest system does leave a chain of light
conflicting systems waiting, putting the chain's passes into one system (several `[ForEach]` methods run in order)
gives it the graph's schedule today; `DescribeSchedule` and `SystemStats` show such a stage. Measured again if a world
shows a graph path well below its stage path.

## D77. Grid tiles: a parameter that loads its halo [#d77-tiles]

**Decision.** A grid of cells updated from its neighbors (water, light, heat) is cut into tiles, one entity each: a
component that implements `ITile<TKey>` (its shape as static members, `Width`, `Depth`, `Height`, `Faces`; its key in
a value index; `Beside(key, face)`, the key of a neighbor) and a `DynamicBuffer<TCell>` of its cells. A `[ForEach]`
method takes a `Tile<TCell, TTile>` parameter, and the generator writes the plumbing: it finds the tile's neighbors in
the index once per entity, declares the reads (the index, `DynamicBuffer<TCell>`), adds the shape and the buffer to the
method's filter, and keeps the method parallel. `Pad(from, to)` copies the layers into a texture of the thread with a
ring of `Halo` cells from the facing edges of the neighbors (and layers under and over), records a bit per row that
holds a cell that is not zero, and returns a `PaddedTile`: `Rows(reads)` walks the rows a stencil can change with
`TrailingZeroCount`, `At(row)` is a cursor whose `Load128` / `Load256` / `LoadVector` read a vector one cell, row or
layer away. A tile parameter beside a write of its cell buffer is EECS059, the rule of `Lookup<T>`.

The shape also says how far and how wide a stencil reads: `Halo` (cells of halo, up to the tile's extent),
`Neighborhood` (the faces, the faces and edges, or all 26 neighbors) and `Boundary` (fill, clamp or mirror where a
tile has no neighbor; a periodic grid is a `Beside` that wraps). `Tile.ChangedEdges` / `Tile.Facing` let a grid put its
quiet tiles to sleep and wake only the tiles facing an edge that changed. A tile takes one step per pass. EECS072
reports a shape a tile cannot hold, EECS073 two tiles of one cell type in one method.

**Why.**
- **Every grid wrote the same 80 lines.** The VoxelServer water found its four neighbors, read their counts and
  buffers through four `Lookup`s, padded a `stackalloc` texture with an edge case per face and kept its own row mask.
  With a tile, `Flow.cs` keeps the rule and its row loop; the shape is four members of `Chunk`.
- **As fast as the hand-written loop.** `WaterTileBenchmark` (400 chunks, one step, the hand-written system against
  the tile one, outputs compared chunk by chunk, two rounds): the tile 482–513 µs, by hand 516–524 µs at 1 thread
  (263 µs against 263–269 µs at 4), 0 B both.
- **The load of the common shape is its own loop.** With halos, neighborhoods and boundaries added, the general load
  (every neighbor slot, a fill or a clamp per cell) made the water up to 40 % slower than its first version. Three
  changes brought it back: a missing neighbor reads a blank array of the fill (no branch per cell), the rows are
  copied through refs computed once per row, and a halo of 1 with faces only and a border boundary (the water, the
  Laplacian) takes a loop of its own, chosen by a condition of constants; the neighbor search is unrolled per face
  for the faces neighborhood. That loop is compiled twice, with and without the row masks (`Masked` / `Unmasked`, a
  `typeof` constant), so a tile only sampled (the water's blocks) tests no cell, and a halo cell is tested in the
  register it was moved through. The water's tile went from 566–585 µs to 482–513 µs at 1 thread; the first version
  took 528–547 µs. The row loop of the general load keeps its vectors in registers (no spill).
- **The constants fold.** The shape is static abstract members of a struct type argument, so the JIT compiles every
  stride, every `Offset` check and every copy size as a constant: a sample is one `vmovdqu` from a fixed displacement.
- **The method is its own compilation root.** The generated accessor that calls a method with a tile is
  `NoInlining | NoOptimization`: inlined into the small `Execute` of the job, the method spent the inliner's budget
  (about ten times the root's size) and its eleven `Load128` calls stayed calls. As its own root it inlines all of
  them (192 inlinees, no call in the row loop). The hand-written version had the same effect by accident: a method
  with `stackalloc` is never inlined.
- **A throw helper that never returns, and one x check per column.** The cursor's throw helpers are
  `[DoesNotReturn]`, not `NoInlining`: the JIT compiles a call to a method that may return as one that clobbers every
  vector register, so each check spilled the stencil's vectors (the 9-point blur's Tier1 body: 1,399 bytes before,
  884 after). The x check stands on its own: dy and dz are constants and fold, and the loads of one column (x − 1 in
  three rows) repeat one compare, which the JIT then removes, so a 9-point blur checks three times per vector, not nine.
  The 9-point blur at 1 thread went from 969 µs to 756–765 µs, the Laplacian from 966 µs to 661–678 µs.
- **Tiles against hand-written stencils.** `TileStencilBenchmark` (1,024 plates of 16 × 16 floats on a torus, outputs
  compared, two rounds): the 9-point blur 756–765 µs with a tile, 679–690 µs with a direct-mapped key, 389–432 µs by
  hand at 1 thread (406–428, 389–403 and 253–269 µs at 4); the Laplacian 661–678 µs against 385–397 µs (381–393 against
  249–273 µs at 4); 0 B all. The gap is the general load (about 200 ns per plate: every neighbor slot through one copy
  loop with its row mask) and the index search (about 150 ns): a stencil this cheap per cell is dominated by them, and
  one that does real work per cell (the water) is not.
- **Quiet tiles cost nothing.** `TileActiveBenchmark` (1,024 Life plates, 16 blinkers, two rounds): always on 369–378 µs,
  with sleep and wake 10.7–11.6 µs at 1 thread (222–226 µs and 12.7–13.1 µs at 4), 0 B both.
- **A texture per thread, not on the stack.** A `stackalloc` sized by a type argument is not a constant; the texture
  is a `[ThreadStatic]` array per cell type and shape, allocated on the thread's first load for every layer, then
  reused (the same rule as `Scratch<T>`, D74).

**Considered.**
- **Several steps per load (temporal blocking, a deep halo):** built and dropped. With a halo of k, one load holds what
  k steps of a stencil reaching one cell need; the prototype ran them on two textures of the thread, the region
  shrinking each step. `TileStepsBenchmark` (four blur steps on 1,024 plates; ratios against four plain passes, two
  rounds): two passes of two steps 1.55–1.58 at 16 × 16 cells and 1.70–1.86 at 32 × 32 at 1 thread (1.14–1.22 and
  1.55–1.57 at 4), one pass of four steps 1.55–1.70 and 1.75–1.80 (1.08–1.10 and 1.60–1.61 at 4). Each step also
  computes the halo cells the next one reads, and on a grid whose cells fit the cache the passes it saves cost less
  than that. Steps could pay on a grid far larger than the cache; nothing measured here is.
- **A sliding window along y (2.5D streaming):** a prototype kept three padded layers and padded layer y + 1 just before
  stepping layer y. A 7-point stencil over 8 × 8 chunks of 16 × 16 × Height floats, two rounds: Height 32, 416–443 µs
  whole against 434–454 µs sliding (1.03–1.04); Height 256, 3,821–4,091 µs against 3,847–3,894 µs (0.95–1.01, within the
  error). Not built: a texture of the whole tile fits the cache at these sizes.
- **A cache of the neighbors' ids:** `TileNeighborBenchmark` (1,024 plates, 8 neighbors, a pass that only finds
  them, two rounds): searching the index 147–159 µs, a direct-mapped key 107 µs, ids read from a component 1.4–1.5 µs
  at 1 thread (60–66, 46–48 and 2.8–2.9 µs at 4). Not built: in a stencil pass the search is about a fifth of the
  cost, and a cache needs per-entity state outside the tables and an invalidation on every create, destroy and key
  change; a key that implements `IDirectMapped<TKey>` makes each search an array read without one.
- **The neighbor search unrolled for every neighborhood (each of the 26 slots a constant):** tried and dropped.
  `TileNeighborBenchmark` at 1 thread, two rounds against three of the loop over the slots: searching the index
  148–154 µs against 166–173 µs, but a direct-mapped key 127 µs against 117–123 µs (the unrolled body outgrows what an
  array read per neighbor pays for); the 9-point blur and the Laplacian with a tile within noise (708–753 against
  726–749 µs, 713–737 against 739–766 µs). The faces neighborhood keeps its unrolled search.
- **A generated per-cell kernel (the user writes `Next(center, north, south, ...)`, the generator the loop):** not
  built. C# arithmetic on `byte` promotes to `int`, so a scalar body does not map onto byte lanes; the vector loops
  of the generator target `Vector<T>` (32 bytes on AVX2), not a 16-cell row; and the water reduces per row (wet
  rows, the first and last layer that changed, edges that changed), which a per-cell function cannot say. What is
  left in the user's method is the rule itself.
- **A new analyzer id for a tile that writes its own cells:** it is the misuse EECS059 already reports for
  `Lookup<T>` (a read of what the pass writes), so EECS059 covers both.
- **Several fields in one tile, deinterleaved:** not built. One struct per field, each its own buffer and tile type, is
  what the texture and the masks already handle; EECS073 rejects two tiles of one cell type in one method, since they
  would share the thread's texture.
- **A periodic boundary mode:** a `Beside` that wraps is the periodic grid, with no mode to add.

## D78. Records out of a pass are an `Emit<T>` parameter, appended in row order [#d78-emit]

**Decision.** An `Emit<T>` parameter of a `[ForEach]` method (taken by value, `T` a struct) appends records:
`Add(in T)`, `AddRange(span)`. Each chunk of a parallel pass, or the whole pass on one thread, appends to its own list,
taken from a pool per `T`; when the pass ends the lists are appended, in chunk order, to `Items` (a `DynamicBuffer<T>`)
of singleton `Emitted<T>`, added when missing. Passes append and never clear: the system that applies the records
clears them. The system writes `Emitted<T>` (once per pass), so a reader of it waits for the emitter. EECS070 rejects
a method that also takes `Emitted<T>` or two `Emit<T>` of one `T`. Snapshots and saves copy the records.

**Why.**
- **A parallel pass had no output but its own rows.** A combat pass that produces hits for other entities, or an
  area-of-interest pass that produces packets, either wrote a pending record into each row and scanned the rows
  again, or shared a queue. `EmitBenchmark` (half of 10,000 / 100,000 attackers hit; 4 cores): `Emit<T>` in
  parallel took 10 to 16 µs at 10,000 attackers and 103 to 121 µs at 100,000 (two rounds), about what the same method takes on one thread (the step per row is light and memory bound), ahead of the hand-written component-then-scan (1.3 to 2 times as slow), a `ConcurrentQueue`
  (13 to 72 times as slow) and an `Interlocked` cursor into a preallocated array (5 to 23 times), all at 0 B.
- **Row order, on any number of threads.** The chunks are already numbered in row order (the order `Reduce<T>`
  combines in, D69), so joining their lists in that order gives the records of the serial method, record for
  record. A replay, a test and a server with another core count see the same list.
- **Append, not replace.** Several systems emit one kind of record in one update (melee and spells both emit damage);
  a pass that replaced the list would drop the earlier system's records before the applying system ran. Whoever
  applies the records is the one that knows they are applied, so it clears them.
- **0 B after warm-up.** The first chunk's list becomes `Items` when `Items` has none; later lists are copied in and
  go back to the pool, which keeps them at the largest size a chunk needed (the pool is per `T`, under a lock taken
  once per chunk, not per record).

**Name.** `Emit` is what a GPU geometry shader, a Flink operator and Unity's `NativeStream` writer call adding to an
output stream; `Emitted<T>` is what came out. Considered: `Output<T>` (also the name of a parameter direction),
`Stream<T>` (`System.IO.Stream`), `Events<T>` (an event system, which EasyEcs does not have: D1), `Append<T>` (a
verb that says nothing about the pass).

**Considered.**
- **Replace the list each pass:** loses records of the other systems emitting the same `T` (above).
- **Lists swapped into the singleton each pass:** the first version did, and the singleton's list then grew again
  every pass (1.6 MB per 100 updates); stealing only into an empty `Items` keeps it.
- **A code fix for "write a component, then scan it":** not detectable reliably (a component written in one system
  and collected in another is also how state is kept between ticks); only the benchmark shows the cost.
- **Per-thread lists:** a thread takes chunks in an order that depends on timing, so the records would come out of
  order.

## D79. Deterministic random numbers are a pure function, `EntityRandom` [#d79-entity-random]

**Decision.** `EntityRandom` is a singleton (`Seed`, `Tick`) and a set of pure static functions of (seed, entity id,
tick, stream): `Bits`, `Float` ([0, 1) in steps of 2^-24), `Range` (int by multiply-high, float) and `Chance`. The
bits are four rounds of SplitMix64's finalizer, one per input, the seed mixed first. EECS071 reports `Random.Shared`
and `new Random()` in a `[ForEach]` method; its fix draws from `EntityRandom` with a stream per call site.

**Why.**
- **Parallel passes could not draw repeatable numbers.** `Random.Shared` gives rows numbers in the order threads
  ask; a seeded `Random` is one thread's state. A counter-based generator (cuRAND's Philox, JAX's threefry) has no
  state: the same inputs give the same number on any thread, in any row order.
- **The hash was measured.** `EntityRandomBenchmark`, one float per entity of 100,000: four SplitMix64 rounds
  420 to 467 µs, Philox-4x32 with 7 rounds 2.4 to 2.7 times as slow, with 10 rounds (cuRAND's) 3.9 to 4.0 times, a seeded `Random`
  2.2 to 2.3 times as slow, and repeatable on one thread only; `Random.Shared` (one xoshiro256** per thread, nothing to mix) 0.8 times the time. In a parallel pass (one roll
  per row), `EntityRandom` took 266 to 440 µs and `Random.Shared` 157 to 270 µs: the price of numbers that repeat.
  The JIT inlines the whole function into the row loop (three multiplies per round, no call); Philox's 32×32→64
  multiplies would vectorize with AVX2 where 64-bit ones need AVX-512DQ, a gain for a vector loop that is not
  measured here.
- **The seed is mixed first.** With `seed ^ id`, seeds 1 and 2 would only swap the numbers of entities 1 and 2.
- **A stream per call site.** The same four inputs give the same number, so two draws of one row in one tick need
  two streams; the fix numbers them.

**Considered.**
- **A generator state per entity (a component):** a write per draw, a tracked component stamped, a save larger.
- **Philox or threefry:** slower here, and the quality of four 64-bit finalizer rounds over independent inputs is
  enough for games and simulations (it is not a cryptographic generator, nor documented as one).
- **The seed only passed explicitly:** kept (the static members), and the singleton added so a `[ForEach]` method
  takes one `in` parameter.

## D80. A parallel loop over a range or a list is `world.ForParallel` [#d80-for-parallel]

**Decision.** `world.ForParallel(count, ref job)` runs an `IForRange` job (`Execute(start, end)`) over indexes, and
`world.ForParallel(ref buffer, ref job)` an `IForSpan<T>` job (`Execute(start, span)`) over the elements of a
`DynamicBuffer<T>` (an `Emitted<T>`'s records), on the world's runner: the chunks of parallel `[ForEach]` (about four
per thread, multiples of 64 between 1,024 and `MaxChunkRows`, or `chunkSize`), the same claiming and helper
waking, the structure frozen during the call. One job copy per chunk; nothing is merged back. EECS060 and EECS061
cover the jobs.

**Why.**
- **Records need processing after the pass that emitted them.** `ForParallelBenchmark`, 4 cores: a heavy step per
  record (a few square roots) 1.2 to 2 times faster than one thread at 10,000 / 100,000 records (the machine was
  shared, so the gain varied between rounds), level with `Parallel.For` over the same chunks with a static delegate
  (within the noise of each other across the two rounds), which allocates 2 KB per call; ForParallel allocates
  nothing. A light step (one multiply-add) is memory bound: 1.7 to 1.8 times slower than one thread at 10,000 records
  (handing out chunks costs more than the work) and 0.9 to 1.2 times its time at 100,000; such a step stays a loop.
- **One runner.** `Parallel.For` beside the world's runner would put two pools of helpers on the same cores; the
  runner's adaptive waking already knows when helpers pay.
- **Small and like the rest.** Two interfaces and two calls; a span per chunk, as `ForEachBatchParallel` gives.

**Considered.**
- **Merging job copies (a reduction over a range):** a `Reduce<T>` method covers totals over rows; over a plain
  range it would be a second reduction API, and no use case asked for it.
- **Taking a `Span<T>`:** a span cannot be captured by the runner's work items (a ref struct); the buffer, or a
  range over an array the job holds, covers it.

## D81. Keyed reductions not added [#d81-keyed-reductions]

**Decision.** No dedicated keyed (histogram) reduction. A histogram of up to a few thousand bins is a `Reduce<T>` of
a singleton holding an `[InlineArray]` of counts (its `Combine` adds the bins); more bins are counted on one thread,
or into a component per key. The pattern pays when the counting rides along a parallel pass that does real work per
row; a pass that only counts is faster on one thread.

**Why.** `HistogramBenchmark`, 100,000 rows, 4 cores: per-thread bins merged once per thread (the candidate API)
were 17 to 24 % faster at 1,024 bins, but 1.9 times slower at 16,384 and 2.8 to 2.9 times slower at 65,536 than one thread's plain loop: zeroing and
merging threads × bins outweighs counting 100,000 rows. `Reduce<T>` over `[InlineArray]` bins was 1.1 to 1.3 times slower than one thread at 1,024
and 3.1 times slower at 4,096 bins; an `Interlocked` increment per row into shared bins was 4 to 27 times as slow. No candidate wins
clearly at the sizes a keyed API would be for.

**Limit found.** A `Reduce<T>` of 64 KB or more (16,384 ints) fails at the first pass: the generated job keeps its
per-chunk copies in an array, and the runtime creates no array of a value type that large (`TypeLoadException`).

**Considered.**
- **Per-thread bins** (above) and **a sparse list per chunk** (pairs sorted and merged): the second adds a sort per
  chunk to the same merge, so it was not built.

## D82. One entity is a `[ForEntity]` method [#d82-for-entity]

**Decision.** A static method marked `[ForEntity]` runs on one entity. The generator writes the `IForEachEntity` job
that `entity.Run` takes (its `ref` parameters are the `WriteMask`, its filter attributes are a `static readonly`
filter, and it implements `INoStructuralChanges` when the method makes no structural change). It also writes an entry
point next to the method, with the method's name: `Owner.Method(entity, [since,] values…)`. The entry point returns
whether the method ran.

**Why.**
- **A request handler written as a job is four declarations for one line of work.** You write a struct, its fields,
  a `WriteMask` that must match the `ref` parameters (EECS037 checks it), and a filter field. Then each call site
  creates the job and calls `Run` with the type arguments spelled out. A `[ForEach]` method outside a system already
  gets a generated job and entry point
  ([D26](#d26-generated-members-and-a-suggestion-to-use-them)). One entity is the same pattern with
  `entity.Run` in place of `world.ForEach`.
- **The name pairs with `[ForEach]`.** `[ForEach]` runs the method for each matching row; `[ForEntity]` runs it for
  the one entity the caller gives. Both attributes declare what the method is, not when it runs.
  - The working name, `[RunOn]`, reads as a schedule (run on a thread, on an update) and suggests a target type
    argument.
  - `[OneEntity]` names the cardinality, but no verb or preposition says the method runs.
- **The entry point keeps the shape of the other generated runners.** It is a static member of the method's type,
  named like the method, with the entity first. A method with `[Changed<T>]` / `[Removed<T>]` takes the tick to look
  back from second, the way `Since` does. As with runners, the method stays private so that its name is free for the
  entry point.
- **It costs what the hand-written job costs.** The generated code is the same `entity.Run` call: `ForEntityBenchmark` (1,000 hits on 10,000 units, a tenth dead): 9.80 and 9.96 µs in two rounds against 10.04 and 9.97 µs for the hand-written job and filter field, inside the error, 0 B both.

**Considered.**
- **An extension member on `Entity` (`unit.TakeHit(30)`).** Every request of every module would land in `Entity`'s
  member list, and two owners with one method name would collide. The owner's name says whose request it is.
- **Returning the method's result.** `ref` values already carry results, as they do for runners; a `bool` keeps one
  meaning, whether the method ran.
- **Converting jobs whose fields are read after the call.** EECS080 converts a job only when every use of it is a
  creation followed by one `Run`. A job that returns a result in a field becomes a method with a `ref` parameter, and
  that rewrite of the call site is left to its author.

## D83. A system's cadence is an attribute [#d83-update-interval-attribute]

**Decision.** `[UpdateInterval(n, Phase = p)]` on a system sets how often the system runs; there are no `UpdateInterval`
and `UpdatePhase` properties. The generator writes the two values into the system's code struct, which `AddSystem`
reads once into the system's record. EECS083 reports an interval below 1 or a phase outside 0 to n - 1.

**Why.**
- **The cadence was meant to be a constant, and a property could not say so.** EECS018 warned on a computed override
  after the fact. An attribute argument is a compile-time constant, so that warning and its code fix go away.
- **One virtual call less per update, below what measures.** `RunSystem` used to make one virtual call per system per update to read the interval;
  it now reads a field of the system's record, set when the system is added. In `OrderingBenchmark` (four systems over 10,000 entities per
  update): before and after, 6.96 and 7.21 µs in one round, 7.55 and 7.16 µs in a second (registered order; ordered: 6.99 and 7.09, then 7.96 and 7.02 µs), each inside its error (±0.22 to 0.69 µs): one virtual call per system is below what the benchmark can see, so the reason for the change is the constant, not the speed. 0 B either way.
- **The cadence is visible without running code.** Tools, the analyzer (EECS028 exempts the `[OnUpdate]` method of a
  system with a cadence) and readers all see it on the declaration.

**Considered.**
- **Keeping the properties next to the attribute.** That gives two ways to say one thing, with an order between them to
  learn. The breaking change is one line per system, and the migration guide shows it.
- **Run-time cadence.** A server that changes how often a system runs puts the system in a group and updates the group
  when it is due ([system groups](/en/docs/guide/systems#system-groups)), as
  [D51](#d51-not-added) already recommends over a time-based interval.

## D84. `[Consume]` destroys the visited rows in bulk when it can [#d84-consume]

**Decision.** `[ForEach, Consume]` destroys exactly the rows its pass visited, when the pass ends.
- **A method that makes no structural change** (or a batch method) is followed by one `DestroyAll` with the method's
  own filter. Whole tables that match and hold no cleanup component are freed in one step.
- **A method that may change structure** destroys each entity right after the method ran on it.
- **If the pass throws,** nothing it has not finished is destroyed.
- A method that consumes makes its system run alone in a parallel update. `[Consume]` with `Slices` is EECS085.

**Why.**
- **Bulk is exact only when the pass cannot change what matches.** After a method without structural changes, the
  rows that match the filter are exactly the rows the pass visited: no entity was created, moved or tagged in between.
  A method that creates entities matching its own query (a `Spawn` that spawns) would see them destroyed by a
  `DestroyAll`, so such a method destroys row by row.
- **Measured** (`ConsumeBenchmark`: each operation creates N event entities and runs one pass that applies and destroys
  them; `HandWritten` calls `entity.Destroy()` in the body, `EachRow` is `[Consume]` on a method that may change
  structure, and `Bulk` is `[Consume]` on one that does not):

| Events | `HandWritten` | `EachRow` | `Bulk` | Allocated |
| --- | --- | --- | --- | --- |
| 1,000 | 37.85 / 36.65 µs | 38.39 / 38.61 µs | 14.84 / 14.84 µs (0.39× / 0.41×) | 0 B |
| 100,000 | 3,923.61 / 3,946.63 µs | 3,878.94 / 3,908.39 µs | 1,499.03 / 1,392.84 µs (0.38× / 0.36×) | 0 B |

  (two rounds, first / second)

  Bulk takes about 0.4 of the time of a destroy per row. Per row, `[Consume]` costs what the hand-written destroy
  costs, so the methods that cannot use bulk lose nothing.

- **What a throw leaves.** The bulk destroy runs after the pass, so an exception skips it and every event stays for the
  next run, which visits them again. The per-row path has already destroyed the rows it finished, as hand-written code
  would have.

**Considered.**
- **Always row by row.** It is simple, but it pays the per-row cost where a table could be freed at once.
- **Recording the visited ids and destroying those.** That is exact for every method, but it costs a buffer that grows
  with the pass (unbounded memory per pass) and a lookup per id. Per-row destroy is already exact for the methods
  where bulk is not.
- **Consuming with `Slices`.** Each destroy moves rows of the other slices, so events could wait many runs.

## D90. Vector loops for parallel methods, optional and narrow lanes, struct values and wide rows [#d90-vector-loops-reach]

**Decision.** The vector loop of [D68](#d68-vector-loops-without-opting-in) takes more of the methods real systems
write, and each method's loop is listed:
- **Parallel methods.** A `[ForEach(Parallel = true)]` method's chunks run their runs of rows through the same loop.
- **`FloatMode.Fast` math.** `MathF.Sin`, `Cos`, `Exp`, `Log`, `Log2` and `Hypot` (and their `double` forms) take
  .NET's vector approximations (`Vector512.Sin`...); under `FloatMode.Exact`, EECS055 names the call.
- **`Maybe<T>` as a lane mask.** The presence bits of the run's optional column are a lane mask per vector, `HasValue`
  is that mask and `Value`'s fields are lanes read (and written) where rows have `T`; a read of `Value` for a row
  without it sends the vector's rows to the method, which throws as written.
- **Narrow lanes.** `byte`, `sbyte`, `short` and `ushort` components get 64 or 32 rows per `Vector512`. C# computes
  them as `int`, so the generator follows each value as low bits plus the interval it lies in, and takes an operation
  only where that proves the narrow lane is the `int` result's: wrapping `+ - * & | ^ ~ <<` (the low bits of the `int`
  result), `Math.Min` / `Max` chains around a sum or difference as `AddSaturate` / `SubtractSaturate`, compares against
  a constant inside the range (a saturated sum against 255 is not), right shifts and `Abs` of exact values. Masked words
  of narrow lanes run the method.
- **Struct values.** A field of `System.Numerics` or Godot `Vector2` / `Vector3` / `Vector4` (or another struct of
  lanes) gives its lanes; `new T(...)` (a record's positional constructor, or one that only sets fields), `with`, the
  vector types' component-wise operators, `Min` / `Max` / `Abs` / `SquareRoot` and struct locals become one statement
  per lane, so the Godot sample's `position = new Position(position.Value + velocity.Value * dt)` is a flat loop.
- **Cold branches.** A call (or anything else the loop cannot express) under a condition the loop computes sends the
  rows of a vector whose lanes take it to the method, in row order, before any store; the other vectors stay vectors.
- **Wide components.** On AVX-512, a component the loop does not split (more than 4 lanes, fields of other types) gets
  a `Vector512` loop when the method uses only 4-byte lanes of it on word boundaries, the row is at most 16 words, and
  the permutes pay: the 16 rows of a vector are loaded as K whole vectors, a pruned tree of two-source permutes
  (`vpermt2ps`) gathers each used field, and only the vectors holding written words are permuted and stored back.
  The job's tables are `static readonly` fields, and a `static readonly bool` checks the runtime layout (the size, and
  each used lane set through `with` and found in its word), so a layout the generator did not predict runs the method.
- **An inspector.** `DescribeSchedule()` lists each method's loop (`SystemInfo.Loops`: "Move: vector (Vector512 or
  Vector&lt;float&gt;), flat", "Steer: vector (Vector512 only), wide component (permutes), masked words scalar",
  "Spawn: scalar (it takes the Entity)"); `tools/jitdisasm.sh` prints the Tier-1 code of a loop
  (`DOTNET_JitDisasm`, `DOTNET_TC_CallCountingDelayMs=0`).
- **The advice to split.** When a component is too wide or too mixed for the loop and the method uses at most half its
  fields (at most 4, of one size), EECS055 ends with them: "it uses 3 of Body's 12 fields (X, VX, Y): split them into a
  component of their own".

**Why.**
- **`FloatMode.Exact` is deterministic, and stays so.** Each lane is one IEEE operation of the scalar code, in its
  order: `+ - * /`, `Sqrt`, `Min` / `Max` and the conversions are correctly rounded on x64 and on ARM64 (AdvSimd)
  alike, so a vector loop gives every machine the scalar code's bits. `FloatMode.Fast` is the mode that may differ:
  reordered float sums, and approximations, measured against `MathF` on 1.6 million random inputs each (`Sin` and
  `Cos` in ±100, `Exp` in ±80, `Log` in 10^-30 to 10^30): `Sin`, `Cos`, `Log` and `Log2` within 1 ulp, `Exp` within 2
  (`Exp(0)` is `1 + 1 ulp`), `Hypot` equal on every pair tried; for `double`, `Sin` within 1 ulp, `Exp` and `Log`
  within 2.
- **Narrow lanes are proven, lane by lane.** A unit test runs every pair of `byte` (and `sbyte`) values, 65,536 rows,
  through each narrow kernel, with and without rows that lack a component, and compares the bits with the method;
  swapping `AddSaturate` for `SubtractSaturate` fails it. Anything the interval does not prove stays scalar, with the
  reason.
- **Wide rows: where the permutes pay.** Prototype (BenchmarkDotNet, this machine, AVX-512), the permute tree against
  the per-row loop at 1,000 / 10,000 / 100,000 rows: 3 of 12 fields under 11 vector operations 0.48 / 0.60 / 0.85 of
  the scalar time; 4 of 8 fields under 4 operations 0.69 / 0.67 / 0.97; 3 of 12 under 3 operations 0.89 / 1.03 /
  1.10; 4 of 16 under 4 operations 1.07 / 0.96 / 0.94; 2 of 8 under 2 operations 0.66 / 0.97 / 1.06. The gate is the
  line between them: fewer permutes per 16 rows than 8 per vector operation of the body (31 permutes against 11
  operations vectorizes, 42 against 4 stays scalar, and says so). The same rows split into a component of the 3 used
  fields ran in 0.16 to 0.34 of the scalar time: the advice is worth more than the permutes.
- **Cold branches cost only where taken.** Prototype at 10,000 rows, a call under a condition: 7.75 µs →
  1.06 µs when no row takes it, 1.09 at 0.1 %, 1.94 at 1 %, 9.30 (against 12.74) at 10 %.
- **The generated loops, against the same method per row** (`KernelBenchmark`, 1,000 / 100,000 rows, two runs): a
  byte brightness with saturation 48 ns / 2.6 µs against 3.1 µs / 311 µs; `Vector3` movement 96 to 108 ns / 23 µs
  against 488 to 565 ns / 53 to 58 µs; a `Maybe<T>` mask 261 to 298 ns / 24 µs against 1.5 µs / 148 to 156 µs
  (`MaybeBenchmark.OneMethod` 109 → 10 µs, as fast as two methods); a parallel step 274 to 294 ns / 23 to 25 µs against
  1.4 µs / 207 to 215 µs; a cold branch 87 ns / 10 µs when no row takes it and 281 to 287 ns / 27 µs when one row in
  100 does, against 752 ns / 64 to 68 µs and 773 to 811 ns / 83 to 85 µs; `Sin` and `Exp` under `FloatMode.Fast`
  1.8 µs / 178 µs against 7.2 µs / 1.43 ms; the wide component of 12 floats 898 to 916 ns / 186 to 196 µs against
  1.6 to 1.8 µs / 209 to 217 µs. Every one allocates 0 B, and the loops the branch had before kept their times.

**Considered.**
- **A full transpose of 8 or 16 words a row** (butterflies, every word moved): 1.07 to 2.05 times the scalar time (8
  words at 1,000 rows 983 against 531 ns, 16 words 2,666 against 1,301 ns). The pruned tree moves only the used words.
- **Gathers.** .NET 10 has no AVX-512 gather API; AVX2 gathers of 8 rows ran in 0.8 to 1.18 of the scalar time, below
  the tree wherever the tree paid. Reads of other entities through a `Lookup<T>` gather on request ([D131](#d131-lookup-gathers)).
- **Strided loads** (one insert per lane): 1.0 to 2.9 times the scalar time.
- **`[Lane]` / `[Hot]` field markings, `[Layout(Soa)]` storage.** The method already says which fields it uses, so
  marking them adds nothing the generator lacks. A struct-of-arrays table was the fastest form (3 of 12 fields: 97 ns
  against 765 at 1,000 rows, 19.9 against 185 µs at 100,000) but changes every API that hands out a `ref` to a row;
  splitting the component gets most of it (263 ns, 30.7 µs) with storage unchanged, so EECS055 says that instead.
- **Unrolling the loop** by 2 or 4: 37.4 → 33.1 / 34.1 ns at 1,000 rows, 1,018 → 1,037 / 1,076 ns at 10,000, within
  noise at 100,000: no consistent gain, and twice the code.
- **Left for later:** masked words of parallel methods (a chunk passes whole runs), `Maybe<T>` in parallel methods
  and of narrow lanes, masked words of narrow lanes and of wide rows (they run the method), `Atan2`, `Asin`, `Pow`
  and kin (no vector form in .NET 10), `Vector2.Clamp` (the sample clamps each field with `Math.Clamp`).

## D94. A parallel pass opens the blocks its `Maybe<T>` writes [#d94-optional-writes]

**Decision.** A generated parallel job that writes a tracked component through a `Maybe<T>` names it in
`OptionalWrites`, a `ComponentSet` held in a static field of the job type. `ForEachParallel` treats those components
as it treats the written components it queries: its chunks end on multiples of 4,096 rows, or the change-tick blocks
of the rows they cover are opened at the pass's tick before any chunk runs.

**Why.**
- **The race.** A block's summary of change ticks is raised without a lock only once it holds the pass's tick
  (`Open`). A chunk that stamps an unopened block first resets the block's words while another chunk of the same block
  may be adding its own. The queried columns were opened; a `Maybe<T>` column, outside the query, was not.
  `ChunksSplittingBlocksKeepTheChangeTicksOfAMaybeExact` (10,000 rows in chunks of 64, 6,666 of them with the
  component, 1,000 passes) found 6,623 changed rows after a pass before the change, and every row of every pass after.
- **The cost stays out of the rows.** The set is a constant of the job type, read once per table and pass; the row
  loop is unchanged. `ChangeTrackingWrite` and `ParallelForEach`, which take no `Maybe<T>`, kept their times within
  the error, 0 B.

**Considered.**
- **Opening every tracked column of a table when a job takes a `Maybe<T>`.** Simpler, but a block the pass does not
  write then moves its latest words into the rest, and a later `[Changed<T>]` reader visits all of its words.
- **An atomic update of every summary.** It costs a locked instruction per first stamp of a word in every pass,
  single-threaded ones included, to fix a case the parallel pass can avoid.
- **Making the component a type parameter of the call.** A type parameter of `ForEachParallel` is a queried
  component: the pass would then skip the rows without it.

## D95. The generators find namesakes by name and rule out vector loops before binding [#d95-generator-per-edit]

**Decision.** Two parts of the generators' work per edit no longer grow with the code around them. The structs and
enums of a namespace are indexed by name once per compilation, and a member a type would get is checked only against
the types whose name a member pattern cuts out of it. A `[ForEach]` method whose signature rules out a vector loop
(it returns a value, is generic, or takes a parameter the loop cannot hold) is decided from the signature, without
binding the body or throwing.

**Why.**
- **Quadratic per keystroke.** Every component and every `DynamicBuffer<T>` element walked all the structs of its
  namespace on each edit to find the types offered the same member names: n squared in the types of a namespace.
- **Exceptions as control flow.** The vector-loop translator gave up by throwing: 419 exceptions per edit of the
  generator benchmark's input, 14 after.
- **Numbers.** `GeneratorBenchmark` (BenchmarkDotNet, two rounds each, 60 modules), base / after:
  `EditMethodBody` 357 / 338 ms against 172 / 168 ms and 39.2 MB against 28.4 MB; with every module in one namespace
  443 / 405 ms against 166 / 151 ms and 59.5 MB against 28.0 MB. `Cold` 368 / 372 ms against 249 / 215 ms. `Compile`
  and `CompileAndAnalyze` stayed within the error. The generated code is the same, file for file.

**Considered.**
- **Caching the members per type across compilations.** A type's member names depend on the other types of its
  namespace, which any edit can change; the index lives as long as its compilation and needs no invalidation.

## D97. Rules for code that does by hand what a parameter does per chunk [#d97-hand-written-parameters]

**Decision.** Three rules point a `[ForEach]` method to the parameter that does its work per chunk of rows. None of
them has a code fix.
- **EECS086** (a suggestion) reports a `ref` singleton accumulated row by row, when system code also resets it each
  update. The parameter is `ref Reduce<T>`.
- **EECS087** (a warning) reports a `World` parameter used only to find other entities and read components the method
  does not write. The parameter is `Lookup<T>`.
- **EECS089** (a suggestion) reports records added one by one to a list that a `ref` singleton holds. The parameter
  is `Emit<T>`.

**Why.**
- **The hand-written forms keep a method on one thread.** A `ref` singleton races in a parallel pass
  ([EECS010](/en/docs/guide/analyzer#eecs010)). A `World` parameter makes the system run alone in its stage. And
  [D69](#d69-reductions), [D75](#d75-lookup) and [D78](#d78-emit) measured the parameters against those forms. The
  rules make the faster form the one users meet.
- **EECS086 waits for a reset.** A first version reported every accumulation. In the docs it fired on 16 examples, and
  each was a running total: a score, deaths so far, rows sent. A reduction replaces its singleton with one pass's
  result, so for a running total it is not the same code. A singleton that a system resets each update (a whole
  assignment, a constant given to a field, `AddSingleton`, `RemoveSingleton`, `SetX`, `RemoveX`, outside `[OnCreate]`
  and `[OnDestroy]` methods) does hold one pass's result. The reset can be in any file, so the rule reports at the end of the
  compilation, and the message names the reset that the reduction makes redundant.
- **EECS087 is a warning.** The cost is the whole system's, a stage of its own, and the fix is one parameter per
  component. EECS086 and EECS089 change two places (the reset, the readers of the list), so they stay suggestions.
- **No code fix.** For EECS086 the reset has to go too. For EECS087 the reads (`Read<T>()`, `entity.X`, `Has<T>()`)
  do not map one for one onto `lookup[id]`, `Read(id)` and `Has(id)`. For EECS089 the readers of the list read
  `Emitted<T>` instead.
- **One mistake, one diagnostic** ([D60](#d60-one-diagnostic-per-mistake)). EECS055 leaves a method that accumulates
  into a singleton to EECS086, and EECS033 leaves a read that EECS087 reports.

**Considered.**
- **Reporting running totals too, with the advice to reduce into a second singleton.** That gives two singletons and
  a system that adds one to the other for every counter, against one `ref` that a sequential method writes in a
  register. It was dropped.
- **A rule for a hand-written `Scratch<T>`** (a `new List<T>` per row). EECS028 already reports the allocation, and
  its message now names the `Scratch<T>` parameter, so no separate rule was added.

## D98. EECS088: one stream per draw, checked in pass code only [#d98-random-streams]

**Decision.** EECS088 reports two `EntityRandom` draws of the same stream for the same entity in one method, and a
draw in a loop that changes neither its stream nor its entity. It checks the code of passes only: `[ForEach]` and
`[ForEntity]` methods and the `Execute` of jobs. Its code fix gives the later draw the next stream that no draw of the
method uses.

**Why.**
- **Two draws of one stream are one number.** `EntityRandom` is a pure function of seed, entity, tick and stream
  ([D79](#d79-entity-random)), so a direction whose two parts share a stream lies on the diagonal. Nothing fails, and
  nothing shows it in a test that checks ranges.
- **Pass code only.** Tests and tools compare two draws of the same stream on purpose, to check that the function is
  pure. In a pass, each row draws once per update, and there a repeated stream is a mistake.
- **Draws that never run together may share a stream.** The two branches of an `if` and the arms of a `switch` are
  left alone.
- **The fix is the next free stream, not `stream + 1`.** `stream + 1` could collide with a third draw.

**Considered.**
- **A fix for a draw in a loop.** Adding the iteration (`stream + (uint)i`) needs a loop variable that the analyzer
  would have to choose. It also changes the numbers of every iteration but the first, so it is left to the author.

## D99. EECS069 warns for a singleton only when the code saves whole worlds [#d99-singleton-saves]

**Decision.** EECS069 (a managed component or singleton without a Nino formatter) is a warning for a component when
the code calls `Save`, `SaveWithout` or `SaveEntities`. It is a warning for a singleton only for `Save` or
`SaveWithout`, and a suggestion otherwise.

**Why.**
- **Entity saves write no singletons.** `SaveEntities` writes the components of the entities it is given. A project
  that saves only player records got a warning for each managed singleton it holds, and none of those warnings could
  throw.
- **Warnings were left in the build.** The benchmarks and the tests built with EECS069 warnings: two benchmark
  components that hold lists, and test fixtures that hold references on purpose. The benchmark components are now
  `[NotSaved]`, and the test project silences the rule.

**Considered.**
- **Following which types each save can reach.** That would need the `ComponentSet` of every call and the data flow
  into it. The rule already leaves a type that a `ComponentSet` names to the code that chose it.

## D100. The names of 4.8: one spelling, verbs for actions, the cadence of a system [#d100-names-of-4-8]

**Decision.** A naming review before 4.8 renames, beyond [D64](#d64-names-of-4-7), names that are new in 4.8:
`TileNeighbourhood` / `ITileShape.Neighbourhood` / `TileNeighbours` → `TileNeighborhood` / `Neighborhood` /
`TileNeighbors`, `tile.Load()` → `tile.Pad()`, `tile.Changes(next, out changed)` → `ChangedEdges`,
`TileStencil.Sides` → `NorthSouth`, `[ForEach(Simd = …)]` → `[ForEach(SimdMode = …)]`, `DynamicBuffer<T>.ReservePool` /
`PoolCapacity` → `FillPool` / `MaxPooledLength`, `[Key]` → `[IndexKey]`, `prefab.Absent<T>()` → `SetAbsent<T>()`, and
the EECS083 descriptor (`BadUpdateInterval`). `Lookup<T>.TryFind`, new
in 4.8, gives an `Entity`, as the released `ValueIndex.TryFind` does. Hidden and internal names follow: `SavedTypes` →
`TypeRegistry` (called by generated code only) and the analyzer's descriptor fields. No alias is kept, and no released
call changes.

**Why.**
- **One spelling.** The API and the analyzer write US English (`Color`, `Behavior` in .NET); "neighbour" was the one
  British word, so a search for "neighbor" missed the tile API.
- **A verb says what happens.** `Load` read like loading a save (`World.Load`); the call pads a tile with its halo
  into a texture. `Changes` read like a collection; it compares and returns the faces whose edge changed. `Absent<T>`
  read like a query; it sets a column without the component, as `Set` does with one.
- **A name says what it holds.** `PoolCapacity` was a length of each pooled list, not a number of lists;
  `ReservePool` fills the pool with lists. `Sides` of `TileStencil` named two rows, not the four sides of `TileFaces.Sides`.
  `[Key]` alone read like any key; `[IndexKey]` says the index, next to `[UniqueKey]` ([D129](#d129-lookup-key) renamed it `[LookupKey]`).
- **The property names its type.** `Simd = SimdMode.Off` repeated the word in two forms; `SimdMode = SimdMode.Off`
  reads like `FloatMode`.
- **Cadence, not schedule.** `World.DescribeSchedule` is the order and the stages of systems; how often one runs is its
  cadence (`[UpdateInterval]`), and the rule and its messages say so.
- **One out type for a key's entity.** `Lookup<T>.TryFind` gave an id and `ValueIndex.TryFind` a handle, so code moving
  between a pass and the owner thread changed types. The released call keeps its handle and the new one follows it; a
  handle converts to its id where one is stored. The tile neighbor search, which stores ids, calls an internal core
  that returns the id, so no handle is built there.

**Considered.**
- **`ValueIndex.TryFind` giving an `EntityId`:** it matches the index's storage, but breaks released code, and every
  owner-thread caller that wants the handle would pay a liveness check (`world.GetEntity`) the index already knows.
- **A `TryGet(key, out Entity)` on every value index:** two calls for one lookup that differ only in their out type;
  the unique index's `TryGet` is the one with a single answer.
- **`[Obsolete]` aliases:** pre-1.0, as in D54 and D64: the compiler finds every use, and every renamed name is new in
  4.8.

## D101. A type declares what it is with attributes; the generator writes the members and the setup [#d101-declaration-attributes]

**Decision.** What a component or singleton is, declared once on its type, is an attribute:
- **A reduction** ([D69](#d69-reductions)): `[Sum]`, `[Product]`, `[Min]`, `[Max]`, `[All]` or `[Any]` on every
  instance field of a partial struct. The generator writes `IReduction<T>`: `Identity` (0, 1, `MaxValue` or +∞,
  `MinValue` or -∞, `true`, `false`) and `Combine`, field by field.
- **A key or a group:** `[LookupKey]` or `[UniqueKey]` on a member (`[LookupKey]` on the type for the value itself), and
  `[Group]` on an `int` or enum member. The generator adds `IIndexed<TKey>`, `IUniqueIndexed<TKey>` or `IGroup` with an
  explicit `Key` or `Group`, unless an interface the struct declares brings it (`IDirectMapped<TKey>` keeps its
  `Slots` and `SlotOf`).
- **World setup:** `[GroupBy]`, `[WhenTargetDestroyed(policy)]` and `[NotSaved]` are registered when the module loads.
  Every world applies them from its first table holding the type. A world's own `GroupBy` or `WhenTargetDestroyed`
  call wins and is never overridden. A `[NotSaved]` type is left out of every save, and a load keeps the world's own singleton of it.

The generator writes the members into a part of the type, so the type and the types around it are partial. The
runtime never reads the attributes: the generated code registers what they mean. The interfaces stay, for a key
computed from several members or a reduction the attributes cannot say. Rules EECS062 to EECS069 check the
declarations, and the generator and the analyzer read them once, through the same `Parts` and `Symbols` code
(EECS062: a type not partial; EECS063: members written beside the attributes; EECS064: a field no attribute
combines; EECS065 and EECS067: a reduction or a key written by hand that an attribute declares, with code fixes;
EECS066: a wrong `Identity`; EECS068: a setup attribute on a type it does not fit; EECS069: a managed type no save
can write).

**Why.**
- **The identity is where hand-written reductions go wrong.** Each chunk starts at `Identity`, so a minimum that
  starts at 0 adds that 0 once per chunk, and the result depends on the thread count and the table sizes. The
  attribute names the operation and the generator picks the identity for the field's type. `ReduceBenchmark` measures
  the generated reductions against the same ones written by hand: the same time, 0 B.
- **An explicit `Key` is the right one, and nobody writes it.** A public `Key => this` on a record struct makes
  `ToString()` print the key forever (EECS043), and a public `Key` is a second name for a field that callers reach
  by mistake. The generated member is explicit.
- **Setup was a call each world had to make.** A world without its `GroupBy` call puts every table in group 0, so an
  `InGroup` filter walks them all. A world without its `WhenTargetDestroyed` call keeps the links to destroyed
  targets. Nothing fails in either case. A test world, a tool that loads a save, or the second world of a process
  behaved unlike the server. Declared on the type, the setup holds in every world.
- **Applied with the first table, not when a world is created.** A world that never holds the type pays nothing, and
  a grouping installed before any row holds the type moves no row.
- **Runtime state needs no formatter.** A connection or a cache in a component would make every save throw without a
  Nino formatter, and a restart builds it again anyway. `[NotSaved]` says so where the type is declared, so a save
  never needs a `ComponentSet` that leaves it out.

**Considered.**
- **Only the interfaces, written by hand:** they stay, but each reduction repeats its identities and each key is a
  member someone must remember to make explicit. The analyzer now points them to the attributes (EECS065, EECS067).
- **Setup through `WorldOptions`:** it is still one setting per world, so it can still be forgotten.
- **Reading the attributes by reflection when a world starts:** every world would pay at its start for every loaded
  type, and trimming could drop what it reads. The generated registration costs nothing until a table holds the type.

## D102. Systems are ref structs of static methods; the world holds their bookkeeping [#d102-systems-are-ref-structs]

**Decision.** A system is a `ref struct` marked `[EcsSystem]` whose members are all static: `[ForEach]` methods and
the `[OnCreate]`, `[OnUpdate]` and `[OnDestroy]` hooks, each hook taking the `World`, the `SystemHandle`, both or
neither. The world never creates a system. It adds one by type (`AddSystem<T>()`, `T : struct, allows ref struct`)
and keeps a record of it: enabled, error, interval and phase, last run tick, run count, stats. A `SystemHandle` is a
(world, slot, version) over that record, and a handle to a removed system throws, as a stale `Entity` does. There is
no inheritance: what a base class shared is a generic system or a static class of helpers, and a constructor argument
is a [`[NotSaved]`](/en/docs/guide/saves#not-saved) singleton. EECS074 to EECS077 keep the form, and a code fix on
CS0246 rewrites a class system of 4.7.

**Why.**
- **A system is a name for static functions.** State belongs in components and singletons
  ([ECS principles](/en/docs/ecs-principles)); an instance only invited fields (EECS007 policed them one by one), and
  cost a heap object per system and a virtual call per hook per update.
- **A ref struct is never an object, and still a type argument.** It cannot be boxed, stored in a field or captured,
  so nothing can hold a system, and with `allows ref struct` it names the system in `AddSystem<T>()`,
  `[UpdateAfter<T>]` and `HasSystem<T>()`. A static class cannot be a type argument.
- **Bookkeeping is the world's data.** One system type added to several worlds has a record in each, and a tool reads
  every record through `world.Systems` without knowing the types.
- **The handle is checked like an entity.** A removed system frees its slot; the version tells a handle to the old
  system from one to a system added later.

**Considered.**
- **Static classes:** no type argument, so ordering and lookups would take `typeof` or strings.
- **Classes with virtual hooks** (the 4.7 form): an object and a virtual call per system, and instance fields.
- **A struct implementing an interface of static abstract members:** the user would write the plumbing the generator
  writes now, and a plain struct can be created, stored and boxed.
- **A generated `world.AddMovement()` per system:** names clash between assemblies, and the ordering attributes still
  need the type.

## D103. One system set per assembly: a switch over its systems, one call per stretch of the schedule [#d103-system-sets]

**Decision.** The generator writes one code struct per system (`__X_SystemCode : ISystemCode`, static `Update`,
`Create`, `Destroy` and `Access`) and one set per assembly (`__EasyEcsSystems : ISystemSet`): every system the assembly
declares and every closed generic system it names, numbered from 0, with a switch per hook whose cases call each code
struct directly. A module initializer registers the set, held weakly. The world schedules at run time as before
(registration order, groups, orderings, parallel stages, cadence) and cuts each stage into segments of consecutive
systems of one set. A segment runs as one call through a function pointer to `World.RunSystems<TSet>`, bound once per
set, which loops over its systems and switches into their code.

**Why.**
- **One indirect call per segment, direct calls inside.** The cases are static calls the JIT can inline. A program
  whose systems live in one assembly pays one indirect call per group update, whatever the number of systems.
- **A function pointer per system costs more than its call.** Each update made one indirect call per system, and
  under the JIT a pointer to a method that is not yet at its final tier lands on its precode stub: one more jump.
  `SystemDispatchBenchmark` measures what a system costs per update apart from its rows.
- **Per assembly, so it stays incremental.** The set depends on the list of systems and their declarations; an edit
  inside a method body regenerates only that system's code (GeneratorBenchmark's `EditMethodBody`).
- **Weakly held, so plugins unload.** A collectible assembly's set goes with its context once its systems leave every
  world ([D17](#d17-unloading-removes-types-from-worlds-bits-are-reused)).

**Considered.**
- **A function pointer per system** (the previous form): an indirect call per system and the precode jump.
- **One generated switch over the whole schedule:** the schedule is decided at run time (registration order, groups,
  `Enabled`, cadence) and spans assemblies; the generator sees neither.
- **Interceptors at `AddSystem` calls:** the call that adds a system is not where it runs, and interceptors key on
  call sites the generator would have to find in every file.
- **Guarded devirtualization:** the JIT guesses one or a few targets per call site; one loop over all systems has as
  many targets as systems.

## D104. A generated job's pass finds its query by job type [#d104-one-query-per-job-type]

**Decision.** The job interfaces have `static virtual bool OneQuery => false`. Generated jobs set it true: the filter
of a generated method is a constant of its declaration, so every pass of the job type takes the same filter, its tick
and slice aside. The world keeps the query's cache entry per job type (`TypeIndex<KeptQuery, TJob>`), and a pass reads
its match with two loads and a null test instead of comparing its filter against the memo's ways. The kept entries
are an immutable array published by compare-and-swap and reset with the memo. A hand-written job opts in by setting
`OneQuery`.

**Why.**
- **Comparing filters was the bulk of a small system's pass.** A profile of a system over a few rows showed the
  memo's `SameQuery`, a compare of filters of about 200 bytes against each way, ahead of the rows themselves.
- **The key is safe because it is a constant.** `OneQuery` is a JIT-time constant of the job type; a job that is
  false takes the memo as before. The tick (`Since`) and the slice vary per run, but they are not part of the match.
- **No new invalidation.** The kept entries hold the same cache entries the memo does and are emptied with it
  (`RemoveTypes`, `ClearArchetypes`), so a table added later reaches them as it reaches the memo.

**Considered.**
- **Hashing the filter:** still reads all of it on every pass.
- **Keying by call site:** for generated code the job type is the call site.
- **`OneQuery` by default:** a hand-written job type run with different filters would get the tables of the first.

## D105. Passes on the owner thread take the gate with plain stores [#d105-owner-thread-passes]

**Decision.** `ForEach`, `ForEachBatch`, `ForEachMasked` and query walks on the owner thread freeze the structural gate
with `FreezeAlone` and count the pass with `BeginPassAlone` when nothing holds the gate: plain stores, no locked
instruction. When the gate is held or frozen already, they take the atomic forms. The parallel runner's claim cursor
sits alone on a cache line, and each participant adds its sums once when it leaves.

**Why.**
- **No other thread touches the flag then.** The threads of a stage or of parallel chunks run only inside a region
  the owner opened, so while the gate is free on the owner thread a locked instruction orders nothing.
- **A pass is the unit users repeat.** A system of a few rows runs several passes per update; an atomic
  read-modify-write per pass was a fixed cost on each.
- **The cursor is the one contended word.** On its own line, the threads that claim chunks do not invalidate the
  line that holds the job.

**Considered.**
- **Always atomic** (the previous form): correct, and the cost of each pass.
- **No freeze for passes that cannot change structure:** a job's `Execute` could still call a structural change, and
  the freeze is what turns that into an exception instead of torn tables.

## D106. The runtime synchronizes with a `Lock` or a compare-and-swap, never a locked object [#d106-lock-or-cas]

**Decision.** Where the runtime synchronizes, it takes a `System.Threading.Lock` (cold, process-wide registries:
component types, systems, interned filters), a compare-and-swap gate where the threads of parallel work enter at
once (the helpers' queue, the buffer and record pools: [D128](#d128-spin-gates-and-settled-measurements)), or swaps an
immutable array by compare-and-swap (the query cache, the query memo and the queries kept per job type). The memo's writer reads the
array, looks up its cache entry after that read, and publishes its copy with `Interlocked.CompareExchange` against
the array it read, retrying from the start when another writer or a reset got there first. A reset drops the stale
cache entries first, then swaps in an empty array with `Interlocked.Exchange`. Nothing locks a plain object.

**Why.**
- **`Lock` is the lock .NET 9 made for this.** A `lock` statement over one compiles to `Lock.EnterScope`; a
  `lock (object)` takes the object's monitor, whose state moves into a sync block when contended.
- **Readers never wait.** Queries run on any thread; an immutable array read with `Volatile.Read` is always whole.
- **The order makes a reset safe.** A writer that read the array before a reset fails its compare-and-swap and
  retries on the empty array with an entry looked up again, so a stale entry is never published again; one that
  published before the reset is wiped by it.

**Considered.**
- **A lock around the memo's writers:** a parallel stage's threads reach the memo on a first query, and would queue
  there.
- **`ReaderWriterLockSlim`:** heavier when uncontended, and the readers need no lock at all.

## D107. `[ForEach]` and hook methods are not reported as unused [#d107-never-used-warnings]

**Decision.** A `DiagnosticSuppressor` in the package hides IDE0051 (EECSS01) and IDE0052 (EECSS02) on `[ForEach]`,
`[ForEntity]`, `[OnCreate]`, `[OnUpdate]` and `[OnDestroy]` methods. The attributes carry JetBrains'
`[MeansImplicitUse]` (an internal copy, which Rider and ReSharper read by name), `[EcsSystem]` with `WithMembers`.

**Why.**
- **The generated code calls them by name.** It reaches them through `UnsafeAccessor`
  ([D16](#d16-no-partial-generated-code-lives-outside-the-users-type)), which the IDE does not see as a use, so every
  private method of a system showed as dead code, and the IDE's fix deletes it.
- **Exactly these methods.** The suppressor checks the attribute through the same `Symbols` test the generator uses;
  a private helper that nothing calls is still reported.
- **Two IDE families, two mechanisms.** Roslyn hosts (Visual Studio, the C# extension of VS Code, `dotnet build`) run
  suppressors; Rider and ReSharper run inspections of their own and read the JetBrains annotation.

**Considered.**
- **Making the methods public:** a system's methods would be callable from everywhere, which EECS008 forbids.
- **`[SuppressMessage]` or `.editorconfig` in each project:** written by every user, and too wide.
- **A reference to `JetBrains.Annotations`:** a package dependency for one attribute that the IDE matches by name.

## D108. Native AOT: the instruction set is the program's choice, `native` in the templates [#d108-aot-instruction-set]

**Decision.** The `easyecs` template, the server samples and the Native AOT test set
`<IlcInstructionSet>native</IlcInstructionSet>`. The FAQ and the hosting guide tell a server to set it, or a level
such as `x86-64-v3` (AVX2) or `x86-64-v4` (AVX-512) for a fleet. The package sets nothing.

**Why.**
- **The default baseline compiles out the wide tier.** Native AOT compiles hardware checks to constants for its
  target; at the default baseline `Vector512` is not accelerated, so the `Vector512` tier of generated vector loops
  is removed and `Vector<T>` is 16 bytes. Under the JIT the same checks are decided at run time.
- **`native` fits a binary built where it runs.** The samples and the CI test publish and run on one machine.
- **A level fits a fleet.** A binary built on an AVX-512 machine with `native` does not run on one without it; a
  level states the contract every machine meets.

**Considered.**
- **Leaving the default:** the AVX-512 loops never run under Native AOT.
- **Setting it in the package's build files:** a library would choose the CPUs its users' programs run on.

## D109. A `[View]` is one entity's components with the methods that use them, taken as a parameter [#d109-views]

**Decision.** A `ref struct` marked `[View]` declares a view of one entity: an instance field per component, `ref`
for one it writes, `ref readonly` for one it reads and `Mut<T>` for a tracked one it writes on some rows, and the
business methods over them.

```csharp doccheck=skip
[View]
public ref struct Fighter
{
    public ref Health Health;
    public ref readonly Armor Armor;

    public readonly bool Dead => Health.Value <= 0;
    public void TakeDamage(int damage) => Health.Value -= Math.Max(0, damage - Armor.Value);
}

[EcsSystem]
public ref struct Poisoning
{
    [ForEach] static void Tick(Fighter fighter, in Poison poison) => fighter.TakeDamage(poison.PerTick);
}
```

- **A parameter.** A `[ForEach]` or `[ForEntity]` method, or a lambda pass (`world.ForEach(static (Fighter f, in
  Poison p) => f.TakeDamage(p.PerTick))`), takes the view by value. The method visits the entities that
  have every component of the view. The generated job builds the view over the row (`new Fighter { Health = ref c1,
  Armor = ref c2 }`, `Unsafe.Add` of the run's refs in a batch job). The view's fields count as the method's own
  `ref` / `in` parameters would: the system writes `Health` and reads `Armor` for the schedule, and a tracked
  component behind a `ref` field is stamped on every visited row, one behind a `Mut<T>` field only on the rows written
  through `Write()` or a `SetIfChanged` that changed it (as a `Mut<T>` parameter, D66). EECS053 follows writes through
  view members: a `ref` field of a tracked component that a method, or a view member, writes on some paths only is
  reported, with `Mut<T>` as the fix.
- **From an entity.** The generator writes `entity.AsFighter()` (throws when a component is missing, as `Get` does)
  and `entity.TryGetFighter(out Fighter fighter)`.
- **What a view may hold.** EECS098 rejects a view that is not a ref struct, is generic, holds a value or a ref of a
  non-component, hides or makes `readonly` a field the generated code sets, writes an indexed component (the index
  would miss the write: `ref readonly` reads it), covers a component twice, or covers none or more than nine.
  EECS099 rejects a method that reaches a component through a view and through a parameter or another view: two
  refs to one column, one perhaps read-only. EECS100 (Warning) reports a view member that takes or uses the `World`,
  an `Entity`, an `EntityId`, a `Lookup` or another view, or keeps static state. EECS101 (Warning, with a code fix)
  reports a view built by hand from a method's component parameters (fix: take the view as the parameter) or from
  one entity's components (fix: `entity.AsX()`).

**Why.**
- **The same lines in every system.** A fighter's rules (the armor formula, what dead means) were written again in
  each system that touches health and armor. In a view they are written once, and the systems stay one job each.
- **It stays ECS.** The view holds no state (only refs into the row) and runs no logic of its own; systems decide
  when its methods run, and the scheduler sees exactly what each system reads and writes. A view is how a method
  names a group of its parameters, not an object.
- **No cost.** The view is a ref struct of refs that the JIT keeps in registers: `ViewBenchmark` measures a pass
  taking a view against the same pass taking the refs. Over 100,000 movers (AVX-512, two rounds at load 2-3): 24.7 / 24.0 μs
  by the refs and 25.0 / 25.4 μs (±2.1 μs) through the view, within each other's error. With `SimdMode.Off`,
  97.4 / 96.1 μs by the refs and 93.0 / 94.9 μs through the view (its scalar tail is inlined). One entity at a
  time, 1,000 calls: `Get` / `Read` 8.2 / 8.2 μs, `AsMover()` 7.9 / 9.7 μs (±1.9 μs). 0 B everywhere. The Tier1 vector loop
  bodies of the two passes are the same instructions.

**Considered.**
- **Names.** *View* is the database sense: a named projection of one row's columns that reads and writes through to
  them. Unity's *Aspect* is the closest idea, and Unity deprecated it in Entities 1.3; Bevy's `#[derive(QueryData)]` struct and Flecs' and Arch's typed
  queries declare the components of a query, not methods on one entity. EnTT and Friflo use *view* for the query
  itself; here a query is a filter and a pass, so *view* is free for the row. *Facet* and *Role* were rejected: a
  facet is a filter in search engines, and a role is a permission.
- **`AsX()` beside `TryGetX(out x)`.** `TryGetX` is .NET's Try pattern and the name of a component's generated
  `TryGetHealth`. The throwing form is `AsX`, not `GetX`: a view is not stored on the entity, it is built over the
  entity's components, as `AsSpan()` builds a span over an array, and `GetX` would read as a component named `X`.
- **A class or an interface on components.** Methods on a component see only that component; a class holding the
  entity allocates and hides the schedule. Default interface methods box.
- **Generating the view from a list of components** (`[View<Health, Armor>]`): the read/write choice and the field
  names are the user's to write, and a ref field says both.

## D110. A method calling a view's members gets the vector loop of the same code over parameters [#d110-vector-loops-through-views]

**Decision.** A `[ForEach]` method that takes a view is vectorized as if its view's fields were parameters: before
the vector loop is translated, the method is rewritten with one parameter per view field, a call of a void view
method becomes its body (its parameters as locals), and a field, a single-expression getter or a value-returning
single-expression method becomes the expression over those parameters. The rewritten method is bound in a copy of its
syntax tree, and `Kernel` translates it as it translates any method. A view with a `Mut<T>` field keeps the scalar loop, as a `Mut<T>`
parameter does, and so does a lambda pass taking a view (EECS097 says so): its body has no declaration to inline the
members from, and a `[ForEach]` method taking the same view gets the loop. When a member cannot be inlined (a loop, a
`return` in the middle, a lambda, a member of another type that is not static, recursion past eight levels), the
method keeps the scalar loop and EECS055 / EECS056 name the reason.

**Why.**
- **A view must cost nothing, the vector loop included.** A method over components that qualified for a vector loop
  would lose it the day its code moved into a view, which would make views a cost. Inlining gives `Kernel` the same
  method it would see without the view. `ViewTests` checks that the view, the scalar method and the refs by hand
  write bit-identical positions, and that 1 and 4 threads agree.
- **One translator.** `Kernel` already knows every vector form; teaching it member calls would duplicate it.

**Considered.**
- **Vectorizing view members on their own** (a vector form per member): the member's lanes depend on the caller's
  other parameters and filters, so each caller would need its own copy anyway.
- **Scalar loops for view parameters:** simpler, but a hidden cost of a feature meant to be free.

## D111. A `[Prefab]` declares a prefab as the components it starts with [#d111-prefab-declarations]

**Decision.** A partial struct marked `[Prefab]` declares a `Prefab` at compile time: one field per component, each
field's initializer its default. The generator writes `X.Prefab`, a `static readonly Prefab` built once from those
defaults (one `Prefab.Set` per nine components), and the parameterless constructor field initializers need (unless
the struct declares one). Creation is `Instantiate`, as for any prefab:

```csharp doccheck=skip
[Prefab]
public partial struct Goblin
{
    public Health Health = new(30);
    public Position Position;
    public Speed Speed = new(2f);
    public IsGoblin Tag;                                                  // what systems filter on
}

var goblin = world.Instantiate(Goblin.Prefab);                            // the defaults
var fast = world.Instantiate(Goblin.Prefab, new Speed(9f));               // only what differs
world.Instantiate(Goblin.Prefab, wave);                                   // a span, at once
var boss = new Prefab(Goblin.Prefab).SetBuffer(new Drops(7));             // a variant
```

EECS102 rejects a declaration the generator cannot write (not partial, generic, a ref struct, a property, ref or
non-component field, a `DynamicBuffer<T>` field, a component twice, none, or a member named `Prefab`).

**Why.**
- **A kind's components and defaults were repeated at every creation.** The goblin of a spawn system, a test and a
  tool drifted apart; declared once, a creation states only what differs.
- **One way to create from a recipe.** `Instantiate` already writes the prefab's values and the given ones into the
  final table in one row copy, takes a span, and a prefab already has variants, buffers and members. A declaration
  that only builds the prefab adds none of that again.
- **No filter.** A declaration's components match entities of other kinds that happen to have them too. A kind that
  systems must find declares a tag component, which every filter can name.

**Considered.**
- **`[Archetype]` with `world.CreateX()` / `CreateXs(span)` and `X.Filter`, dropped.** "Archetype" is the table of one
  component combination (the glossary, `DescribeTables`), so the name would mean two things; the filter matched every
  entity with those components, not that kind; and the creation calls duplicated `Instantiate` without its variants
  or buffers. A Warning for a `CreateEntity` that lists a declaration's components was dropped with it: the
  replacement is no faster, and the same components are often a different kind.
- **Methods of a declaration as systems** (an object of a kind with an `Update`): logic would live on a kind of
  entity instead of on the data it reads. Logic stays in systems; a `[View]` is how a system names the components it uses.
- **A generated view over a declaration's components, dropped.** It would write every component, so every system
  taking it would write all of them: tracked components stamped on every row, and systems that touch disjoint fields
  serialized into separate stages. A user's `[View]` states what each system writes.
- **Bevy's *Bundle*:** a set of components inserted together, without defaults; a prefab already is the recipe.

## D112. A lambda pass is compiled at its call into the job of a `[ForEach]` method [#d112-lambda-passes]

**Decision.** `world.ForEach(dt, static (ref Position p, in Velocity v, float dt) => p.Value += v.Value * dt)` and
`world.ForEachParallel(…)` run a pass written inside a method. The core declares the calls with a `Delegate` last
parameter and up to four values before it, and throws when it is reached. The generator intercepts every call it can
compile (a C# interceptor, `[InterceptsLocation]`, written per file into the namespace `EasyEcs.Generated`, which the
package's build file adds to `InterceptorsNamespaces`). The interceptor runs the struct job a `[ForEach]` method with
the lambda's parameters and body gets, with the same filter, access, reductions and vector loop. The lambda's
attributes are its filters (`[With<T>]`, `[Without<T>]`, `[WithAny<T>]`, `[Changed<T>]`, `[Removed<T>]`). A change
filter looks back from a tick passed first, which the lambda does not take: `world.ForEach(since, [Changed<Health>]
static (in Health h) => …)`, as a runner method takes `since`. A call the generator cannot compile is an error
(EECS095), so the throw is never reached in code that builds clean.

**Why.**
- **A pass used once in one method does not need a name.** A `[ForEach]` method lives in a type of its own, away
  from the code that runs it; a pass that belongs to one handler reads better where it runs.
- **One job form, so one speed.** The lambda is compiled by the code that compiles `[ForEach]` methods, so it gets
  the same job and the same vector loop (`Kernel` takes the lambda's body as it takes a method's). It is not a
  second, slower way to iterate.
- **Interceptors are source only.** The call stays plain C#; the generated file replaces it at compile time. No
  reflection, nothing at run time, Native AOT unchanged.

**Considered.**
- **`foreach (var (p, v) in world.Query<P, V>())` compiled into a job:** a `foreach` is a statement, not a call, so no
  interceptor can replace it; rewriting it would need the user's code to change, which generators cannot do.
- **Unity's `Entities.ForEach`:** a lambda compiled by an IL post-processor, deprecated by Unity for its compile
  times and its many special cases. Interceptors keep the compiler's own pipeline, and the rules here are those of
  `[ForEach]` methods, nothing more.
- **Change filters looking back from the system's last run:** a pass written in a method has no system, so no
  `LastRunTick` of its own. The caller knows which tick it means (a system's `LastRunTick + 1`, a tick it saved), so
  it passes that tick first; a filter without one is EECS095.
- **`Maybe<T>`, tiles and spans:** refused (EECS095); they need the batch and masked job forms, which a lambda does
  not take yet.

## D113. A lambda pass is static; the values it reads are passed before it [#d113-lambda-values-not-captures]

**Decision.** The lambda must be `static`. A value it needs from the method (`dt`, a rate) is passed before it and
taken as a parameter after its components, in order: `world.ForEach(dt, static (ref P p, float dt) => …)`. The job
holds the values as fields, as it holds a `[ForEach]` method's values. A capturing lambda is EECS095, with a fix that
passes what it captures (locals and parameters it only reads, up to four values).

**Why.**
- **An interceptor cannot skip an argument.** The call's arguments are evaluated before the interceptor runs, so a
  capturing lambda allocates its closure and its delegate on every call
  ([D18](#d18-no-interceptors-for-query-calls-filters-carry-no-references)): measured 88 B per call, the cost
  `[ForEach]` exists to remove.
- **A static lambda's delegate is cached by the compiler.** Passing it costs a static field read, nothing allocated.
- **The values are the job's fields.** A value passed before the lambda is what a `[ForEach]` method's value
  parameter is; the job reads it from a register, not through a closure object per row.

**Considered.**
- **Reading the captured variables out of the closure:** the closure is allocated before the interceptor sees it.
- **Allowing captures with a Warning:** 88 B and a delegate call per row behind a call that looks free.

## D114. The lambda's body is copied into the generated file; a body that cannot be runs through its delegate [#d114-lambda-body-copied]

**Decision.** The generator copies the lambda's body into the method its job calls, with every type, namespace and
static member qualified and constants written as their values (a private constant too). A body that names what code
in another file cannot reach (a private or protected member of the type around the call, a file-local type, a type
parameter) runs through its delegate instead: the job calls the static lambda, kept in a static field, once per row,
with no vector loop. That case is a Warning (EECS096), with a fix that makes a private member declared in the same
file internal. A copied body that stays scalar is reported with its reason (EECS097, Info), as EECS055 reports a
method's.

**Why.**
- **A copied body is a `[ForEach]` method.** The JIT inlines it into the job's row loop and `Kernel` turns it into a
  vector loop; a delegate call per row is neither.
- **The fallback keeps the code working.** A private helper is common; the call still runs, the warning says what it
  costs and how to remove the cost.

**Considered.**
- **An error for an unreachable body:** a correct call refused for its speed.
- **`UnsafeAccessor` for private members:** fields and methods only, not types, and one accessor per name.

**Numbers.** BenchmarkDotNet, two rounds (load 2.2 and 2.8 when they started), one pass over 1,000 / 100,000
entities, the [ForEach] method, the lambda pass and the hand-written job, 0 B every way (`LambdaPassBenchmark`):
- **Scalar body** (an integer division): method 2,155, 2,177 ns / 220.6, 209.2 µs; lambda 2,155, 2,139 ns / 219.1,
  208.3 µs; hand-written job 2,094, 2,107 ns / 211.1, 210.2 µs. One speed, within the error.
- **Vector body** (a multiply-add): method 68.4, 71.6 ns / 11.7, 11.5 µs; lambda 72.0, 69.9 ns / 11.7, 11.2 µs; the
  hand-written job, one row at a time, 787, 759 ns / 74.7, 77.7 µs.
- **The machine code** of the lambda's job at Tier1 (`tools/jitdisasm.sh`) is the method's: the same vector loop,
  no call in it.
- **The generator** (`GeneratorBenchmark`, base against this change, two rounds, interleaved): `EditMethodBody`
  207.5, 211.3 -> 226.3, 224.3 ms and 195.7, 201.5 -> 241.9, 190.8 ms (one namespace), all within the error of
  25 to 52 ms, 0.1 to 0.3 MB more per edit; `CompileAndAnalyze` within the error, 2 % more allocated with one
  namespace (993 -> 1,012 MB).

## D118. EECS055 warns when the method can be rewritten; EECS091 names the fields a frequent pass never touches [#d118-fixable-reasons-and-cold-fields]

**Decision.** Each reason `Kernel.Vectorize` gives for a scalar method is marked where it is raised as fixable (the
user can rewrite the method without changing what it computes, and the reason names the rewrite) or inherent (what
the method computes stops the loop). EECS055 reports a fixable reason as a warning and an inherent one as a
suggestion, through one descriptor whose severity is chosen per report; EECS056 (`SimdMode.Require`) stays an error
for both. Fixable today: the few fields a method uses of a wide or mixed component (split them out), a `ref` local
(name the parameter's fields), a local without a value, fields declared in several parts, a reduction field that is a
property or `readonly`, a method that is not static. A new rule, EECS091 (warning, at the end of the compilation),
reports a component of 32 bytes or more whose untouched fields are at least half of it: the fields that no frequent
`[ForEach]` pass touches, with the passes and the fields to move. A pass is frequent unless its system has
`[UpdateInterval]` above 1, or the method visits changed rows only (`[Changed<T>]`, `[Removed<T>]`) or a slice
(`Slices`). A split is the form the project pushes, so both rules carry a code fix that writes it: the layout stays
the user's ([D90](#d90-vector-loops-reach): nothing moves on its own), the fix writes it for them when they apply it.
It declares the new component next to the old one (named after it and its first moved field, `BodyName`, for the user
to rename), removes the moved fields from the old one and rewrites every use across the solution: a `[ForEach]`
parameter that reads only moved fields takes the new component, one that reads both gains it with the same access
(`in`, `ref`, `Mut<T>`, `Maybe<T>`, a span), creations and `Set` give both values, `Remove` removes both,
`entity.Body.Name` and `entity.Get<Body>().Name` read the new component. It is offered only when the program does
what it did after it: not for a component used whole (copied, passed to a helper, bound to a `ref` local, queried
with `Query<T>`), read by its own members, tracked, given a constructor or a layout, saved by a world (the saved
format would change without a migration), or taken by a `[ForEach]` method something calls directly; then the
message says which fields to move, and the user moves them.

**Why.**
- **Users miss suggestions.** A method left scalar for a reason the user can fix in one line was reported as a
  suggestion; the fixable reasons now fail a build that treats warnings as errors, and the message says how. A
  suggestion is left for what the method needs: a call, integer division, a conversion, a float sum in another order,
  a `Maybe<T>` in a parallel method.
- **One place decides.** The flag sits on the reason where `Kernel` raises it, so the generator and the analyzer keep
  reading one function: a method skipped by the generator is a method reported, as before, now with a severity.
- **What was left inherent, and why.** A `bool` field: the fix is a byte or a tag, and a tag flipped every update is
  a structural change per flip, worse than the scalar loop. A value taken by `ref` outside a system: in the samples it
  is as often a running index (the demo's frame writer) as a sum, so a `Reduce<T>` is not the same method.
- **A pass reads whole rows.** A `[ForEach]` pass walks the column of each component it takes; the fields its method
  never names come into the cache with the ones it does. `HotColdBenchmark` (100,000 rows, a pass reading and writing
  8 bytes of each row, both forms scalar so only the memory differs; 4 cores, AVX-512): a row of 16 bytes 56.8 µs
  against 48.9 µs with the cold fields in a component of their own, 32 bytes 132.5 against 50.6 µs, 64 bytes 261.6
  against 50.4 µs, 128 bytes 508.0 against 48.8 µs, 0 B each. The split pays from 32 bytes on, by 2.3 to 2.6 times there over two rounds (the second: 118.6 against 50.9 µs);
  at 16 bytes the gain is within what a second component costs elsewhere, so the rule starts at 32 bytes and asks
  for at least half the row to be cold.
- **The rules cost no measurable build time.** EECS091 reads the [ForEach] bodies the performance rules already walk, and EECS092 the
  operations of the compilation once. `GeneratorBenchmark` (the analyzer over the battle server and modules, its time
  being `CompileAndAnalyze` less `Compile`): 0.93 s before and 1.02 s after in one namespace, 1.26 s and 1.12 s in
  many, each within the error of 0.11 to 0.44 s.
- **One mistake, one diagnostic** ([D60](#d60-one-diagnostic-per-mistake)). When EECS055 already advises to split
  the fields a pass uses out of a component, EECS091 leaves that component to it; a method kept scalar with
  `SimdMode.Off` gets no EECS055, so EECS091 reports its component.

**Considered.**
- **Two rule ids, a warning and a suggestion:** two ids for one reason list, and a reason moving between them would
  change its id. One id, two severities, as EECS069 does.
- **Reporting every component a pass leaves fields of:** a 12-byte component with a 4-byte field read once a minute
  costs nothing measurable; the threshold keeps the rule to rows where the cache lines show.
- **Moving the fields automatically** (`[Hot]` / `[Layout(Soa)]`): dropped in [D90](#d90-vector-loops-reach); the
  split changes every reader of the moved fields, which the user sees in the fix's diff before applying it.
- **Leaving the split to the user, no fix:** the split is the faster form (a column of only the fields the pass reads,
  and a component few enough fields for a vector loop), and the rewrite is mechanical once every use is one of the
  forms above; a fix that refuses the rest keeps it exact.

## D119. No code fix from object-oriented classes to components and systems: a migration guide [#d119-no-oop-code-fix]

**Decision.** There is no code fix and no analyzer hint that turns a class with fields and an `Update(float dt)`
method into components and an `[EcsSystem]` with a `[ForEach]` method. The public skill that users' AI agents
follow (`skills/easyecs/SKILL.md`) has a section that maps each object-oriented form to its ECS form: a class to components, an
instance to an entity (a prefab), a method to a system, inheritance to composition and filters, a reference to an
`EntityId` (a `Lookup<T>`, `ChildOf`, a relation or an index), an event to records (`Emit<T>`) or a tracked write, a
manager singleton to a singleton component, and services to the host.

**Why.**
- **No shape is always correct.** The smallest case, a class of two floats and `Update(float dt)`, already needs a
  singleton for `dt` that the host must set, turns a reference type into a value type (code that shares one instance
  between two holders would copy it), and leaves the callers (`new`, the list the loop walks, `foreach … Update`) to
  change by hand. Inheritance, virtual methods, references to other objects and events have several right answers each.
- **A hint without a fix is noise.** A warning on every class with an `Update` method would fire on code that is not
  game state (a UI widget, a network client) and say only "rewrite this".
- **The judgment is what an assistant does well.** The guide gives it the mapping and the rules to check against
  (EECS006, EECS007, EECS017, EECS091, EECS092), and the analyzer then checks the result.

**Considered.**
- **A fix limited to a class with only value fields and one `Update` method:** still changes reference semantics at
  every use of the class, and the callers stay broken; not always correct, so not offered.

## D120. Not added: `[Feature]` modules and a generated reader of records; EECS092 reports records nothing clears [#d120-feature-modules-and-data-events]

**Decision.** Two generator ideas were weighed and left out. A third finding became a rule: EECS092 (warning, at the
end of the compilation) reports an `Emit<T>` whose records no code of the compilation clears (no `Clear`, `RemoveAt`
or `RemoveAtSwapBack` of a `DynamicBuffer<T>`, no `RemoveSingleton<Emitted<T>>()`, no assignment of `Emitted<T>` or its
`Items`), once per record type, unless the record type is public in a library (another assembly may clear it).

**Why.**
- **`[Feature]` modules** (a feature's components, systems, groups and setup registered together, `world.AddFeature<Water>()`).
  Registration order is the tick's order and builds the parallel stages from consecutive systems
  ([D56](#d56-not-added), [D76](#d76-stages-not-a-dependency-graph)). The VoxelServer sample registers 37 systems
  with features interleaved on purpose (the water's steps between the zombies', so systems with disjoint data share a
  stage); a module per feature would either fix one order per feature, losing those stages, or need the order spelled
  out again. The setup a feature has besides its systems is already declared on its types (`[GroupBy]`,
  `[WhenTargetDestroyed]`, `[NotSaved]`, [D101](#d101-declaration-attributes)), so a module saves the `AddSystem`
  lines only, and those are the schedule's documentation.
- **A generated reader of records** (a hook parameter that hands the system `Emitted<T>` and clears it after the
  hook). `Emit<T>` and `Emitted<T>` already give the buffer per event type and the emitting side
  ([D78](#d78-emit)). What users write by hand around events is the reader: in the battle server, the VoxelServer
  sample, the Actors sample and the threading guide, each reader is a `GetOrAddSingleton<Emitted<T>>().Items` line, a
  loop and a `Clear()`. A parameter would save one or two lines per reader and add a hook parameter kind, its schedule
  access and its docs; the readers differ in what they do (count, send, save through the host outside any system).
  The line that matters is the `Clear()`: without it every update applies the earlier records again and the list
  grows, a mistake the common-mistakes page documented with "no rule catches it".
- **The compilation sees every clear.** One system emits and another clears, so no single method shows the mistake,
  but at the end of the compilation the analyzer has every `Emit<T>` and every clear. A record type public in a
  library is left alone: a plugin's host may apply and clear its records.

**Considered.**
- **Clearing in the runtime after each update:** a reader that runs at another cadence (a send every third update,
  a save group) would lose records, and the reader is the one that knows when they are applied.
- **A reader system generated per record type:** one more system the schedule places by itself, where the user
  writes the order.

## D122. A structural change under a condition marks rows; the change is applied in bulk after the pass [#d122-marked-rows]

**Decision.** A `[ForEach]` method that changes its own entity under a condition gets a vector loop:

```csharp
public record struct Kill(EntityId Victim);

[EcsSystem]
public ref struct DyingSystem
{
    [ForEach, Without<Dead>]
    static void Die(Entity unit, in Health hp, Emit<Kill> kills)
    {
        if (hp.Value > 0) return;
        unit.SetDead();
        kills.Add(new Kill(unit.Id));
    }
}
```

- **The condition is a lane mask, and the change marks rows.** The loop computes the mask per vector and records the
  rows that pass as bits of 64-row words (`MarkedRows`, pooled per world). When the pass ends, one call applies the
  change to them: `SetAll`, `RemoveAll`, `DisableAll`, `EnableAll` or `DestroyAll`. A table whose rows change in place
  (a column it has, a removal that keeps the column) takes a word at a time; the others go row by row.
- **In the method's order.** The marked rows are visited from the first table to the last, rows ascending, inside a
  pass of their own: a row that moves leaves a tombstone as it would during the method's pass, and the tombstones
  close the same way. Every table ends with the rows the method would have left, in its order, so later passes visit
  and emit in the scalar method's order, and ids are freed (and the destroy log written) in its order. A table whose
  every row is destroyed is freed at once, its ids in row order.
- **Records.** `Emit<T>.Add(new T(x))` appends the passing lanes' `x` (a lane of the method, or the entity's id),
  compacted with `Lanes.Compact`, in row order.
- **Every row takes the vector form.** The rows after the last whole vector are copied into a vector's worth of rows
  (`Interleaved.LoadTail` / `StoreTail`) and run masked. Hardware without the loop's vectors runs the method's own
  job one row at a time; the choice is a JIT-time constant (`Vectorizes`).
- **Recognized by meaning.** `Symbols.StructuralChange` reads the generated members (`SetDead()`, `RemoveX()`,
  `SetX(args)`), the generic forms (`Set<T>(...)`, `Set(new T())`, `Remove<T>()`, `Disable<T>()`, `Enable<T>()`) and
  `Destroy()`, for the generator and the analyzer alike. `unit.Set<Dead>()` keeps its EECS033 warning.

**What stays scalar.** These are the reasons EECS055 and EECS056 report. A fixable reason names the fix.
- **The method takes the component it changes** (as a parameter, a `Maybe<T>` or a `Mut<T>`). The method would see
  the change at once; the loop applies it after the pass. *Fixable:* change it in a method of its own.
- **Two different changes, or a value that differs per row** (`SetH(hp.Value)`). The loop marks one change of one
  value. *Fixable:* write one method per change, or set a tag here and the value in a method over the tag.
- **Another use of the entity** (`entity.Has<T>()`, `entity.Id.Index`, `Clone()`). *Fixable:* read it as a
  parameter or a filter.
- **A branch the loop cannot express** (a call, `Console.WriteLine`) in a method that changes structure. Such a
  branch would run the method during the pass, which is frozen. *Fixable:* move the branch into a method of its own.
- **A destroy together with an `Emit<T>` or a `Reduce<T>`.** A destroy cascades to children the pass has not reached
  yet. *Fixable:* emit or reduce in a method over a tag.
- **A unique key** (`Set` or `Enable`). One value would be claimed by every row. Inherent.
- **`[Consume]`, a `Maybe<T>`, lanes of 1 or 2 bytes, a wide component.** Their words of passing rows run the method
  itself. Inherent.

**Why.**
- **The cost per row was the structural call, not the condition.** A scalar structural pass pays an entity handle, a
  lookup and a row move or a bit flip for each row that passes, and its condition has no vector form. Marking moves
  the condition into the vector loop and the change into the bulk walk that `SetAll` already uses.
- **The same results, not only the same sets.** Applying the changes in the method's order inside a pass keeps each
  table's row order, the order ids are freed in and the destroy log. `StructuralLoopTests` compares a vector world with
  its scalar twin over random rows: 0 to 10,003 rows, every row passing, no row passing, a table emptied, and rows
  moved by another method in the same tick. Every entity, every record in order, the index and the destroy log match.
  Steady updates allocate 0 B.
- **Measured** (`StructuralLoopBenchmark`, on an AVX-512 machine). A tag is set on the rows of one table that pass at
  the given rate, then lifted from all of them by the same `RemoveAll` in every case. The tag's column stays in the
  table, so a set flips presence bits: the case of a status that comes and goes. `CommandBuffer` records the ids and
  sets each after the pass; `SetAll` is the bound of a bulk change whose rows are already tagged. Two rounds, first /
  second; all four allocate 0 B.

| Rows | Pass | Scalar | Vector | CommandBuffer | SetAll |
| --- | --- | --- | --- | --- | --- |
| 10,000 | 1% | 11.72 / 11.17 µs | 1.00 / 1.04 µs (0.09×) | 8.64 / 8.97 µs | 0.18 / 0.19 µs |
| 10,000 | 10% | 44.23 / 42.40 µs | 1.43 / 1.52 µs (0.03×) | 18.54 / 19.33 µs | 0.40 / 0.39 µs |

**Considered.**
- **Changing rows during the pass** (a call per row from the vector loop): the pass is frozen, and that call is the
  cost to remove.
- **Recording ids** (a command buffer) and changing them after the pass: a lookup per id, and a buffer that grows with
  the rows; the `CommandBuffer` case measures it.
- **Applying from the last row down** (the swap-remove order of the bulk calls, no pass of their own): the rows that
  move land in their new tables in reverse, so later passes would emit in an order other than the scalar method's.
- **Several changes per method:** each would move rows the other's marks name. One method per change is clearer and
  costs one more walk over the marked rows.

## D125. Passes that merge per chunk cut 16 chunks; the helpers' spin, the partitioner and the chunk size stay as they were [#d125-scheduler-tuning]

**Decision.** A parallel pass that merges per chunk (a `Reduce<T>`, an `Emit<T>`) and sets no `ChunkSize` cuts its
rows into 16 chunks of 1,024 to 16,384 rows, from the row count alone; the threads only share them out. Other passes
keep about four chunks per thread. Four scheduler changes were measured and left out: helpers that spin only while
work is near, one spinning helper at a time, an affinity partitioner, and a tuner of the chunk size.

**Why.**
- **A float reduction gave different bits at different thread counts.** Each chunk's partial result is rounded on
  its own and the chunks are combined in order ([D69](#d69-reductions)), so the result depends on where chunks begin,
  and those followed `MaxDegreeOfParallelism`. A server whose tick sums a float (a mass, a center) got another total
  on a 2-core and an 8-core machine. 16 is four per thread at four threads, what the old rule cut there; from 262,144
  rows the chunks reach 16,384 rows and their count grows with the rows, enough for any thread count.
  `AFloatReductionDoesNotDependOnTheThreads` checks the same bits at 1, 2, 3, 4 and 8 threads, 50 runs each, at
  5,000, 100,000 and 400,000 rows. BDN, two rounds (base / 16 chunks, load 1.6 to 3.1 on 4 cores):
  `ReduceBenchmark.MassParallelReduce` 100,000 rows 25.2, 27.1 / 27.0, 26.6 µs, 1,000,000 rows 227, 232 / 237,
  232 µs; `SumParallelGenerated` 100,000 rows 5.9, 7.2 / 6.5, 6.3 µs; `EmitBenchmark.EmitParallel` 100,000 attackers
  95.3, 113.1 / 102.6, 106.0 µs. Level, 0 B.
- **Spinning only while work is near did not pay.** A helper that runs out of work spins up to 100 µs, then parks.
  The variant spun only while a world was inside an update or a parallel pass, or between updates that came back to
  back (a process-wide count of busy worlds and the last idle gap), and otherwise parked at once. Between the ticks
  of a server the helpers already park 100 µs after the last pass, so all it could save is 3 x 100 µs per tick: a
  60 Hz harness measured CPU per tick 2,986, 2,858 / 3,088, 2,767 µs (steering pass) and 5,345, 5,196 / 5,237,
  5,416 µs (battle server), and 0.2 to 0.4 ms per idle second either way. BDN, two rounds, interleaved:
  `ParallelSystemsBenchmark` parallel 54.8, 54.6 -> 73.8, 73.4 µs, `ParallelForEachBenchmark.Tick` parallel 553,
  569 -> 647, 701 µs (a rerun at load 3.3: 69.0, 65.7 -> 70.0, 69.6 µs and 557, 625 -> 656, 617 µs).
- **One spinning helper at a time (Go's scheduler)** saved CPU in the harness (9 to 16 % per tick) and lost the
  back-to-back passes: `ParallelSystemsBenchmark` 61 -> 72 to 82 µs, `ParallelForEachBenchmark.Tick` 465, 525 ->
  524, 663 µs, `HeavyForParallel` 100,000 records 299, 308 -> 337, 388 µs. Waking the rest from the first helper
  instead of the owner was worse (`ParallelSystemsBenchmark` 61 -> 103 to 126 µs).
- **A shorter spin** (35 µs, the .NET thread pool's `LowLevelLifoSemaphore`): `ParallelSystemsBenchmark` 69 to 84 ->
  104 to 111 µs for about 3 % less CPU per tick. The spin stays 100 µs.

**Considered.**
- **TBB's affinity partitioner** (each thread starts on the chunks it ran last time, then steals): it kept a thread's
  rows in its cache only when they fit (`LightForParallel` 10,000 records 9.3, 8.4 -> 7.0, 6.5 µs) and lost on the
  passes of 100,000 rows (`ParallelForEachBenchmark.Tick` 527, 574 -> 635, 629 µs, `EntityJob` 589, 544 -> 762,
  631 µs). The shared cursor balances better than fixed homes on a shared machine.
- **A tuner of the chunk size** (Halide's autotuning, per job type: try 1, 2, 4, 8 and 16 chunks per thread, six
  samples each, keep the least time per row, try again every 256 to 8,192 runs): no consistent win over four per
  thread, and `RunnerBenchmark.HandWrittenJob` 48, 46 -> 55, 54 µs. It could not try chunks under 1,024 rows, the
  floor of the default; a tuner that does would pick from rows (64 to 16,384) instead of chunks per thread, only for
  passes that do not merge (their boundaries must not move), and a pass that stamps a tracked component below 4,096
  rows opens its blocks first, as `ChunkSize` already does ([D67](#d67-chunk-rows)). [D130](#d130-measured-chunks)
  cuts by the measured time per row instead.

## D126. Vector loops: flat lanes for element-wise passes, the masked form starts from the rows that pass [#d126-loop-shape]

**Decision.** Two changes to the loops the generator writes from a `[ForEach]` method ([D90](#d90-vector-loops-reach)), and
three measured and left out:

- **Element-wise passes run over flat lanes.** A method whose every written field k depends only on field k of
  inputs of the same layout (`p += v`, `p = new(p.X + v.X, p.Y + v.Y)`, `c *= s`) loads and stores the columns as
  plain floats, `rows * fields` lanes, with no deinterleave. Masked words (a table with rows that lack a component)
  still take the deinterleaving loop.
- **The masked form starts its active mask from `pass`.** The rows of a masked word that pass are the first mask of
  every condition chain, so each write is one `ConditionalSelect` against them instead of a select per condition and
  one more per written column and accumulator at the end.
- **Not changed: the permutation tables.** They stay `static readonly` vectors the JIT turns into constants.
- **Not changed: the last rows of a run.** The rows after the last whole vector still call the method one by one.
- **The loads name each field once.** A deinterleaving load writes each field straight into its name
  (`out Vector512<float> __c1_0`); only a field of another type of the lane size keeps a temporary and its
  reinterpretation (`As<int, float>`).

**Why.**
- **Flat lanes.** Two-float `Move` spent 6 `vpermt2ps` and 4 table loads per 16 rows on 2 adds. BDN, two rounds
  (base / flat, ns): `KernelBenchmark.PushGenerated` 1,000 rows 174.4, 172.4 / 94.1, 98.6; 100,000 rows level
  (memory-bound: 0.85, 0.96 and 1.01, 0.98 in the first runs).
- **Masked words stay with the deinterleaving loop.** Splitting a masked word's flat lanes into per-field masks
  (a lane mask widened per field) lost: `Move2GapsGenerated` 1.06, 1.19 at 1,000 rows and 1.09, 1.07 at 100,000.
- **The active mask from `pass`.** The Tier1 code of `Cycle` (`Without<Dead>`, a masked word per table with dead
  rows) lost 7 instructions and 6 of its 44 `vpternlogd` per vector. BDN, two rounds (base / new):
  `CycleHolesGenerated` 1,000 rows 3,739.6, 3,673.9 / 2,718.3, 2,958.4 ns, 100,000 rows 377,475, 374,377 / 296,799,
  269,758 ns; `WorldSimulationBenchmark` 100,000 entities 1,320.1, 1,419.2 / 1,243.3, 1,250.4 µs;
  `MultiWorldBenchmark` 709.0, 675.9 / 629.6, 602.7 µs; `BattleServerBenchmark` 3,976, 4,130 / 3,911, 3,947 µs.
  `Holes`, `Halves`, `Optional` and `Move2Gaps` level; 0 B.
- **The tables are already loaded once per use, and must be.** In the Tier1 code each `vpermt2ps` / `vpermi2ps`
  takes its table as `vmovups zmm, [rip+const]` inside the loop. Every two-source permute overwrites one of its
  operands, so a table hoisted into a register would still be copied before each permute: the copy costs what the
  load costs (an L1 hit, off the critical path). Passing the tables into the helpers as arguments loaded before the
  loop changes nothing the JIT emits per vector.
- **A copy per field kept masked jobs out of their runner.** The JIT inlines no method that declares more than 32
  IL locals (`MAX_INL_LCLS`, reported as "too many locals"), `AggressiveInlining` or not, and then marks it noinline
  for every caller. Loading into a temporary and copying it into the field's name (`out __s1_0; var __c1_0 =
  __s1_0;`) declares two locals per field, which Roslyn keeps when the field is written later: `Move3`'s masked
  `Execute` had 36, `Move4`'s 44, so `World.Masked` called them once per 64-row word. Without the copy they have 24
  and 28 and are inlined; that is the 934 to 1,095 instructions and 36 to 54 permutes seen in `Move3`'s runner,
  whose benchmark never runs a masked word (its speed was level). In the benchmark assembly 16 jobs fall under
  the limit (25 over, 9 over after). With PGO off the masked loops already inlined gain one register move
  (`vmovaps`) per written two-field component per vector: the register allocator gives a local one register for
  both its definitions, the load and the select, so the last destructive `vpermt2ps` needs a copy; every other
  listing of `Cycle`, `CycleHoles`, `BattleServer` and `WorldSimulation` is identical. Neither the `out` (no
  stack slot in any loop) nor the IL size (590 / 638 bytes, the reason given is the locals) was the cause.
  BDN, two rounds (base / head): `Move3GapsGenerated` (Move3 over a table whose every third row lacks the velocity)
  100,000 rows 85.1, 86.0 / 80.5, 81.2 µs, 1,000 rows 695, 721 / 681, 713 ns; `Move4Generated` 1,000 rows 186.9,
  185.4 / 170.2, 172.8 ns; `Move3`, `Move2Gaps`, `Push` level; `WorldSimulationBenchmark` and
  `BattleServerBenchmark` within run-to-run spread (BattleServer six rounds each, 3.65 to 4.39 ms / 3.79 to
  4.20 ms); 0 B. The 9 jobs still over the limit run their loops in methods ([D135](#d135-inlined-locals)).
- **A masked vector for the last rows lost.** On AVX-512 the rows after the last whole `Vector512` ran as one vector
  whose loads and stores were masked to them (`Avx512F.MaskLoad` / `MaskStore` under `Interleaved.Load` / `Load2..4`
  with a row count). It won where the body is small and most rows are last rows: on a world of 1,000 tables of 5 to 20
  rows (`KernelBenchmark.Fragments*`, four runs, base / tail, µs) one float 41.6, 42.4, 32.2, 43.0 / 27.5, 23.5, 21.5,
  21.2. It lost where the body is large: `CycleGenerated` 1,000 rows 380, 385 / 567, 1,071 ns, `CycleHolesGenerated`
  1,000 rows 2,713, 2,663 / 10,004, 4,479 ns and 100,000 rows 276, 258 / 423, 412 µs, three floats deinterleaved on
  the fragmented world 54.2, 73.4, 61.5, 56.7 / 68.8, 71.4, 61.0, 70.7 µs, `PushGenerated` 1,000 rows 94.0, 91.4 /
  105.6, 100.7 ns. The Tier1 code said why: `Cycle`'s masked `Execute` declared 33 IL locals, one past the 32 the JIT
  inlines (`MAX_INL_LCLS`, "too many locals"), so the runner (`World.Masked`) called it per run, and per 64-row word in a
  masked table, instead of inlining it (`Cycle`'s runner went from 199 vector instructions to 6 and 4 calls of
  `Execute`). Retried once every job fits ([D135](#d135-inlined-locals)), with the tail a `NoInlining` method called
  once per run (a `Vector512` over a copy of the rows left, `Interleaved.LoadTail` / `StoreTail`, as the vector tail of
  a structural change), it still lost: two rounds (without / with the tail) `CycleHolesGenerated` 1,000 rows 2,736,
  2,861 / 4,437, 4,504 ns and 100,000 rows 287, 260 / 430, 431 µs, `CycleGenerated` 1,000 rows 381, 372 / 610, 604 ns,
  `HolesGenerated` 406, 393 / 614, 620 ns, `HalvesGenerated` 475, 485 / 748, 751 ns, `Move2GapsGenerated` 100,000 rows
  43.3, 41.1 / 58.1, 56.6 µs, `BattleServerBenchmark` 100,000 3,766, 3,803 / 4,155, 3,975 µs; it won only
  `FragmentsMove3Generated` 100,000 (76.6, 57.0 / 51.9, 51.4 µs). The copy in and out costs more than the up to 15 rows
  it saves; the scalar rows stay.

**Considered.**
- **The loads returning a value tuple or a struct of vectors** (`var (__c1_0, __c1_1) = Interleaved.Load2Of512(...)`):
  as many locals as naming the outs (Roslyn deconstructs with `dup`), more IL, six new methods (a return type cannot
  overload), and a 128- to 256-byte return through a hidden buffer. Reading a struct's fields in place would declare
  one local per load, but every write becomes a field store and the whole loop text changes.
- **A tail only for bodies the runner still inlines**: the generator counts the locals now (D135), and the retry above
  lost with every job inlined.
- **A file-level alias** for `global::System.Runtime.Intrinsics.Vector512` and `Vector<T>`: the generic types need
  one alias per closed type, and the loops name both widths; it would shorten the text, not the code.
- **One body for both widths** (`Vector<T>` and `Vector512<T>` from one text): needs a generic vector abstraction
  .NET 10 keeps internal (`ISimdVector`); the width the hardware lacks is removed at JIT time, so the copies cost
  build output and IL, not instructions per vector.

## D127. Vector loops lower integer division and the math .NET has vectors for, exactly unless `FloatMode.Fast` [#d127-math-lowerings]

**Decision.** A `[ForEach]` method that divides integers, or calls math the vector loop lacked, gets a vector loop
whose results are the scalar method's, bit for bit:

- **Integer `/` and `%` by a constant.** A power of two is a shift (signed: rounded toward zero by adding the sign's
  low bits first, as the C# operator does); 1 and -1 are the value or its negation. Any other constant, and a
  divisor that varies per row, divide 32-bit lanes through `double` (`LaneMath.Quotient`): an int32 quotient computed
  in double precision and truncated is exact (both operands are exact in 53 bits and the rounding error,
  below 2^-21 / |y|, cannot cross an integer). 64-bit lanes take powers of two only.
- **Lanes that would throw run the method.** A divisor of 0, `int.MinValue / -1`, `Math.Abs(int.MinValue)`,
  `int.CopySign(int.MinValue, positive)`, `Math.Sign(NaN)` in a vector send that vector's rows to the method, which
  throws as written; the rows before them keep the vector's results. A division behind `y != 0 &&` divides by 1 in
  the lanes the guard leaves out.
- **Floats.** A division by a power-of-two constant whose reciprocal is a float is a multiply (exact: both round the
  same real number); `Pow(x, 1)` is `x` and `Pow(x, 0)` is 1 (NaN lanes run the method: the C runtime's `pow` returns
  1 or NaN for NaN depending on the platform).
- **`FloatMode.Fast` only** (results within 2 ulps, `Tan` within 4 or 1e-7): `Pow` by 2, 3, 4, -1, -2 and 0.5 as
  products, a reciprocal and a square root; a division by any other constant as a multiply by its reciprocal;
  `Log10`, `Tan`, `Sinh`, `Cosh` and `Tanh` of floats through .NET's vector `Log`, `Sin`, `Cos` and `Exp` in double
  precision (`LaneMath`). Without it each is reported with its fix: "set FloatMode = FloatMode.Fast".
- **Not lowered**: `Asin`, `Acos`, `Atan`, `Atan2`, `Cbrt`, `Pow` by other exponents, the hyperbolic functions of
  doubles. .NET 10 has no vector form for them, and the generator writes no polynomial of its own: the reason says
  so.

**Why.**
- **Exact by proof, then by test.** Each exact rewrite is checked against the scalar operation over every 32-bit input
  (`LaneMathTests`, category `Exhaustive`, explicit: about 8 minutes in Release on 4 cores) and over a stride of
  them with every edge by default. The exhaustive run found one Fast-mode difference: `x * x * x` overflows to
  infinity where `MathF.Pow(x, 3)` rounds to `float.MaxValue`, 1 ulp apart.
- **`pow` is not correctly rounded**, so `Pow(x, 2)` differs from `x * x` by 1 ulp on about 1.5 million floats, and
  `Pow(x, 0.5)` from `Sqrt(x)` likewise: those belong to fast math. `Pow(x, -2)` is `(1 / x)^2`, not `1 / x^2`, which
  broke the 2-ulp bound where `x^2` is subnormal; `Log10` of a float through `Log2(x) * c` was up to 3.4 ulps off,
  through the double `Log` it is within the bound.
- **BDN, two rounds** (base, where the methods run scalar / lowered, ns): `KernelBenchmark.RatioGenerated` (`/ 7`,
  `% 8`, a float `/ 2f`) 1,000 rows 1,729, 1,764 / 746, 741, 100,000 rows 169,590, 170,118 / 72,353, 72,645;
  `ShareGenerated` (a divisor per row) 1,000 rows 4,406, 4,293 / 2,497, 2,503, 100,000 rows 436,433, 436,991 /
  257,962, 248,375. `BattleServerBenchmark` 4,115, 3,693 / 3,890, 3,757 µs; `LambdaPassBenchmark` and
  `GeneratorBenchmark` level (`EditMethodBody` 248, 212 / 216, 213 ms and 213, 204 / 223, 185 ms); 0 B.

**Considered.**
- **A multiply-high by a magic number** for constants other than powers of two (what compilers emit for scalars):
  AVX-512 has no 32 x 32 -> high 32 multiply of vectors, so it costs two `vpmuludq` and shuffles per vector against
  one conversion pair and a `vdivpd`, for the same exact result. Not tried; the division already runs at 0.43 of
  the scalar time.
- **Polynomials for `Atan2`, `Cbrt` or general `Pow`**: our own approximations would be one more thing to prove on
  every platform; the loop waits for .NET to ship them.

## D128. Parallel work's queue and pools take a spin gate; allocation tests measure once no background collection runs [#d128-spin-gates-and-settled-measurements]

**Decision.** The helper threads' queue (`Workers`), `EmitPool<T>` and the buffer pool's shared list
(`BufferStore<T>`) are entered through `SpinGate`: one compare-and-swap to enter, a plain write to leave, and a
contended thread spins on a plain read, then yields, and never blocks (the structural gate's shared flag is the same
gate). The tests' allocation measurements (`Allocations.Of`, `Allocations.Baseline`) start after a blocking full
collection, which waits for a background one that is still running.

**Why.**
- **Two things counted bytes on a thread that allocated nothing it measured.** The 0 B tests around parallel runs
  failed now and then (2,616 to 8,096 B, 56 B, 120 B, 280 B), more often on a loaded machine. A harness ran their
  worlds next to six busy threads on four cores and read the caller's allocated bytes per update and at points of
  the runner: on the base, ParallelForEachDoesNotAllocateAfterItsFirstCall and its neighbors failed 4 times in 60
  runs, and an update allocated 3,304 B at a different point each time (inside an item, between two timestamps,
  between two updates of the harness), with `MaxDegreeOfParallelism = 1` and the JIT's tiering off too.
- **A background collection voids every allocation context.** An EventPipe trace marked each update: every update
  that counted bytes overlapped the end of a background gen2 collection (reason AllocLarge, started by the large
  tables the tests create, slow to finish when its thread shares the cores). At the end of its mark phase it sets each
  thread's `alloc_ptr` and `alloc_limit` to 0 (gc.cpp, `repair_allocation_contexts(FALSE)`) and leaves `alloc_bytes`,
  so `GC.GetAllocatedBytesForCurrentThread` grows by the unused rest of the thread's context: 3,304 B in that world,
  any amount up to a few KB in another. A blocking full collection first waits for a running background one
  (`background_gc_wait`), and the measured code allocates nothing, so none starts during the measurement: the same
  harness, 120 runs, no failure.
- **A `Lock` allocates the first time a thread waits on it.** Past its spin, `Lock` blocks on an `AutoResetEvent` it
  creates then, on the waiting thread: 56 B, once per lock (280 B for the first wait of the process). The helpers'
  queue and the pools are entered by the threads of a pass at once; whenever a holder is preempted (a loaded machine)
  for the first time, the next thread to wait allocates in steady state. The sections are a few instructions, so a
  thread that finds the gate held is better off spinning and yielding than blocking.

**Numbers.** BenchmarkDotNet, the base (`Lock`) and the spin gate interleaved on the same machine, all 0 B:
- `ParallelForEachBenchmark.Tick` (100k, parallel), 8 rounds: 537 µs on the base, 531 µs with the gate (one base
  round reported 1 B per operation, a `Lock`'s wait event spread over its iterations).
- `ParallelSystemsBenchmark.Tick` (100k, parallel), 3 rounds: 55.1 µs on the base, 52.8 µs with the gate.
- `SystemDispatchBenchmark.ParallelStage`, 3 rounds: 710 ns on the base, 753 ns with the gate, both ±50 to 180 ns.
- Spinning that sleeps a millisecond after twenty spins (`SpinWait`'s default) measured the same within the noise;
  the gate never sleeps, since a holder leaves after a few instructions.

**Considered.**
- **Running a lock's first wait at start** (a thread holding each lock while another waits on it): one thread per
  lock to work around the runtime's laziness, and every new `Lock` would need it.
- **A lock-free stack for the pools** (Treiber): an ABA guard per pool for sections that hold the gate a few
  nanoseconds.
- **Retrying or tolerating bytes in the tests:** they would hide a real allocation of the same size.
- **Settling inside `SystemStats`** (a measured run that discounts a background collection): the runtime does not
  say that a collection voided a context, so a run that overlaps one shows the rest of its context in
  `LastAllocated`.

## D129. `[IndexKey]` is `[LookupKey]` [#d129-lookup-key]

**Decision.** The attribute that declares the key a world indexes a component by is `[LookupKey]` (it was
`[IndexKey]`); `[UniqueKey]` keeps its name. No alias is kept: `[IndexKey]` no longer compiles (CS0246, CS0234 when
qualified), and a code fix renames it to `[LookupKey]`, the `Attribute` suffix and the qualification kept. The
generated members (`world.XIndex`, `IIndexed<TKey>.Key`) and the index types do not change.

**Why.**
- **The two names were too alike.** `[IndexKey]` and `[UniqueKey]` differ in one word that does not say what
  differs: both declare an index's key. Readers took `[IndexKey]` for "the key of any index", the unique one
  included, and asked which to use.
- **The name says what the key is for.** A lookup key finds the entities that hold a value (several per key:
  `index.Find(key)`, `Lookup<T>.Find` in a pass); a unique key finds the one entity that holds it. "Lookup" is also
  what the pass parameter that reads it is called (`Lookup<T>`).

**Considered.**
- **`[Key]` back** (D100 renamed it to `[IndexKey]`): read like any key, a record's primary key included.
- **`[MultiKey]` / `[GroupKey]`:** "multi" names how many entities share a key, not what the key does; "group" is
  taken by `[Group]` and `GroupBy` (tables split by a value).
- **An `[Obsolete]` alias:** pre-1.0, as in D54, D64 and D100: the compiler finds every use and the code fix
  rewrites it.

## D130. Parallel passes cut chunks by the rows' measured cost; `ChunkSize` only overrides it [#d130-measured-chunks]

**Decision.** A parallel pass (a `[ForEach(Parallel = true)]` method, `ForEachParallel`, `ForParallel`) that sets no
`ChunkSize` cuts its chunks from the time its rows took. Each pass keeps a moving average of thread time per row,
from the runs it already times to choose between helpers and the caller alone, and from one run in 16 of a pass that
runs as one chunk; the first timed run is dropped (cold). From it: four chunks per thread, unless that makes chunks
longer than 25 µs (heavy rows: chunks of 25 µs, at most 64 per thread) or shorter than 5 µs (a short pass: chunks of
5 µs, one on the caller when the whole pass is shorter), a multiple of 64 rows. Before the first measurement the
count rule decides (four per thread, 1,024 to 16,384 rows). A pass that merges per chunk keeps 16 chunks by count
([D125](#d125-scheduler-tuning)): its chunk boundaries must not follow timing. `ChunkSize` stays as an override; a
stamping pass whose measured chunks are under 4,096 rows opens its blocks, as `ChunkSize` does
([D67](#d67-chunk-rows)).

**Why.**
- **The row count did not know the rows' cost.** A few hundred rows of microseconds each (a chunk of terrain, a path
  search) made one chunk of the 1,024-row floor and ran on one thread unless the user found `ChunkSize`; uneven rows
  (an eighth costing 64 times the rest, all in one place) left threads idle behind the chunk holding them. The cost
  is already measured (the runner times every run it samples), so the chunk size costs one division per pass.
- **Measured, BDN, two rounds, base / new, 4 threads, load 1.6 to 3.4, 0 B both** (`ChunkRowsBenchmark`, a parallel
  system per body; µs): Uneven 1,000 rows 238, 231 / 141, 142; 4,000 rows 944, 951 / 292, 293; 10,000 rows 2,116,
  2,074 / 758, 795; 100,000 rows 12,041, 12,095 / 6,280, 6,171. Expensive (1 to 1,000 rows of about 30 µs) 100 rows
  2,849, 2,824 / 1,989, 1,969; 1,000 rows 28,815, 28,532 / 8,188, 7,854. Light 4,000 rows 1.05, 1.06 / 0.88, 0.94;
  8,000 rows 2.17, 2.98 / 1.76, 1.72; 10,000 rows 3.29, 3.29 / 2.22, 2.14. Heavy (steering) 1,000,000 rows 6,077,
  7,003 / 5,296, 5,609. Level within noise: Light 1,000 rows 0.12, 0.12 / 0.13, 0.13; Light and Heavy at 100,000
  rows; Uneven 1,000,000 rows (63,502, 63,987 / 64,417, 66,965: chunks were already small enough);
  `ParallelForEachBenchmark`, `ParallelSystemsBenchmark`, `RunnerBenchmark`, `ParallelRunnerBenchmark.Runner`,
  `ForParallelBenchmark`, `WorldSimulationBenchmark`, `BattleServerBenchmark` (4,144, 3,968 / 3,924, 4,824 µs; two
  earlier rounds 3,919, 3,952 / 3,675, 3,847).
- **Short passes must not pay for it.** The first prototype cleared chunk arrays sized for the most chunks a cost can
  ask for after every call, and read the clock twice on every one-chunk run: Light 1,000 rows went from 124 to
  354 ns. Clearing only the chunks a call cut, timing one run in 16 once the cost is known and skipping the arithmetic
  for a pass shorter than 5 µs brought it to 0.13 µs. Dropping the first, cold run keeps a light pass from being cut
  into chunks it does not need and from waking the helpers for the first time on its second call (which allocates:
  `ALambdaPassAllocatesNothing`).
- **25 µs and 5 µs:** claiming a chunk, timing it and copying the job cost well under a microsecond, so a 25 µs chunk
  spends about 1 % on them; below 5 µs a chunk is mostly that overhead and the wait for a helper to wake, so a short
  pass makes fewer. 64 chunks per thread bound the chunk arrays, which the first call reserves, so a cost measured
  later never grows them.

**Considered.**
- **OpenMP's `schedule(guided)` / `auto` and TBB's `auto_partitioner`:** they split while threads are idle, from
  large chunks down to a minimum the user sets; the minimum is the unknown here. Splitting on demand would also need a
  shared queue of ranges per pass instead of one claim counter. Measuring per pass gives the minimum directly.
- **Halide's autotuning (D125's tuner):** tried chunk counts and kept the fastest; it could not go below 1,024 rows
  and gained nothing over four per thread. Measuring the time per row reaches heavy rows on the second run.
- **Static priors** (bytes per row, a vector loop or a scalar one, the generator's estimate of a method's cost): the
  measured cost replaces any guess after one run, and the first run keeps the count rule, so they would only change
  the first pass.
- **Dropping `ChunkSize`:** it stays for a pass that knows better than one run's average (rows whose cost changes
  from tick to tick). EECS054 still reports an invalid one (negative, or on a method that is not parallel); its
  description says 0 lets the runtime choose from the measured cost.

## D131. Vector loops gather other entities' fields when the method asks for it (`SimdMode.Require`) [#d131-lookup-gathers]

**Decision.** A `[ForEach]` method that reads other entities through a `Lookup<T>` (`lookup[id]`, `Read`, `Has`, at
an `EntityId` its lanes hold) gets a vector loop only with `SimdMode = SimdMode.Require`; with `SimdMode.Auto` its rows
run one by one, and EECS055 says why (Info). The loop resolves the ids of each vector with AVX2 gathers of their
records (`Lookup<T>.Resolve`: versions, rows, and the one table every live lane's entity lives in, read as managed
references, never gathered as addresses), then gathers each field the method reads from that table's pinned column
(`LookupLanes.Gather`; a 512-bit vector is two 256-bit gathers, .NET 10 has no AVX-512 gather). A vector whose
entities live in several tables, or in a table that holds `T` for some rows only (presence bits), is not resolved:
its rows run the method, before any gather, and so do the next 3, then 15, then 63 vectors without trying (a backoff
per lookup and run, reset by a vector that resolves), in one call of a row loop out of the vector loop (`__Rows`) per
span. Fields are lanes of 4 bytes (float, int, uint); the loop gathers only in loops of 4-byte lanes, and needs AVX2
(`LookupLanes.IsAccelerated`), without which every row runs the method.

**ARM64.** .NET 10 has no gather in AdvSimd (NEON); `Sve` has gathers, experimental in .NET 10, on SVE hardware
only, and not measured here. So `LookupLanes.IsAccelerated` is false there and a method reading other entities runs row by
row under every `SimdMode`, `Require` included, as on x64 without AVX2. A lane fill by scalar loads was not built:
it is the per-lane walk below without its gathers, and the walk's cost per lane is what the method's own lookup
costs. The choice is the same on every ISA: gathers only on request, and only where AVX2 runs them. The tests run
once with `DOTNET_EnableAVX2=0`, the row-by-row path ARM64 takes.

**Why on request.** The gathers win where a vector's targets share a table and lose where they spread over many
tables, and where targets live is the data's, which the generator cannot see. `SimdMode.Require` already means "this
method is a vector loop"; for a lookup it is also the author's word that targets cluster. Targets cluster when the
entities a pass looks up share their components and their group value (`[Group]`, `GroupBy`): the layout decides
what a lookup costs, as cluster pairs do for GROMACS.

| 100k | 64, a quarter removed | 1.18 / 1.15 | 1.05 / 0.99 | 1.07 / 1.01 | 1.05 / 0.94 |
| 1M | one table | 0.44 / 0.45 | 0.62 / 0.74 | 0.67 / 0.75 | 0.75 / 0.70 |
| 1M | runs into 4 tables | 0.41 / 0.44 | 0.63 / 0.66 | 0.68 / 0.67 | 0.63 / 0.68 |
| 1M | 64 tables | 1.06 / 1.01 | 0.95 / 0.93 | 1.01 / 1.05 | 1.05 / 1.00 |
| 1M | 1,000 tables | 0.98 / 1.11 | 1.03 / 1.01 | 1.00 / 1.03 | 1.05 / 1.04 |
| 1M | 64, a quarter dead | 1.00 / 1.03 | 0.98 / 1.12 | 0.98 / 1.00 | 0.93 / 1.17 |
| 1M | 64, a quarter removed | 1.14 / 1.21 | 1.06 / 1.04 | 1.10 / 1.03 | 0.98 / 1.07 |

The vector loop wins wherever a vector's targets share a table (0.41 to 0.99; the 2.59 is one round's outlier), and
loses up to 1.21 times where they spread over tables, are dead, or the table holds the component for some rows
only; at 1M rows the misses to memory hide most of the difference. The neighbors, before the gathers against with them, two rounds: `WorldSimulationBenchmark.Tick(100000)` 3.97 /
4.11 against 3.93 / 4.02 ms, `BattleServerBenchmark.Tick` 106.9 / 112.4 against 109.3 / 107.3 µs (10k) and 1,261 /
1,276 against 1,249 / 1,278 µs (100k), `MultiWorldBenchmark.TickAllWorlds` 595 / 646 against 664 / 662 µs (error
±57-121 µs): none reads a lookup. Every form allocates 0 B; the tests check every form against the method row by row
bit for bit (one table, runs, 64 and 1,000 tables, dead, recycled, null and foreign ids, a negative index, a table
without the component, presence bits, tables grown between passes; three bodies), the same exception for a read of a
missing target, 1 and 4 threads, and 0 B per frame.

**Why the spread case loses, and why no form found wins it** (Sapphire Rapids, AVX-512, .NET 10.0.13):
- **The vectors miss.** A 512-bit vector holds 16 lanes; with targets random over 64 tables, all live lanes share a
  table almost never, so every vector over such data is the row-by-row method plus the attempt, the backoff and the
  call of `__Rows`. The user's method is called, not inlined, in the row loops of both forms, and the job's
  `Execute` is not inlined into its caller either: 52 / 56 IL locals in the lookup jobs, over the JIT's 32 (the two
  copies of the loop, `Vector512` and `Vector<T>`, with their locals), so neither form gains there.
- **Resolving each lane's table costs what the method does.** A gather costs about one load per lane on this core, and
  a lane's table is a chain of loads (the record's table, its column for the component, the presence bits). A loop
  that resolves every lane in registers (the walk below) spends that chain per lane, as the method's own lookup does.
  Measured on the walk, 64 tables, bearing body, one round, at 1k and 100k rows: as built, 1.26 and 1.33 times the
  row-by-row time; the field gathers masked off, 1.28 and 0.97; the walk skipped (every lane empty), 0.55 and 0.37.
  The walk is the cost: about 2.75 µs per 1,000 rows, three quarters of the whole row-by-row pass.

**Considered.**
- **Gathers in `SimdMode.Auto`**: the table above; a pass over targets spread over many tables runs up to 1.21 times
  as slow, which the project's rule (a net win, no regression) refuses.
- **A per-lane walk across tables** (each lane's table resolved in registers, re-reading the column only when the
  table changes; the column's pinned address as a 64-bit lane, base 0, ISPC's form: two `vpgatherqd` of 4 lanes per 8;
  one table keeps 32-bit offsets from one base). Safe because unmanaged columns are pinned arrays (the POH) that live
  while their table holds them, are replaced only by structural changes inside the gate, and no structural change and
  no row move (tombstones close only when no pass runs) happens during a pass; the addresses live within one vector,
  the tables are read as managed references, managed `T` is refused. Bearing body, one round, against the method row
  by row: 0.88 / 0.85 / 1.36 / 0.97 / 1.29 / 1.49 at 1k (one table, 4 tables, 64, 1,000, dead, removed) against
  0.80 / 0.84 / 1.10 / 0.98 / 1.13 / 1.07 for the shipped form; 1.17 at 100k and 1.15 at 1M over 64 tables. A first
  version storing every lane's address to memory and loading them back ran 1.54 (one table) and 1.48 (64 tables) at 1k.
- **A micro-adaptive choice between the two forms** (Vectorwise, SIGMOD 2013): each job, per thread, times both forms
  on its runs and takes the cheaper. A moving average of every run, the other form tried every 16th: the first
  sample of the vector loop came from the JIT's first code and the job kept the rows for 1M rows in one table (0.97
  against 0.62). Rounds of 4 measured runs per form, the cheapest kept, then 64 to 1,024 runs of the winner unmeasured
  (the wait doubling while the winner and its cost hold), over the walk: two rounds against the shipped form, 1k
  rows, one field: one table 0.64 / 0.64 against 0.52 / 0.52, 64 tables 0.89 / 0.91 against 1.16 / 1.15, removed
  0.98 / 1.02 against 1.29 / 1.24; bearing, 64 tables 1.04 / 1.03 against 1.15 / 1.12; 1M rows, one table, bearing
  0.67 / 0.90 against 0.70 / 0.58. It takes back most of the spread case, never wins it with the bearing body, and
  costs the one-table case: refused.
- **An AVX-512 gather** (16 lanes, a mask register): .NET 10 exposes gathers only in `Avx2` (and Arm's `Sve`), none
  in `Avx512F` or `Avx10v1`.
- **The table check by a gather of the records' table references as addresses** (8 lanes compared in one instruction):
  about 5% faster than reading them as references in the prototype, but an address read outside a managed reference
  can be stale once a collection moves the table; a cache of such addresses tagged with the collection count
  (`GC.CollectionCount`) would need a clamp on every lane to stay memory safe, for a gain the walk's numbers bound.
- **A table id per entity the gathers read** (so a lane's table is one gather): a field of the 16-byte `EntityMeta`
  or an array beside it, which the rule on per-entity state refuses without a measured need; recorded in
  `docs/owner-review.md`.
- **Sorting or grouping the reads by target table** (a counting sort of each run's rows by table, then gathers per
  group; hand-written prototype, bit-identical): 1.37 to 2.2 times the row-by-row time with targets in 1 or 4 tables,
  4.97 to 9.0 times over 64.

**How the backoff was set** (vector against row by row at 1k / 100k / 1M, 64 tables, bearing body, two rounds):
- every vector tried, the bail after the body: 1.54 / 1.57, 1.28 / 1.31, 1.15 / 1.28;
- an unresolved vector leaves before its gathers: 1.43 / 1.44, 1.14 / 1.14, 1.28 / 1.25;
- then the next 1, 3, 7 ... 63 vectors run without trying, one by one: 1.24 / 1.22, 1.14 / 1.22, 1.12 / 1.17;
- each vector's rows through the out-of-line row loop: 1.18 / 1.10, 1.26 / 1.02, 1.18 / 1.03;
- the skipped vectors as one span per call, waits doubling: 1.11 / 1.08, 1.11 / 1.02, 1.01 / 1.01;
- waits of 3, 15, 63 (shipped): 1.13 / 1.05, 0.97 / 1.00, 1.05 / 1.04.

## D134. EECS103: a batch method's hand-written vector loop is reported with the method for one row [#d134-eecs103]

**Decision.** A batch `[ForEach]` method whose body is a vector loop written by hand, which the generator would write
from the method for one row, is reported (EECS103, Warning) with that method, and the code fix writes it. The
rewrite is read once (`HandSimd.cs`) for the analyzer and the fix: each span a `ref` (written) or `in` component,
each vector statement one statement per field of the components, each broadcast a scalar local, the casts, the
index and the scalar tail dropped. It is reported only when it is exact and gets the generator's loop: the method
for one row replaces the batch method in a copy of the compilation (the technique of `Kernel.Views`), must compile
there, and `Kernel.Vectorize` must return a loop for it under the method's own `SimdMode` and `FloatMode`.

**What qualifies.** Spans, singletons and values as parameters; a prelude of local declarations (streams through
`MemoryMarshal.Cast<C, T>`, `Cast<C, VectorN<T>>`, `Cast<T, VectorN<T>>` or `ref T r = ref Unsafe.As<C, T>(ref
MemoryMarshal.GetReference(span))`; the index and its bound; uniform values: constants, singletons, values, static
readonly fields, `Math` / `MathF`, broadcasts), also inside `if (VectorN.IsHardwareAccelerated)`; one loop, from 0 by
1 over a vector stream (`p[i]`) or by `VectorN<T>.Count` up to the lanes' length (loads `new Vector<T>(s.Slice(i))`,
`VectorN.Create(s.Slice(i[, Count]))`, `VectorN.LoadUnsafe(ref r, (nuint)i)`; stores `v.CopyTo(s.Slice(i))`,
`v.StoreUnsafe(ref r, (nuint)i)`); in it only lane-wise operations with a scalar twin (`+ - * /` of floats,
`& | ^ ~ << >> >>>` of integers, `Min`, `Max`, float `Abs`, `Sqrt`, `Floor`, `Ceiling`, `FusedMultiplyAdd`, `ConditionalSelect`
of comparisons joined by and, or and not, `AndNot`, conversions between lanes of one size); after it, a tail that
writes only elements of the spans and its own locals. Every component a stream reads has the same F fields, all of
the lane type, F a power of two no larger than the narrowest vector's lanes (the flat-lane check: lane j is field
j % F of a row). Lanes are float, double, int, uint, long and ulong (byte and short arithmetic is computed in int by
C#, so a statement per field would not compile as written).

**Left alone.** `SimdMode.Off`, `[GeneratedCode]`, a method that is no `[ForEach]` pass; shuffles and horizontal
operations (`Shuffle`, `Sum`, `Dot`, `GetElement`, `ExtractMostSignificantBits`, `Narrow`, `Widen`), the classes of
one instruction set (`X86`, `Arm`), vector constants that are not broadcasts; loads at other offsets (a stencil); the
`EntitySpan`; a call into user code in the prelude (the method for one row would call it per row: the demo's
`DragBatchSystem`); a uniform written in the loop (an accumulator across vectors); integer division and integer
`Abs` (a lane that throws in the method for one row does not in the vector); components of mixed field types, a field
count the vectors do not hold whole, a step neither 1 nor `Count`; a span the loop does not read.

**Where the plan was wrong, and why.**
- **No lambda passes.** A lambda pass takes no spans (EECS095: "write a [ForEach] method"), so no lambda body can hold
  a hand-written vector loop; v1 covers batch methods only.
- **No accumulators, integer ones included.** The method for one row of a loop that sums across vectors needs a
  `Reduce<T>` parameter and a singleton to combine into, which the fix cannot write mechanically; EECS086 already
  points a singleton accumulated row by row to `Reduce<T>`.
- **A span the loop only reads becomes `in`**, not `ref`: a `ref` it never writes would trade EECS103 for EECS025.

**Numbers.** `GeneratorBenchmark`, base and this change, two rounds (the benchmark's code has no vector code, so the
analyzer pays only the prefilter). `CompileAndAnalyze`, one namespace off: 3,143 / 2,625 ms and 2,752 / 2,870 ms; on:
3,256 / 3,206 ms and 3,604 / 3,785 ms. The direction flips between rounds inside the error (±130-490 ms); allocation is
level (531.8 / 530.3 MB, 994.7 / 993.4 MB). The rows without analyzers (`Cold`, `Edit*`, `Compile`) do not run the rule.
The rewrite is bound only for attributed methods whose bodies name a vector type.

**Considered.**
- **Reporting every vector type in a batch method**: most hand-written SIMD in the samples (VoxelServer water,
  tile stencils, byte lanes) has no plain form the generator vectorizes yet; a message without a fix that works is
  noise. Tile stencils wait for the `Cell<,>` form (v2), element loops over buffers for the inner-loop form (v3).
- **Comparing the tail with the method for one row**: the tail is dropped, not proven equal to the vector body; a
  tail that differs was a bug of the batch method already (its rows past the last vector got another result).

## D135. Generated jobs stay within the inliner's 32 IL locals; loops past it run as methods per width [#d135-inlined-locals]

**Decision.** Every generated `Execute`, and every method a runner inlines, keeps at most 32 IL locals: RyuJIT
inlines no method with more (`MAX_INL_LCLS`, "too many locals"), `AggressiveInlining` included, and a job its runner
calls instead of inlining pays a call per run and loses the runner's hoisted state. The generator does two things:
- **It writes fewer locals.** Constants, guard lanes and kept lanes are written in place instead of in locals (one
  `__lanes` text, written twice: `AllBitsSet` in loops over whole vectors, `__pass` or `__pass & mask` in the masked
  loop); a lane no write of the statement overwrites, or equal to its own destination, needs no `__t` temp, and a lane
  equal to its destination is not stored.
- **It counts them, and splits before the limit.** `Locals` counts the declarations of the job's text (plus one
  temp for a `default` struct argument). When the inline form would pass 32, each width's loop becomes an
  `AggressiveInlining` method (`__Loop512`, `__Loop`, `__MaskedLoop512`, ...) with its own locals, and `Execute`
  keeps only the dispatch.

The count is an estimate from above: release Roslyn keeps a slot per declared local (same-typed locals of disjoint
scopes do not share one) and drops some locals used once, so the real count is equal or lower. `tools/inlining.sh`
reads the JIT's inlining events of the benchmarks and reports every generated job a runner does not inline.

**Locals, before and after** (`Execute`, copy fix only → this change). Steer 40/44, Gate 40/42, Seek 40/42,
SeekParallel 40, ParallelSteer 40, Share 34/36, Step 32/34, Cycle 31/33 → every `Execute` at 30 or fewer; the split
methods hold 13 to 21 (the masked loops of Gate, Seek, Share, Step, Cycle and UpdateCell, Steer's loops), the widest
27 (SteerJob18's `__Loop512`). `tools/inlining.sh`: every generated job inlined, in the benchmarks, samples and test
corpora; the generator test `LargeJobsStayWithinTheInlinersLocals` asserts it and the split of a 16-field job.

**Machine code** (Tier1, `DOTNET_JitDisasm`, PGO off; instructions of the runner and calls to the job). Gate masked
765 with 3 `Execute` calls → 990 with none; Cycle masked 1,024 with 1 call → 1,217 with none; Seek and Share masked
inline as well (728 → 1,313, 725 → 1,440). In Gate's loop over whole vectors a literal in place is seen by the JIT:
`Max(x, -50f)` is one `vmaxps` (28 instructions, no moves) instead of `vrangeps`, two `vfixupimmps` and a broadcast.

**Numbers** (BenchmarkDotNet, default job, two rounds per pair, compared only within a round: the machine's speed
moved about 13% between sessions). Base is the commit before the copy fix ([D126](#d126-loop-shape)).
- WorldSimulation 100k: 1,091.7 / 1,183.5 µs → 1,102.1 / 1,110.7 µs; 10k: 91.8 / 92.5 → 95.5 / 96.4 µs (inside the
  error, ±5-6 µs; a short interleaved screen read 98.6 / 101.9 / 94.9 → 93.4 / 100.9 / 91.5 µs).
- BattleServer 100k: 3,239 / 3,245 → 3,114 / 3,220 µs.
- Kernel jobs at 100k: Step 21.8 / 23.4 → 18.1 / 18.9 µs, Share 220.9 / 233.4 → 191.4 / 203.6 µs, Gate 26.3 / 28.4 →
  23.3 / 22.2 µs, Seek 85.5 / 88.9 → 80.5 / 82.7 µs; at 1k Step 0.225 / 0.221 → 0.175 / 0.173 µs. The rest level inside the error.
- 0 B everywhere (single-byte or 93 B rows of the parallel and multi-world benchmarks appear on either side in one
  round: thread-pool noise).

**Considered.**
- **Splitting by temperature** (the cold branch in its own method): the width split alone brings every job under the
  limit; not needed.
- **Moving the boundary** (the runner's per-run work into the job): left to the inner-loop work that changes the
  runners; not needed to fit.
- **Literals in place in the masked and gather loops**: the JIT does not hoist out of a block a `continue` skips, so
  every vector re-broadcast them (Gate's masked loop 49 → 52 instructions, 9 broadcasts in the loop); they stay
  locals there.
- **Counting same-typed locals once**: underestimated (33 IL locals where the estimate said 31); Roslyn keeps the slots.
- **`out _` discards**: Roslyn gives each a temp; no locals saved.
- **Sharing the permutation tables in big runners**: the JIT reloads a vector constant at each use and the
  destructive permutes need a copy anyway; nothing to win.
- **The masked AVX-512 tail** (retried here once every job fits): slower, see [D126](#d126-loop-shape).

**ARM64.** The split is per width, so the `Vector128` / `Vector<T>` loop ARM64 runs is split and checked the same way
(the tests run with `DOTNET_EnableAVX=0` too). The forms that need x86 permutes still run scalar there: components of
several fields stored interleaved (`Interleaved.IsAccelerated` needs AVX2 or AVX-512), `Lookup<T>` gathers (AVX2), and
the AVX-512 permutes of wide loops.
