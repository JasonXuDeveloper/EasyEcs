Which C# ECS is fastest depends on the work. EasyEcs is measured against Friflo.Engine.ECS, Arch and DefaultEcs in
<FeatureCount k="total" /> head-to-head benchmarks: it is faster in <FeatureCount k="ahead" />, within the
measurement error in <FeatureCount k="even" /> and slower in <FeatureCount k="slower" />. The biggest leads are in
the work a server does in bulk or now and then (saving, bulk changes, spawning, value queries, hierarchies, indexes,
change detection); plain iteration over dense columns is close, because there the loop is bound by memory, not by the
library. This page lists every result, sorted by lead, losses included and explained.

## How changes are made [#how-changes-are-made]

The biggest difference is not speed but how a system changes the world. Friflo, Arch and DefaultEcs forbid (or do
not guard) structural changes while a query iterates, so a system records them in a command buffer that is played
back later: until then the entity still has its old components, and the order of effects depends on when buffers are
flushed. EasyEcs applies every change at once, also in the middle of a pass over the same table, and still visits
each entity at most once:

```csharp title="DeathSystem.cs"
public class DeathSystem : EcsSystem
{
    [ForEach, Without<Dead>]
    static void Die(Entity unit, in Health hp)
    {
        if (hp.Value <= 0) unit.SetDead();   // applied now: later systems already see the corpse
    }
}
```

The ports follow each library's model (Friflo and Arch play their command buffer back after every system that
records changes), so the measured worlds behave the same. How EasyEcs makes immediate changes cheap is on
[Why EasyEcs is fast](/en/docs/why-fast#structural-changes).

## The same server tick [#the-same-server-tick]

A whole tick mixes every kind of work, so it shows what a real server gets, and it is closer than the single
features: most of its time is iteration, where the loop is bound by memory. `EcsComparisonBenchmark` runs the headline world of EasyEcs (30% players, 70% NPCs, projectiles; movement, area of
interest, combat, status effects, death, respawn, shooting) in each library, single-threaded. The EasyEcs side is
`benchmarks/EasyEcs.Benchmark/WorldSimulation.cs` compiled unchanged; the others are `ArchSimulation.cs`,
`FrifloSimulation.cs` and `DefaultEcsSimulation.cs`. Setup warms every world up for 200 ticks and checks that its
counters (hits, deaths, spawns, area changes, entities) match an EasyEcs reference run within 5%: they cannot match
exactly, because entity ids feed the random rolls and each library recycles ids in its own order.

## Operations [#operations]

`OperationBenchmark` isolates single operations of that world (100,000 entities), EasyEcs against Friflo, the closest
peer on the tick. Every operation leaves the world as it found it.

<BenchChart bench="OperationBenchmark" title="Single operations, 100,000 entities: EasyEcs and Friflo.Engine.ECS" />

- **Toggle** (stun 5% of the fighters, then recover them) is where presence bits pay: EasyEcs flips a bit and the
  entity keeps its row; Friflo moves it to another archetype and back through its command buffer.
- **Instantiate** spawns 5,000 NPCs of six components: EasyEcs copies a `Prefab`'s row into consecutive rows at once,
  Friflo clones an entity of the store one by one (`CloneEntity`).
- **Entity**: a per-entity job receives a handle built from the row's 8-byte `EntityId`; Friflo's `ForEachEntity`
  calls a delegate per entity.
- **Ties**: two- and three-component iteration (`Iterate2`, `Iterate3`) and batched entity access (`EntityBatch`)
  come out even. Both libraries walk dense arrays there, and the loop is bound by memory, not by the library.

## Change tracking [#change-tracking]

`ChangeTrackingComparison`: 100,000 entities, 10 (a quiet tick) or 1,000 of them get a new health per tick, and a
system copies the changed healths into a replica. Each library uses its built-in feature where it has one (EasyEcs
`[Changed<T>]`, DefaultEcs `WhenChanged<T>()` fed by `NotifyChanged<T>()`), else a scan comparing values or a dirty
tag added on write and removed after the copy.

`[Changed<T>]` leads at both rates and needs no code at the write site: a write through `ref` is the change. A

## Removal detection [#removal-detection]

`RemovalComparison`: 100,000 entities with a buff; per tick 10 or 1,000 buffs expire and the ones that expired the

collecting the ids, Arch a `Lost` tag added next to each removal. Setup checks that every removal is sent exactly

## Parallel work [#parallel]

`ParallelQueryComparison`: 100,000 agents steer towards the nearest of 16 waypoints on all cores. EasyEcs uses
`[ForEach(Parallel = true)]`, Friflo a `QueryJob` with a `ParallelJobRunner`, Arch `InlineParallelQuery` on its job
scheduler, DefaultEcs an `AEntitySetSystem` with a `DefaultParallelRunner`.

<BenchChart bench="ParallelQueryComparison" title="Steer 100,000 agents on all cores" />

**EasyEcs does not win this one**: Arch and Friflo (<BenchValue k="parallelQuery.friflo" />) come out ahead of
EasyEcs (<BenchValue k="parallelQuery.easyecs" />), within this run's error. Their runners keep worker threads of
their own; EasyEcs runs on the calling thread plus thread-pool helpers that it wakes only while they pay. Measured back to back, as BenchmarkDotNet
does, dedicated workers win; in a server tick where passes are milliseconds apart, a dedicated spinning crew measured
worse in tail latency and CPU per tick ([D22](/en/docs/decisions)), so EasyEcs keeps the thread pool.

`ParallelSystemsComparison`: four independent systems over 100,000 entities, sequential and in parallel. DefaultEcs
is the only peer that schedules whole systems in parallel (`ParallelSystem<T>`); EasyEcs forms the stage from the
systems' generated access, so you cannot put two conflicting systems in one by mistake.

## Their features in EasyEcs [#their-features-in-easyecs]

What the other libraries offer and how EasyEcs does the same job. Some are built in under another name; some are
done with data instead of a mechanism (EasyEcs has no events or command buffers on purpose); a few are not offered.
The [battle server example](/en/docs/example) shows most of them.

| Their feature | In | EasyEcs |
| --- | --- | --- |
| Command buffer for changes during a query | Friflo, Arch, DefaultEcs | not needed: changes apply at once, also mid-pass |
| Thread-safe command buffer | Friflo | a queue you own, drained by a system on the world's thread ([threading](/en/docs/guide/threading)) |
| Component added / removed / set events | Friflo, Arch, DefaultEcs | state changes are data: a component the next system queries |
| `WhenChanged` sets and `NotifyChanged` | DefaultEcs | `[Changed<T>]`, `QueryFilter.Changed<T>(since)`: a `ref` write is the change |
| `WhenRemoved` sets, removal events | DefaultEcs, Friflo, Arch | `[Removed<T>]`, `QueryFilter.Removed<T>(since)` |
| Prefab entities, cloning | Friflo, DefaultEcs | `Prefab` and `world.Instantiate`; `entity.Clone()` for a living entity |
| Tags | Friflo | empty components; removing one flips a bit |
| Unique entity, world components | Friflo, DefaultEcs | singletons, as `[ForEach]` parameters or a `SingletonRef<T>` |
| Enable / disable an entity | Friflo, DefaultEcs | a tag (`[Without<Asleep>]`), or `Disable<T>()` for one component |
| Systems, groups, ordering | Friflo, DefaultEcs, Arch.Extended | `EcsSystem`, `[UpdateBefore<T>]` / `[UpdateAfter<T>]`, `ISystemGroup`, `UpdateInterval` |
| Struct query jobs, chunk iteration | Arch, Friflo | `IForEach`, `IForEachEntity`, `IForEachBatch`; batch `[ForEach]` methods |
| Parallel query | Friflo, Arch, DefaultEcs | `[ForEach(Parallel = true)]`, `ForEachParallel`, `ForEachEntityParallel` |
| Parallel systems | DefaultEcs | `WorldOptions.ParallelSystems` |
| Bulk changes | Friflo, Arch | `SetAll`, `RemoveAll`, `DisableAll`, `EnableAll`, `CreateEntities`, `DestroyAll` |
| Indexed components | Friflo, DefaultEcs | `IIndexed<TKey>`: `Find`, `TryFind`, `Count`, ordered `Range` |
| Links and relations | Friflo | an indexed `EntityId`, or `IRelation` for many targets |
| Parent / child hierarchy | Friflo | `ChildOf`, `world.Children`, cascading destroy; no transform propagation |
| Serialization | Friflo (JSON), DefaultEcs (text, binary) | binary `Save` / `Load`, plus in-memory `Capture` / `Restore` |
| System performance monitor | Friflo | `WorldOptions.MeasureSystems`, `system.Stats` |
| Shared components (`SetSameAs`) | DefaultEcs | not built in: keep shared data in a singleton and an id into it |
| Unity, older runtimes | all three | not offered: net10.0 only |

## When to pick which library [#which-one-to-pick]

| Pick | When |
| --- | --- |
| **EasyEcs** | A .NET 10 server, Godot game or simulation where state flips constantly and you want changes applied where they are decided, systems generated and checked at compile time, change and removal tracking, prefabs, indexes, relations, saves and snapshots built in, and nothing allocated per tick. |
| **Friflo.Engine.ECS** | You need Unity or older runtimes, events, or JSON serialization, accept command buffers for changes during iteration, and want a fast general-purpose ECS. |
| **Arch** | You need Unity or older runtimes and a small core with chunk-based storage, adding systems and generators from Arch.Extended. |
| **DefaultEcs** | You need netstandard down to 1.1, reactive sets and built-in serializers, and the world is small enough that its per-tick allocations do not matter. |
